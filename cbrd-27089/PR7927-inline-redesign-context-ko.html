문제는 소유권, 설계 쟁점은 중간 행의 표현입니다

원래 버그는 파티션 목적지가 결정되기 전에 root heap에 OOS 값을 기록하고, 행은 child heap에 저장하면서 소유 heap이 달라지는 문제입니다. PR #7927은 목적지를 선택한 뒤 해당 heap의 OOS 파일에 값을 기록하도록 순서를 바꿉니다. [S9][S2]

리뷰의 재설계 제안도 같은 소유권 목표를 따릅니다. 차이는 OOS 체인을 언제 기록하는가에 더해, 그 전에 값을 어떤 메모리 표현으로 유지하는가에 있습니다. 현재 방식은 먼저 compact 행과 보관 payload를 만들고, 제안 방식은 전체 인라인 행을 유지하다가 뒤에서 값을 분리합니다. [S4][S5]

이미 인라인 행을 받는 client copy-area 경로는 현재 설계에서도 목적지를 먼저 선택하고 필요한 변환을 수행합니다. 모든 입력이 같은 준비 순서를 따른다고 가정하면 실제 설계보다 단순하게 비교하게 됩니다. [S4]

이 구분 때문에 현재 PR이 이미 올바른 목적지에 기록한다는 사실과, 표현을 바꿔 더 단순하게 만들 수 있다는 제안은 동시에 성립합니다. 재설계의 이득은 소유권 버그 수정과 별도로 입증해야 합니다.

기존 POC는 무엇을 입증했습니까

POC는 일반 SQL INSERT/UPDATE의 동기 호출 범위에서, 새 행 소유 객체 없이 전체 인라인 RECDES로 목적지를 선택하고 OOS를 뒤늦게 기록하는 구현이 가능함을 보였습니다. 일반 테이블, 부모 경유 INSERT, 자식 직접 INSERT, 자식 간 이동 UPDATE와 실패 문장의 부분 기록 롤백을 확인했습니다. [S1]

이후에는 compact 행과 owner를 유지하는 설계를 선택했습니다

10월 7일 승인 문서는 heap_pending_record가 compact 행과 선택된 payload를 함께 소유하고, reader에는 이 owner를 빌려주는 구조를 명시합니다. 임시 stub에는 메모리 주소 대신 owner 내부 payload 번호를 넣고, 목적지가 결정되면 같은 24바이트 자리에 실제 OOS 참조를 덮어씁니다. [S4]

이 선택은 reader에 owner를 전달하는 복잡성을 받아들이는 대신, 이미 만든 compact 행을 재사용하고 finalization에서 행 전체를 다시 만들지 않는 계약을 유지합니다. 인터뷰에도 compact 행 재사용, 제자리 교체, 공통 memory/disk 접근을 유지하겠다는 사용자 결정이 남아 있습니다. [S3]

재설계를 다시 평가할 때 비교해야 할 비용
현재 방식이 부담하는 것전체 인라인 대안에서 확인할 것
reader·routing·중복 키 경로의 owner 인자, pending 값 접근과 수명 관리같은 경로를 일반 인라인 reader로 처리했을 때 실제로 없어지는 인터페이스와 남는 예외
선택된 payload의 별도 보관과 loader queue의 retained-byte 계산큰 연속 버퍼, 확장·재배치, queue에 유지되는 전체 행의 peak 메모리
이미 준비한 compact 행의 stub만 제자리 교체인라인 바이트 이동, VOT 재작성, MVCC 헤더·representation 변경과의 결합
현재 producer별 finalization·rollback·publication 순서bulk 선행 페이지 fix, UPDATE 인덱스·복제 로그, 이미 OOS가 있는 복제 입력의 예외

리뷰의 단순화 가설에는 검토 가치가 있습니다. 다만 payload 총량이 비슷하다는 직관으로 연속 버퍼 확장·복사·queue peak까지 같다고 결론 낼 수는 없습니다. 반대로 기존 기록만으로 전체 인라인 방식이 더 느리다고 판정할 근거도 없습니다. POC가 남긴 비교 미실시 항목을 실제 측정으로 채워야 합니다. [S1]

기존 POC의 단순화를 전체 PR의 단순화로 계산하면 안 되는 이유

POC는 짧게 살아 있는 동기 호출에서 attrinfo를 빌려 썼습니다. loader는 DB_VALUE를 정리한 뒤에도 행을 queue에 보관하므로 그 수명을 별도로 해결해야 합니다. 복제 입력은 이미 완성된 OOS stub을 가질 수 있고, REPLACE/ODKU는 실제 기록 전의 probe 단계가 있습니다.

기존 보고서도 지원 범위를 줄여 짧아진 코드를 전체 설계의 우월성으로 계산하지 말라고 명시했습니다. 이 경로들을 같은 계약으로 연결한 뒤 코드·메모리·실패 처리를 다시 비교하는 것이 다음 평가입니다. [S1]
