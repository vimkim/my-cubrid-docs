# OOS 큰 값 조회의 지연 증가 원인과 개선 방향

실측·개정일: 2026-10-28, Asia/Seoul. 대상: CUBRID PR #7990의 고정 revision 비교.
관련 이슈: [CBRD-27788](https://jira.cubrid.org/browse/CBRD-27788), 후속 개선 검토 [CBRD-27791](https://jira.cubrid.org/browse/CBRD-27791).

## Abstract

OOS는 큰 컬럼 값을 행 밖에 저장하여 작은 컬럼만 읽는 조회의 비용을 줄인다.
그러나 큰 값의 내용까지 필요한 조회에서는 별도 페이지를 찾아 읽는 비용이 발생한다.
본 보고서는 100,000행의 큰 컬럼 내용을 비교하는 쿼리가 OS 파일 캐시 해제 요청 조건에서
기준 엔진 2.32초, OOS 엔진 5.67초로 약 2.44배 느려진 현상을 분석한다.

OOS의 CPU 사용 시간과 페이지 읽기 횟수는 증가하지 않았지만, 파일 읽기 대기는 늘었다.
기록한 파일 읽기를 별도 프로그램에서 실행해도 지연 차이가 재현됐으며,
같은 데이터를 파일 위치순으로 읽고 인접 요청을 합치면 OOS 재생 시간이 4.396초에서 1.445초로 줄었다.
이 대조는 해당 입력에서 읽기 순서와 요청 방식이 지연에 영향을 준다는 근거다.

개선 후보는 제한된 행 묶음의 읽기 순서 조정, 필요한 페이지의 선행 읽기, 조건부 요청 병합이다.
먼저 제한된 범위에서 읽기 순서를 바꾸는 시제품을 실제 SQL로 검증할 것을 제안한다.
파일 읽기 재생의 시간 단축은 실제 엔진 개선율을 뜻하지 않으며,
최종 해결 방식은 정확성, 실행 시간, 메모리와 추가 읽기 비용을 함께 측정해 결정해야 한다.

## 1. Introduction — 분석 목적

OOS(Out-of-row Overflow Storage)는 큰 컬럼 값을 별도 페이지에 저장하고, 행에는 그 위치를 가리키는 참조를 둔다.
작은 컬럼만 필요한 조회는 큰 값을 가져오지 않아도 된다.
반대로 큰 컬럼의 내용을 비교하거나 집계하는 조회는 행에서 얻은 참조를 따라 큰 값을 읽어야 한다.

[전체 SELECT 실측](CBRD-27788-oos-select-performance_dcbf09e_codex.md)에서는 이 이득과 비용이 함께 나타났다.
특히 기존 overflow 저장을 사용하는 입력에서 큰 컬럼 하나의 내용을 비교하는 Q4가,
OS 파일 캐시 해제 요청 후 OOS에서 더 오래 걸렸다.
읽은 양은 줄었는데 실행 시간은 늘었다는 점이 원인 분석의 출발점이다.

본 보고서의 목적은 어떤 조건에서 무엇이 느려졌는지 규정하고, 지연의 원인을 대조 실험으로 확인하며,
그 근거로 검토할 수 있는 해결 후보를 비교하는 것이다.
실제 SQL의 성능 관측, 파일 읽기만 따로 실행한 대조, 아직 구현하지 않은 개선안을 구분한다.

## 2. Experimental Setup — 비교 대상과 측정 방법

### 2.1 비교 엔진과 입력

비교 대상은 CUBRID/CUBRID의 기준 revision 4781495f01523a3ecc5891e3377ad62cf876a1cd와
OOS revision dcbf09e4f7fd02ff9c8fc6493ec8887fc2919d67이다.
각각의 독립 설치와 DB를 사용했으며, 측정 엔진의 소스 수정·재빌드·데이터 재배치는 하지 않았다.
GCC 11.5.0/O2, 16KiB DB 페이지, 512MiB 데이터 버퍼, Linux/XFS/NVMe 조건을 유지했다.

대상 테이블은 100,000행이며, 기준 엔진에서는 평균 22,016B의 행이 기존 overflow 저장을 사용한다.
OOS 엔진에서는 행의 기본 저장 공간인 heap의 평균 행 길이가 4,040B이고, 큰 값은 별도로 저장된다.
Q4는 7,000B짜리 컬럼 cold_1의 전체 내용을 원본과 비교해 일치하는 행 수를 센다.
값의 길이만 확인하는 조회가 아니며, 정답은 100,000이다. 정확한 SQL과 설정은 부록에 보존했다.

### 2.2 캐시 조건의 의미

여기서 **OS 파일 캐시**는 Linux가 파일에서 읽은 내용을 메모리에 보관해 재사용하는 기능이다.
CUBRID 서버가 DB 페이지를 보관하는 **데이터 버퍼**와 구분한다.
DB 서버를 재시작하면 이전 서버의 데이터 버퍼는 사라지지만, OS 파일 캐시에는 DB 파일 내용이 남을 수 있다.
따라서 단순한 DB 재시작을 저장장치에서 다시 읽는 조건과 같은 뜻으로 사용할 수 없다.

본 진단에서는 서버를 정지한 뒤 실험용 DB의 데이터 파일에 기록을 반영하고,
그 파일의 OS 캐시를 해제하도록 요청했다.
사용한 API는 fsync와 POSIX_FADV_DONTNEED이며, fincore로 파일 내용이 메모리에 남은 양을 확인한 뒤 서버를 시작했다.
대상은 작업 전용 DB 파일에 한정했고, SSD 내부 캐시는 초기화하지 않았다.
캐시의 의미와 해제 요청의 성격은 [Linux 커널 문서](https://docs.kernel.org/admin-guide/mm/concepts.html#page-cache)와
[Linux API 문서](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html)에 따른다.

### 2.3 관측과 대조 방법

먼저 실제 엔진에서 Q4를 실행하여 전체 경과 시간, 서버 CPU 시간, 엔진 페이지 읽기와 스레드 대기를 관측했다.
이어 별도 실행에서 파일의 읽기 위치·크기·순서를 기록했다.
추적 도구가 실행 시간에 영향을 주므로, 추적 중 걸린 시간을 원래 SQL의 성능 수치로 사용하지 않았다.

읽기 순서의 영향을 확인할 때는 DB 서버를 정지하고, 별도 프로그램이 기록된 파일 위치를 읽도록 했다.
이 실험을 **파일 읽기 재생**이라고 부른다.
재생 프로그램은 SQL을 처리하지 않으며, 요청의 순서와 묶음을 바꿔 비교한다.
주요 SQL 조건과 재생 조건은 각각 3회 반복했고, 아래 표는 중앙값이다.
원진단은 Work Item 536의 기록이며, 본 개정에서 새 엔진 성능을 측정한 것은 아니다.

## 3. Results — 무엇이 느려졌는가

**OS 파일 캐시 해제 요청 후, 큰 컬럼 하나의 내용을 모든 행에서 비교하는 Q4가 느려졌다.**
기준 엔진과 OOS 엔진의 차이는 약 3.35초였다.
같은 입력·쿼리·캐시 조건에서 얻은 실제 엔진 실행 결과는 다음과 같다.

| 실제 SQL에서 관측한 값 | 기준 엔진 | OOS 엔진 |
| --- | ---: | ---: |
| SQL 실행을 포함한 전체 경과 시간 | 2.32초 | 5.67초 |
| 전체 경과 시간 범위 | 2.29–2.33초 | 5.67–5.74초 |
| 서버 CPU 사용 시간 | 2,271.41ms | 2,208.35ms |
| 엔진의 DB 페이지 읽기 횟수 | 200,087회 | 133,339회 |

OOS는 CPU를 더 오래 사용하거나 페이지를 더 많이 읽어서 느려진 양상을 보이지 않았다.
또한 이 결과는 모든 큰 값 조회의 성능 방향을 대표하지 않는다.
2026-10-27 전체 실측에서 같은 overflow 입력의 Q4를 먼저 한 번 실행하고 다시 측정한 warm 조건은
기준 1.33초, OOS 1.10초였다.
이 값은 앞 표와 별도의 캐시 조건에서 얻은 기록이며, 두 결과를 섞어 하나의 개선율로 해석하지 않는다.

## 4. Discussion — 왜 느려졌는가

### 4.1 추가 지연은 파일 읽기 대기에 집중됐다

서버 CPU 시간은 비슷했지만 전체 경과 시간은 크게 늘었다.
스레드 관측에서는 Linux의 파일 페이지 읽기 경로에서 기다리는 표본이 증가했다.
CPU를 배정받기 위한 대기만으로 약 3.35초의 차이를 설명할 근거는 없었다.
이 결과를 바탕으로 계산량보다 파일 읽기 경로를 조사했다.

CPU 시간과 전체 경과 시간의 차이를 그대로 특정 종류의 I/O 대기 시간으로 계산한 것은 아니다.
대기의 위치를 관측하고, 다음 절의 읽기 기록과 대조 실험을 함께 사용해 원인을 판단했다.

### 4.2 파일을 읽는 순서의 연속성이 크게 달라졌다

두 엔진 모두 한 번에 DB 페이지 하나인 16KiB를 요청했다.
기준 엔진에서 바로 앞 요청의 다음 파일 위치를 이어 읽은 비율은 99.95%였고, OOS에서는 1.01%였다.
파일별 이전 위치보다 뒤로 돌아간 읽기도 기준 43회에서 OOS 32,585회로 늘었다.

이번 입력에서는 OOS가 heap의 행과 별도 큰 값의 페이지를 따라 읽으며 파일의 여러 위치를 방문했다.
Linux의 미리 읽기와 장치의 요청 처리 효과는 읽는 위치·순서에 따라 달라질 수 있다.
따라서 전체 요청량이 적다는 사실만으로 읽기 대기까지 짧아진다고 예상할 수 없다.
다만 이 기록만으로 인과관계가 확정되는 것은 아니므로, 같은 데이터를 다른 순서로 읽는 대조를 수행했다.

### 4.3 읽기 순서와 요청 방식을 바꾸면 지연이 줄었다

이 실험의 입력은 **Q4 실행을 추적해 얻은 쿼리 스레드의 DB 파일 읽기 요청 목록**이다.
각 요청에는 파일, 파일 안의 시작 바이트 위치, 읽을 크기가 있다.
Q4 실행 중 이 목록을 기록한 뒤 DB 서버를 정지하고, 별도 Python 프로그램이 같은 파일의 같은 위치를 읽게 했다.
표에서 OOS는 이 목록을 만든 엔진을 뜻한다. 목록에는 heap과 OOS 페이지를 포함한 작업 DB 데이터 파일 읽기가 들어 있다.

세 방식의 차이를 같은 파일의 네 페이지로 설명하면 다음과 같다.
아래 페이지 번호는 설명용 예시이며, 각 페이지는 16KiB다. 실제 측정 요청의 개수와 주소는 이 예시와 다르다.

| 재생 방식 | 별도 프로그램이 실행하는 읽기 | 읽기 요청 수 | 총 요청 바이트 |
| --- | --- | ---: | ---: |
| 원래 순서 | 103번 → 101번 → 102번 → 205번을 각각 16KiB씩 읽음 | 4회 | 64KiB |
| 파일 위치순 정렬 | 101번 → 102번 → 103번 → 205번을 각각 16KiB씩 읽음 | 4회 | 64KiB |
| 정렬 후 인접 요청 병합 | 붙어 있는 101~103번을 한 번에 48KiB 읽고, 205번을 따로 16KiB 읽음 | 2회 | 64KiB |

**정렬한 것은 메모리에 있는 읽기 요청 목록이다.** DB 파일의 데이터 배치는 그대로 유지했다.
여러 파일의 요청이 있으면 같은 파일끼리 묶고 각 파일 안에서 시작 위치순으로 정렬했다.
정렬만 한 경우에는 요청 하나당 16KiB를 읽는 호출을 그대로 유지했다.
병합한 경우에는 같은 파일에서 바로 맞닿은 구간만 한 번의 호출로 읽되, 한 요청을 최대 1MiB로 제한했다.
예시의 104~204번처럼 원래 목록에 없던 중간 페이지는 이 방식으로 읽지 않는다.

원래 요청 순서를 그대로 재생했을 때 기준은 1.102초, OOS는 4.396초였다.
SQL 처리가 없는 실험에서도 약 3.29초의 차이가 남았다.
실제 OOS 요청 목록에 위 세 방식을 적용한 결과는 다음과 같다.
세 방식 모두 프로그램의 총 요청 바이트는 2,083.45MiB로 같았다.

| OOS 엔진의 DB 파일 읽기 재생 | 유지한 조건과 바꾼 조건 | 읽기 요청 수 | 시간 |
| --- | --- | ---: | ---: |
| 원래 순서 | 기록한 파일·위치·크기·순서를 유지 | 133,341회 | 4.396초 |
| 파일 위치순 정렬 | 파일·위치·크기·횟수를 유지하고 순서만 변경 | 133,341회 | 2.825초 |
| 정렬 후 인접 요청 병합 | 필요한 페이지와 총 요청 바이트를 유지하고 붙어 있는 구간을 한 번에 요청 | 100,522회 | 1.445초 |

각 조건을 실행하기 전에 대상 파일의 OS 캐시 해제를 요청하고 남은 양을 확인했다.
실행 순서를 교대하며 조건별 3회 측정한 중앙값이다.
표의 시간은 **미리 준비한 목록을 따라 파일을 읽는 반복문**에 걸린 시간이며,
요청 목록 수집·정렬·병합, 파일 열기와 사전 캐시 해제 시간은 포함하지 않는다.
원래 순서 재생도 기록된 주소 순서대로 차례로 읽는 것이며, 원래 SQL의 계산이나 요청 사이의 시간 간격을 재현하지 않는다.

따라서 해당 입력에서는 **읽기 순서와 요청 방식이 지연을 늘리는 데 영향을 주었다**고 판단한다.
마지막 방식은 프로그램의 총 요청 바이트가 같았지만 OS의 저장장치 읽기량은 오히려 늘었다.
읽기 바이트 감소, 요청 횟수 감소, 실행 시간 감소는 서로 같은 지표가 아니다.

이 대조는 전체 읽기 기록을 확보한 뒤 수행했다.
실제 엔진은 아직 방문하지 않은 행의 큰 값 위치를 모두 알고 있지 않으므로,
이 결과를 그대로 엔진의 실행 방식으로 옮길 수는 없다.

### 4.4 OS의 미리 읽기만으로 원인을 설명할 수는 없다

Linux는 앞으로 필요할 것으로 예상하는 파일 내용을 미리 읽을 수 있다. 이 기능이 readahead다.
이를 끄는 설정으로 대조했을 때 실제 SQL은 기준 2.32초에서 5.69초,
OOS 5.67초에서 8.73초로 양쪽 모두 느려졌다.
미리 읽기를 끈 상태의 재생에서도 OOS의 원래 순서 7.141초와 정렬 4.158초 사이에 차이가 남았다.

따라서 미리 읽기를 끄는 설정을 해결책으로 채택할 근거는 없다.
읽기 패턴의 영향은 확인했지만, OS 미리 읽기·장치 내부 캐시·요청 처리 각각의 기여율은 분리하지 않았다.

## 5. Potential Solutions — 해결 방식은 무엇이 있을까

### 5.1 제한된 행 묶음에서 읽는 순서를 조정한다

첫 번째 후보는 몇 개 행에서 필요한 큰 값의 참조를 모은 뒤, 파일 위치가 가까운 순서로 읽는 것이다.
이를 batch read의 한 형태로 검토할 수 있다.
읽은 값이 원래 어느 행과 컬럼에 속하는지 연결해 두고, 한 번에 모을 행·페이지·바이트 수를 제한한다.
기존의 페이지 읽기와 값 검증 경로를 유지하면서 순서 변경의 효과를 먼저 확인하는 방식이다.

[후속 재생 분석](../CBRD-27791/CBRD-27791-oos-batch-read-analysis_dcbf09e_codex.md)은
전체 기록 대신 제한된 구간 안에서만 순서를 바꾸는 모델도 비교했다.
heap 페이지 읽기 64개를 기준으로 기록을 나누고, 각 묶음 안에서 순서를 바꿨을 때도 재생 시간이 줄었다.
구체적인 비교는 5.3절의 표에 제시한다.
묶음의 기준은 기록에 나타난 페이지 읽기이며, 실제 엔진의 64행 batch를 구현한 것은 아니다.

이 후보는 순서 변경의 효과를 직접 시험하기 좋다.
반면 여러 행과 참조를 보관하는 메모리가 필요하고, 충분한 요청이 모일 때까지 첫 결과가 늦어질 수 있다.
아직 보지 않은 행의 참조를 얻는 비용과 모아 둔 값의 유효성을 실제 엔진에서 검증해야 한다.

### 5.2 필요한 페이지를 먼저 읽도록 힌트를 전달한다

두 번째 후보는 앞으로 사용할 큰 값의 페이지 위치를 페이지 버퍼에 먼저 알려 주는 것이다.
값을 실제로 사용하는 시점에는 기존 경로로 읽고 검증한다.
필요한 데이터가 미리 준비된다면, 값이 필요한 순간의 파일 읽기 대기를 줄일 가능성이 있다.

이 방식은 여러 값의 내용을 전부 미리 보관하지 않고도 검토할 수 있다.
그러나 결국 사용하지 않을 페이지를 읽거나, 현재 유용한 캐시 내용을 밀어낼 수 있다.
앞으로 필요한 페이지를 얼마나 정확히 예측할 수 있는지와 추가 I/O를 함께 측정해야 한다.
본 진단은 이 후보를 구현하거나 그 SQL 성능을 측정하지 않았다.

### 5.3 인접 요청을 합치되 추가 읽기의 비용을 제한한다

세 번째 후보는 파일에서 붙어 있는 구간의 읽기를 한 요청으로 합치는 것이다.
더 큰 구간으로 묶기 위해 원래 필요하지 않았던 중간 페이지까지 읽는 방법도 생각할 수 있다.
후자는 요청 수를 줄이는 대신 읽는 바이트를 늘리는 선택이다.

요청 병합의 효과는 묶는 범위에 따라 달랐다.
다음은 앞서 설명한 제한된 묶음을 사용한 후속 재생의 3회 중앙값이다.
4.3절의 전체 기록 정렬 대조와는 별도의 반복에서 얻었으며, 실제 SQL의 시간도 아니다.

| 후속 파일 읽기 재생 | 시간 | 원래 순서 대비 총 요청 바이트 변화 |
| --- | ---: | ---: |
| 원래 순서 | 4.413초 | 0% |
| 묶음 안에서 파일 위치순 정렬 | 3.449초 | 0% |
| 정렬 후 인접 요청 병합 | 3.974초 | 0% |
| 정렬 후 중간 페이지까지 읽어 병합 | 1.965초 | +72.4% |

순서만 바꾸면 약 21.8% 짧아졌지만, 인접 요청 병합을 추가하면 정렬만 했을 때보다 느렸다.
중간 페이지까지 읽는 방식은 시간이 더 짧아진 만큼 추가 읽기의 비용도 평가해야 한다.
따라서 요청을 합치면 항상 유리하다거나 가장 짧은 재생 시간을 제품 목표로 삼을 수는 없다.

본 보고서는 먼저 5.1의 순서 변경을 실제 엔진에서 검증하고, 5.2의 선행 읽기 후보와 비교할 것을 제안한다.
요청 병합은 별도의 이득이 확인될 때 검토한다.
최종 판단에는 큰 값 조회 시간뿐 아니라 작은 컬럼 조회의 이득, 조회 정답,
최대 메모리, 첫 결과 지연, 추가 읽기량이 포함돼야 한다.
구체적인 구현 후보와 검증 순서는 [후속 구현·검증 계획](../CBRD-27791/CBRD-27791-oos-batch-read-plan_dcbf09e_codex.md)에 정리돼 있다.

## 6. Conclusion — 결론

이번 비교에서 느려진 것은 OS 파일 캐시 해제 요청 후 기존 overflow 입력의 큰 컬럼 내용을 읽는 Q4다.
OOS는 기준보다 적은 페이지를 읽고도 약 2.44배 오래 걸렸다.
스레드 관측과 파일 읽기 재생 대조는, 해당 입력에서 불연속적인 읽기 순서와 요청 방식이
파일 읽기 대기를 늘리는 데 영향을 주었음을 뒷받침한다.

실제 해결을 위해서는 필요한 읽기를 제한된 범위로 모아 순서를 조정하거나, 페이지를 먼저 준비하는 방식을 검토할 수 있다.
다만 본 보고서가 확인한 것은 지연의 원인과 개선 후보를 시험할 근거다.
엔진 수정 후 SQL이 빨라졌다는 결론은 아직 내릴 수 없다.
후속 작업은 작은 컬럼 조회의 이득과 정확성을 유지하면서 큰 값 조회의 실제 대기를 줄일 수 있는지 검증하는 것이다.

## 7. Limitations — 한계

- **입력과 반복 수**: 주요 원인 진단은 특정 100,000행 입력의 Q4와 엔진별 3회 반복에 한정된다.
  여러 조각에 걸친 큰 값, 다른 데이터 분포·규모·동시 사용자 수의 성능을 대표하지 않는다.
  중앙값과 범위는 보존했지만 통계적 유의성이나 신뢰구간을 검증한 결과는 아니다.
- **캐시와 호스트 통제**: OS 캐시 해제 요청 대상은 작업 전용 DB 파일이다.
  서버 시작 중 일부 페이지를 다시 읽을 수 있으며, SSD 내부 캐시와 공유 호스트의 다른 작업은 통제하지 않았다.
  완전히 초기화된 저장장치의 성능으로 일반화할 수 없다.
- **원인의 세부 분해**: 읽기 기록의 주소는 파일 내 위치이며 NVMe의 물리 주소를 직접 측정한 것이 아니다.
  읽기 순서·요청 방식의 영향은 확인했지만, OS와 장치의 어느 부분이 얼마만큼 기여했는지는 미확정이다.
- **재생과 실제 구현의 차이**: 재생 도구는 기록에서 읽을 주소를 미리 안다.
  실제 엔진의 행 수집, 필요한 값 판단, 버전 확인, 메모리 관리와 결과 생성 비용은 포함하지 않는다.
  4.3절의 재생 시간에는 요청 목록을 미리 정렬·병합하는 비용도 포함하지 않는다.
  제한된 묶음의 재생도 이 차이를 완전히 없애지 못하므로, 재생 시간 단축을 SQL의 예상 개선율로 사용하지 않는다.
- **검증 범위**: 측정 revision을 고정했으며 최신 변경이나 별도 CPU 개선 PR #8299를 재검증한 결과가 아니다.
  새 batch read 구현, 동시 변경·HA·복구·전체 회귀 검증은 수행하지 않았다.
  따라서 제품 기본값이나 PR 통합의 승인 근거를 이 문서만으로 확정하지 않는다.

후보는 평균 4,040B의 heap과 OOS 값으로 나뉜다. SQL은 다음 하나로 좁혔다.

```sql
SELECT /*+ NO_MERGE RECOMPILE PARALLEL(0) NO_PARALLEL_HEAP_SCAN */ COUNT(*)
FROM perf_overflow_22000
WHERE cold_1 = CAST(REPEAT(X'AA', 7000) AS BIT VARYING);
```

정답은 100,000이며 전체 값 비교를 수행한다. 원래 다른 컬럼과 테이블도 DB 안에
보존했다. 물리 배치가 조사 대상이므로 새로운 작은 DB로 바꾸거나 행을 삭제하는
최소화는 하지 않았다. 단일 SQL과 그 쿼리 스레드의 실제 읽기로 실행 범위를 좁혔다.

실측 호스트는 Linux `5.14.0-570.30.1.el9_6.x86_64`, XFS, NVMe 볼륨이다.
서버 CPU 16–19, client 12, 관측 도구 13, 저수준 재생 16을 사용했다. NUMA node 0이며
전용 core를 예약한 것은 아니다. 서버는 한 번에 하나만 실행했다.
각 OS 파일 캐시 해제 실험 전에 정지한 작업 전용 DB의 등록된 permanent volume만 `fsync`와
`POSIX_FADV_DONTNEED`로 해제 요청하고 fincore로 확인했다. 전역 cache 초기화는 하지 않았다.

### 1. 같은 증상 재현과 대기 위치

기본 설정의 최초 두 번과 마지막 재확인 한 번을 합친 엔진별 3회 중앙값이다.
마지막 재확인에서도 기준 2.33초, OOS 5.74초로 원래 증상이 유지됐다.

| 지표 | 기준 | OOS |
| --- | ---: | ---: |
| 전체 시간 | 2.32s | 5.67s |
| 전체 시간 범위 | 2.29–2.33s | 5.67–5.74s |
| 서버 CPU task-clock | 2271.41ms | 2208.35ms |
| 서버 instructions | 7,945,429,758 | 8,063,383,998 |
| 엔진 ioread | 200,087 | 133,339 |
| trace fetch 시간 | 1,561ms | 4,944ms |

한 차례씩 별도로 실행한 `/proc/PID/task/TID` 관측에서 가장 많은 CPU를 쓴 쿼리
스레드의 runqueue 대기는 기준 0.079ms, OOS 0.805ms였다. CPU 배정을 기다린 시간은
추가 약 3.3초를 설명하지 못한다. 10ms 간격의 wchan 표본에서는
`filemap_update_page`가 기준 3회, OOS 284회 관측됐고 `futex_wait_queue`는 각각 6회·5회였다.
표본 수를 정확한 대기 시간으로 환산하지 않았다.

이 symbol은 DB latch가 아닌 Linux 파일 page cache 경로다.
[upstream Linux 5.14의 구현](https://github.com/torvalds/linux/blob/v5.14/mm/filemap.c#L2365)은
page lock을 기다리거나 파일 페이지 읽기로 이어진다. 호스트는 EL9 backport 커널이므로
이 upstream source를 호스트 binary의 정확한 line mapping으로 취급하지 않는다.

### 2. 실제 읽기 주소와 크기

각 엔진에서 단일 Q4 실행 동안 `strace`로 `pread64`를 기록했다. raw argument 모드로
buffer 내용은 출력하지 않았다. file descriptor의 경로를 전후에 확인하고, 이 작업의
DB data volume만 골랐다. 요청이 가장 많은 쿼리 스레드의 결과는 다음과 같다.

| 지표 | 기준 | OOS |
| --- | ---: | ---: |
| pread 요청 | 200,089 | 133,341 |
| 요청 크기 | 모두 16,384B | 모두 16,384B |
| 동일 파일에서 바로 다음 위치인 읽기 | 199,994 | 1,348 |
| 그 비율 / 전체 요청 | 99.95% | 1.01% |
| 파일별 이전 요청보다 뒤로 되돌아간 경우 | 43 | 32,585 |
| 연속 요청 run 최댓값 | 2,438 | 3 |
| 요청 바이트 | 3,126.39MiB | 2,083.45MiB |

OOS가 더 많은 syscall이나 더 작은 요청을 보내서 느린 것은 아니다. **요청은 적지만
연속성이 크게 나빠졌다.** OOS 요청을 파일·offset 순으로 정렬해도 99,994곳에서
16KiB를 건너뛴다. 요청한 페이지의 시작점이 32KiB 간격인 패턴이다.

```text
기준의 주된 패턴: [읽음][읽음][읽음][읽음] ...
OOS의 주소 정렬 후에도 남는 패턴: [읽음][건너뜀][읽음][건너뜀] ...
원래 OOS 순서에는 heap과 값 페이지 사이의 앞뒤 이동도 포함된다.
```

[OOS read](https://github.com/CUBRID/cubrid/blob/dcbf09e4f7fd02ff9c8fc6493ec8887fc2919d67/src/storage/oos_file.cpp#L2793)는
heap에서 얻은 참조로 값의 head page를 찾아간다. 반면
[기준 overflow read](https://github.com/CUBRID/cubrid/blob/4781495f01523a3ecc5891e3377ad62cf876a1cd/src/storage/overflow_file.c#L751)는
record의 overflow chain을 따라간다. 실제 16KiB `pread`는
[fileio_read](https://github.com/CUBRID/cubrid/blob/dcbf09e4f7fd02ff9c8fc6493ec8887fc2919d67/src/storage/file_io.c#L3945) 아래에서 수행된다.
코드만으로 물리적 연속성을 가정하지 않고 위 주소 기록으로 확인했다.

각 trace는 쿼리 스레드의 CSQL 연결 준비에 필요한 소량의 읽기도 포함한다. 따라서
SQL trace ioread와 정확히 같은 수는 아니다. 별도 background 스레드의 12개 data read는
재생에서 제외했다. strace가 실행 시간을 바꾸므로 traced 경과 시간을 원래 SQL의
성능 수치로 사용하지 않았다.

### 3. 동일한 읽기 집합의 순서·요청 크기 대조

DB 서버를 정지하고, 기록한 파일 주소를 읽기 전용 `os.pread`로 재생했다.
여기서 주소는 OS volume 파일의 offset이며 NVMe LBA를 직접 측정한 것은 아니다.
각 trial 전 동일 파일 cache 해제 절차를 적용했다. 같은 physical core에서 실행하고
3회 반복하며 실행 순서를 교대했다. SQL·heap·OOS 코드가 없는 I/O 재생 실험이다.

- 주소 정렬은 원래 `(file, offset, size)` multiset을 정확히 보존한다.
- 인접 요청 병합은 정렬된 목록에서 서로 붙은 구간만 최대 1MiB로 묶는다.
  16KiB 페이지로 다시 풀어 원래 집합과 정확히 일치하는지 검사했다. 요청 바이트도 같다.
- 한 페이지 간격까지 병합하는 별도 대조군은 필요한 페이지를 모두 포함하지만,
  건너뛰던 데이터까지 추가로 읽는다. 앞의 두 대조군과 구분한다.
- source FD map의 전후 일치, short read 부재, 원래 선택 집합의 hash도 검사했다.

| 엔진 / 재생 방식 | 요청 수 | 요청 MiB | OS read_bytes MiB | 시간 중앙값 (범위) |
| --- | ---: | ---: | ---: | ---: |
| 기준 / 원래 순서 | 200,089 | 3,126.39 | 3,145.47 | 1.102s (1.102–1.102) |
| 기준 / 주소 정렬 | 200,089 | 3,126.39 | 3,143.84 | 1.051s (1.051–1.051) |
| OOS / 원래 순서 | 133,341 | 2,083.45 | 2,793.11 | 4.396s (4.396–4.396) |
| OOS / 주소 정렬 | 133,341 | 2,083.45 | 2,765.25 | 2.825s (2.821–2.826) |
| OOS / 정렬 + 인접 요청 병합 | 100,522 | 2,083.45 | 3,579.64 | 1.445s (1.444–1.446) |
| OOS / 정렬 + 한 페이지 간격까지 병합 | 3,649 | 3,597.12 | 3,657.59 | 1.278s (1.277–1.278) |

원래 읽기 순서에서 기준과 후보 사이에 생긴 약 3.3초 차이가 SQL 밖에서도 남는다.
OOS는 순서만 바꿔도 약 35.7% 빨라지고,
인접 요청 병합까지 하면 원래 재생보다 약 67.1% 빨라졌다.
필요한 페이지 집합과 총 요청량을 유지한 대조이므로 순서·요청 방식이 지연에 영향을
준다는 인과 근거다. 원래 SQL에 이 전략을 적용·검증한 것은 아니다.

빠른 대조군의 OS read_bytes가 더 크다는 점도 중요하다. readahead로 더 읽더라도
대기가 줄면 시간이 짧아질 수 있다. 이번 조건에서는 읽기 바이트의 감소만으로 시간 개선을 예측할 수 없다.

### 4. readahead만의 문제인가

`data_file_os_advise=3`은 source에서 `POSIX_FADV_RANDOM`으로 전달된다.
[설정 적용 코드](https://github.com/CUBRID/cubrid/blob/dcbf09e4f7fd02ff9c8fc6493ec8887fc2919d67/src/storage/file_io.c#L3033)를
확인하고 각 trial의 paramdump로 실제 적용을 검증했다. 이 설정 하나만 바꾼 SQL 대조는
엔진별 3회 중앙값에서 다음과 같았다.

| 설정 | 기준 SQL | OOS SQL |
| --- | ---: | ---: |
| 기본값 0 | 2.32s | 5.67s |
| RANDOM 3 | 5.69s | 8.73s |

양쪽 모두 느려졌다. **readahead를 끄는 설정을 해결책으로 제안하지 않는다.**
RANDOM 상태의 저수준 재생도 OOS의 원래 순서 7.141초,
정렬 4.158초였다. 두 경우 OS read_bytes는 요청 바이트와
같았지만 순서 효과는 남았다. 따라서 OS readahead가 유일한 원인은 아니다. 더 아래의
I/O 지역성·장치 cache·요청 처리 중 각각 무엇이 얼마만큼 기여하는지는 미분리 상태다.

### 판정과 후속 범위

관측과 대조로 확인한 것은 다음 범위다.

1. 이 fixture에서 추가 지연은 계산량보다 파일 페이지를 기다리는 경로에 집중된다.
2. 현재 OOS 조회는 대부분 비연속적인 16KiB 요청을 만든다. 큰 값이 없는 작은 컬럼
   조회에서 얻는 compact heap의 이득과, 큰 값을 다시 읽는 경로의 비용이 다르다.
3. 동일한 요청 집합의 순서와 묶음을 바꿔 지연을 줄였으므로 읽기 패턴의 인과 영향은
   확인했다.
4. 특정 저장 layout·Q4·호스트에서 얻은 결론이다. 모든 OOS workload나 모든 storage에서
   같은 비율을 보장하지 않는다.

후속 최적화는 필요한 OOS 페이지의 선행 읽기·batch read·배치 지역성 중 무엇을
개선할지 검토할 수 있다. 이번 재생은 그 후보를 판별하는 근거이며, MVCC·동시성·
복구 계약을 만족하는 엔진 구현이나 개선 후 회귀 검증은 수행하지 않았다.
실험 종료 후 원래 설정을 복원했고 마지막 원래 SQL도 여전히 느리게 재현됐다.

### 재현과 증거

[선별 수치와 fingerprint](cold-read-diagnostic-summary_dcbf09e.json)에 native 16 trial,
저수준 30 trial의 조건·중앙값·범위, 스레드 관측, 주소 패턴과 script hash를 남겼다.
기존 200개 기본 표본과 24개 보조 표본은 수정하지 않았다.
원시 SQL·stdout/stderr·perf·strace·FD map·요청 목록·대기 표본과 진단 코드는 다음에 있다.

```text
/mnt/nvme/data-5/tmp/CBRD-27788-io-diagnosis-20261028-run1
```

현 호스트의 재현 entry point는 `diagnose.py`이며 이전 DB·설치 경로를 검증해 사용한다.
기존 결과 디렉터리를 덮어쓰지 않는다. 아래 명령은 진단 script들을 새 디렉터리로 복사해
그 디렉터리를 artifact root로 사용하는 경우의 예다. 원본 DB와 설치는 보존된 환경을 사용한다.

```sh
python3 -B diagnose.py repro --name new-repro --repeats 2
python3 -B diagnose.py trial --name strace-default-base --label base --trace
python3 -B diagnose.py trial --name strace-default-head --label head --trace
python3 -B read_pattern.py
python3 -B run_controls.py
```

`repro`의 exit 1은 이 증상이 재현됐다는 RED 판정이다. 진단 marker는
OOS wall > 기준 1.5배, CPU < 1.2배, engine reads < 0.8배이며 제품의 합격 예산이 아니다.
처음과 마지막에 실제로 이 판정을 얻었다. query 정답·직렬 TABLE SCAN·client/server
identity·source SHA·perf 계수 검증도 통과했다.

`read_pattern.py`는 보존된 두 trace를 해석하고 `requests.tsv`를 만든다.
`replay.py`는 서버가 정지한 작업 DB의 해당 주소만 읽기 전용으로 재생한다.
초기 재현·wchan·strace·RANDOM·원래 설정 재확인을 각각 구분해 보존했다.
시스템 tracepoint 디렉터리는 접근 권한이 없어 사용하지 못했으며 strace와 `/proc`
관측으로 대체했다. tracer와 관측 thread를 종료하고 작업 서버·master를 정지했다.
DB·설치와 원시 근거는 보존했다.
