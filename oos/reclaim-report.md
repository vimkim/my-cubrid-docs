# OOS 회수 설계 개정 보고

2026-11-03 (Asia/Seoul) · 검토 대상 CUBRID/cubrid `feature/oos-merge`, `dcbf09e4f7fd02ff9c8fc6493ec8887fc2919d67`. 현행 구현 설명은 이 버전에 한정한다.

OOS는 큰 값을 여러 조각으로 나누어 행 바깥에 저장한다. 현행 회수 방식에는 다른 트랜잭션이 확정한 데이터를 덮어쓰거나, 아직 필요한 값을 지우는 경로가 있다. **삭제 결정이 확정되고 기존 독자의 사용이 끝난 뒤 회수하며, 실패하면 복원 대신 재시도로 마무리하는 설계**를 제안한다.

## 현재 구현에서 충돌하는 조건

복원이 가능하려면 원래 조각의 저장 위치인 슬롯이 비어 있어야 하고, **현재 사용량 + 복원할 데이터량 ≤ 페이지 용량**이어야 한다. 현행 구현은 조각을 지운 직후 다른 INSERT가 슬롯과 공간을 가져갈 수 있어 두 조건을 보장하지 못한다. 용량 2단위인 페이지가 1단위 조각 두 개로 찼다고 하자. 하나를 지우고 다른 INSERT가 1단위를 쓰면, 이후 복원에 필요한 양은 2 + 1 = 3단위다. 슬롯 번호만 예약해도 다른 슬롯이 그 공간을 쓰면 3 ≤ 2라는 불가능한 조건이 된다. 같은 슬롯까지 재사용하면 복원이 새 레코드를 덮어쓴다. CBRD-27781의 데이터 손상과 복원 공간 부족이 이 경우다.

삭제 대상 판단에도 조건이 필요하다. 트랜잭션이 끝났다는 사실은 특정 UPDATE가 확정됐다는 뜻이 아니다. UPDATE 한 문장만 취소한 뒤 나머지 작업을 commit할 수 있으므로, 트랜잭션의 commit 여부를 추가 확인해도 부족하다. 취소된 UPDATE의 과거 기록은 현재도 필요한 원래 값을 가리킨다. 이 기록으로 회수하면 CBRD-27237처럼 원래 값을 지운다. OOS 값을 바꾸지 않은 UPDATE도 같은 값을 계속 쓰므로, 과거 기록에 있다는 이유로 지워서는 안 된다.

## 필요한 설계 변화

1. **실제로 버린 값만 회수 예정 작업으로 남긴다.** 문장이나 savepoint를 되돌리면 해당 예정 작업도 취소한다. commit 결정이 장애 후에도 남도록 저장된 뒤, 예정 작업을 실행해 vacuum에 회수 알림을 보낸다. CUBRID의 지연 실행 장치인 postpone을 쓰는 안이다. 알림만 저장되고 commit 전에 장애가 나는 경우를 막는다. 알림을 받은 뒤에도 UPDATE 확정 전의 snapshot으로 옛 값을 읽는 독자가 모두 끝날 때까지 기다린다.
2. **꼬리부터 지우고 첫 조각은 마지막에 지운다.** 각 삭제는 복원 없이 재실행하는 redo-only 방식으로 기록한다. 첫 조각을 먼저 지우면 중간 장애 후 나머지 조각을 찾지 못해 공간이 영구히 남을 수 있다. 첫 조각을 남겨 두면 재시도가 남은 조각을 찾는다. 오류가 나도 예정 작업을 완료로 버리지 않고, 재시작 후에도 찾아 끝낼 수 있게 한다.
3. **주소와 조각의 식별값을 함께 확인한다.** 이미 비운 슬롯을 다른 값이 재사용하면 주소는 같아도 데이터는 다르다. 기존 CBRD-26950은 첫 조각의 식별값 검사로 대응되어 있다. 새 설계는 일부만 지운 상태에서 재시도하므로, 각 연결에 다음 조각의 식별값을 추가하고 매번 대조한다. 이미 반납된 중간 페이지도 재시도에서 처리해야 한다.

## 해결 범위와 비용

이 설계를 따르면 OOS 삭제를 복원할 일이 없어져, 다른 INSERT를 덮어쓰거나 복원 공간이 부족해지는 원인이 사라진다. 실제로 버린 값만 알리고 과거 독자가 끝나기를 기다리므로, 취소된 UPDATE나 값을 유지한 UPDATE의 살아 있는 데이터를 지우는 경로를 없앤다. 꼬리부터 삭제하고 식별값을 대조하며 재시도하는 조건은 공간 누락과 다른 값의 오삭제를 막는다. 복원을 위해 빈 페이지 회수를 미루던 제한도 제거하는 안이다. **heap forward 슬롯 복원(CBRD-27858)과 latch 순서 문제(CBRD-27860)는 별도 수정이 필요하다.**

현재는 회수 실패 시 복원하려고 값 전체를 조각별 undo 로그에 쓴다. 제안은 이 복원용 로그를 없애고 작은 삭제 재실행 로그와 회수 예정 기록을 유지한다. 대신 조각마다 식별값 8바이트가 늘고, 확인 후 삭제하므로 페이지 접근도 증가한다. 로그 감소량과 처리 속도는 아직 측정하지 않았다. 사양과 저장·복구 형식을 개정하고, 실제 엔진에서 문장 취소·중간 장애·재시작·동시 회수와 성능을 검증한 뒤 채택 여부를 결정해야 한다.
