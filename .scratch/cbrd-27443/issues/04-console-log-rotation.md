# 04: 별도 출력 로그의 용량 제한과 회전

**What to build:** 별도 stdout·stderr 로그가 장기 실행으로 무한히 커지지 않도록 저장 한도와 회전을 제공하고, 재시작·동시 출력·초기 실패 중에도 해당 정책에 따라 진단을 보존한다.

**Blocked by:** 01: 기존 master 환경에서 서버 시작·실패 후 파이프 종료.

**Status:** ready-for-agent

**Parent:** CBRD-27443 — [합의된 스펙](../spec.md). 착수 전에 전체 스펙의 외부 계약·시험 원칙과 이 티켓에 해당하는 근거를 읽는다.

**Acceptance coverage:** A09, A10, A05(로그 장애); A02–A04 출력 계약 회귀.

- [ ] 01의 별도 로그 방식에 맞춰 크기 한도·보관 개수·권한·회전 담당자와 실행 중 쓰기/회전 실패 처리를 정하고 문서화한다. 기존 오류 로그의 위치와 기록 정책은 유지한다.
- [ ] 실제 백그라운드 프로세스의 stdout·stderr에 출력이 발생하는 검증 경로를 사용해 기록·회전·보관 한도를 확인한다. 한도 도달을 시험할 수 있는 반복 가능한 조건을 마련한다.
- [ ] 반복 시작과 동시 작성 중 기존 내용을 시작 시점에 잘라내지 않고, 정한 보관 범위의 메시지가 유지된다. 회전 후 프로세스가 삭제된 이전 파일에 계속 써서 새 로그가 비는 문제를 방지한다.
- [ ] 초기 실패가 기록 중 회전과 겹쳐도 이번 시작 시도의 기존 실패 진단이 호출자에게 전달된다. 이전 시도·다른 DB의 로그가 섞이지 않는다.
- [ ] 로그 생성·쓰기·회전 실패에서 정한 오류 동작을 검증한다. 시작 전 로그 열기 실패는 호출자가 진단과 실패 코드를 받아야 하며 새로운 출력 수집 무한 대기를 만들지 않는다.
- [ ] 기존 오류 로그 정상 기록, SQL·PL 기능, 시작 명령 코드와 EOF를 회귀 검증한다.
- [ ] 구현과 CLI 회귀 사례를 함께 제공한다. 02 이후 추가된 서비스 로그에도 같은 정책을 적용할 수 있게 하고 최종 조합은 08에서 확인한다.

## Implementation notes

01의 실제 출력 대상과 진단 전달 방식에 의존한다. 모든 서비스 경로의 구현 완료를 기다릴 필요는 없다. 보관 한도에 따른 정상 삭제와 의도하지 않은 로그 유실을 구분해 판정한다.
