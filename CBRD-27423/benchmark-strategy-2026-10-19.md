# pgbuf 벤치마크 동기화·병목 조사 — 10/19 회의 검토안

작성·최종 수정: 2026-10-16 KST. 관련 이슈: [CBRD-27423](https://jira.cubrid.org/browse/CBRD-27423). 작업 374.

**회의 목표:** 형규님과 첫 부하·실행 환경·최소 지표·역할·다음 조치를 합의한다. 측정으로 병목을 확정하는 일은 이후 단계다. 회의 시간과 실행 일정은 미정이다.

**추천 순서:** 실행 가능한 읽기 부하 하나를 고르고 → 동일 revision의 비계측 반복으로 편차를 확인하고 → 별도 실행에서 CPU 프로파일을 얻는다. 변화가 없는 실행끼리 얼마나 달라지는지 알아야 이후 코드 변경의 효과를 해석할 수 있다. 현재 부하 파일과 검증된 성능용 환경은 아직 선택하지 않았다.

## 첫 실험 제안: 동일 빌드 반복 후 CPU 비용 확인

1. **실행 전 확인:** 합의한 부하·데이터·기대 결과와 전용 DB를 확보한다. 엔진 전체 SHA, 패치, 빌드 옵션, 바이너리 해시, 부하 버전과 설정을 기록한다. 설치본과 소스의 대응 및 DB 접근 상태를 확인한다. 준비가 안 되면 누락 항목·담당자·다음 확인을 남기고 실행을 보류한다. 기존 세미나 패치를 성능용 실행기로 전환하는 작업은 별도 범위다.
2. **준비와 warm-up:** 데이터 준비·연결·warm-up을 측정 구간에서 분리한다. 동일 요청열을 사용하고 SQL 결과 캐시로 요청이 생략되지 않는 조건을 확인한다. warm-up 종료 조건과 버퍼 크기를 기록한다. 검증된 읽기 카운터가 없으면 “상주 확인” 대신 “반복 접근으로 warm-up 시도”라고 표시한다. OS 캐시와 엔진 버퍼 상태를 구분한다.
3. **기본 시간 측정:** 상세 trace·프로파일러를 끈 채 같은 빌드·같은 부하를 직렬 반복한다. 각 실행의 완료 작업 수, 결과 검증 값, wall time과 서버 CPU를 보관한다. 동일 빌드의 반복 결과를 A/A 대조로 사용하고, 시간 순서에 따른 변화와 실행별 편차를 본다. 고정 반복 횟수나 회귀 임계값은 아직 채택하지 않는다.
4. **별도 프로파일:** 같은 조건으로 `perf` 표본을 수집하고, `pidstat`로 foreground와 관련 데몬의 CPU를 가능한 범위에서 구분한다. 서버 PID·스레드와 심볼·호출 스택이 식별되는지 먼저 확인한다. 이 실행의 시간을 기본 시간 표본에 섞지 않는다. 계측 유무의 차이도 기록한다.
5. **유효성·재현 확인:** 종료 코드뿐 아니라 성공 작업 수·기대 결과 일치, SQL 오류·timeout·미완료 작업을 확인한다. 실패 표본은 원인을 보존하고 성능 표본과 분리한다. 같은 명령·설정·데이터로 재실행할 수 있게 원시 결과와 요약을 연결한다. 초기 읽기 부하의 결과만으로 전체 pgbuf 또는 SQL 성능을 대표한다고 결론 내리지 않는다.

### 처음 수집할 최소 지표

| 질문 | 지표·수집 방법 | 해석 한계 |
| --- | --- | --- |
| 같은 일을 끝냈는가? | 실행기 출력의 성공 작업 수·검증 값·오류와 종료 상태 | SQL 호출 수와 fix/unfix 수는 다르다. |
| 결과가 반복 가능한가? | 실행기의 측정 구간 wall time, 성공 작업 수/wall time, 반복별 값과 범위 | 고정 배치 소요 시간과 작업당 평균은 fix/unfix p95/p99가 아니다. 개별 지연은 기존 실행기가 유효한 표본을 제공할 때만 추가한다. |
| CPU가 어디에 쓰이는가? | `pidstat`의 서버·스레드 CPU, 별도 `perf` 프로파일 | CPU 표본 비중은 대기 시간이나 mutex 경합의 직접 증거가 아니다. 대상 서버 권한·심볼·스택 수집은 실행 전 확인한다. |
| 읽기·I/O가 조건을 바꾸는가? | 의미를 확인한 엔진 hit/read 통계의 구간 차이, 해당 장치의 `iostat` | 엔진 read와 물리 장치 I/O는 다르다. 장치 지표에는 다른 프로세스가 섞일 수 있다. 미수집 값은 0으로 쓰지 않는다. |

## 형규님께 확인할 질문·연락 문안

확인할 질문은 네 가지다. **①** 바로 재실행할 수 있는 부하·데이터·결과 검증 방법이 있는가? **②** 사용할 머신·빌드와 동시 부하 조건은 무엇인가? **③** 실행·계측·분석은 누가 맡을 수 있는가? **④** 첫 실행과 결과 검토 시점, 결과 공유 위치는 어떻게 정할 것인가?

> 형규님, 10/19에는 pgbuf 벤치마크의 첫 부하·환경·지표·역할과 다음 실행을 맞추고 싶습니다. 기존에 재실행 가능한 부하와 머신이 있으면 그 조건부터 확인하고, 동일 revision 반복으로 편차를 본 뒤 별도 CPU 프로파일로 조사 대상을 좁히는 순서를 제안드립니다. 실행 가능한 부하·데이터, 사용 환경, 분담 가능 범위를 회의에서 함께 확인하면 좋겠습니다.

위 문안은 사용자 검토용이며 발송하지 않았다.
