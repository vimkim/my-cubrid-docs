CBRD-27157 · Design review · 2026-08-12

TT_LOADDB도
MVCCID self-lock을 잡아야 할까?

형규님의 답변을 현재 CUBRID 소스에 대조하여, 논리적으로 맞는 부분과 성능 논거에서 바로잡아야 할 부분을 분리한다. 결론보다 먼저 self-lock이 무엇을 보호하는지, 어느 함수에 어느 분기가 생기는지를 정확히 본다.

1. 먼저 결론

형규님의 핵심 결론은 타당하다.

loaddb worker가 MVCCID self-lock을 잡아도 lock 수는 transaction 수에 비례하고, fresh MVCCID이므로 획득 경쟁도 없다. uniform self-lock은 미래의 INSID 생산 경로까지 불변식을 구조적으로 지킨다는 장점이 있다.

하지만 “lock_internal_perform_lock_object()의 레코드별 hot path에 TT_LOADDB skip 분기가 추가된다”는 성능 비교는 현재 시험한 skip안과 맞지 않는다. skip 분기는 generic lock 함수가 아니라 logtb_acquire_mvccid_self_lock()에 있다. 현재 loaddb bulk row는 이 helper를 레코드마다 호출하지 않는다.

따라서 이 결정을 성능으로 가르기 어렵다. 실제 쟁점은 다음 한 문장이다.

모든 active worker MVCCID를 self-lock할 것인가?
아니면 다른 transaction에 관찰 가능한 INSID가 있는 MVCCID만 self-lock할 것인가?

2. 논쟁에 필요한 최소 모델

행위자와 lock owner

server-side loaddb session

session transaction S
└─ class T에 BU_LOCK 보유
   ├─ TT_LOADDB worker W1 ─ batch transaction B1 ─ MVCCID M1
   └─ TT_LOADDB worker W2 ─ batch transaction B2 ─ MVCCID M2

class BU owner       = session transaction S
MVCCID self-lock owner = worker batch transaction B1/B2

BU_LOCK과 MVCCID self-lock은 같은 lock이 아니다. key, owner, 보호 목적이 모두 다르다.

구분Class BU_LOCKMVCCID self-lock
resource keyclass OIDworker의 MVCCID
ownersession transactionbatch transaction
modeBU_LOCKinserter X_LOCK, waiter S_LOCK
목적bulk load 중 일반 class/row data access 제한unique/FK 검사가 unfinished inserter의 종료를 기다리는 rendezvous
현재 loaddb에서 waiter일반 data mode와 충돌bulk row에 INSID가 없어 형성되지 않음

self-lock이 보호하는 불변식

T1: MVCCID M 발급
T1: resource TRANSACTION(M)에 X_LOCK
T1: row header에 INSID=M 공개

T2: unique/FK 검사 중 active INSID=M 발견
T2: TRANSACTION(M)에 S_LOCK 요청 → T1 종료까지 대기
T2: 깨어난 뒤 key와 active 상태를 다시 검사
핵심 불변식 다른 transaction이 관찰할 수 있는 active INSID가 있다면, 같은 MVCCID resource에는 matching X self-lock이 있어야 한다.

이 설명은 “모든 transaction은 시작할 때 반드시 self-lock을 가진다”와 다르다. 현재 구현도 transaction 시작 즉시가 아니라 MVCCID를 lazy 할당하는 시점에 self-lock을 시도한다. boot/recovery 및 system/vacuum transaction은 concurrent waiter와 정상 해제 경로가 없다는 이유로 이미 예외 처리한다.

3. CBRD-27157 회귀는 왜 발생했나?

server-side loaddb가 첫 OOS-backed attribute를 적재
  → OOS file lazy create
  → file_create(FILE_OOS)
  → vacuum dropped-file 검사에 current MVCCID 필요
  → logtb_get_current_mvccid()가 MVCCID lazy 할당
  → logtb_acquire_mvccid_self_lock()
  → lock_transaction_mvccid()
  → lock_internal_perform_lock_object()
  → assert(thread_p->type != TT_LOADDB)

file_create()가 원하는 것은 dropped-file 식별자 재사용 검사를 위한 MVCCID 값이다. row에 INSID를 쓰기 위해 들어온 경로가 아니다. OOS는 새로운 lock 정책을 만든 것이 아니라, loaddb worker가 이전에는 가지 않던 MVCCID 발급 경로를 열었다.

구분 MVCCID 값이 필요하다는 사실만으로 MVCCID self-lock도 반드시 필요하다고 결론 내릴 수는 없다. self-lock 필요성은 그 MVCCID를 관찰하고 기다릴 주체가 있는지까지 확인해야 한다.

4. 형규님 답변을 문장별로 분석

판정주장분석
표현 보완 “TT_LOADDB가 BU_LOCK을 보유한다.” 정확히는 TT_LOADDB worker가 아니라 session transaction이 class BU를 보유한다. worker의 object-lock 조회가 session transaction으로 redirect된다.
맞음 “loaddb는 row에 MVCCID를 표시하지 않아 경쟁이 일어나지 않는다.” 현재 bulk insert는 is_bulk_op=true이고 record의 MVCC flag를 제거한다. unique/FK waiter가 worker MVCCID를 INSID에서 발견하는 경로가 없다.
맞음 “uniform self-lock을 잡아도 최대 lock 수는 O(txn)이다.” per-row X lock의 O(row) 증가와 다르다. main/sub MVCCID 단위의 self-lock이므로 active transaction·subtransaction 수에 비례한다.
설계 선택 “메인 로직에 TT_LOADDB 예외를 둘 이유가 없다.” uniform 불변식을 우선하면 타당하다. 그러나 source상 절대 규칙은 아니다. 이미 no-waiter/lifecycle 전제를 근거로 boot/recovery/system/vacuum을 생략한다. TT_LOADDB도 같은 종류의 정책 예외로 정의할 수는 있다.
비교 불일치 “레코드마다 호출되는 generic lock 함수에 TT_LOADDB skip 분기가 생겨 더 큰 영향이 있다.” 현재 skip 실험은 generic 함수에 runtime skip을 넣지 않는다. logtb_acquire_mvccid_self_lock()에서만 early return한다. 현재 loaddb bulk row는 레코드별 ensure 경로에도 들어가지 않는다.

여기서 “맞음”은 현재 revision의 reachable source에 대한 판정이다. 미래의 모든 loaddb path 부재를 증명한다는 뜻은 아니다.

5. 성능 주장을 정확한 위치에서 비교하기

Uniform안

generic lock assert를 좁힌다

assert(thread_p->type != TT_LOADDB
       || is_transaction_lock);
  • release 빌드에서는 assert 전체가 제거된다.
  • debug에서도 기존부터 thread type 검사는 있었다.
  • 일반 non-TT_LOADDB 호출은 short-circuit된다.
  • 실제 비용은 transaction당 self-lock resource 한 개와 종료 시 해제다.
현재 skip 실험안

self-lock policy helper에서 종료한다

if (thread_p->type == TT_LOADDB)
  {
    return NO_ERROR;
  }
  • generic object-lock hot path에 추가된 분기가 아니다.
  • 정상 transaction은 이미 self-locked이면 앞선 dedup에서 반환한다.
  • TT_LOADDB는 skip 후 hint가 unset이지만, 현재 bulk row는 ensure를 레코드마다 호출하지 않는다.
  • OOS 회귀 경로에서는 첫 MVCCID lazy assignment에서 주로 실행된다.

왜 bulk row마다 helper를 호출하지 않는가?

heap_get_insert_location_with_lock()
  if (context->is_bulk_op)
    lock = NULL_LOCK;

  if (lock == X_LOCK && MVCC class)
    logtb_ensure_mvccid_self_lock();

TT_LOADDB bulk insert: lock == NULL_LOCK
→ per-row ensure 호출 조건이 false
성능 판단: 두 안 모두 비용이 매우 작다고 보는 것이 안전하다. 측정 없이 어느 쪽이 더 빠르다고 주장하기보다, 불변식과 예외의 유지보수 비용으로 결정해야 한다.

6. 실제 선택지는 두 개가 아니라 세 개다

A · Uniform

TT_LOADDB도 self-lock 획득

transaction resource인 경우 internal assert를 허용한다.

장점: 모든 active worker MVCCID에 동일 규칙을 적용한다. 미래에 loaddb INSID producer가 생겨도 안전하다.

대가: 현재 waiter가 없는 MVCCID에도 lock entry를 만든다. generic lock module의 assert가 loaddb transaction 예외를 안다.

B · Common helper skip

현재 실험 중인 방식

공통 logtb_acquire_mvccid_self_lock()에서 TT_LOADDB를 반환한다.

장점: 현재 의미상 불필요한 lock을 만들지 않고 strict internal assert를 보존한다.

대가: assignment뿐 아니라 ensure도 같은 helper를 사용한다. 미래에 TT_LOADDB가 INSID를 공개해도 ensure가 실제 lock을 잡지 못한다.

C · Assignment-only skip

좁은 절충안

MVCCID assignment의 best-effort wrapper에서만 TT_LOADDB를 생략하고, error-propagating ensure는 실제 self-lock을 허용한다.

장점: 현재 file_create()의 불필요한 eager lock은 생략하면서, 미래 INSID producer는 ensure에서 불변식을 복구할 수 있다.

대가: policy가 eager assignment와 publication ensure로 갈라져 설명과 테스트가 더 필요하다. ensure가 generic assert를 통과하도록 별도 허용도 필요하다.

7. 권고

보고서 권고

성능 논거는 제외하고, 기본 선택은 A(uniform)가 더 방어적이다

self-lock 비용은 O(txn)이고 fresh MVCCID 획득은 기다리지 않는다. 반면 A안은 observable INSID ⇒ matching X self-lock 불변식을 future path까지 구조적으로 유지한다. 별도 예외 전제를 학습하고 감시할 필요가 적다.

다만 팀의 명시적 정책이 “TT_LOADDB는 object lock뿐 아니라 역할 없는 transaction self-lock도 잡지 않는다”라면 skip 선택도 논리적으로 성립한다. 그 경우 현재 B안은 예외 범위가 다소 넓다. 다음 안전장치가 필요하다.

  1. 전제 명문화: TT_LOADDB bulk row는 다른 transaction에 worker MVCCID를 INSID로 공개하지 않는다.
  2. 금지 경로 검증: TT_LOADDB가 INSID를 stamp하는 위치에 들어오면 debug assertion 또는 실패가 발생하도록 한다.
  3. 전용 동시성 테스트: unique/PK/FK를 포함한 server-side loaddb에서 다른 session이 worker MVCCID waiter가 되지 않음을 검증한다.
  4. helper 범위 재검토: assignment-only skip(C안)이 공통 helper skip(B안)보다 요구사항에 더 정확한지 검토한다.
회의에서 사용할 한 문장:
“형규님의 uniform안은 O(txn) 비용으로 미래 불변식까지 지키므로 유지보수 면에서 더 방어적입니다. 다만 hot-path 분기 비용 주장은 현재 skip 위치와 맞지 않으므로, 성능이 아니라 TT_LOADDB의 no-INSID 전제를 별도 정책으로 둘 것인지로 결정하는 것이 맞습니다.”
