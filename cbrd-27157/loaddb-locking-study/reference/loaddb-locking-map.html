loaddb 잠금 빠른 참조

resource, owner, observer, invariant를 섞지 않기 위한 한 장짜리 지도. 회의 전에 2분 동안 훑고 바로 사용할 수 있다.

기준 revision f11fc4259 인쇄 친화적 현재 결정: 미합의
바로가기 행위자 두 resource 호환성 용어집 결정 질문 소스 지도

1. 먼저 transaction owner를 그린다

server-side loaddb session

session transaction S
└─ class T의 BU_LOCK 보유
   ├─ TT_LOADDB worker W1 ─ batch transaction B1 ─ 자체 tran_index / MVCCID
   └─ TT_LOADDB worker W2 ─ batch transaction B2 ─ 자체 tran_index / MVCCID

object-lock 조회: W1/W2 → session transaction S로 redirect
transaction self-lock: W1/W2 → 자기 batch transaction B1/B2 소유
SOURCE FACT worker는 batch마다 새 tran_index를 받고 표준 commit/abort 경로로 끝난다. object-lock 조회는 TT_LOADDB일 때 connection의 session transaction index를 사용한다.

현재 PR 쟁점기존 우회 유지TT_LOADDB도 획득할지 skip할지
금지할 문장 “BU_LOCK이 MVCCID self-lock을 대신 잡아 준다.” 두 lock은 key도 owner도 다르므로 직접 대체 관계가 아니다.
정확한 문장 “BU_LOCK과 bulk row의 INSID 미기록 때문에 self-lock을 기다릴 observer가 현재 없다.” 이것은 resource 대체가 아니라 필요성 제거 논리다.

5. 결론을 가르는 네 질문

  1. Resource: 지금 요청한 key는 class/instance OID인가, MVCCID인가?
  2. Observer: 이 lock을 기다릴 수 있는 row INSID 또는 다른 표식이 실제로 존재하는가?
  3. Invariant: 현재 정확성만 지킬 것인가, future path까지 uniform invariant로 막을 것인가?
  4. Seam: “누가 self-lock을 해야 하는가”는 logtb 정책인가, “어떤 resource를 허용하는가”는 lock-manager 정책인가?
