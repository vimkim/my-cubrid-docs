Lesson 0001 · CUBRID loaddb locking

두 lock을 분리하면
논쟁이 보인다

PR #7588의 핵심은 “lock을 잡을까 말까”가 아니다. 서로 다른 두 resource, 두 transaction owner, 한 observer protocol이 OOS file 생성에서 우연히 만난 사건이다.

오늘의 tangible win

이 lesson을 마치면 stack의 lock_transaction_mvccid를 보고 “session의 BU_LOCK과 같은 lock이 아니다”라고 즉시 말할 수 있다. 동시에 “그렇다고 BU_LOCK이 논쟁과 무관한 것은 아니다”라는 이유도 설명할 수 있다.

막히면 먼저 loaddb 잠금 빠른 참조를 열어 용어를 확인하자. 암기보다 resource와 owner를 매번 다시 그리는 편이 안전하다.

1. loaddb에는 transaction이 하나만 있지 않다

server-side loaddb의 worker는 session transaction을 그대로 공유하지 않는다. 각 batch마다 새 tran_index를 받아 자기 transaction으로 insert하고 commit 또는 abort한다. 소스에서 logtb_assign_tran_index와 xtran_server_commit을 직접 확인할 수 있다.[1]

session transaction S
└─ class T에 BU_LOCK
   ├─ worker W1 → batch transaction B1 → row batch insert → commit
   └─ worker W2 → batch transaction B2 → row batch insert → commit

질문: "누가 lock을 소유하는가?"
답: object BU는 S, 새 MVCCID self-lock은 B1/B2
Session side

BU_LOCK의 owner

loaddb worker가 object lock을 조회하면 lock manager는 connection의 session transaction index로 redirect한다.[2]

Worker side

MVCCID의 owner

lock_transaction_mvccid()는 호출 thread의 tran_index를 사용하므로 self-lock은 worker batch transaction 소유다.[3]

SOURCE FACT 같은 loaddb 작업 안에서도 session transaction과 worker batch transaction은 구별해야 한다. client identity를 복사하는 것과 transaction/lock ownership을 공유하는 것은 다른 일이다.

2. Object lock과 transaction lock은 key부터 다르다

보호 질문“누가 이 class/row에 접근할 수 있나?”“이 inserter가 끝났나?”
이번 진입점lock_object()lock_transaction_mvccid()

LK_RES_KEY.type이 key identity의 일부이므로 class OID와 MVCCID는 같은 hash table을 사용해도 서로 alias되지 않는다.[4] 따라서 다음 문장은 틀렸다.

틀린 설명: “session이 BU_LOCK을 보유하니 worker의 MVCCID self-lock은 이미 잡힌 셈이다.”

그러나 BU_LOCK은 여전히 self-lock의 필요성 판단에 관여한다. compatibility table에서 BU는 다른 BU와 호환되지만 일반 data access에 필요한 IS/S/IX/SIX/X와 충돌한다.[5] 즉 일반 transaction이 loaddb의 bulk row를 관측하거나 충돌할 가능성을 제한한다.

정확한 추론 “BU와 self-lock은 같은 resource라서 대체된다”가 아니라 “BU가 observer의 진입을 막기 때문에 self-lock protocol을 쓸 상황이 없어질 수 있다”이다.

정밀한 주의: BU는 SCH_S_LOCK과는 호환된다. 따라서 “다른 transaction은 아예 하나도 들어오지 못한다”보다 “일반적인 row data access mode와 충돌한다”가 소스에 더 가까운 표현이다.

3. MVCCID self-lock은 inserter와 waiter의 rendezvous다

CUBRID의 row version은 inserter/deleter의 MVCCID를 metadata로 사용한다. 공식 매뉴얼은 다른 transaction이 row header의 MVCCID로 writer가 아직 active인지 판단한다고 설명한다.[6]

Inserter T1이 MVCCID 42를 발급받는다.
T1이 transaction resource MVCCID=42에 X_LOCK을 건다.
새 row header에 INSID 42가 기록되어 다른 검사자가 발견할 수 있다.
unique/FK 검사자 T2가 같은 resource에 S_LOCK을 요청해 T1 종료까지 기다린다.
T1 commit/abort 후 lock이 풀리면 T2가 key를 다시 검사한다.

이 protocol의 핵심 invariant는 다음 한 줄이다.

observable INSID  ⇒  inserter가 같은 MVCCID에 X self-lock 보유

그런데 loaddb는 has_BU_lock을 context.is_bulk_op으로 전달하고,[7] heap insert는 bulk op일 때 INSID를 기록하지 않는다.[8]

현재 정확성

observer가 없다

INSID가 없으므로 unique/FK waiter가 이 worker MVCCID를 row에서 발견할 수 없다. 현재 경로만 보면 self-lock은 불필요하다는 근거다.

미래 불변식

uniform은 방어가 된다

향후 어떤 loaddb path가 INSID를 만들더라도 모든 정상 worker가 발급 즉시 self-lock한다면 invariant는 구조적으로 유지된다.

4. OOS는 새 잠금 규칙이 아니라 숨은 경로를 열었다

OOS file은 첫 OOS-backed attribute를 저장할 때 lazy create된다. file_create(FILE_OOS)는 vacuum이 dropped file identifier를 재사용하지 않도록 현재 MVCCID를 요구한다.[9] 이 때문에 기존 bulk insert가 평소에는 가지 않던 MVCCID 발급 경로로 들어갔다.

oos_create_file() → file_create(FILE_OOS)
logtb_get_current_mvccid()가 lazy MVCCID 발급
CBRD-26942 이후 발급 즉시 logtb_acquire_mvccid_self_lock()
lock_transaction_mvccid()가 MVCCID key로 internal lock engine 진입
debug의 assert(thread_p->type != TT_LOADDB) 실패
핵심 진단 OOS가 object lock을 새로 요구한 것이 아니다. file identifier 안전 검사가 MVCCID를 요구했고, MVCCID 발급에 새로 붙은 self-lock side effect가 오래된 TT_LOADDB assert와 충돌했다.

5. 이제 두 수정안이 정확히 보인다

안 A · explicit skip

logtb에서 early return

전제: bulk row에는 INSID가 없고 BU가 일반 data observer를 막으므로 waiter가 없다.

장점: 불필요한 lock entry를 만들지 않고 “load worker no-lock” 규칙을 보존한다. self-lock 적용 정책이 logtb_acquire_mvccid_self_lock()에 모인다.

위험: 미래에 TT_LOADDB가 INSID를 만들면 self-lock 없는 observable INSID가 생길 수 있다.

안 B · uniform acquire

transaction key는 assert 허용

전제: CBRD-23375는 class/instance object lock 정책이고 transaction rendezvous는 별개다.

장점: “observable INSID ⇒ self-lock”을 future path까지 유지한다. fresh MVCCID의 자기 X 요청은 기다리지 않으며 batch 종료 시 해제된다.

위험: generic lock manager가 loaddb batch 정책을 알아야 하며, assert가 모든 transaction resource 요청을 허용한다.

Module seam으로 한 번 더 보기

DESIGN LENS “누가 self-lock 대상인가?”를 결정한다면 self-lock policy를 이미 모으고 있는 logtb_acquire_mvccid_self_lock()가 locality가 높은 seam이다. 반대로 “TT_LOADDB에 허용되는 lock resource 종류가 무엇인가?”를 정의한다면 lock manager의 assert가 그 interface를 표현한다.

회의에서 물어야 할 결정 질문:
CBRD-23375의 “no locking”은 object lock만 금지하는가, 아니면 TT_LOADDB worker의 모든 실제 lock resource 획득을 금지하는가? 그리고 현재 observer 부재보다 future uniform invariant에 더 높은 우선순위를 둘 것인가?

현재 source만으로 두 설계 중 하나가 유일하게 옳다고 증명되지는 않는다. source는 각 전제와 대가를 보여 주고, 정책 범위는 maintainer가 명시적으로 결정해야 한다.
