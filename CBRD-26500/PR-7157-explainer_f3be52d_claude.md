# PR #7157 — 적중률 언더플로 수정과 옵션 2 미채택 배경 (해설)

PR: https://github.com/CUBRID/cubrid/pull/7157
JIRA: https://jira.cubrid.org/browse/CBRD-26500
분석 기준 커밋: `f3be52d2f` (PR HEAD)
관련 문서: [상세 비교 보고서](./PR-7157-option-comparison_f3be52d_claude.md) · [근본 원인 분석](./PR-7157-explanation.md)

본 문서는 리뷰 스레드에서 논의된 두 가지 해결 방안(옵션 1 clamp / 옵션 2 카운터 게이트 통일) 중 옵션 1로 종결한 배경을, 사전 지식 없이도 따라올 수 있도록 풀어 쓴 해설이다. file:line 단위 근거와 구현 스케치는 상세 비교 보고서를 참조한다.

## 1. Background — 무엇이 문제였나

CUBRID는 디스크 페이지를 메모리 버퍼에 캐싱하며, 이와 관련해 두 개의 통계 카운터를 유지한다.

- **fetches** — 페이지 요청 총 횟수 (버퍼에서 해결했든 디스크까지 갔든 전부)
- **ioreads** — 그중 버퍼에 없어 디스크에서 실제로 읽어 온 횟수

버퍼 적중률은 다음과 같이 계산된다.

```
hit ratio = (fetches − ioreads) / fetches
```

두 카운터는 `UINT64`, 즉 음수가 존재하지 않는 64비트 정수다. 순간적으로 `ioreads`가 `fetches`보다 1이라도 커지면 뺄셈 결과가 −1이 아니라 모듈러 연산으로 한 바퀴 돌아 `2^64 − 1 = 18446744073709551615`가 된다. 이 값으로 비율을 계산한 결과가 JIRA에 보고된 `Data_page_buffer_hit_ratio = 4034632613888.00` 같은 비현실적 출력이다.

## 2. Two Options — 리뷰 스레드에서 나온 두 방안

| | 옵션 1 — 출력 단 clamp | 옵션 2 — 카운터 게이트 통일 |
|---|---|---|
| 접근 | 뺄셈 직전 `ioreads > fetches`이면 0으로 처리 | 두 카운터의 "모니터링 활성 여부" 확인 방식을 통일해 어긋남의 원인을 제거 |
| 성격 | 증상 차단 (출력 직전 안전장치) | 원인 제거 (단, 아래에서 보듯 원인의 일부만) |
| 상태 | PR에 반영 완료 | 미채택 |

옵션 2가 더 근본적으로 보이지만, 결론부터 말하면 **옵션 2는 카운터가 어긋나는 4가지 원인 중 1가지만 제거한다.** 나머지 3가지가 남는 한 clamp는 어차피 필수이고, clamp가 있으면 옵션 2의 효과는 출력에서 관측되지 않는다.

## 3. Why Counters Diverge — 어긋남의 4가지 원인

### 원인 1 — 활성화 시점 비대칭 (옵션 2가 제거하는 유일한 원인)

페이지 요청 처리 함수(`pgbuf_fix`)는 **진입 시점에** "모니터링이 켜져 있는가"를 확인해 지역 변수에 저장하고, fetch 계상 여부는 이 저장값으로 판정한다. 반면 ioread는 계상하는 **그 순간에** 전역 상태를 다시 확인한다. 두 확인 시점 사이에 statdump가 모니터링을 켜면, 해당 요청은 ioread만 계상되고 fetch는 누락된다.

단, 이 현상은 **모니터링을 켜는 순간에 1회성으로만** 발생한다.

### 원인 2 — 스냅샷 straddle (매 interval 재발, 실질적 주범)

한 건의 miss 처리에서 `ioread++`는 디스크 읽기 **전에**, `fetch++`는 처리가 모두 끝난 **후에** 실행된다. 두 증가 사이에는 최소한 디스크 읽기 시간만큼의 간격이 항상 존재한다.

한편 `statdump -i 1`은 매초 "이번 1초 동안의 증가량"(현재 누적 − 직전 누적)을 보고한다. 장부를 매초 정각에 마감하는 것과 같다 — 접수 도장은 찍혔는데 완료 도장은 아직인 건이 마감 시각에 걸리면, 이번 장부에는 접수만 기록되고 완료는 다음 장부로 넘어간다. 마찬가지로 스냅샷 경계에 걸린(in-flight) miss는 ioread가 interval N에, fetch가 interval N+1에 귀속된다.

평상시에는 문제가 되지 않는다. interval당 hit이 수천 건이면 한두 건의 귀속 오차로는 `fetches − ioreads`가 음수가 되지 않는다. 문제는 JIRA 재현 워크로드(10M × 10M 조인)처럼 **거의 모든 요청이 miss(적중률 ≈ 0%)** 인 경우다. 이때는 매 interval `fetches ≈ ioreads`이므로 경계에 걸린 요청 **단 한 건**이 부호를 뒤집는다. JIRA에 기록된 스냅샷이 `fetches = 33511, ioreads = 33512` — 정확히 1 차이 — 인 것이 이 클래스의 전형적 증거다.

핵심은 이 원인이 **게이트 확인 방식과 무관하다**는 점이다. 두 증가 지점의 시간 분리라는 계측 구조 자체에서 나오므로, 옵션 2를 완벽히 구현해도 그대로 남는다. 원인 1이 활성화당 1회성인 데 비해 이 원인은 매 interval 반복된다.

### 원인 3 — ioread 이후 실패 경로 (영구 어긋남)

디스크 읽기까지 수행해 ioread를 계상한 뒤에도, 인터럽트나 I/O 오류로 요청 처리가 중도 실패할 수 있다. 이 경우 fetch는 영영 계상되지 않아 실패 1건당 ioread 잉여 +1이 **영구적으로** 남는다.

### 원인 4 — fetch를 계상하지 않는 별도 경로

임시 볼륨 페이지(정렬·임시 결과 등)를 읽는 `pgbuf_simple_fix`는 miss 시 ioread는 계상하지만 fetch는 **원래부터 계상하지 않는** 경로다. 옵션 2 방식으로 이 경로의 ioread 계상까지 차단하면, 실제 발생한 물리 읽기가 `Num_data_page_ioreads` 통계에서 누락된다. 적중률 하나를 고치려다 정상 동작하던 다른 원시 통계의 의미를 훼손하는 부작용이다.

## 4. Conclusion — 옵션 1로 종결한 이유

1. **clamp는 어차피 필수다.** 원인 2·3·4가 남는 한 `ioreads > fetches`는 계속 발생하므로, 옵션 2는 clamp의 대체재가 될 수 없다.
2. **clamp 이후 옵션 2의 효과는 관측 불가능하다.** 원인 1로 인한 어긋남도 clamp가 이미 흡수하므로, 옵션 2를 추가해도 출력에서 달라지는 것이 없다.
3. **비용은 실재한다.** 서버에서 가장 빈번히 실행되는 경로(`pgbuf_claim_bcb_for_fix`)의 통계 시맨틱 변경, `Num_data_page_ioreads` 의미 변경 리스크, 추가 리뷰 표면.
4. **clamp의 정확도 손실은 실질적으로 없다.** 원인 2가 부호를 뒤집을 수 있는 조건 자체가 "진짜 hit이 노이즈(수 건)보다 적은 구간", 즉 참값이 ≈ 0%인 구간이다. clamp가 0을 출력하는 순간의 참값이 바로 그 근방이다.

요컨대 옵션 2는 "혜택은 관측 불가, 리스크는 실재"이므로 본 PR에서 진행하지 않는다. 카운터 게이팅 일관성 자체가 별도로 필요해지면 저우선 이슈로 분리하되, 위 원인 4의 함정을 이슈 본문에 명기한다.
