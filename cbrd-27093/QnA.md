# CBRD-27093 QnA — "DWB를 끄면 어차피 정합성이 깨지는데 fsync가 왜 필요한가?"

- 이슈: <http://jira.cubrid.org/browse/CBRD-27093>
- 관련 수정 커밋: `85b6b5743` [CBRD-27093] Synchronize volumes when DWB is disabled
- 배경 문서: [CBRD-27093-dwb-off-checkpoint-fsync-missing.md](./CBRD-27093-dwb-off-checkpoint-fsync-missing.md)

---

## Q. 질문 요지

> `double_write_buffer_size=0`으로 DWB를 끄고 운영한다는 것 자체가 torn page를
> 감수하겠다는 뜻 아닌가? 정전이 나면 어차피 페이지가 찢어져서 DB가 망가질
> 텐데, 그런 구성에서 checkpoint가 데이터 볼륨을 fsync해봐야 무슨 의미가
> 있나? **어차피 깨질 정합성이라면 fsync를 건너뛰는 (버그 이전의) 동작도
> 사실상 문제가 없는 것 아닌가?**

합리적으로 들리는 질문이다. "보호 장치 하나를 껐으니 나머지 보호도 의미
없다"는 직관인데, 결론부터 말하면 **성립하지 않는다.** fsync와 DWB는 서로
다른 장애를 막는 직교적(orthogonal) 보호 장치이기 때문이다.

## A. 한 줄 답변

> DWB는 **쓰기 원자성**(페이지가 반쯤 찢어지는 것)을 막고, fsync는
> **내구성과 순서**(쓴 줄 알았던 페이지가 통째로 유실되는 것)를 막는다.
> DWB를 끄는 것은 "torn page 방어를 스토리지 계층에 위임한다"는 뜻이지
> "정합성을 포기한다"는 뜻이 아니며, 그런 환경에서도 fsync가 빠지면
> **torn page와 무관하게 모든 정전에서 커밋된 데이터가 유실**된다.

---

## 1. 두 장치는 서로 다른 장애를 막는다

### 1.1 fsync가 막는 것: lost write (유실된 쓰기)

checkpoint의 계약을 다시 보자 (배경 문서 §1.2):

```
1. dirty 데이터 페이지를 볼륨에 write        (flush — OS 페이지 캐시까지만)
2. 볼륨을 fsync                              (sync — 디스크까지 강제 반영)
3. chkpt_lsa(복구 재시작 위치) 전진
4. 더 이상 필요 없는 아카이브 로그 삭제
```

2번 없이 3, 4번을 하면 이런 일이 생긴다:

- 페이지는 OS 페이지 캐시에만 있는데 checkpoint는 "chkpt_lsa 이전 변경은
  전부 디스크에 있다"고 선언한다.
- 정전이 나면 페이지 캐시가 증발한다. 디스크 위에는 checkpoint **이전의
  낡은 버전** 페이지가 남는다. 찢어진 게 아니다 — 온전하게 낡은 버전이다.
- 복구는 chkpt_lsa부터 redo를 시작하므로, 그 페이지를 최신으로 만들
  로그는 재적용 대상이 아니고, 4번에서 이미 삭제됐을 수도 있다.

결과: **페이지가 단 하나도 찢어지지 않아도, 완벽하게 원자적인 스토리지
위에서도, 커밋된 데이터가 조용히 사라진다.** 복구는 에러 없이 성공하므로
운영자는 알아챌 수도 없다.

### 1.2 DWB가 막는 것: torn write (찢어진 쓰기)

torn page의 근본 원인은 크기 불일치다: DB 페이지(16KB)가 스토리지의 원자
쓰기 단위(전통적으로 512B~4KB 섹터)보다 크다. 16KB write는 디바이스
레벨에서 여러 섹터 쓰기로 쪼개지고, 그 **중간에** 전원이 나가면 앞쪽은 새
내용 + 뒤쪽은 옛 내용인 페이지가 남는다. 이런 페이지는 self-consistent하지
않아 로그 redo로도 복원이 안 될 수 있다.

주목할 점은 발생 조건이 매우 좁다는 것이다:

- 전원 차단 **그 순간에 디스크로 내려가던(in-flight)** 페이지만 대상이고,
- 스토리지가 페이지 크기의 원자 쓰기를 보장하지 않을 때만 발생한다.

### 1.3 비교표

| | fsync 누락 (이 버그) | torn page (DWB가 막는 것) |
|---|---|---|
| 장애 원인 | OS 페이지 캐시 증발 | 페이지 크기 > 원자 쓰기 단위 |
| 피해 형태 | 페이지가 통째로 **옛 버전** | 페이지가 **반반 섞임** |
| 피해 범위 | 마지막 실제 sync 이후의 **모든** 미동기화 페이지 | 정전 순간 in-flight였던 **소수** 페이지 |
| 발생 확률 | 정전 시 사실상 **결정적** | 정전 시에도 확률적, 좁은 창 |
| 스토리지로 회피 가능? | **불가능** (페이지 캐시는 항상 스토리지 위에 있음) | **가능** (원자 쓰기 보장 스토리지) |
| 다른 DB의 대응 | 모든 DB가 checkpoint에서 fsync | InnoDB doublewrite, PostgreSQL full_page_writes — 그리고 **모두 끄는 옵션 제공** |

핵심은 마지막 두 줄이다. torn page는 스토리지 계층에서 원천 차단할 수 있어
방어를 끄는 것이 정당한 선택지가 되지만, lost write는 **어떤 스토리지도
대신 막아줄 수 없다.** fsync 호출 자체가 유일한 방어다.

## 2. "DWB=0은 정합성 포기"라는 전제가 틀린 이유

DWB를 끄는 것은 보통 "corruption을 감수하겠다"가 아니라 **"torn page 방어를
스토리지 계층에 위임하겠다"**는 운영 판단이다. 페이지 크기 이상의 쓰기
원자성을 스토리지가 보장하면 torn page는 물리적으로 발생할 수 없고, DWB는
순수 오버헤드(모든 페이지를 두 번 쓰기)가 된다.

실제로 그런 보장을 제공하는 계층이 셋 있다.

### 2.1 ZFS — Copy-on-Write라서 제자리 덮어쓰기 자체가 없음

torn page의 전제는 "기존 페이지를 제자리에서(in-place) 덮어쓰다가 중간에
끊기는" 상황인데, ZFS는 이 전제를 제거한다.

- 16KB를 쓰면 기존 블록을 건드리지 않고 **새 위치에 새 블록을 통째로** 쓴다.
- 새 블록이 완전히 써진 뒤에야 부모 메타데이터의 블록 포인터(체크섬 포함)를
  새 위치로 바꾸고, 이 변경은 트랜잭션 그룹 커밋을 타고 최상위 uberblock
  갱신(섹터 단위 원자 쓰기)으로 확정된다.
- 크래시 시점이 어디든 결과는 둘 중 하나다: 포인터가 아직 옛 블록을
  가리킴(온전한 옛 페이지) 또는 새 블록을 가리킴(온전한 새 페이지).
  **반반 섞인 상태는 포인터로 도달할 수 없는 위치에 있으므로 관측 자체가
  불가능하다.**
- 덤으로 모든 블록에 체크섬이 있어 하위 디바이스의 부분 쓰기도 읽기 시점에
  검출된다.

MySQL/InnoDB에서 ZFS 위에 올릴 때 `innodb_doublewrite=OFF`가 문서화된
관행인 것이 정확히 이 이유다 (단, ZFS `recordsize`를 DB 페이지 크기에
맞추는 것이 전제).

### 2.2 NVMe — 스펙 차원의 원자 쓰기 보장 (AWUPF)

NVMe 스펙에는 **AWUPF**(Atomic Write Unit Power Fail) 필드가 있다.
컨트롤러가 "이 크기 이하의 쓰기는 전원 장애가 나도 all-or-nothing"이라고
보고하는 값이다. 구현은 보통 컨트롤러 내부의 커패시터 백업 캐시
(power-loss protection)로, 전원이 끊겨도 잔류 전력으로 진행 중인 쓰기를
완결하거나 통째로 버린다.

AWUPF ≥ DB 페이지 크기인 디바이스라면 16KB 쓰기가 하드웨어 차원에서
원자적이므로 torn page가 불가능하다. 단, 중요한 단서가 있다: **I/O가
쪼개지지 않고 정렬된 채로 디바이스까지 도달해야 한다.** 파일시스템이나
블록 레이어가 16KB를 두 개의 bio로 분할하면 보장이 깨진다. Linux가 최근에야
`RWF_ATOMIC`(untorn writes, 6.11+) 인터페이스를 추가한 이유이고, "아무
NVMe나 꽂으면 안전"이 아니라 스택 전체가 갖춰져야 성립한다.

### 2.3 SAN / 엔터프라이즈 어레이 — 배터리 백업 NVRAM 캐시

엔터프라이즈 스토리지 어레이는 쓰기가 **배터리/커패시터로 보호되는 NVRAM
캐시에 완전히 적재된 시점에 ack**를 돌려준다. 전원이 나가도 캐시에 통째로
들어간 쓰기는 복구 후 디스크로 마저 내려가고(destage), 통째로 못 들어간
쓰기는 ack된 적이 없으니 없던 일이 된다. "절반만 매체에 닿은 상태"가
호스트에게 관측되지 않는다. 다만 이는 스펙 필드가 아니라 벤더 구현 보장이라
어레이별 문서 확인이 필요한 영역이다.

### 2.4 공통점, 그리고 한계

세 경우 모두 **"페이지의 절반만 디스크에 남는 순간"을 관측 불가능하게**
만든다 — 정확히 DWB가 소프트웨어로 흉내 내는 일이다. 그래서 이런 환경에서
DWB는 중복 비용이고, 끄는 옵션이 존재하는 것이다.

그러나 셋 다 보장하는 것은 **원자성뿐**이다. OS 페이지 캐시는 여전히 이들
**위에** 있다. `write()`만 하고 fsync를 안 하면 데이터는 ZFS에도, NVMe에도,
SAN에도 아직 도달하지 않은 상태다. 즉:

> 가장 안전한 스토리지를 골라 DWB를 끈 모범적인 운영자일수록, 이 버그
> (fsync 스킵) 때문에 **"안전해서 껐는데 오히려 모든 정전에서 데이터가
> 깨지는"** 역설적 상황에 놓인다.

## 3. torn page가 가능한 스토리지에서 DWB를 껐다면?

"그럼 원자성 보장이 없는 일반 디스크에서 DWB를 끈 경우는? 그땐 진짜
어차피 깨지는 것 아닌가?" — 이 경우조차 답은 같다. **피해의 성격과 규모가
다르기 때문이다.**

- torn page: 정전 순간 in-flight였던 소수 페이지가 **확률적으로** 깨진다.
  좁은 시간 창, 제한된 페이지 수.
- fsync 누락: 마지막 실제 sync 이후 축적된 **모든** 미동기화 쓰기가, 정전이
  나기만 하면 **결정적으로** 유실된다. 시간 창의 크기에 상한이 없다
  (이 버그에서는 서버 기동 이후 영원히).

전자를 감수하는 선택이 후자까지 감수하는 선택을 함의하지 않는다. "자동차
에어백을 뺐으니 브레이크도 필요 없다"가 성립하지 않는 것과 같은 구조다.
게다가 두 장애는 증상도 다르다 — torn page는 checksum/복구 단계에서
드러나기라도 하지만, lost write는 복구가 **오류 없이 성공**한 뒤 한참
지나서 unique 위반이나 인덱스-데이터 불일치로 나타난다 (배경 문서 §3).

## 4. 이 논리가 수정 설계에 반영된 방식

이 질문의 답이 곧 `all_sync` out-parameter의 의미론 수정이다
(`src/storage/double_write_buffer.cpp`, `dwb_flush_force`):

| 상황 | 버그 이전 | 수정 후 |
|---|---|---|
| DWB 활성, flush 완료 | `all_sync=true` | `true` 유지 — DWB의 file sync helper가 데이터 볼륨 fsync까지 실제로 수행했으므로 정당한 보증 |
| DWB 미생성 (`size=0`) | `all_sync=true` ("할 일 없음") | **`false`** — "할 일이 없었다"는 "디스크에 내렸다"는 보증이 아니다 |
| 실행 중 DWB가 동시 비활성화 | `all_sync=true` | **`false`** — 비활성화 이후 직접 볼륨에 쓰인 페이지는 DWB가 보증 못 함 |

`all_sync=false`를 받은 호출자(`fileio_synchronize_all`,
`src/storage/file_io.c:4624`)는 이미 올바른 폴백을 갖고 있다: 전 영구 볼륨
순회 fsync. 즉 이 수정은 "DWB가 꺼졌으니 내구성도 포기"가 아니라 **"torn
page 방어는 스토리지에 위임하되, 내구성 보장의 책임은 caller가
넘겨받는다"**는 역할 분리를 코드에 명시한 것이다.

## 5. 요약

1. **fsync = 내구성·순서** (write-ahead 불변식), **DWB = 쓰기 원자성**.
   서로 대체재가 아니라 직교적 보호 장치다.
2. DWB=0은 정합성 포기가 아니라, torn page 방어를 ZFS(CoW), NVMe(AWUPF),
   SAN(NVRAM 캐시) 같은 스토리지 계층에 위임하는 정식 지원 구성이다.
3. 그 스토리지들은 원자성만 보장할 뿐 OS 페이지 캐시의 내구성은 보장하지
   않으므로, fsync는 어떤 구성에서도 생략할 수 없다.
4. torn page가 가능한 스토리지에서조차, 확률적·국소적 피해(torn)를 감수하는
   선택이 결정적·전면적 피해(lost write)까지 감수하는 선택을 함의하지 않는다.
