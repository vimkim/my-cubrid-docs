# CBRD-28062: `oos_trigger_threshold` 스윕 측정 (기본값 → 최대, develop 대비)

작성일 2026-11-19, Asia/Seoul. 작성: Claude Code 세션(work-tracker 982).
관련: [CBRD-28062](https://jira.cubrid.org/browse/CBRD-28062), [CBRD-27788](https://jira.cubrid.org/browse/CBRD-27788) AC-P2, [CBRD-27785](https://jira.cubrid.org/browse/CBRD-27785) AC-P3, 앞선 측정 [CBRD-27788 AC-P2·AC-P3 재측정](../CBRD-27788/CBRD-27788-ac-p2-p3-remeasure_67220b7_claude.md).

CBRD-28062는 OOS 트리거 임계값을 정적 서버 파라미터 `oos_trigger_threshold`로 만든다. `0`은 자동(한 페이지에 행 4개가 들어가는 크기, 16KiB 페이지에서 4,060B, 티켓 기준)이고, 명시값은 25B부터 `heap_Maxslotted_reclength`(16KiB 페이지에서 16,236B)까지다. 티켓의 인수 조건은 파라미터를 기본값에서 최대까지 바꿔 가며 develop과 비교하는 스윕이다. 이 문서는 그 스윕의 결과다.

독자는 CBRD-28062의 소유자와 리뷰어다. 범위는 4~16KB 값 전체 읽기(CBRD-27788 AC-P2), 작은 컬럼 읽기, UPDATE와 INSERT, 저장 크기와 I/O다. **이 문서는 제품 기본값을 고르거나 바꾸지 않는다.** 그 결정은 소유자가 이 보고서를 읽고 내린다. 아래는 결정에 필요한 대가를 한 표씩 보여 준다.

## 수치를 읽는 법

- 변화율은 `(base − X) / base`다. 좋아지면 +, 나빠지면 −다. CBRD-27788 재측정과 같은 부호다. base는 develop이다.
- 판정 지표는 서버 프로세스의 `instructions:u` 중앙값이다. 잠정 목표는 −2%보다 나쁘지 않은 것이다. cycles와 실행 시간은 판정에 쓰지 않는다. 공유 호스트라 load average(1분)가 측정 단위 시작·끝 기준 7~141이었다.
- 표의 열 이름 `0`, `5,000` 같은 숫자는 `oos_trigger_threshold`(바이트)다. `0`이 기본값이고 `16,236`이 최대다.
- 결론과 본문의 주장에 (측정) 또는 (추론)을 붙였다. (측정)은 이 실행의 표본에서 읽은 값이다. (추론)은 코드나 다른 측정에서 미루어 본 것이고 이번에 확인하지 않았다.
- 잡음의 크기. 읽기 표본의 spread(최대−최소 / 중앙값)는 엔진 7개 모두 1.3% 이하이고, 라운드 1과 2의 변화율 차이는 최대 1.0%p다. INSERT·UPDATE의 spread는 최대 2.4%이고 라운드 차이는 최대 0.6%p다. 이보다 작은 차이는 구분하지 못한다고 읽는다.

## 결론

- **기본값(0)에서 AC-P2는 목표 밖이다. (측정)** 12개 전체 읽기 케이스가 develop보다 명령어를 2.67~69.81% 더 쓴다. 값이 작을수록 나쁘다. CBRD-27788 재측정의 head 결과(2.8~69.5%)와 같은 모양이다.
- **최대(16,236)에서 AC-P2는 목표 안이다. (측정)** 같은 12개가 −0.16%~+0.03%이고 라운드별 값도 모두 −0.34% 이내다. 14.5KB heap 행(io_bench)도 최대에서 −0.07%~+0.08%다. 최대에서는 4~16KB 값이 모두 heap에 남아 develop과 같은 경로를 탄다. 이 판정은 위 기본값 판정과 따로 읽는다.
- **중간 값에서는 크기마다 한 단계에서 목표 안으로 들어온다. (측정)** −2%보다 나쁜 케이스가 임계값 0, 5,000, 7,000, 10,500, 14,500에서 12, 9, 6, 3, 0개다. 각 크기는 heap에 남는 단계에서만 develop과 같아지고(±0.3% 안), 그 앞 단계에서는 OOS라서 나쁘다. 14,500에서 이미 네 크기 모두 목표 안이다(−0.20%~+0.07%).
- **작은 컬럼 읽기의 이득은 같은 단계에서 사라진다. (측정)** OOS일 때 작은 컬럼 조회는 6.0KB +26.2%, 9.9KB·13.8KB +59.7~59.9%다. heap으로 돌아오면 −0.63%~+0.29%로 develop과 같다. 4.6KB는 OOS일 때도 −2.38%라 이득이 없다. 즉 AC-P2를 맞추는 임계값이 이 이득을 내놓는 임계값이다. cold 시작 직후 작은 컬럼 조회가 읽는 페이지는 6,671~20,003쪽에서 99쪽으로 준다(측정).
- **UPDATE와 INSERT는 방향이 갈린다. (측정)** heap에 남을 때 UPDATE는 −0.10%~−1.10%(목표 안)이고 INSERT는 +1.91%~+6.93%(develop보다 적게 쓴다, 원인은 확인하지 않았다). OOS일 때 INSERT는 −1.21%~−23.39%(값이 작을수록 나쁘다)이고, 작은 컬럼 UPDATE는 +1.26%(4.6KB)~+16.94%(13.8KB), 큰 컬럼 UPDATE는 6.0~13.8KB에서 +6.57%~+12.66%, 4.6KB에서 −3.38%다.
- **저장 크기는 OOS에서 늘고 최대에서 줄어든다. (측정)** 4~16KB 표는 OOS일 때 페이지 합계가 +0.5%~+1.4%다. 14.5KB heap fixture는 OOS 값이 있으면 +33.3%이고 최대에서 +0.0%다. 22KB overflow fixture는 기본값 +10.0%, 5,000·7,000에서 +16.6%, 10,500·14,500에서 ±0%, 최대에서 −25.0%다.
- **22KB overflow 행(AC-P2 범위 밖, 참고)은 최대에서도 목표 밖이다. (측정)** 큰 값 하나를 읽는 q4가 −3.12%, 모든 컬럼을 읽는 q5가 −1.43%(목표 안), 작은 컬럼 q1이 +36.61%다. q4는 임계값 0에서 −0.82%, 10,500·14,500에서 −4.19%·−4.18%, 최대에서 −3.12%다. 작은 컬럼 이득은 임계값을 올릴수록 줄어든다(+73.33% → +36.61%).
- **작은 행(92B) 대조군은 임계값과 무관하게 같다. (측정)** scan −0.62%~−0.74%, 조건 scan ±0.10%, UPDATE −1.18%~−1.34%다. 모두 목표 안이다. 임계값과 무관한 상시 비용이므로 head가 OOS 통합 코드를 develop 위에 얹은 비용으로 본다(추론).
- **heap에 남는 값의 cold 작은 컬럼 조회는 −1.61%~−2.10%다. (측정)** 서버 시작 직후 첫 질의에서 명령어가 4.6KB는 0.74M, 13.8KB는 2.28M(16,236 기준) 더 든다. 13.8KB는 14,500·16,236에서 −2.03%·−2.02%로 −2% 경계다. warm 작은 컬럼은 −0.63%~+0.29%다. 표본이 2개이고 원인은 확인하지 않았다.

크기 이름은 CBRD-27788과 같다. `4.6KB`는 표 `w36`(`big VARCHAR(20000)`에 4,608자), `6.0KB`는 `w47`, `9.9KB`는 `w78`, `13.8KB`는 `w110`이고 각 20,000행이다. 값은 SHA2-512 hex 연결이다. 질의는 `length`=`SUM(LENGTH(big))`, `substr`=`SUBSTR(big,4000,1)='a'` 조건 `COUNT(*)`, `LIKE 전체`=`big LIKE '%G%'`(hex에 없는 문자라 모든 byte를 읽는다), `작은 컬럼`=`COUNT(*), SUM(a)`다. 서버는 기본 설정대로 병렬 heap scan(worker 4개)을 쓴다. cold 표본의 trace로 확인했다. 모든 질의는 결과 값을 검증한다.

- 네 크기가 임계값 5,000, 7,000, 10,500, 14,500에서 각각 한 번씩 heap으로 돌아온다. 컷 포인트는 이 fixture의 행 크기(`Avg_rec_len` 4,646 / 6,032 / 9,872 / 13,763B)에서 정했고 조정할 필요가 없었다. 16,236은 네 크기에 새로 바꾸는 것이 없다. 이 값이 의미를 갖는 곳은 아래 14.5KB·22KB fixture다.
- 14.5KB heap fixture(평균 행 14,480B)는 14,500에서도 컬럼 하나가 OOS로 간다. 코드는 `header_size + payload_size + mvcc_extra`를 목표와 비교한다(`src/storage/heap_file.c:14161-14162` at `49d8df0dd5`). 보고된 평균 행 크기보다 MVCC 헤더만큼 더 크기 때문으로 본다(추론). 이 행이 heap에 남는 첫 값은 16,236이다(측정).
- 22KB 행은 develop에서 overflow다. head는 행마다 OOS로 4개(0), 3개(5,000·7,000), 2개(10,500·14,500), 1개(16,236)를 보낸다.
- 파라미터는 서버 기동 때 읽는 정적 값이다(`heap_manager_initialize`, `src/storage/heap_file.c:3967-3973` at `49d8df0dd5`). 한 DB를 다른 값으로 다시 기동했을 때 기존 행이 옮겨지지 않는다고 본다(추론, 이번에 확인하지 않았다). 그래서 값마다 DB를 따로 만들었다.

## 한계와 측정 중 일어난 일

- **압축된 payload로 잰 첫 INSERT·큰 컬럼 UPDATE는 버렸다.** 첫 단계는 값을 `REPEAT('0123456789abcdef', n)`으로 만들었다. 이 값은 LZ4로 행당 약 92B까지 줄어 OOS나 heap 배치를 시험하지 못했다(`SHOW HEAP CAPACITY`의 평균 행 길이 92B로 발견했다). 그 결과는 표에 쓰지 않았고, SHA2 source 표의 값으로 다시 쟀다(위 표). 작은 컬럼 UPDATE는 fixture 행을 복제하므로 첫 단계 값을 그대로 썼다. 도구는 이제 표본마다 저장된 바이트가 값 길이의 90% 이상인지 확인한다(random hex는 LZ4로 약 2% 줄어서 98%가 아니라 90%로 잡았다).
- **로그 보존.** 첫 단계(cpu)는 `log_max_archives` 기본값(무제한)으로 돌렸고 sw DB마다 archive 로그가 26~45GB 쌓였다. 디스크가 찰 위험이 있어 sw DB 섹션에 `log_max_archives=2`를 넣고 오래된 archive를 지웠다(내 측정 DB만). INSERT·큰 컬럼 UPDATE 재측정(dml2)은 이 설정으로 돌렸다. 모든 엔진이 같은 설정이고 표의 변화율은 단계 안에서 base와 비교한 값이다. cpu 단계와 dml2 단계의 절대 명령어 수는 서로 비교하지 않는다.
- **디스크가 찼다.** 측정 중 같은 볼륨에 다른 세션이 쓰는 큰 파일(57.7GB)과 내 archive 로그로 볼륨이 가득 차서 io_bench 단계가 한 표본(heap q5, 임계값 10,500)에서 중단됐다. 중단된 표본은 버리고 처음부터 다시 쟀다. 중단 때 남은 io 서버(`iot10500`)는 내가 멈췄다. 다른 세션의 파일은 건드리지 않았다.
- **서버가 겹친 단위를 다시 쟀다.** 내가 단계 순서를 잘못 이어 base 서버가 cold 단위 `r1-t14500` 위에 약 17초 겹쳐 돌았다. 그 단위는 버리고(`failed/`에 보존) 다시 쟀다. 겹친 서버가 만든 표본은 쓰지 않았다.
- dml2 단계는 시작 직후 두 번 실패했다. 한 번은 앞서 중단한 실행이 남긴 표 때문이고(표 생성 전에 `DROP TABLE IF EXISTS`를 넣었다), 한 번은 저장 바이트 검증 기준이 98%라서 13.8KB 값(97.6%)을 거부했기 때문이다(90%로 낮췄다). 실패한 부분 결과는 쓰지 않았고 처음부터 다시 돌렸다.
- 표본 수가 적다. cold는 2개, io_bench는 3개이고 INSERT·UPDATE는 8~20개다. 이 표본에서 변화율 차이가 spread보다 작은 칸은 판정하지 않았다.
- 원인을 프로파일로 확인하지 않았다. 값이 작을수록 나쁜 이유, INSERT가 heap에서 develop보다 적게 드는 이유, 4.6KB 작은 컬럼이 OOS에서 나쁜 이유, heap 배치에서 cold 작은 컬럼 조회가 더 드는 명령어가 모두 (추론) 또는 미확인이다.
- 쓰지 않은 것: 임계값 25B~4,060B 구간, 임계값 변경 뒤 재기동한 DB, 실행 시간 판정(공유 호스트), 파일 캐시를 비운 cold(`file-evict`), warm io_bench, q2·q3, 동시 접속, vacuum 비용, HA·복제, 22KB 말고 다른 overflow 크기.
- 22KB overflow 행은 AC-P2 범위(4~16KB) 밖이다. AC-P3 관련 참고로만 적었다.
