## A. 문제 정의 · 동기 (slides 2–3)

### 🔴 A-1. Narrow read 가 정말 병목인가? Buffer pool 이 크면 hot page 는 어차피 메모리에 있다.

현대 서버는 메모리가 싸다. 자주 읽는 페이지는 buffer pool 에 상주하므로, "작은
컬럼 읽는데 큰 payload I/O" 는 **disk-bound 워크로드에서만** 성립하는 것 아닌가?

- **방어**: 큰 컬럼이 인라인이면 페이지당 행 수가 줄어 **같은 buffer 로 캐시할 수
  있는 행 수 자체가 준다** — 이득은 disk I/O 만이 아니라 buffer 효율(working set
  밀도)에도 있다. memory-resident 여도 scan 이 만지는 페이지 수가 줄면 CPU 캐시와
  latch 비용도 준다. 정량화는 S1/S3 에서 cold/warm 캐시를 나눠 측정한다.
- **솔직한 약점**: buffer 크기를 바꿔가며 측정하는 스윕이 시나리오에 없다. 지적
  받으면 S1/S3 에 buffer 스윕 축을 추가하겠다고 받는다.

### 🔴 A-2. "큰 컬럼은 가끔 읽는다"는 가정의 근거는? 실제 워크로드 데이터가 있나?

접근 빈도 가정이 무너지면 (큰 컬럼이 hot 이면) OOS 는 순손해다.

- **방어**: 가정이 아니라 **분리** 가 목적이다 — access pattern 이 어느 쪽이든,
  작은 컬럼과 큰 컬럼의 I/O 를 서로 독립으로 만든다. 큰 컬럼이 hot 한 테이블은
  OOS 트리거 자체가 안 되게 스키마를 잡으면 되고, per-column 제어
  (`STORAGE PREFER_INLINE`, CBRD-26912 proposed) 가 그 안전판이다.
- **솔직한 약점**: 국내 고객 워크로드에서 "wide row + narrow read" 비중을 조사한
  데이터는 없다. TOAST/off-page 가 PG/MySQL 에서 표준이 된 것을 간접 근거로 쓰되,
  고객 사례 수집은 후속 과제로 인정한다.

### 🟡 A-3. 애플리케이션에서 분리하면 되지 않나 — 별도 테이블 + FK, 수직 분할?

엔진에 이 복잡성(새 파일 타입, vacuum 연동, recovery 경로)을 넣을 가치가 있나?

- **방어**: 애플리케이션 분리는 (1) 기존 스키마 전면 수정 요구, (2) JOIN 비용,
  (3) 트랜잭션 원자성 관리를 사용자에게 전가한다. 저장 엔진이 투명하게 해주는
  것이 DBMS 의 존재 이유고, PG(TOAST)/MySQL(off-page)/Oracle(LOB) 전부 같은
  결론에 도달했다.
- **재반격 대비**: "그럼 왜 지금까지 CUBRID 엔 없었나" → 기존 overflow 가 record
  단위로 같은 역할을 했지만 column 단위 분리가 없어 narrow read 이득이 없었다.

### 🟡 A-4. `DB_PAGESIZE/4` (4KB) gate 의 근거는? 실험으로 정했나, 관습인가?

- **방어**: PostgreSQL 과 같은 비율이다 — PG 의 `TOAST_TUPLE_THRESHOLD` ≈ 2KB 는
  8KB 페이지의 1/4 이고, 우리는 16KB 페이지의 1/4 = 4KB. "페이지당 최소 4행"
  이라는 slotted page 의 오래된 휴리스틱을 공유한다. M1 의 /8 (2KB) 에서 /4 로
  올린 것은 과잉 demotion 을 줄이기 위해서였다 (CBRD-26776).
- **솔직한 약점**: 우리 페이지 크기·워크로드에서 1/4 이 최적이라는 실험은 없다.
  gate 를 파라미터로 스윕하는 실험은 좋은 후속 과제 — 지적받으면 수용.

### 🟡 A-5. Column floor 16B 는 너무 낮지 않나 — 17B 값을 내보내면 1B 아끼자고 read I/O 한 번을 산다.

- **방어**: floor 는 "내보내면 record 가 줄어드는가"의 **논리적 하한**(포인터
  크기)이지 "내보낼 가치가 있는가"의 경제적 하한이 아니다. 실제로는
  largest-first + early stop 이라 작은 컬럼은 큰 컬럼으로 gate 를 못 맞출 때만
  나간다 — 17B 컬럼이 나가는 경우는 이론상 존재하나 병리적 스키마다.
- **재반격 대비**: "그 병리적 케이스에 하한을 두면 되지 않나" → 두면 그 스키마는
  저장 불가(에러)가 된다. 저장 가능성을 우선했다. PG 도 같은 구조다.

## B. Insert/Delete-only · Always-new-OID (slides 12–14) — 예상 최대 격전지

### 🔴 B-1. 굳이 insert/delete only 를 고른 이유가 뭔가? 타당한가?

OOS record 에 update 를 안 만든 것이 단순화인가 회피인가.

- **방어 (3단)**:
  1. **MVCC 정합성** — CUBRID 는 in-place MVCC 로, 옛 버전 독자가
     `prev_version_lsa` → undo recdes → 옛 OID 로 옛 값을 읽는다. OOS record 를
     in-place update 하면 옛 독자가 깨진다. 즉 "OOS update" 를 만들려면 OOS
     자체에 버전 체인을 또 만들어야 하는데, 그 버전 관리는 heap 이 이미 하고
     있다. **버전 관리를 한 곳(heap)에만 두는 것이 이 설계의 핵심 결정**이다.
  2. **불변식 단순성** — always-new-OID 라서 old/new OID 가 항상 서로소고, undo
     recdes 에서 뽑은 OID 는 무조건 지워도 된다는 vacuum forward-walk 의 논리가
     성립한다. OID 재사용을 넣는 순간 "이 OID 를 post-image 도 쓰는가" 판별이
     필요해진다 (CBRD-26516 의 전제조건으로 명시돼 있다).
  3. **선례** — PG TOAST 도 chunk 는 immutable, update 시 새 TOAST 값을 쓴다.
     차이는 PG 가 **미변경 컬럼의 포인터를 재사용**한다는 것 — 그것이 우리의
     future 과제(dedup)다.
- **솔직한 약점**: 미변경 컬럼까지 새 OID 를 만드는 것은 순수 낭비가 맞다. M1
  단순성의 대가이며 S5 가 이 비용을 정량화한다. "그 낭비가 크면 dedup 을
  앞당긴다"가 정직한 답.

### 🔴 B-2. (사용자 예시 질문) 현대 디스크는 I/O 가 굉장히 빠르다. Write amplification 만 나쁘고, 저장 공간 낭비 + vacuum CPU 병목 + 트랜잭션 병목만 생기는 것 아닌가?

NVMe 시대에 read I/O 절약은 사소하고, 쓰기 증폭·GC 부담이라는 비용이 더 크지
않은가 — OOS 의 손익 자체에 대한 근본 질문.

- **방어 (구조 분해)**:
  1. **쓰기 증폭의 실제 증가분을 분리하라** — 인라인일 때도 UPDATE 는 record
     전체를 다시 쓰고 undo 에 전체 사본을 남긴다. OOS 후에는 heap record 가
     작아져 heap 쪽 쓰기·undo·WAL 은 오히려 준다. 순증가분은 정확히 **"값이 안
     바뀐 큰 컬럼의 재기록"** (B-1 의 약점) 하나다. 전체 write path 가 증폭되는
     것이 아니다.
  2. **read 이득은 I/O 속도가 아니라 밀도** — A-1 과 동일: NVMe 가 빨라도 buffer
     pool 밀도와 scan 페이지 수는 여전히 성능을 지배한다.
  3. **vacuum 병목** — OOS 삭제는 vacuum 이 **이미 그 heap record 를 정리하러 간
     김에** 하는 일이라 별도 스캔이 없다. 추가 비용은 OID 당 `oos_delete` 한
     번이고, 독립/동일 sysop 으로 트랜잭션 경로와 분리돼 있어 사용자 트랜잭션을
     막지 않는다.
  4. **그래도 수치로 답한다** — 이 질문이 정확히 S2(read 비용), S4(insert),
     S5(안 바뀐 컬럼 재기록), S6(공간 회수) 를 설계한 이유다. 측정값 없이
     단정하지 않는다.
- **솔직한 약점**: vacuum lag 시 dead OOS 가 쌓여 파일이 커지는 것은 사실이고
  (G-2 와 연결), vacuum 처리량 자체를 재는 시나리오가 현재 없다 — 지적받으면
  S6 에 vacuum 지연·처리량 축을 추가한다고 받는다.

### 🔴 B-3. SA_MODE 는 eager delete, SERVER_MODE 는 vacuum — 모드마다 생명주기가 다르면 테스트 표면이 2배고, 실제로 CBRD-26950 같은 버그의 온상 아닌가?

- **방어**: SA_MODE 는 vacuum 데몬이 없으므로 구조적으로 불가피한 분기다. 대신
  eager 경로는 old∩new 비교라는 더 단순한 로직이고, 26950 은 SERVER_MODE
  vacuum retry 의 문제지 모드 분기 자체의 문제가 아니다.
- **솔직한 약점**: 두 경로의 동작 차이를 체계적으로 대조하는 테스트 매트릭스는
  아직 없다 (CBRD-26665 범위로 흡수 예정이라고 답).

## C. 저장 구조 선택 (slides 4–7)

### 🔴 C-1. TOAST table 방식을 기각한 진짜 이유가 뭔가? CUBRID 는 이미 heap+btree 다중 파일 원자성을 sysop 으로 다루고 있는데.

- **방어 (두 축)**:
  1. **접근 경로가 결정의 축** — TOAST 는 값을 읽을 때마다 logical key
     (`chunk_id`) 로 toast index (btree) 를 탄다: key → btree 탐색 → chunk
     tuple. OOS 는 **물리 locator (OOS OID) 로 페이지를 직접 fix** — 역참조
     1회, btree 없음. 값 접근은 OOS 의 최빈 연산이므로 최단 경로를 우선했다.
  2. **결합도** — 별도 relation 은 카탈로그 등록/권한/통계/DDL 경로와 전부
     얽힌다 (물리적 원자성 문제가 아니라 논리적 결합 문제). 전용 파일은 heap
     내부로 캡슐화되고, 팀이 15년+ 다뤄온 overflow file 패턴을 참조할 수 있어
     구현 리스크도 낮다.
- **대가 (선제 인정)**: 물리 locator 라 replication/HA 가 OID 를 그대로 복사할
  수 없다 — replica 가 자체 `oos_insert` 로 값을 다시 넣고 OID 를 바꿔 다는
  구현을 M1 에서 치렀다 (값 동등성만 보장, OID 동등성 없음). 관측 도구도 자체
  구현이 필요하다 (G-1, CBRD-26871).
- **재반격 대비**:
  - "toast index 는 캐시에 상주해 저렴하다" → 상주해도 탐색 CPU 와 상위 페이지
    latch 경합은 남고, 큰 값 read 마다 반복된다. 정량 비교 실험은 없다 —
    인정하되 구조적 우위(단계 수) 논거로 방어.
  - "spacedb/checkdb 가 공짜였을 텐데" → 맞는 지적. 그 대가를 owner descriptor
    (CBRD-26871) 로 회수 중.

### 🟡 C-2. Slotted page 공유 — hot table 에 INSERT 가 몰리면 bestspace 가 같은 페이지를 계속 주고, latch 경합이 페이지 분산을 강제해 공간 효율이 떨어진다. 경합↔효율 상충 분석은?

- **방어**: zero-wait conditional latch 라 경합 시 대기 없이 다음 후보로
  넘어간다 — 경합이 심하면 자연히 분산되고, 한가하면 조밀하게 찬다. 적응적
  동작이 설계 의도다.
- **솔직한 약점**: 동시 INSERT 부하에서 페이지 점유율 분포를 측정한 적 없다.
  S4 를 멀티 세션으로 확장하겠다고 받는다 (H-1 과 연결).

### 🟡 C-3. 테이블당 OOS file 1개 — 파일 수가 테이블 수만큼 늘어난다. 전역 공유 OOS 저장소가 아니라 1:1 인 이유는?

- **방어**: DROP TABLE 시 파일째 반납(`oos_file_destroy`)이 가능한 것이 1:1 의
  최대 이점 — 전역 저장소면 테이블 삭제가 per-record GC 가 된다. 공간 격리,
  per-table 통계(향후), TDE 적용 단위도 깔끔하다. 파일 수는 기존에도 heap +
  overflow + btree 로 테이블당 여러 개라 관리 체계는 동일하다.

### 🟡 C-4. OOS OID 16B 중 위치 정보는 8B 뿐이고 나머지는 length — PG 18B 와 "포인터 크기" 비교는 공정한가? volid 2B/pageid 4B 는 용량 확장 한계 아닌가?

- **방어**: PG 의 18B (va_valueid 등) 도 길이/원본 크기를 포함한 값이라 비교는
  동일 조건이다. volid/pageid 폭은 CUBRID 전역 주소 체계(OID) 그대로라 OOS 가
  새 한계를 만들지 않는다 — 한계를 손대는 일은 OOS 범위 밖의 엔진 전체 과제.
- **파생 질문 대비**: chunk 의 next 포인터가 8B 인 이유 — chunk 는 길이가 chunk
  자신에 있으므로 위치 8B 면 충분, inline 은 길이 조회 I/O 를 없애려고 16B
  (CBRD-26630). 포맷이 두 개인 것은 목적이 두 개라서다.

### 🟢 C-5. RECDES 4B 길이 한계로 OOS 값도 2GB 제한 — full_length 는 8B 인데 왜?

- **방어**: 알고 있는 설계 제한이다 (known limitation 문서화됨). 8B 는 포맷을
  미리 넓혀둔 것이고, 2GB 를 넘기려면 RECDES/API 전반의 8B 화가 필요해 별도
  과제다. 현 고객 요구엔 2GB 로 충분하다.

## D. Demotion 정책 (slides 8–9)

### 🔴 D-1. Largest-first 가 항상 옳은가? 접근 빈도를 모르면 가장 큰 컬럼이 가장 hot 일 수 있다. PG 는 `SET STORAGE` 로 사용자 제어를 주는데.

- **방어**: 빈도 정보가 없을 때 record 축소 효율이 최대인 순서가 largest-first
  고, PG 기본 정책도 동일하다. 사용자 제어는 `STORAGE PREFER_INLINE`
  (CBRD-26912, proposed) 으로 설계돼 있다 — largest-first 정렬 키에 사용자
  선호를 앞세우되, 안 들어가면 결국 내보내는 soft 정책이라 "record 는 페이지에
  들어간다" 불변식을 깨지 않는다.
- **솔직한 약점**: 26912 는 아직 proposed 다. "정책의 구멍이 아니라 로드맵의
  순서"라고 프레임.

### 🟡 D-2. 경계 flapping — record 가 4KB 근처에서 진동하면 UPDATE 마다 컬럼이 OOS 로 나갔다 들어왔다 한다. hysteresis 가 없다.

- **방어**: 나가는 것은 gate 초과 시점, 들어오는 것은 다음 UPDATE 가 gate
  이하일 때다. 어차피 M1 은 UPDATE 마다 OOS 를 새로 쓰므로 (always-new-OID)
  flapping 이 **추가 비용을 만들지 않는다** — 안 바뀐 컬럼도 재기록하는 비용에
  이미 포함돼 있다. dedup 이 들어오는 시점에 hysteresis 도 같이 설계해야 한다는
  지적은 타당하다.
- **솔직한 약점**: dedup 이후를 위한 경계 정책 설계는 아직 없다.

### 🟢 D-3. Over-demote 를 허용하는 보수적 추정 — header 를 매 반복 재계산하면 정확히 되는데 왜 안 하나?

- **방어**: VOT offset 폭(BYTE/SHORT/INT)이 demote 도중 바뀔 수 있어 정확
  계산은 레이아웃 재계산 반복이다. 틀려도 "한 컬럼 더 내보내는" 안전한
  방향뿐이고 발생 조건도 경계 근처로 좁다 — 단순성의 이득이 크다. PG 도 같은
  보수적 접근이다.

### 🔴 D-4. 압축이 먼저 아닌가? PG 는 compress → 그래도 크면 TOAST 다. 압축했으면 OOS 갈 일 자체가 없는 값이 대부분일 텐데 순서가 거꾸로다.

- **방어**: CUBRID 는 이미 VARCHAR ≥255B 를 type layer 에서 LZ4 압축한다 — 즉
  "압축 먼저"는 부분적으로 이미 있다. OOS 는 압축 후에도 큰 값의 문제를 푼다.
  전 타입 압축은 CTO 방향대로 type-serialization layer (`mr_data_writeval`) 에
  두는 것으로 정리됐고, 그 위치면 OOS 와 직교라 나중에 넣어도 OOS 설계가 안
  바뀐다.
- **재반격 대비**: "그럼 VARBIT/JSON 은 지금 미압축으로 OOS 에 들어가네?" →
  맞다, future 과제로 인정. 다만 그 값들은 지금도 미압축 인라인이므로 OOS 가
  상황을 악화시키진 않는다.

### 🟡 D-5. OOS + bigone 거부 — 기존엔 저장되던 스키마가 OOS 도입 후 에러가 되는 것 아닌가? 하위 호환 파괴다.

- **방어**: 아니다 — 거부되는 것은 "demotion 후에도 ~16KB 초과 + has_oos" 조합
  뿐인데, OOS 도입 전 같은 record 는 그냥 bigone 으로 저장됐고 **지금도 OOS
  트리거가 안 되는 형태면 bigone 으로 저장된다**. 문제가 되는 것은 variable
  컬럼이 OOS 로 나가고도 fixed 컬럼만으로 16KB 를 넘는 극단 스키마이며, 실측
  사례는 QA 의 인위적 케이스뿐이다. PG 는 아예 "row is too big" 에러다 — 우리는
  PG 보다 관대하다.
- **주의**: bigone 제거 로드맵(미래)이 실현되면 그때는 진짜 호환성 논의가
  필요하다 — "그 시점의 마이그레이션 설계 과제"로 미룬다.

## E. Read path (slides 10–11)

### 🔴 E-1. Expand opt-in 으로 바꿨더니 22곳 중 17곳이 잘못 마이그레이션됐고 unloaddb 누출(CBRD-26948)까지 났다 — 이 설계 자체가 실수 유발적이라는 증거 아닌가?

- **방어**: 반대다 — eager 였던 M1 이 "필요 없는 곳까지 Expand" 하는 비용을
  숨겼고, opt-in 전환의 census 가 그 17곳을 **드러낸** 것이다. 남는 문제는
  "raw-byte 소비 경로가 Expand 를 잊는 것"인데, 판별 기준(4가지: 전송/재삽입/
  비교/파싱)을 ADR 로 문서화했다.
- **솔직한 약점**: 컴파일 타임 강제가 없다 — expand 된 recdes 를 타입으로
  구분하는 방안은 좋은 제안으로 받고, 26948 재발 방지는 fetch-보이는-모든-바이트
  경로의 회귀 테스트(26659/26665)로 커버 예정.

### 🟡 E-2. 한 record 에 OOS 컬럼이 N 개, 각 M chunk 면 read 한 번에 page fix 가 N×M — latency 와 deadlock 표면이 커진다. batch/prefetch 는?

- **방어**: Resolve 는 lazy 라 **요청된 컬럼만** 읽는다 — N 은 projection 크기지
  스키마 크기가 아니다. 같은 페이지 다중 insert 의 fix 일원화(최적화 아이디어
  C)와 PEEK(D) 가 로드맵에 있다.
- **Deadlock 은 F-1 로 넘어감** — 여기서 정직하게 인정.

### 🟢 E-3. PEEK 없이 항상 COPY — 큰 값일수록 memcpy 낭비다.

- **방어**: 알려진 제한, future (M4 취소로 이월). COPY 는 latch 를 빨리 놓는
  이점도 있어 순수 손해는 아니다 — 큰 값 read 가 병목으로 측정되면(S2) 우선순위
  올린다.

## F. 동시성 · 정합성 (slides 13–16)

### 🔴 F-1. Ordered fix deadlock — 한 record 의 OOS 페이지 A, B 를 두 트랜잭션이 역순으로 fix 하면 데드락이다. M4 가 취소됐는데 이 리스크를 그냥 안고 가나?

- **방어**: 현재 read 경로는 컬럼 순(=VOT 순) 순회라 접근 순서가 사실상
  일정하고, write 는 새 페이지/bestspace 라 교차 fix 폭이 좁다 — 발생 조건이
  좁다는 판단으로 후순위였다. pageid 순 ordered fix 정책이 설계돼 있고(최적화
  E), 페이지 데드락은 기존 lock manager 탐지로 잡혀 hang 이 아니라 abort 다.
- **솔직한 약점**: "좁다"의 정량 근거가 없고 전담 이슈도 아직 없다 (M3 킥오프
  시 생성 예정으로 문서화돼 있음). 이 질문이 나오면 이슈 번호를 약속하는 것이
  최선.

### 🔴 F-2. CBRD-26950 (vacuum slot 재사용 데이터 손실) — owner/generation 필드는 디스크 포맷 변경인데, develop 머지 전에 넣어야 하는 것 아닌가?

- **방어**: 정확한 지적이고 그래서 머지 게이트다. develop 머지 전이라 포맷
  변경 부담이 없는 지금이 적기 — chunk header 에 owner OID(or generation) 를
  추가하는 방향으로 ANALYSIS 중. 대안인 retry-idempotent 설계(재삭제 전 소유
  검증)도 비교 중이며, 오늘 그 두 방향에 대한 의견을 구하는 것이 Q2 다.

### 🟡 F-3. Undo 가 OID 를 품는 설계 — undo log 와 OOS file 간 참조 무결성을 검증하는 도구(checkdb 류)가 있나? 깨지면 조용한 손상이다.

- **방어**: 현재 없다 — 정직하게 인정. WAL 완전성 + sysop 원자성이 1차 방어고,
  crash-recovery 테스트(26659/26665)가 시나리오 검증을 한다. OOS-aware checkdb
  확장은 owner descriptor(G-1) 가 들어오면 자연스럽게 가능해진다 — 좋은 후속
  과제로 수용.

### 🟡 F-4. Replication 에서 slave OID 불일치 — 논리 복제는 값 기반이라 좋다. 그런데 페이지 기반 도구(물리 백업/restore, incremental backup)와의 정합성은?

- **방어**: 물리 복제/백업은 페이지를 통째로 복사하므로 OOS 페이지도 같이 가서
  OID 가 보존된다 — 불일치는 **논리 replication 에만** 있는 성질이고, 각 경로는
  자기 안에서 일관적이다. 백업/restore 는 QA 매뉴얼 테스트 범위(26660)에서 검증
  중 (spacedb assert 사례처럼 유틸리티 이슈가 나오면 잡는다).

## G. 운영 · 관측 가능성 (slides 17, 21)

### 🔴 G-1. spacedb 에 OOS 가 안 보인다 — 운영자가 "디스크가 왜 찼는지" 알 수 없는 기능을 릴리스할 수 있나?

- **방어**: 현재는 TOAST 방식과 동일하게 "테이블 저장 공간"으로 합산해 보이게
  했고(출력 호환), per-table 귀속은 owner descriptor (`FILE_OOS_DES`) 로 설계돼
  있다 (CBRD-26871). 릴리스 노트에 관측 한계를 명시하고, 통계 노출을 develop
  머지 후 첫 후속으로 잡는 것이 현재 계획.
- **솔직한 약점**: release 빌드에서 "이 행이 OOS 로 갔는지" 확인할 방법이 debug
  `oos.log` 뿐이라 QA 게이트가 debug 빌드에 묶여 있다 — 알려진 부채.

### 🔴 G-2. 빈 OOS 페이지 반납이 없다 + bestspace fit-check 결함으로 6→26 페이지 증식 관찰 — delete-heavy 워크로드에서 파일이 단조 증가한다. 이대로 머지 가능한가?

- **방어**: fit-check 결함(+slot 과다 예약)은 원인·수정 방향이 확정된 버그로 M2
  내 수정 대상. 페이지 반납(CBRD-26786)은 slot 재사용(bestspace)이 있어 공간이
  **재활용은 되고** 파일 크기만 고수위로 남는 것 — heap 파일도 같은 정책이라
  엔진 관행과 일치한다. S6 이 delete→재삽입 후 파일 크기 추이를 정확히 재는
  시나리오다.
- **주의**: ADR-0001 (non-numerable 전환) 이 페이지 반납의 선행 조건임을 알고
  있음을 보여주면 신뢰를 얻는다.

### 🟡 G-3. TDE 누락(CBRD-26830) 은 "새 파일 타입 추가 시 챙길 목록"이 없다는 프로세스 문제 아닌가?

- **방어**: 맞다 — 개별 버그이자 프로세스 공백이다. 수정은 walker 분기 +
  lazy-create 인라인 TDE 이중 방어로 확정. 재발 방지로 "새 FILE_* 타입
  체크리스트"(TDE, spacedb, checkdb, tracker) 를 문서화하는 것을 이번 회고
  산출물로 삼겠다고 답하면 가장 좋은 그림.

### 🟡 G-4. unloaddb 말고 다른 유틸리티(compactdb, checkdb, backup, restoredb, killtran …)는 전수 검증했나?

- **방어**: QA 매뉴얼 테스트(26660)가 유틸리티 표면을 훑는 중이고, 실제로
  spacedb assert / unloaddb 누출이 그 경로에서 발견·수정됐다 — 프로세스가
  작동한다는 증거. 전수 완료 선언은 아직 못 한다 (26660 종료가 머지 게이트).

## H. 성능 측정 설계 자체에 대한 공격 (slides 18–20)

### 🔴 H-1. S1–S7 전부 단일 세션이다 — latch 경합, vacuum 경합, lock 대기는 하나도 측정 안 된다. 동시성 없는 스토리지 벤치마크가 의미 있나?

- **방어**: S1–S7 은 **경로별 비용 분해**가 목적인 1단계다 (어느 경로가 얼마나
  비싼가를 격리 측정). 혼합·동시 부하는 그 다음 단계로 설계하는 것이 맞고, 이
  자리에서 "S8: multi-session INSERT/UPDATE + vacuum 동시 실행" 을 추가하는
  피드백을 받고 싶다 — 라고 오히려 요청으로 전환 (Q4 와 연결).

### 🟡 H-2. Buffer 크기·데이터셋 크기 스윕이 없다 — in-memory 와 disk-bound 에서 결론이 뒤집힐 수 있다.

- **방어**: cold/warm 두 점은 있다. 스윕 축 추가 수용 (A-1 과 동일 대응).

### 🟡 H-3. VARBIT 만 쓰면 실제 고객 데이터(압축되는 VARCHAR)와 괴리 — 압축이 값을 줄이면 OOS 트리거 빈도 자체가 낮은데, 측정이 OOS 에 유리하게 편향된 것 아닌가?

- **방어**: VARBIT 는 **크기 제어**를 위한 계측 선택이지 대표 워크로드 주장이
  아니다 (압축 때문에 디스크 크기가 비결정적이면 시나리오 재현이 안 된다).
  보완으로 "압축 VARCHAR 현실 데이터셋" 변형을 S1/S2 에 추가할 수 있다 — 수용
  가능한 지적.

### 🟡 H-4. unloaddb 1.6–1.7× — 원인(`heap_attrinfo_start` per `heap_next`)을 아는데 왜 아직 안 고쳤나?

- **방어**: 수정이 heap scan 공통 경로를 건드려 리스크가 커서, 원인 격리까지만
  하고 M2 기능 완결(회수 경로) 을 우선했다. 26458 로 추적 중이며 머지 전 수정
  대상인지 여부가 오늘 논의 안건이 될 수 있다.

### 🟢 H-5. 지표에 latency 분포(p99)가 없고 elapsed 평균뿐이다.

- **방어**: 수용 — statdump 기반이라 평균 중심이었다. S1/S2 에 p95/p99 를
  추가한다.

## I. 큰 그림 · 로드맵 (slides 9, 22–23)

### 🔴 I-1. M3/M4 를 취소했다 — dedup, deadlock 대응, 모니터링이 전부 "future" 로 갔는데, 그 future 는 언제인가? 취소가 아니라 무기한 연기 아닌가?

- **방어**: M2 를 "develop 머지 가능 품질"이라는 단일 목표로 재정의하면서,
  머지에 불필요한 것을 전부 뒤로 뺀 것이다 (마일스톤 구조조정이지 포기가
  아니다). 머지 후 사용 데이터(S 시나리오 실측 + 고객 워크로드)가 future 항목의
  우선순위를 정한다 — dedup 이 그 첫 후보다.
- **주의**: "그 우선순위 판단을 위해 뭘 측정할 건가"까지 물으면 S5(재기록 비용)
  수치가 dedup 의 비즈니스 케이스라고 연결.

### 🔴 I-2. CRITICAL 2건(26950 데이터 손실, 26830 TDE)을 안고 develop 머지가 가능한가? 머지 게이트를 명시하라.

- **방어**: 불가능하다 — 두 건 모두 머지 블로커로 분류돼 있고, A/C 와 DoD 에
  반영돼 있다 (26950 수정 방향이 오늘 안건 Q2). 이 슬라이드(리스크)가 존재하는
  이유 자체가 "숨기지 않고 게이트로 관리한다"는 것.

### 🟡 I-3. bigone 을 OOS 로 일원화하는 미래 — heap record 최대 크기가 사실상 "fixed 부분 ≤ 한 페이지"로 줄어드는 것인데, 이것은 스펙 축소다. 사용자 공지/마이그레이션 계획 없이 방향만 말해도 되나?

- **방어**: 방향 검토 단계임을 명시했고 (슬라이드에도 "검토한다"), 실제 추진
  시 deprecation 정책·마이그레이션 도구가 선행돼야 한다는 데 동의한다. 오늘은
  "그 방향이 아키텍처적으로 타당한가"에 대한 의견을 구하는 것.

### 🟡 I-4. 이 기능의 성공 지표(KPI)가 뭔가? 머지가 목표가 아니라 고객 가치가 목표일 텐데.

- **방어**: 1차 지표는 S1/S3 형 워크로드의 I/O·elapsed 개선폭 (TBD 채워지면
  구체화), 2차는 wide-row 스키마에서의 저장 효율(overflow 대비 단편화 감소).
  릴리스 노트에 "어떤 워크로드에서 켜야 하는가" 가이드로 번역하는 것까지가
  성공 조건이라고 답한다.

|------|------|
