CBRD-27014 · OOS 기술 리뷰
Problem · 01

작은 컬럼 하나를 읽어도, 큰 payload 가 함께 따라온다

AS-IS — row 를 한 덩어리로

Record HDR+ VOT
id4B
name40B
big_text4.5 KB
big_blob4.5 KB

SELECT id, name 도 이 record 가 실린 heap page 전체 I/O 를 유발한다. 수 KB 의 가변 컬럼이 페이지를 지배하면 페이지당 행 수가 줄고 buffer pool 효율이 함께 떨어진다.

문제를 다시 정의하면

기존 overflow (REC_BIGONE) 는 "record 가 한 페이지를 넘으면 어디에 담을까" 를 다룬다. OOS 가 다루는 문제는 다르다 — 자주 읽는 작은 컬럼과 가끔 읽는 큰 컬럼이 한 덩어리로 묶여 있어서, 작은 컬럼만 읽어도 큰 컬럼의 I/O 비용을 함께 내야 한다는 것이다. 그래서 해법도 record 가 아니라 컬럼 단위 분리다.

기존 Overflow 와의 구분

Overflow (기존)OOS (신규)
분리 단위record 전체column
페이지 구조1 record / pageslotted (多 record)
내부 단편화큼감소
발동 조건record > pagerecord > page/4
한 줄 요약 — 큰 값이 문제가 아니다. 큰 값이 작은 컬럼을 읽으러 가는 길목에 놓여 있는 것이 문제다. OOS 는 그 길목에서 큰 값을 치워준다.

왜 TOAST table 이 아니라 "전용 OOS file + 물리 OOS OID" 인가

기존 overflow 확장안은 1 record/page 구조의 내부 단편화 때문에 초기에 제외했다. 실질 후보는 둘 — PG 식 TOAST table 이냐, 전용 파일이냐.

Record binary layout — 플래그 2개, 포인터 16B

Record Headerflags + txn ids

Fixed cols
Variable area실제 값

두 단계 플래그

  • Record-level — record header bit 3 OR_MVCC_FLAG_HAS_OOS: 이 record 에 OOS 컬럼이 하나라도 있는가
  • Column-level — VOT entry bit 0 OR_VAR_BIT_OOS: 이 offset 의 변수 영역이 값인가, 16B stub 인가
주의 — record header 크기 lookup 은 하위 3비트만 사용 (idx & 0x07). HAS_OOS 는 header 크기에 영향을 주지 않는 순수 metadata 비트다.

volid2B
pageid4B
slotid2B

full_length 를 inline 에 함께 저장 (CBRD-26630) — 길이 조회 (oos_get_length) 를 위한 추가 OOS page I/O 를 제거했다. PG 18B · MySQL 20B 대비 여전히 가장 작다.

Record Format · 06

VOT entry 해부 — offset 하위 2비트를 플래그로 쓴다

변수 값은 항상 4B 정렬로 기록되므로 offset 하위 2비트는 언제나 0 — 이 자리를 플래그 2개로 재활용한다 (CBRD-26352)

예시 — variable column 3개: name (40B inline) · big_text · big_blob (demote 후 16B stub) — entry 폭 1B

Record HeaderHAS_OOS=1 · offset 폭 코드
12 | 00entry[0] name
52 | 01entry[1] big_text
68 | 01entry[2] big_blob
84 | 10entry[3] 끝 표시
fixedid + bound bits
name 값@12 · 40B
OOS OID@52 · 16B stub
OOS OID@68 · 16B stub

offset 은 Record Header 끝 기준이고 entry 는 항상 N+1 개 — 컬럼 길이는 이웃 entry 의 차로 구한다 (name = 52−12 = 40B). 마지막 값의 길이도 끝 표시 entry (fencepost) 가 닫아준다.

Entry 비트 구성 — 폭은 1B / 2B / 4B

offset상위 비트 · 항상 4의 배수
LASTbit 1 · 0x2
IS_OOSbit 0 · 0x1
  • OR_VAR_BIT_OOS — 이 offset 의 변수 영역은 값이 아니라 16B stub
  • OR_VAR_BIT_LAST_ELEMENT — VOT 의 끝 (fencepost entry) 표시
  • entry 폭은 record 크기가 결정 — ≤127B 는 1B · ≤32767B 는 2B · 그 이상 4B. record header 의 2비트 코드 (OR_GET_OFFSET_SIZE) 로 식별

fencepost 의 쓸모 — attrinfo 없이 OOS OID 추출

vacuum 이 undo log 의 recdes 에서 old OOS OID 를 뽑을 때는 class representation (attrinfo) 이 없어 VOT entry 개수를 알 수 없다. 끝 entry 에 LAST_ELEMENT 를 찍어 두면 raw recdes 스캔만으로 충분하다 — heap_recdes_get_oos_oids:

  • ① record header 의 HAS_OOS 확인 — 없으면 즉시 종료
  • ② VOT 를 앞에서부터 스캔 — IS_OOS entry 의 offset 에서 16B stub 를 읽어 OOS OID 수집
  • ③ LAST_ELEMENT 를 만나면 종료

사용처: vacuum forward-walk (undo recdes 에서 old OOS OID 추출) · SA_MODE eager cleanup 의 old/new OID 비교.

CBRD-27014 · OOS 기술 리뷰
Write Path · 08

한계 조건 — 다 내보내도 한 페이지에 안 들어가면?

demotion 이 옮길 수 있는 것은 variable column 뿐이다. 큰 고정 길이 컬럼만 남으면 더 내보낼 것이 없다.

언제 생기나 — 고정 길이 컬럼은 내보낼 수 없다

CREATE TABLE t (
  id   INT,
  img1 BIT(70000),  -- 고정 8,750B
  img2 BIT(70000),  -- 고정 8,750B
  memo BIT VARYING -- 가변 — demote 가능한 건 이것뿐
);

memo 를 OOS 로 보내 16B stub 로 줄여도, BIT(70000) 두 개는 고정 길이라 항상 17,500B 를 차지한다 — record 가 한 페이지 (≈16KB) 를 넘는 것을 demotion 으로는 막을 수 없다 (실제 QA 에서 만난 사례).

이렇게 OOS OID 를 품은 채 여러 페이지짜리 bigone (overflow record) 이 되어야 하는 조합은 지원하지 않는다 (CBRD-26937).

현재 동작 — 명확한 에러로 거부

저장하지 않고 ER_HEAP_OOS_OVERPASS_MAXOBJ_SIZE (−1375) 를 돌려준다. 거부 시점은 demotion 후 · OOS 기록 전이라, 실패해도 orphan OOS record 가 남지 않는다.

일반 (OOS 없는) bigone record 는 기존과 동일하게 허용된다.

PostgreSQL 도 같은 방침이다 — TOAST 로 다 내보내고도 row 가 페이지에 안 들어가면 "row is too big" 사용자 에러로 처리한다. 스키마가 페이지 한계를 넘는 것은 저장 엔진이 아니라 사용자가 고칠 문제라는 입장 — 우리도 같은 선을 긋는다.
미래 방향 — 장기적으로는 heap 의 여러 페이지짜리 bigone (multipage overflow) 자체를 없애고, 큰 데이터는 OOS 로 일원화하는 방향을 검토한다. 그때가 되면 이 한계 조건 자체가 사라진다.

각 chunk 는 OOS page 의 평범한 slot 하나다 — 서로 다른 페이지에 흩어져 있어도 된다.

OOS Chunk 의 생김새

next OOS OID (8B) + chunk data. 마지막 OOS Chunk 만 next 가 NULL 이다.

왜 꼬리부터 넣나

chunk ① 을 쓰는 순간 ② 의 주소가 이미 있어야 하기 때문이다. 꼬리부터 넣으면 앞 chunk 를 다시 방문해 포인터를 고칠 일이 없다.

WAL · Recovery · Replication — 지켜야 할 6개 불변식

1 WAL 완전성

3-Tier Bestspace — 빈 공간을 다시 쓰게 만들기 CBRD-26658

M1 의 "마지막 삽입 페이지 1개" 캐시를 heap 의 15년+ 검증된 bestspace 구조로 교체 — hotspot 과 낭비를 동시에 완화.

Tier 1 — 글로벌 hash cache (VFID→entry · 전용 mutex, heap 과 독립)
↓ miss
Tier 2 — header page 의 best[10] 순환 배열 (non-logged hint · disk 보존)
↓ miss
Tier 3 — sync scan: 파일의 ≤20% 또는 100 페이지 한도로 재충전 후 재시도
↓ 그래도 없으면
Fallback — 새 페이지 할당

설계 성질

  • hint 는 로그를 남기지 않는다 (non-logged) — crash 로 날아가도 sync scan 이 스스로 다시 찾아낸다
  • 후보 페이지는 기다리지 않는 latch (zero-wait conditional) 로 잡는다 — 여러 INSERT 가 얽혀도 deadlock 이 없다
  • delete/rollback 이 일어나면 낡은 cache 항목을 그 자리에서 지운다
확인된 결함 (수정 예정) — fit-check 가 +sizeof(SPAGE_SLOT) 을 과다 예약해 들어갈 페이지를 거절 → 불필요한 새 페이지 할당 (delete/재삽입 반복에서 6→26 페이지 증식 관찰). heap 계약과 동일하게 raw length 비교로 수정.
ADR-0001 — 페이지 열거를 numerable find_nth → sector-bitmap walk 로 전환 (mark-delete 누적 시 O(n) 회피). experimental 브랜치에 구현, 검증 대기.

slotted page 공유 (多 record/page) 의 운영 리스크 — 단편화 이득 대비 page latch 경합을 어떤 지표로 감시할지. 섹션 분할 latch 같은 완화책이 필요한 임계점.

Q2 Vacuum 안전성

slot 재사용 데이터 손실 (CBRD-26950) 의 머지 전 결정 — chunk header 의 owner/generation 필드로 갈지, retry-idempotent 경로까지 포함할지.

Q3 압축의 위치

향후 압축의 책임 경계 — type-serialization layer (mr_data_writeval) 와 OOS 경계 중 어느 쪽에 둘지, PG 의 TOAST 통합 방식과 비교해 정리.

Q4 성능 결과의 경계

narrow read 는 크게 이기지만 ordinary heap 의 OOS-column read 는 8–14% 느리고 all-column 은 거의 동률 — 다음 검증은 mixed OLTP, raw-recdes Expand, dedicated-host cold run 중 무엇을 우선할지.
