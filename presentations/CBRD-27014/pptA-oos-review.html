CBRD-27014 · OOS 기술 리뷰
Problem · 01

작은 컬럼 하나를 읽어도, 큰 payload 가 함께 따라온다

AS-IS — row 를 한 덩어리로

Record HDR+ VOT
id4B
name40B
big_text4.5 KB
big_blob4.5 KB

SELECT id, name 도 이 record 가 실린 heap page 전체 I/O 를 유발한다. 수 KB 의 가변 컬럼이 페이지를 지배하면 페이지당 행 수가 줄고 buffer pool 효율이 함께 떨어진다.

문제를 다시 정의하면

기존 overflow (REC_BIGONE) 는 "record 가 한 페이지를 넘는가" 를 다룬다. OOS 가 다루는 것은 다르다 — "자주 안 읽는 큰 컬럼이 자주 읽는 작은 컬럼의 I/O 를 오염시키는가", 즉 column-level 분리 문제다.

Overflow (기존)OOS (신규)
분리 단위record 전체column
페이지 구조1 record / pageslotted (多 record)
내부 단편화큼감소
발동 조건record > pagerecord > page/4
핵심 질문 — 큰 값은 어차피 어딘가에 저장해야 한다. 문제는 그것이 작은 컬럼의 read path 위에 놓여 있는가 이다.

Design Choice · 03

왜 "전용 OOS file + slotted page" 인가

A — TOAST 식 별도 테이블

  • 일반 relation 재사용은 매력적
  • 그러나 다중 테이블 트랜잭션 동기화가 새로 필요
  • catalog/스키마 결합도 증가

B — 기존 overflow 확장

  • record 단위 한계 그대로
  • 1 record/page → 내부 단편화 큼
  • column 분리 효과 없음

채택 C — 전용 OOS file

  • FILE_OOS — heap file 과 1 : 1
  • slotted page: 페이지당 多 record → 단편화 감소
  • 팀이 15년+ 다뤄온 저수준 heap/slotted API 재사용
얻는 것 — 기존 overflow 구현 패턴을 참조하는 낮은 구현 리스크, 트랜잭션/로깅 경로 재사용, 페이지 공간 효율.
감수하는 것 — 한 OOS page 를 여러 트랜잭션이 동시에 수정할 때의 page latch 경합 가능성. (검토 질문 ①과 연결)

Record Format · 05

Record binary layout — 플래그 2개, 포인터 16B

Record Headerflags + txn ids
Variable Offset Tableentry 당: offset 30b · RSV 1b · IS_OOS 1b
Fixed cols
Variable area실제 값
또는 OOS OID16B stub

두 단계 플래그

  • Record-level — record header bit 3 OR_MVCC_FLAG_HAS_OOS: 이 record 에 OOS 컬럼이 하나라도 있는가
  • Column-level — VOT entry bit 0 OR_VAR_BIT_OOS: 이 offset 의 변수 영역이 값인가, 16B stub 인가
주의 — record header 크기 lookup 은 하위 3비트만 사용 (idx & 0x07). HAS_OOS 는 header 크기에 영향을 주지 않는 순수 metadata 비트다.

pageid4B
slotid2B

full_length 를 inline 에 함께 저장 (CBRD-26630) — 길이 조회 (oos_get_length) 를 위한 추가 OOS page I/O 를 제거했다. PG 18B · MySQL 20B 대비 여전히 가장 작다.

Write Path · 06

Demotion 정책 — largest-first, 딱 필요한 만큼만

PG TOAST 의 main loop 와 같은 골격, 압축 단계만 없다 — heap_attrinfo_determine_disk_layout (CBRD-26776)

1Record gate — record > DB_PAGESIZE/4 (16K 페이지에서 4KB)? 아니면 전부 inline, OOS 없음
↓
2후보 선정 — variable column 이면서 값 > OR_OOS_INLINE_SIZE (16B). 16B stub 보다 커야 내보내는 의미가 있다
↓
3Largest-first 루프 — 크기 내림차순으로 하나씩 demote, record 가 gate 이하로 내려오는 순간 break. 작은 후보는 inline 에 남는다

예시 — 5KB record (vc1 3KB · vc2 2KB)

HDR
vc1 · 3KB
vc2 · 2KB
↓ 가장 큰 vc1 만 demote → 2KB ≤ 4KB → break
HDR
OOS OID 16B
vc2 · 2KB ← inline 유지
불변식 — 틀려도 안전한 방향으로만 틀린다. 루프가 쓰는 record 크기 추정치는 항상 실제 이상이다 (비교 기준 header 크기를 루프 시작 시점 값으로 고정). 예: 실제 record 는 이미 3.9KB 로 줄었는데 추정치가 4.1KB 면 컬럼 하나를 더 내보낼 수 있다 — 비용은 약간의 추가 OOS I/O 뿐. 반대로 덜 내보내서 페이지에 못 들어가는 일은 없다. PostgreSQL 도 TOAST 로 내보낼 때 같은 보수적 추정을 쓴다.

(구) M1 정책 — 2KB gate + 512B 이상 전 컬럼 일괄 externalize — 는 폐기됨.

Write Path · 07

경계 조건 — OOS + bigone 공존은 거부한다

demotion 은 variable column 만 옮긴다. 거대한 고정 컬럼이 남으면? — CBRD-26937

demotion 이후 record 크기에 따른 3개 구간

≤ 4KB
inline 저장 — OOS 불필요 또는 demotion 으로 해소
4KB ～ ≈16KB
OOS 후 inline 잔여 — 정상 저장 (gate 초과여도 OK)
> ≈16KB + has_oos
거부 — ER_HEAP_OOS_OVERPASS_MAXOBJ_SIZE (−1375)

왜 생기는 조합인가

거대한 고정 길이 BIT(n)/CHAR 컬럼, 또는 16B 이하 variable 컬럼 다수 — demotion 으로도 record 가 bigone 문턱 (heap_Maxslotted_reclength ≈ 16KB) 을 넘게 남을 수 있다. OOS OID 를 품은 record 가 다시 REC_BIGONE overflow 로 가는 조합은 지원하지 않기로 결정했다.

거부 시점이 핵심 — demotion 후, OOS record 기록 전 (heap_attrinfo_transform_to_disk_internal). 거부되어도 orphan OOS record 가 생기지 않는다.
범위 — has_oos 일 때만 발동. 일반 (non-OOS) bigone record 는 기존과 동일하게 허용.

Lifecycle · 10

UPDATE / DELETE — 옛 OOS 는 vacuum 까지 산다

1UPDATE — 새 record 의 OOS 후보를 oos_insert → 항상 새 OOS OID (값이 안 바뀌어도 — M1 설계)
↓
2이전 record 는 OOS OID 를 품은 그대로 undo log 에 보존 — resolved 값이 아니다 (undo 비대화 방지)
↓
3옛 OOS record 는 계속 생존 — MVCC snapshot 독자가 prev_version_lsa → undo recdes → oos_read 로 옛 버전을 재구성
↓
4vacuum 이 죽은 heap 버전을 정리할 때 oos_delete 로 옛 OOS 도 함께 회수

DELETE 는 OOS 를 건드리지 않는다

  • heap record 에 delete MVCC id 만 기록
  • OOS OID 는 그대로 — resolve 도 삭제도 하지 않음
  • 이유: MVCC 가시성 + record 를 in-place 로 펼치면 16KB 페이지 한계를 넘는다
불변식 재확인 — 하나의 OOS OID 는 정확히 하나의 record (heap page 또는 undo log) 가 참조한다. UPDATE 가 항상 새 OID 를 만들기에 old/new OID 는 서로소 — vacuum forward-walk 이 이 성질에 의존한다.
Rollback — undo 로 이전 record 복원 → 그 안의 OOS OID 들은 여전히 살아있는 OOS record 를 가리킨다. 별도 OOS 복원 작업이 필요 없다.

Durability · 11

WAL · Recovery · Replication — 지켜야 할 6개 불변식

1 WAL 완전성

모든 OOS insert/delete 는 로깅된다. crash + recovery 후 OOS 상태 = 마지막 commit 상태

2 Undo 정확성

undo 는 이전 record 를 OOS OID 포함 그대로 보존 — resolved 값을 저장하면 OOS 의 목적 자체가 무너진다

3 Orphan 금지

UPDATE 의 옛 OOS 는 vacuum 이 죽은 heap 버전과 함께 회수 — 영구 잔존 없음

4 DELETE 안전성

삭제된 record 도 OOS OID 유지 — vacuum 전까지 옛 snapshot 이 접근 가능

5 Replication 충분성

repl log 는 slave 가 스스로 oos_insert 할 수 있는 데이터를 담는다

6 1 : 1 매핑

heap file 당 OOS file 최대 1개 · OOS VFID 는 heap header 에

Replication 주의 — slave 의 OOS OID 는 master 와 다를 수 있다. 보장되는 것은 값의 동등성이지 OID 동등성이 아니다 — 검증/툴링도 값 기준으로 설계해야 한다.

Vacuum 연동 — 세 갈래 정리 경로 merged · CBRD-26668

① Forward-walk

UPDATE/DELETE 의 undo recdes 에서 옛 OOS OID 를 직접 추출해 oos_delete (불변식 2 에 의존)

독립 sysop — 중간 실패 시 자기 삭제분만 롤백

② Within-sysop

지금 vacuum 중인 heap record 가 참조하는 OOS 를 호출자의 sysop 안에서 삭제

heap 회수와 OOS 회수가 원자적으로 묶인다

③ Eager (SA_MODE)

단독 프로세스 모드엔 vacuum 이 없다 — UPDATE 시점에 동기 삭제

old ∩ new OID 비교로 post-image 가 참조하는 것은 보존

Record 까지, page 는 아직 — vacuum 은 OOS slot 을 비우지만 빈 페이지 dealloc 은 미구현 (oos_remove_page 호출자 없음 · CBRD-26786 proposed). 빈 공간은 bestspace 재활용으로 흡수한다.
Crash 안전성 — chunk 삭제 각각이 sysop 내에서 로깅 → 중간 crash 에도 heap 회수와 OOS 상태가 원자적으로 복원.

Operations · 13

3-Tier Bestspace — 빈 공간을 다시 쓰게 만들기 CBRD-26658

M1 의 "마지막 삽입 페이지 1개" 캐시를 heap 의 15년+ 검증된 bestspace 구조로 교체 — hotspot 과 낭비를 동시에 완화.

Tier 1 — 글로벌 hash cache (VFID→entry · 전용 mutex, heap 과 독립)
↓ miss
Tier 2 — header page 의 best[10] 순환 배열 (non-logged hint · disk 보존)
↓ miss
Tier 3 — sync scan: 파일의 ≤20% 또는 100 페이지 한도로 재충전 후 재시도
↓ 그래도 없으면
Fallback — 새 페이지 할당

설계 성질

  • hint 는 non-logged — crash 후 sync scan 이 스스로 재발견 (self-healing)
  • 후보 페이지는 zero-wait conditional latch — 다중 INSERT 간 deadlock 회피
  • delete/rollback redo 가 stale cache entry 를 즉시 evict
확인된 결함 (수정 예정) — fit-check 가 +sizeof(SPAGE_SLOT) 을 과다 예약해 들어갈 페이지를 거절 → 불필요한 새 페이지 할당 (delete/재삽입 반복에서 6→26 페이지 증식 관찰). heap 계약과 동일하게 raw length 비교로 수정.
ADR-0001 — 페이지 열거를 numerable find_nth → sector-bitmap walk 로 전환 (mark-delete 누적 시 O(n) 회피). experimental 브랜치에 구현, 검증 대기.

Performance · 14

Risks · 17

해결해야 머지할 수 있는 것들 — 정직한 리스크 목록

CRITICAL Vacuum slot 재사용 데이터 손실

vacuum 이 비운 OOS slot 을 다른 행의 oos_insert 가 재사용 → vacuum block retry 가 undo image 의 옛 OID 를 다시 삭제 — 이번엔 산 데이터를 지운다. 존재 확인 (oos_chunk_exists) 은 "점유 여부"만 알지 "내 것인지"를 모른다.

방향 — chunk header 에 owner OID / generation 필드 추가로 소유 검증. CBRD-26950

SECURITY TDE 미적용 — plaintext 노출

TDE walker 가 FILE_OOS 를 건너뛰고, lazy-create 경로도 TDE 설정을 누락 → encrypt 테이블의 OOS 데이터가 디스크에 평문으로 남는다. 동일 데이터가 기존 overflow 경로에서는 암호화됐다 — 명백한 회귀.

방향 — walker 에 OOS 분기 + lazy-create 인라인 TDE (이중 방어). CBRD-26830

TOOLING Observability 공백

spacedb 가 OOS 공간을 heap 으로 합산 — 테이블별 OOS 사용량 귀속 불가, release 빌드에서 "이 행이 OOS 로 갔다"를 증명할 도구가 없다 (debug oos.log 뿐).

방향 — OOS file 에 owner descriptor 부여 → per-table 귀속 + 통계 노출. CBRD-26871

이 세 항목이 develop 머지 전 정리 대상이며, ①②는 오늘 설계 피드백을 받고 싶은 안건이기도 하다.

여쭙고 싶은 것들

오늘의 목적은 보고가 아니라 검증입니다 — 설계 판단에 대한 의견을 부탁드립니다.

Q1 저장 단위

slotted page 공유 (多 record/page) 설계 — 단편화 이득 대비 page latch 경합 tradeoff 를 어떻게 평가하시는지. 섹션 분할 latch 같은 완화책이 필요한 수준인지.

Q2 Vacuum 안전성

slot 재사용 데이터 손실 (CBRD-26950) 의 수정 방향 — chunk header 의 owner/generation 필드가 충분한가, retry-idempotent 설계로 더 가야 하는가.

Q3 압축의 위치

향후 압축을 type-serialization layer (mr_data_writeval) 에 둘 것인가, OOS 경계에 둘 것인가 — PG 의 TOAST 통합 방식과 비교해 의견을 듣고 싶습니다.

Q4 성능 시나리오

S1–S7 이 OOS 의 가치·비용을 공정하게 드러내는가 — 빠진 워크로드 (예: 혼합 OLTP, 대량 scan + 부분 payload) 가 있다면.
