## CBRD-27407 source chain

Feature's `merge_list_ids()` receives lists with `last_pgptr == nullptr`, i.e. already closed, at [px_scan_result_handler.cpp:585](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/parallel/px_scan/px_scan_result_handler.cpp#L585). When the destination is empty, it destroys that destination and copies the worker list at [line 624](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/parallel/px_scan/px_scan_result_handler.cpp#L624). `qfile_copy_list_id()` clears `tpl_descr` at [list_file.c:524](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/list_file.c#L524). The parallel hash-aggregate caller performs this takeover at [line 697](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/parallel/px_scan/px_scan_result_handler.cpp#L697) and goes straight to updating hash-trace status, with no restoration.

The main execution path later flushes its hash table to `part_list_id` at [query_executor.c:5675](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/query_executor.c#L5675). Each partial tuple writes through `list_id->tpl_descr.f_valp[col++]` at [query_aggregate.cpp:3010](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/query_aggregate.cpp#L3010). The upstream fix restores the missing array and reopens the closed partial list at [baseline helper:632](https://github.com/CUBRID/CUBRID/blob/e1c3db19800a0170942cec8b23cac4705efbb6e3/src/query/parallel/px_scan/px_scan_result_handler.cpp#L632), called immediately after merge at [baseline:727](https://github.com/CUBRID/CUBRID/blob/e1c3db19800a0170942cec8b23cac4705efbb6e3/src/query/parallel/px_scan/px_scan_result_handler.cpp#L727).

The [retained QA report](qa_comparison_1ec35f8_codex.md#i01-missing-develop-fix-for-the-partitionparallel-hash-aggregation-crash) records feature server death/cores and issue CBRD-27407. The [JIRA verification](http://jira.cubrid.org/browse/CBRD-27407) includes the 2026-09-29 verification of the exact same testcase passing isolation and isolation_debug on `11.5.0.2622-e1c3db1`. Upstream's commit message also records normal results with 20 rows equal to NO_PARALLEL_SCAN and NO_HASH_AGGREGATE controls. Those are upstream results, not runs performed in this triage.

This explains why OOS ancestry can lag a working develop baseline even when the actual failing mechanism is pre-existing develop query code. The comparison still legitimately counts it as two additional feature failures.

The CCI patch [79d0888:cci_network.c:507](https://github.com/CUBRID/cubrid-cci/blob/79d0888c26a2543d31f53eb7b6c9738db110fff4/src/cci/cci_network.c#L507) adds token bytes, while [engine cas_protocol.h:260](https://github.com/CUBRID/CUBRID/blob/bc1a91769/src/broker/cas_protocol.h#L260) defines protocol 13.
