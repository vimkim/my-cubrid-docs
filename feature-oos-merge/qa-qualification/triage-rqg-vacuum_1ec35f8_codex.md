Date: 2026-09-29. Source inspected: feature `1ec35f86c5e43b9ca86d81e202c68899f8ce4f21`; QA develop comparator `e1c3db19800a0170942cec8b23cac4705efbb6e3`.

This is read-only triage requested by the user. Diagnosis phases requiring a runnable feedback loop, reproduction, instrumentation, and a fix are deferred explicitly. No tests, builds, instrumentation, engine edits, or testcase answer changes were performed for this investigation. Predictions below are untested. Develop has no RQG result, so this is an observed serious crash with **provisional regression attribution**.

## Finding and priority

Treat `random_query_generator/_03_mvcc/vacuum/dead_data_03/dead_data_03_big_record/cases/dead_data_03_big_record.sh` as a P0 investigation candidate: the QA page reports **five analyzed cub_server cores** reaching `pgbuf_fix_debug`'s `PAGE_UNKNOWN` assertion. One arrives through vacuum; four arrive through an index scan fetching a heap object. This is broader than a vacuum-only call-site failure. The portal also lists `core.594392` inside a later backup archive, but supplies no corresponding analyzed stack. It must not be counted as another diagnosed instance of the same symptom.

The evidence identifies an expected-live physical page that the buffer pool sees as deallocated. It does not identify the physical VPID, the file owner, which operation freed it, or whether the five crashes share one page. Do not claim OOS caused this, and do not change `OLD_PAGE` to a tolerant mode merely to hide it.

## Source reconstruction

1. Vacuum walks MVCC log records, first checks the dropped-file registry, and derives a heap OID from the log address (`volid`, `pageid`, flags-stripped offset). It copies this OID and the logged VFID into `worker->heap_objects`; it does not derive the home VPID from an OOS stub. Heap work is delayed until after the block's log traversal and index cleanup. See [collection and OOS cleanup](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/vacuum.c#L3547), [worker queue](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/vacuum.c#L7091), and [heap execution](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/vacuum.c#L3745).
2. `vacuum_heap_page` takes the first queued OID's VPID. An interrupted block uses `pgbuf_fix_if_not_deallocated` and tolerates a deallocated page or reuse as `PAGE_FTAB`; ordinary work uses `OLD_PAGE`. In this core `was_interrupted=false`. `pgbuf_fix_debug` aborts because the page type is `PAGE_UNKNOWN`. See [guard](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/vacuum.c#L1649) and [buffer invariant](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/storage/page_buffer.c#L2472).
3. Heap vacuum permits empty-page removal only when page vacuum status says this job is the last expected work (or the interrupted-job guard applies), the heap reuses slots, and there is no deallocation prevention. `heap_remove_page_on_vacuum` protects the header, conditionally obtains neighbors, rechecks emptiness and deallocation prevention, rejects unexpected waiters, updates the chain, and deallocates through `file_dealloc(..., FILE_HEAP)` in a system operation. Its documented invariant is that neither active direct references nor another vacuum worker should remain. See [eligibility](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/vacuum.c#L1829) and [heap removal](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/storage/heap_file.c#L3349).
4. On the reader side, `scan_next_index_lookup_heap` passes the current index OID directly to `heap_get_visible_version`. `heap_prepare_object_page` fixes its VPID with `OLD_PAGE`. The four read stacks fail at this fix; the later OOS Resolve/Expand logic is not reached. See [index lookup](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/scan_manager.c#L6814) and [direct fix](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/storage/heap_file.c#L27535).
5. Dropping files has a registry and worker version handshake: the dropper waits for active workers to observe the version; a worker removes already-collected objects for that VFID and skips log records belonging to dropped files. A mere concurrent DROP is therefore not sufficient explanation without evidence that this protocol failed or was bypassed. See [worker filter](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/vacuum.c#L4193) and [drop handshake](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/vacuum.c#L6513).

## Feature changes relevant to the investigation

`git diff e1c3db198 1ec35f86c` shows the assertion implementation is unchanged: `page_buffer.c` has one added `PAGE_OOS` statistics case elsewhere. The normal/retry fix branch, empty heap-page removal eligibility, `heap_remove_page_on_vacuum`, page-chain vacuum-status update function, and `heap_prepare_object_page` have no direct changes. The missing develop commits through the specified QA baseline contain no fix to those vacuum/heap/buffer paths. This does not rule out an integration defect in their callers.

The feature **does broaden heap vacuum scheduling**: relocation UPDATE's `update_old_forward` branch changes physical forward-page logging from `RVHF_UPDATE` to `RVHF_UPDATE_NOTIFY_VACUUM`. Consequently a physical `REC_NEWHOME` page now has queued heap work in addition to the home-page work. This selection is unconditional on HAS_OOS when `is_mvcc_op` is true. `heap_log_update_physical` already updates that page's chain vacuum status for any `LOG_IS_MVCC_HEAP_OPERATION`, so the easy hypothesis “new notification without a vacuum-status update” is contradicted by source. The new scheduling remains a useful boundary to inspect, particularly for forward-record deletion, rollback, and jobs spanning different blocks. It is **not** a demonstrated cause of the captured crashes. See [changed producer](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/storage/heap_file.c#L24472), [status update](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/storage/heap_file.c#L24871), and [classification](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/transaction/mvcc.h#L252).

The distinct `RVHF_DELETE_NEWHOME_NOTIFY_VACUUM` tag deliberately sits outside `LOG_IS_MVCC_HEAP_OPERATION`, because its forward slot has already been physically removed. It therefore does **not** itself enqueue that deleted OID for heap vacuum. An allegation that this delete tag directly queues dead heap work is contradicted. See [consumer](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/query/vacuum.c#L3717).

OOS page reclaim is a different path. It fixes candidates with `OLD_PAGE_MAYBE_DEALLOCATED`, checks `PAGE_OOS` and zero records in both phases, excludes the sticky first page, checks an LSA horizon, and calls `file_dealloc(..., FILE_OOS)`. The captured vacuum frame is fixing its heap home page before this routine executes for that page. An assertion that normal OOS reclaim freely deallocates heap pages conflicts with these checks. Wrong cross-file ownership or prior page corruption remains technically possible, but requires physical evidence. See [OOS checks](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/storage/oos_file.cpp#L1478), [revalidation and deallocation](https://github.com/CUBRID/CUBRID/blob/1ec35f86c5e43b9ca86d81e202c68899f8ce4f21/src/storage/oos_file.cpp#L1627).

The known rollback-forward-walk problem documented as CBRD-27237 concerns deletion of **live OOS chains** from aborted UPDATE undo images. Its presence is an independent concern; it is not evidence that it produced this deallocated **heap** page. Neither the testcase's “big record” name nor an OOS-related branch is proof that a specific failing row was demoted.

## Context and limits

The complete [OOS normative context](https://github.com/vimkim/cubrid-oos-context/blob/75f8b58674ac901d478ba60f9b2cc2fff11f66f6/OOS-CONTEXT.md), [ADR-0001](https://github.com/vimkim/cubrid-oos-context/blob/75f8b58674ac901d478ba60f9b2cc2fff11f66f6/docs/adr/0001-oos-page-enumeration-non-numerable.md), and [ADR-0005](https://github.com/vimkim/cubrid-oos-context/blob/75f8b58674ac901d478ba60f9b2cc2fff11f66f6/docs/adr/0005-defer-oos-history-from-the-11-5-merge.md) were consulted. ADR-0001's tolerant fixes apply to stale **read-only OOS hint enumeration**; they do not authorize masking an ordinary heap vacuum or index lookup invariant. CDC/flashback deferral does not exclude RQG, vacuum, or heap consistency.

The source provides useful boundaries and rules out several easy explanations. The captured portal stack is not the complete core or a minimized reproducer. No hypothesis has been confirmed, no root cause has been assigned, and the absent develop RQG result prevents a claim that this is newly introduced by feature/oos-merge.
