## Purpose

- AS-IS: OOS(큰 컬럼 값을 별도 페이지에 저장하는 방식)의 변경 이력을 오래 보존하려면 새 이력 형식이 필요하지만, 기존 데이터베이스를 안전하게 전환하는 절차와 구형 엔진 차단이 없다.
- TO-BE: 새 데이터베이스는 현재 형식으로 생성하고, 기존 데이터베이스는 정상 종료 후 명시적으로 전환한다. 전환하지 않은 데이터베이스에서는 불완전한 OOS 이력이 생기는 쓰기를 거부한다.

이 PR은 승인된 여섯 작업 중 첫 번째인 활성화와 호환성 기반만 구현한다. CDC(데이터 변경 내역 추출)와 flashback(과거 변경을 확인하는 기능)의 OOS 값 보존 자체는 후속 작업이다.

소스 커밋: `9960c7fc6`, 기준: `feat/oos`의 `f4299ac0c`. 구현 브랜치는 `CBRD-26939-oos-cdc`다.

## Implementation

### 상태와 전환

`src/base/release_string.c`는 새 데이터베이스의 디스크 호환성 식별자를 11.6으로 설정한다. 이는 제품 버전 변경이 아니다. 업그레이드한 엔진은 기존 11.5 데이터베이스를 자동 전환하지 않고 연다. 실제 기준 엔진 `2940b1cfbc3c2d4d0fac3f9244a960350debd380`은 11.6 데이터베이스를 복구 전에 거부한다.

`cubrid activatehistorydb database_name`은 서버를 시작하지 않는 오프라인 유틸리티다. `src/executables/util_sa.c`에서 설정을 초기화하고 파일 잠금을 강제한다. `src/transaction/log_page_buffer.c`에서 활성 로그를 독점 잠금하고 정상 종료 여부와 헤더를 검증한다. 저장된 로그 페이지 크기로 전체 헤더 페이지를 읽고 호환성 필드만 바꾼다. 다른 헤더 필드, 현재 데이터, 기존 비-OOS 이력은 보존한다.

### 장애와 쓰기 거부

활성화는 `fsync` 성공 후 잠금을 해제한다. 일반 동기화 생략 설정인 `suppress_fsync`로 이 순서를 건너뛸 수 없다. 활성화 도중 프로세스가 종료되어 새 표식이 운영체제 캐시에만 남았을 수 있으므로, 현재 형식의 시작 경로도 복구 전에 동기화를 확인한다. 동기화 실패 시 시작을 중단한다.

`src/storage/heap_file.c`는 supplemental logging(변경 이력용 추가 로그)이 필요한 쓰기에서 이전/이후 행의 OOS 포함 여부를 확인한다. 미활성 데이터베이스의 해당 INSERT/UPDATE/DELETE는 행 변경 전에 `ER_OOS_HISTORY_ACTIVATION_REQUIRED`(-1385)를 반환한다. 정상 종료가 아닌 활성화 요청은 -1386을 반환한다. 추가 로그를 끈 일반 쓰기는 유지된다.

### 백업과 로그 읽기

백업 헤더와 서버 접속 정보는 엔진 기본값 대신 실제 데이터베이스의 호환성 값을 사용한다. 미활성 백업은 기준 엔진으로 복구할 수 있고, 현재 형식 백업은 업그레이드한 엔진이 필요하다. 복사된 활성 로그를 읽는 경로는 해석 전에 호환성을 검사한다.

CCI(C 클라이언트 인터페이스)의 오류 정의는 별도 커밋 `76b293743800620cc521fb818b9567b6ae19cad9`에 있다. 기존에 고정한 CCI 커밋에서 파생했고, 이 PR은 해당 커밋을 참조한다. [CCI 변경](https://github.com/vimkim/cubrid-cci/commit/76b293743800620cc521fb818b9567b6ae19cad9).

## Remarks

### 검증

- 병합된 소스에서 빌드 성공, 구성된 CTest 27개 모두 통과(130.34초).
- `unit_tests/oos/scripts/test_history_compatibility.sh`로 실제 기준 엔진과 비교했다. 데이터/로그 페이지 4KB, 8KB, 16KB 모두 통과했다.
- 새 데이터베이스 및 활성화 후 구형 엔진 거부, 미활성 유지, 실행 중/비정상 종료 활성화 거부, SA(단독 실행)/CS(서버 접속) 쓰기 실패 후 값 보존을 검증했다.
- 기존 비-OOS flashback 결과 보존, 복사 로그 읽기, 백업/복구 후 호환성 보존을 검증했다.
- 로그 쓰기와 동기화 전후 프로세스 종료, 쓰기/동기화 오류, 활성화 재시도 없이 직접 시작할 때의 동기화 실패를 주입했다. 이후 정상 시작과 데이터 보존을 확인했다.
- Linux의 격리된 프로세스·네트워크·파일시스템 환경에서 테스트했다. Windows는 지원 범위가 아니다.
- 코드 규칙 및 명세 리뷰의 지적 사항을 반영했고 미해결 지적은 없다. 커밋 이동은 소스를 바꾸지 않았으며 위 결과는 동일한 커밋에 대한 결과다.

### 한계와 후속 작업

현재 형식 활성화만으로 완전한 OOS CDC 지원이 생기지는 않는다. 이미 회수된 저장 공간에 의존하는 과거 OOS 이력은 복원하지 않는다. DELETE 이미지 보존, INSERT/UPDATE 이미지 보존, 이력 읽기와 재시작 지원은 후속 작업이다. `bug_bts_4633` JDBC 오류도 별도 작업으로 남는다.

HA(여러 서버 사이의 복제)에서는 엔진뿐 아니라 독립적으로 실행되는 구형 로그 읽기 프로그램도 먼저 교체하고 중지해야 한다. 기존 구형 프로그램에는 이 검사 코드가 없고, 보관 로그 헤더에는 호환성 필드가 없다. 따라서 엔진 시작 차단만으로 모든 구형 읽기 프로그램을 차단했다고 볼 수 없다.

### 설계 문서 점검

승인된 설계 질의의 결론을 유지해 두 차례 대조했다. 첫 점검에서는 활성화 기반과 완전한 CDC 지원을 구분하고, 구형 독립 읽기 프로그램의 한계를 명시했다. 두 번째 점검에서는 실제 기준 바이너리, 동기화 실패 후 시작, 백업 복구, CCI 의존성을 코드와 테스트에 대조했다. 새로운 설계 결정은 추가하지 않았다.
