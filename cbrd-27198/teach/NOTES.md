# Teaching notes

- The course begins with an unassisted diagnostic retrieval quiz; do not pre-teach the answers.
- Prefer plain, short sentences and stable domain terms.
- Each lesson must stay tightly scoped and include exact-commit source links with line anchors.
- Treat the published report as authoritative evidence, but train the user to explain the review without reading it.
- The author's later response makes one sentence in the published report stale; it does not resolve the positive-timeout blocker.
- Diagnostic baseline: the user can already distinguish the lock/latch/fix layers and mode versus condition. Tighten two points: transaction locks are mode-dependent logical isolation, not always “do not modify”; a CUBRID page fix includes acquiring the requested latch as well as pinning the page.
- Begin instruction at the zero-wait demotion path. The user does not yet know the wait-policy sentinels, timeout-classification branches, or architecture-versus-blocker defense.
- First retrieval after lesson 0002 reversed conditional/unconditional and inferred a timed wait. Re-pitch with only three states: caller requests unconditional; zero-wait demotes it to conditional; a busy page rejects immediately without entering the timed-sleep path.
- After retrieving the three-arrow trace, the user asked whether immediate rejection is correct because `lock_timeout=0`. Teach this as “locally consistent, wrong contract”: a logical transaction-lock preference must not defeat a mandatory unconditional fix of a short-lived internal structural-page latch.
- Important correction from JIRA/source tracing: the caller is not fundamentally incapable of handling immediate rejection. The ticket's initial analysis proposed treating `ER_LK_PAGE_TIMEOUT` as expected contention. The reviewed PR chooses a different design—wait locally at the narrowly scoped structural fix—because the high-level reservation path otherwise unwinds cache reservations, partial disk changes, its critical section, and its system operation. Teach this as a trade-off and existing contract, not a physical impossibility.
- The user challenged the forced wait on deadlock grounds. Exact HEAD adds no tests and does not prove deadlock impossible. The wait is watchdog-bounded, not truly infinite: nonzero policies sleep for `page_latch_timeout_in_msecs` (default 300 seconds), while the PR's `LK_INFINITE_WAIT` classification selects assert/unilateral-abort on expiry. The PR preserves existing latch order but exposes zero-wait transactions to that wait path.
- A strict no-wait alternative cannot stop at removing the assert. Late failure can occur after partial sector-table changes, and temporary-allocation cleanup fixes the same structural pages again. It needs typed `WOULD_BLOCK` plus either preflight-before-mutation, a resumable compensator, or an explicitly unconditional cleanup exception.
- Code-level verdict on the author's architecture response: “lock-only” is a plausible intended/target meaning, supported by names and source comments, but not a proven existing contract. `db_set_lock_timeout`, `LOG_TDES::wait_msecs`, and reset comments say lock; page-buffer code directly consumes the same field for latch admission and timeout classification, while `bestspace` and B-tree diagnostic code deliberately install `LK_FORCE_ZERO_WAIT` to avoid/skip latch waits. The unconditional-to-conditional coupling is present in blame back to at least 2014. Treat user intent as ambiguous without authoritative documentation.
- The PR's scoped zero-wait override therefore changes an observable long-standing behavior for two structural-page classes. It may be a reasonable policy, but it needs an explicit specification and contention/watchdog/latch-order evidence; name-based intent alone does not establish compatibility.
- The attached `cbrd_27198_repro.sh` validates only the original failure chain under probabilistic contention: local large sorts force disk temp-file creation, eight `lock_timeout=0` sessions and client kills amplify temp-volume-header contention, and PID/boot-count plus `CODE = -76` detect the debug assert crash. It does not validate user intent, the lock-only architecture claim, the PR's wait policy, deadlock absence, positive finite behavior, or cleanup correctness. Treat script evidence as mechanism reproduction, not specification evidence.
