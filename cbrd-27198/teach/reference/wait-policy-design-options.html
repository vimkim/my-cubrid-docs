Page-latch wait-policy 설계 대안

Exact reviewed HEAD 1185f16d 기준. 질문은 transaction zero-wait와 내부 structural-page contention이 만나는 seam을 어디에 둘 것인가다.

A · 최소 interface: reservation이 WOULD_BLOCK을 반환

disk_try_reserve_sectors가 OK / WOULD_BLOCK / ERROR를 반환한다. zero-wait contention은 queue나 retry 없이 정상 unwind 후 즉시 상위로 전달한다. interface는 작고 disk cleanup 지식의 locality가 좋지만, 일시적 내부 경합 때문에 쿼리가 실패한다.

B · 명시적 page-buffer wait policy

pgbuf_fix_with_policy가 IMMEDIATE / UNTIL(deadline) / INTERNAL을 받고 ACQUIRED / WOULD_BLOCK / DEADLINE_EXPIRED / INTERNAL_STALL / ERROR를 반환한다. admission, 실제 deadline, error classification을 한 module 안에 숨겨 가장 높은 leverage를 얻지만 migration 범위가 크다.

C · common caller를 단순하게

대부분의 caller는 단순 pgbuf_fix(..., mode)로 required wait을 사용하고, 예외적인 caller만 pgbuf_fix_with_wait를 사용한다. page buffer에서 transaction-lock 지식을 제거해 interface가 선명해지지만, 현재 숨은 lock_timeout → latch condition 결합에 의존하는 caller 전체 audit가 필요하다.

D · reservation preflight + bounded retry

수정 전에 필요한 structural page를 정해진 순서로 try-fix하고, 하나라도 busy면 아무 page도 수정하지 않은 채 unwind한다. partial rollback 문제를 피하지만 여러 write latch를 오래 보유해 latch footprint와 새로운 deadlock 위험을 키울 수 있다. strict zero-wait이면 retry budget은 1이어야 한다.

추천

현재 PR 범위에서는 zero-wait 두 값만 scoped override하고 positive/infinite 분류를 보존하는 것이 가장 작은 수정이다. 그러나 “zero-wait이면 latch도 절대 기다리지 않는다”가 제품 원칙이라면 A만 단독 적용해서는 부족하다. B의 typed WOULD_BLOCK seam과 reservation의 all-or-nothing redesign을 결합해야 한다.

특히 현재 temp reservation cleanup은 이미 수정한 sector를 되돌리기 위해 volume header와 sector table을 다시 fix한다. rollback까지 strict no-wait이면 cleanup 자체도 WOULD_BLOCK할 수 있다. 단순 assert 제거가 안전성 증명이 되지 않는 이유다.
