Lesson 2B · Evidence boundary

Repro는 mechanism을 검증한다. Policy를 정하지 않는다.

cbrd_27198_repro.sh는 original crash chain을 재현하도록 load와 timing을 만든다. 무엇이 옳아야 하는지는 말해 주지 않는다.

스크립트가 만드는 조건

  1. Temp file을 disk에 강제한다.temp_file_memory_size_in_pages=0과 작은 temp cache를 설정하고, 100만 행을 정렬한다.
  2. No-wait transaction을 만든다.각 세션이 SET SYSTEM PARAMETERS 'lock_timeout=0'을 실행한다.
  3. 경합 확률을 높인다.8개 세션이 동시에 여러 대형 정렬을 실행하고, 곧바로 client를 SIGKILL해 temp 파일 생성과 연결 정리를 겹친다.
  4. 결과를 관찰한다.서버 PID·boot 횟수 변화와 서버 로그의 CODE = -76을 센다.

무엇을 입증하는가

주장증거 수준
dblink 없이 local sort만으로 같은 종류의 crash를 만들 수 있다.직접 검증
lock_timeout=0, disk temp-file 생성, structural-page 경합이 함께 있을 때 -76과 debug server restart가 재현된다.직접 검증하되 timing-dependent
서버 생존 여부만 보면 cub_master의 빠른 재기동 때문에 crash를 놓칠 수 있다.PID/boot counter로 보완
정확한 내부 chain은 unconditional→conditional→immediate reject→assert다.스크립트만으로는 부족; core stack과 source trace를 결합해야 함

무엇을 입증하지 않는가

  • 사용자가 latch까지 zero-wait을 의도했는지, lock만 의도했는지
  • structural page에서 wait하는 정책이 제품적으로 옳은지
  • unconditional wait 경로에 deadlock이나 latch-order inversion이 없는지
  • positive finite와 infinite policy가 PR에서 보존되는지
  • 즉시 실패를 expected outcome으로 바꿨을 때 partial cleanup이 안전한지
이 스크립트로 “기존 crash가 사라졌다”는 before/after 확인은 가능하다. 하지만 crash가 사라진 이유가 올바른 정책인지, 다른 regression을 만들지 않았는지는 별도 test matrix가 필요하다.

Code chain: zero-wait demotion, immediate rejection, unexpected-error assert.
