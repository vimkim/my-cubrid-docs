Lesson 1D · Design truth

Could the caller handle immediate failure? Yes.

“Must wait” is the PR's chosen contract for these structural fixes, not a law of database physics.

Non-negotiable

The thread must obtain a write latch before changing the volume header or sector-allocation table. Concurrent physical edits would corrupt shared allocation metadata.

Design choice

When that latch is temporarily busy, the system may wait there—or unwind the larger operation and arrange a safe retry.

Why a retry is not one line

disk_reserve_sectors is a multi-step operation. It starts a system operation, enters the disk-check critical section, reserves capacity in the in-memory cache, and may update several volume sector tables. See the setup and reservation path.

If a later page fix fails, its error path may undo partial temporary allocations, return cache reservations, leave the critical section, and abort the system operation before deciding what to do. See the unwind path. The current expected-error list does not include ER_LK_PAGE_TIMEOUT, so debug builds assert.

Why this PR waits locally

  1. The conflict is internal and transient.A busy structural page does not mean the disk is full or the reservation is invalid.
  2. The latch is held briefly.Waiting at the exact conflict avoids abandoning the larger reservation operation.
  3. The scope is narrow.The override surrounds only the volume-header and sector-table fixes, not arbitrary page access.
Precision: “unconditional” does not mean the page fix cannot fail. I/O errors, interrupts, and the separate page-latch timeout still exist. It means latch incompatibility does not cause an immediate would-block rejection.

The original JIRA analysis actually proposed the alternative: treat ER_LK_PAGE_TIMEOUT as expected contention. The PR chose local waiting instead. Both can be engineered safely; this review evaluates whether the submitted implementation preserves every wait policy while implementing its chosen design.
