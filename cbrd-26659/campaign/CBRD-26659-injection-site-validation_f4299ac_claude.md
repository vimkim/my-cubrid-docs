## 2. Existing controls, examined before patching

**The generic fault-injection facility exists at the pin and was reused.** `src/base/fault_injection.{c,h}` compiles only when `NDEBUG` is undefined (so on the debug build), is armed by the hidden server parameter `fault_injection_ids` (an integer list; `PRM_USER_CHANGE | PRM_FOR_SERVER`, so it accepts both a `cubrid.conf` line and `SET SYSTEM PARAMETERS` at run time) or by `fault_injection_test=recovery` (a fixed group), and `fault_injection_action_prefer_abort_to_exit` chooses `abort()` or `_exit(0)` for exit-type handlers. It has 17 codes at the pin, none in OOS code, and its handlers are random (`rand () % 20000` exits or failures), hang or hold; none acknowledges that it fired. It therefore did not reliably target any OOS event, and the patch adds deterministic, acknowledging handlers to it rather than a parallel mechanism.

**The `CUBRID_UNIT_TEST_ENABLED` seams are not runtime controls.** The four seams named by the assignment (`oos_test_fail_insert_many_after_publications`, `oos_test_throw_bad_alloc_on_next_oid_publication`, `oos_test_fail_next_reclaim_write_fix`, `heap_oos_test_fail_before_vfid_lookup_once`) are compiled into both unmodified builds, but a search of `src/` finds no caller outside `unit_tests/oos/`; no parameter, SQL or signal arms them. Per ticket 11 §9 they count as existing controls only with a trigger path, so the minimal patch places fault-injection sites next to three of them with the same semantics (700000 next to the bad_alloc publication seam, 700005 next to the fail-after-publications seam, 700010 next to the write-fix seam). The fourth seam (failure before the OOS VFID lookup) was left without a trigger; it precedes every chunk operation and adds nothing to the four failure groups. Ticket 12's counter channel (`oos_get_debug_counters`) likewise has no runtime reader and is unchanged.

**Two arming paths, both verified.** Every validated site below was armed at run time from the workload's own csql session (`SET SYSTEM PARAMETERS 'fault_injection_ids=<code>; fault_injection_fire_at_occurrence=<k>'`) and disarmed the same way (`fault_injection_ids=1`, the `FI_TEST_HANG` code that no site tests). Arming through `cubrid.conf`, the only way to arm a restart, was verified separately: site 700000 armed in the file fired on the first insert ([`sites/conf-arming-probe/`](evidence/ticket16/sites/conf-arming-probe/)).

## 3. The acknowledgement contract

Each site declares one static descriptor (`FI_SITE_DESC`: code, site function, target operation, requested action, reach and fired counters) and passes it as the `FI_TEST_ARG` argument. When the code is armed the handler counts the reach; with `fault_injection_fire_at_occurrence = 0` every reach fires, with `k > 0` exactly the k-th reach since the server started fires (one-shot). A firing writes, before the action, one notification to the server error log (`$CUBRID/log/server/<db>_<timestamp>.err`; the instrumented configuration sets `error_log_level=notification`):

```
Time: … - NOTIFICATION *** file …/oos_file.cpp, line 2088  CODE = -588, Tran = 1, CLIENT = dev2:csql(2649123), EID = 3
INTERNAL ERROR: Assertion 'FAULT INJECTION ACK site=oos_publish_oos_oid code=700000 target_operation="OOS OID publication during insert (value construction)" requested_action="throw std::bad_alloc" reach=1 fired=1 fire_at=0' failed.
```

The header line gives the site's file and line, the transaction and the client; the message gives the five fields the attempt record needs. A case consumes it at the shell seam with `grep -B1 "FAULT INJECTION ACK" <db>_2*.err` (the `_latest.err` symlink must be excluded or the line is counted twice). Mapping to the attempt-record `injections[]` entry: `site` = `site` (plus file:line), `target_operation` = `target_operation`, `occurrence_count` = `reach` at which it fired, `requested_action` = `requested_action`, `fired` = the line exists, `acknowledgement` = the path of the saved excerpt. The `Assertion … failed` wording is CUBRID's text for `ER_FAILED_ASSERTION` (-588), which the pre-existing handlers also use; the handler clears the thread's error state after logging, so the site sets whatever error its action needs. The acknowledgement precedes the action, so crash actions leave it behind (verified: e1, g1, h1, i1). Counters live for the server process: with `k > 0` a code fires once per server lifetime, which suits one attempt per server; the case must not rely on re-arming the same code in one server.

## 6. Corruption-detection procedure on copied images

Judged against: the normative context documents no detection or recovery guarantee for corrupted OOS pages or OOS log records (catalogue **OOS-DUR-07**, BLOCKED, Specification gap); the only documented statement is the manual's general one, `cubrid checkdb` "checks the consistency of a database … the internal physical consistency of the data and log volumes" (`admin_utils.rst`, checkdb section). Nothing below is asserted; each line is an observation for the corruption group's cases.

Procedure ([`tools/t16_corruption.sh`](evidence/ticket16/tools/t16_corruption.sh), [`corruption/journal.txt`](evidence/ticket16/corruption/journal.txt)): two source images are built in standalone mode under their own `CUBRID_DATABASES` — a clean one (three rows: 8,000 B, 20,000 B two-chunk, 8,000 B) and a crash image (same rows committed, the standalone process killed with `SIGKILL` before it flushed). Every experiment works on a raw copy in its own directory with its own `databases.txt` and rewritten `_vinf` paths; the sources are hashed before and after (identical). Target pages are located by scanning the copy for `PAGE_OOS` (ptype 8 at page offset 14) and reading the first record's `OOS_RECORD_HEADER` (length is the serialized value length, 8,008 and 20,008 B): the OOS file of the test table lives in volume `x001`, pages 641 (header page), 642 (row 1's chunk), 643 (row 2's head chunk), 644 (row 3's chunk). Detection is `cubrid checkdb -S` on the copy and a whole-value read through `csql -S`.

| Experiment | Mutation (copy only) | `checkdb -S` | Read path | Observation |
|---|---|---|---|---|
| E0 clean copy | none | passes | all three values equal | the copy procedure is sound |
| E1 payload bytes | 32 bytes of row 1's payload XORed | passes | no error; row 1 compares unequal, rows 2 and 3 equal | payload corruption is neither detected by checkdb nor by the read path (no payload checksum); the wrong value is returned silently |
| E2 chunk header | head chunk length of row 2 overwritten (20,008 → 4,660) | passes | `ERROR: Internal error: out-of-row storage record metadata is inconsistent or corrupted.` (`ER_HEAP_OOS_CORRUPTED_RECORD`, from `oos_check_head_header`) | header corruption is detected on read with a clean error, not by checkdb |
| E3 slotted-page header | `num_slots`/`num_records` of row 1's page XORed | passes | the debug `csql -S` aborts with a core (slotted-page assertion) | checkdb does not examine OOS pages' slotted structure; the debug read path asserts instead of reporting |
| E4c crash image, clean | none | passes | all three values equal | restart recovery of the crash image works (redo of the OOS inserts) |
| E4 log page | 64 bytes of the last written active-log page (physical page 177) XORed | `*** FATAL ERROR ***` (exit 254) | `LOG FATAL ERROR: log_recovery_analysis`, abort with a core | log page corruption is detected (page checksum) and refuses recovery; nothing is silently applied |

A precaution learned the hard way: the first pass of this procedure picked the wrong page (offset arithmetic before the serialized-length correction) and corrupted a volume header, which the debug utilities also answer with an assertion (`disk_verify_volume_header`) — a reminder that with copied images every mutation must be located by a scan of the copy itself, as the final procedure does.

## 7. Bounded test filesystem for exhaustion experiments

**Method that works (no root):** `unshare --user --map-root-user --mount --pid --fork --mount-proc --ipc`, then `mount -t tmpfs -o size=<N> tmpfs <dir under the ticket home>`; the database is created and driven inside that namespace in standalone mode (no port, no `cub_master`). The current user must be mapped to root inside: with `--map-current-user`, both `mount(8)` and a direct `mount(2)` return `EPERM` on this kernel (5.14.0-570.30.1.el9) even though the namespace owns the mount namespace ([`bounded-fs/probe-tmpfs-userns*.txt`](evidence/ticket16/bounded-fs/)). Mapping to root changes only the uid seen inside: files land on the tmpfs, `createdb` inside the namespace on an ordinary disk directory also works (probe T1 in the journal), and the private PID namespace tears everything down when the leader exits. Ports are not involved because the experiments are standalone; a client-server variant would need the campaign's port allocation as in ticket 14.

**Confinement shown** ([`bounded-fs/journal.txt`](evidence/ticket16/bounded-fs/journal.txt)): inside, `df` shows the tmpfs filling (0 → 231,981,056 of 268,435,456 bytes); after the namespace exits the mount point holds 0 entries, `mount` lists 0 tmpfs entries outside, and the only trace on `/home` is the small `databases.txt` and the copied logs under the ticket directory (the host-wide `df` delta of a few hundred MB during the run is this ticket's own concurrent evidence copying, not the tmpfs).

**Exhaustion observed, four attempts:**

| Attempt | Setting | Outcome |
|---|---|---|
| 1 | 48 MiB tmpfs, `--log-volume-size=16M` | `createdb` refuses: the log volume minimum is 20 MiB |
| 2, 3 | 128 MiB and 256 MiB tmpfs, default `db_volume_size` | `createdb` itself exhausts the filesystem while formatting the generic volume `_x001` at the default 512 MiB (`ER_IO_FORMAT_OUT_OF_SPACE`: "Unable to format disk volume …/bfs_x001 with 32768 pages … due to insufficient space"), then the debug utility aborts on `catcls_install(): Assertion 'false'` and leaves a half-created database whose open asserts in `disk_is_sector_reserved` |
| 4 (final) | 256 MiB tmpfs, `db_volume_size=32M` | `createdb` succeeds (64 MiB primary — the 16 MiB request is rounded up — plus 20 MiB log, 20 MiB temporary archive, 1 MiB DWB); the fill inserts **7,422 rows of 12,000 B** (89 MB of OOS payload, volumes `_x001`/`_x002` added automatically), then adding `_x003` fails with `ER_IO_FORMAT_OUT_OF_SPACE` ("with 4096 pages … Current space available is 2176 pages"), `OOS [ERROR](oos_file_alloc_new): file_alloc failed`, and the debug process aborts on `oos_file_alloc_new … Assertion 'false'` (core); a fresh open recovers and reads 7,422 rows, `Oos_num_recs` 7,422 ([`A-csql-err-excerpt.txt`](evidence/ticket16/bounded-fs/A-csql-err-excerpt.txt)) |

**CUBRID-level bounds are not available at the pin.** Permanent data volumes auto-extend (`disk_extend`: expand the last volume to its maximum, then add volumes up to `LOG_MAX_DBVOLID`); no parameter disables it, `volume_extension_path` only chooses where extensions go, and `--db-volume-size=16M` is rounded up to 64 MiB. Variant B (same fill on disk, [`B-*`](evidence/ticket16/bounded-fs/)) inserted 1,500 rows with `_x001`/`_x002` added at 64 MiB each. Space experiments must therefore bound the filesystem, as above, or use a size-capped block device that this host does not offer without root.
