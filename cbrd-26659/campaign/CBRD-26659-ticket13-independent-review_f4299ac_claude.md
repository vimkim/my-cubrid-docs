## Findings

### F1 — MAJOR, blocking. The record declares the specification's independent review done, and the answer promotion accepted

§10 of the ticket 13 report is titled "Independent agent review (2026-09-10)", opens "That review has now run, in a session with no access to this one's reasoning, read-only", and states **"Verdict: ACCEPT WITH CONDITIONS. The answer promotion is accepted."** §12 closes with **"The answer promotion is accepted. None of the conditions blocked it."**

That review was commissioned by the authoring session. §12 says so itself, while disclosing that the brief the author wrote for it "contained a false premise" about what was running on the host. The specification requires "an independent agent session, never the authoring session". Ticket 13's own Outcome block says the review "was commissioned by the authoring session and does not satisfy it." §9 of the same report lists the independent review under *Still outstanding*. The document therefore contradicts itself, and the half a future reader meets first — a bold verdict under a heading that quotes the spec's own sentence — is the half that says "accepted".

The campaign has already settled this question for the sibling ticket: docs commit `cbcfc0a`, *"Say plainly that the review record is not a clearance"*, corrected ticket 14's record to state that every commissioned pass was briefed and scoped by the author, that a long list of fixed findings makes a change look cleared rather than making it so, and to name the places where the author's briefs steered attention. Ticket 13's record was left on the wrong side of that line, in the same folder, one day earlier.

**What must change.** Retitle §10 and §12 as commissioned review passes; delete both "the answer promotion is accepted" sentences and the ACCEPT verdict; state that the specification's independent review is this record and not §10; and name where the author's briefs steered attention. For ticket 13 those places are: the decision to classify the promotion as unflagged, which no pass challenged; the `reused` framing of the activation evidence (O2 below); and the choice of `OOS-REP-01`, `OOS-REP-02` and `OOS-SQL-01` as the requirements this case covers, which nothing in §9 to §12 examines (F2 is the consequence).

### F2 — MAJOR, blocking. `OOS-REP-01` is recorded as fully covered on evidence no executed suite produces

The commissioned review's R4 gave `OOS-REP-02` the careful treatment: a `SCOPE OF THIS ROW` note, a caseless companion row `OOS-REP-02/-/placement-discrimination` with `latest_outcome: null`, and `gap_kind: "Delivery gap"` on both, because the committed case cannot detect a largest-first regression. That reasoning applies verbatim to `OOS-REP-01`, and was not applied.

The catalogue statement for `OOS-REP-01` is: "A heap record whose serialized size does not exceed the OOS inline target is stored entirely inline: **no attribute is demoted, HAS_OOS stays clear, and a class that has never demoted a value has no OOS file.**" None of those three clauses is observable at the public SQL seam. If a regression wrongly demoted the comparator row's `big`, `DISK_SIZE` would still report 1,008 — it reports the logical serialized size regardless of placement (ticket 11 §5.2, and the manual: "the size in bytes required to store the value of *expr* after evaluation") — the digests, lengths and equality flags would be unchanged, and CTP would report success. The matrix row's own summary concedes where its evidence comes from: "the activation checker asserted `Has_oos_file` 0 and `Oos_num_recs` 0 after it was inserted". That checker is `activation_check.sh`, a manually invoked script that the same matrix's `placement-discrimination` row describes as "not part of any CTP suite". Yet the `OOS-REP-01` row carries `gap_kind: "none"`, `latest_outcome: "PASS"`, with no scope note.

This is a stronger overclaim than the one R4 fixed. The `OOS-REP-02` case row at least executes the "every value reads back exactly" clause of its statement at the seam. `OOS-REP-01` has no clause the public case executes.

The same question is open for `OOS-SQL-01`, whose statement is about "an inserted **OOS-backed** row". The value-correctness half is genuinely executed by the case — three independent characterizations, all predicted before the run — but the OOS-backed premise rests on the same non-executed checker, and the row says nothing about that. This part is a note, not a blocker: the executed half is the substantive half of that requirement.

**What must change.** Either give `OOS-REP-01` the two-row split R4 gave `OOS-REP-02`, or set `gap_kind: "Delivery gap"` on the existing row with a scope note stating that every clause of the statement is evidenced only by the non-executed checker. Add to the `OOS-SQL-01` row one sentence saying where its OOS-backed premise comes from. The rule these three rows share, and which tickets 18 to 22 will meet on every case: **a matrix row whose only OOS-path evidence is a checker outside every executed suite says so on the row, and does not carry `gap_kind: "none"`.**

### F3 — MAJOR, non-blocking. The R5 fix was applied to the manifest and its schema, and not to the attempt record or its schema

`inv-T13-0002.json` records `executed.assertion_count: null` and, per case, `assertions.executed: null`, with a note stating that recording 27 "would have manufactured a measurement and made the comparison against expected 27 vacuous". `att-T13-0002.json`, the attempt record for the same run in the same directory, records `"assertions": {"executed": 27, "failed": 0}`. The manifest schema was widened (`executed.assertion_count` is now `["integer", "null"]` with a description saying when null is required); `schemas/attempt-record.schema.json` still has `assertions.executed` as a bare `{"type": "integer", "minimum": 0}`, so the attempt record is *obliged* to invent the number — the exact trap R5 said it was removing at the source. Both records validate; that is why the checker did not catch it.

**What must change.** Widen `attempt-record.schema.json` the same way, with the same description, and set `att-T13-0002.json`'s `assertions.executed` to null. Record the schema edit as R5 recorded its own: it is an edit to ticket 12's deliverable, and it is the campaign's contract.

## Observations

### O1 — for ticket 15. CTP's serialized `hasAnswer` reads `false` on every run, including runs that compared against an existing answer

In all four result directories this ticket produced — bootstrap `1020410056` (Fail:1), green `1020415767` (Fail:0), negative control `1020463816` (Fail:1), final `1020515363` (Fail:0) — `summary.info` carries `<hasAnswer>false</hasAnswer>` beside `<shouldRun>true</shouldRun>`. Two of those runs compared against an answer that existed and matched or mismatched it. `ConsoleBO.java:411` (`caseResult.setHasAnswer(hasAnswer)`) looks like it should have written `true`; this review did not find the reason and reports the value as reproducible and unexplained.

It matters because ticket 13's finding (a) tells later tickets to detect the missing-answer trap, and the obvious implementation — read `hasAnswer` from the summary — would mark every case answerless. Use `notRunList` and `execute_case`, which this review confirmed are correct in `main.info` (`execute_case:1, success:1, total:1` for the green run).

### O2 — for the user. What "execution path must match" means for evidence reuse was settled inside an implementation ticket

The specification says activation evidence "is reused only when fixture, execution path, engine configuration and tested conditions match, and that applicability is recorded." Ticket 13 reused standalone (`csql -S`) evidence for a client-server CTP run, and its `applicability.execution_path` says "DIFFERENT" in capitals, then explains why reuse is still licensed: the heap write path under test is server-side and identical, and the spec's own gloss — "proof of an insert path never certifies an unrelated scan, recovery or vacuum path" — makes "execution path" mean the OOS operation, not the run mode.

This review agrees with that reading, and with the choice of `reused` over `proven`; recording the mismatch verbatim instead of quietly upgrading the word is the honest call. But it is a campaign-wide interpretation of a spec rule that tickets 15, 18 to 22 and 23 to 32 will all inherit, and it was decided inside ticket 13, which the spec's reopening rule ("any new design choice reopens the map with a new decision ticket. Decisions are never settled inside an implementation ticket") says is the wrong place. Agents propose; the decision is the user's. Three ways to take it: reopen the map with a decision ticket; fold the interpretation into ticket 35 as a recorded reading with the reasoning above and leave the map closed; or retire it empirically, since ticket 14's `campaign_ns.sh` now makes a namespaced *client-server* activation run cheap and tickets 18 to 22 could run their activation checks in the same mode as the case. The reviewer's preference is the third with the second as the note covering ticket 13 retroactively.

## What was verified and found sound

- **Provenance (criteria 1 and 9).** Branch is exactly `CBRD-26659-oos-testcases-handover`. `origin/develop`'s fetch reflog shows `b94995abf` arriving as a fast-forward on the fetch, `FETCH_HEAD` carries it for `branch 'develop' of https://github.com/CUBRID/cubrid-testcases`, and it is the merge-base with `HEAD`. (`git ls-remote origin develop` today returns `b8874de38`; the remote has moved since the pin, as expected.) Two commits, no upstream configured, the branch on neither `origin` nor `vk`. The `oos-ctp` worktree's two deleted `.sql` files and two untracked `.sql.disable` files are intact at their 2026-02-10 mtimes; the other three public worktrees are untouched.
- **The arithmetic is faithful to the pinned engine, not merely self-consistent.** `oos_boundaries.py`'s model was checked against `src/storage/heap_file.c` at `f4299ac0c`: the gate is `DB_PAGESIZE / 4`; eligibility is `column_size[i] > OR_OOS_INLINE_SIZE`; `OR_OOS_INLINE_SIZE` is `OR_OID_SIZE + OR_BIGINT_SIZE` = 16 (`object_representation.h:466`); `OR_BOUND_BIT_BYTES(count)` is `(((count) + 31) >> 5) * 4` (`object_representation.h:647`); the MVCC header constants are 32 and 16 (`object_representation_constants.h:142,148`); candidates sort largest-first with an index-descending tiebreak; and the model reproduces the engine's detail of testing a *stale* `header_size` inside the demotion loop and recomputing after it. Hand-checked: row 1 = 28 + 4,220 + 16 = 4,264 B, demotes `big` under both accountings, lands at 1,272 B pinned / 1,280 B normative; row 2 = 1,564 B under both. `derive_case_sizes.py` and `--self-test` reproduce `derivation-output.txt` and `selftest-output.txt` exactly.
- **The oracle is genuinely independent of the engine.** All four digests reproduce in Python from the byte patterns alone: `md5("cc"*1000)` = `b8db77f0…`, `md5("dd"*500)` = `d9a0e8de…`, `md5("aa"*3000)` = `56d1d803…`, `md5("bb"*1200)` = `6d5d5cbc…`, matching the committed answer byte for byte. This is the strongest part of the delivery: it makes the "justified before the engine ran" claim verifiable without trusting file mtimes, which the report itself correctly declines to rely on.
- **`DISK_SIZE` in the answer asserts documented behavior.** This review checked whether asserting `disk_size(big) = 3008` for a demoted value promotes an undocumented observation, which the authority policy forbids. It does not: the manual (`en/sql/function/information_fn.rst:232`) documents `DISK_SIZE` as "the size in bytes required to store the value of *expr* after evaluation", a property of the value, and the case's 3,008 / 1,208 / 1,008 / 508 are `ALIGN(5 + N, 4)` derived from source. The case header's caution that `DISK_SIZE` is not a placement oracle is correct and is what F2 turns on.
- **Promotion by rename (criterion 4).** The committed answer, the untracked `cases/*.result`, the bundle's `candidate.result` and `expected.answer` all hash to `b38a24b5e1b4c35ce80d9553cef177ba7b0b05228edd3ca286fb19901713aea6`. The review note in `answer_promotions` is present and accurate.
- **The CTP comparison is whole-text, so the derived-27 argument is sound.** `ConsoleBO.saveResults` compares `answer.equals(result)` after `replaceAll("\r", "").replaceAll("\n", "")` on both sides: a byte-identical `.result` does entail that every scalar matched. Finding (a)'s citation is also correct: `ConsoleBO.java:366-375` sets `shouldRun = false` when the answer file is missing under `MODE_RESULT`.
- **Negative controls (criterion 6 and the spec's checker-validation rule).** Three checking mechanisms, three controls, each shown to fail. CTP: the control scenario at `~/.cub/campaign/cbrd-26659/negative-control/cbrd_26659_nc/` is outside the repository, its `.sql` is byte-identical to the committed case, its answer differs in exactly one hex digit, and CTP reported `Fail:1 Success:0 Total:1`. Activation checker: `check-negcontrol/assertions.txt` fails exactly the discriminating assertion (`expected 1224 got 3024`) and the script exits 1. Derivation gate: both disputed fixtures rejected, the shipped fixture accepted. The record's account of the `tee`-subshell defect the activation control exposed — a checker that printed FAIL and exited 0 — is the campaign's best single argument for the rule, and it was found by the control rather than by reading.
- **Activation evidence and its channel (criterion 5).** The ticket text asked for the debug OOS log; ticket 11 §6 had already established that the INSERT path writes none. The delivery measured it (`oos.log` at 10 lines before and after on the debug install, 0 `oos_insert` lines), used `SHOW HEAP OOS OF` instead as the handoff directs, and recorded the channel gap as its own Capability-gap matrix row so no later ticket assumes the log can witness an insert. That is the right handling of an infeasible criterion. `checkdb -S` exit 0 on all three checker databases.
- **Records and bundle (criterion 7).** `inv-T13-0002.json`, `att-T13-0002.json`, `matrix.json` and `bundle-att-T13-0002.json` all validate under the campaign's `minischema`; `check_campaign_records.py` passes; `render_docs.py --check` reports fresh. The bundle's 19 indexed files verify with `sha256sum -c`; `total_bytes` 46,360 is the 20-file directory total including `SHA256SUMS` itself (44,735 + 1,625), which is a reasonable reading of the field. Retention class `success-bulky`, expiry 2026-09-17.
- **Timing (criterion 8).** 39 s wall clock (20:41:25 to 20:42:05) recorded in `timing.txt`, the manifest and the report for ticket 17; both caps far from reached. CTP's own `Elapse Time:69` in the same log is on some other clock and should not be mistaken for the wall-clock figure.
- **Cleanup disclosure.** The attempt record's `cleanup.evidence` states outright that "no unrelated process was killed" held only because the kernel refused 22 signals, not because CTP scoped its kill, and that the user's idle `develop` `cub_master` was stopped by hand beforehand.
