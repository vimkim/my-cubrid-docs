## Checker and fixture hazards

**H dur01 has unusually good reusable checks.** `expected_md5` computes the digest using host `md5sum`, independently of the database (`:254–261`). `assert_row` checks that digest, octet/bit/serialized lengths and exact SQL equality in one tagged row (`:315–340`). `run_txn` journals request, exit code, affected rows and output errors (`:278–311`). OOS fields are located by exact header-name equality, a named quoted class row, and adequate field count (`:401–451`). These checks are safer reuse targets than a grep for a success token alone. The negative control tests one wrong expected multichunk byte and cannot enter normal discovery (`make_negative_control.sh:28–35`, `:59–75`).

Its limits must be kept explicit:

- The four fixture sizes `4036/16284/4011/4036` and count expectations `4` before crash, `3..5` after recovery (`:129–142`) were reconciled historically with two layouts; they are not a reusable boundary proof. For a non-boundary durability scenario, comfortably large deterministic values such as 8KB/40KB avoid depending on the disputed band; derive exact serialized/chunk counts from the chosen source/layout before asserting them.
- The post-recovery `3..5` range intentionally permits unreclaimed old chains; it proves no cleanup/reclaim deadline (`:811–818`).
- Its recovery reader demands exactly one new REDO phase and nonzero total redo records (`:552–573`, `:785–796`). This is useful proof that recovery did work, but not that a particular `RVOOS_INSERT`/`RVOOS_DELETE` was replayed. Flushed OOS pages plus replayed unrelated metadata can satisfy that predicate. Require an OOS-specific recovery trace or a discriminating unflushed/undo schedule before crediting the stronger path claim. Current logging functions name `RVOOS_INSERT` and `RVOOS_DELETE` at [`oos_file.cpp:3193–3221`](/home/vimkim/gh/cb/CBRD-26659-oos-testcases-handover/src/storage/oos_file.cpp:3193).
- Release/debug-label gating yields a reasoned SKIP, unlike legacy TDE's bare OK; the native runner's `verdictOf` still declares any nonempty result without substring NOK successful ([`case.go:163–179`](/home/vimkim/gh/cubrid-testkit/main/internal/runner/shellsuite/case.go:163)). H's custom `case_outcome=SKIP` therefore needs the focused verifier or stricter required-capability handling; runner green alone cannot be coverage evidence (`:860–883`).
- With `SHOW HEAP OOS` unavailable, it can report a case-level SKIP after functional values pass. Required optdebug coverage needs an explicit non-skip validation result; absent observability is a capability gap, not a passing storage assertion.
- `wait_for` bounds polling elapsed time, but a condition command itself can hang; the synchronous `cubrid server start` is outside the 60-second readiness polling (`:485–499`, `:764–767`). There is no EXIT/TERM trap. A testcase-level timeout and cleanup-aware process handling still matter.
- Crashing all newly appearing masters (`:723–747`) is acceptable only within the case's disposable PID namespace. The pre-existing-master snapshot does not prevent an unrelated master started later from becoming a target outside containment. Native isolated slot execution is the intended boundary.

**D DROP scripts can pass without OOS.** Their 600–1,000B fixtures are below the record gate; ordinary DROP/checkdb can satisfy the assertions. The two big helpers use 4,000B, also below the accepted/current trigger for the simple schema; actual string-to-bit behavior must not be assumed from an old comment. Their `after_insert` value is only printed, not asserted to grow (`bigoos.sh:43–45` and CS `:45–47`); both empty `spacedb` parses compare equal (`:62`, CS `:65`); final checkdb error is a warning (`:71–75`, CS `:74–78`). Their filenames make them undiscoverable, even though comments call them tests. Early calls to `finish` without a following exit should also be reworked into an explicit terminal path rather than relying on helper behavior.

**M cbrd_26527 proves more, but costs more.** It disables compression, reduces `postpone_cache_size` to 8 and loads **10,000 rows × ten `char(2048)` columns**, approximately 205MB of logical payload, with 100M initial data/log volumes (`:34–54`). The ten Cartesian digit sources with `LIMIT 10000` need not materialize 10^10 rows, but remain unnecessary complexity for a new narrow OOS case. The useful positive owner-HFID extraction precedes disappearance (`:107–128`). However createdb/start/DML/diagdb status and complete outputs are not explicitly checked. An empty failed post-DROP diagdb produces zero counts and can satisfy absence checks; parse/utility failure must fail separately. Record actual OOS VFID too, and retain a surviving table as a control rather than proving whole-output disappearance alone.

**TDE uses optdebug-compatible gating, with weak fallback.** Most listed file/log cases call `write_ok` and exit when `cubrid_rel` lacks `debug` (`file_enc_01:7–13`; analogous lines in the others). That branch is not verified coverage. At engine `fb567a629`, `OptDebug` maps to the string **optdebug**, so the normal optdebug identity includes `debug`; GCC optdebug flags omit NDEBUG ([`CMakeLists.txt:187–194`](/home/vimkim/gh/cb/CBRD-26659-oos-testcases-handover/CMakeLists.txt:187), [`:234–237`](/home/vimkim/gh/cb/CBRD-26659-oos-testcases-handover/CMakeLists.txt:234)). Do not report a speculative optdebug skip. Record the actual build identity and prove the intended assertions ran. Digits stripped from TDE event diffs discard VFID/VPID correlation; metadata TDE checks still have value but do not prove ciphertext or recovered byte identity.

**CDC is expensive and incompletely bounded.** cbrd_27064's 300-second timeout covers extraction only, after synchronous setup/workload (`:174–209`); five successful extraction phases can each use that allowance, and DML/start/compilation is outside it. cbrd_27075 bounds its C API driver internally but `wait "$wpid"` for the workload has no shell deadline (`:130–137`). Both compile a C driver and modify supplemental logging/archive policy; neither is a small replacement for an OOS-specific shell test. Retain these important regressions because of scope/defect policy, not because an old generic timing projection says they are cheap.

## Feasible activation evidence and stable test layout

Current source supports per-class `SHOW HEAP OOS OF` and `SHOW ALL HEAP OOS OF`, DBA-only, with named fields for file existence/identity, pages, chunks, sum length and physical/unused bytes ([`show_meta.c:388–420`](/home/vimkim/gh/cb/CBRD-26659-oos-testcases-handover/src/parser/show_meta.c:388)). Prefer that existing interface to requiring an engine change for every new testcase. Match fields by exact names and class identity; parse failures and errors fail the test. A positive OOS file plus positive live chunk count on a deliberately large VARBIT fixture is practical activation evidence. `DISK_SIZE` is a logical value size and cannot substitute for physical placement.

This statistics walk is **not a synchronized oracle** under concurrent mutation: it conditionally read-latches pages and deliberately skips busy/deallocated pages, accepting slight undercount ([`oos_file.cpp:3854–3908`](/home/vimkim/gh/cb/CBRD-26659-oos-testcases-handover/src/storage/oos_file.cpp:3854)). For exact count assertions, stop writers and wait for declared barriers/quiescence; do not infer reclamation from one low racing sample. VFID/page measurements should be tied to the same fixture and phase. For DROP and metadata TDE attribution, current diagdb prints the OOS owner class and HFID ([`file_manager.c:1407–1409`](/home/vimkim/gh/cb/CBRD-26659-oos-testcases-handover/src/storage/file_manager.c:1407)); the cbrd_26527/tbl_enc parsers can be strengthened around that format.

Not every accepted internal invariant is fully observable through SQL/shell. Exact same-slot identity retry, allocator growth-gate cursor execution, LSA-horizon defer/reclaim and mid-chunk atomic failure need a deterministic existing control/trace. If a required seam is absent, record **capability gap**, required evidence and expected behavior; a random churn pass is not a replacement. Existing unit tests/source evidence may explain the design, but the user authorized developer-delivered public SQL and private shell cases, so unit coverage must not be counted as a delivered case.

Recommended new shell layout follows repository discovery, e.g. `shell/_06_issues/_26_2h/cbrd_26659_oos_<behavior>/cases/cbrd_26659_oos_<behavior>.sh`. Keep immutable expected `.answer` files and necessary model/checker source tracked; result/journal/log/database files are disposable execution artifacts. Helpers use nonmatching names; controls have a separate scenario root. Use `. $init_path/init.sh`, `init test`, explicit `write_ok`/`write_nok`, and `finish`, with cleanup on failure/timeouts. Avoid copying the 888-line historical case into every new scenario: retain a small shared helper only when several actual cases need it, and keep per-case expected states readable.

Polling sleep only paces a wait; it does not prove ordering or vacuum completion. A schedule needs persistent sessions, a coordinator, acknowledged barriers, a per-stage deadline, query/utility timeout, logged expected outcome, and explicit terminal cleanup. Retain failed model/input, result file, relevant server/recovery/OOS logs and database image before deletion when the failure requires it. Fresh execution-owned directories avoid stale-log passes.
