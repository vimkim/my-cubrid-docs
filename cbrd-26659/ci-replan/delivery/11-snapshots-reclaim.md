## Snapshot and reclaim proof boundaries

[The manual's isolation rule](/home/vimkim/gh/cubrid-manual/en/sql/transaction.rst:1535) gives a unique snapshot for an entire `REPEATABLE READ` transaction and allows another transaction to modify rows read by it. Real CSQL clients run with autocommit disabled; reader isolation is read back with `GET TRANSACTION ISOLATION LEVEL`. Marker SELECTs acknowledge each completed command group. Reader first establishes A/D/S, then retains exactly A/D/S while writer changes are uncommitted and after acknowledged writer commit. A fresh client must see N/S and no row2. Both persistent clients acknowledge their last commit, exit zero and are waited before reclaim polling.

The case uses ordinary CS mode, 16KiB I/O/log pages and 64MiB initial DB/log volumes. Attempt-local `[@dbname]` sets `vacuum_disable=n`, `vacuum_log_block_pages=4`, `vacuum_worker_count=1`. Ordinary parameter dumps and developer-hidden `--dump-flag 8` prove these effective values. The four-page block setting shortens log advancement for this focused fixture and is source-permitted; it is not an internal test hook. Hidden flags follow [paramdump](/home/vimkim/gh/cb/CBRD-26659-oos-testcases-handover/src/executables/util_cs.c:2339) and `PRM_HIDDEN=0x8`. Config restoration is independently checked by the controller and framework wrapper.

Fixed `BIT(8000)` filler rows advance logged data until the actual append page closes the mutation block and moves at least two four-page blocks beyond its marker. `SHOW LOG HEADER` omits a path: [log_active_log_header_start_scan](/home/vimkim/gh/cb/CBRD-26659-oos-testcases-handover/src/transaction/log_manager.c:9330) copies the live server header under the log read lock; a supplied path reads the disk header. This matters because a stale disk header cannot establish eligibility.

The normal daemon supplies progress. CS `vacuumdb` is used only for `--dump`, consistent with [the documented unsupported CS trigger](/home/vimkim/gh/cubrid-manual/en/admin/admin_utils.rst:3650). After three equal consecutive expected SHOW states spaced 0.5 seconds, the reported first pending log page must pass the entire mutation block. [vacuum_update_keep_from_log_pageid](/home/vimkim/gh/cb/CBRD-26659-oos-testcases-handover/src/query/vacuum.c:5954) identifies the first page of the first unvacuumed block, or the next block after the last completed one. Reclaim credit requires positive prior owned OOS data, unchanged class/HFID/VFID, no owned active session, stable exact chunk/byte statistics, full live survivor checks and a user-page count below the observed positive high-water mark.

Three bounded INSERT/DELETE cycles use the same workload. Cycle2/3 drained pages must not exceed cycle1's drained count, and each cycle must show positive OOS growth followed by a physical page drop and exact S. This is an observed compact plateau. It does not prove exact growth cursor position, LSA horizon calculation, lost-hint recovery, deterministic same-slot retry, forced latch loss, concurrent deallocation counters or OS file shrinking.

The abort case keeps a committed delete-control table. Its zero chunks/zero record bytes, stable samples and progress dump establish daemon completion after the aborted UPDATE block; the OOS sticky header may remain. Only then does the intended A/S post-vacuum read execute. Immediate rollback success remains a separately named assertion.
