## What can and cannot be timed from existing artifacts

1. **Whole invocation:** time the native or company runner from before testcase/runner setup through cleanup. SQL CTP performs initial cleanup, configuration, database creation, test execution, and final cleanup in that order. The runner has fixed sleeps during service startup/stop and deletion, making per-case execution sums insufficient for whole-invocation timing. Evidence: [run.sh, lines 899–916](https://github.com/CUBRID/cubrid-testtools/blob/44e3f97c788ad82091d5b66d728852f3279b1e86/CTP/sql/bin/run.sh#L899-L916), [stop/delete/start, lines 457–552](https://github.com/CUBRID/cubrid-testtools/blob/44e3f97c788ad82091d5b66d728852f3279b1e86/CTP/sql/bin/run.sh#L457-L552).
2. **Per-case work:** SQL `summary_info` contains case verdicts and milliseconds; shell publishes `feedback.log` and `test-shell.xml`. SQL's inner timer starts after connection reset and finishes after executing the case SQL, so it excludes suite startup and at least some per-case preparation. Evidence: [SQL timer start, lines 1025–1034](https://github.com/CUBRID/cubrid-testtools/blob/44e3f97c788ad82091d5b66d728852f3279b1e86/CTP/sql/src/com/navercorp/cubridqa/cqt/console/bo/ConsoleBO.java#L1025-L1034), [timer end, lines 1280–1285](https://github.com/CUBRID/cubrid-testtools/blob/44e3f97c788ad82091d5b66d728852f3279b1e86/CTP/sql/src/com/navercorp/cubridqa/cqt/console/bo/ConsoleBO.java#L1280-L1285), [artifact publication, lines 2036–2056](https://github.com/CUBRID/cubrid/blob/350958e8484d0e7a558ad166bffbd56e70683202/.github/workflows/gha-ci.yml#L2036-L2056).
3. **CI wall clock:** workflow stamps report queue/build/split and each suite's longest/median shard and wall-clock span. Shard stamps begin before storage/provenance/setup, and end after publishing results. Consequently they cover a different boundary than testcase elapsed time, and parallel wall-clock span differs from aggregate runner occupancy. Evidence: [shard start, lines 1744–1749](https://github.com/CUBRID/cubrid/blob/350958e8484d0e7a558ad166bffbd56e70683202/.github/workflows/gha-ci.yml#L1744-L1749), [shard end, lines 2116–2120](https://github.com/CUBRID/cubrid/blob/350958e8484d0e7a558ad166bffbd56e70683202/.github/workflows/gha-ci.yml#L2116-L2120), [clock calculation, lines 2303–2354](https://github.com/CUBRID/cubrid/blob/350958e8484d0e7a558ad166bffbd56e70683202/.github/workflows/gha-ci.yml#L2303-L2354).
4. **Scheduling history:** only shell's per-case timings feed the current splitter; all attempts are summed. SQL splits by directory/name, not timings. A new OOS SQL directory may therefore increase one existing shard's duration even if the total testcase set stays small. Evidence: [shell timing update, lines 2231–2264](https://github.com/CUBRID/cubrid/blob/350958e8484d0e7a558ad166bffbd56e70683202/.github/workflows/gha-ci.yml#L2231-L2264), [SQL split, lines 1562–1578](https://github.com/CUBRID/cubrid/blob/350958e8484d0e7a558ad166bffbd56e70683202/.github/workflows/gha-ci.yml#L1562-L1578).

## Planning implications and outstanding verification

- Chosen validation reference: the existing local setup. Record engine, testcase and native-runner identity, effective configuration, page-size readback, case counts, results and timing boundaries. Company configuration is compatibility evidence, rather than a required GHA timing run.
- Report SQL and shell local elapsed times separately. Roughly ten minutes for each is guidance; no company-CI speedup or fixed conversion factor can be inferred from local measurements.
- The CI shell timeout of 1200 seconds is an infrastructure failure bound. Dedicated OOS cases should use justified bounded waits and report useful expensive workloads explicitly.
- Configured pod values were found, but deployed values and exact worker CPU/storage hardware were not inspected: this host has no `kubectl` executable or detected `~/.kube/config`. No fixed CI throughput can be inferred from CPU/memory limits alone.
- Current configurations and API identities were captured read-only at research time. Test images, branch tips and production deployment can change before integration. This report establishes no pass verdict or new OOS testcase elapsed time.

Known engine defects and reproducers must remain visible with explicit disposition and receive no verified-coverage credit; the delivered company-CI set must pass, per the user's planning decision. Coverage selection and exact mandatory modes are owned by the coverage/specification phase.
