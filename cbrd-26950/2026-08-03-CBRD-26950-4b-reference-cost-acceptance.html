CBRD-26950 · Executive Decision Brief

OOS generation reference의
4B 비용을 왜 수용해야 하는가

작성일 2026-08-03 · JIRA 상태 Analysis (2026-08-03 조회) · 상세 검증 기준 feat/oos 0ad6afc0f (2026-07-31)
결론: OOS inline stub을 16B에서 20B로 늘리고, generation 4B를 reference의 일부로 받아들여야 합니다. 이 4B는 성능 기능을 위한 선택 비용이 아니라, 재시도 가능한 삭제가 살아있는 데이터를 지우지 않도록 만드는 최소 correctness 비용입니다.
수용하지 않을 때
무증상 데이터 손실
오류 없이 살아있는 OOS value chain 전체가 삭제될 수 있습니다.
수용할 비용
reference당 +4B
청크 헤더도 청크당 +4B이며, 비용은 명시적이고 상한을 계산할 수 있습니다.
반영 시점
출시 전 지금
feat/oos 출시 전이므로 기존 OOS 포맷 마이그레이션이 필요하지 않습니다.

1. 문제는 “두 번 삭제”가 아니라 “다른 데이터 삭제”입니다

OOS OID는 논리 식별자가 아니라 (volid, pageid, slotid) 물리 주소입니다. 슬롯이 비었다가 다른 OOS chunk record에 재할당되면 같은 OID가 즉시 다시 나타납니다. vacuum은 미완료 블록을 처음부터 재처리하지만, 현재 probe는 슬롯의 점유 여부만 확인합니다.

01옛 참조 보존UPDATE undo image에 옛 head OOS OID가 남습니다.
021차 삭제 커밋vacuum sysop이 옛 value chain을 정상 회수합니다.
03슬롯 재사용다른 INSERT가 같은 물리 OID에 새 청크를 저장합니다.
04블록 재처리중단된 vacuum이 같은 undo image를 다시 읽습니다.
05살아있는 값 삭제“점유됨”만 확인하고 새 점유자의 체인을 삭제합니다.
sysop은 한 번의 멀티페이지 삭제를 all-or-nothing으로 만들지만, 이미 커밋된 요청이 다시 호출되는 것을 막거나 현재 점유자의 신원을 확인하지는 않습니다.

2. 4B는 reference가 가져야 할 최소 신원 정보입니다

안전한 지연 삭제에는 “어디인가”뿐 아니라 “그 주소의 몇 번째 점유자인가”가 필요합니다. generation은 주소 재사용 전후를 구분하는 incarnation 값입니다.

같은 주소와 같은 길이의 새 값은 옛 reference와 구분되지 않습니다.

현재 청크와 기대 generation이 다르면 재사용된 슬롯이므로 삭제하지 않습니다.

2026-08-03 설계 논의의 전제는 향후 RECDES.length를 64-bit로 확장하는 것입니다. 따라서 full length 8B를 4B로 줄여 generation 공간으로 재사용하는 안은 미래 포맷 요구를 훼손하므로 제외합니다.

결국 OID와 64-bit length를 유지한 채 슬롯 incarnation을 구분하려면, 새 정보가 reference에 영속적으로 포함되어야 합니다. 32-bit generation은 검토안 중 이 목적만 수행하는 독립 필드이며, 잘못된 일치가 다시 나오려면 stale한 vacuum reference가 남아 있는 동안 같은 페이지에서 counter가 2^32회 돌아야 하므로 충분한 범위를 제공합니다.

3. 비용은 작고 명시적이며, 회피안의 비용은 더 큽니다

+4BOOS-backed attribute 1개
+16BOOS-backed attribute 4개
+40BOOS-backed attribute 10개
  • Heap record: OOS-backed attribute마다 inline stub이 16B → 20B가 됩니다.
  • OOS storage: OOS chunk header가 16B → 20B가 되어 청크마다 4B가 추가됩니다.
  • OOS page: page-local uint32 counter가 페이지마다 한 번 추가됩니다.
  • 4,060B target과 비교: stub 1개의 +4B는 약 0.10%, 10개의 +40B도 약 0.99%입니다.
  • 16KB page와 비교: 큰 청크 1개의 +4B는 페이지 규모의 약 0.025%입니다.
“4B를 없애는” 대안은 비용을 제거하지 않습니다. heap record 공통 확장, UPDATE hot path backfill, vacuum 진행 모델 변경, 슬롯 재사용 격리 같은 더 넓고 지속적인 비용으로 이동시킵니다.

4. 제안은 기존 흐름을 유지하는 국소 변경입니다

  • 이미 W-latch를 보유한 OOS page에서 counter를 증가시켜 generation을 발급합니다.
  • OOS chunk header와 inline stub에 같은 head generation을 저장합니다.
  • undo image는 inline stub을 그대로 보존하므로 기대 generation도 자동으로 보존됩니다.
  • 삭제 전 현재 generation과 기대 generation을 비교하고, 불일치하면 성공적인 no-op으로 처리합니다.
  • RVOOS_INSERT/RVOOS_DELETE는 레코드 전체 이미지를 물리 로깅하므로 복구 handler의 기본 구조는 유지됩니다.
  • slave는 기존처럼 자체 oos_insert를 수행하고 로컬 OID와 로컬 generation을 함께 발급합니다.
  • stub은 20B로 유지하고 24B padding은 추가하지 않습니다. variable area에서 8-byte 정렬을 보장하지 못하기 때문입니다.

5. 지금 수용하지 않으면 출시 후 비용이 커집니다

feat/oos가 아직 출시되지 않은 현재는 OOS 온디스크 포맷을 바꿔도 기존 고객 데이터에 대한 호환 처리나 마이그레이션이 필요하지 않습니다. 출시 후 동일한 변경을 하면 구·신 stub과 chunk header 판별, 파일 포맷 버전, 백업/복구 호환, 마이그레이션 정책이 추가됩니다.

반면 수정을 미루면 silent data loss 가능성을 가진 포맷을 먼저 고정하게 됩니다. 이번 결정은 4B와 0B의 비교가 아니라, 지금의 국소적인 4B 비용과 출시 후의 데이터 손실·마이그레이션 비용을 비교하는 결정입니다.

승인 요청

  • OOS inline stub의 4B generation reference 비용을 수용합니다: 16B → 20B.
  • OOS chunk header에도 generation 4B를 추가합니다: 16B → 20B.
  • 향후 64-bit RECDES.length 확장을 위해 full length 8B는 그대로 유지합니다.
  • MVCC 필드 hash, length bit 재사용 등 신원 정보를 저장하지 않는 shortcut은 채택하지 않습니다.
  • 온디스크 호환 부담이 생기기 전인 feat/oos 머지·출시 전에 반영하고 fault-injection 회귀 테스트를 merge gate로 둡니다.
