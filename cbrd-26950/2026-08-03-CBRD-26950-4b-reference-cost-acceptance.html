CBRD-26950 · Formal Decision Report

OOS 참조에 generation 4바이트를
반드시 추가해야 하는 이유

vacuum 재처리와 OOS 슬롯 재사용이 만나면 살아있는 데이터가 삭제되는 문제를, 데이터베이스를 처음 배우는 독자도 따라갈 수 있도록 정상 동작부터 단계별로 설명한 승인 검토 보고서

작성일 2026-08-03 · JIRA CBRD-26950 Analysis · 기술 검증 기준 feat/oos 0ad6afc0f (2026-07-31)

승인 요청 결론 OOS inline stub을 16바이트에서 20바이트로 늘리고, 물리 주소와 함께 4바이트 generation을 저장해야 합니다. 이 비용은 선택적인 성능 개선 비용이 아니라, 재시도 가능한 삭제가 주소를 재사용한 다른 데이터까지 지우지 않게 만드는 데이터 정확성 비용입니다.
수정하지 않을 때 무증상 데이터 손실 오류나 경고 없이 다른 행의 살아있는 OOS 값 전체가 사라질 수 있습니다.
수정 비용 참조마다 +4바이트 OOS-backed attribute의 stub과 각 OOS 청크 헤더에 각각 4바이트가 추가됩니다.
수정 효과 주소 + 신원 확인 같은 슬롯의 새 점유자를 옛 점유자와 구분하여 잘못된 삭제를 성공적인 no-op으로 바꿉니다.

1. 먼저 알아야 할 용어

이 문제는 어려운 약어가 많지만, 핵심은 “주소는 재사용될 수 있으므로 주소만으로 물건의 주인까지 알 수 없다”는 간단한 원리입니다. 아래 용어만 이해하면 뒤의 사고 순서를 그대로 따라갈 수 있습니다.

용어쉬운 뜻이 보고서에서의 역할
heap record테이블의 한 행을 디스크에 저장한 레코드입니다.큰 값 자체 대신 OOS를 찾아갈 작은 참조를 보관합니다.
OOS
Out-of-row Storage		행 안에 넣기 큰 가변 길이 값을 별도 파일에 저장하는 방식입니다.큰 문자열·비트 값 등을 하나 이상의 청크로 나누어 저장합니다.

WAL

2. OOS의 정상 동작부터 이해하기

2.1 큰 값은 밖에 두고, 행에는 16바이트 안내표만 둡니다

큰 값을 heap record 안에 그대로 넣으면 한 페이지에 들어갈 행 수가 줄어듭니다. OOS는 큰 값을 별도 OOS 파일에 두고, heap record에는 그 값을 찾는 참조만 남깁니다. 현재 OOS inline stub은 다음과 같습니다.

head OOS OID
8B
full length
8B

예를 들어 (vol 1, page 20, slot 5)는 “1번 볼륨의 20번 페이지에 있는 5번 슬롯”이라는 주소입니다. 이 값에는 “R1 행의 데이터”라는 소유자 정보가 없습니다.

2.2 UPDATE는 새 OOS chain을 만들고, 옛 chain은 당장 지우지 않습니다

CUBRID의 MVCC에서는 UPDATE 이전 값을 보고 있는 트랜잭션이 있을 수 있습니다. 따라서 UPDATE가 끝났다고 옛 OOS 값을 즉시 지우면 안 됩니다. 현재 설계는 새 버전에 새 OOS chain을 만들고, 옛 버전의 inline stub을 undo image에 그대로 남깁니다.

UPDATE 전 heap R1 ── stub { OID=A, length=5000 } ──▶ OOS chain A UPDATE 후 현재 heap R1 ── stub { OID=B, length=5000 } ──▶ 새 OOS chain B undo image ── stub { OID=A, length=5000 } ──▶ 옛 OOS chain A 옛 버전을 볼 수 있는 트랜잭션이 사라진 뒤 vacuum이 undo image에서 OID=A를 읽고 옛 OOS chain A를 삭제

2.3 vacuum은 로그 블록 전체가 끝나야 진행 완료를 기록합니다

vacuum은 로그를 블록 단위로 나누어 처리합니다. 하지만 한 OOS chain 삭제는 그보다 작은, 레코드 단위 sysop으로 먼저 확정됩니다. 따라서 블록 중간까지 처리한 뒤 worker가 중단되면 다음 두 사실이 동시에 성립할 수 있습니다.

  1. 이미 처리한 OOS chain 삭제는 sysop commit으로 확정되어 있습니다.
  2. 블록 전체는 끝나지 않았으므로 시작 위치 start_lsa가 전진하지 않았고, 같은 블록을 처음부터 다시 읽습니다.
이것은 sysop이 실패한 것이 아닙니다. 작은 작업의 성공 기록과 큰 블록의 완료 기록이 서로 다른 단위이기 때문에 생기는 재처리입니다. 재처리 자체는 vacuum이 누락 없이 청소하기 위한 정상적인 복구 전략입니다.

3. 살아있는 데이터가 삭제되는 정확한 순서

아래에서 R1은 이미 UPDATE되어 옛 OOS chain을 청소해야 하는 행이고, R2는 그 뒤 새 값을 저장한 살아있는 행입니다. 같은 주소를 A = (V, P, S)라고 표시합니다.

R1의 옛 OOS 주소 A가 undo image에 남습니다

R1을 UPDATE하면 새 버전에는 새 OOS chain이 생깁니다. 옛 주소 A는 불변인 WAL의 undo image에 남아 vacuum의 삭제 대상이 됩니다.

vacuum이 A의 옛 chain을 정상 삭제합니다

vacuum은 undo image에서 A를 읽고, oos_chunk_exists(A)가 true이면 oos_delete(A)를 실행합니다. 삭제 sysop이 commit되므로 R1의 옛 chain은 정상적으로 사라집니다.

빈 슬롯 S가 즉시 재사용 가능한 공간이 됩니다

OOS 페이지는 ANCHORED 방식이므로 삭제한 slotid를 재사용합니다. 삭제된 페이지는 bestspace 후보로 등록되고, insert는 사용 가능한 페이지와 빈 슬롯을 적극적으로 찾습니다.

다른 행 R2의 새 청크가 같은 주소 A를 받습니다

R2의 OOS insert가 같은 (V,P,S)를 배정받습니다. 주소 A는 같지만 내용과 소유자는 완전히 다릅니다. R2 트랜잭션이 commit하면 이 시점의 A는 복구 뒤에도 남아야 하는 살아있는 R2 데이터입니다.

vacuum worker가 블록 완료 전에 중단됩니다

크래시, 정상 종료 중단, worker pause 또는 블록 중간 오류가 발생할 수 있습니다. 개별 삭제는 이미 commit되었지만 블록 완료는 기록되지 않았습니다.

vacuum이 같은 블록과 같은 undo image를 다시 읽습니다

재시작된 vacuum은 start_lsa부터 블록을 다시 처리합니다. WAL의 undo image는 수정되지 않으므로 여전히 옛 주소 A를 돌려줍니다.

현재 probe가 R2의 살아있는 청크를 “삭제 대상 있음”으로 판정합니다

oos_chunk_exists(A)는 슬롯에 레코드가 있는지만 확인합니다. R1 것인지 R2 것인지 확인할 필드가 없으므로 true를 반환하고, oos_delete(A)는 현재 점유자인 R2의 chain을 삭제합니다. 이 두 번째 삭제도 새 sysop과 새 WAL 로그를 가진 정상 연산으로 commit됩니다.
핵심 구분: 같은 데이터를 두 번 지우는 “중복 삭제”라면 두 번째에는 슬롯이 비어 있어 no-op으로 끝납니다. 이 결함은 첫 삭제와 두 번째 삭제 사이에 슬롯의 주인이 바뀐 경우입니다. 두 번째 삭제는 같은 주소에 있는 다른 데이터를 지웁니다.

4. 왜 조건이 갖춰지면 오삭제는 반드시 일어나는가

정확한 표현이 중요합니다. 모든 운영 환경에서 일정 시간 안에 이 사고가 무조건 발생한다는 뜻은 아닙니다. 운영 패턴별 발생 빈도는 아직 측정하지 않았습니다. 그러나 아래 A–G가 한 번 같은 순서로 성립하면, 현재 코드에는 마지막 오삭제를 피할 분기가 없으므로 결과는 결정적입니다.

4.1 논리식으로 본 필연성

A. 1차 OOS 삭제가 독립 sysop으로 commit됨 + B. vacuum 블록 완료 위치는 아직 기록되지 않음 + C. 삭제한 슬롯을 다른 insert가 재사용함 + D. 같은 블록을 start_lsa부터 재처리함 + E. 불변 undo image가 같은 옛 OID를 다시 제공함 + F. probe가 “현재 점유자의 신원”이 아니라 “슬롯 점유 여부”만 검사함 + G. oos_delete가 그 주소의 현재 점유자를 삭제함 ──────────────────────────────────────────────────────────── = 살아있는 새 점유자의 데이터 삭제

A부터 G까지 어느 하나라도 불가능하다는 시스템 불변식이 있으면 사고는 막힙니다. 현재 소스 검증에서는 그런 불변식을 찾지 못했으며, 오히려 각 단계가 기존 설계의 정상 동작으로 확인되었습니다.

4.2 A–G가 실제로 도달 가능한 이유

증명 의무현재 동작왜 다음 단계로 이어지는가판정
A · 삭제 commitforward-walk의 OOS 삭제는 레코드별 독립 sysop입니다.블록이 끝나지 않아도 이미 지운 chain은 복구 시 되살아나지 않습니다.확인
B · 진행 미기록개별 레코드 완료 위치를 영속 저장하지 않고, 블록 완료 전에는 start_lsa가 그대로입니다.중단 뒤 이미 처리한 로그 레코드도 다시 만납니다.확인
C · 재사용 창삭제된 슬롯을 보호하는 장기 잠금이나 격리 기간이 없습니다.다른 트랜잭션의 insert가 중간에 들어올 수 있습니다.확인
D · 동일 slotidANCHORED 페이지는 삭제된 slotid를 재사용하며, bestspace가 빈 공간을 다시 insert에 제공합니다.새 청크가 정확히 같은 (V,P,S)를 받을 수 있습니다.확인
E · 옛 참조 반복undo image는 append-only WAL에 있는 과거 기록입니다.슬롯 주인이 바뀌어도 undo image 속 OID는 바뀌지 않습니다.확인
F · 신원 미검사청크 헤더에는 length, index, next OID만 있고 owner·generation이 없습니다.probe는 R1과 R2를 구분할 정보 자체가 없습니다.차단 없음
G · 현재 체인 삭제oos_delete는 현재 슬롯 헤더를 읽고 그 next OID를 따라갑니다.R2가 멀티청크면 R2의 현재 chain 전체로 피해가 확대됩니다.확인

4.3 “희귀할 수 있다”와 “안전하다”는 같은 말이 아닙니다

현재 단계에서 정직하게 말할 수 있는 범위는 다음과 같습니다.

아직 모르는 것

  • 실제 고객 운영 패턴에서 시간당 발생 확률
  • 크래시 없이 중간 오류만으로 발현되는 빈도
  • 특정 페이지에 insert가 집중되는 정도

이미 아는 것

  • 각 단계는 코드상 도달 가능합니다.
  • 슬롯 재사용은 금지되지 않고 오히려 공간 정책이 촉진합니다.
  • 조건 충족 후 신원 오판과 삭제는 결정적입니다.
  • 결과가 silent data loss라 사후 발견·복구가 어렵습니다.

장시간 운영에서는 UPDATE·vacuum·OOS insert·worker 재시작의 기회가 반복됩니다. 개별 사건의 확률이 작아도 시도 횟수가 누적되면 전체 위험은 커집니다. 다만 실제 확률을 측정하지 않았으므로 이 보고서는 수치를 만들어 내지 않습니다. 승인 근거는 “높은 확률”이 아니라 도달 가능한 실행 순서 + 차단 불변식 부재 + 데이터 손실 결과입니다.

5. sysop·WAL·page LSA·latch가 왜 막지 못하는가

5.1 sysop은 “정확히 한 번”이 아니라 “한 번 호출의 원자성”을 보장합니다

sysop은 한 번의 oos_delete가 여러 청크를 지우다가 실패했을 때, 전부 지우거나 전부 되돌리게 합니다. 그러나 sysop은 바깥의 vacuum 블록이 같은 삭제 요청을 다시 만들지 못하게 하지 않습니다.

질문sysop이 보장sysop이 보장하지 않음
한 체인을 반만 지울 수 있는가?아니오. 한 호출은 원자적입니다.—
이미 commit된 요청이 다시 호출되는가?—막지 않습니다.
같은 OID의 현재 점유자가 옛 점유자인가?—확인하지 않습니다.
두 번째 호출 내용이 논리적으로 올바른가?—호출자가 올바른 대상을 넘겨야 합니다.
은행 이체에 비유하면, sysop은 “A 계좌에서 빼고 B 계좌에 더하는 두 단계가 함께 성공한다”를 보장합니다. 같은 이체 요청을 다음 날 다시 실행해도 되는지는 별도의 요청 번호, 즉 멱등성 키가 판단해야 합니다. generation이 OOS 삭제의 멱등성 키 역할을 합니다.

5.2 WAL과 page LSA는 잘못된 새 삭제까지 성실하게 보존합니다

page LSA는 복구 중 같은 redo 로그를 같은 페이지에 두 번 적용하지 않게 합니다. 하지만 사고의 두 번째 삭제는 옛 redo의 반복 적용이 아닙니다. 복구가 끝난 뒤 vacuum 코드가 undo image를 다시 읽고 실행하는 새로운 삭제 연산입니다. 새 WAL 로그도 정상적으로 생성됩니다.

복구 redo의 중복 적용 같은 로그 L을 다시 적용하려 함 → page LSA 비교 → 이미 적용했으면 건너뜀 CBRD-26950의 두 번째 삭제 vacuum이 옛 undo image를 다시 읽음 → 새 oos_delete 호출 → 새 로그 L2 생성 → page LSA 관점에서는 처음 보는 정상 로그 → 적용하고 영속화

따라서 WAL은 데이터 손실의 원인이 아니라, 잘못 선택된 대상을 일관되게 삭제하고 그 결과를 복구 가능하게 만드는 장치가 됩니다. “복구가 정확하다”와 “업무 의미가 정확하다”는 서로 다른 문제입니다.

5.3 latch는 현재 접근만 직렬화하며 과거 참조까지 보호하지 않습니다

page latch는 한 시점에 같은 페이지를 동시에 수정하여 구조가 깨지는 것을 막습니다. 첫 삭제, R2 insert, 두 번째 삭제가 순서대로 각각 올바른 latch를 잡아 실행하면 물리 구조는 완전히 정상입니다. latch가 해제된 뒤까지 옛 OID의 의미를 보존해 주지는 않습니다.

5.4 MVCC 임계값은 R1의 옛 버전이 죽었다는 것만 증명합니다

vacuum이 R1의 옛 버전을 지워도 된다는 판단은 맞습니다. 문제는 그 판단에서 얻은 옛 물리 주소 A가 시간이 지난 뒤에도 여전히 R1의 청크인지입니다. R2의 새 청크는 별도 행·별도 버전이므로 R1의 MVCC 판단으로 보호할 수 없습니다.

6. heap도 OID를 재사용하는데 왜 같은 사고를 피할 수 있는가

heap 슬롯도 삭제 뒤 재사용될 수 있습니다. 차이는 vacuum이 물리 삭제 직전에 현재 heap record를 다시 읽고 그 안의 MVCC header를 확인할 수 있다는 점입니다. 주소만 같고 MVCC 신원이 다르면 “내가 지울 옛 버전이 아니다”라고 판단할 근거가 있습니다.

비교 항목heap record현재 OOS chunk record

OOS 청크에 heap의 전체 MVCC header를 복사하자는 뜻은 아닙니다. OOS 삭제에 필요한 질문은 “이 주소의 현재 청크가 옛 참조가 가리킨 바로 그 세대인가?” 하나입니다. generation은 그 질문에만 답하는 최소한의 신원 정보입니다.

“5번 슬롯의 41번째 점유자”를 가리킵니다. 같은 주소의 42번째 점유자와 구분됩니다.

7.2 숫자로 보는 삭제 판정

R1 생성 시 inline stub: { OID=A, length=5000, generation=41 } chunk header: { ..., generation=41 } R1의 옛 chain 삭제 후 R2가 같은 A를 재사용 R2 chunk: { ..., generation=42 } 옛 undo stub: { OID=A, length=5000, generation=41 } ← 불변 vacuum 재처리 시 expected generation = 41 current generation = 42 41 != 42 → 슬롯이 재사용됨 → 삭제하지 않고 성공 no-op

이 비교는 첫 삭제가 아직 필요할 때는 방해하지 않습니다. 현재 청크가 정말 R1의 것이라면 두 값이 41로 같아 정상 삭제합니다. 이미 슬롯이 비었다면 기존처럼 no-op이고, 새 청크가 들어왔다면 generation 불일치로 no-op입니다.

7.3 generation은 어디서 만들고 어디에 저장하는가

  1. OOS 페이지 헤더에 uint32 generation counter를 둡니다.
  2. 청크를 insert할 때 이미 해당 페이지의 write latch를 잡은 상태에서 counter를 증가시킵니다.
  3. 발급된 값을 OOS chunk header에 저장합니다.
  4. head 청크의 generation을 heap record의 inline stub에도 저장합니다.
  5. UPDATE undo image는 inline stub을 그대로 보존하므로 옛 generation도 자동으로 보존됩니다.
  6. vacuum은 head 삭제 진입 전에 expected generation과 current generation을 비교합니다.
필수 원자성 조건: generation을 별도 probe에서 확인한 뒤 latch를 놓고 나중에 삭제하면 안 됩니다. 확인과 삭제 사이에 슬롯이 다시 바뀌는 TOCTOU(Time Of Check To Time Of Use, “검사한 때와 사용한 때가 다른” 경쟁 조건)가 생길 수 있습니다. head 청크의 generation 비교와 실제 head 삭제 진입은 같은 page write-latch 구간, 같은 삭제 연산 안에서 수행되어야 합니다. 즉, API의 의미도 단순한 exists가 아니라 delete_if_generation_matches여야 합니다.
이 설계는 vacuum의 블록 재시도 정책, undo image 활용, 레코드 단위 sysop을 그대로 유지합니다. 고장 난 것은 재처리 자체가 아니라 재처리 때 대상의 신원을 확인할 방법이 없다는 점이므로, 확인 정보를 추가하는 것이 가장 국소적인 수정입니다.

7.4 이 문제는 전형적인 ABA 문제입니다

동시성 분야에서는 “처음 읽은 주소가 A였고, 중간에 없어졌다가 다른 객체가 같은 A를 차지했는데, 나중에 주소만 보고 처음과 같다고 오인하는 문제”를 ABA 문제라고 부릅니다. 현재 vacuum은 옛 OID A를 보관했다가 나중에도 A가 점유되어 있다는 이유로 같은 청크라고 오인합니다. 주소에 generation을 붙이는 tagged reference는 ABA를 막는 일반적인 방법입니다. 이 설계는 OOS만의 임시 예외가 아니라 알려진 문제에 맞는 표준적인 해법입니다.

7.5 왜 32비트면 충분한가

32비트 부호 없는 정수는 0부터 2^32-1, 즉 약 42억 9천만 개의 값을 가집니다. 옛 참조의 generation과 재사용된 새 청크의 generation이 우연히 다시 같아지려면, 그 옛 참조가 vacuum 재처리 대상으로 남아 있는 짧은 구간 동안 같은 페이지 counter가 한 바퀴를 모두 돌아야 합니다. 이는 같은 페이지에 약 43억 번의 청크 insert가 필요하다는 뜻입니다.

따라서 uint32는 무한히 충돌하지 않는 값은 아니지만, 이 결함의 재처리 시간 창에 대해 충분한 폭으로 판단합니다. 단, 이 계산은 generation namespace가 crash나 페이지 재할당 때문에 조기에 0으로 초기화되지 않는다는 전제가 필요합니다.

7.6 page-local counter가 지켜야 할 수명 규칙

현재 vacuum은 빈 OOS 페이지 안의 청크 슬롯만 지우며, 페이지 자체를 해제하지는 않습니다. 이 범위에서는 페이지 헤더 counter가 계속 남습니다. 그러나 후속 기능에서 빈 OOS 페이지를 해제하고 같은 VPID를 새 OOS 페이지로 재사용하면, counter를 작은 값으로 초기화하는 순간 (OID, generation) 쌍이 232번을 기다리지 않고 다시 나타날 수 있습니다.

따라서 구현 계약에는 다음 중 하나와 동등한 보장이 필요합니다: 페이지 재할당 뒤에도 이전 generation namespace와 겹치지 않는 seed/epoch를 사용하거나, 파일 수준의 영속 high-water mark에서 발급하거나, 옛 참조가 존재할 수 있는 동안 동일 VPID의 generation을 초기화하지 않습니다. 정확한 발급 위치는 구현 설계에서 선택할 수 있지만, 페이지 수명보다 짧은 counter 초기화는 허용할 수 없습니다. 이 조건은 향후 OOS 빈 페이지 회수 기능의 선행 조건입니다.

8. 수용해야 할 실제 비용과 그 크기

“참조에 4바이트 추가”가 전체 비용의 전부는 아닙니다. 의사결정에 필요한 비용을 숨기지 않고 세 부분으로 나누면 다음과 같습니다.

heap record stub마다 +4B OOS-backed attribute 하나마다 16B stub이 20B가 됩니다.
OOS file 청크마다 +4B oos_record_header가 16B에서 20B로 늘어납니다.
OOS page 페이지마다 +4B generation 발급용 uint32 counter가 한 번 추가됩니다.

8.1 heap record 비용 예시

한 행의 OOS-backed attribute 수현재 stub 합계제안 stub 합계추가 비용4,060B target 대비
1개16B20B+4B약 0.10%
4개64B80B+16B약 0.39%
10개160B200B+40B약 0.99%

여기서 4,060바이트는 현재 16KB I/O 페이지 구조에서 계산되는 PG-style four-record heap target입니다. stub이 20바이트가 되면 OOS로 내보내어 실제로 행 크기를 줄일 수 있는 값의 기준도 >16B에서 >20B로 함께 바뀌어야 합니다.

8.2 한 OOS 값의 총 추가 비용 공식

한 OOS-backed attribute의 추가 비용 = heap inline stub 4B + (그 값을 구성하는 chunk 수 × 4B) + page counter 비용의 분담분 예: 한 청크로 저장되는 값 1개 = heap 4B + OOS chunk 4B + page counter 분담분 예: 세 청크로 저장되는 값 1개 = heap 4B + OOS chunks 12B + page counter 분담분

큰 청크 하나의 4바이트는 16KB 페이지 규모와 비교하면 약 0.025%입니다. 실제 데이터베이스 전체 추가 비율은 OOS-backed attribute 수, 값별 청크 수, 페이지 채움 정도에 따라 달라지므로 하나의 고정 백분율로 말할 수 없습니다. 다만 OOS는 원래 큰 값을 대상으로 하므로 청크 payload에 대한 4바이트 비율은 작고, 위 공식으로 운영 패턴별 상한을 계산할 수 있습니다.

8.3 왜 8바이트 length를 줄여 공간을 만들면 안 되는가

현재 stub의 full length는 8바이트 DB_BIGINT입니다. 향후 RECDES.length도 64비트로 확장할 계획이므로, length를 4바이트로 줄이고 남은 4바이트에 generation을 넣는 방식은 미래의 큰 레코드 표현 범위를 스스로 막습니다.

length 상위 비트를 generation으로 겹쳐 쓰는 방법도 채택하면 안 됩니다. 한 필드에 크기와 신원이라는 서로 다른 의미를 섞으면 최대 길이, 부호 처리, 직렬화, 복구, 호환성 해석이 모두 결합됩니다. 64비트 length 요구를 온전히 보존하려면 generation은 독립 4바이트여야 합니다.

8.4 왜 20바이트이고 24바이트가 아닌가

단순한 8바이트 정렬을 위해 4바이트 padding을 추가하면 OOS-backed attribute마다 비용이 다시 늘어납니다. variable area 안의 stub 시작 오프셋 자체가 항상 8바이트 경계라는 보장이 없으므로, 전체 크기를 24바이트로 만든다고 내부 필드 정렬까지 보장되는 것도 아닙니다. 따라서 포맷은 20바이트로 유지하고 reader가 기존 방식대로 안전하게 값을 읽어야 합니다.

11. 팀장 검토 예상 질문과 답변

Q1. 이 문제가 정말 “반드시” 발생합니까?

모든 서버에서 기한 내 반드시 발생한다고 주장하지 않습니다. 정확한 주장은 A–G 실행 순서가 성립하면 현재 코드상 반드시 R2가 삭제된다는 것입니다. 각 단계는 정상 정책에서 도달 가능하고, 이를 금지하는 불변식이 없습니다. 발생률 수치가 필요한 경우 별도 장기 stress·fault-injection 측정이 필요하지만, silent data loss를 수정할지 여부는 그 측정 전에도 판단할 수 있습니다.

Q2. 슬롯이 정확히 같은 slotid로 그렇게 빨리 재사용됩니까?

가능합니다. OOS 페이지는 ANCHORED이며 삭제된 slotid를 재사용합니다. 삭제 뒤 페이지는 bestspace 후보로 다시 들어가고 insert는 빈 공간을 우선 활용합니다. OID에는 별도 “재발급” 절차가 없습니다. 같은 물리 슬롯을 다시 채우는 순간 같은 OID가 재등장합니다. 재사용이 느리다는 불변식도, vacuum 블록 완료까지 막는 격리도 없습니다.

Q3. 왜 vacuum은 이미 처리한 레코드 다음부터 재개하지 않습니까?

현재 진행 관리 단위가 개별 로그 레코드가 아니라 블록이기 때문입니다. 블록을 모두 끝내기 전에는 start_lsa를 세밀하게 전진시킨 영속 기록이 없습니다. 이 방식은 중단 시 누락을 피하기 위해 블록을 다시 읽는 보수적인 설계입니다. 이를 바꾸려면 각 삭제 sysop과 진행 포인터를 원자적으로 결합하는 vacuum 핵심 상태 변경이 필요합니다.

Q4. OOS multi-chunk 삭제가 이미 sysop인데 왜 충분하지 않습니까?

sysop은 한 번 호출된 chain 삭제의 all-or-nothing만 보장합니다. 첫 호출은 R1을 정확히 지우고 commit됩니다. 두 번째 호출은 R2를 대상으로 하는 별개의 새 연산이며, 그것도 원자적으로 정확히 commit됩니다. 두 호출 사이의 대상 동일성을 확인하는 것이 generation의 책임입니다.

Q5. 블록 전체를 sysop으로 묶으면 4바이트를 피할 수 있지 않습니까?

블록 sysop commit과 블록 완료 상태 영속화가 하나의 원자적 사건이 아니면 여전히 재처리 창이 남습니다. 또한 vacuum 블록은 많은 레코드와 페이지를 포함하므로 sysop이 매우 길어지고 로그·undo·페이지 노출 문제를 키웁니다. 대상 신원 부재를 해결하지 않고 실행 단위만 크게 만드는 방법입니다.

Q6. page LSA나 recovery가 두 번째 삭제를 막아야 하지 않습니까?

두 번째 삭제는 같은 redo의 재적용이 아니라 복구 후 vacuum이 만드는 새 로그 연산입니다. page LSA는 이를 정상적인 새 변경으로 봅니다. recovery는 로그 순서를 정확히 복원하지만, OID의 과거 소유자와 현재 소유자가 같은지는 알지 못합니다.

Q7. heap도 재부팅 뒤 옛 OID를 다시 지울 수 있지 않습니까?

heap vacuum은 현재 record의 MVCC header를 다시 읽어 대상 버전인지 확인할 수 있습니다. 슬롯 주소는 같아도 현재 신원이 다르면 삭제하지 않을 근거가 있습니다. OOS 청크에는 그에 해당하는 최소 신원 필드가 없어 주소 점유만 확인하는 것이 차이입니다.

Q8. OOS에 전체 MVCC header를 넣는 편이 더 일관적이지 않습니까?

전체 MVCC는 insert ID, delete ID, 이전 버전 연결, visibility 규칙과 vacuum 관리까지 요구합니다. OOS chain은 각 heap-record version이 단독 소유하고 공유하지 않으므로, 이 문제에 필요한 것은 visibility 판단이 아니라 슬롯 incarnation 판단 하나입니다. 4바이트 generation이 더 작은 계약입니다.

Q9. 값의 length까지 비교하면 충분하지 않습니까?

충분하지 않습니다. R1과 R2가 모두 5,000바이트이면 OID와 length가 모두 같습니다. 공격적 입력이 아니어도 컬럼 크기가 일정한 운영 패턴에서는 같은 길이가 흔합니다. 길이는 내용의 크기이지 점유자의 신원이 아닙니다.

Q10. generation도 232번 뒤에는 충돌하는데 완전한 해결입니까?

수학적으로 무한한 고유값은 아닙니다. 다만 위험한 옛 참조가 남아 있는 한 번의 vacuum 재처리 창 안에 같은 페이지가 약 43억 번의 청크 insert를 해야 wrap 충돌이 가능합니다. 이 시간 경계에서 uint32를 충분한 공학적 폭으로 선택한 것입니다. 구현에는 wrap 경계 테스트와 규칙을 포함해야 합니다.

Q11. 참조만 4바이트 늘리면 됩니까?

아닙니다. 비교하려면 inline stub의 expected generation과 현재 OOS chunk header의 generation이 모두 필요합니다. 페이지 counter도 필요합니다. 따라서 정확한 비용은 stub당 +4B, 청크당 +4B, 페이지당 +4B입니다. 이 보고서는 세 비용을 모두 승인 범위에 포함합니다.

Q12. 왜 출시 전에 지금 결정해야 합니까?

OOS는 아직 미출시 feature이므로 지금 포맷을 바꾸면 기존 고객 OOS 파일을 변환할 필요가 없습니다. 출시 뒤 16B와 20B 포맷을 바꾸면 버전 판별, backup/restore 호환, rolling upgrade, 마이그레이션 정책이 추가됩니다. 지금의 명시적 4바이트 비용보다 출시 후 포맷 전환 비용이 훨씬 커집니다.

Q13. generation을 먼저 검사하고 기존 oos_delete를 호출하면 충분합니까?

검사와 삭제가 서로 다른 latch 구간이면 충분하지 않습니다. 검사 직후 슬롯이 바뀌는 TOCTOU 경쟁이 남습니다. generation 비교는 head를 실제 삭제하는 연산 안에 들어가야 하며, 비교가 끝난 때부터 head 삭제가 결정될 때까지 같은 page write latch가 유지되어야 합니다.

Q14. inline stub에만 generation을 넣거나, 청크 헤더에만 넣으면 안 됩니까?

두 곳 모두 필요합니다. inline stub은 vacuum이 기대하는 “옛 점유자의 번호”를 undo image까지 전달하고, 청크 헤더는 “현재 점유자의 번호”를 제공합니다. 한쪽만 있으면 비교의 두 피연산자 중 하나가 없어 신원 일치를 판정할 수 없습니다.

Q15. 빈 OOS 페이지가 해제되었다가 같은 pageid로 재할당되면 counter가 초기화되지 않습니까?

현재 vacuum 경로는 청크만 삭제하고 페이지 자체는 해제하지 않으므로 당장 그 초기화는 없습니다. 하지만 향후 빈 페이지 회수를 구현할 때는 반드시 해결해야 합니다. 같은 VPID에서 counter가 작은 값으로 초기화되면 32비트 wrap 안전성 설명이 무효가 됩니다. 따라서 페이지 재할당에도 겹치지 않는 seed/epoch 또는 파일 수준 high-water mark 같은 generation namespace 보존 규칙을 페이지 회수의 선행 조건으로 둡니다.

Q16. JIRA Priority가 Minor인데 왜 저장 포맷까지 바꿔야 합니까?

JIRA Priority는 현재 일정·분류 메타데이터이며 안전성 증명이 아닙니다. 이 보고서는 priority를 임의로 변경하지 않고 Minor라고 정확히 기록합니다. 별도로 기술 영향은 살아있는 데이터의 무증상 삭제이고, 이를 막는 불변식이 없다는 사실을 평가합니다. 특히 미출시 기능은 고객 노출 전에 포맷을 바로잡을 수 있으므로, 현재 priority만으로 데이터 정확성 문제를 수용하는 것은 타당하지 않습니다.

Q17. 기존 테스트가 모두 통과했다면 이 실행 순서가 현실적으로 불가능한 것 아닙니까?

아닙니다. 일반 SQL 테스트는 “1차 삭제 sysop commit 직후 worker 정지”와 “그 사이 정확한 슬롯 재사용”을 결정적으로 고정하지 못합니다. 테스트가 이 순서를 만들지 않았다는 사실은 차단 불변식이 있다는 증거가 아닙니다. 이 때문에 수정 검증에는 시간 순서를 통제하는 fault-injection이 필요합니다.

Q18. inline stub은 head만 가리키는데 왜 모든 청크 헤더가 4바이트 늘어납니까?

현재 oos_record_header는 head와 non-head가 같은 고정 포맷을 사용합니다. head 여부에 따라 서로 다른 헤더를 만들면 파싱·복구·검증 분기가 늘고, 각 물리 청크가 재사용될 때의 신원도 표현하지 못합니다. 삭제 진입을 막는 데 가장 중요한 비교는 head generation이지만, 공통 청크 포맷의 자기 식별성과 향후 chain 무결성 검증을 위해 청크마다 같은 필드를 두는 비용을 명시적으로 계산했습니다.

12. 최종 승인 요청

다음 항목을 하나의 설계 묶음으로 승인해 주시기를 요청합니다.

  1. OOS inline stub에 generation 4바이트를 추가합니다: 16B → 20B.
  2. OOS chunk header에 generation 4바이트를 추가합니다: 16B → 20B.
  3. OOS 페이지에 generation 발급용 uint32 counter를 추가합니다: 페이지당 +4B. crash·wrap·페이지 재할당에도 namespace가 조기 재사용되지 않게 합니다.
  4. vacuum 삭제는 같은 write-latch 구간에서 OID 점유 여부와 generation 일치를 확인하고, 불일치는 성공적인 no-op으로 처리합니다.
  5. 향후 64비트 RECDES.length 확장을 위해 full length 8바이트는 그대로 유지합니다.
  6. OR_OOS_INLINE_SIZE와 수익성 경계를 20바이트 기준으로 갱신합니다.
  7. fault-injection으로 “1차 삭제 commit → 슬롯 재사용 → 블록 재처리”를 고정한 단일·멀티청크 회귀 테스트를 merge gate로 둡니다.
  8. 미출시 OOS 포맷에 호환성 부채가 생기기 전, feat/oos 머지·출시 전에 반영합니다.

이 결정은 “4바이트와 0바이트”의 비교가 아닙니다. 지금 지불하는 작고 계산 가능한 저장 비용과 출시 뒤 발생할 수 있는 무증상 데이터 손실 및 포맷 마이그레이션 비용의 비교입니다. 현재 구조에서는 주소만으로 지연 삭제의 안전성을 증명할 수 없으므로, generation 비용을 수용하는 것이 타당합니다.
