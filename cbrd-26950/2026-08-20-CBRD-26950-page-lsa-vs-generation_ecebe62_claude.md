## 한 줄 요약

vacuum 이 "이 저장 공간, 지워도 되나?"를 확인할 때 쓸 **신분증**이 필요하다. 현재 PR 은 신분증을 **새로 만든 일련번호 (generation counter)** 로 발급하는데, 리뷰어가 "**이미 모든 페이지에 있는 타임스탬프 (page LSA)** 를 쓰면 관리 장치가 통째로 사라진다"고 제안했다. 검증 결과 제안이 옳다 — **page LSA 로 전환한다.**

## 장 1. 배경 ① — 레코드의 주소는 "아파트 호수"다

데이터베이스는 데이터를 **페이지** (CUBRID 는 16KB) 단위로 디스크에 저장한다. 한 페이지 안에는 여러 개의 레코드가 들어가는데, CUBRID 는 이를 **slotted page** 구조로 관리한다:

```
┌────────────────────────── 페이지 (16KB) ──────────────────────────┐
│ 페이지 헤더 │ 슬롯 0 │ 슬롯 1 │ 슬롯 2 │ ...        ...  │ 레코드들 │
│  (LSA 등)   │  ───────── 슬롯 디렉토리 ─────────→   ←──── 데이터 ──│
└────────────────────────────────────────────────────────────────────┘
   슬롯 N = "이 페이지의 N 번째 레코드는 저기 있음" 을 가리키는 엔트리
```

그래서 레코드 하나의 주소는 **(볼륨 번호, 페이지 번호, 슬롯 번호)** 세 값으로 표현된다. CUBRID 에서 이걸 **OID** 라고 부른다.

여기서 이 문서 전체를 관통하는 사실 하나:

> **OID 는 물리 주소다. 아파트 호수와 같다.** 레코드가 삭제되면 그 슬롯은 비고, 나중에 **다른 레코드가 같은 슬롯을 재사용**할 수 있다. 즉 "101동 503호"라는 주소만으로는 *지금 거기 사는 사람이 내가 알던 그 사람인지* 알 수 없다.

이 "슬롯 재사용" 이 이번 버그의 뿌리다.

## 장 2. 배경 ② — OOS: 큰 값은 행 밖에 저장한다

테이블에 이런 행이 있다고 하자:

```sql
CREATE TABLE t (id INT, name VARCHAR(20), big_text ..., big_blob ...);
-- big_text 4.5KB, big_blob 4.5KB
```

이 행 전체는 약 9KB 다. 그런데 쿼리 대부분이 `SELECT id, name FROM t` 처럼 작은 컬럼만 읽는다면? 4바이트 `id` 를 읽으려고 매번 9KB 를 통째로 읽는 건 낭비다.

**OOS (Out-of-row Overflow Storage)** 는 이 낭비를 없앤다. 큰 가변 길이 값을 행 밖의 **OOS 파일**로 옮기고, 행에는 16바이트짜리 참조만 남긴다:

```
AS-IS:  [ id │ name │ big_text (4.5KB) │ big_blob (4.5KB) ]   ← 행이 ~9KB

TO-BE:  [ id │ name │ stub (16B) │ stub (16B) ]               ← 행이 아주 작아짐
                        │             │
                        ▼             ▼
                 [ big_text ]   [ big_blob ]                   ← OOS 파일 (별도 페이지들)
```

이 16바이트 참조를 **OOS inline stub** 이라고 부르고, 내용은:

- **head OOS OID (8B)** — 값이 저장된 첫 OOS 청크 레코드의 물리 주소 (장 1 의 그 OID!)
- **전체 길이 (8B)**

값이 한 페이지보다 크면 여러 개의 **청크 레코드**로 쪼개져 연결 리스트 (**OOS 값 체인**) 로 저장되고, stub 은 체인의 머리만 가리킨다.

핵심: **stub 안의 OOS OID 도 물리 주소, 즉 아파트 호수다.** 슬롯 재사용 문제를 그대로 물려받는다.

## 장 3. 배경 ③ — MVCC 와 vacuum: 옛 버전은 나중에 청소한다

CUBRID 는 **MVCC** (다중 버전 동시성 제어) 를 쓴다. `UPDATE` 가 값을 제자리에서 덮어쓰지 않고, **이전 버전을 undo 로그에 보존**한다. 이유: 먼저 시작한 다른 트랜잭션은 아직 *옛 값*을 읽을 권리가 있기 때문이다.

OOS 도 마찬가지다. OOS 컬럼을 UPDATE 하면 새 값은 새 OOS 체인으로 저장되고, **옛 체인은 바로 지우지 않는다** — 옛 버전을 읽는 트랜잭션이 undo 로그의 옛 stub 을 따라 옛 체인을 읽어야 하니까.

그럼 옛 체인은 누가 언제 지우나? **vacuum** 이다. vacuum 은 "이 버전은 이제 아무도 안 본다"가 확정된 옛 버전들을 백그라운드에서 청소하는 청소부다. OOS 옛 체인도 이때 함께 회수한다.

vacuum 동작에서 이번 버그와 직결되는 특성 하나:

> vacuum 은 로그를 **블록 단위**로 처리하고, "여기까지 했음"이라는 진행 기록도 **블록 단위로만** 남긴다. 블록 처리 도중 서버가 죽거나 worker 가 중단되면, **그 블록을 처음부터 다시 돌린다.** 즉 *같은 삭제 작업이 두 번 시도될 수 있다.* (이를 "블록 재시도"라 부르겠다)

두 번 지우는 게 뭐가 문제냐 — "이미 지웠으면 그냥 없을 텐데"? 장 5 에서 보겠지만, **그 사이에 다른 데이터가 이사를 들어오면** 문제가 된다.

## 장 4. 배경 ④ — WAL 과 LSA: 모든 페이지에는 이미 타임스탬프가 있다

데이터베이스는 크래시 후에도 데이터가 깨지지 않아야 한다. 이를 위한 표준 기법이 **WAL (Write-Ahead Logging)**:

> 페이지를 고치기 전에, "무엇을 고치는지"를 먼저 **로그**에 기록한다.

로그는 추가 전용 (append-only) 파일이고, 로그 레코드 하나하나는 자기 위치 주소를 갖는다. 이 주소가 **LSA (Log Sequence Address)** 다. 로그는 뒤에만 붙으므로 **LSA 는 시간처럼 단조 증가한다.**

크래시 후 복구는 로그를 다시 재생한다:

- **redo**: "이 변경, 디스크에 반영 안 됐으면 다시 적용"
- **undo**: "커밋 못 한 트랜잭션의 변경은 되돌리기"

그런데 redo 를 하려면 "이 페이지에 이 로그가 이미 적용됐었나?"를 알아야 한다. 그래서 **모든 페이지의 헤더에는 page LSA 가 있다**: *이 페이지에 마지막으로 적용된 로그 레코드의 LSA*. 페이지를 고치는 모든 로깅된 연산이 이 값을 갱신한다.

이 문서에서 기억할 성질 세 가지:

1. page LSA 는 엔진이 **이미** 모든 페이지에 유지하는 값이다 — 새로 만들 필요가 없다.
2. 로그가 추가 전용이므로 page LSA 는 **절대 뒤로 가지 않는다.**
3. 이 값의 유지·복구는 **복구 기계 자체의 일**이다 — 우리가 관리 코드를 쓸 필요가 없다.

레코드 안에 LSA 를 담아두는 선례도 이미 있다: MVCC 헤더의 `prev_version_lsa` (옛 버전을 찾아가는 포인터).

## 장 5. 버그 — 청소부가 새 입주자의 집을 철거한다 (CBRD-26950)

이제 재료가 다 모였다. 버그 시나리오:

```
T1  vacuum: 옛 버전의 undo 이미지에서 stub 을 읽음 → "OOS (1|50|3) 지워라"
    → 체인 삭제, 슬롯 (1|50|3) 이 빈다
T2  다른 행의 INSERT 가 OOS 값을 저장하는데, 마침 빈 슬롯 (1|50|3) 을 재사용
    → 새 입주자의 살아있는 데이터가 그 주소에 들어감
T3  vacuum worker 가 중단됨 → 블록 재시도 (장 3)
    → 같은 undo 이미지에서 같은 주소 (1|50|3) 을 다시 도출
T4  oos_delete (1|50|3) 실행 → 이번엔 "새 입주자의 살아있는 체인"이 삭제됨
    → 조용한 데이터 손실. 에러도 경고도 없다.
```

아파트 비유로: 철거 명령서에 "101동 503호"라고만 적혀 있다. 첫 철거 후 새 입주자가 들어왔는데, 분실됐다 재발견된 같은 명령서로 **새 입주자의 집을 철거**해 버린 것이다.

기존 코드에 방어가 하나 있긴 했다 — `oos_chunk_exists`: "그 슬롯에 뭔가 있나?" 확인. 하지만 이 질문은 T4 에서 **오히려 삭제를 통과시킨다**. 슬롯엔 (새 입주자가) 분명히 있으니까. 필요한 질문은 "누가 살고 있나?"가 아니라 "**내가 알던 그 사람인가?**"다.

체인이 여러 청크면 피해가 증폭된다: 삭제는 각 청크의 `next_chunk_oid` 를 따라가므로 새 입주자의 **체인 전체**가 증발한다.

## 장 6. 현재 PR 의 해법 — 신분증 (generation counter) 발급

아이디어는 자연스럽다: **입주할 때마다 신분증 번호를 발급하고, 철거 명령서에도 번호를 적고, 철거 전에 대조하자.**

현재 PR 의 구현:

1. 모든 OOS 데이터 페이지의 **슬롯 0 에 특별한 헤더 레코드**를 만들고, 그 안에 `generation_counter` 를 둔다.
2. 청크를 삽입할 때 counter 에서 새 generation 을 발급해서 **청크 헤더** (+4B) 와 **stub** (16B → 20B) 양쪽에 기록한다.
3. `oos_delete (주소, expected_generation)` — 삭제 전에 현재 입주자의 generation 과 대조. **불일치 (재사용됨) 또는 부재 (이미 철거됨) 면 아무것도 안 하고 성공 반환 (no-op).**

장 5 의 T4 를 다시 보면: 새 입주자의 generation 은 다른 값이므로 대조 실패 → 재시도 삭제는 무해한 no-op. 버그가 막힌다. ✅

여기까지는 좋다. **이 "대조 후 no-op" 계약 자체는 이 문서의 쟁점이 아니다 — 쟁점은 신분증 번호를 어디서 얻느냐다.**

## 장 7. 문제 — counter 는 "없던 상태"라서 유지비가 든다

counter 는 세상에 없던 상태를 새로 만든 것이다. 상태를 만들면 그 상태의 **생애 전체** — 어디 살지, 크래시에서 어떻게 살아남을지, 넘치면 어떡할지, 리셋되면 어떡할지 — 를 전부 우리가 관리해야 한다. 현재 PR 에 실제로 들어있는 관리 장치 다섯 가지를 보자.

### 7.1 살 집: 슬롯 0 헤더 레코드

counter 값은 크래시에도 살아남아야 하니 페이지 위 어딘가 저장돼야 한다. 그래서 **모든** OOS 데이터 페이지의 슬롯 0 에 헤더 레코드를 심었다. 대가:

- 페이지마다 레코드 + 슬롯 하나만큼 실데이터 용량이 준다.
- 모든 청크 코드가 "슬롯 0 은 청크가 아님"을 알아야 한다 — 삽입·삭제·체인 순회 곳곳에 특별 취급이 생겼다.

### 7.2 출생 신고: `RVOOS_NEWPAGE` 복구 인덱스 신설

이건 조금 깊이 들어가 보자. 좋은 질문이 나왔던 부분이다: *"복구할 때 왜 `RVOOS_NEWPAGE` 가 새로 필요한가?"*

새 페이지를 할당받으면 초기화 (포맷) 를 하는데, **초기화도 페이지 수정이므로 WAL 원칙상 로그로 남겨야 한다.** 크래시 직후 디스크의 그 페이지는 쓰레기값일 수 있고, redo 가 초기화를 재현할 수 있어야 하니까.

- **PR 이전**: OOS 페이지 초기화는 "페이지 타입 설정 + 빈 slotted page 만들기"뿐이었다. 초기화 결과가 완전히 뻔하므로 (내용물이 없다!), 엔진의 **범용** 초기화 로그 (`RVPGBUF_NEW_PAGE`) 로 충분했다. OOS 전용 복구 코드가 필요 없었다.
- **PR 이후**: 초기화가 "슬롯 0 에 헤더 레코드 삽입"까지 하게 됐다. 갓 태어난 페이지에 *OOS 만 아는 내용물*이 생긴 것이다. 이러면:
  - 범용 로그의 redo 는 빈 페이지만 재현한다 → 크래시 복구 후 슬롯 0 레코드가 없는 "고장난 페이지"가 된다.
  - 청크 삽입용 로그 (`RVOOS_INSERT`) 를 빌려 쓸 수도 없다 → 그 redo 는 counter 를 갱신하려고 **슬롯 0 레코드를 읽는데**, 슬롯 0 자기 자신을 만드는 replay 중에는 아직 슬롯 0 이 없다 (닭과 달걀).
  - 결국 "타입 + 빈 페이지 + 슬롯 0 레코드"를 **한 번에** 재현하는 전용 복구 인덱스 `RVOOS_NEWPAGE` 를 신설할 수밖에 없었다.

즉 `RVOOS_NEWPAGE` 는 counter 에게 집 (7.1) 을 지어준 대가로 생긴 **출생 신고 제도**다.

### 7.3 유산 상속 규칙: redo 의 MAX 재생

counter 의 최신 값은 사실 슬롯 0 이 아니라 **각 청크의 삽입 로그**가 나른다 (발급과 삽입이 한 로그로 묶임). 그래서 복구 redo 는 청크 이미지의 generation 을 보고 `counter = MAX(counter, 청크의 generation)` 으로 능동적으로 복원해야 한다. "counter 는 단조 증가"라는 불변식을 **복구 코드가 지켜줘야** 하는 구조다.

### 7.4 번호 고갈 대책: wrap-around 은퇴 로직

counter 는 32비트다. 페이지당 2^32 회 발급하면 넘친다 (wrap). 넘친 번호가 옛 번호와 겹치면 신분증 제도 자체가 무너지므로, 지난 리뷰에서 이 질문이 나왔고 — 그 답으로 **HEAD 커밋 (`ecebe6288`) 이 통째로 추가됐다**: 발급 시 포화 검사 + 포화된 페이지를 삽입 후보에서 은퇴시키는 로직. 즉 counter 의 수명 관리 비용은 *가설이 아니라 이 브랜치가 이미 지불한 실비용*이다.

### 7.5 이사 후 리셋 문제: 페이지 재활용 (CBRD-26786) — 이게 결정타

페이지 초기화 코드는 counter 를 **0 으로 리셋**한다. 지금은 OOS 페이지를 통째로 회수 (dealloc) 하는 경로가 없어서 "새 페이지 = 진짜 처음"이 참이다. 그런데 **CBRD-26786 (빈 OOS 페이지 회수)** 가 들어오면, 회수됐다 재할당된 페이지도 초기화를 거친다 → counter 가 1 부터 다시 발급된다 → **그 페이지의 과거를 기억하는 오래된 stub 의 (주소, generation) 과 새 발급분이 충돌할 수 있다.** 장 5 의 버그가 슬롯 단위에서 **페이지 단위로 부활**하는 것이다.

현재 코드도 이 위험을 알고 있어서 해당 지점에 "페이지 회수는 counter 를 보존하거나, 오래된 stub 이 페이지보다 오래 살 수 없음을 보장해야 한다"는 제약 주석을 남겨 놨다. 즉 **미래 세대가 지켜야 할 규칙이 하나 더 생겼다.** 참고로 CBRD-26786 은 이미 별도 브랜치 (`cbrd-26786-oos-page-clean`) 에 구현돼 있다 — 이 위험은 "언젠가"가 아니라 가까운 미래다.

## 장 8. 제안 — 신분증을 발급하지 말고, 이미 있는 시계를 읽자

리뷰어의 통찰은 이것이다:

> 신분증에 필요한 성질은 딱 하나다 — **"같은 호수의 서로 다른 두 입주자가 다른 값을 가질 것."** 그런데 그 성질을 가진 값이 이미 모든 페이지에 있다: **page LSA** (장 4).

### 8.1 왜 성립하나

삽입 시점의 page LSA 를 스탬프로 쓰면:

```
페이지 LSA:  L0 ──[insert A, 스탬프=L0]──▶ L1 ──[delete A]──▶ L2 ──[insert B, 스탬프=L2]──▶ L3
```

슬롯이 재사용되려면 **먼저 이전 입주자를 지운 delete 가 있어야 하고, 그 delete 도 로그에 남아 페이지 LSA 를 전진시킨다** (L1 → L2). 그러니 두 입주자의 스탬프는 반드시 다르다 (L0 ≠ L2). "이사 나가는 행위 자체가 시계를 돌린다"는 게 포인트다.

장 5 의 T4 재방문: 재시도 삭제는 expected = L0 을 들고 오는데 현재 입주자의 스탬프는 L2 → 불일치 → no-op. counter 와 똑같이 버그를 막는다. ✅

### 8.2 구현은 드롭인이다

발급 지점 (`oos_insert_record_in_fixed_page`) 은 이미 페이지 쓰기 latch 를 쥐고 있다. counter 증가 대신 `pgbuf_get_lsa (page_ptr)` 한 줄로 현재 페이지 LSA 를 읽어 청크 헤더에 넣으면 된다. `oos_delete (주소, expected)` 의 대조-후-no-op 계약, 세 가지 삭제 경로, 테스트 계약은 **전부 그대로다** — 비교하는 값의 타입만 4B → 8B 로 바뀐다.

한 가지 주의 (리뷰어가 정확히 지적): 스탬프는 반드시 **삽입 직전의** 페이지 LSA 여야 한다. "로그를 먼저 쓰고 그 로그의 LSA 를 레코드에 적는" 순서는 안 된다 — 복구 redo 는 자기가 재생 중인 로그 레코드의 LSA 를 모르기 때문에 그 값을 재현할 수 없다. 반면 삽입 직전 LSA 는 청크 이미지 *안에* 담겨 로그로 남으므로 redo 가 이미지를 복원하면 스탬프도 따라온다.

### 8.3 장 7 의 다섯 장치가 각각 어떻게 되나

| 장 7 의 관리 장치 | page LSA 에서는 |
|---|---|
| 7.1 슬롯 0 헤더 레코드 | **불필요** — 페이지 헤더의 기존 LSA 를 읽을 뿐, 저장할 새 상태가 없다 |
| 7.2 `RVOOS_NEWPAGE` | **불필요** — 슬롯 0 레코드가 없으니 초기화가 다시 "뻔한 빈 페이지"가 되고, 범용 로그로 복귀 |
| 7.3 MAX 재생 | **불필요** — 스탬프는 청크 이미지 속 데이터라 redo 가 그대로 복원; LSA 단조성은 복구 기계가 원래 보장 |
| 7.4 wrap 은퇴 로직 | **불필요** — 64비트라 현실적 수명 안에 안 넘친다. `ecebe6288` 커밋 전체 삭제 |
| 7.5 페이지 재활용 리셋 규칙 | **불필요 — 리셋될 상태가 없다.** 재할당 페이지의 초기화도 로깅되므로 페이지 LSA 는 과거 발급분보다 항상 크다. 미래 세대가 지킬 규칙 자체가 소멸 |

7.5 행이 결정타다. counter 는 "규칙을 문서화해서 미래에 지키게" 하는 반면, LSA 는 **위험의 구조 자체를 없앤다.**

## 장 9. 꼼꼼히 따져본 걱정거리 두 가지 (제안자가 미확인으로 남긴 것)

제안 코멘트는 정직하게 "확인 못 한 것 둘"을 남겼다. 둘 다 확인했다.

### 9.1 "LSA 를 되감는 절차가 있으면 어떡하나?" → 있다. 그런데 안전하다

LSA 가 시계라면, 시계를 되감는 절차가 있으면 스탬프가 겹칠 수 있지 않을까?

실제로 있다: `log_recreate` — 로그를 파괴하고 새로 만드는 유틸리티 절차 (copydb 등 특수 상황용) 인데, 이때 **모든 영구 페이지의 page LSA 를 NULL 로 리셋**한다. 반면 청크·stub 데이터 *안에* 박힌 스탬프는 페이지 데이터라 그대로 남는다. 시계는 0 으로, 신분증들은 옛 번호 그대로 — 겹칠 조건처럼 보인다.

그런데 안전한 이유가 절묘하다: **이 절차는 로그 자체를 파괴한다.** vacuum 의 할 일 목록 (undo 이미지들) 은 로그 안에 있으므로, 로그가 사라지면 *"옛 (주소, 스탬프) 를 들고 재시도할 주체"도 함께 사라진다.* 위험한 재생 창이 텅 빈다. 남는 건 "리셋 후 로그가 다시 자라서 옛 LSA 구간을 통과하는 동안 하필 살아남은 오래된 참조가 있어야 성립하는" 이론적 충돌뿐인데, 이는 설계가 이미 수용한 7.5 급 잔여 위험이다.

실질 숙제 하나만 남는다: 리셋 직후 아직 아무 로그도 안 닿은 페이지에 삽입하면 스탬프가 NULL LSA 가 될 수 있다. **"NULL LSA 스탬프의 의미"** (현재 "generation 0 = 미발급"의 대응물) 를 정의해 둬야 한다.

### 9.2 "여러 삽입을 한 로그로 묶는 최적화가 오면?" → 생각보다 안전하다

한 로그 레코드로 여러 청크를 삽입하면, 그 청크들이 같은 페이지 LSA 를 스탬프로 갖게 되지 않나?

갖게 된다. 그런데 무해하다. 신분증은 스탬프 단독이 아니라 **(OOS OID, 스탬프) 쌍**이고, OID 에 슬롯 번호가 들어 있다. *서로 다른 슬롯*이 같은 스탬프를 갖는 건 애초에 주소가 달라 충돌이 아니다. 위험한 건 오직 *같은 슬롯의 두 입주자*가 같은 스탬프를 갖는 경우인데 — 재입주 사이엔 반드시 로깅된 delete 가 끼므로 (8.1) 불가능하다.

정리하면 지켜야 할 불변식은 하나로 좁혀진다: **"같은 슬롯의 두 점유 사이에는 최소 1회의 로깅된 페이지 연산이 있다."** 지금 구조에선 자동으로 성립하고, 미래의 최적화가 깨지 않도록 주석으로 박아두면 된다.

## 장 10. "generation 은 UPDATE 중복 제거에도 쓰이지 않나?" — 아니다, 이 선택과 무관하다

counter 를 옹호할 때 나올 수 있는 마지막 논거를 짚는다. 후속 과제 **CBRD-27230** 은 "UPDATE 가 안 바꾼 OOS 값은 새로 저장하지 말고 기존 체인을 재사용하자" (중복 적재 방지, dedup) 인데, 여기에 generation 이 필요하니 counter 를 유지해야 하지 않느냐는 것이다.

결론: **아니다.** 잠긴 CBRD-27230 설계에서 두 질문은 담당이 다르다:

| 질문 | 답하는 주체 |
|---|---|
| "이 UPDATE 가 어떤 체인을 버렸나?" (dedup 판단) | **UPDATE 실행자 자신** — 어떤 컬럼이 할당됐는지 그 시점에 이미 안다. 버린 체인 목록을 커밋 시 로그 레코드로 vacuum 에 알린다 |
| "이 주소의 청크가 아직 그 체인인가?" (재시도 안전) | **신원 스탬프** — 알림 로그도 불변이라 블록 재시도 때 재소비되므로, 멱등성은 여전히 `oos_delete (expected)` 대조가 책임진다 |

"vacuum 이 스탬프를 비교해서 dedup 을 판단"하는 설계는 분석 과정에서 기각됐다. 이유가 깔끔하다: 체인 재사용은 stub 의 byte-copy 라서, 재사용된 체인은 옛 버전의 stub·새 버전의 stub·청크 헤더 **셋 다 같은 (주소, 스탬프)** 를 갖는다. 값이 같으니 "지워도 됨"과 "지우면 안 됨"을 구분할 정보가 애초에 스탬프에 없다.

그래서 스탬프의 역할은 counter 든 LSA 든 **재시도 멱등성 토큰으로 동일**하다. 바뀌는 건 알림 로그의 쌍이 (주소, 4B) 에서 (주소, 8B) 가 되는 것뿐. **CBRD-27230 은 이 교체의 찬성 논거도 반대 논거도 아니다.**

**정직한 단점 두 가지**: (1) stub·청크 헤더가 각 4B 커진다 — stub 크기는 "행이 OOS 로 갈지" 판단 기준 계산에 들어가므로 stub 개수만큼 누적된다. (2) 자기완결적 counter 대신 로그/LSA 체계에 의존하게 된다 — 다만 "이미 15년+ 검증된 기계를 재사용한다"는 게 바로 제안의 요지다.

**결론: 전환한다.** feat/oos 는 아직 미머지 브랜치고 이 PR 이 이미 테스트 DB 재생성을 요구하므로, 온디스크 포맷을 바꿀 마지막 값싼 시점이라는 제안자의 판단에도 동의한다.

**전환 시 코드 주석·스펙에 박아둘 불변식 세 가지:**

1. 스탬프는 반드시 **삽입 직전** 페이지 LSA (§8.2 — redo 재현 가능성의 조건)
2. 같은 슬롯의 두 점유 사이 최소 1회의 로깅된 페이지 연산 (§9.2 — 배치 최적화 가드)
3. NULL LSA 스탬프의 의미 정의 (§9.1 — `log_recreate` 직후 케이스)

**재작업 범위** — 보기보다 작다:

- **그대로**: `oos_delete (expected)` no-op 계약, 세 삭제 경로 (vacuum 두 경로 + 단독 모드 즉시 삭제), 복제 fixup 구조, 불일치 no-op 테스트 계약
- **교체**: 발급부 한 줄 (`pgbuf_get_lsa`), 스탬프 폭 4B → 8B (stub·청크 헤더·복제 fixup)
- **삭제**: 슬롯 0 레코드와 특별 취급 전부, `RVOOS_NEWPAGE`, MAX 재생, wrap 은퇴 로직 (`ecebe6288` 전체), 테스트 브리지
