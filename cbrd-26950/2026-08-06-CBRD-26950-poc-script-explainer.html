1.판정 기준 — '조작'의 세 가지 층위

재현 스크립트를 평가할 때 "무언가를 설정했다 = 조작"으로 뭉뚱그리면 판단을 그르칩니다. 재현 스크립트가 할 수 있는 개입은 성격이 전혀 다른 세 층위로 나뉩니다:

ⓐ 메커니즘 조작

자연 상태에서 일어날 수 없는 동작을 만들어내는 개입 — 소스 패치, fault-injection 훅, 디버거로 스레드 정지, 내부 페이지 직접 변조, 인위적 스케줄링 강제. 이것이 있으면 재현의 증거 능력이 훼손됩니다.

ⓑ 시간 압축

자연적으로 일어나는 사건들의 동시 발생을 몇 분 안에 앉히는 개입 — 부하 크기, 허용 범위 안의 파라미터 튜닝, 진행률을 보고 종료 시점 잡기. 사건 하나하나는 전부 정상 동작입니다.

ⓒ 관측 장치

동작에 영향을 주지 않고 증거만 남기는 장치 — 디버그 로그 읽기, 페이로드에 id 각인, 대조군 설계. 있으나 없으나 서버의 행동은 같습니다.

이 문서의 주장 cbrd-26950-poc.sh 의 모든 구성 요소는 ⓑ 또는 ⓒ입니다. ⓐ는 없습니다. 따라서 이 재현은 "스크립트가 만들어 낸 현상"이 아니라, 운영 달력이 언젠가 스스로 만들 상태를 미리 당겨서 보여준 것으로 읽어야 합니다. 이하 전 절이 이 분류의 근거입니다.

2.스크립트의 5단계 — 각 단계의 운영 환경 대응물

스크립트는 phase 0~4의 다섯 단계로 진행됩니다. 각 단계 아래에 "평상시 운영에서 같은 상태를 만드는 시나리오"를 초록 상자로 함께 적었습니다 — 이 대응이 성립하는지가 이 문서의 핵심 검증 포인트입니다.

  • 전용 DB 생성 — oos26950, 16K 페이지
    cubrid createdb --db-page-size=16K (기본 페이지 크기 그대로) + 전용 cubrid.conf 를 CUBRID_CONF_FILE 로 주입. 설치본의 다른 DB에 영향을 주지 않기 위한 격리 장치이지 동작 변경이 아니다.
    새 서비스용 DB 하나를 표준 옵션으로 만드는 것과 동일.
  • 1단계 — 20,000행 INSERT (gen=1, 'AA' 패턴, 행당 5,000B)
    payload는 BIT VARYING 5,000바이트. OOS 트리거 기준(4,060B)을 넘으므로 전부 OOS 적재. payload 첫 8자에 자기 id를 16진수로 각인(관측 장치 ⓒ — §6). 표준 INSERT 문 20,000개.
    문서·이미지 메타데이터·JSON 등 수 KB짜리 값을 가진 테이블의 일상적 대량 적재.
  • 2단계 — 전체 UPDATE(단일 트랜잭션) + 동시 INSERT 6세션, 그리고 정상 종료
    ① UPDATE t SET payload = ...('BB' 패턴) 을 한 트랜잭션으로 실행·커밋 — 커밋 순간 옛 체인 20,000개가 한꺼번에 vacuum 회수 대상이 된다. ② 동시에 별도 세션 6개가 같은 크기(gen=3, 'DD' 패턴)로 INSERT를 계속한다 — vacuum이 비우는 슬롯을 이들이 재사용. ③ oos.log 의 삭제 건수를 폴링하다가 30% 회수 시점에 cubrid server stop (정상 종료).
    야간 일괄 배치(전 행 마스킹·재계산·포맷 변환)가 돌고, 그동안에도 서비스 INSERT는 계속 들어오며, 배치 후 정기 점검·패치를 위해 서버를 내리는 흔한 운영 순서. 단일 트랜잭션 대량 UPDATE는 배치 작업의 가장 흔한 작성 방식이다.
  • 3단계 — 재기동, vacuum이 잠잠해질 때까지 대기
    서버 시작 후 oos.log 삭제 건수가 5초간 변하지 않을 때까지 기다린다. 개입 없음 — 그냥 기다린다.
    점검 후 서버를 올리고 평소처럼 운영. vacuum 재주행은 사용자가 시키는 게 아니라 엔진이 스스로 한다.
  • 4단계 — 판정: SELECT로 무결성 검사
    id 250개 단위 범위로 나눠 SELECT ... WHERE payload <> 기대값 실행. gen-1(대조군)은 전부 정상이어야 하고, gen-3(피해 후보)에서 판독 불가/값 불일치가 나오면 재현. 추가로 두 vacuum pass의 삭제 OID 집합 교집합(comm -12)을 보강 증거로 수집.
    평범한 조회. 피해 행은 "해제된 슬롯 이후에 INSERT·커밋되고 다시는 건드리지 않은 행"인데도 읽기가 실패한다.
주목 — 종료 방식이 가장 온건한 형태라는 점 스크립트는 kill -9 도, 크래시 유발도 쓰지 않습니다. cubrid server stop — 관리자가 매일 쓰는 정상 종료 명령 하나입니다. vacuum worker는 종료 신호를 받으면 설계된 대로 블록을 중단하고(vacuum.c:3494), 그 중단된 블록의 재주행 역시 설계된 정상 동작입니다. 즉 이 재현은 비정상 상황을 흉내 낸 것이 아니라, 설계된 두 정상 동작(중단, 재주행)의 조합이 데이터를 훼손함을 보인 것입니다.

3.실행되는 SQL의 전부

스크립트가 서버에 보내는 SQL은 아래 네 종류가 전부입니다. 힌트, 시스템 프로시저, 카탈로그 조작, 내부 함수 호출은 없습니다.

-- P0: 테이블 생성
CREATE TABLE t (id INT PRIMARY KEY, gen INT, payload BIT VARYING);

-- P1: 적재 (id를 payload 앞 8자에 각인; 'AA' 반복으로 5,000B)
INSERT INTO t VALUES (1, 1, CAST(CONCAT('00000001', REPEAT('AA',4996)) AS BIT VARYING));
-- ... 20,000행

-- P2: 일괄 갱신 (단일 트랜잭션) + 동시 INSERT (gen=3, 'DD')
UPDATE t SET payload = CAST(CONCAT(LPAD(HEX(id),8,'0'), REPEAT('BB',4996)) AS BIT VARYING);
COMMIT;

-- P4: 무결성 검사 (250개 id 범위 단위)
SELECT COUNT(*) FROM t WHERE id BETWEEN 1 AND 250
   AND payload <> CAST(CONCAT(LPAD(HEX(id),8,'0'), REPEAT('BB',4996)) AS BIT VARYING);

BIT VARYING 을 쓰는 이유는 OOS 테스트 원칙(OOS-CONTEXT §6) 그대로입니다 — VARCHAR는 문자열 압축 때문에 디스크 크기가 예측 불가라, 크기가 정확히 계산되는 타입으로 "이 행은 반드시 OOS에 간다"를 보장하는 것뿐입니다. 5,000B라는 크기 자체는 OOS의 대상 사용례 (수 KB 문서·직렬화 객체) 한가운데 있는 평범한 값입니다.

4.설정값 전수 검토 — 기본값과 다른 것들의 정체

스크립트가 만드는 cubrid.conf 는 9줄입니다. 한 줄씩, 무엇을 위한 것이고 어느 범주(ⓑ 시간 압축 / ⓒ 관측)인지 전수 검토합니다. "이 설정이 없으면 버그가 물리적으로 불가능한가?"가 판단 질문입니다 — 답이 '예'인 항목은 하나도 없습니다.

설정역할분류"이게 없으면 버그가 불가능한가?"
vacuum_log_block_pages=128 블록 하나를 로그 128페이지(2MB) 분량으로 — 블록 처리가 충분히 오래 걸려 4분짜리 테스트 안에서 종료가 블록 중간에 떨어지게 함. 허용 범위(4~1024, system_parameter.c:3790) 안의 튜닝값 ⓑ 시간 압축 아니오. 블록 크기와 무관하게 종료 시점에 처리 중이던 블록은 항상 중단·재주행된다. 기본 크기(≈31페이지)면 잡히는 창이 좁아질 뿐 0이 되지 않는다 — backlog가 있는 한 어느 블록인가는 반드시 처리 중이다
vacuum_worker_count=1 진행률(30%) 측정과 로그 해석을 단순하게 ⓑ 시간 압축 아니오. 오히려 보수적인 설정이다 — 기본값 10이면 종료 순간 처리 중인 블록이 최대 10개라 중단·재주행되는 블록이 더 많아진다
vacuum_master_interval_in_msecs=10 vacuum 기상 주기 단축 — 커밋 후 회수가 즉시 시작돼 테스트가 짧아짐 ⓑ 시간 압축 아니오. 기본 주기여도 회수는 시작되고, 시작된 이상 같은 타임라인이 펼쳐진다. 몇 초 늦게 시작될 뿐
enable_string_compression=no 크기 예측성 보강. 실제 페이로드는 어차피 압축 대상이 아닌 BIT VARYING — 이중 안전장치 ⓒ 관측 아니오. OOS 적재 여부를 결정론적으로 만들 뿐, 슬롯 재사용·블록 재주행과 무관
er_log_vacuum=4163 서버 에러 로그에 vacuum 블록 상태 전이를 남김 (로깅 상세도) ⓒ 관측 아니오. 로그를 더 쓸 뿐 동작 불변
data_buffer_size=256M
log_buffer_size=64M
max_clients=20		 평범한 소형 인스턴스 사이징 ⓒ 관측 아니오. 통상 운영 범위의 값
cubrid_port_id=21950 공용 장비에서 다른 DB와의 충돌 방지 (격리) ⓒ 관측 아니오
파라미터 튜닝을 어떻게 읽어야 하나 vacuum_log_block_pages 와 worker 수는 "몇 분짜리 테스트가 그 창을 확실히 잡는가"를 조절하는 손잡이지, 창을 만들어내는 손잡이가 아닙니다. 운영 환경의 창은 다르게 생깁니다 — 기본 블록 크기라도 backlog가 수십만 건이면 처리 중 블록은 언제나 존재하고, worker 10개면 중단되는 블록도 10개까지 늘어납니다. 스크립트는 그 창을 20,000행·4분 규모로 축소 모형화한 것입니다.

6.증거 설계 — 결과를 신뢰할 수 있는 이유

6-1. 페이로드에 id를 각인 — "조용히 남의 값을 읽는" 경우까지 탐지

payload 5,000바이트의 구조
HEX(id) 8자
자기 id 각인
패턴 반복 × 4,996회 ('AA' → 'BB' → gen3는 'DD')
세대마다 다른 패턴 — 어느 세대의 값인지 식별 가능
검증은 "payload ≠ 이 행의 기대 바이트열"을 보므로, 에러가 나는 손상뿐 아니라 에러 없이 남의 데이터가 반환되는 무증상 손상(슬롯이 또 재할당된 경우)도 "rows wrong"으로 잡힌다.

6-2. 대조군 — 손상이 정확히 예측 지점에만 국한됨을 증명

집단정의기대 결과실측 (3회 실행)
gen-1 대조군
(20,000행)		 UPDATE 후의 'BB' 체인 — 어떤 삭제보다도 먼저 할당됐으므로 재사용된 슬롯에 있을 수 없다. 버그와 무관해야 하는 행들 반드시 무손상 3회 전부 0 손상
gen-3 피해 후보
(수백~수천 행)		 슬롯 해제가 시작된 뒤에 INSERT·커밋되고, 이후 한 번도 수정되지 않은 행들. 이 행을 건드린 주체는 vacuum 2차 pass뿐 재현 시 일부 판독 불가 293 / 163 / 240행 손상

이 설계의 힘: 만약 손상이 스크립트의 다른 요소(부하, 종료, 설정) 때문이라면 대조군도 같이 손상돼야 합니다. 3회 실행 모두 대조군이 완전 무손상이고 피해가 gen-3에만 나타났다는 것은, 손상 원인이 "재사용된 슬롯에 대한 2차 삭제" 단 하나임을 가리킵니다.

6-3. 교차 검증 — 독립적인 두 증거의 수치 일치

  • 증거 A (결정적): SQL 레벨 — 판독 불가가 된 gen-3 행 수
  • 증거 B (보강): 스토리지 레벨 — oos.log 에서 1차 pass와 2차 pass 양쪽에서 삭제된 OOS OID 집합의 크기 (같은 물리 슬롯이 11초 간격으로 두 번 삭제된 기록)

서로 다른 층위에서 수집된 두 수치가 3회 실행 모두 정확히 1:1로 일치했습니다 (293=293, 163=163, 240=240). 이 일치는 우연히 만들기가 매우 어렵습니다 — 손상된 행 하나당 재사용-재삭제된 슬롯이 정확히 하나씩 대응한다는, 사고 메커니즘이 예측하는 바로 그 관계입니다.

7.예상 반론과 답 (Q&A)

"30% 시점에 정확히 서버를 내리는 건 타이밍 조작 아닌가?"
스크립트가 잡는 것은 순간이 아니라 상태입니다 — "vacuum backlog가 남아 있는 동안의 종료". 이 상태는 밀리초 정밀도가 필요한 레이스 윈도우가 아니라, 이 실험 조건에서 수 초~수십 초간 지속되는 구간이고, 운영에서는 backlog 규모에 따라 훨씬 깁니다. 30%라는 숫자 자체도 정밀 타이밍이 아닙니다 — 실제 실행에서는 stop 명령이 worker에 닿는 1.5초 동안 회수가 계속되어 목표 6,000개가 8,215개로 지나쳤는데도 재현됐습니다. 운영에서는 "대량 배치가 끝난 지 얼마 안 된 시점의 점검 재시작"이 정확히 이 상태를 만듭니다 — 야간 배치 후 새벽 점검이라는 아주 흔한 조합입니다.
"단일 트랜잭션으로 20,000행 UPDATE라니, 극단적인 워크로드 아닌가?"
일괄 배치를 단일 트랜잭션으로 묶는 것은 극단이 아니라 가장 흔한 배치 작성 방식입니다 (원자성을 위해 오히려 권장되는 패턴입니다). 20,000행 × 5KB도 소규모입니다 — 운영 배치는 수백만 행 단위가 흔하고, backlog가 클수록 이 버그의 창은 더 넓어집니다. 즉 스크립트는 운영보다 불리한(작은) 조건에서 재현한 셈입니다. 단일 트랜잭션이 필요한 이유도 조작이 아니라 관찰 가능성입니다: 커밋 전에는 vacuum이 손댈 수 없으므로, 커밋 순간 backlog가 한꺼번에 생겨 "backlog가 남은 상태"를 4분짜리 테스트 안에서 안정적으로 만들 수 있을 뿐입니다.
"동시 INSERT 6세션은 버그를 만들기 위한 특수 장치 아닌가?"
동시 INSERT는 슬롯 재사용이라는, 엔진이 스스로 촉진하는 동작을 받아주는 상대역일 뿐입니다. oos_delete_chain 은 슬롯을 비우면 즉시 그 페이지를 bestspace에 재등록하고, 다음 oos_insert 는 그 페이지의 최저 빈 슬롯부터 씁니다 — 재사용은 INSERT가 6개라서가 아니라 설계가 유도해서 일어납니다. 6이라는 수는 "재기동 전, 같은 세션 안에서" 가장 최근에 해제된 슬롯까지 재사용이 따라잡게 하는 처리량 매칭이고 (writer 1개는 vacuum 회수 속도를 못 따라감), 운영에서는 배치와 무관하게 계속 흐르는 서비스 INSERT가 이 역할을 합니다.
"debug 빌드에서만 재현한 것 아닌가?"
debug 빌드는 증거 수집용이지 발현 조건이 아닙니다. 유일한 관측 창구인 oos.log (청크 삭제 기록)가 debug 전용이라 debug를 쓴 것뿐, 사고 경로의 코드 (vacuum_forward_walk_reclaim_oos, oos_chunk_exists, oos_delete, 블록 상태 기계)는 release와 동일하게 컴파일됩니다. 오히려 release에는 "블록 중간 에러 시 계속 진행" 같은 추가 중단 경로가 있어 창이 더 넓을 수 있습니다. release에서는 증거 A(판독 불가 행)는 그대로 관측 가능하고, 증거 B(oos.log)만 없습니다.
"그래서 실제 운영에서 일어날 확률이 얼마나 되는가?"
필요 조건을 다시 세면: ① OOS 사용 테이블에 UPDATE가 만든 회수 backlog — 대량 UPDATE 배치가 있으면 항상; ② 같은 테이블에 동시 INSERT — 서비스가 살아 있으면 항상; ③ backlog 소진 전의 종료·재시작 — 점검·패치·페일오버마다. 셋 다 개별적으로는 일상이고, 겹치는 것도 "배치 직후의 재시작"이라는 달력 수준의 우연이면 충분합니다. 한 번 발현하면 에러·경고 없이 커밋된 데이터가 사라지므로(무증상), 낮은 빈도로도 심각도는 CRITICAL입니다. 그리고 이 스크립트로 측정한 발현률은 조건 성립 시 3회 시도 중 3회였습니다.
