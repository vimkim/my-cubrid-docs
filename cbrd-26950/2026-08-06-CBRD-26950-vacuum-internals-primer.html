1.전체 지도 — 한 UPDATE의 일생

세부로 들어가기 전에 목적지를 먼저 봅니다. UPDATE t SET ... WHERE id=1 한 문장이 커밋된 뒤, 그 흔적이 완전히 정리되기까지의 전 과정입니다. 이 그림의 각 상자가 §2~§9의 주제입니다.

① UPDATE 실행 — 두 곳에 동시에 쓴다 (§2, §3, §4) heap 페이지: 새 버전 레코드 (+ 이전 버전 위치 링크 prev_version_lsa) · WAL 로그: UPDATE 로그 레코드 (옛 버전 전체가 undo 이미지로 들어감)
↓ 로그가 쌓여 블록 경계를 넘는 순간
② 로그 블록 발행 (§5) 블록 요약 {블록 번호, 시작 LSA, 최고(最古)/최신 MVCCID}이 락프리 버퍼로 push
↓ vacuum master가 소비
③ vacuum data(영속 작업 큐)에 등록 (§5) 블록 상태: AVAILABLE → (배포되면) IN_PROGRESS → (완주하면) VACUUMED
↓ 블록의 옛 버전을 볼 수 있는 트랜잭션이 모두 끝나면
④ 워커 잡 1단계 — 로그 스캔 (§6, §9) 블록 안 MVCC 로그 레코드 순회: heap 대상 수집 · B-tree 엔트리 즉시 청소 · UPDATE undo 이미지 속 옛 OOS 체인 즉시 삭제(= 포워드 워크)
↓
⑤ 워커 잡 2단계 — vacuum_heap (§6, §7) 수집한 heap 레코드를 페이지 단위로 일괄 처리: 살아있는 레코드는 도장 정리, 죽은 레코드는 슬롯 제거(+ 딸린 OOS 체인 동반 삭제)
↓ 두 단계 완주 시에만
⑥ 블록에 VACUUMED 도장 — 청소 완료 이 UPDATE의 흔적(옛 버전, 도장, 인덱스 잔재, 옛 OOS 체인)이 모두 정리됨
한 UPDATE의 일생. §10에서 이 그림을 코드 좌표(파일:라인)와 함께 다시 본다.

2.왜 vacuum이 필요한가 — MVCC의 청구서

CUBRID는 MVCC(다중 버전 동시성 제어)를 씁니다. 원칙은 하나입니다 — "쓰는 사람은 읽는 사람을 기다리게 하지 않는다. 대신 읽는 사람마다 자기 시점의 버전을 보게 한다." 이를 위해 모든 heap 레코드는 데이터 앞에 MVCC 헤더라는 이력표를 답니다.

heap 레코드의 물리 구조 (개념도)
insert MVCCID
"누가 만들었나"
delete MVCCID
"누가 지웠나"
(안 지워졌으면 없음)
prev_version_lsa
"이전 버전은 로그 어디에"
고정 길이 컬럼들
가변 길이 컬럼들
MVCC 헤더의 세 필드가 이 문서 전체의 주인공이다. MVCCID는 트랜잭션마다 부여되는 단조 증가 순번 — 레코드에 찍힌 MVCCID를 내 스냅숏과 비교하면 "이 버전을 내가 봐도 되는가"가 결정된다.

세 가지 기본 연산이 이 이력표를 어떻게 다루는지 봅시다. 공통 원칙은 "그 자리에서 없애지 않고, 표시만 남긴다"입니다.

연산그 순간 하는 일나중에 치워야 할 것 (= vacuum의 일감)
INSERT 새 레코드에 insert MVCCID 도장을 찍는다. 커밋 후에도 도장은 남는다 — 아직 이 삽입을 못 보는 오래된 스냅숏이 있을 수 있으므로. 모두가 볼 수 있게 된 뒤에는 도장이 무의미 → 도장 정리 (있으면 매 판독마다 비교 비용)
DELETE 레코드를 지우지 않는다. delete MVCCID 도장만 찍는다 — 옛 스냅숏은 아직 이 행을 봐야 하므로. 아무도 못 보게 된 뒤 레코드(슬롯) 실제 제거 + 인덱스 엔트리 제거
UPDATE = "옛 버전 보존 + 새 버전 기록". 새 레코드를 쓰고, 옛 레코드 전체를 로그에 undo 이미지로 남기며, 새 레코드의 prev_version_lsa 가 그 로그 위치를 가리킨다. 아무도 옛 버전을 못 보게 된 뒤: 새 레코드의 도장·링크 정리 + (OOS가 있다면) 옛 OOS 체인 삭제
vacuum의 정체 즉 vacuum은 "빨아들이는 무언가"가 아니라, MVCC가 미뤄 둔 뒷정리 — ① 죽은 레코드의 슬롯 제거, ② 살아남은 레코드의 도장·링크 정리, ③ 부속물(인덱스 엔트리, 외부 LOB 파일, OOS 체인) 청소 — 를 백그라운드에서 수행하는 데몬입니다. PostgreSQL의 VACUUM과 목적은 같지만, CUBRID는 "테이블을 훑어서" 일감을 찾지 않고 로그를 다시 읽어서 찾는다는 점이 다릅니다(§5).

3.UPDATE 한 번이 남기는 것 — 로그 해부

"heap update가 일어나면 걔들이 어떻게 undo 로그에 가는가"를 코드 수준에서 봅니다. 먼저 알아 둘 것: CUBRID에는 별도의 undo 저장소가 없습니다. Oracle의 롤백 세그먼트나 PostgreSQL의 dead tuple과 달리, CUBRID의 옛 버전은 WAL 로그 레코드 안에 삽니다.

비유 — 한 봉투에 두 장 UPDATE가 남기는 로그 레코드는 봉투 하나에 지시서 두 장을 담은 것과 같습니다. redo 장: "크래시 후 다시 적용할 때는 이 새 값으로" · undo 장: "롤백하거나 옛 버전이 필요할 때는 이 옛 값으로 — 옛 레코드 원본 전체". 이 undo 장이 바로 이 문서 내내 말하는 undo 이미지이고, MVCC의 옛 버전 읽기와 vacuum의 청소가 모두 이 장을 다시 꺼내 읽는 행위입니다. 봉투가 물리적으로 어떻게 생겼는지는 §4에서 바이트 단위로 봅니다.

UPDATE의 실제 순서 (heap_update_home, heap_file.c)

  • 새 레코드 준비
    새 버전의 MVCC 헤더에 내 insert MVCCID를 찍는다. prev_version_lsa 자리는 일단 비워 둔다 — 아직 로그를 안 써서 "이전 버전의 로그 주소"를 모르기 때문 (heap_file.c:21478-21479).
  • UPDATE 로그 레코드를 WAL에 쓴다
    로그 종류는 RVHF_UPDATE_NOTIFY_VACUUM — undo = 옛 레코드 recdes 통째, redo = 새 레코드 (heap_file.c:23756). 이름의 "NOTIFY_VACUUM"이 핵심: 이 로그는 복구용이면서 동시에 "vacuum아, 나중에 여기 와서 치워라"라는 예약장이다.
  • 방금 쓴 로그의 주소(LSA)를 얻는다
    LSA_COPY (&prev_version_lsa, logtb_find_current_tran_lsa (thread_p)) (heap_file.c:23765) — "내 트랜잭션이 마지막으로 쓴 로그 레코드"가 곧 방금 그 UPDATE 로그다.
  • 그 주소를 새 레코드의 머리에 새긴다
    heap_update_set_prev_version() (heap_file.c:26598)이 heap 페이지의 새 레코드 MVCC 헤더에 prev_version_lsa 를 직접 써 넣는다. 이로써 heap의 새 버전 ↔ 로그 속 옛 버전이 연결된다.
  • heap 페이지를 새 레코드로 교체
    같은 슬롯의 내용이 새 버전으로 바뀐다. 옛 버전의 실체는 이제 로그 속 undo 이미지가 유일하다.
heap 페이지, 슬롯 k — 새 버전 (v2) insert MVCCID = 나
prev_version_lsa = 로그 주소 L
새 컬럼 값들
→주소 L을 따라가면
WAL, 주소 L — UPDATE 로그 레코드 종류: RVHF_UPDATE_NOTIFY_VACUUM
redo: 새 레코드 · undo: 옛 레코드(v1) 원본 전체
+ 같은 블록 내 이전 MVCC 연산 링크
UPDATE 직후의 상태. 옛 스냅숏을 가진 트랜잭션이 이 행을 읽으면 v2의 MVCCID가 "안 보임"으로 판정되고, prev_version_lsa 를 따라 로그에서 v1을 꺼내 읽는다 (heap_file.c:26185 부근 — "check visibility of old versions from log following prev_version_lsa links").

여러 번 UPDATE되면 — 버전 체인

같은 행이 또 UPDATE되면 같은 일이 반복됩니다. 각 undo 이미지는 자기가 옛 버전이던 시절의 prev_version_lsa 를 그대로 품고 있으므로, 로그 속에 체인이 생깁니다.

heap: v3 (현재)prev = L2
→L2
로그: v2의 undo 이미지자기 머리에 prev = L1
→L1
로그: v1의 undo 이미지prev 없음 (체인 끝)
중요한 관찰: 중간 버전(v2, v1)은 heap 어디에도 없다. 로그는 불변이므로 이 체인은 수정할 수 없고, 살아있는 레코드에서 도달 가능한 가변 상태는 v3의 prev_version_lsa 하나뿐이다. (이 사실이 CBRD-26950 대책 논의에서 반복적으로 중요해진다 — 자매 문서 참고.)

이렇게 태어난 체인이 언제 "필요 없어지고", 언제 실제로 끊기는지 — 스냅숏과 MVCCID의 시간축 — 는 §7의 마지막 절에서 따로 따라갑니다.

변형: 레코드가 커져서 이사 가는 경우 (relocation)

UPDATE로 레코드가 커져 원래 페이지에 안 들어가면, 본체는 다른 페이지로 이사하고(REC_NEWHOME) 원래 슬롯에는 이정표(REC_RELOCATION)만 남습니다. 이 상태에서 또 UPDATE가 일어나 본체가 다시 이사하면, 옛 본체 슬롯은 물리적으로 즉시 삭제되며 그 삭제 로그(RVHF_DELETE_NEWHOME_NOTIFY_VACUUM)의 undo 이미지가 옛 버전 보존을 대신하고, 그 로그의 LSA가 새 버전의 prev_version_lsa 가 됩니다 (heap_file.c:23710-23720). — "heap 슬롯이 아예 없는 옛 버전"이 존재할 수 있다는 뜻이라, §9에서 다시 만납니다.

DELETE가 남기는 것 (대조용)

DELETE는 훨씬 단순합니다: 레코드에 delete MVCCID 도장을 찍고, RVHF_MVCC_DELETE_REC_HOME 계열 로그를 남깁니다(heap_file.c:23081). 옛 버전 보존이 필요 없습니다 — 레코드 자체가 heap에 그대로 남아 있으니까요(도장만 찍힌 채). 이 차이가 §7과 §9의 안전성 차이로 직결됩니다.

4.WAL은 디스크에 어떻게 저장되는가 — 페이지·레코드 포맷·LSA

§3에서 "undo 이미지가 로그 주소 L에 있다"고 했습니다. 그 주소가 실제로 어떻게 생겼고, 어떻게 바이트 단위 정확한 위치를 찾아내는지를 이 절에서 해부합니다. 결론부터: 로그는 OID도 슬롯 페이지도 쓰지 않습니다. 로그만의 세 번째 주소 체계 — LSA — 를 씁니다.

4-1. 파일 레이아웃 — 무한한 논리 로그, 유한한 물리 파일

개념적으로 로그는 무한히 자라는 페이지의 나열입니다. 페이지마다 영원히 증가하는 논리 페이지 번호(logical pageid)가 붙습니다. 물리적으로는 두 종류의 파일에 삽니다:

파일역할
active 로그 (<db>_lgat)고정 크기. 최신 로그 페이지들이 순환(circular)하며 담긴다. 물리 0번 페이지는 로그 전체의 메타데이터(로그 헤더).
아카이브 로그 (<db>_lgar000…)active가 한 바퀴 돌아 덮어쓰기 전에, 오래된 페이지들을 통째로 복사해 보존한 파일들. 아직 필요로 하는 독자(대표적으로 vacuum과 오래 걸리는 트랜잭션의 롤백)가 있는 한 지우면 안 된다.

논리 번호 → 물리 위치 변환은 산수입니다 (logpb_to_physical_pageid, log_page_buffer.c:4949):

물리 페이지 = ((논리 페이지 − 최초 active 페이지) mod active_페이지수) + 1   /* +1: 물리 0번은 로그 헤더 */

단, 이 산수는 그 논리 페이지가 아직 active 안에 살아 있을 때 이야기이고, 이미 한 바퀴 돌아 덮어쓰였다면 아카이브에서 읽습니다(logpb_is_page_in_archive). vacuum이 오래된 블록을 처리할 때 로그 페이지를 가져오는 vacuum_fetch_log_page 가 정확히 이 분기를 수행합니다 — 그래서 vacuum이 밀려 있으면 아카이브를 지울 수 없는 것입니다.

4-2. 로그 페이지 — 슬롯 없는 append-only 바이트 스트림

LOG_PAGE 한 장 (log_storage.hpp:63-87)
페이지 헤더 (LOG_HDRPAGE)
논리 pageid · 이 페이지 첫 레코드의 offset
· flags · checksum(CRC32)
area[] — 로그 레코드들이 빈틈없이 이어 붙는 공간
LOGAREA_SIZE = LOG_PAGESIZE − 헤더 크기 (log_impl.h:121)
데이터 볼륨의 슬롯 페이지와 달리 슬롯 디렉터리가 없다. 레코드는 앞에서부터 순서대로 이어 붙고, 절대 이동하지 않는다.

여기서 첫 질문 — "왜 로그에는 슬롯 페이지를 안 쓰나?" — 에 답할 수 있습니다. 슬롯 페이지가 슬롯 번호라는 간접층을 두는 이유는, 레코드가 커지고 줄고 지워지고 재배치(compaction)되어도 바깥의 참조(OID)가 깨지지 않게 하기 위해서입니다. 그런데 로그는 append-only 불변 — 한 번 쓴 레코드는 절대 수정·이동·삭제되지 않습니다(수명이 다하면 페이지째 아카이브로 갈 뿐). 움직이지 않는 것에는 간접층이 필요 없으므로, 물리 바이트 오프셋을 그대로 영구 주소로 쓸 수 있습니다.

4-3. LSA — 6바이트 페이지 번호 + 2바이트 오프셋

struct log_lsa                     /* log_lsa.hpp:38-40 */
{
  std::int64_t pageid : 48;        /* 논리 로그 페이지 번호 (6바이트) */
  std::int64_t offset : 16;        /* 페이지 area[] 안의 바이트 오프셋 (2바이트) */
};

LSA(Log Sequence Address)는 이 8바이트가 전부입니다. "LSA로 어떻게 정확한 위치를 찾는가"의 답은 그래서 단순합니다:

  1. pageid → §4-1의 산수(또는 아카이브 탐색)로 물리 페이지를 찾아 읽는다
  2. offset → 그 페이지 area[offset] 이 곧 로그 레코드 공통 헤더의 첫 바이트다 — 탐색도, 슬롯 조회도 없다

또 하나의 성질: pageid가 단조 증가하므로 LSA는 주소이면서 동시에 시간 순서입니다. 두 LSA의 대소 비교가 곧 "어느 쪽이 먼저 일어났나"입니다 — 페이지 LSA 기반 redo 중복 방지, 커밋 대기("내 LSA까지 flush됐나"), vacuum 블록의 시간 범위가 전부 이 성질 위에 서 있습니다.

이 그림에 이 절의 질문들과 앞뒤 절들의 연결 고리가 전부 들어 있습니다:

  • OID는 어디에? — 로그 레코드 자신의 주소는 LSA지만, "이 연산이 어느 데이터를 건드렸나"는 데이터 헤더의 LOG_DATA {volid, pageid, offset(슬롯)} 이 담습니다. 즉 OID(에 해당하는 3요소)는 내용물로서 로그 안에 들어 있는 것이지, 로그를 찾는 열쇠가 아닙니다. vacuum 1단계가 heap 대상을 수집할 때 바로 이 세 값으로 OID를 조립합니다(vacuum.c:3563-3565).
  • undo 이미지의 정체 — undo 데이터부에 옛 recdes가 [타입 2바이트][원본 바이트 그대로]로 담깁니다 (log_append_undoredo_recdes2, log_manager.c:2548-2565). "원본 그대로"이므로 옛 레코드의 MVCC 헤더·가변 오프셋 테이블·OOS inline stub까지 전부 보존됩니다 — §9의 포워드 워크가 undo recdes에서 stub를 꺼낼 수 있는 근거입니다.
  • vacuum_info.prev_mvcc_op_log_lsa — "같은 로그 안의 직전 MVCC 연산" 링크. §6의 로그 스캔이 블록 안을 역방향으로 걸을 수 있는 것이 바로 이 필드 덕분입니다. 로그를 처음부터 다 읽지 않고 MVCC 연산만 골라 딛는 징검다리입니다.

4-5. 압축과 diff — 내용은 줄여도 주소는 불변

undo/redo 데이터가 문턱 크기 이상이면 쓰기 시점에 압축됩니다 (log_append.cpp:677-813):

  • undo·redo가 둘 다 크면 먼저 redo를 undo와 XOR(log_diff)합니다 — UPDATE의 옛/새 레코드는 대부분 비슷하므로 XOR 결과는 거의 0으로 채워져 압축이 잘 됩니다. 이때 레코드 타입이 LOG_MVCC_DIFF_UNDOREDO_DATA 로 바뀝니다.
  • 그 다음 LZ4로 압축하고, 압축 여부는 길이 필드의 최상위 비트로 표시합니다 (MAKE_ZIP_LEN(len) = len | 0x80000000, log_compress.h:33-40). 읽는 쪽(복구·vacuum·MVCC 옛 버전 읽기)은 이 비트를 보고 log_unzip 후 사용합니다.
쓰기 경로 한 줄 요약 — LSA는 언제 확정되나 로그 레코드는 디스크로 직행하지 않습니다. 먼저 메모리에서 prior list라는 대기열의 노드로 만들어지는데, 대기열에 붙는 그 순간 LSA가 배정됩니다(prior_lsa_next_record_internal, log_append.cpp:1359 — §5의 "블록 경계 체크"도 정확히 이 자리에서 일어납니다). 그 뒤 로그 flush 스레드가 노드들을 §4-4의 바이트 배치로 직렬화해 로그 페이지 버퍼에 쓰고 디스크로 내립니다. 커밋 = "내 커밋 레코드의 LSA까지 flush 완료"를 기다리는 것입니다. 일단 쓰인 바이트는 불변이므로, 그때 확정된 LSA는 영원히 유효한 주소가 됩니다.

5.로그가 작업 큐가 되기까지 — 블록의 생산과 배포

CUBRID vacuum의 독특한 점: 청소할 곳을 찾으려고 테이블을 스캔하지 않습니다. UPDATE/DELETE가 일어난 곳은 반드시 로그에 있으니, 로그를 다시 읽으면 일감 목록이 공짜로 나온다는 발상입니다. 다만 로그 전체를 통째로 다루면 너무 크므로, 일정 크기의 블록 단위로 자릅니다.

모든 트랜잭션 스레드 (생산자) 로그 레코드를 하나 쓸 때마다(prior_lsa_next_record_internal, log_append.cpp:1359) "이 레코드가 블록 경계를 넘었나?"를 확인. 넘는 순간, 방금 닫힌 블록의 요약을 발행 (vacuum_produce_log_block_data 호출, log_append.cpp:1384)
↓ 블록 요약 = {블록 번호, start_lsa, 블록 내 최고(最古)·최신 MVCCID}

알아두면 좋은 세부 사항 두 가지 ① 블록은 다음 로그 레코드가 경계를 넘어야 발행됩니다. 대량 UPDATE 후 로그가 더 안 쓰이면 마지막 블록은 발행 대기 상태로 남습니다 (CBRD-26950 재현 실험에서 실측된 사실). ② 완주(VACUUMED) 도장은 워커가 아니라 master가 비동기로 기록합니다 — 워커는 완료 보고만 하고 다음 잡으로 넘어갑니다.

중단과 재실행 — 블록 상태 기계의 핵심 규칙

워커가 블록을 처리하다 서버 종료·크래시·에러로 멈추면, 그 블록은 완주 도장을 못 받습니다. 재기동 시 vacuum data를 읽으며 IN_PROGRESS인 블록을 발견하면 INTERRUPTED 표시와 함께 다시 AVAILABLE로 되돌리고 (vacuum.c:4398-4403 부근), 다음 배포 때 블록 시작점부터 통째로 재실행합니다. "어느 레코드까지 했는지"의 기록은 없습니다 — 이를 개선할 수 있는지 검토하라는 TODO 주석이 코드에 남아 있습니다(vacuum.c:3766). 이 설계가 성립하려면 블록 안의 모든 청소 동작이 두 번 실행돼도 안전(멱등)해야 합니다. 어떤 동작이 그 성질을 갖고 어떤 동작이 못 갖는지가 §7과 §9의 주제입니다.

  • OOS 동반 삭제: 제거되는 레코드가 OOS inline stub를 갖고 있으면(HAS_OOS 플래그), 같은 sysop 안에서 그 레코드가 현재 가리키는 OOS 체인들을 함께 삭제한다 (vacuum_heap_oos_delete_within_sysop, vacuum.c:2520-2526). — §9와 대비되는 "동반(within-sysop) 경로".

실행 ② — 도장 정리: vacuum_heap_record_insid_and_prev_version (vacuum.c:2239)

  • insert MVCCID 도장을 "모두에게 보임"을 뜻하는 상수 MVCCID_ALL_VISIBLE 로 교체
  • prev_version_lsa 를 NULL로 — 이제 아무도 옛 버전을 따라갈 필요가 없으므로 링크를 끊는다 (vacuum.c:2331-2332)

그래서, 체인은 언제 끊기는가 — MVCCID·가시성의 시간축

§3에서 태어난 prev_version_lsa 체인이 언제 "필요 없어지고" 언제 실제로 끊기는지를 시간 순서로 따라갑니다. 결론부터: 논리적 죽음과 물리적 절단은 서로 다른 순간에 일어나며, 그 사이를 잇는 것이 MVCCID와 스냅숏의 산수입니다.

먼저 못 박아 둘 두 가지 ① "끊는다"가 일어나는 곳은 heap 위 살아있는 레코드의 머리, 단 한 곳입니다. 로그 속 undo 이미지들은 불변이라 아무도 손대지 않습니다 — 체인 절단의 물리적 실체는 살아있는 레코드 헤더에서 링크 필드를 지우는 것뿐입니다. ② 끊어도 되는 시점은 부등식 하나가 결정합니다: 레코드의 insert MVCCID < 임계값(전역 최고령 가시 MVCCID). 이 부등식이 성립하는 순간, 옛 버전을 봐야 할 스냅숏이 시스템에 하나도 남지 않았음이 보장됩니다.

독자는 언제 체인을 따라가는가. 판독을 시작하는 트랜잭션은 스냅숏을 받습니다 — 그 순간의 세계를 세 가지로 요약한 것입니다: 하한(lowest_active_mvccid — 이보다 앞선 MVCCID는 전부 완료됨이 보장), 상한(highest_completed_mvccid — 이보다 뒤는 전부 내 스냅숏 이후의 미래), 그리고 그 사이 구간의 활성 비트맵. 레코드에 찍힌 도장 하나를 이 셋과 비교하면 "그 트랜잭션이 내 시점에 아직 진행 중이었나"가 즉시 판정됩니다 (mvcc_is_id_in_snapshot, mvcc.c:91-108):

현재 버전이 "안 보임"으로 판정될 때만 독자는 prev_version_lsa 를 따라 로그로 내려가고, 보이는 버전을 만날 때까지 한 칸씩 거슬러 간다 (heap_get_visible_version_from_log, heap_file.c:26134 — "iterate through old versions until a visible object is found"). 즉 체인은 "현재 버전이 안 보이는 스냅숏"이 존재하는 동안만 필요하다.

임계값은 어디서 오는가. 스냅숏마다 하한이 있으므로, 지금 살아있는 모든 스냅숏의 하한들 중 최솟값을 구할 수 있습니다. 이것이 임계값 — 전역 최고령 가시 MVCCID입니다 (mvcctable::compute_oldest_visible_mvccid, mvcc_table.cpp:355). 이보다 과거의 MVCCID는 어느 스냅숏의 눈에도 첫 구간("완료된 과거")에 떨어지므로, 그 도장이 찍힌 버전을 두고 옛 버전을 찾으러 갈 독자는 존재할 수 없습니다. 이 값은 트랜잭션이 끝날 때마다 앞으로만 전진하며, vacuum master가 깨어날 때마다 갱신해 (vacuum.c:3165) 두 군데에 씁니다 — 블록 배포 문턱(블록의 최신 MVCCID가 이보다 과거여야 배포, vacuum.c:3260)과, 워커 잡이 시작할 때 한 번 붙잡는 threshold_mvccid (vacuum.c:3419 → 위 판정 mvcc_satisfies_vacuum 의 입력, vacuum.c:1773).

이제 UPDATE 하나(v1 → v2, 갱신 트랜잭션의 MVCCID = 1042)를 놓고 시간축을 따라갑니다.

  • 커밋 — 체인의 전성기
    v2가 heap에, v1은 로그 속 undo 이미지로, v2의 prev_version_lsa 가 그 주소를 가리킨다. mvcctable에서 1042는 완료로 바뀌지만 — 커밋 전에 스냅숏을 뜬 트랜잭션들의 비트맵에서 1042는 여전히 "활성"이다 (스냅숏은 뜬 순간의 세계를 고정하므로). 그들이 이 행을 읽으면 v2가 "안 보임"으로 판정되고 체인을 따라 v1을 꺼낸다. 체인이 생명줄인 시기.
  • 옛 스냅숏들이 하나씩 소멸한다
    스냅숏의 수명은 짧다 — READ COMMITTED는 문장마다 새로 뜨고, REPEATABLE READ도 트랜잭션이 끝나면 사라진다. 1042 이전에 뜬 스냅숏이 하나 끝날 때마다 "하한들의 최솟값"이 오를 수 있고, 임계값은 조금씩 전진한다.
  • 임계값이 1042를 지난다 — 논리적 죽음
    이 순간부터 모든 현재·미래 스냅숏의 하한이 1042보다 크다. 어떤 독자가 와도 3구간 판정의 첫 구간에 떨어져 v2가 곧장 보이고, 체인을 따라갈 이유 자체가 없다. 포인터는 아직 물리적으로 남아 있지만 아무도 참조하지 않는 죽은 링크다.
  • vacuum 방문 — 물리적 절단
    이 UPDATE 로그가 속한 블록이 배포되고(T3가 배포의 전제조건), 워커 2단계가 이 행을 판정한다: Q2 "insert 도장이 임계값보다 과거인가" = 예 → 도장 정리. REC_HOME/REC_NEWHOME은 헤더에서 INSID와 prev 두 필드를 물리적으로 들어내고(플래그 해제 + 뒤 내용 앞당김, vacuum.c:2282-2290) 레코드가 몇 바이트 줄어든다. 크기를 못 바꾸는 overflow 헤더(REC_BIGONE)만 INSID를 상수 MVCCID_ALL_VISIBLE(=3)로 덮고 prev를 NULL로 만든다 (vacuum.c:2330-2333).
  • 보상 — 이후의 판독이 더 싸진다
    INSID 플래그가 없는 레코드는 mvcc_satisfies_snapshot 의 첫 분기에서 비교조차 없이 "모두에게 보임"으로 통과한다 (mvcc.c:163-172). 도장 정리는 공간 몇 바이트를 아끼는 일이 아니라, 매 판독의 비교 비용을 없애는 일이다.
  • 로그 쪽 잔해의 최후
    undo 이미지들은 끝까지 수정되지 않는다 — 머리가 잘리는 순간 도달 불가능해질 뿐이다. 물리적으로 사라지는 것은 훨씬 나중, 그 로그 페이지가 담긴 아카이브가 정리될 때다. 단, undo 이미지가 참조하던 옛 OOS 체인은 별도 경로(§9 포워드 워크)가 회수한다.

자주 나오는 변형 세 가지.

  • 절단 전에 또 UPDATE되면? 절단은 언제나 "그 시점의 살아있는 머리"에서만 일어납니다. v3가 생기면 살아있는 머리의 링크는 v3 → (v2의 undo 이미지)이고, v2 이미지 안에 든 옛 링크(→ v1)는 불변 로그의 일부라 영원히 그대로입니다. vacuum은 v2를 만든 UPDATE의 블록과 v3를 만든 UPDATE의 블록에서 같은 행을 각각 방문하며, 매번 "지금 머리의 insert 도장이 임계값보다 과거인가"만 봅니다 — 아직이면 판정 ③(건너뜀), 나중 블록의 방문이 마저 처리합니다.
  • DELETE로 끝난 행의 체인은? 따로 자르지 않습니다. 판정이 ① REMOVE로 떨어져 레코드(=체인의 머리)가 슬롯째 제거되므로, 체인 전체가 같은 방식으로 도달 불가능해집니다.
  • T3~T4 사이(논리적 사망 후, 절단 전)에 읽으면 위험하지 않나? 아닙니다. 포인터는 남아 있지만 어떤 스냅숏도 v2를 "안 보임"으로 판정하지 않으므로, 따라가는 코드 경로 자체가 실행되지 않습니다. 절단이 급하지 않은 이유이자, vacuum이 이 일을 백그라운드로 미룰 수 있는 이유입니다.
이 경로가 블록 재실행에 안전한 이유 (§5의 복선 회수) 판정의 입력이 레코드 자기 몸의 MVCC 헤더라는 점이 전부입니다. 재실행된 2차 방문에서 — 이미 도장이 정리된 레코드는 Q2가 "아니오"가 되어 ③ 건너뜀으로 빠지고, 이미 제거된 슬롯은 타입이 달라 스위치의 default로 빠지며(vacuum.c:1812-1816 주석: "이미 다른 워커가 청소했거나 롤백·재사용된 경우"), 슬롯이 재사용되어 새 레코드가 앉아 있어도 그 새 레코드의 헤더(최근 MVCCID)가 조건에 안 맞아 건너뜁니다. 즉 heap 청소는 대상이 자신의 상태와 신원을 스스로 증언하기 때문에 몇 번을 다시 방문해도 안전합니다. B-tree도 같습니다 — 키 값과 MVCC 정보를 대조하니까요. 이 성질을 갖지 못한 유일한 청소 대상이 §9에 나옵니다.

8.OOS 배경 지식 — 큰 컬럼의 별거 생활

OOS(Out-of-row Overflow Storage)는 feat/oos 브랜치에서 개발 중인 기능으로, 큰 가변 길이 컬럼 값을 heap 레코드 밖의 전용 OOS 파일로 분리합니다. 동기는 단순합니다 — 4바이트 id 를 읽으려고 9KB 레코드 전체를 읽는 낭비를 없애는 것.

개념내용
트리거레코드가 기준 크기(현 16KB 페이지 레이아웃에서 4,060B)를 넘으면, 큰 가변 값부터 하나씩 OOS로 내보내고(largest-first) 기준 이하가 되면 멈춘다
OOS inline stub내보낸 값의 자리에 남는 16바이트 표지: head OOS OID (8B) + 전체 길이 (8B). 레코드의 가변 오프셋 테이블(VOT)에 "이 자리는 stub"라는 비트(IS_OOS)가 서고, MVCC 헤더에 HAS_OOS 플래그가 선다
OOS OID = 물리 주소(volid | pageid | slotid) — OOS 파일 안 슬롯 페이지의 좌표 그 자체. 논리적 이름이 아니라 물리 주소이므로, 슬롯이 비워지고 다른 데이터가 앉으면 같은 OID가 다른 내용을 가리키게 된다
OOS 체인값이 한 페이지보다 크면 여러 청크 레코드로 쪼개 링크드 리스트로 저장. 청크 헤더는 [전체 길이 | 청크 순번 | 다음 청크 OID] — 주인이 누구인지에 대한 정보는 없다
UPDATE 의미론OOS가 있는 행을 UPDATE하면 (값이 안 변해도) 항상 새 체인을 새 주소에 만든다. 옛 체인은 옛 버전 독자(MVCC)를 위해 남겨 두는데, 그 유일한 참조가 undo 이미지 속 옛 stub다
삭제 시점DELETE/UPDATE 순간에는 OOS 체인을 절대 지우지 않는다(옛 버전 독자가 남아 있을 수 있으므로). 청소는 전부 vacuum의 몫
heap 레코드 (UPDATE 후 새 버전) [헤더 | id | name | stub → 새 체인 주소]
→prev_version_lsa
undo 이미지 (옛 버전) [헤더 | id | name | stub → 옛 체인 주소 V|P|S]
→V|P|S
OOS 파일, 페이지 P 슬롯 S 옛 값의 청크 (→ 다음 청크 …)
vacuum이 지워야 할 대상
UPDATE 직후의 OOS 상황. 옛 체인 V|P|S 로 가는 유일한 이정표가 불변 로그 속에 있다.

9.포워드 워크 경로 — undo 이미지에서 직접 지우기

이제 "포워드 워크가 뭐냐"에 답할 수 있습니다. 포워드 워크는 vacuum 잡의 1단계(로그 스캔)가 UPDATE 로그 레코드를 만났을 때, 그 undo 이미지 속 옛 stub에서 옛 OOS 체인의 주소를 직접 꺼내 즉시 삭제하는 경로입니다 (vacuum_forward_walk_reclaim_oos → vacuum_forward_walk_oos_delete_atomic, vacuum_oos.cpp).

왜 이 경로가 존재해야 하는가

vacuum이 OOS 체인을 지우는 경로는 둘입니다. 나눠지는 기준은 "살아있는(또는 heap에 남아 있는) 레코드가 그 체인을 가리키고 있는가"입니다.

② 동반 경로 (within-sysop, §7)① 포워드 워크 (§9, 이 절)
대상제거되는 죽은 레코드가 지금 들고 있는 체인 (DELETE된 행의 것)UPDATE가 남긴 옛 버전의 체인 — 살아있는 레코드는 이미 새 체인을 가리킴
주소를 어디서 얻나heap 레코드의 stub에서undo 이미지의 stub에서 — heap 어디에도 없으므로 (소스 주석: "Reading the undo image is the only way left to free them", vacuum.c:3581-3588)
실행 시점2단계 vacuum_heap, 슬롯 제거와 같은 sysop1단계 로그 스캔 중 즉시, 삭제마다 독립 sysop 커밋

같은 이유로 DELETE 로그에서는 포워드 워크를 하지 않습니다 — DELETE된 행의 체인은 동반 경로가 지울 것이므로, 여기서 또 지우면 이중 삭제가 됩니다 (소스 주석이 명시: "DELETE keeps the same OIDs, so REMOVE frees them already... the check below lets UPDATE in but keeps DELETE out", vacuum.c:3586-3588). 예외적으로 RVHF_DELETE_NEWHOME_NOTIFY_VACUUM(§3의 relocation 변형)은 형식상 삭제 로그지만 실질은 "UPDATE의 옛 본체"이므로 포워드 워크 대상입니다(vacuum.c:3724-3731).

포워드 워크의 실제 절차

  • undo 이미지 파싱
    UPDATE 로그의 undo recdes(옛 레코드 원본 — §4-4에서 본 대로 바이트 그대로 보존됨)에서 MVCC 헤더의 HAS_OOS 확인 → 가변 오프셋 테이블(VOT)을 돌며 IS_OOS 비트가 선 자리의 stub에서 head OOS OID 추출.
  • 확인(probe)
    oos_chunk_exists — 그 주소의 슬롯에 레코드가 존재하는지만 확인. 내용은 읽지 않고, 읽어도 대조할 신원 정보가 청크에 없다(§8의 청크 헤더 참고).
  • 삭제
    oos_delete — 현재 그 슬롯에 있는 청크의 헤더에서 '다음 청크' 주소를 따라 체인 끝까지 삭제. 비워진 슬롯은 즉시 빈자리 목록(bestspace)에 재등록된다.
  • 레코드 단위 sysop 커밋
    이 삭제만의 미니 트랜잭션이 즉시 확정된다. 단, "이 로그 레코드는 처리 완료"라는 기록은 어디에도 남지 않는다 — 블록 전체의 완주 도장이 유일한 진행 기록(§5).
§7과의 결정적 차이 — 그리고 그것이 의미하는 것 동반 경로의 판정 입력은 "지금 heap에 있는 레코드 자신"이지만, 포워드 워크의 입력은 불변 로그 속 과거의 주소입니다. 블록이 재실행되면 같은 undo 이미지에서 같은 주소가 다시 나오는데, 1차 실행이 이미 그 슬롯을 비웠고 그 사이 다른 행의 새 체인이 같은 슬롯을 재사용했다면 — probe는 "점유됨 = true"라고 답하고, 삭제는 새 주인의 살아있는 데이터에 적용됩니다. 이것이 CBRD-26950입니다(§11).

10.종합 — 한 UPDATE의 일생, 코드 좌표와 함께

§1의 지도를 이제 코드 좌표와 함께 다시 봅니다. OOS가 있는 행 하나가 UPDATE된 경우입니다.

  • UPDATE 실행
    새 OOS 체인 삽입(heap_attrinfo_insert_to_oos) → 새 레코드 heap 기록 → RVHF_UPDATE_NOTIFY_VACUUM 로그 (undo = 옛 레코드, 옛 stub 포함; heap_file.c:23756) → 로그 LSA를 새 레코드의 prev_version_lsa 에 기록 (heap_file.c:23765, 26598)
  • 커밋 후에도 옛 것들은 그대로
    옛 버전(undo 이미지)과 옛 OOS 체인은 옛 스냅숏 독자를 위해 존속. 독자는 prev_version_lsa → undo recdes → (필요 시) oos_read 로 옛 값 복원
  • 블록 발행 → vacuum data 등록
    후속 로그가 블록 경계를 넘는 순간 vacuum_produce_log_block_data (log_append.cpp:1384) → master가 소비해 vacuum data에 AVAILABLE로 저장
  • 임계값 통과 → 워커 배포
    블록의 최신 MVCCID < 가장 오래된 활성 스냅숏 → 잡 생성, 블록 IN_PROGRESS
  • 1단계 로그 스캔
    UPDATE 로그 도달 → heap OID 수집(vacuum.c:3567) + 포워드 워크로 옛 OOS 체인 삭제(vacuum.c:3589, 독립 sysop) · 같은 블록의 B-tree 로그들은 인덱스 엔트리 즉시 청소
  • 2단계 vacuum_heap
    수집된 OID의 레코드를 판정(mvcc_satisfies_vacuum, mvcc.c:321): 이 행은 살아 있으므로 도장 정리 — insert MVCCID → ALL_VISIBLE, prev_version_lsa → NULL (vacuum.c:2239, 2331-2332). (만약 그 뒤 DELETE까지 됐었다면 REMOVE — 슬롯 제거 + 현재 체인 동반 삭제, vacuum.c:2424, 2520)
  • 블록 완주 → master가 VACUUMED 기록
    이 UPDATE의 모든 흔적 정리 완료. — 만약 5~6 사이 어디서든 중단됐다면? 블록은 INTERRUPTED로 재장전되고 5부터 통째로 재실행된다. 6은 재실행에 안전(§7), 5의 포워드 워크만 안전 보장이 없다(§9)

11.CBRD-26950과의 연결

이 문서가 설명한 구조에서, 재실행 안전성(멱등성)의 성립 근거를 대상별로 정리하면:

vacuum이 지연 청소하는 대상재방문 시 판별 근거 (자기 몸의 신원·상태)재실행 안전성
heap 슬롯MVCC 헤더 (insert/delete MVCCID)안전 (§7)
B-tree 엔트리키 값 + MVCC 정보안전 (§6)
OOS 청크 (포워드 워크 대상)없음 — 헤더는 [길이 | 순번 | 다음 주소]뿐보장 없음 (§9)

이 비대칭이 실제 사고로 이어지는 조건(블록 재실행 + 슬롯 재사용)과 재현 결과(정상 종료만으로 발현, 293건/163건 행 판독 불가), 그리고 대책 후보 비교는 자매 문서 2026-08-06-CBRD-26950-vacuum-oos-explainer-report.html 에 정리되어 있습니다.
