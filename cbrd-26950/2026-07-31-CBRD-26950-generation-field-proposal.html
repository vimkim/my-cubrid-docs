CBRD-26950 · Analysis · 미팅 자료

vacuum이 살아있는 행의 OOS 데이터를 지울 수 있습니다
— 청크 헤더에 4B generation 필드를 제안합니다

검증 기준: feat/oos HEAD 0ad6afc0f (2026-07-31, bestspace 리디자인 이후) · 발견: PR #6986 리뷰 · JIRA 상태: Analysis
vacuum이 블록을 재처리할 때, 이미 회수했다가 다른 살아있는 행이 재사용한 OOS 슬롯을 구분하지 못하고 다시 지웁니다 — 에러도 로그도 없는 무증상 데이터 손실입니다. ✓ 수정 제안: OOS 청크 헤더에 4B generation 하나를 추가하고, 삭제 전에 대조합니다.
오늘 요청드리는 결정: ① 결함 성립 인정(코드 수준 증명 완료), ② generation 방식으로 ANALYSIS 확정, ③ feat/oos 머지 전 처리 (미출시 상태라 온디스크 포맷 변경 비용이 지금 0입니다).

1사고 시퀀스

  • UPDATE R1
    옛 OOS 체인 V|P|S 의 참조가 로그의 undo image에만 남음 (UPDATE는 항상 새 OID 발급). 이 로그는 블록 B 소속.
  • vacuum이 블록 B 처리 시작 (IN_PROGRESS)
    블록에는 레코드가 여러 개 — 진행 기록은 블록 단위뿐, 레코드 단위 메모 없음.
  • 1차 회수 (정상)
    undo image → V|P|S 추출 → oos_delete → 레코드 단위 sysop 커밋. 슬롯이 비고 페이지는 즉시 bestspace 재등록. start_lsa 는 전진하지 않음.
  • 다른 행 R2의 INSERT가 같은 슬롯 재사용
    bestspace tier-1이 그 페이지를 우선 선택 + spage_find_free_slot 은 최저 빈 슬롯부터 → R2의 청크가 정확히 V|P|S 에 앉음. R2 커밋.
  • 블록 B 완료 전 중단
    크래시 / 정상 셧다운 / (릴리스) 중간 에러 — 셋 중 무엇이든. 블록은 INTERRUPTED로 재장전.
  • 2차 처리 — 사고
    같은 start_lsa 부터 블록 전체 재주행 → 불변 undo image에서 같은 V|P|S → probe oos_chunk_exists: "슬롯에 뭔가 있음" → true → oos_delete 가 R2의 살아있는 청크를 삭제 (멀티청크면 R2의 체인 전체). 에러·경고 없음.

2왜 이것이 반드시 문제가 되는가

2-1. 사고에 필요한 다섯 링크가 전부 "설계된 정상 동작"입니다

이 버그는 어떤 컴포넌트의 오동작도 필요로 하지 않습니다. 각 링크가 의도된 계약이고, 전부 현재 HEAD 소스에서 라인 단위로 확인했습니다:

#링크왜 정상 동작인가근거 (HEAD 기준)
1청크 삭제가 블록 완료 전에 영구 확정 레코드 단위 sysop은 멀티페이지 원자성을 위한 의도된 설계. 복구 undo는 커밋된 sysop을 lastparent_lsa 로 건너뛰므로 크래시로도 안 돌아옴 vacuum_oos.cpp:171,196 · log_recovery.c:4800-4804
2미완 블록은 처음부터 통째로 재처리 진행 위치 start_lsa 는 부분 완료 시 전진하지 않음(코드에 명시적 TODO). 미완 → AVAILABLE+INTERRUPTED, 크래시 부팅 시 IN_PROGRESS도 동일 재장전. 재처리는 버그가 아니라 vacuum의 계약 vacuum.c:3764(TODO), 3926, 8357-8361, 4398-4401
3비운 슬롯·페이지는 즉시 재사용 후보 공간 회수가 OOS 회수의 존재 이유. ANCHORED 페이지의 삭제 슬롯은 REC_DELETED_WILL_REUSE 가 되고 최저 슬롯부터 결정적으로 재사용, 페이지는 삭제 직후 bestspace 전역 캐시+best[]에 재등록 slotted_page.c:2093-2095, 1284-1290 · oos_file.cpp:2189→912-961

5재처리 때 같은 옛 OID가 다시 나옴 WAL은 append-only — undo image는 불변이고, 재주행은 같은 LSA의 같은 이미지를 다시 파싱. oos_delete 는 현재 점유자의 헤더에서 next_chunk_oid 를 읽어 남의 체인을 끝까지 따라감 vacuum.c:3488, 3587-3590 · oos_file.cpp:2171-2194
핵심: 다섯 링크가 전부 "설계대로"인데 조합하면 데이터 손실입니다. 즉 이것은 어느 한 컴포넌트의 버그가 아니라 계약 사이의 상호작용 결함이라서, 주변 코드가 개선돼도 자연 치유되지 않습니다 — 실제로 JIRA 앵커(2c329a4e0) 이후 bestspace 리디자인(CBRD-26176) 등 대형 변경을 전수 검토했지만 이 결함을 막거나 좁힌 커밋은 없습니다.

2-2. 막아줄 불변식이 있는지 전수 수색했습니다 — 없습니다

"어딘가에서 막히지 않을까"라는 가설 7개를 세우고 하나씩 소스로 반박했습니다:

차단 후보반박
블록은 재방문되지 않는다미완 블록은 AVAILABLE+INTERRUPTED로 되돌아가 재배포됨 (위 링크 2)
진행 위치가 처리된 엔트리 뒤에서 재개된다start_lsa 불변 — 명시적 TODO. 레코드 단위 진행 메모는 어디에도 없음
그 구간엔 슬롯 재할당이 불가능하다비운 슬롯을 보호하는 잠금 없음(oos_file.cpp:2116 TODO — 죽은 행의 row lock은 무의미). bestspace가 재사용을 오히려 촉진
페이지/슬롯 메타데이터가 새 점유자를 구분한다헤더에 신원 필드 없음. probe는 내용조차 읽지 않음
트랜잭션/sysop/래치/스케줄링이 직렬화한다sysop은 원자성만 제공(신원 아님), 래치는 fix 단위, vacuum 디스패치 게이트(MVCCID 임계값)는 죽은 행 조건일 뿐 새 점유자와 무관
복구가 재사용 전에 옛 참조를 제거한다undo image는 불변이고, 복구는 오히려 블록을 재장전함. page LSA는 "같은 redo 두 번 적용"만 막음 — 2차 삭제는 replay가 아니라 복구 후 평시 코드의 신규 연산
oos_delete 전에 다른 검증이 있다점유-여부 probe가 유일한 관문

2-3. "확률이 낮으니 넘어가자"가 성립하지 않는 네 가지 이유

#이유상세
1트리거가 일상 이벤트 블록 재처리의 방아쇠는 이국적인 조건이 아니라 정상 셧다운(패치·재시작), 크래시, 릴리스 빌드의 블록 중간 에러입니다. vacuum이 블록 하나라도 처리 중일 때 서버가 내려가면 그 블록은 반드시 재처리됩니다. 운영 수명 동안 수백~수천 번 반복되는 이벤트입니다.
2시간 경쟁조차 필요 없음 재사용 창은 "다음 OOS insert까지" — blob-heavy 테이블이면 초 단위입니다. 더 나쁜 것: 셧다운·크래시 시나리오에서는 재사용이 중단 이전에 이미 일어난 경우에도 성립하므로, 재기동 후 타이밍 경쟁이 아예 필요 없습니다. "1차 회수 → R2 insert → (몇 시간 뒤) 셧다운"이라는 완전히 여유로운 순서로도 발생합니다.
3무증상 + 원인-증상 분리 + 백업 오염 발생 시점엔 아무 신호가 없습니다(정상 vacuum 로그와 구분 불가). 증상은 R2를 나중에 읽을 때에야 — "행은 있는데 특정 컬럼만 못 읽음" — 나타나고, 슬롯이 3차 재사용된 뒤라면 에러조차 없이 다른 행의 값을 읽습니다. 원인(vacuum 재처리)과 증상(며칠 뒤 읽기 실패) 사이 거리가 멀어 진단이 사실상 불가능하고, 그 사이 백업에는 손실이 그대로 복제됩니다. 릴리스 빌드에 OOS 관측 도구도 없습니다(CBRD-26871).
4피해가 확률과 독립적으로 증폭 재사용된 head 슬롯이 멀티청크 값이면 probe는 head만 보고 oos_delete 는 새 점유자의 체인 전체를 따라가 지웁니다 — 한 번의 오판이 수십 KB를 지울 수 있습니다. 그리고 DBMS에서 "확률적 무증상 데이터 손실"은 빈도와 무관하게 correctness 결함입니다 — 고객이 우리 제품에 기대하는 첫 번째 계약이 데이터 보존입니다.

3근본 원인 — vacuum의 지연 삭제 대상 중 OOS 청크만 신원이 없다

vacuum의 블록 재시도는 원래 설계된 동작입니다. 다른 대상들이 재시도+재사용에도 안전한 이유는 삭제 대상이 자기 몸에 신원 메타데이터를 지니기 때문입니다:

재시도 대상재시도를 안전하게 만드는 것재사용돼도 안전한가
heap 슬롯MVCC 헤더 — 재사용된 슬롯은 새 MVCCID라 임계값 검사에서 자동 스킵안전
btree 엔트리키 + MVCC info — 키 조회로 정확히 그 엔트리만 접근안전
OOS 청크없음 — 헤더는 길이/인덱스/다음 OID뿐, probe는 "점유 여부"만 확인데이터 손실

generation 필드는 새 발명이 아니라, vacuum이 건드리는 모든 대상이 이미 갖춘 계약을 OOS에도 채우는 것입니다. (eager 경로가 신원 필드 없이 안전한 유일한 이유도 동기 실행이 주는 공짜 신원 보장입니다 — 지연되는 vacuum은 그걸 받을 수 없습니다.)

4대안 전수 검토 — 각각이 통하지 않는 이유

7개 대안을 검토했습니다. 각 대안이 "왜 매력적으로 보이는지"와 "정확히 어디서 무너지는지"를 함께 적습니다.

대안 1 — 수정하지 않음 ("재사용이 드물 것이다") 탈락

아이디어: 삭제된 OID가 재발급되지 않거나 아주 늦게 재발급된다면 실질 위험이 없다.
  • OOS OID는 논리 식별자가 아니라 물리 주소 (volid, pageid, slotid) 그 자체 — "재발급 절차"가 존재하지 않고, 슬롯 재점유가 곧 같은 OID의 재등장입니다.
  • 현재 코드는 재점유를 막기는커녕 최단 경로로 유도합니다: 삭제 직후(sysop 커밋 전!) 페이지를 bestspace에 재등록하고, insert는 tier-1 캐시에서 그 페이지를 우선 선택하며, 슬롯 선택은 최저 번호부터 결정적입니다.
  • 재사용 지연은 "엄청난 시간"이 아니라 같은 테이블에 다음 OOS 값이 들어오는 순간입니다. §2-3의 이유 1~4가 그대로 적용됩니다.

대안 2 — INTERRUPTED 블록에서 forward-walk 스킵 탈락

아이디어: 재처리 블록임을 알 수 있으니(INTERRUPTED 플래그), 위험한 forward-walk만 건너뛰자. 한 줄짜리 수정.
  • INTERRUPTED 플래그는 "재처리 중"만 알려줄 뿐 "1차에서 어디까지 처리했는지"를 알 수 없습니다. 크래시로 재장전된 블록은 1차에서 한 건도 처리하지 못했을 수도 있는데, 그것까지 통째로 스킵됩니다.
  • forward-walk는 UPDATE 옛 체인을 회수하는 유일한 경로입니다(살아있는 슬롯이 참조하지 않아 REMOVE 경로가 구조적으로 도달 불가). 스킵된 몫은 영구 누수가 됩니다.
  • 정상 셧다운마다 진행 중이던 블록의 OOS가 누수 — 운영 수명 동안 무한 누적됩니다. 무한 누수 차단이 CBRD-26668(vacuum 통합)의 존재 이유인데, 그 목적을 스스로 훼손하는 트레이드입니다.

대안 3 — 레코드 단위 진행 영속화 (start_lsa 전진) 탈락

아이디어: vacuum.c:3764 의 TODO 그대로 — 부분 완료 시 진행 위치를 저장해 같은 로그를 재처리하지 않게 하자.
  • forward-walk는 블록의 마지막 MVCC op에서 prev 링크로 역방향 진행합니다. "여기까지 했음"이 단순 LSA 워터마크로 표현되지 않습니다.
  • 진행 기록은 각 레코드의 삭제 sysop과 원자적으로 WAL-log돼야 합니다 — 아니면 "sysop 커밋 ~ 진행 기록" 사이 크래시에서 정확히 같은 구멍이 재발합니다. 즉 vacuum data 갱신을 레코드 단위로, worker의 sysop 안에서 하도록 바꿔야 합니다.
  • 결과적으로 15년 된 블록-단위 vacuum data 계약을 OOS 하나 때문에 레코드-단위로 수술하는 것 — 회귀 리스크 반경이 청크 헤더 4B와 비교가 안 됩니다. heap·btree는 이 수술이 필요 없습니다(자기 신원 메타데이터로 이미 멱등).

대안 4 — 블록 전체를 단일 sysop으로 탈락

아이디어: 재시도가 항상 깨끗한 상태에서 시작하도록, 블록의 모든 삭제를 하나의 sysop으로 묶자. (overflow도 sysop을 쓰지 않나?)
  • 선례 오인: overflow(REC_BIGONE)의 sysop은 레코드 단위이고, OOS forward-walk도 이미 같은 패턴입니다. 블록 단위 sysop은 선례가 없습니다.
  • 창이 닫히지 않습니다: "블록=VACUUMED" 표기는 worker가 아니라 master가 비동기로(finished job queue 소비) 기록합니다. "블록 sysop 커밋 ~ VACUUMED 영속화" 사이에 크래시가 나면 커밋된 삭제는 영구인데 블록은 INTERRUPTED로 재처리 — 같은 버그가 좁아진 창에서 그대로 재현됩니다. 닫으려면 master/worker 프로토콜 재설계까지 필요합니다.
  • 다른 손상 채널을 증폭시킵니다: oos_delete_chain 은 커밋 전에 페이지를 unfix하고 bestspace에 재등록하므로, 커밋 전 빈 슬롯이 물리적으로 노출됩니다. 그 슬롯을 다른 트랜잭션이 차지한 뒤 sysop이 abort되면 undo(spage_insert_for_recovery)가 남이 앉은 슬롯에 옛 청크를 복원하려는 충돌이 발생합니다. 이 창이 레코드 sysop에선 마이크로초, 블록 sysop에선 블록 처리 시간 전체가 됩니다.
  • 로그 수십 페이지 분량의 무한계 sysop(undo 체인 누적, 말단 실패 시 전량 롤백·전량 재실행)은 vacuum이 긴 시스템 트랜잭션을 피하도록 설계된 이유와 정면충돌합니다.

대안 5 — forward-walk 폐지, 슬롯 기반(REMOVE식) 재설계 탈락

아이디어: REMOVE 경로는 heap 슬롯 + MVCC 체크로 안전하니, 옛 체인 회수도 슬롯 기반으로 바꾸자.
  • 슬롯 기반이 되려면 "옛 체인 참조를 vacuum 때까지 살아있는 어딘가에 유지"해야 합니다. 후보는 셋뿐이고 전부 더 비쌉니다:
  • (a) 새 버전 레코드에 tombstone 매달기 — vacuum 전에 N번 갱신되면 tombstone N세대 누적, 레코드 비대(4,060B 타깃 잠식), tombstone의 복제·복구 의미론 신설. UPDATE 의미론 자체의 대수술.
  • (b) 온디스크 "삭제 대기 큐" 신설 — UPDATE 핫패스에 쓰기+WAL 추가, 큐의 크래시 일관성 관리, MVCCID 게이팅 재구현. 결정적으로 "큐 엔트리를 정확히 한 번 소비"라는 원자성 문제가 지금 블록 재처리 문제의 옷만 갈아입은 버전으로 그대로 남습니다.
  • (c) 무참조 청크 스캔 GC — "이 청크를 가리키는 live 레코드가 있나"를 답하려면 청크→소유자 역참조, 즉 신원 메타데이터가 어차피 필요하고 전체 스캔 비용까지 얹게 됩니다.
  • 관점 전환이 핵심입니다: forward-walk는 우회책이 아니라 WAL undo image가 이미 완벽한 삭제 대기 큐(영속 + MVCCID 게이팅 내장 + 추가 쓰기 0)라는 사실을 활용한 설계입니다. 고장난 것은 큐가 아니라 소비 단계의 신원 확인 하나입니다. 건물은 건강한데 나사 하나가 빠진 상황에서 건물을 다시 짓자는 안입니다.

대안 6 — 생성 트랜잭션 MVCCID를 스탬프로 탈락

아이디어: 청크에 생성 MVCCID를 찍으면(쓰는 시점에 이미 알고 있음) stub도, insert 흐름도 안 바꿔도 된다 — undo image의 MVCC 헤더에서 기대값을 얻으면 되니까.
  • 같은 트랜잭션의 다중 UPDATE에서 충돌: 트랜잭션 T가 같은 행을 두 번 갱신하면 1차 새 체인과 2차 새 체인이 같은 T로 찍힙니다. 1차 체인이 회수·재사용되고 그 자리에 2차 체인이 앉으면 스탬프가 일치 → 오판 그대로.
  • 기대값 출처인 undo image의 insert MVCCID는 이미 이전 vacuum이 지웠을 수 있습니다(insert MVCCID 클리어는 vacuum의 정상 작업) → 대조 불가 케이스가 구조적으로 존재.

대안 7 — owner OID 스탬프 (신원 필드, 차선) 차선

아이디어: 청크 헤더에 소유 heap 레코드의 OID를 찍자. 기대값은 vacuum이 로그 레코드 주소에서 공짜로 얻으므로 stub 불변.
  • 방향은 옳습니다(신원 대조) — 그러나 소스로 확인한 함정: heap_attrinfo_insert_to_oos 는 recdes 변환 단계(heap_file.c:13128)에서 실행되고, 이는 heap 슬롯 할당(heap_insert_logical) 이전입니다. 즉 INSERT로 만들어지는 체인은 쓰는 시점에 owner OID가 아직 존재하지 않습니다.
  • 그런데 1세대 체인도 행이 나중에 UPDATE되면 forward-walk 회수 대상입니다. 스탬프 없이 두면(NULL) 대조 불가 → 스킵 → 모든 행의 첫 체인이 영구 누수 — 본말전도.
  • 남는 선택지는 heap insert 후 청크 헤더 backfill(OOS INSERT 핫패스에 청크당 페이지 재고정+WAL — 영구 런타임 비용) 또는 OID 할당을 변환 앞으로 재배치(insert 흐름 침습 변경)뿐입니다.
  • generation과의 저울: owner OID = 포맷 변경 1곳 + 핫패스 영구 비용, generation = 포맷 변경 2곳 + 흐름 불변. 포맷 변경은 미출시인 지금 공짜지만 핫패스 비용은 영원히 냅니다 → generation 우세.

채택 — 4B generation 대조 제안

재사용마다 반드시 달라지는 세대 번호를 청크에 찍고, 삭제 전 대조. 불일치 = 슬롯 재사용됨 = no-op.
  • 위 대안들이 무너진 지점을 전부 통과: 회수 유지(↔대안 2), vacuum 코어 무변경(↔대안 3·4), 기존 아키텍처 유지(↔대안 5), 같은-트랜잭션 충돌 없음(↔대안 6), 쓰기 흐름 불변(↔대안 7).
  • 단일 청크·멀티청크 데이터 손실이 같은 근본 원인(신원 부재)이므로 필드 하나로 둘 다 차단. 미래의 재시도성 호출자(페이지 회수 CBRD-26786, flashback FU-01)까지 같은 계약으로 커버.

5제안 설계 — 4B generation

변경 내용

  • 페이지 헤더에 uint32 카운터 — 그 페이지에 청크가 insert될 때마다 +1 (어차피 W-latch 잡고 쓰는 페이지라 비용 0)
  • 청크 헤더 oos_record_header 16 → 20B: generation 4B 추가
  • inline stub 16 → 20B: 기대 generation 4B 추가 (옛 참조가 살아남는 유일한 곳이 undo image 속 stub이므로)
  • 삭제 계약 변경: probe가 "슬롯이 점유됐나"가 아니라 "점유자의 generation이 내 기대값과 같은가" — 불일치 = 재사용됨 = no-op

왜 이 수치인가

  • uint32 충분: 오탐에는 블록 재처리 창 안에 한 페이지에서 2³² 번의 insert/delete 사이클이 필요 — 물리적으로 불가
  • 20B(패딩 없음): stub은 행·컬럼마다 반복 지불하는 비용. variable area 내 오프셋이 임의라 24B 패딩은 8-정렬을 보장하지 못함(정렬은 리더 책임). PG TOAST 포인터도 18B
  • 미래 예약이 필요하면 행당 반복인 stub이 아니라 체인당 1회인 청크 헤더에

7왜 지금인가

  • 포맷 변경이 공짜인 마지막 시점 — 출시 후에는 온디스크 호환/마이그레이션이 붙습니다. 늦출수록 같은 수정의 비용이 커지는 유일한 방향입니다.
  • 후속 작업이 이 구멍 위에 쌓입니다 — OOS 빈 페이지 회수(CBRD-26786)는 재시도성 삭제 호출자를 추가하고, flashback retention(CBRD-26847 FU-01)은 이 수정이 오독 차단의 전제라고 명시돼 있습니다.
  • 터지면 진단이 불가능한 부류입니다 — §2-3 이유 3. 사전 수정 외의 방어선이 없습니다.

8예상 질문 (사전 답변)

Q. REMOVE 경로는 heap 레코드와 sysop으로 묶이고 MVCC 체크가 있으니 안전하지 않나?
정확합니다 — 그래서 REMOVE 경로는 이 이슈 대상이 아닙니다. 버그는 forward-walk 경로인데, UPDATE의 옛 체인은 살아있는 heap 레코드가 참조하지 않아(undo image에만 존재) MVCC 체크를 걸 대상 자체가 없습니다. pass 1의 forward-walk는 heap 레코드를 건드리지 않으므로 어떤 heap 기반 게이트도 pass 2에서 같은 답을 냅니다. heap을 지키는 그 원리(자기 몸의 신원 메타데이터)를 청크에도 주자는 것이 이 제안입니다.
Q. page LSA가 있으니 recovery가 이중 적용을 막지 않나?
page LSA는 "같은 redo 두 번 적용"을 막습니다. 2차 삭제는 replay가 아니라 복구 완료 후 평시 코드의 신규 연산이라 새 로그를 남기며 정상 통과합니다. 크래시 없는 시나리오(셧다운, 릴리스 중간 에러)에서도 동일하게 발생합니다.
Q. bestspace 최근에 리디자인되지 않았나 (CBRD-26176)?
그 커밋은 heap bestspace 전용입니다 — oos_file.* 는 파일 목록에 없습니다. 본 분석의 모든 인용은 리디자인 이후 HEAD(0ad6afc0f) 기준입니다.
Q. 재현해봤나?
레이스라 단일 SQL 재현은 불가하고, 결정적 재현에는 fault-injection 훅(소스 변경)이 필요해 실험 설계까지 준비했습니다. 대신 증거 의무 A–H를 현재 소스 라인으로 전부 확인했고, 차단 불변식 후보 7종을 전수 반박했습니다(§2-2). 수정 후에는 같은 훅으로 회귀 테스트를 만들 수 있습니다.
