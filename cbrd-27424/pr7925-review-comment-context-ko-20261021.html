1. 이 PR은 어떤 문제를 고치고 있었나?

OOS는 큰 컬럼 값을 행 바깥의 별도 저장 공간으로 옮기는 기능입니다. 행 안에는 그 값을 찾아갈 참조가 남습니다. 작은 값은 행 안에 그대로 남을 수 있습니다.

기존 standalone 적재의 문제

loaddb -S와 일부 csql -S 쓰기는 workspace에서 만든 행을 저장할 때 OOS 변환을 건너뛰었습니다.

값을 다시 읽으면 맞더라도, 큰 값을 분리해야 한다는 저장 정책은 적용되지 않을 수 있었습니다.

PR이 연결한 처리

실제 저장할 목적지를 정한 뒤 기존 OOS 준비·최종화 경로를 거치게 했습니다.

이 과정은 OOS 선택뿐 아니라 행을 읽고 다시 직렬화하는 작업도 수행합니다. [1]

리뷰 댓글의 범위: OOS 기능 전체를 없애자는 의견이 아닙니다. OOS 준비를 마쳤지만 값이 모두 행 안에 남은 경우, SA에서만 원래 행을 다시 선택하는 처리가 필요한지 묻는 의견입니다.

2. 같은 행을 표현하는 버퍼가 두 개 생깁니다

사용자가 행을 두 번 INSERT한 것이 아닙니다. 한 행을 저장하기 위해 메모리에 두 가지 바이트 표현이 존재하는 상황입니다.

A

workspace가 보낸 원래 행

객체를 workspace에서 이미 직렬화한 결과입니다. OOS 준비 함수에 들어가기 전부터 존재합니다.

이 문서에서 “원본”은 원래 입력 버퍼 A를 뜻합니다.

B

OOS 준비 함수가 다시 만든 행

heap_prepare_oos_record가 A의 컬럼 값을 읽고, 저장 배치를 정하고, 새 버퍼에 직렬화한 결과입니다.

헤더도 원본에서 전달합니다. CHN 보존이 원본 선택 분기에만 의존하는 구조는 아닙니다. [3]

B를 만들었다고 OOS가 반드시 생기는 것은 아닙니다. 준비 결과 모든 값이 inline으로 남아도 B는 만들어집니다. 바로 이 경우의 A/B 선택이 댓글의 쟁점입니다.

5. 어느 부분에서 논리가 약해지나?

댓글에는 어떤 명제를 인정하고 동시에 부정하는 식의 명백한 자기모순은 없습니다. 주로 비교에서 빠진 효과와 관찰보다 넓어진 결론이 있습니다. 댓글 자체도 단정적인 오류 선언보다는 재검토 요청으로 읽는 편이 정확합니다.

가. 버퍼 해제는 없어지는 비용이 아닙니다

원래 SA 분기는 B를 바로 해제합니다. 분기를 없애면 B를 저장 처리에 사용하고 나중에 해제합니다. 분기를 지워도 B 메모리의 해제 자체는 필요합니다.

따라서 조기 해제는 저장 처리 중 살아 있는 임시 메모리를 줄일 수 있습니다. 한편 원본 A를 추가 검증하는 호출은 실제로 있습니다. 이 inline 경우 검증은 기본 헤더 확인 뒤 끝나므로 컬럼 전체를 다시 읽는 작업은 아닙니다. [4]

정확한 표현: 이 분기는 재인코딩 비용을 줄이지 못합니다. 대신 원본을 선택하고 임시 버퍼를 일찍 해제합니다. 제거하면 선택·검증 처리는 단순해지지만 B의 생존 기간은 길어집니다.

나. 패딩 차이는 이해할 수 있지만, 표본은 표본입니다

예를 들어 고정 컬럼이 하나이고 값이 NULL이 아니라면, bound bit 영역에서는 해당 컬럼의 비트 하나만 값의 유무를 나타냅니다. 4바이트로 정렬된 나머지 공간은 그 컬럼의 의미를 결정하지 않습니다. [6]

근거로 쓸 수 있는 결론: 분기 제거의 영향을 직접 확인할 assertion을 검토하고, 요구하는 동작을 명확히 한 뒤 변경된 소스에서 검증하자.

라. 모드가 다르게 동작한다는 사실은 오류의 증명이 아닙니다

SA와 서버가 서로 다른 버퍼를 사용해도 필요한 값·헤더·소유권·트랜잭션 계약을 지키면 올바를 수 있습니다. 반대로 서버 경로에서 사용 중이라는 사실만으로 SA에도 안전하다고 결론 낼 수는 없습니다.

공통 경로를 쓰자는 제안의 강점은 특수 처리를 줄여 유지보수를 쉽게 한다는 점입니다. 정확성과 안전성은 CHN·최종화·버퍼 수명 등 필요한 계약을 확인해 뒷받침해야 합니다.

7. 분기 삭제와 사전 판정은 서로 다른 변경입니다

현재 반영된 방향

B를 만들었다면 B를 사용한다

A → B 생성 → B 최종화 → B로 저장 처리

늦은 A 선택 분기를 없앱니다. B를 만드는 비용은 계속 발생합니다.

주된 효과는 경로와 소유권 처리를 단순하게 만드는 것입니다.

별도로 검토할 방향

B 생성이 필요 없는 입력은 미리 거른다

A → 준비 필요성 검사 → 필요할 때만 B 생성

안전하게 건너뛸 수 있다면 재인코딩 자체를 피할 수 있습니다.

행 크기, 저장 정책, 표현 버전, 기존 OOS 참조 등을 보수적으로 판정해야 합니다.

원래 조건은 B에 OOS가 있는지도 확인합니다. B를 만들기 전에는 B를 볼 수 없으므로 같은 if문을 단순히 위로 옮길 수는 없습니다. 별도의 안전한 판정 기준이 필요하며, 댓글은 이를 PR #7927의 관련 사전 필터 의견과 연결했습니다. [0]

사전 판정이 보수적이라면, 검사에서 걸러내지 못해 B를 만들었지만 결과는 inline인 경우가 남을 수 있습니다. 따라서 사전 필터를 추가하는 것만으로 늦은 원본 유지 분기의 설계 문제가 자동으로 사라지지는 않습니다.
