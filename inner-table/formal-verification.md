# Sidecar 설계의 TLA+ 검증

사용자는 엔진 구현에 들어가기 전에 Sidecar 설계를 더 깊이 검증하고,
서브에이전트가 검증 자체의 허점도 찾기를 요청했다. 이 문서는 설계 승인자가
무엇을 확인했고 무엇이 남았는지 판단하기 위한 보고서다.

분석일은 2026-11-04, Asia/Seoul이다. 엔진 기준은 CUBRID/CUBRID
`e64a04a79a5842827a124b3f8313516d0da2594c`, 설계 출발점은 문서 커밋
`12b1d0d20a0669ff0401c8290e672d65198aaf0d`이다. 이번 변경은 검증 도구와
설계 문서에 한정된다. 엔진 구현 승인은 아직 받지 않았다.
검증 산출물의 소스 커밋은 `c1d54924652a1aca71e26e00ec92c8e6f4c06965`이며,
`sidecar-codex`의 `.agents/skills/verify-sidecar-protocol/`에 있다.

## 쉽게 말하면

TLA+ 모형에는 “새 값을 저장한다”, “이전 값으로 되돌린다”, “서버가 꺼진다”
같은 단계를 적는다. TLC는 정해진 크기 안에서 그 단계들이 일어날 수 있는
모든 순서를 탐색한다. 값의 내용은 모형 안의 유한 토큰으로 나타낸다.
각 순서에서 값이 빠지거나, 롤백한 값이 다시 보이거나,
복제가 일부만 적용되는지를 검사한다.

탐색이 끝나도 “실제 CUBRID에 결함이 전혀 없다”는 뜻은 아니다. 모형에 적은
규칙, 가정, 크기 안에서 위반을 찾지 못했다는 뜻이다. 모형이 검사하지 않는
중요한 약속을 빠뜨리면 정상으로 판정할 수 있다. 이번 독립 검토는 실제로
그런 누락을 발견했다.

## 최종 실행 결과

최종 공통 qualification 실행은 종료값 0으로 끝났다. 121개 설정이 모두
예상 결과와 일치했다. 정상 설정 14개는 비어 있지 않은 상태 공간의 탐색과
설정된 시간 속성 검사를 마쳤고, 의도적 결함 68개는 지정한 속성 위반으로
잡혔으며, 도달 증거 39개는 목표 상태에 도달했다. 도달 증거도 목표의
부정을 검사하므로 TLC 출력에는 지정한 위반이 나타난다. 이를 새 결함으로
세지 않는다. 시간 초과나 도구 오류를 성공으로 센 경우는 없다.

| 모형 | 정상 완주 | 의도적 결함 검출 | 실행 경로 도달 |
| --- | ---: | ---: | ---: |
| Lifetime | 4 | 19 | 11 |
| History | 5 | 19 | 9 |
| Undo | 3 | 10 | 6 |
| Boundary | 2 | 20 | 13 |
| 합계 | 14 | 68 | 39 |

qualification에는 기본 quick 설정 116개가 모두 포함된다. 같은 입력으로
quick을 별도 반복 실행하지 않았다. 정상 설정의 고유 상태 수는 Lifetime
13,048 / 1,805 / 55,406 / 8,058, History 18,805 / 1,172 / 98,248 /
219 / 216,142, Undo 203 / 132 / 472, Boundary 54,736 / 108,726이다.
각 숫자는 별도 설정에서 도달 가능한 추상 상태 수다. 실제 데이터베이스
실행 횟수나 성능 측정치가 아니다.

검증은 네 부분으로 나눴다. 세부 모형만 따로 통과해서는 경계의 일치까지
보장할 수 없으므로, 작은 통합 모형도 추가했다. 세부 모형 전체의 곱을
완주했다거나 일반적인 합성 증명을 했다고 주장하지 않는다.

| 모형 | 검사하는 약속 | 주요 유한 범위 |
| --- | --- | --- |
| Lifetime | 부모가 가리키는 조각의 완전성, 소유권, 저장점 복원, 오래된 읽기와 정리 | 행 1개, 값당 조각 2개, 쓰기 주체 최대 2개; 주체 1의 새 문장 최대 5개, 주체 2는 교체 1회 |
| History | 기록된 값과 실제 복원된 값의 일치, 취소 기록 보존, 복제의 중복 방지와 트랜잭션 원자성 | 원본 트랜잭션 1개, 작업 최대 3개, before/after 각각 조각 최대 2개, 소비자 2개, 원본·복제 중단 각각 1회 |
| Undo | 실제 잡고 있는 슬롯·공간·페이지 보호, 경쟁 트랜잭션 데이터 보존, 복구 진행 | 페이지 1개, 삭제 이미지 1개, 경쟁 삽입 1개, 중단 1회; 슬롯 최대 3개·공간 4단위 |
| Boundary | 저장·취소·복구·기록 보존·복제의 연결, 완료 후 남는 조각 | 작업 3개, 로컬 조각 2개, 이미지 한쪽당 기록 조각 최대 2개, 원본·복제 중단 각각 1회 |

표의 최대치를 모두 결합한 한 번의 실행은 아니다. 예를 들어 Lifetime의
5문장 설정과 취소·중단·저장점 설정은 별도다. 실제 상수와 검사 목록은
각 `.cfg`와 독립 `references/requirements.json`에 고정되어 있다.

## 독립 검토가 찾은 허점과 수정

아래는 검증 모형 또는 판정 도구의 결함이다. 실제 엔진 결함으로 확정한
목록이 아니다. 일부 변형은 기존 정상 검사 전체를 통과했다. History의
생성자 변형은 기존 이미지 검사에서는 통과했지만, 뒤의 복제 검사는 잡았다.
비복제 소비자의 실제 복원 결과를 검사하지 않는 누락은 여전히 남아 있었다.
보강 후에는 독립 정답과 실제 복원 결과를 검사하고, 전체 정상 검사 항목을
켠 직접 변형으로 검출 여부를 다시 확인했다.

| 발견한 허점 | 통과하면 놓치는 동작 | 보강한 검사 |
| --- | --- | --- |
| Undo가 실제 보호 자원 대신 “작업 중” 상태를 믿음 | 래치나 예약을 잡지 않아도 다른 삽입이 막힘 | 실제 보유 자원으로 할당·페이지 해제를 제어; 보호 획득 생략과 조기 해제 변형 |
| 삽입한 조각의 롤백 누락을 검사하지 않음 | 부모 없이 조각만 남음 | 정리 완료 후 반대 방향 소유권 검사 `NoUnownedAfterDrain` |
| 저장점 정답도 같은 undo 기록과 목표에 의존 | 데이터와 정답을 함께 너무 멀리 되돌림 | undo 기록 밖에 문장·저장점의 보존할 상태를 별도 보관 |
| 정리 작업의 실행만 보고 완료는 요구하지 않음 | 정리 작업이 계속 돌면서 조각을 영원히 남김 | 가용성과 공정성을 유지한 채 실제 정리 완료를 요구 |
| 기록 생성 함수가 정답 생성 함수이기도 함 | before/after가 함께 뒤바뀌어도 같은 값으로 비교 | 입력의 정답과 실제 기록·복원 결과를 직접 비교 |
| 복제된 작업의 올바른 앞부분만 검사 | 원본 트랜잭션의 일부가 먼저 노출됨 | 모든 살아남은 작업과 적용 위치를 한 번에 커밋 |
| 취소된 작업의 이미지 의존성만 계산 | 취소 기록을 먼저 지워 롤백한 작업이 되살아남 | 취소·커밋 기록을 포함한 트랜잭션 의존 구간 보존 |
| 통합 모형이 복구·취소 완료 표지만 검사 | 부모나 삽입 조각을 남긴 채 완료 선언 | `AbortRestored`, `CancellationChunksRestored`; 이전 실제 공개를 요구하는 도달 증거 |
| 큰 정상 설정에서 검사 항목을 빼도 공통 목록 충족 | 다른 설정이 대신 검사해 큰 설정이 약해짐 | 설정별 specification·검사 목록·상수·행렬을 독립 목록에 고정 |
| 시작 상태가 0개여도 TLC 성공을 그대로 수용 | 실행할 수 있는 상태가 없는 빈 모형이 통과 | 시작 상태와 탐색 상태가 양수이고 탐색이 완주했는지 확인 |

독립 Terra 재검사는 Lifetime과 Undo의 실제 동작·조건을 직접 바꾼 11개
변형을 모두 검출했다. 내장 Fault 선택에만 의존하지 않았다. History는
별도 Terra 검토자가 33개 설정 전체와 복원 데이터 변형을 재실행했다.
Boundary는 Astra 검토자가 복구 완료와 저장점 취소의 조건만 제거했을 때
기존 모든 검사와 진행 조건을 통과하는 것을 확인했다. 이후 새 검사로
그 변형을 검출한다. 각 모형의 `coverage.md`에 재현과 범위가 있다.

## 설계에 명확히 추가한 약속

기록은 살아남은 값 조각만 보존해서는 부족하다. 취소·커밋 기록까지 소비자가
필요로 하는 전체 구간을 보존해야 한다. 복제는 원본 트랜잭션의 살아남은
작업을 모두 준비한 뒤, 데이터와 적용 위치를 하나의 로컬 커밋으로 공개한다.

저장점 취소가 완료되면 해당 작업이 삽입한 조각이 없어야 한다. 미커밋
트랜잭션의 재시작 복구가 중단 완료를 선언하면 원래 부모와 조각 상태가
복원되어야 한다. Boundary의 중단은 서버 중단 후 복구이며, 실행 중 전체
트랜잭션의 abort는 이 모형에 없다.

작업 범위의 지연 읽기 뷰는 rollback이나 abort 때 할당 없이 닫는다.
이미 복사한 값의 소유권은 유지한다. 뷰를 다음 변경까지 유지하도록 모형을
넓히는 대신, 문서의 수명 계약과 맞췄다.

## 한 명령으로 재실행

CUBRID 소스 작업 디렉터리에서 실행한다.

```sh
python3 .agents/skills/verify-sidecar-protocol/scripts/check.py
python3 .agents/skills/verify-sidecar-protocol/scripts/check.py --matrix qualification
python3 .agents/skills/verify-sidecar-protocol/scripts/selftest.py
```

기본 실행은 빠른 행렬, qualification은 더 큰 필수 설정까지 포함한다.
`--model lifetime`, `history`, `undo`, `boundary`는 해당 부분만 검사한다.
Python 3.10 이상, Java, TLA+ tools 배포판 1.7.4가 필요하다. 저장소의
스킬은 설치하지 않으며 `~/.cache/tlaplus/tla2tools-1.7.4.jar` 또는
`TLA2TOOLS_JAR`의 SHA-256을 확인한다.

```text
936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88
```

이 배포판의 실행 배너는 TLC 2.19다. JVM마다 임시 디렉터리를 따로 써서
동시 실행 중 표준 모듈 압축 해제가 충돌하지 않게 한다. 입력, 실제 명령,
검사 결과, 상태 수, 로그, 해시를 실행별 임시 디렉터리에 남긴다. 엔진
소스는 추출하거나 인증하지 않는다. 실행 중 runner 파일을 수정하지 않는다.
Java 실행 파일 해시는 전체 Java 런타임을 고정하지 않으므로 로그의 버전도
함께 확인한다.

정상 설정은 시작 상태가 있고 탐색 큐가 비었으며 설정된 시간 속성 검사까지
끝나야 성공이다. 결함 변형과 도달 증거는 지정한 속성의 위반이어야 한다.
시간 초과·구문 오류·교착·다른 속성의 위반은 성공으로 세지 않는다.
결과는 `/statechart`로 해석한다. 특정 반례 뒤의 추가 상태도 탐색하는
statechart 실행 중 하나는 100,000상태 제한에 도달했다. 그 추가 탐색으로
완전성이나 교착 부재를 주장하지 않는다. 필수 정상 TLC 탐색에 이 제한을
적용한 것은 아니다.

## 남은 한계와 다음 승인 단계

Boundary는 실제 History 연산자를 가져다 쓴다. Lifetime과 Undo에는 명시적
사건 대응과 가져온 가정이 있고, 기계적으로 검사한 동작 정제 증명은 없다.
별도 정상 모형들의 통과가 전체 구현의 합성 증명은 아니다.

물리 Undo는 WAL과 페이지 효과의 대응, 복구 순서, 복구 자원의 가용성을
가정한다. sysop 종료 후 페이지 해제와 그 WAL·redo, 반복 중단, 보상 로그,
복수 패자 트랜잭션은 검증하지 않았다. 취소·오래된 읽기는 정해진 행과
트랜잭션 계열 및 고정 스냅샷 안에서 검사했다. 여러 원본 트랜잭션, 늦은
소비자 등록, 만료 기록 요청의 오류 경로도 남아 있다.

메모리 안전성, 실제 디스크 기록 순서, 암호화, 포맷 호환성, 도구 전체 동작,
성능과 전체 회귀 시험도 이 결과가 증명하지 않는다. 크기에 무관한 증명이
필요하면 별도 정리 증명과 구현 대응 작업이 필요하다.

기존 [일반 힙 진공 검증](verification.md)의 forward 슬롯 충돌은 별개다.
이번 재실행도 home PASS, forward MODEL FINDING, 종료값 1이었다. 새 설계의
보호 조건을 만족하는 모형이 통과해도 그 발견은 해결되지 않는다.

이 결과와 [설계](design.md), [POC 계획](poc-plan.md)을 검토한 뒤 구현을
승인하는 단계가 남아 있다. 현재 엔진 코드는 변경하지 않았다. 코드를
구현한 뒤에는 `/maintain-formal-verification-skill`로 모형의 대응을 다시
검토하고 실제 복구·HA·회귀 검증을 수행해야 한다.

## 검토와 기록

모형 설계에는 Astra와 Terra를 사용하고, 수정자는 해당 결함을 처음 검토한
에이전트와 분리했다. 두 모델은 같은 공급자 계열이다. 다른 공급자와의
독립 검토나 정리 증명으로 표현하지 않는다. [실행 절차](formal-workflow.md)와
[결정 기록](decisions.tsv)이 판단의 근거와 미완료 항목을 남긴다.

최종 판정 파일은 다음과 같다. 실행 로그와 원본 리뷰 실험은 Git에 넣지
않았다. 현재 검증 코드와 설정으로 새 실행을 재현할 수 있지만, 임시 원본
로그에 무기한 접근할 수 있다고 보장하지 않는다.

