# CBRD-27791: OOS batch read 구현·검증 계획

계획 작성 및 근거 측정: 2026-10-28, Asia/Seoul. 설명 개정: 2026-10-28, Asia/Seoul.
독자: CUBRID 개발 경험이 있지만 이번 OOS 분석을 처음 읽는 구현·검증 담당자.

## 어떤 개선을 준비하는가

OOS는 큰 컬럼 값을 행의 본체인 heap record 밖에 저장하고, 행에는 그 값을 찾아갈 참조를 남기는 방식이다.
작은 컬럼만 조회할 때는 큰 값을 읽지 않아도 되므로 유리하다. 큰 값의 내용이 필요한 조회에서는 참조를 따라 별도 페이지를 읽어야 한다.
이때 읽는 순서와 방식에 따라 조회 대기가 길어질 수 있다.

기존 엔진에서 SQL을 직접 실행해 잰 결과, 작업 파일의 OS 캐시 해제를 요청한 조건에서 큰 값 하나를 비교하는 조회는 기준 2.38초, OOS 5.72초였다.
OS 캐시는 운영체제가 파일 내용을 메모리에 보관해 다음 읽기에 재사용하는 기능이다. 이 결과를 캐시가 남아 있는 조회에 그대로 적용할 수는 없다.
입력과 조건의 상세 근거는 [분석 보고서](CBRD-27791-oos-batch-read-analysis_dcbf09e_codex.md)에 있다.

목표는 필요한 읽기 요청을 제한된 범위로 모아 처리하는 batch read로 큰 값 조회의 대기를 줄이는 것이다.
작은 컬럼만 읽을 때의 이득과 값의 정확성도 함께 유지해야 한다.
다음 작업은 수집할 수 있는 범위를 정하고, 읽는 순서를 바꾼 작은 시제품을 실제 엔진에서 검증하는 것이다.

이 문서는 그 작업 순서를 제안한다. 엔진 수정은 아직 수행하지 않았고, 최종 구현 방식과 성능·메모리 허용치는 ANALYSIS에서 결정한다.
대상은 [CBRD-27791](https://jira.cubrid.org/browse/CBRD-27791)이며,
[CBRD-26978](https://jira.cubrid.org/browse/CBRD-26978) 아래의 성능 후속 Sub-task다.
이를 [PR #7990](https://github.com/CUBRID/cubrid/pull/7990)의 병합 선행 조건으로 지정한 결정은 확인하지 못했다.
독립 성능 개선 과제로 계획하며, 통합 일정과의 관계는 담당자가 명시적으로 결정한다.

## 왜 읽는 순서부터 확인하는가

분석에서는 SQL 실행 측정과 별도로, 기록된 파일 읽기 요청만 엔진 밖에서 다시 실행했다.
이 읽기 재생 실험은 요청 순서나 묶음을 바꿀 때의 차이를 살피는 도구다.
행을 찾고 조건을 평가하는 비용, 동시성 제어, 값 복사 비용은 수행하지 않는다. 따라서 재생 시간이 줄어든 만큼 SQL도 빨라진다는 뜻은 아니다.

다음은 같은 OOS 읽기 기록을 재생한 결과다. 각 값은 3회 중앙값이다.
여기서 제한 범위인 window는 한 번에 순서를 조정하는 요청 묶음이다.
64 heap-page 모델은 heap 페이지 읽기 64개를 기준으로 기록을 나눈다. 각 묶음의 OOS 외 읽기를 원래 순서로 먼저 실행한 뒤 OOS 요청의 순서를 조정한다.

| 엔진 밖 읽기 재생 방식 | 시간 | 다음 구현에 주는 근거 |
| --- | ---: | --- |
| 원래 요청 순서 | 4.413초 | 비교 기준이다. |
| 연속해서 나타난 짧은 OOS 요청 구간만 인접 병합 | 4.409초 | 이 범위만 묶어서는 차이가 거의 없었다. |
| 64 heap-page 모델에서 주소순 정렬 | 3.449초 | 제한된 범위의 순서 변경을 실제 엔진에서 확인할 근거가 있다. |
| 같은 범위에서 정렬 후 인접 요청 병합 | 3.974초 | 요청 횟수를 줄여도 정렬만 한 경우보다 느렸다. |
| 같은 범위에서 정렬 후 gap까지 함께 읽기 | 1.965초 | 더 빨랐지만 요청 바이트가 72.4% 늘었다. |

인접 요청 병합은 주소가 바로 이어지는 요청들을 한 번의 읽기로 합치는 것이다.
gap 읽기는 떨어진 두 요청 사이의 원래 요청 목록에 없던 구간까지 함께 읽는 방식이다. 후자는 추가 I/O를 만들므로 속도와 요청량을 함께 평가해야 한다.

이 결과를 바탕으로 먼저 제한된 범위에서 읽는 순서만 바꾸어 보고, 연속 읽기를 추가할 가치는 그 뒤에 판단한다.
짧은 구간의 묶음 읽기만 확대하면 충분하다거나, 요청을 병합하면 항상 유리하다고 전제하지 않는다.

재생 도구는 각 묶음 안의 미래 주소를 기록에서 미리 안다. 실제 엔진은 행을 읽어야 OOS 참조를 얻고, 큰 값이 여러 조각이면 앞 조각을 읽어야 다음 주소를 안다.
또한 기록에 나타난 요청 수와 실제 행 수는 같지 않다. 이 차이를 포함한 비용은 실제 엔진의 시제품에서 확인해야 한다.
세부 실측과 재생 조건은 [분석 보고서](CBRD-27791-oos-batch-read-analysis_dcbf09e_codex.md),
수치는 [기계 요약](selected-summary_dcbf09e.json)에서 확인한다.

## 실제 엔진에서 비교할 두 방법

첫 번째 후보는 여러 행에서 필요한 참조를 제한된 범위로 모으고, 기존 페이지 읽기 경로를 유지하면서 읽는 순서를 바꾸는 것이다.
연속 I/O를 새로 넣기 전에 순서 변경 자체가 도움이 되는지 확인할 수 있다.
다만 모아 둔 요청이 어느 행·속성의 값인지 계속 알아야 하고, 그동안 원본 record와 결과를 담을 메모리도 유효해야 한다.
조건 평가 순서가 달라지거나 첫 결과가 늦어지는지도 확인한다.

두 번째 후보는 앞으로 읽을 페이지 주소를 페이지 버퍼에 먼저 알려 주되, 실제 값은 기존과 같이 필요한 순간에 읽는 것이다.
페이지 버퍼는 디스크 페이지를 메모리에 보관하고 동시 접근을 관리하는 층이다.
이 후보는 값을 실제로 사용할 때만 읽는 지연 평가를 유지하기 쉽고, 모든 값의 내용을 미리 보관하지 않아도 된다.
반면 사용하지 않을 페이지를 먼저 읽거나 기존의 유용한 캐시 페이지를 밀어낼 수 있다. 주소를 모으는 동안 record를 보존해야 하는 문제도 남는다.

첫 후보는 순서 변경의 효과를 직접 확인하기 좋다. 두 번째는 기존 지연 평가와 함께 사용할 수 있는지 검토하기 좋다.
최종 선택은 실제 엔진 시제품의 정확성·성능·메모리 측정으로 정한다. 두 구현을 모두 제품에 남기기로 결정한 것은 아니다.
함수별 한계와 각 층의 책임, 후보의 상세 비교는 [부록 B](#부록-b-기존-코드와-책임-분담)에 있다.

## 무엇을 어떤 순서로 할 것인가

### 1. 적용할 scan과 지켜야 할 조건을 먼저 정한다

어떤 scan에서 어떤 속성의 참조를 모을지 정한다. 한 번에 모을 행·페이지·바이트 수의 상한, 오류와 취소 처리, 요청과 결과 메모리를 누가 보관할지도 문서화한다.
현재 행에서 빌린 record나 임시 버퍼를 다음 행으로 넘어간 뒤에도 사용할 수 있다고 가정해서는 안 된다.
이 조건을 먼저 정해야 읽는 순서를 바꾸어도 정답과 오류 동작을 보존할 수 있다.

착수 시 실제 구현 시작 revision과 별도 CPU 개선의 포함 여부를 기록한다.
다음 행으로 넘어갈 때의 수명이나 필요한 값만 읽는 동작을 보존할 수 없다면 적용 대상을 줄인다.
지원하지 않는 scan·표현식은 기존의 개별 읽기 경로로 처리한다. 이를 fallback이라고 한다.
세부 조건은 [부록 C](#부록-c-정확성과-값-수명-조건)를 따른다.

### 2. 요청을 모으고 순서만 바꾸는 작은 시제품을 만든다

1단계의 범위 안에서 참조를 모으고, 각각이 원래 어느 행·속성에 속하는지 연결한다.
기존 페이지 읽기와 값 검증 경로를 재사용한다. 시제품은 기본 비활성 또는 제한된 적용으로 시작한다.
이 단계에서는 실제 수집 비용과 정답 보존을 확인한다.

상한을 넘거나 지원하지 않는 조건을 만나면 기존 경로로 돌아간다.
큰 값 하나가 바이트 상한을 넘더라도 묶음을 계속 키우지 않고 그 값을 개별 읽기로 처리한다.
같은 입력에서 정답이나 오류가 달라지면 성능 평가를 중단하고 수집 범위·수명·평가 순서를 다시 확인한다.

첫 크기 탐색에는 재생에서 사용한 요청 32/128/512개와 heap 페이지 16/64개 모델을 참고한다. 이를 제품 기본값이나 행 수 상한으로 채택한 것은 아니다.
제품에서는 행 수, 서로 다른 페이지 수, 인코딩된 값과 임시 보관 데이터의 바이트 수, 한 번의 I/O 크기, 대기 시간을 각각 제한하도록 설계한다.

### 3. 실제 SQL로 순서 변경과 선행 읽기 후보를 비교한다

2단계에서 정답이 유지되면, 기존 페이지 읽기의 순서를 바꾼 경우와 페이지 버퍼에 주소 힌트를 먼저 준 경우를 비교한다.
핵심은 실제 SQL 대기가 반복 측정의 흔들림보다 크게 줄어드는지다. 재생 실험에서 빨랐다는 사실만으로 통과시키지 않는다.

파일 캐시 해제 요청 조건의 큰 값 조회에서 차이가 반복 변동 범위 안에 있거나 작은 컬럼 조회의 이득을 훼손하면 후보를 재검토한다.
필요에 따라 1단계의 적용 범위를 줄이거나 2단계의 수집 방식을 수정한다.

### 4. 추가 가치가 확인될 때 연속 페이지 읽기를 검토한다

요청을 병합하는 별도의 이득이 3단계에서 확인되면 페이지 버퍼 안에 안전한 연속 읽기를 넣는 방안을 검토한다.
이 순서가 필요한 이유는 재생에서 인접 요청 병합이 정렬만 한 경우보다 느렸기 때문이다. 처음부터 병합을 필수 기능으로 넣지 않는다.

페이지 버퍼는 이미 메모리에 있는 페이지, 같은 페이지를 동시에 읽으려는 요청, 복구용 쓰기 버퍼와 암호화 처리도 관리한다.
새 연속 읽기는 이 동작과 부분 읽기·실패 후 결과 공개 순서를 보존해야 한다.
이를 증명하지 못하면 이 단계를 보류하고 기존 페이지 읽기 경로를 유지한다.

### 5. 선택한 후보의 정확성과 성능을 함께 검증한다

같은 입력으로 수정 전후를 비교하고, 선택한 방식이 위험하게 만드는 조건에 검증을 집중한다.
여러 조각으로 나뉜 값, 동시 UPDATE/DELETE/vacuum, 오래된 snapshot, 취소와 LIMIT, 메모리 할당 실패 등이 여기에 해당한다.
검증할 항목은 [부록 D](#부록-d-정확성-검증표)에 있다.

정확성을 통과한 뒤 성능과 메모리, 첫 결과 지연을 평가한다. 합의한 기준을 모두 충족해야 최종 적용 정책을 정할 수 있다.
실패하면 해당 후보나 적용 범위를 다시 검토한다.
새 batch의 결함과 원래 revision의 기존 결함을 구분하도록 수정하지 않은 엔진에서도 같은 집중 검증을 실행한다.

### 6. 구현 PR과 testcase를 리뷰하고 해당 커밋의 CI를 확인한다

선택한 구현과 연결된 testcase를 함께 리뷰하고, 실제 PR head 커밋을 실행한 CI 근거를 남긴다.
수정한 층에 맞게 CTest·SQL·shell·medium 검증을 선택한다. PR 정책에서 요구하는 전체 CI는 별도로 수행한다.
문서 개정이나 읽기 재생 실험이 이 단계를 대신하지 않는다.

## 어떤 결과로 판단하는가

SQL 실행 시간은 실제 엔진에서 잰 표에, 엔진 밖 읽기 재생 시간은 별도 표에 기록한다.
최종 성능 판정은 읽기 추적 도구를 붙이지 않은 SQL 실행 결과로 한다.
큰 값 하나를 비교하는 Q4를 우선 확인하면서, 작은 컬럼만 읽는 Q1과 큰 값 전체를 읽는 Q5도 유지한다.
작은 컬럼 조회가 불필요하게 큰 값을 읽게 되면 목표를 달성한 것이 아니다.

속도와 함께 요청 바이트·OS 읽기량, 최대 메모리 사용량, 실제 첫 행 또는 첫 batch가 반환되기까지의 시간을 잰다.
gap 읽기는 추가 I/O와 다른 동시 작업에 미치는 영향을 따로 검토·승인할 수 있어야 한다.
측정 조건과 수집 항목은 [부록 E](#부록-e-성능-측정-절차)에 정리한다.

최종 시간 개선율, Q1의 허용 성능 저하, 최대 메모리와 첫 결과 지연의 허용치는 TBD이며 ANALYSIS에서 합의한다.
기존 [CBRD-27785](https://jira.cubrid.org/browse/CBRD-27785)의 일반 heap CPU 2% 예산이나 진단용 1.5배 marker를 이 이슈의 합격 기준으로 가져오지 않는다.
시제품을 계속 진행할 최소 근거는 정확성 통과와 반복 변동을 넘어서는 실제 SQL 개선이다.

## 부록 B. 기존 코드와 책임 분담

현재 [`heap_oos_read_grouped_payloads`](https://github.com/CUBRID/cubrid/blob/dcbf09e4f7fd02ff9c8fc6493ec8887fc2919d67/src/storage/heap_oos.cpp#L734)는 한 record의 요청 속성만 모은다.
[`oos_read_many`](https://github.com/CUBRID/cubrid/blob/dcbf09e4f7fd02ff9c8fc6493ec8887fc2919d67/src/storage/oos_file.cpp#L2854)는 같은 첫 페이지 주소인 head VPID를 공유하는 요청의 페이지 고정을 줄인다. 여러 행을 모으거나 연속 I/O를 발행하지는 않는다.
따라서 구현은 다음 책임을 분리해야 한다.

| 담당 위치 | 책임과 호출자가 지킬 조건 |
| --- | --- |
| heap scan의 제한된 요청 수집기 | 조회 snapshot에서 보이는 record와 필요한 속성의 참조만 모은다. 원래 행·속성과의 대응, 행·페이지·바이트 상한, 다음 행으로 넘어갈 때와 취소 때의 수명을 관리한다. |
| OOS 읽기 순서 조정기 | head 참조와 호출자가 소유한 결과 버퍼를 원래 요청에 연결한다. 같은 페이지의 요청을 묶되, 아직 읽지 않은 다음 조각의 주소를 미리 안다고 가정하지 않는다. |
| 페이지 버퍼 | 캐시 재사용인 cache hit, 동시에 같은 페이지를 읽어 오는 concurrent miss, 페이지 상태 정보 BCB의 예약·공개, 복구용 DWB, 암호화 처리 TDE와 페이지 검증을 유지한다. 새 연속 읽기·선행 읽기 경로는 이 층에서 제공한다. |
| 기존 개별 읽기 경로 | 지원하지 않는 scan·표현식·메모리 조건에서는 기존 경로로 정확히 진행한다. |

어떤 행이 보이고 어떤 조건의 속성이 필요한지 아는 scanner가 수집기 후보이며, `file_io`가 행 batch를 소유하는 안은 피한다.
`FILE_OOS`는 logical file이므로 VFID 하나를 OS 파일 하나로 취급하지 않는다. 읽기 묶음은 실제 volume과 page 주소로 나눈다.

### 두 후보의 상세 비교

| 후보 | 기대 효과 | 비용과 실패 조건 | 판별 방법 |
| --- | --- | --- | --- |
| 제한된 행 묶음에서 필요한 읽기의 순서 변경 | 연속 I/O 추가 전에 순서 효과를 검증하고 기존 참조 검증·복사 경로를 재사용한다. | 여러 record와 값을 유효하게 보관해야 한다. 조건 평가 순서·메모리·첫 결과 지연을 확인한다. `oos_read_many`의 이중 순회를 큰 요청 범위에 확대할 때의 CPU 비용도 확인한다. | 제한된 읽기 전용 직렬 scan부터 적용한다. 순서만 바꾼 재생과 실제 엔진 시제품을 대조한다. |
| scan이 모은 제한된 페이지 주소 힌트를 버퍼에 먼저 전달하고 Resolve는 필요한 순간에 수행 | 지연 평가와 값 공개 순서를 유지하기 쉽다. 값 전체의 버퍼를 미리 보관하지 않아도 된다. | 선행 읽기가 유용한 캐시를 밀어내거나 불필요한 I/O를 만들 수 있다. 힌트를 모으는 동안 scan 데이터의 수명을 관리해야 한다. | 값을 요구하는 순서를 유지한 실제 엔진 시제품에서 읽기 대기·불필요 페이지·Q1·LIMIT를 잰다. 단순 정렬 재생만으로 효과를 입증하지 않는다. |

`fileio_read_pages`를 heap/OOS에서 직접 호출하는 안은 page buffer 계약을 제공하지 못하므로 후보에서 제외한다.

## 부록 C. 정확성과 값 수명 조건

- 조회 snapshot에서 보이는 heap record의 OOS 참조인 inline stub을 사용한다. 과거 버전을 읽어야 하면 undo record에 있는 stub과 그 값의 chain을 따른다.
- 해제되거나 다른 용도로 바뀐 head page는 slotted page로 해석하지 않는다. 값의 내용을 호출자에게 넘기기 전에 slot, 재사용 여부를 구별하는 identity stamp, head index와 길이를 검증한다.
- OOS page latch와 heap watcher 규칙을 보존한다. 정렬된 주소라는 이유로 여러 page latch를 잡고 기다리는 경로를 새로 만들지 않는다.
- heap `PEEK` record, 지연 평가용 attribute cache와 scratch buffer에서 빌려 쓴 참조는 다음 행으로 넘어간 뒤 보관하지 않는다. 필요한 record/stub을 복사하거나 재검증 가능한 소유권을 정한다.
- 값이 필요할 때 수행하는 정상 읽기의 복사 동작과 `DB_VALUE` 수명을 보존한다. 성공하지 않은 batch의 부분 payload를 SQL 값으로 공개하지 않는다.
- 사용하지 않는 속성의 실제 값 읽기인 Resolve를 강제하지 않는다. 조건 평가가 이미 끝나 나머지를 건너뛰는 short-circuit, 오류 발생 시점, LIMIT와 취소 동작도 확인한다.
- 모든 영구 page 접근은 page buffer 계약을 따른다. raw `pread` 실험을 엔진의 storage 접근으로 옮기지 않는다.

## 부록 D. 정확성 검증표

| 영역 | 집중 확인 항목 |
| --- | --- |
| 값과 요청의 대응 | OOS 속성 0개·1개·다중, 같은 페이지의 다른 slot, 서로 다른 페이지·volume, NULL과 행 내부 값의 혼합, 중복 참조를 확인한다. 요청 순서를 바꾸어도 원래 결과 버퍼에 올바른 값을 넣어야 한다. |
| 여러 조각으로 나뉜 값인 multi-chunk | head를 읽은 뒤에야 다음 주소를 알 수 있는 진행 단계, 서로 다른 chain 길이, 잘못된 index·길이, 부족하거나 초과한 payload를 확인한다. 실패 후 일부 결과를 공개하지 않아야 한다. |
| 참조 검증과 동시성 | 해제되거나 용도가 바뀐 페이지, 비거나 재사용된 slot, stamp 불일치를 확인한다. 동시 UPDATE/DELETE/vacuum, 오래된 snapshot·undo record, batch 도중 scan 재시도도 검증한다. |
| 수명과 자원 | heap 페이지 고정 해제, 다음 행으로 이동, attribute cache 재사용 후에도 값이 유지되어야 한다. 메모리 할당 실패, interrupt/cancel, 조기 종료·LIMIT를 확인하고 latch/pin 누수가 없어야 한다. |
| 지연 평가 | 작은 컬럼만 읽는 Q1에서 OOS Resolve가 없어야 한다. short-circuit으로 건너뛸 값의 오류를 미리 발생시키지 않아야 한다. 조건을 통과하는 행이 적을 때의 불필요한 읽기도 확인한다. |
| 페이지 버퍼 확장 시 | cache hit나 메모리에서 변경된 dirty page를 디스크 내용으로 덮어쓰지 않아야 한다. 동시 miss, DWB, TDE, volume 경계·EOF·부분 읽기·I/O 오류를 확인한다. |

수정하지 않은 엔진에서도 같은 집중 대조를 실행해 기존 결함과 새 batch의 결함을 구분한다.
알려진 OOS 소유권·vacuum 미완료 사항은 별도 이슈로 구분하며, batch가 그 결함을 해결했다고 주장하지 않는다.

## 부록 E. 성능 측정 절차

실제 엔진 시제품은 같은 source 계열의 독립 설치·DB로 비교한다.
저장 형식이 달라지면 DB를 새로 만들고 기존 측정 자료를 보존한다.

1. 우선 재현된 overflow Q4를 작업 파일 캐시 해제 요청 조건에서 비교한다. 일반 heap 입력의 Q4, 전체 큰 값을 읽는 Q5와 작은 컬럼만 읽는 Q1도 유지한다.
2. 단순 DB 재시작인 restart-only, 같은 SQL을 먼저 실행한 뒤 재는 warm, 작업 파일의 OS 캐시 해제 요청 조건을 각각 기록한다. 재시작만으로 OS 캐시가 비워지지는 않는다. 전역 캐시 해제를 사용하지 않고, 작업 전용의 정지한 volume에만 해제를 요청한 뒤 캐시에 남은 상태인 residency를 기록한다.
3. 작은 값·큰 값, 단일·다중 속성, 단일 조각·multi-chunk, DB 버퍼 안·밖, 조건 선택도와 LIMIT를 설계 위험에 맞춰 추가한다. 모든 경우를 전수 조합하지 않는다.
4. 엔진 실행 순서를 교대하고, 사전 실행인 warmup과 반복 수, 다른 작업의 간섭을 기록한다. 최종 합격 판단은 추적 도구를 붙이지 않은 SQL 실행으로 한다.
5. 전체 경과 시간인 wall, CPU 시간과 instructions, 엔진의 fetch/ioread, OS read_bytes, 요청 바이트와 추가 읽기, 최대 메모리인 peak memory, 실제 첫 행 또는 첫 batch 반환 시간을 수집한다.

SQL 실행과 엔진 밖 재생은 별도 표로 남긴다. 재생 도구가 측정한 첫 묶음의 I/O 시간은 실제 SQL 첫 결과 지연을 대신하지 않는다.
성능·메모리·첫 결과 지연의 최종 허용치는 ANALYSIS에서 합의하며, 추가 I/O가 생기는 gap 읽기는 동시 작업의 영향까지 함께 판단한다.
