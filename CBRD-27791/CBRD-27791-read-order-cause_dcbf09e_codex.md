# CBRD-27791: 읽기 순서를 바꾸면 왜 빨라지는가

2026-10-28, Asia/Seoul. OOS와 이번 실험을 처음 접하는 개발자를 위한 설명이다.

이번에 알아보려 한 것은 **“읽어야 할 데이터가 같아도, 가져오는 순서를 바꾸면 더 빨리 끝날까?”**였다.

실험에서는 문서의 기본정보와 큰 본문을 번갈아 읽는 대신, **기본정보를 먼저 읽고 본문을 모아서 읽는 쪽이 빨랐다.** 본문끼리 저장 위치순으로 정렬하는 것은 그다음의 작은 추가 이득이었다.

실험에는 기존 SQL이 파일의 어디를 어떤 순서로 읽었는지 기록한 목록을 사용했다. 별도 프로그램으로 같은 곳들을 다시 읽으면서 순서만 바꿨다. 아래 시간은 이 프로그램의 파일 읽기 시간이다. 실제 CUBRID에 새 방법을 구현했을 때의 SQL 속도는 아직 확인하지 않았다.

먼저 문서 세 개를 읽는 예시로 순서 변경이 무엇을 뜻하는지 설명하고, 그다음에 결과와 근거를 살펴본다. 상세 측정 수치와 재현 명령은 뒤쪽 부록에 모았다.

## 큰 본문을 읽으려면 무엇을 가져와야 하는가

문서 테이블에 문서 번호와 큰 본문이 있다고 하자. OOS는 큰 본문을 행 밖에 따로 저장하고, 행에는 본문을 찾을 위치 정보를 남기는 방식이다. 행의 기본 부분을 담는 저장 공간을 **heap**, 따로 저장한 큰 본문을 **OOS 값**이라고 부른다.

문서 번호만 필요한 조회는 큰 본문을 가져오지 않아도 된다. 반면 본문의 내용을 비교하거나 집계하려면, 행을 읽어 본문 위치를 알아낸 뒤 실제 본문도 가져와야 한다.

다음은 문서 세 개의 본문이 모두 필요한 경우다. 파일을 일정 크기로 나눠 읽는 단위를 **페이지**라고 한다. 아래 페이지 번호는 같은 파일 안의 본문 위치를 가리키는 설명용 숫자다.

| 문서 | 행에서 알아낸 본문 위치 |
| --- | --- |
| 문서 1 | 103번 페이지 |
| 문서 2 | 101번 페이지 |
| 문서 3 | 102번 페이지 |

데이터를 파일에서 가져와야 한다면, 어떤 순서로 읽을 수 있을까?

## 세 가지 순서를 비교했다

**첫 번째는 한 문서씩 처리하는 방식이다.** 행에서 본문 위치를 알아내면 바로 그 본문을 가져온다. 다음 문서에서도 같은 일을 반복한다.

```text
문서 1 기본정보 → 본문 103
문서 2 기본정보 → 본문 101
문서 3 기본정보 → 본문 102
```

**두 번째는 기본정보를 먼저 모으는 방식이다.** 먼저 몇 개 행을 읽어 본문 위치를 모아둔다. 본문을 가져오는 일은 그 뒤로 미룬다.

```text
문서 1·2·3의 기본정보를 먼저 읽기
→ 본문 103 → 본문 101 → 본문 102
```

여기서는 본문끼리 읽는 순서는 그대로다. 바뀐 것은 기본정보와 본문을 번갈아 읽던 순서다.

**세 번째는 본문끼리 정렬까지 하는 방식이다.** 두 번째와 같이 기본정보를 먼저 읽되, 본문은 파일 위치순으로 가져온다.

```text
문서 1·2·3의 기본정보를 먼저 읽기
→ 본문 101 → 본문 102 → 본문 103
```

이렇게 비교하면 “기본정보를 먼저 읽은 효과”와 “본문끼리 정렬한 추가 효과”를 구분할 수 있다. 세 방법 모두 프로그램이 요청하는 파일 위치, 횟수와 데이터 크기를 같게 맞췄다. 한 번에 모을 범위는 제한했다. 위의 세 문서는 개념을 설명하는 예시이며, 실제 묶음 기준은 부록에 적었다.

여러 행에 필요한 읽기를 모아 처리하려는 아이디어를 이 보고서에서는 **batch read**라고 부른다.

## 대부분의 시간 단축은 기본정보를 먼저 읽었을 때 생겼다

실제 측정에는 100,000행의 큰 컬럼 값을 비교하던 SQL의 읽기 기록을 사용했다. 먼저 같은 기본 설정에서 세 방법을 비교했다. 아래는 각 방법을 6회 측정한 대표값인 중앙값이다.

| 읽는 방법 | 파일 읽기를 마치는 데 걸린 시간 |
| --- | ---: |
| 한 문서씩 기본정보와 본문을 번갈아 읽기 | 4.362초 |
| 기본정보를 먼저 읽고, 본문은 원래 순서로 읽기 | 3.465초 |
| 기본정보를 먼저 읽고, 본문은 파일 위치순으로 읽기 | 3.408초 |

기본정보를 먼저 읽는 것만으로 약 **0.90초** 줄었다. 본문끼리 정렬을 더했을 때는 약 **0.06초**가 더 줄었다.

따라서 이번 결과에서 먼저 주목할 변화는 **본문을 정렬한 것보다, 기본정보와 본문을 번갈아 읽지 않도록 한 것**이다. 전체 약 22%의 시간 단축을 본문 정렬만의 효과로 설명하면 두 변경을 섞어 해석하게 된다.

## 왜 더 빨리 끝났는가

### 필요한 본문이 메모리에 미리 준비된 경우가 늘었다

운영체제는 파일에서 읽은 내용을 메모리에 보관할 수 있다. 이를 **OS 캐시**라고 한다. 필요한 내용이 이미 여기에 있으면 저장 장치에서 새로 읽어오는 대기를 피할 수 있다.

운영체제는 앞으로 필요할 것 같은 파일 내용을 프로그램의 요청보다 먼저 읽어두기도 한다. 이것이 **미리 읽기**다. 읽는 순서가 달라지면 미리 읽기가 준비해 두는 내용도 달라질 수 있다.

이를 확인하려고 본문을 읽기 직전에 해당 페이지가 메모리에 있는지 관측했다. 기본정보와 본문을 번갈아 읽을 때는 본문 읽기 요청의 **33.5%**, 기본정보를 먼저 읽을 때는 **51.8%**에서 필요한 페이지가 이미 메모리에 있었다.

비율을 본문 읽기 요청 100개로 환산하면, 미리 준비된 요청이 약 33~34개에서 약 51~52개로 늘어난 셈이다. 그만큼 실제로 필요해진 순간에 저장 장치에서 새로 가져오기를 기다리는 경우가 줄어들 수 있다.

이 해석을 뒷받침하는 확인도 했다.

- 소유한 테스트 파일에 일반 사용자 권한으로 캐시 해제를 요청하고, 실제로 0B인지 확인한 뒤 시작했다.
- 한 실행에서 같은 페이지를 다시 요청하지 않았다.
- 미리 읽기를 끄면, 관측한 표본에서 읽기 직전의 캐시 적중이 모두 0%가 됐다.

따라서 반복해서 같은 페이지를 읽어서 생긴 적중과 구분할 수 있었다. **운영체제가 필요한 본문을 먼저 준비하는 동작이 실제로 있었고, 기본정보를 먼저 읽는 순서에서 그 도움을 더 많이 받았다**는 근거다.

### OS 캐시를 쓰지 않아도 일부 이득은 남았다

미리 읽기만으로 전체 시간 차이를 설명할 수 있는지도 확인했다. 이번에는 OS 파일 캐시를 우회하는 **직접 I/O** 방식으로 같은 요청을 읽었다.

이 조건에서도 기본정보와 본문을 번갈아 읽으면 **6.672초**, 기본정보를 먼저 읽으면 **6.044초**였다. 요청 하나하나의 완료 시간을 따로 재보니, 주로 기본정보를 읽는 요청이 빨라졌고 본문을 읽는 요청의 평균은 거의 같았다.

즉, 미리 읽기의 도움 외에도 OS 캐시를 사용하지 않는 읽기 경로에서 차이가 남았다. 다만 저장 장치 내부의 캐시나 다른 내부 동작 중 무엇이 그 차이를 만들었는지는 아직 구분하지 못했다.

### 읽는 양이 줄어든 결과는 아니었다

프로그램이 요청한 데이터는 같게 맞췄지만, 운영체제가 추가로 미리 읽은 양은 달랐다. 기본정보를 먼저 읽은 방식은 실제 저장 계층에서 더 많은 데이터를 가져왔는데도 빨리 끝났다.

따라서 이번 결과에서는 읽는 양과 함께 **필요한 순간에 데이터가 준비돼 있는지**, **요청이 끝나기까지 얼마나 기다리는지**를 봐야 한다. 단순히 적게 읽는 것만으로 속도를 설명할 수는 없었다.

## 이 결과로 무엇을 결정할 수 있는가

이번 실험은 **기본정보와 큰 본문을 번갈아 읽는 순서를 바꾸어 볼 근거**를 보탰다. 본문 정렬만 복잡하게 만드는 것보다, 여러 행의 읽기를 일정 범위로 모으는 방법을 먼저 검증할 이유가 생겼다.

아직 실제 SQL도 같은 비율로 빨라진다고 결론 내릴 수는 없다. 실험 프로그램은 이미 기록된 읽기 위치 목록을 사용했다. 실제 DB는 행을 읽으면서 본문 위치를 알아내므로, 여러 행의 정보를 모아 보관하는 시간과 메모리가 추가로 필요하다. 다른 사용자가 행을 수정하는 중에도 올바른 값을 읽어야 한다.

또 다른 데이터 배치나 저장 장치에서도 같은 결과가 나오는지는 확인해야 한다. 평균 시간이 줄었어도 일부 느린 요청의 지연은 늘어났다. 모든 조회나 모든 읽기가 빨라진다는 의미로 넓힐 수 없다.

다음 단계는 작은 엔진 시제품으로 이 추가 비용과 정확성을 포함해 실제 SQL 시간을 비교하는 것이다. 관련 후보와 검증 순서는 [구현·검증 계획](CBRD-27791-oos-batch-read-plan_dcbf09e_codex.md)에 있다.

## 부록: 측정값과 재현 방법

이하 내용은 수치를 대조하거나 실험을 재현할 때 사용하는 상세 기록이다.

측정·분석일과 설명 개정일: 2026-10-28, Asia/Seoul. 기존 측정은 Work Item 541에서 수행했으며 이번 개정에서 실험을 다시 실행하지 않았다. 대상은 OOS `dcbf09e4f7fd02ff9c8fc6493ec8887fc2919d67`로 만든 전용 DB와 그 SQL 실행의 읽기 기록이다. 앞선 [분석 보고서](CBRD-27791-oos-batch-read-analysis_dcbf09e_codex.md)의 실제 SQL 결과는 그 당시 revision과 조건의 결과로 유지한다.

부록의 A는 한 문서씩 읽는 원래 순서, B는 기본정보를 먼저 읽는 순서, C는 B에 본문 정렬을 더한 순서다. 실험의 묶음은 heap 페이지 읽기 64회를 기준으로 나눴으며 실제 행 64개를 뜻하지 않는다. B에서는 각 묶음의 OOS 이외 요청을 먼저 읽고 OOS 요청은 원래 순서대로 읽었다. C는 B와 같되 OOS 요청끼리 파일 위치순으로 정렬했다.

모든 방법에서 요청한 파일 위치, 횟수, 바이트 수와 페이지별 중복 횟수는 같았다. 요청을 합치거나 원래 없던 구간을 추가로 읽지 않았다. B에서는 OOS 요청만 뽑아 나열한 순서가 A와 완전히 같은지도 검사했다.

### 72회 비교 결과

C 도구로 각 조건·방법을 6회씩, 총 72회 직렬 실행했다. 조건의 실행 순서를 회전하고 세 방법의 순서 여섯 가지를 모두 사용했다. 아래는 6회 중앙값이다.

| 캐시·읽기 조건 | A. 원래 순서 | B. 읽기 분리 | C. 분리 후 정렬 |
| --- | ---: | ---: | ---: |
| 파일 캐시 해제 후 기본 미리 읽기 | 4.362초 | 3.465초 | 3.408초 |
| 파일 캐시 해제 후 미리 읽기 끄기 | 7.070초 | 6.436초 | 6.378초 |
| 파일 캐시 해제 후 직접 I/O | 6.672초 | 6.044초 | 5.964초 |
| 같은 요청을 먼저 읽어 캐시에 올린 뒤 실행 | 0.345초 | 0.345초 | 0.342초 |

기본 조건에서 A→B는 약 20.6%, B→C는 추가 약 1.6% 짧아졌다. A→C 전체 시간 차이의 약 94%가 B까지의 단계에서 나타났다. 이는 이번 입력에서 두 변경을 이 순서로 누적 비교한 결과이며, 일반적인 기여율이나 제품의 예상 개선율은 아니다.

기본 조건의 6회 범위는 A 4.348~4.367초, B 3.455~3.474초, C 3.397~3.424초였다. 반복별 수치와 다른 조건의 범위는 [선별 측정 요약](read-order-cause-summary_dcbf09e.json)에 보존했다.

### OS 캐시에 미리 들어온 큰 값이 늘었다

페이지를 읽기 직전에 `mincore`로 그 내용이 메모리에 있는지 확인했다. heap 요청 2,083개와 OOS 요청 6,250개를 종류별로 무작위 추출하고, 모든 방법에서 같은 주소를 관측했다. seed는 27791이다. 각 요청은 16KiB이며, 아래 적중은 해당 요청의 OS 페이지 네 개가 모두 메모리에 있는 경우다.

| 조건·방법 | heap 요청의 읽기 직전 적중률 | OOS 요청의 읽기 직전 적중률 |
| --- | ---: | ---: |
| 기본 미리 읽기, A | 98.0% | 33.5% |
| 기본 미리 읽기, B | 97.9% | 51.8% |
| 기본 미리 읽기, C | 97.9% | 51.7% |
| 미리 읽기 끄기, A·B·C 각각 | 0% | 0% |

기본 조건은 방법별 3회 관측의 중앙값, 미리 읽기 끄기는 방법별 1회 관측이다. 계측한 실행의 시간은 앞의 성능 표에 섞지 않았다. `mincore` 값은 호출 시점의 스냅샷이므로 읽기 직후까지 같은 상태를 보장하지 않는다. [Linux mincore 설명](https://man7.org/linux/man-pages/man2/mincore.2.html)

모든 관측은 파일 캐시가 0B인 상태에서 시작했고, 이 기록의 페이지는 각각 한 번만 요청한다. 따라서 앞선 동일 페이지의 명시적 읽기가 적중률을 만든 경우는 없다. 기본 조건에서는 처음 요청하는 페이지의 일부가 이미 캐시에 있었고, 미리 읽기를 끄면 표본의 캐시 적중이 모두 0이 됐다. 이 대조는 **미리 읽기가 실제로 필요한 큰 값을 먼저 캐시에 채웠으며, 읽기 분리 후 그 기회를 더 많이 활용했다**는 근거다.

heap의 적중률은 A에서도 이미 높았다. 관측한 큰 변화는 OOS 요청의 적중률이었다. 별도 C 성능 측정에서도 자발적 context switch 횟수의 중앙값이 A 67,892회에서 B 49,381회로 줄어, 읽기 중 대기가 줄었다는 관측과 방향이 맞았다.

미리 읽기는 뒤에 필요한 데이터를 OS 캐시에 먼저 채울 수 있는 기능이다. `POSIX_FADV_RANDOM`은 Linux에서 파일 미리 읽기를 끈다. 이번 대조는 같은 파일 요청을 유지하고 이 동작을 켜거나 끈 것이다. [미리 읽기 설명](https://man7.org/linux/man-pages/man2/readahead.2.html), [파일별 advice 설명](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html)

### OS 캐시를 우회해도 heap 읽기의 완료 시간이 줄었다

직접 I/O는 `O_DIRECT`로 실행했다. 각 실행에서 OS 파일 캐시는 시작 전과 읽기 후 모두 0B였고, 저장 계층 읽기량은 요청 바이트 수와 같은 2,184,658,944B였다. 이 조건에서도 A→B가 약 9.4% 짧아져, OS 미리 읽기 하나로 전체 효과를 설명할 수 없다. [O_DIRECT 설명](https://man7.org/linux/man-pages/man2/open.2.html)

어느 요청에서 차이가 생겼는지 보기 위해 별도 실행에서 각 `pread`의 완료 시간을 쟀다. 방법별 2회 관측을 평균했다.

| 직접 I/O 방법 | heap 요청 평균 완료 시간 | OOS 요청 평균 완료 시간 |
| --- | ---: | ---: |
| A. 원래 순서 | 49.3µs | 50.4µs |
| B. 읽기 분리 | 30.3µs | 50.5µs |
| C. 분리 후 정렬 | 30.1µs | 49.8µs |

직접 I/O에서 A→B의 차이는 주로 heap 요청에서 나타났다. heap 요청 33,339회의 합계가 약 1.64초에서 1.01초로 줄었고, OOS 요청 100,000회의 합계는 약 5.04~5.06초로 비슷했다. C에서 OOS 정렬을 더한 이득은 이보다 작았다.

B·C의 전체 요청 목록에는 바로 이어지는 파일 위치를 읽는 쌍이 32,818개 생겼다. A에는 4개였다. B에서는 이 변화가 heap 읽기를 모으는 것만으로 생겼다. 이 주소 순서 대조와 호출 시간은 **heap을 이어 읽을 때 OS 캐시 아래 읽기 경로에서도 완료 시간이 달라진다**는 근거다. 여기서 측정한 것은 파일 시스템·커널·장치를 거친 `pread` 전체 호출 시간이다. 저장 장치 내부 캐시, 펌웨어, NAND 접근 각각의 기여는 분리하지 못했다.

평균이 줄어도 모든 호출이 빨라진 것은 아니다. 직접 I/O heap 호출의 p95는 A 약 52µs에서 B 약 79µs로 늘었다. 평균 개선과 긴 대기의 변화는 별도로 평가해야 한다.

### 더 적게 읽어서 얻은 개선은 아니다

모든 방법이 요청한 양은 2,083.45MiB다. 기본 조건의 프로세스 `read_bytes`는 A 2,793.11MiB, B·C 2,946.63MiB였다. B·C는 저장 계층에서 약 153.52MiB를 더 읽고도 빨리 끝났다. 미리 읽기를 끈 조건과 직접 I/O에서는 세 방법 모두 2,083.45MiB였고, warm 측정에서는 모두 0B였다. 이 지표는 저장 계층에서 가져온 바이트를 뜻한다. 장치 내부 캐시의 적중 여부까지 알려주지는 않는다. [프로세스 I/O 지표 설명](https://man7.org/linux/man-pages/man5/proc_pid_io.5.html)

따라서 batch 후보를 평가할 때 요청 바이트 수, 실제 저장 계층 읽기량, 완료 시간과 대기를 함께 봐야 한다. 이번 결과에서 “읽는 양이 적다”와 “빨리 끝난다”는 같은 판정이 아니었다.

서로 다른 조건의 시간 차이를 단순히 빼서 미리 읽기와 장치의 기여율로 계산하지 않았다. 각 조건은 읽기 경로 자체를 바꾸므로 효과가 독립적으로 더해진다고 가정할 수 없다. 파일 안의 위치만 제어했으며 NVMe의 물리 위치는 측정하지 않았다.

### 재현 조건과 방법

원래 CUBRID 실행 환경은 보존했다. 이번에는 서버를 시작하거나 엔진을 수정·빌드하지 않고, 정지한 전용 DB의 읽기 기록만 사용했다.

| 항목 | 이번 실험의 조건 |
| --- | --- |
| 입력 | 기존 Q4의 OOS trace 133,341개 요청: heap 33,339개, OOS 100,000개, 기타 2개. 각 요청 16KiB, 페이지 중복 없음 |
| 호스트 | Linux 5.14.0-570.30.1.el9_6, XFS/LVM, Samsung SSD 990 PRO 4TB |
| 읽기 도구 | GCC 11.5.0, C11/O2. 직렬 `pread`, CPU 16 고정. 한 번에 애플리케이션 요청 하나를 실행 |
| 미리 읽기 | NVMe와 LVM 큐의 `read_ahead_kb=4096`. 값을 변경하지 않고 NORMAL/RANDOM advice를 파일별로 적용 |
| 파일 캐시 | 매번 전용 데이터 파일 13개에 `fsync`와 `POSIX_FADV_DONTNEED`를 적용한 뒤 `fincore` 합계 0B를 요구. warm은 이 절차 뒤 같은 요청을 먼저 실행 |
| 직접 I/O | 4KiB 정렬 버퍼와 16KiB 정렬 요청. 실패 시 buffered I/O로 바꾸지 않고 실행을 중단 |
| 보존 확인 | manifest의 장치·inode·크기·소유권, 설치의 실행 프로세스 유무 검사. 실험 전후 선택 데이터 내용 hash 일치, 파일 크기·mtime·ctime 불변 |

기존 Python 재생도 순서를 번갈아 4회씩 실행해 원래 4.416초, 기존 heap64 방식 3.449초를 재현했다. C 도구에서도 같은 차이가 남았고, warm에서는 세 방법의 차이가 수 ms 수준이었다. Python 처리량 차이가 큰 시간 차이의 주원인이라는 설명은 이 대조와 맞지 않는다.

입력의 물리 배치가 실험 대상이므로 이번에는 DB를 줄이거나 다시 적재하지 않았다. 대신 같은 요청 목록을 유지한 채 순서·미리 읽기·캐시 경로를 각각 바꿨다. 실제 SQL 정확성, 엔진 batch 구현, CTest·SQL·shell·medium 회귀와 PR CI를 수행한 결과로 해석하지 않는다.

이 디렉터리의 도구를 사용한다. 아래 `manifest_file`은 해당 호스트의 정지한 전용 fixture를 검증할 수 있는 manifest로 지정한다. 형식과 준비 조건은 기존 분석의 [재현 절차](CBRD-27791-oos-batch-read-analysis_dcbf09e_codex.md#부록-f-재현-절차와-보존한-근거)에 있다. 다른 호스트에 원래 파일 경로·inode를 그대로 옮겨 사용할 수는 없다.

```sh
manifest_file=/path/to/stopped-fixture-manifest.json
artifact_root="$(mktemp -d /tmp/oos-read-order-XXXXXX)"
cc -std=c11 -O2 -Wall -Wextra -Werror read_order_probe.c -o "$artifact_root/probe"
python3 -B run_read_order_matrix.py --manifest "$manifest_file" \
  --output "$artifact_root/matrix" --probe "$artifact_root/probe" --repeats 6 --cpu 16
python3 -B read_order_cache_probe.py --manifest "$manifest_file" \
  --output "$artifact_root/cache-normal-defer" --mode normal --schedule defer
```

각 방법의 캐시 관측은 `--schedule captured|defer|sorted`로, 미리 읽기 끄기는 `--mode random`으로 비교한다. 개별 호출 시간은 `read_order_experiment.py`의 같은 입력에 `--mode direct --schedule <방법> --instrument`를 지정해 얻는다. 출력의 `durations.bin`은 해당 순서의 호출별 little-endian uint64 nanoseconds다.

이번 원시 근거는 다음 위치에 보존했다. 기존 실험의 산출물을 덮어쓰지 않았다.

```text
/mnt/nvme/data-5/tmp/CBRD-27791-order-cause-20261028-anh840mu
```

주요 결과는 `matrix-1/`, 최종 무작위 캐시 표본은 `cache-v2-*/`, 호출 시간은 `latency-*/`에 있다. 초기 주소 주기 표본인 `cache-r*/`는 최종 적중률 표의 근거에서 제외하고 원시 기록으로 보존했다. 선택 데이터의 실험 전후 SHA-256은 모두 `e3be9a3a58bfb2b25b69439d141f4ad501bc2a7a257841b92b14f38495d00c53`였다.

### 보존한 산출물과 확인

- [선별 측정 요약](read-order-cause-summary_dcbf09e.json): 72회 시간, 조건별 통계, 캐시 표본과 직접 I/O 관측, 입력·도구 hash. 보고서 수치를 독립적으로 대조하기 위해 보존한다.
- [C 읽기 도구](read_order_probe.c), [개별 실행·검증 도구](read_order_experiment.py), [균형 순서 실행 도구](run_read_order_matrix.py), [캐시 관측 도구](read_order_cache_probe.py): 같은 요청·조건 대조를 재현하기 위한 소스다. 실행 파일과 원시 로그는 Git에 넣지 않는다.

C 빌드는 `-Wall -Wextra -Werror`를 통과했다. 요청이 파일 범위를 벗어나거나 writable descriptor가 전달되면 읽기 전에 거부하는 것을 확인했다. 작은 입력으로 묶음 경계와 B의 OOS 순서 보존, C의 정렬 및 중복 횟수를 검사했다. 전후 내용 hash와 파일 식별 정보 검사도 통과했다.

관련 이슈는 [CBRD-27791](https://jira.cubrid.org/browse/CBRD-27791)이고, 기존 OOS 변경은 [PR #7990](https://github.com/CUBRID/cubrid/pull/7990)과 관련된다. 이번 실험은 그 구현을 변경하지 않았다.
