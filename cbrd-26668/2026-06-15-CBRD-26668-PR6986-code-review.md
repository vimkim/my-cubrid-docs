## Verdict: Request changes — not merge-ready

Beyond the author-acknowledged "REVERT BEFORE MERGE" instrumentation, this review finds **two independent real defects that would survive a clean-up of the temp code**:

1. **Silent data loss (critical):** the forward-walk idempotency probe `oos_chunk_exists()` is identity-blind; block re-processing + OOS slot reuse can make vacuum delete a **live row's** OOS chunk.
2. **TDE data-at-rest regression (high, confirmed):** the new log tag is missing from `LOG_MAY_CONTAIN_USER_DATA`, so deleted-row column values are written to the WAL **unencrypted** on TDE tablespaces.

And one **confirmed concurrency hazard**:

3. **Latch-ordering inversion (high):** `heap_oos_find_vfid()` fixes the heap header page **unconditionally while heap data pages are write-latched** — an AB/BA deadlock against the normal header→data insert path. CUBRID's own `heap_ovf_find_vfid` / REC_BIGONE path use a conditional-latch + retry exactly to avoid this; the new OOS sites skip it.

## 1 🔴 Retry + slot-reuse forward-walk data loss
`vacuum_oos.cpp` (`vacuum_forward_walk_oos_delete_atomic`) / `oos_file.cpp:1779`

Three links, all confirmed in code (verdict: PLAUSIBLE only because the trigger needs a timing window — crash recovery widens it arbitrarily):

- **Block re-processing.** Each forward-walk delete commits its *own* sysop per record (`vacuum_oos.cpp:171-197`). `data->start_lsa` is never advanced mid-block (explicit `TODO`, `vacuum.c:3754`); the block returns to AVAILABLE and is re-walked on worker interrupt/shutdown, on any mid-block error, or on crash-recovery re-arm (`vacuum_data_load_and_recover`, `vacuum.c:4385`). Already-committed deletes survive; the **immutable** undo image still lists the OLD head OID.
- **Slot reuse.** OOS pages are `ANCHORED` (`oos_file.cpp:1630`); on delete `spage_delete` marks the slot `REC_DELETED_WILL_REUSE`, and `oos_stats_update` re-registers the freed page in bestspace (`oos_file.cpp:1753`), so the next `oos_insert` for a *different live row* can reclaim the exact `(volid,pageid,slotid)`.
- **Identity-blind probe.** `oos_chunk_exists` returns `*out_exists = true` for *any* record at the slot (`oos_file.cpp:1807`); `oos_record_header` (`oos_file.hpp:26`) has no owner-OID / generation field, so it cannot tell "still my chunk" from "reused by another row".

**Failure:** pass 1 deletes old chunk `V|P|S`; the slot is reused by a live row's new chunk; the re-walked block sees `exists==true` and `oos_delete(V|P|S)` destroys the live row's data. The eager non-MVCC path already defends this exact aliasing with an old-vs-new OID set diff (`heap_oos_delete_unreferenced`); the vacuum path has no equivalent.

**Fix:** add an owner/generation stamp to the OOS chunk header and make the probe identity-aware before `oos_delete`; or carry the expected identity into `oos_delete` and no-op on mismatch.

## 2 🔴 Multi-chunk chain amplification
`oos_file.cpp:1696,1779` — `oos_chunk_exists` probes only the chain **head**; `oos_delete`→`oos_delete_chain` then follows `next_chunk_oid` out of whatever header now occupies the reused slot. If the head was reused by a live multi-chunk record, the **entire foreign chain** is deleted. Same root cause as #1, larger blast radius.

## 3 🟠 TDE plaintext user data in WAL (CONFIRMED)
`src/storage/tde.h:107` — `LOG_MAY_CONTAIN_USER_DATA` lists `RVHF_DELETE` (line 109) and `RVHF_UPDATE_NOTIFY_VACUUM` (line 113) but **not** `RVHF_DELETE_NEWHOME_NOTIFY_VACUUM` (136). `log_append_undoredo_crumbs` gates TDE encryption on this macro (`log_manager.c:2310-2319`): a rcvindex absent from it skips `prior_set_tde_encrypted` even on a TDE page. `heap_update_relocation`'s remove_old_forward now tags the forward delete (undo image = full REC_NEWHOME body) with the new value, so on a TDE tablespace the deleted row's column values are logged in cleartext. **Regression** — pre-PR this path hardcoded `RVHF_DELETE`, which *is* in the macro.
**Fix:** `|| (rcvindex) == RVHF_DELETE_NEWHOME_NOTIFY_VACUUM` in the macro.

## 4 🟠 Latch-ordering inversion in `heap_oos_find_vfid` (CONFIRMED)
`heap_file.c:12177` fixes the heap **header** page with `PGBUF_UNCONDITIONAL_LATCH` (mode WRITE when `docreate`, else READ), and the signature offers no conditional-latch parameter. It is called while heap **data** pages are write-latched, from:
- 4 eager sites (`heap_file.c:22770 / 23116 / 23550 / 24037`, home/forward W-latched) — and `heap_oos_delete_unreferenced` runs server-side too (the `!is_mvcc_op` gate fires for MVCC-disabled catalog classes, per its own comment), and
- 2 vacuum sites (`vacuum.c:2086 / 2202`, home/forward W-latched).

CUBRID ranks the header **before** data pages (`PGBUF_ORDERED_HEAP_HDR` < `PGBUF_ORDERED_HEAP_NORMAL`); the insert path `heap_stats_find_best_page` fixes header-then-data (`heap_file.c:3582`). Holding a data page then unconditionally waiting on the header inverts that order → concrete AB/BA cycle: an inserter holds the header and waits for data page X while an OOS-delete/vacuum thread holds data page X and waits for the header. The sibling `heap_ovf_find_vfid` takes a `PGBUF_LATCH_CONDITION` param, and the **REC_BIGONE branch in the same `vacuum_heap_prepare_record`** (`vacuum.c:2106-2135`) does conditional-latch → release home → retry. The new OOS sites skip this.
**Fix:** give `heap_oos_find_vfid` a conditional-latch parameter and apply the release-and-retry pattern the REC_BIGONE / overflow paths already use. See the companion caveat doc for the full deadlock walk-through.

## 5–10 🟠/🟡 Seven `abort()` "REVERT BEFORE MERGE" sites
Live in NDEBUG paths: `vacuum_oos.cpp:315,372`; `vacuum.c:1581,2326,2569`; `heap_file.c:21321,21540` (8 "remove before merge" markers). Author-acknowledged temporary, but three points make them more than benign:
- **#5/#6 (`heap_file.c`)** run on the **foreground user INSERT/UPDATE** path — a single OOS+big-length row crashes the server for all clients (remote DoS) in release.
- **#7 (`vacuum.c:1581`)** *replaced* the prior `er_clear(); error_code = NO_ERROR; continue;`. The design doc §8-1 claims the fix here is `page_ptr = obj_ptr; continue;` (the spin-loop cure) — **that code is not present at HEAD**. Removing the abort() without adding `page_ptr = obj_ptr` reintroduces the release CPU-spin regression.
- **#8 (`vacuum_oos.cpp:372`)** the `abort()` makes `assert_release(false); er_clear(); VFID_SET_NULL; return NO_ERROR;` below it dead code and contradicts the function's "never return error, bounded logged leak" contract (§7-7). Same contract violation at **#9 (`:315`)**.
- **#10** REC_BIGONE+OOS aborts in both builds where `assert_release`-and-continue is the release norm.

**Fix:** remove all eight; and at `vacuum.c:1581` apply the real `page_ptr = obj_ptr; continue;` guard the doc already documents.

## 11 🟡 Relocated debug VOT walker changed semantics
`oos_util.cpp:134` — the move heap_file.c→oos_util.cpp also changed behavior: old returned `true` on the first OOS-flagged VOT entry; new accumulates `has_oos` and returns it only at `OR_IS_LAST_ELEMENT`, returning `false` if no terminator is reached. A HAS_OOS record with a missing/legacy terminator now mismatches the trusted flag → `assert(walked_has_oos == has_oos)` fires in debug. The old `index==max_var_count` corruption assert was also dropped. Debug-only; author scopes §8-4 out, but the move introduced the divergence.

## 12–16 Cleanup / Altitude / Efficiency
- **12** — `if (!is_mvcc_op && X.type==REC_xxx && heap_recdes_contains_oos(&X)) { rc=...; if (rc){ASSERT_ERROR; return;} }` duplicated 4× in `heap_file.c`. Push the `!is_mvcc_op`/`contains_oos` short-circuit inside `heap_oos_delete_unreferenced`.
- **13** — `oos_oid_in_vector` adds a TU + header + 2 CMake edits for an 8-line scan with one caller; `std::any_of(oids, [&](const OID&c){return OID_EQ(&c,oid);})` inlines it away.
- **14** — three loops `oos_delete` one OID at a time (each re-fixes the page) and `oos_chunk_exists` double-fixes the head page; OIDs are already page-sorted, so group by `(volid,pageid)` under one `pgbuf_fix` (existing `TODO(perf)`).
- **15** — OOS+REC_BIGONE "never coexist" is enforced by `abort()` in 4+ detection sites, not by construction (the OOS-column choice and big-length decision are independent). The real fix (a REC_BIGONE OOS-reclaim loop) is deferred.
- **16** — per-record `db_private_alloc`+`memcpy` of the undo image on the vacuum hot path; a per-block reusable scratch buffer (like the existing `VACUUM_OOS_VFID_MEMO`) replaces N alloc/free pairs.

## Verified NOT bugs (do not re-litigate)
- **Aborted-txn / rollback reclaim — REFUTED.** Vacuum only processes log blocks whose entire MVCCID range is strictly below the global oldest-visible threshold (block gate `vacuum.c:3248`; per-record assert `vacuum.c:3538`). Abort ordering (`log_rollback` at `log_manager.c:5304` runs *before* `logtb_complete_mvcc` at `:5317`) keeps an abortable txn's MVCCID active, pinning `oldest_visible`, so its block is never dispatched. The forward-walk's lack of an on-page `mvcc_satisfies_vacuum` re-check is safe by design. (Full reasoning in the companion caveat doc.)
- **MVCC record-layout change — REFUTED.** Adding the tag to `LOG_IS_MVCC_OPERATION` flips the record to `LOG_MVCC_UNDOREDO_DATA`, but recovery strips the MVCC header before dispatch (`log_recovery.c`); `heap_rv_undo_delete`/`redo_delete` are layout-agnostic and never read `rcv->mvcc_id`. MVCC UPDATE always holds a valid MVCCID; sibling `RVHF_UPDATE_NOTIFY_VACUUM` is the precedent. Doc §4-2's "identical replay" is true at the handler level.
- **`heap_log_delete_physical` arity change:** all four pre-existing callers pass `RVHF_DELETE`; behavior preserved.
- **`RVHF_DELETE_NEWHOME_NOTIFY_VACUUM` else-if reachability:** correctly NOT in `LOG_IS_MVCC_HEAP_OPERATION`, and the undo-unpack gate (§7-2) was extended — branch is live.
- **`helper->record` for REC_RELOCATION:** is a forward REC_NEWHOME copy, not the home 8-byte pointer — REMOVE-path parse is on the right bytes.
- **Memo cache** (stack-local, 3-state, `VFID_EQ` key), **`oos_chunk_exists` unfix ordering**, **`stable_copy` free paths**, **`std::move`**, **RV_fun[] ordering (134/135/136)** — all sound.

## Grilling the explanation doc
`CBRD-26668-code-review-explanation.md` is high quality but diverges from HEAD in four places (corrections applied to that file; plain-language write-up in the companion corrections doc):
1. **§8-1** shows the release path as `page_ptr = obj_ptr; continue;`. The code is `abort();`. No spin-loop remedy exists in the tree.
2. **§7-5 / §7-8** argue `oos_chunk_exists` makes block retry safe but never address **slot reuse** — the data-loss path (#1/#2).
3. **§10 risk table** has no row for "a new rcvindex carrying user data must join `LOG_MAY_CONTAIN_USER_DATA`" (the TDE leak, #3) nor for the latch-ordering rule (#4).
4. The "안전성 / Crash-safe / 18-18 통과 / CI 통과" framing predates the `abort()` instrumentation now in the tree; the PR as submitted is self-described "REVERT BEFORE MERGE".

Doc claims that **checked out correct:** eager/deferred split, REMOVE-vs-forward-walk double-delete avoidance, `_within_sysop`/`_atomic` sysop-ownership argument, REC_BIGONE `mvcc_header` read, undo-snapshot rationale.

## Recommendation
Blocking before merge: **#1–#4** (data loss, TDE, deadlock), and removal of all eight `abort()` markers **with** restoration of the real spin-loop guard at `vacuum.c:1581`. **#5–#11** depend on the temp-code clean-up. **#12–#16** are non-blocking quality/altitude improvements.
