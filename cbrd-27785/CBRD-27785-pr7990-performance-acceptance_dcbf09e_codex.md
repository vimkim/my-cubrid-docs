# PR7990 성능 판단 기준과 Acceptance Criteria

작성일: 2026-10-28. 수정일: 2026-10-31, Asia/Seoul. 대상 독자는 OOS 통합 작성자와 성능 리뷰어다.

**현재는 1번 일반 테이블 비교와 3번 현재 버전의 이득·손해 보고를 우선한다. 비교 성능의 잠정 목표는 develop 대비 instructions 증가 약 2% 이내다. 2번 기본 threshold의 4–16KB 행 전체 읽기는 후속으로 미룬다.**

2번은 기본 저장 정책이 달라지는 설계 trade-off로 다룬다. 추후 OOS threshold system parameter를 기존 overflow와 같은 기준, 즉 행이 페이지 크기를 넘을 때 OOS로 보내도록 설정한 뒤 다시 측정한다. 이번 수락에서 제외한 조건을 통과로 표시하지 않는다.

근거는 shparkcubrid님의 [10/28 성능 답변](https://github.com/CUBRID/cubrid/pull/7990#issuecomment-6461744209)과 **그 이후 사용자가 정정한 현재 작업 방향**이다. 리뷰어 원문은 세 조건을 모두 제시했지만, 이번 작업은 1·3번을 우선하고 2번을 이연한다. 잠정 +2%는 사용자가 정한 현재 목표이며 리뷰어의 승인된 허용치로 쓰지 않는다. 이 문서는 [CBRD-27785](https://jira.cubrid.org/browse/CBRD-27785)의 개정 기준서이며 새 측정·회사 승인 완료 기록이 아니다.

## 2. 현재 우선 조건과 후속 조건

| ID | 현재 처리 | 수락할 결과·근거 |
| --- | --- | --- |
| **AC-P1 — 일반 테이블** | **지금 우선** | PR8299를 먼저 반영한다. OOS 미사용을 확인한 일반 테이블에서 스캔·조건 스캔·UPDATE 등을 같은 조건으로 비교하고, 서버 instructions 증가를 develop 대비 잠정 약 +2% 이내로 관리한다. 최종 통합 head의 결과를 사용한다. |
| **AC-P2 — 기본 threshold의 4–16KB 전체 읽기** | **이번 수락에서 제외·후속 이연** | 현재 기본값의 heap→OOS 전환은 설계 trade-off다. 기본값 상태에서 develop과 동등해야 한다는 조건을 이번 필수 항목으로 두지 않는다. |
| **AC-P3 — 현재 버전의 이득·손해** | **지금 우선** | 현재 PR 버전의 작은/큰 컬럼 읽기·쓰기, 메모리/I/O 조건의 이득·손해와 CBRD-27788 결과를 함께 제시한다. 같은 저장 정책으로 비교하는 heap→heap·overflow→OOS 성능은 잠정 약 +2% 목표로 평가한다. 보고 제출 자체를 숫자 기준으로 대신하지 않는다. |

현재 단계의 완료는 AC-P1·P3의 결과와 판정 근거로 확인한다. 기존 +2% 스캔 두 건의 결과는 재사용하되, 그 결과만으로 나머지 작업까지 완료됐다고 표시하지 않는다. PR8299 반영·현재 head의 재검증과 결과 공유도 별도로 확인한다.

### AC-P2 후속 재측정 방향

1. OOS threshold를 조절할 system parameter의 실제 이름·지원 상태를 확인하고, 필요한 후속 변경을 정리한다. 이 문서는 그 parameter가 이미 구현됐다고 단정하지 않는다.
2. 기존 overflow와 같은 기준으로 설정한다. **행이 페이지 크기를 넘을 때 OOS로 보내고, 페이지 안에 들어가는 행은 heap에 남긴다.** 실제 record header 등을 포함한 경계와 저장 상태를 확인해 설정이 의도대로 동작하는지 검증한다.
3. 같은 입력이 develop에서 heap이면 비교본에서도 heap에, develop에서 overflow면 비교본에서 OOS에 저장되는지 확인한다. 그 상태에서 전체 읽기·쓰기 성능을 다시 비교한다.
4. 양쪽 SHA, parameter 값, 실제 행·페이지 크기와 저장 위치, 반복 측정 결과를 보존한다. 후속 결과는 기본 threshold 결과와 구분한다.

이는 지금 합의한 후속 방향이다. 실제 parameter 구현·설정이나 재측정 완료를 뜻하지 않으며, 별도 작업일·마감은 정하지 않았다.

원문의 conf·DDL·데이터 생성 SQL은 [댓글의 재현 방법](https://github.com/CUBRID/cubrid/pull/7990#issuecomment-6461744209)에 있다. 원문 조건은 1·3번 비교의 재현 출발점으로 사용한다. 2번의 기본 threshold 회귀를 지금 해결해야 한다는 전제로 사용하지 않는다. 조건이나 반복 방식을 바꾸면 변경 이유와 비교 가능한 범위를 명시한다.

### 문자셋을 포함한 비교 조건

DB 문자셋을 source SHA·빌드·conf·입력 데이터와 함께 비교 조건으로 기록한다.
2026-10-31의 [원문 SQL 재실행](CBRD-27785-reviewer-reproduction_4408135c_20261031_codex.md)에서
같은 develop 바이너리의 큰 값 LENGTH 중앙값은 UTF-8 294.076M, ISO-8859-1 188.608M이었다.
두 결과의 논리 값·행 수 검증은 통과했다. SQL과 source가 같아도 문자 처리 경로가 같은지는
별도 확인이 필요하다. 이 관측만으로 리뷰어의 locale을 확정하지 않는다.

| 확인할 조건 | 남길 근거 |
| --- | --- |
| DB 생성 locale | 각 DB의 실제 `createdb` 명령과 locale 인수 |
| 실제 charset·collation | `SHOW CREATE TABLE`로 테이블과 컬럼 선언을 확인하고, DB 기본값 상속과 개별 override를 구분한 결과 |
| 양쪽 조건의 일치 | A·B 각각의 값을 기록한다. 문자셋 비교 실험이면 조건별 표본을 분리한다. |
| 반복 전 상태 | 표본·라운드별 초기화 여부, UPDATE 누적 횟수, 질의·서버 실행 순서 |
| 계수 경계 | client·연결 방식, autocommit·명시 COMMIT, 계수 구간에 포함한 작업 |

조건이 누락된 과거 계수에는 미확인을 표시한다. 당시 수치와 revision을 유지하고,
새 실험의 조건을 소급해 붙이거나 원댓글 수치의 검증 완료로 바꾸지 않는다.
서로 다른 문자셋의 표본을 합쳐 하나의 중간값이나 합격 판정을 만들지 않는다.

### 기준 질의와 추가 범위

| 목적 | 원문 기준 질의·작업 | 판단할 것 |
| --- | --- | --- |
| 일반 행 읽기 | `select count(*), sum(a) from n;` | OOS와 무관한 경로에 공통 처리 비용이 추가되는지. |
| 일반 행 조건 스캔 | `select count(*) from n where substr(s, 30, 1) = 'a';` | 조건 계산을 포함한 일반 값 읽기의 비회귀. |
| 일반 행 쓰기 | `update n set a=a+1;` | 20만 행 UPDATE의 비회귀. 반복 전 데이터·트랜잭션 조건을 맞춘다. |
| 전체 큰 값 읽기 | `select sum(length(big)) from w;` | 기본 저장 정책으로 OOS에 옮겨진 큰 값을 모두 읽는 비용. |
| 큰 값 조건 스캔 | `select count(*) from w where substr(big, 5000, 1) = 'a';` | 원문과 같은 큰 값 접근 패턴의 비용. |
| 작은 컬럼 조회의 이득 | `select count(*), sum(a) from w;` | heap 집적도 효과와 메모리/I/O 조건별 실제 이득. |
| UPDATE의 비용 공개 | `update w set a=a+1;` 및 큰 값 5000행 갱신 | 변경하지 않은 OOS 값의 재기록, 로그·vacuum 비용과 관련 이슈 분담. |

현재 기본 threshold에서 얻은 약 6KB 결과는 이득·손해 보고의 관측값으로 보존한다. 4–16KB 전체 읽기의 수락 검증은 AC-P2 후속으로 미룬다. 이후 threshold를 맞춘 비교에서는 실제 행 크기와 heap·overflow·OOS 상태를 먼저 확인한다.

I/O 조건에서는 buffer보다 큰 데이터, cache 상태, page fetch와 실제 저장장치 읽기, 경과 시간을 함께 기록한다. 서버 재시작만으로 OS cache까지 비운 것으로 간주하지 않는다. 파일 읽기 replay나 합성 추정은 보조 진단이며 실제 SQL의 end-to-end 이득을 대신하지 않는다.

## 4. 잠정 +2% 기준의 적용과 판정

각 워크로드의 instructions 변화율은 `(PR 중간값 / develop 중간값 - 1) × 100`이다. **이번 사용자 지시로 잠정 목표를 약 +2% 이내로 정한다.** 우선 안정적으로 비교할 서버 user-space instructions에 적용한다. CPU 시간·경과 시간·I/O는 별도로 함께 보고하며 모든 지표에 2%를 일괄 적용하지 않는다.

현재 대상은 1번 일반 테이블과 3번 보고에서 같은 저장 정책으로 비교하는 heap→heap·overflow→OOS다. **기본 threshold 때문에 heap→OOS로 바뀌는 2번은 이 수치로 지금 강제 판정하지 않는다.**

| 판정 | 현재 작업의 잠정 기준 |
| --- | --- |
| **목표 충족** | 유효한 반복 측정에서 instructions 증가가 약 +2% 이내다. 해당 workload·revision·원시값과 반복 변동을 남긴다. |
| **개선 필요** | 약 +2%를 넘는 증가가 반복된다. 원인과 개선·후속 분담을 기록한다. 다른 workload의 이득과 평균내어 숨기지 않는다. |
| **판정 보류** | +2% 근처에서 변동하거나 비교 조건·표본이 맞지 않아 판단하기 어렵다. 반복·순서 교대 등으로 보완한다. |

기존 두 SELECT의 +2% 검증 완료는 당시 결과로 보존한다. 이번에는 사용자 지시로 현재 비교의 잠정 목표에도 2%를 사용한다. 따라서 기존 자료를 재사용할 수 있지만 현재 통합 head와 추가 workload의 결과를 별도로 확인해야 한다.

원문에 보고된 0.3%p는 관측된 라운드 간 차이이며 새 허용치가 아니다. +2%는 사용자 측의 잠정 작업 기준이다. 리뷰어에게 전달·확인한 결과가 있기 전에는 리뷰어가 이 수치를 승인했다고 기록하지 않는다.

### 보고된 수치는 관측값이다

최신 댓글은 큰 값 `length`·`substr` 스캔의 instructions 증가를 각각 +40.6%·+38.7%, 일반 테이블의 스캔·조건 스캔·UPDATE를 +8.0%·+9.9%·+7.0%로 보고했다. 작은 컬럼 UPDATE는 +73.7%, 큰 값 UPDATE는 +34.6%이며 좁은 컬럼 스캔은 -23.1%였다. 이는 리뷰어가 보고한 비교 결과이며 허용치나 이번 문서 작업의 새 실측값이 아니다.

## 5. Acceptance Criteria와 완료 증거

### 이번 단계 — 1·3번 우선

- [ ] **AC-P1:** PR8299를 먼저 반영하고, 최종 통합 head의 OOS 미사용 테이블을 같은 조건으로 비교한다. Instructions 증가 잠정 약 +2% 목표의 충족 여부를 기록한다.
- [ ] **AC-P3:** 현재 PR 버전의 이득·손해와 CBRD-27788 결과를 제공한다. Heap→heap·overflow→OOS의 비교는 잠정 약 +2% 목표로 평가하고, 개선·잔여 비용을 설명한다.
- [ ] 양쪽 SHA, 빌드·conf·데이터·실제 저장 상태, 측정 구간·cache 조건, 반복별 원시값과 판정 근거를 연결한다.
- [ ] 양쪽 DB 생성 locale과 실제 테이블·컬럼의 charset·collation을 기록하고 일치 여부를 확인한다. 누락 조건과 다른 문자셋의 결과는 분리한다.
- [ ] 일반 heap SELECT 두 건의 과거 완료와 현재 범위의 완료를 구분한다. 기본 threshold의 2번은 후속 이연으로 표시한다.
- [ ] 현재 수행 방향과 잠정 2% 기준을 리뷰어에게 공유할 내용으로 정리하고, 실제 리뷰어 답변·수락 여부는 근거가 있을 때 기록한다.

### 후속 — 2번 threshold 설정 후 재측정

- [ ] System parameter를 이용해 페이지 크기를 넘을 때 OOS로 가도록 설정하고 기존 overflow와 같은 저장 경계가 됐는지 확인한다.
- [ ] 이 설정에서 전체 읽기·쓰기 성능을 재측정한다. 기본값 결과와 설정 변경 결과를 구분한다.

별도 성능 regression TC의 승인·performance 영역 편입은 Work544의 기존 흐름을 유지한다. **비교 성능 TC를 일반 SQL/shell/medium CI나 기본 PR CI의 자동 선택에 추가하지 않는다.**

## 6. 원문 요구와 현재 수행 방향

리뷰어 원문은 1·2·3번을 병합 전 조건으로 제시했다. 현재 문서는 이후 사용자 결정에 따라 2번을 후속으로 미루고 1·3번과 잠정 +2% 목표를 우선한다. 이 변경을 리뷰어의 원래 발언이나 승인 결과로 바꾸어 적지 않는다.

구조 재설계와 batch read는 개선 후보로 관리한다. CBRD-27230의 값 재사용, CBRD-27791의 읽기 지역성, rollback·vacuum 정합성은 각 이슈의 범위를 유지한다. 이번 문서 수정은 threshold parameter나 엔진 코드를 구현하지 않는다.
