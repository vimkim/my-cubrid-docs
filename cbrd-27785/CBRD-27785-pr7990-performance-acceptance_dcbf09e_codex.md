# PR7990 성능 판단 기준과 Acceptance Criteria

작성: 2026-10-28, Asia/Seoul. 대상 독자는 OOS 통합 작성자와 성능 리뷰어다.

**PR7990의 성능 수락에는 일반 테이블의 비회귀, 기본 설정에서 4–16KB 행 전체 읽기의 비회귀, 현재 PR 버전의 이득·손해 보고가 필요하다.** 비회귀는 측정 노이즈를 제외하면 develop보다 느려지지 않는다는 뜻이다. 기존 일반 heap SELECT 두 건의 +2% instructions 기준 통과만으로 이 세 조건을 충족했다고 판단하지 않는다.

근거는 shparkcubrid님의 [10/28 성능 답변](https://github.com/CUBRID/cubrid/pull/7990#issuecomment-6461744209)이다. 이 문서는 그 답변을 측정·판정 항목으로 정리하고, 사용자의 요청에 따라 [CBRD-27785](https://jira.cubrid.org/browse/CBRD-27785)의 PR7990 성능 수락 조건에 반영하기 위한 기준서다. 새 측정이나 리뷰 승인이 완료됐다는 문서가 아니다.

### 기존 범위에서 달라지는 점

기존 CBRD-27785는 heap→heap과 overflow→OOS의 CRUD 개선을 다루고, heap→OOS의 비용을 설계 trade-off로 설명했다. 최신 리뷰는 **기본 설정에서 4–16KB 행 전체 읽기**를 별도 비회귀 조건으로 명시했다. 따라서 이 항목은 heap→OOS에 해당하더라도 PR7990 성능 수락에서 제외할 수 없다.

작은 컬럼 조회의 I/O 이득과 큰 컬럼 읽기의 비용을 함께 공개한다. 한쪽의 이득으로 AC-P1·P2의 회귀를 상쇄해 통과시키지 않는다. 이 밖의 heap→OOS 작업은 비용·이득을 보고하고 필요한 수락 결정을 구분한다. 모든 heap→OOS CRUD에 새 일괄 수치 기준을 만들지는 않는다.

## 3. 무엇을 어떻게 측정하는가

### 리뷰어가 사용한 기준 실험

| 항목 | 원문에 나온 조건 |
| --- | --- |
| 빌드·실행 | 같은 호스트의 release 빌드, 같은 conf. 서버를 하나씩 실행해 직렬 비교. |
| 메모리 | `data_buffer_size=4G`, 데이터가 buffer에 올라간 상태. 이 실험은 디스크 I/O 절감 효과를 측정한 것이 아니다. |
| 대조 데이터 | 약100B 일반 행 20만 개, OOS 미사용 대조군. |
| 큰 값 데이터 | SHA2를 이어 만든 압축되기 어려운 약6KB 값, 2만 행. 선언 길이와 실제 저장 크기를 구분한다. |
| 반복 | 4라운드, 라운드별 5회 실행, 첫 회를 warmup으로 제외. 동일하게 적용하면 질의별 유효 표본은16개다. |
| 주 지표 | `perf stat -e instructions:u -p <cub_server pid>`로 측정한 서버 user-space instructions의 중간값. 전체 비교 구간과 실행한 질의를 일치시킨다. |
| 변동 관측 | 스캔 instructions의 라운드 간 차이는0.3%p 이내라고 보고했다. 공유 호스트의 wall-clock은 크게 흔들렸다. |

원문의 conf·DDL·데이터 생성 SQL은 [댓글의 재현 방법](https://github.com/CUBRID/cubrid/pull/7990#issuecomment-6461744209)에 있다. 원문 조건을 기본 재현 조건으로 사용한다. 조건이나 반복 방식을 바꾸면 변경 이유와 비교 가능한 범위를 명시한다.

### 기준 질의와 추가 범위

| 목적 | 원문 기준 질의·작업 | 판단할 것 |
| --- | --- | --- |
| 일반 행 읽기 | `select count(*), sum(a) from n;` | OOS와 무관한 경로에 공통 처리 비용이 추가되는지. |
| 일반 행 조건 스캔 | `select count(*) from n where substr(s, 30, 1) = 'a';` | 조건 계산을 포함한 일반 값 읽기의 비회귀. |
| 일반 행 쓰기 | `update n set a=a+1;` | 20만 행 UPDATE의 비회귀. 반복 전 데이터·트랜잭션 조건을 맞춘다. |
| 전체 큰 값 읽기 | `select sum(length(big)) from w;` | 기본 저장 정책으로 OOS에 옮겨진 큰 값을 모두 읽는 비용. |
| 큰 값 조건 스캔 | `select count(*) from w where substr(big, 5000, 1) = 'a';` | 원문과 같은 큰 값 접근 패턴의 비용. |
| 작은 컬럼 조회의 이득 | `select count(*), sum(a) from w;` | heap 집적도 효과와 메모리/I/O 조건별 실제 이득. |
| UPDATE의 비용 공개 | `update w set a=a+1;` 및 큰 값5000행 갱신 | 변경하지 않은 OOS 값의 재기록, 로그·vacuum 비용과 관련 이슈 분담. |

약6KB 한 점의 성공으로 4–16KB 전체를 검증했다고 쓰지 않는다. 범위 안의 대표 크기와 저장 경계를 선정하는 일은 추가 검증 계획이다. 데이터의 실제 행 크기와 heap·overflow·OOS 상태를 먼저 확인하고, 선택한 크기·남은 범위를 보고한다.

I/O 조건에서는 buffer보다 큰 데이터, cache 상태, page fetch와 실제 저장장치 읽기, 경과 시간을 함께 기록한다. 서버 재시작만으로 OS cache까지 비운 것으로 간주하지 않는다. 파일 읽기 replay나 합성 추정은 보조 진단이며 실제 SQL의 end-to-end 이득을 대신하지 않는다.

## 4. 수치를 어떻게 판정하는가

각 워크로드의 instructions 변화율은 `(PR 중간값 / develop 중간값 - 1) × 100`이다. 서로 다른 빌드·실행 조건·질의를 한 비율에 섞지 않는다. 비용이 줄어드는 음수와 증가하는 양수를 같은 방식으로 기록한다.

| 판정 | 기록할 조건 |
| --- | --- |
| **PASS** | 유효한 같은 조건 비교에서, 합의한 측정 노이즈를 넘는 지속적인 증가가 없다는 근거가 있다. 해당 범위·revision과 리뷰어의 수락 판단을 기록한다. |
| **FAIL** | 반복에서도 노이즈를 넘는 증가가 유지된다. 좁은 스캔의 개선이나 다른 저장 경로의 이득으로 이 실패를 지우지 않는다. |
| **판정 보류** | 노이즈 범위를 합의하지 못했거나, 반복 간 변동·측정 누락·조건 차이로 회귀와 노이즈를 구분할 수 없다. 같은 조건으로 보완하고 판정 근거를 남긴다. |

**새로운 공통 +2% 허용치는 없다.** 기존 +2%는 과거 일반 heap SELECT 두 건의 수정 검증에 적용한 기준이다. 당시의 완료·측정 결과는 보존하되 최신 AC-P1·P2의 통과로 옮겨 쓰지 않는다.

**관측된0.3%p도 합격선이 아니다.** 댓글은 실험의 반복성을 설명했으며 허용 회귀율을 수치로 승인하지 않았다. 기준 revision의 반복 비교와 순서 교대 등으로 워크로드별 노이즈를 확인하고, 수치 경계가 필요한 부분은 리뷰어와 합의한다. 이 절차는 판정 방법 제안이다.

원문은 instructions를 주 지표로 삼았다. CPU 시간·경과 시간도 함께 보존한다. 재현되는 지연이 남으면 원인을 설명하고, 지표 간 차이에 대한 리뷰어 판단을 기록한다. Instructions 감소만으로 end-to-end 시간의 동등성을 주장하지 않는다.

### 보고된 수치는 관측값이다

최신 댓글은 큰 값 `length`·`substr` 스캔의 instructions 증가를 각각 +40.6%·+38.7%, 일반 테이블의 스캔·조건 스캔·UPDATE를 +8.0%·+9.9%·+7.0%로 보고했다. 작은 컬럼 UPDATE는 +73.7%, 큰 값 UPDATE는 +34.6%이며 좁은 컬럼 스캔은 -23.1%였다. 이는 리뷰어가 보고한 비교 결과이며 허용치나 이번 문서 작업의 새 실측값이 아니다.

## 5. Acceptance Criteria와 완료 증거

- [ ] **AC-P1:** PR8299 반영 후의 통합 head에서 OOS 미사용 테이블의 비회귀를 확인한다.
- [ ] **AC-P2:** 기본 설정의4–16KB 행 전체 읽기를 대상으로 노이즈 외 성능 저하가 없음을 확인한다. 원문의6KB 질의와 추가 대표 조건의 범위를 밝힌다.
- [ ] **AC-P3:** CBRD-27788의 결과와 함께 현재 PR 버전의 이득·손해·남은 비용을 리뷰어에게 제공한다.
- [ ] 각 조건에 대해 양쪽 SHA, 빌드·conf·데이터·실제 저장 상태, 측정 구간·cache 조건, 반복별 원시값·요약과 노이즈 판정 근거를 연결한다.
- [ ] 기존의 두 SELECT 개선 완료와 새로운 병합 수락 판정을 구분한다. 최종 head가 바뀌면 영향받는 측정을 확인한다.
- [ ] CBRD-27785에 세 항목의 충족 여부·근거·미충족 이유를 기록하고, 리뷰어의 성능 수락 확인을 남긴다.

별도 성능 regression TC의 승인·performance 영역 편입은 Work544의 기존 수락 흐름을 유지한다. **비교 성능 TC를 일반 SQL/shell/medium CI나 기본 PR CI의 자동 선택에 추가하지 않는다.** 여기의 병합 전 성능 수락은 검토 기준이며 새 자동 CI gate를 설치한다는 뜻이 아니다.

## 6. 요청된 구현과 검토 제안을 구분한다

원문에서 PR8299 선반영과 세 성능 조건은 명시된 병합 전 요구다. 기존 heap을 활용하는 저장 방식의 구조 검토는 리뷰어의 검토 제안이며, 특정 재설계를 선택한 결정은 아니다. Batch read도 가능한 개선 수단 중 하나다.

CBRD-27230의 변경하지 않은 값 재사용, CBRD-27791의 읽기 지역성, rollback·vacuum 정합성은 각 이슈에서 구현·검증한다. 이 문서는 그 구현을 새로 선택하지 않고, 어떤 변경을 택하든 최종 PR7990이 위 성능 수락 근거를 갖추도록 한다.
