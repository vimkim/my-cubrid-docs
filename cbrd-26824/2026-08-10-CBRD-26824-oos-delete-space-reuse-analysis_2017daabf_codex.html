CUBRID OOS · SPACE REUSE ANALYSIS

빈 공간은 있는데,
왜 새 페이지를 만들까?

OOS 대량 삭제 뒤 공간 재사용률이 낮아지는 현상을, “청소가 늦다”가 아니라 “청소된 자리를 다시 찾는 방법”의 문제로 풀어 설명합니다. 원인 후보의 확실한 부분과 아직 확인이 필요한 부분을 나누고, INSERT 성능을 지키면서 개선하는 방향을 제안합니다.

1. 한눈에 보는 결론

삭제된 OOS 데이터의 자리는 생겼습니다. 하지만 새 INSERT가 그 자리를 충분히 발견하지 못해, 비어 있는 기존 페이지를 두고 새 페이지를 할당하는 것이 가장 유력한 설명입니다.

즉, 현재 증상은 데이터 삭제 실패보다 빈 공간 탐색·재사용 정책의 사각지대에 가깝습니다. Internal LOB만의 문제가 아니라 일반 OOS에도 같은 구조가 적용됩니다.

vacuum 지연 가능성 낮음 DELETE 후 150초를 더 기다려도 패턴이 바뀌지 않았습니다.
기능 정합성 문제는 아님 관찰된 핵심은 읽기 오류나 데이터 손실이 아니라 파일 성장과 재사용 효율입니다.
설계상 성능 절충 과거의 비싼 반복 스캔을 막은 최적화가 삭제 후 탐색 기회를 줄였습니다.
중요한 표현: “정상 상태의 동작”은 “바람직하다”는 뜻이 아닙니다. 대기하면 저절로 해결되는 일시적 지연이 아니라, 현재 정책대로라면 반복해서 나타날 수 있는 안정적인 비효율이라는 뜻입니다.

2. 측정이 말해 주는 것

격리 prefix에서 한 사이클마다 25MB를 넣고, DELETE를 커밋한 뒤 30초를 기다리는 실험을 반복했습니다. 아래 비율은 “다음 INSERT가 직전 사이클의 공간을 얼마나 다시 쓴 것으로 보이는가”를 근사한 값입니다.

왜 Internal LOB이 더 낫게 보일까요? 두 워크로드는 행 수, OOS 값의 크기와 배치, LOB 외부 저장소 사용 방식이 다릅니다. 따라서 70%와 15%의 차이는 “Internal LOB 전용 알고리즘이 우수하다”기보다, 동일한 OOS 탐색 정책이 서로 다른 페이지 배치를 만났을 때 결과가 크게 달라질 수 있음을 보여 줍니다.

3. 먼저 구분할 것: 공간 회수는 네 단계입니다

used가 줄지 않았다는 한 가지 숫자만으로 vacuum 실패를 결론 내리기 어려운 이유입니다. “지웠다”와 “디스크가 작아졌다” 사이에는 서로 다른 네 단계가 있습니다.

1 OOS 청크 삭제

vacuum이 더 이상 필요 없는 OOS 청크 레코드를 슬롯에서 제거합니다.

2 빈 슬롯 발견

해시 캐시, 헤더 best[], bestspace sync가 다시 쓸 페이지를 찾아야 합니다.

3 빈 페이지 반환

완전히 빈 OOS 페이지를 file_dealloc로 파일 할당기에 돌려주는 별도 단계입니다.

4 볼륨 크기 축소

예약된 sector·볼륨 용량 자체를 운영체제에 돌려주는 단계로, 이번 문제와는 별개입니다.

이번 측정은 1단계가 늦다기보다 2단계가 약하다는 설명과 잘 맞습니다. 또한 현재 feat/oos 기준으로 3단계는 아직 들어오지 않았으므로, 레코드가 사라져도 DB 전체 used가 즉시 감소하지 않는 것 자체는 예상 가능한 동작입니다.

4. 가장 유력한 원인: “빈 페이지가 있다는 신호”가 없으면 찾으러 가지 않습니다

원인 A — 스캔 진입 게이트

ratio = estimates.num_other_high_best / estimates.num_pages;

if (ratio >= OOS_BESTSPACE_SYNC_THRESHOLD)  // 0.1
  oos_stats_sync_bestspace (...);
else
  break;                                     // 이후 새 페이지 할당

해시와 best[]가 놓친 페이지는 파일 스캔이 찾아야 합니다. 그러나 게이트 값이 10%보다 작으면 스캔 자체를 시작하지 않습니다. 대량 DELETE로 완전히 빈 페이지가 많아도 그 사실이 힌트에 충분히 반영되지 않았다면, 새 INSERT는 그 페이지를 보지 못한 채 새 페이지를 만듭니다.

원인 B — 스캔 범위가 최대 100페이지

부분 스캔은 clamp(전체 페이지 × 20%, 10, 100)입니다. 파일이 1,000페이지라면 한 번에 100페이지만 확인합니다. 이 제한 자체는 INSERT 지연을 통제하는 합리적인 장치지만, 다음 제약과 함께 있을 때 문제가 커집니다.

원인 C — “이어보기” 위치를 저장하지만 사용하지 않음

/* TODO: ideally find the index of full_search_vpid; for now start from 1 */
start_idx = 1;

마지막 검사 페이지는 full_search_vpid에 저장되지만, 다음 스캔도 1번부터 시작합니다. 따라서 100페이지 제한이 있는 큰 파일에서는 여러 번 스캔해도 앞부분만 반복해서 보고, 뒤쪽의 빈 페이지까지 영원히 도달하지 못할 수 있습니다.

원인 D — 스캔을 허가하는 지표가 스스로 회복하기 어려움

힌트가 낮음 → 스캔 안 함 → 숨은 빈 페이지를 못 찾음 → 힌트가 계속 낮음 한번 과소평가 상태에 들어가면, 외부 사건이 힌트를 충분히 올려 주기 전까지 빠져나오기 어렵습니다.

헤더 통계는 정합성 데이터가 아니라 log_skip_logging으로 저장되는 비로그 힌트입니다. 삭제 시 헤더 WRITE latch를 조건부로 얻지 못하면 best[] 갱신도 건너뜁니다. 이런 “잃어도 안전한 힌트”는 데이터 정확성에는 좋지만, 공간 재사용 효율에는 사각지대를 만들 수 있습니다.

5. 왜 이런 게이트가 생겼나: CBRD-26824가 해결한 실제 성능 문제

게이트를 단순히 제거하면 안 되는 이유가 있습니다. 이전에는 첫 시도마다 파일 스캔을 강제하는 || try_find == 0 조건이 있었습니다. 큰 OOS 청크 하나가 페이지를 거의 채우는 워크로드에서는 부분적으로 빈 페이지를 아무리 찾아도 청크가 들어가지 않습니다. 그런데도 청크마다 스캔을 반복하면서 파일이 커질수록 INSERT가 급격히 느려졌습니다.

CBRD-26824 실측수정 전수정 후의미
마지막 반복의 행당 INSERT 약 890ms 약 71ms 불필요한 첫 스캔 제거로 약 12.5배 개선
시간 추세 파일 성장에 따라 계속 증가 대체로 평탄 스캔 비용이 파일 크기에 결합되어 있었음
피해야 할 되돌림: 모든 OOS 청크의 첫 실패 때 무조건 sync를 다시 실행하면 CBRD-26824가 제거한 “파일이 커질수록 INSERT가 느려지는 문제”를 그대로 되살릴 가능성이 큽니다.
당시 코드 리뷰에서도 콜드 캐시에서 num_other_high_best == 0이면 sync bootstrap이 사라져, 실제 빈 페이지를 영원히 발견하지 못할 수 있다는 절충점이 지적됐습니다. 이번 반복 DELETE 측정은 그 우려가 현실 워크로드에서 나타날 수 있음을 보여 주는 강한 신호입니다.

6. 어디까지 확정됐고, 어디부터 추론인가

원인을 설득력 있게 설명하려면 “코드로 확인한 사실”과 “측정 패턴으로 추정한 실행 경로”를 섞지 않는 것이 중요합니다.

항목상태판단
10% 게이트와 CBRD-26824 도입 근거 코드 확인 oos_find_best_page와 hotfix 커밋에서 직접 확인
부분 스캔 20%, 최소 10, 최대 100 코드 확인 oos_stats_sync_bestspace에서 직접 확인

런타임에서 게이트가 실제로 매번 닫혔음 계측 필요 ratio, sync 호출 수, 할당 이유 카운터가 없음
DB 전체 증가분 중 OOS 파일 몫 분리 필요 현재 측정은 heap·index·catalog·OOS·Internal LOB 합계
현재의 가장 정확한 결론: 코드 구조와 측정 결과는 게이트·제한 스캔·미구현 이어보기를 매우 유력한 원인으로 가리킵니다. 다만 “실행 때마다 게이트가 닫혀 새 페이지를 만들었다”는 최종 인과관계는 파일별 카운터를 한 번 더 수집해야 닫힙니다.

7. 해결 방향: 한 가지 스위치가 아니라 세 층으로 고칩니다

좋은 해결책은 두 조건을 동시에 만족해야 합니다. 삭제 후에는 숨은 빈 공간을 결국 찾아야 하고, INSERT-only 워크로드에서는 쓸모없는 스캔을 매 청크마다 반복하지 않아야 합니다.

8. 권장 순서

“완전 빈 페이지는 반환하고, 남은 부분 공간은 예산 안에서 끝까지 찾는다”

가장 안전한 해법은 한 층에 모든 책임을 몰지 않는 것입니다. 페이지 반환은 완전 빈 페이지를 확실히 처리하고, bestspace는 부분 여유 페이지를 효율적으로 찾는 역할에 집중합니다.

1단계 — 진단 카운터로 인과관계 확정

같은 25MB 반복 시나리오에서 gate skip, sync, alloc의 실제 횟수와 OOS VFID별 페이지 수를 얻습니다.

2단계 — CBRD-26831 + CBRD-26786 방향 검증·통합

non-numerable + sector-bitmap 열거와 vacuum 후 빈 페이지 dealloc으로 완전 빈 페이지를 힌트 체계 밖에서도 재사용합니다.

3단계 — cursor resume 완성

부분 스캔의 100페이지 비용 상한은 유지하되, 호출이 누적되면 파일 전체를 공정하게 순회하도록 합니다.

4단계 — 필요할 때만 deletion-aware trigger 추가

2~3단계 후에도 부분 공간이 숨는다면, vacuum 회수 사건당 한 번의 bounded sync를 허용합니다.

9. 수정이 정말 좋은지 확인하는 기준

“재사용률이 좋아졌다”만 보면 INSERT 지연을 놓칠 수 있고, “INSERT가 빠르다”만 보면 파일 성장을 놓칠 수 있습니다. 공간·시간·정확성을 함께 봐야 합니다.

검증 축시나리오통과 기준 예시
공간 안정성 25MB INSERT → DELETE COMMIT → vacuum 완료를 5~10회 반복 warm-up 이후 OOS 파일 user page 수가 첫 안정 사이클 대비 ±10% 안쪽
prefix 탈출 파일 뒤쪽에만 빈 페이지를 만들고 sync를 여러 번 호출 ceil(data_pages / 100) 이내 호출로 뒤쪽 후보 발견
INSERT 성능 보존 CBRD-26824의 3MB BIT VARYING·20행 반복 워크로드 행당 지연이 파일 크기에 따라 지속 상승하지 않고, 무익한 sync 횟수도 증가하지 않음
콜드 캐시 삭제·vacuum 후 서버 재시작, 다시 INSERT 숨은 빈 페이지를 결국 재사용하며 신규 페이지 폭증 없음
동시성·복구 vacuum과 INSERT 동시 실행, 회수 도중 crash injection COUNT·값 일치, stale VPID 안전 처리, 오류 로그·데이터 손실 없음
측정 분리 DB 전체 used와 OOS VFID page 수를 동시에 기록 증가분을 heap/index/LOB/OOS 중 어디서 만들었는지 설명 가능

성공으로 볼 수 있는 결과

  • 반복 사이클 후 파일 크기가 안정 구간에 들어감
  • 일반 OOS 재사용률이 Internal LOB 수준에 가까워짐
  • sync 비용은 설정한 budget을 넘지 않음
  • 재시작 뒤에도 첫 삽입 묶음 안에서 재사용이 회복됨

회귀 신호

  • 파일이 커질수록 행당 INSERT 시간이 다시 우상향
  • OOS 청크마다 sync가 한 번씩 실행됨
  • 스캔이 같은 VPID 범위만 반복함
  • deallocated page를 write 경로가 다시 선택함
