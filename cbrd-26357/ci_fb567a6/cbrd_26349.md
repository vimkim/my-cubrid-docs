# Why cbrd_26349 reported two failed assertions

**The testcase counted part of the runner IP address as a successful SQL result.** The database produced the expected authentication errors and returned the expected row counts. The failure is in the test's result parser, with high confidence.

## What the test intended to check

This test checks that DBLink credentials continue working after corruption of the local TDE key, that wrong credentials are rejected, and that changing a remote password takes effect. Its result checks search combined SQL output and error messages for `100`, the expected `count(*)` value.

## What actually failed

The runner address was `10.233.111.100`. Every authentication error included this address in its `CAS INFO` suffix. The command `grep -wc "100"` matches a whole word anywhere on a line; dots delimit words, so it matches the address too. It does not restrict the match to a SQL result row. The [exact testcase](https://github.com/CUBRID/cubrid-testcases-private-ex/blob/c4b9d482fbd491a68510b2552df2c3cac91911fc/shell/_40_guava/cbrd_26349/cases/cbrd_26349.sh#L108-L141) uses this command for both failed assertions.

| Assertion | Expected SQL rows containing only 100 | Actual SQL rows | Value computed by the testcase | Why it failed |
| --- | ---: | ---: | ---: | --- |
| 2, wrong password | 0 | 0 | 3 | Three expected error messages each contain the IP suffix `.100` |
| 3, password change | 2 | 2 | 3 | Two successful result rows plus one expected error containing `.100` |

For assertion 2, the trace also records exactly three expected password errors. For assertion 3, it records exactly one expected password error and zero `Cannot allocate request handle` errors. The successful result rows are visible in the failure message. Assertions 1 and 4 passed.

This fully explains both NOKs without assuming a password-decryption or DBLink execution defect. [Shard log](https://github.com/CUBRID/cubrid/actions/runs/36570256001/job/109416879833).

## Verification and retry implications

[The small offline check](verify_result_count.py) reconstructs the two output blocks from the retained JUnit failure text and runs the same `grep` command. It reproduces `3` and `3`. Restricting the match to `^[[:space:]]*100[[:space:]]*$` gives the intended `0` and `2`; replacing only `.100` in the address with `.101` also removes the false matches. [Recorded output](verification.txt).

A retry in the same pod would normally retain the same IP, so retrying would not fix this cause. A fresh pod with a different address could hide it. This is environment-dependent testcase behavior, not evidence that all five failures are timing flakes.

## Attribution and next action

**Category:** testcase result-parsing defect. **PR relation:** unlikely. **Confidence:** high for the cause of the two failed assertions. The testcase is byte-identical to its merged develop parent, and the observed database behavior meets its intended checks. This does not establish correctness beyond this scenario.

**Falsifier:** a preserved output block with a wrong SQL row count or an unexpected authentication error after counting only numeric result lines would contradict the claim that these NOKs are solely false counts. The retained blocks do not contain such a mismatch.

**Next action:** fix the testcase to parse result rows, retain the explicit error checks, and verify outputs with IP addresses both containing and not containing an octet `100`. Then rerun the unchanged database scenario. No testcase edit is included in this research.
