## 1. 리뷰 4번: CDC 회귀를 격리한 채 머지하는 문제

### 1.1 리뷰어 요구
review 5662427700(CHANGES_REQUESTED, 2026-10-27, commit `4408135c0`)의 4번이다. private-ex #4210이 `cbrd_27064`와 `cbrd_27075`를 `_25_unstable`로 옮겼다. 그래서 이미 출시된 CDC 기능이 큰 행에서 깨진 채 develop에 들어간다. 리뷰어는 "이 상태로 머지하려면 **팀 차원의 결정**이 필요하고, 그 결정을 **PR 본문**에 남겨 달라"고 했다.

  1. **결정 주체.** 본문은 "QA팀과 협의"까지만 적었다. 리뷰어가 요구한 것은 이미 출시된 CDC 기능이 큰 행에서 깨지는 상태를 받아들일지에 대한 결정이다. 이는 테스트를 어디서 돌릴지를 정하는 QA 협의와 다른 문제다. 기록 근거도 약하다. 작성자 측 ADR-0007(`cubrid-oos-context/docs/adr/0007-run-deferred-cdc-regressions-in-qa-regression-only.md`, accepted 2026-10-27)은 "accepted with the user"로 되어 있다. Evidence 절에는 "QA 합의는 작성자 진술로 기록했고, 별도 서면 기록은 없다"고 적혀 있다. 반면 ADR-0008은 "Accepted 2026-11-05 by the team lead"로 팀장 확정 기록이 있다. 같은 수준의 확정이 CDC 건에는 없다.
  2. **사용자 영향.** 본문은 테스트 이동만 설명하고, 머지 후 사용자가 겪을 영향은 적지 않았다. CBRD-26939 설명(2026-11-03 갱신)의 "영향"은 다음 네 가지다.

     - (2) 회수된 slot을 같은 길이의 다른 값이 재사용하면 **다른 행의 값이 오류 없이 추출된다.**
     - (3) assert 빌드에서는 `oos_check_head_header()`에서 crash가 난다.
     - (4) flashback도 같은 영향을 받는다.

     특히 (2)는 조용히 틀린 데이터를 내므로, 실패를 알리는 rc=-10보다 위험하다. 리뷰어는 rc=-10만 언급했다.
  3. **릴리스 조건.** 11.5 출시 전에 CBRD-26939를 반드시 넣는지, 이 결함을 안고 출시하는지가 없다. 참고로 CBRD-26939는 다음 상태다 [문서/기록 확인, `cubrid-jira jql`, 2026-11-11].

     "출시된 기능의 회귀"를 Minor로 둔 것은 리뷰어 관점과 맞지 않는다.
  4. **임시 완화책 검토 여부.** 예를 들면 `supplemental_log > 0`인 DB에서는 OOS로 옮기지 않고 develop처럼 heap 또는 REC_BIGONE으로 저장하는 방안이 있다.      - 이미 OOS로 저장된 행의 처리

### 2.4 남은 일 (크기, 위험)

2. **측정 세트**: 측정만 하고, 실행은 이 조사 범위 밖이다.
   - (a) 리뷰어가 6461744209에 올린 재현 세트(w/m/n, cubrid.conf, perf stat instructions:u, 4라운드)를 그대로 쓴다.
   - (b) CBRD-27788 io_bench의 Q1~Q5, heap/overflow 입력, restart-only와 파일 캐시 해제 조건.
   - (c) DML: 작은 컬럼 UPDATE(첫 실행과 연속 실행을 구분), 큰 컬럼 UPDATE, DELETE, vacuum catch-up 시간, 로그량.
   - (d) 결과 표는 이득과 손해를 한 표에 두고, develop 비교 기준(`4781495f` 또는 현재 merge-base)과 charset을 명시한다.
   - 크기: 공유 호스트 직렬 측정으로 기계 시간 1~2일, 정리 0.5일.
   - 위험: 공유 호스트 부하로 wall 시간이 흔들린다. 그래서 instructions로 판정하고 wall은 참고로만 쓴다.
3. **기준 2는 팀 결정이 먼저다** [추론]. 4~16KB 값을 기본으로 OOS에 보내는 한, 큰 값을 읽는 스캔은 값마다 OOS 페이지를 따로 고정하고 복사한다. 이 구조에서 develop보다 느려지지 않기는 어렵다. 측정 근거는 다음과 같다.
   - CBRD-27788 heap Q4 +25.9%
   - #8491 실측: 값 하나에 page fix 3번
   - 대안 POC Sidecar도 같은 조회에서 instructions +6~14%

   선택지는 셋이다.
   - (i) 기본 임계값을 "행이 페이지를 넘을 때"로 올린다. 기준 2는 거의 자동으로 충족되지만, 4~16KB 구간의 좁은 스캔 이득이 사라진다.
   - (ii) 기본값은 두고 CBRD-27791 batch read로 비용을 줄인다. 효과가 검증되지 않았고 일정 위험이 크다.

## 3. 구조 검토 요청: 큰 값을 기존 heap 안에 두는 방식

### 3.1 리뷰어 요구
6461744209 "구조 검토 요청". 리뷰어는 데이터 손실 문제(CBRD-27237, CBRD-27781)와 읽기 비용이 같은 원인에서 나온다고 본다. 원인은 MVCC 없는 별도 저장 공간을 새로 만들면서 삭제, rollback, vacuum, 잘못된 참조 방어를 모두 따로 구현해야 했다는 점이다. 11.5로 나가면 디스크 형식이 굳으므로, 그 전에 큰 값을 별도 저장 공간이 아니라 기존 heap 안에 두는 방식을 검토해 달라는 요청이다.

### 3.2 현재 상태
- **PR에 답변하지 않았다** [문서/기록 확인]. `my-cubrid-docs/oos/issue-graphs.json` PR7990 노드에도 "shparkcubrid가 요청한 큰 값의 heap 보관 구조 검토(댓글 6461744209)에는 아직 답이 없습니다"라고 적혀 있다(2026-11-03).
- **현재 설계와 그 근거** [문서/기록 확인]
  - OOS는 테이블별 `FILE_OOS`/`PAGE_OOS`에 chunk 체인과 identity stamp를 둔다(PR 본문 Implementation).
  - 넓은 행에 REC_BIGONE과 OOS를 함께 쓰지 않는 결정은 CBRD-26937(Resolved)에 있다. 코드는 `67220b7:src/storage/heap_file.c:14935-14944`이다 [코드 확인].
  - 회수 결함에는 ADR-0008 "Reclaim OOS chains only after the delete is final"로 대응한다(accepted 2026-11-05, 팀장 확정). 엔진 구현은 #8434(OPEN)다. 이 ADR은 "설계에 대한 기술 승인일 뿐 PR #7990 머지 승인이 아니다"라고 명시한다.

### 3.3 "기존 heap 안에 두는 방식"의 두 해석과 내부 근거
리뷰어 문장은 두 가지로 읽을 수 있다. 각각의 근거는 아래와 같다.

| 해석 | 내용 | 내부 근거 | 평가 |
|---|---|---|---|
| (A) 같은 heap 파일의 별도 페이지에 둔다 (컬럼 단위 REC_BIGONE과 비슷) | 큰 값을 같은 heap 파일의 cold 페이지에 두고, 행에는 참조만 둔다 | Sidecar 설계 §2·§11 G9: 다음 구성 요소는 heap 파일의 모든 페이지를 훑는다. parallel heap scan(`px_scan_input_handler_heap.cpp:63`), histogram sampling(`histogram_sampler_sr.cpp:1031`), checkdb(`heap_check_all_pages_by_file_table`). 같은 파일에 두면 좁은 스캔의 I/O 이득이 사라진다. 또 "컬럼 단위 REC_BIGONE은 16KB 미만에서 얻는 것이 없다." (`e64a04a79` 기준 인용이며, `67220b7`에서 다시 확인하지는 않았다) | 좁은 스캔 이득(OOS의 존재 이유)과 충돌한다 [문서/기록 확인 + 추론] |
| (B) 값을 일반 MVCC heap 레코드로 둔다 (별도 heap 파일이지만 기존 heap 수명주기를 그대로 사용) | 테이블별 store heap에 값 하나를 일반 heap 레코드 하나로 넣는다. 삭제·undo·vacuum은 기존 heap 코드가 처리한다 | 작성자 측 대안 POC **Sidecar**(`my-cubrid-docs/sidecar/`, branch `sidecar`, PR 없음)와 Codex 대안 **Inner Table**(`my-cubrid-docs/inner-table/`)이 정확히 이 방향이다 | 리뷰어 제안의 실질과 같다 [추론] |

#### 리뷰어 원인 진단의 타당성
- **"데이터 손실은 별도 수명주기에서 나온다": 대체로 타당하다** [문서/기록 확인 + 코드 확인].
  - 코드 비교 [코드 확인]: OOS 페이지는 `ANCHORED`로 초기화된다(`67220b7:src/storage/oos_file.cpp:3159`). heap 페이지는 `ANCHORED_DONT_REUSE_SLOTS`다(`67220b7:src/storage/heap_file.c:1144`).
  - `my-cubrid-docs/oos/design-contradictions.md`(2026-11-04)는 반례 실행으로 두 가지를 보였다. 첫째, 물리 undo와 확정 전 공간 재사용은 commit된 레코드 보존과 양립하지 않는다(CBRD-27781/27858). 둘째, rollback된 UPDATE의 undo image에 근거한 삭제는 현재 값 보존과 양립하지 않는다(CBRD-27237).
  - Sidecar 설계 §3 "Premise verdict"도 같은 결론이다. OOS 결함 군은 "확정 전 공간 재사용", "확정되지 않은 정보로 삭제 결정", "주소 하나가 값 하나를 가리킨다는 가정"에서 나오며, 일반 MVCC heap 레코드는 이 지름길을 쓰지 않는다.
  - 다만 ADR-0008(#8434)이 OOS 안에서 이 두 가정을 없애는 방식으로 대응하고 있다. 따라서 "OOS 구조로는 고칠 수 없다"는 결론까지는 나오지 않는다.
- **"읽기 비용도 같은 원인": 일부만 맞다** [측정 인용 + 추론].
  - 리뷰어가 지적한 "값 하나당 page fix 3번"은 #8491 작성자의 release 실측과 일치한다. 내역은 head page 1번과 할당 확인 fix 2번이다. 할당 확인 fix는 `pgbuf_fix_if_not_deallocated` 호출(`67220b7:src/storage/oos_file.cpp:2555`)에서 나온다 [코드 확인 + 측정 인용]. 이 2번은 OOS 페이지가 해제될 수 있는 고유 수명주기를 방어하는 비용이다. 일반 heap 수명주기를 쓰면 없앨 수 있는 부분으로 본다 [추론].
  - 반면 값을 별도 주소에 두는 한 추가 읽기 비용은 남는다. Sidecar도 큰 값을 읽는 스캔에서 instructions +6~14%를 냈다(아래 표).
- **비교 측정** [측정, **개인 scratch 기록이며 미공개**]: `my-cubrid-docs/.scratch/sidecar/perf-use/SUMMARY.md`(2026-11-10, 4 interleaved blocks, 리뷰어의 4G buffer 설정, parallelism=0). 해당 문서는 OOS는 자기 base 대비, Sidecar는 develop `e64a04a79` 대비로 비교했다. 아래는 instructions 변화다.
