요약 (TL;DR)

bigPageSize 는 현재 ORDER BY 문제로 실패하는 것이 아니다. 지금은 loaddb -C 가 exit 254 로 죽고 (object 0 건 적재), 그 시각에 cub_server 코어덤프가 남는다. 스크립트의 if [ $? -eq 0 ] 가드 때문에 ORDER BY 비교 쿼리는 아예 실행조차 되지 않는다. 원인은 CBRD-27157 (loaddb 워커의 MVCCID self-lock assert) — 다른 loaddb 실패들과 같은 뿌리이며, draft PR #7588 이 고친다.

  • “order by 문제” 결론은 7월 실패 모드에는 정확했고, #7588 머지 후 다시 살아난다. 8/03 로컬 검증에서 #7588 적용 시 loaddb 는 성공하고, CLOB/BLOB locator 2줄 diff 가 남는 것을 확인했다.
  • 단, 그 잔여 diff 의 해석이 두 기존 분석에서 서로 모순된다. 7/08 보고서는 “locator 는 그대로 보존됐고, 256-way tie 에서 다른 row 를 골랐을 뿐” 임을 실측으로 증명했다. 8/03 문서는 “feat/oos loaddb 가 locator 를 재생성하는 듯” 이라고 검증 없이 추정했다. 판별 실험 (수 분 소요) 이 필요하다 — §bigPageSize Layer C.
  • tiebreaker 수정 (order by 1 desc, id) 은 어느 TC 브랜치에도 반영된 적이 없다. tc/pr-6864 (CI 가 실제 사용하는 브랜치), TC feat/oos (PR #3806 head), TC develop 모두 현재도 order by 1 desc limit 1 그대로다.
  • 실패는 9건이 아니라 실제로 10건이다. bug_bts_5730 (loaddb_CS, node 33, 코어덤프 동반) 이 노드별 JUnit XML 에는 있으나 CircleCI 집계 목록에서 누락됐다.
  • CDC 2건 (cbrd_27064, cbrd_27075) 은 지시에 따라 분석 제외.

공통 메커니즘: CBRD-27157 — loaddb 워커 MVCCID self-lock assert

이번 실패의 최대 그룹 (4+1건) 이 공유하는 크래시. 이 커밋의 소스에서 직접 검증했다 (로컬 워크트리가 정확히 07fef9d48).

서버측 loaddb (loaddb -C) 가 OOS 대상 행을 적재
  └─ OOS 파일이 아직 없음 → lazy 생성: oos_create_file
       └─ file_create (file_manager.c:3455)
            └─ FILE_OOS 는 SERVER_MODE 에서 logtb_get_current_mvccid() 필요
                 └─ 트랜잭션의 첫 MVCCID 발급 (develop CBRD-26942, commit 741734a8f)
                      └─ logtb_acquire_mvccid_self_lock (log_tran_table.c:4071)
                           └─ lock_transaction_mvccid (log_tran_table.c:4093)
                                └─ lock_internal_perform_lock_object
                                     └─ assert (thread_p->type != TT_LOADDB);   ← lock_manager.c:3539
                                          └─ loaddb 워커 스레드 (TT_LOADDB) → ABORT → cub_server 코어

즉 develop 의 CBRD-26942 (첫 MVCCID 발급 시 self-lock) 와 feat/oos 의 OOS 파일 lazy 생성 (생성 시 MVCCID 필요) 이 develop 머지에서 처음 만나며 생긴 상호작용이다. CI 는 optdebug 빌드라 assert 가 살아 있어 서버가 즉사한다 (release 는 assert 컴파일 아웃).

수정: PR #7588 — assert 를 assert (thread_p->type != TT_LOADDB || is_transaction_lock); 로 완화 (트랜잭션 self-lock 만 허용, 객체 락 계약은 유지). 현재 draft PoC 상태이며 head 브랜치명이 CBRD-00001-oos-fix-regression-poc (placeholder) 이므로 정식화 후 머지 필요.

반증 조건 (falsifier): node 44 / 33 의 코어 스택이 위 체인 (lock_internal_perform_lock_object ← logtb_acquire_mvccid_self_lock ← file_create(FILE_OOS)) 을 보이지 않으면 이 귀속은 틀린 것. 이번 수집은 text 모드라 코어 바이너리는 내려받지 않았다.

1. bigPageSize 현재: loaddb 크래시 이후: ORDER BY/locator 미결 요청 초점

shell/_35_cherry/issue_21654_server_side_loaddb/bigPageSize/cases/bigPageSize.sh · node 44 · 실행 19.4s

TC 가 하는 일

tdb1 (16K page, csql -S 직접 INSERT, 256 row — 큰 컬럼 c2 ≈ 12KB, c3 ≈ 1.2MB CLOB, j ≈ 1.5MB JSON) 을 unloaddb 로 덤프하고, tdb2 (4K page) 에 loaddb -C 로 재적재한 뒤, 동일 SELECT (… from t order by 1 desc limit 1) 를 양쪽에서 실행해 결과를 비교한다. 이어 load.answer vs load.log 도 비교한다.

관찰 — 이번 CI 에서 실제로 일어난 일 (3중 레이어의 Layer A)

+ cubrid loaddb -C -d tdb1_objects -s tdb1_schema -udba tdb2
+ '[' 254 -eq 0 ']'                     ← loaddb 가 exit 254 로 실패
+ compare_result_between_files load.answer load.log   ← csql 비교 블록은 통째로 스킵됨

diff (load.answer vs load.log):
  Start object loading.                  Start object loading.
  Total 256 object(s) inserted, ...    <                        ← load.log 에 완료 라인 없음
  • node 44 에 cub_server_20260805002806.294.coredump — bigPageSize 재시도 실행 구간 00:27:51–00:28:09 의 정중앙. 즉 tdb2 서버가 object 적재 중 크래시했고 loaddb 클라이언트가 254 로 죽었다.
  • 1차 시도 (00:22:14, time=20) 도 완전히 동일하게 실패 (exit 254 확인) — 결정적 (deterministic) 실패이지 flaky 가 아니다. 1차 시도의 코어는 수집 체계상 남지 않았다 (마지막 시도의 코어만 살아남는 수집 특성).
  • server .err 에 “Internal Error” grep 0건 — assert abort 는 이 grep 에 안 걸린다.
  • 따라서 “bigPageSize 는 order by 문제” 는 현재 실패 신호의 설명으로는 낡았다 (stale). ORDER BY 쿼리는 실행되지도 않았다.

이 크래시는 위 CBRD-27157 메커니즘 그대로다: 4K page 의 tdb2 에서 c2/c3/j 값이 전부 OOS 대상 (4K 레이아웃의 OOS inline target ≈ 1KB) → 서버측 loaddb 첫 OOS demotion 에서 lazy oos_create_file → MVCCID → assert. PR #7588 의 대상 TC 목록에 bigPageSize 를 추가해야 한다 (현재는 cbrd_25481, itrack_10006, bug_xdbms_sus880 3건만 명시).

Layer B — “ORDER BY tie” 분석 (CBRD-26828 초안 + 7/08 보존 로그 보고서) 은 그 당시 실패 모드에 대해선 여전히 타당

  • 256 row 는 seed 1 row + INSERT ... SELECT 8회 self-doubling 으로 생성 → 선택 컬럼 전부 동일, ORDER BY 1 DESC 의 키 col1 = -32768 이 256-way tie. tie 에서 LIMIT 1 승자는 물리 scan 순서 의존 (implementation-defined).
  • heap_insert_physical 계측 (vpid/slot 실측): develop 은 이 행들을 8B REC_BIGONE 포인터로 저장 → 4K 헤더 page 한 장에 256건 순서대로 → scan 첫 row = row 1. OOS 는 컬럼만 빼고 ~656B REC_HOME 유지 → row 1–255 는 뒷 page 로 밀리고 마지막 insert 인 row 256 이 헤더 page 의 남은 슬롯을 차지 → scan 첫 row = row 256 → tie 승자 역전 → NOK.
  • 결정적 증거: csql2 가 출력한 “다른” CLOB/BLOB locator 2건이 tdb1_objects 덤프 안에 같은 row 로 verbatim 존재 — 즉 loaddb 는 locator 를 정확히 보존했고, diff 는 다른 tied row 를 골랐기 때문이지 데이터 손상이 아니다.
  • 기록 정정 1건: CBRD-26828 초안의 “Actual Result” 는 “diff 가 id 컬럼” 이라 했으나 id 는 SELECT 목록에 없다 — 실제 diff 는 cl/bl locator 문자열 (선택 컬럼 중 유일하게 row 별 고유값). 초안 제출 시 수정 필요.

Layer C — #7588 이후 남는 것: 미해결 모순

8/03 로컬 검증 (#7588 포함 빌드): loaddb 성공, TC 는 cl/bl locator 2줄 diff 로 여전히 NOK. 그런데 이 잔여 diff 의 해석이 갈린다:

  • 7/08 보고서 (증거 강함): locator 는 보존됨 + tie 로 다른 row 선택 → TC 비결정성. (csql2 locator 를 tdb1_objects 에서 grep 으로 실증, locator 에 박힌 epoch 가 tdb2 서버 기동 이전임까지 확인)
  • 8/03 문서 (증거 약함): “develop 은 locator 를 보존해서 통과했으므로 feat/oos 가 locator 를 재생성하는 것으로 보임” — 판별 검사 없이 추정, 스스로 “후속 디버깅 필요” 표기.

둘은 상호 배타적이다. 8/03 관찰 (2줄 locator diff) 은 tie-pick 만으로도 완전히 설명되므로, 7/08 의 검증 기준이 우세하다 — 단 7/08 빌드 (309753d) 와 8/03 빌드 (e20543df8) 사이에 locator 처리 회귀가 들어왔을 가능성은 미검증.

판별 실험 (수 분이면 끝남)

  1. #7588 적용 로컬 빌드에서 bigPageSize 를 cleanup 없이 실행.
  2. grep -F '<csql2 의 cl locator>' tdb1_objects — 다른 row 에서 발견 ⇒ tie-pick (Layer B 성립, TC 수정으로 종결) / 부재 ⇒ locator 재생성 실재 (엔진 JIRA + LOB 내용 동등성 검증 필수 — 8/03 런에서 값 왕복 검증은 안 됐음).
  3. 동치의 원샷: tiebreaker (order by 1 desc, id limit 1) 적용 후 재실행 — OK ⇒ tie-pick 확정 + TC 도 고쳐짐 / 여전히 NOK ⇒ 재생성 실재.

관찰 — tiebreaker 는 어디에도 반영된 적 없음

분석 시점 기준 bigPageSize.sh:24 는 from t order by 1 desc limit 1 그대로다 — tc/pr-6864 (tip e21c7ce9c, 이 CI 가 실제 사용하는 브랜치), TC feat/oos (PR #3806 head — #3806 은 bigPageSize 를 건드리지 않음), TC develop 모두 확인. CBRD-26828 과 7/08 보고서가 두 차례 권고했지만 landing 이 없었다. Layer C 결과와 무관하게 256-way tie 는 입증된 잠재 비결정성이므로 tiebreaker 는 반영해야 한다.

6. cbrd_23430 numerable FILE_OOS 북키핑 결함 (추론)

shell/_35_cherry/issue_21522_json/cbrd_23430/cases/cbrd_23430.sh · node 45

TC 가 하는 일

길이 50,000 의 JSON 값을 loaddb -C 로 적재 후 select json_length(j) from t 가 50000 을 돌려주는지 확인.

관찰 — 여기도 1차/재시도 증상이 다르다

[1차 시도, 00:20:25–00:20:34] ← 정보가 있는 쪽
createdb jsondb OK → server start OK
+ cubrid loaddb --no-user-specified-name -d init_data -C jsondb -udba
직후 csql: "Failed to connect to database server, 'jsondb'"   ← 서버가 loaddb -C 직후 사망

[재시도] ← 수집된 failure 레코드는 이쪽 (오독 주의)
createdb → Volume ".../jsondb_vinf" already exists.            ← 1차 잔여물
server start → Database "jsondb" is unknown, or "databases.txt" cannot be accessed
  • 재시도 기록만 보면 “환경 실패” 로 보인다 — 실제로 직전 스냅샷 보고서 (c2cbeaf) 는 동일 시그니처를 환경 실패로 분류했다. 그건 재시도 연쇄에 대해선 맞지만, 1차 시도의 “loaddb -C 직후 서버 사망” 이 진짜 엔진 신호다.
  • 이번 런의 node 45 에 코어 없음 (1차 코어 미보존).

추론 — 왜 CBRD-27157 이 아니라 별도 결함으로 보나

8/03 분석이 정확한 스택으로 로컬 재현했다: pgbuf_fix_debug assert (page_buffer.c:2564), 스택 oos_insert_many → oos_find_best_page → oos_file_alloc_new → file_alloc — file_alloc 이 돌려준 새 페이지가 같은 OOS 파일의 이미 초기화된 dirty PAGE_FTAB 페이지 (user page / FTAB 이중 배정). 즉 numerable FILE_OOS 의 페이지 북키핑 결함이며, ADR-0001 (FILE_OOS 비-numerable 전환 — oos-m2-all-plans-experimental 에 구현됨) 이 정확히 이 regime 을 제거하는 fix 방향이다.

주의: 트리거가 같은 loaddb -C 라서 이번 런 증거만으로는 CBRD-27157 과의 중첩을 배제할 수 없다 — 분리 근거는 8/03 스택뿐. 신뢰도 중간.

다음 액션
numerable FILE_OOS 북키핑 JIRA 신규 발행 (8/03 스택 인용). feat/oos 머지 전 ADR-0001 전환 인입 여부 결정. #7588 만으로 고쳐지는지도 CI 로 판별 가능 (고쳐지면 재분류).

8. log_enc_04 OOS 레이아웃 변화 → TC workload 전제 붕괴

shell/_36_damson/cbrd_23608_tde/log_enc_04/cases/log_enc_04.sh · node 27 · 크래시 없음

TC 가 하는 일

TDE 암호화 DB 에서 다양한 DML 을 수행한 뒤, 로그 덤프 (result.log) 에 특정 recovery 레코드 타입 (rcvindex) 들이 존재하는지를 grep 으로 확인한다 — 로그가 암호화 경로를 제대로 탔는지의 대리 지표.

관찰

grep -rc 'rcvindex = RVHF_MVCC_REDISTRIBUTE'  → 1   OK
grep -rc 'rcvindex = RVHF_INSERT'             → 8   OK
grep -rc 'rcvindex = RVHF_UPDATE'             → 6   OK
grep -rc 'rcvindex = RVHF_DELETE'             → 2   OK
grep -rc 'rcvindex = RVHF_INSERT_NEWHOME'     → 0   ← "RVHF_INSERT_NEWHOME is missing!" → NOK

즉 다른 로그 레코드는 전부 정상 생성·검출됐고, RVHF_INSERT_NEWHOME 딱 하나가 아예 생성되지 않았다. 크래시·코어 없음. 이 TC 는 8/03 에 재보정된 TDE 8건 (tbl_enc_08/14, file_enc_01~05/07) 에 포함되지 않았던, 이번에 새로 표면화된 잔여 TDE 실패다.

추론 — 왜 안 생기나

  • RVHF_INSERT_NEWHOME 의 생산자는 이 트리에서 두 곳: (a) UPDATE 로 레코드가 home page 여유 공간을 넘겨 재배치 (REC_NEWHOME) 될 때 (heap_file.c:22010), (b) bestspace 페이지 insert 경로 (heap_file.c:4048, HA 중복 적용 회피용).
  • 이 TC 의 workload 는 20,000B lpad 값을 t2_big 에 넣고 varchar(10000) 컬럼을 추가하는 식의 큰 값 위주 — develop 에서는 이런 값이 레코드를 키워 재배치를 유발했지만, OOS 에서는 큰 값이 전부 16B stub 으로 demote 되어 레코드가 계속 작게 유지 → 재배치가 일어날 조건 자체가 사라짐 → 해당 rcvindex 미생성.

다음 액션

  1. 선행 확인: 같은 TC 리비전으로 develop 빌드에서 어느 생산자가 이 레코드를 만들었는지 확인 (develop 도 0 이면 OOS 귀속이 틀린 것).
  2. TC workload 수정 (tc/pr-6864): OOS inline target (16K page 기준 ~4,060B) 미만으로 유지되면서도 home page 여유를 넘기게 레코드를 키우는 UPDATE 를 추가해 진짜 재배치를 유발 — answer 만 고치는 게 아니라 workload 를 고쳐야 하는 케이스.

증거와 한계

  • 세 suite 모두 동일 커밋 07fef9d48… 에 고정 수집. 로컬 엔진 워크트리도 정확히 같은 커밋이라 소스 인용은 exact.
  • text 모드 수집 — 코어덤프 12개는 목록만 확보, 바이너리 미다운로드. 백트레이스 아티팩트는 이 런에 존재하지 않음. 따라서 이번 런의 크래시 지점 귀속은 전부 “실행 구간 내 코어 + 선행 정밀 스택 재현” 에 근거한 추론이며 본문에 라벨로 구분했다.
  • CTP 는 실패 시 1회 재시도하며 마지막 시도의 코어만 살아남는다 — 1차 시도 코어의 부재는 1차 크래시의 반증이 아니다. 또 재시도는 1차가 남긴 더러운 작업공간 때문에 다른 증상 (createdb 실패 등) 을 보이는 경우가 있어 (itrack_10006, cbrd_23430), 수집된 failure 레코드 (= 재시도 로그) 만 읽으면 오분류하기 쉽다.
  • testcase_revision 이 세 summary 모두에서 부재 (구버전 번들엔 있었음 — collector 회귀 가능성). TC 브랜치는 config (TC_BRANCH="tc/pr-6864", ls-remote 5회 실패 시에만 develop 폴백) + 내용 증거 (tc/pr-6864 에서 고친 12건이 이번에 전부 통과) 로 도출. CTP 속성 파일의 develop 표기는 장식적 기본값.
  • bigPageSize Layer C (tie-pick vs locator 재생성) 는 의도적으로 미결 — 판별 검사 없이는 어느 쪽도 승인하지 않는다.
  • CDC 2건의 근본 원인은 지시에 따라 주장하지 않는다.
