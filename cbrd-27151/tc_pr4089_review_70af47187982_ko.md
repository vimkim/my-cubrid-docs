# CBRD-27151 — TC PR #4089 정적 검토 요약

- 참조 엔진: [cubrid #7785](https://github.com/CUBRID/cubrid/pull/7785), `CBRD-27151-bulk-file-destroy`, `369cf9ce3a63e057b234af2f36903fc16089310c`

- 작업 기록: work-tracker #492

## 확인된 문제

### P2 — 사전 적재와 DROP의 성공 여부를 확인하지 않는다

새 테스트의 [76행과 82행](https://github.com/CUBRID/cubrid-testcases-private-ex/blob/70af471879821641c99ec8cb35ca4af46992faa2/shell/_06_issues/_26_2h/cbrd_27151/cases/cbrd_27151.sh#L75-L86)은 `CREATE → INSERT → DROP`을 실행한 `csql`의 종료 상태를 확인하지 않는다. 기존 테이블의 적재나 DROP이 실패해도 이후에는 새 테이블 `t2`·`t4`의 행 수와 DB 정합성만 검사한다. 따라서 파괴된 파일의 복구라는 전제조건이 성립하지 않은 채 테스트가 통과할 수 있다.

**보완 방향:** 사전 SQL의 성공, 적재된 행 수, DROP 완료를 각각 확인하고, 실패하면 즉시 NOK로 기록한다.

### P2 — 조회 가능 여부를 서버 재시작의 증거로 사용한다

[`kill_and_restart()`의 35–45행](https://github.com/CUBRID/cubrid-testcases-private-ex/blob/70af471879821641c99ec8cb35ca4af46992faa2/shell/_06_issues/_26_2h/cbrd_27151/cases/cbrd_27151.sh#L33-L51)은 PID 조회와 kill의 성공 여부를 확인하지 않는다. kill이 실패하면 원래 서버가 계속 요청을 처리할 수 있다. 이때 `server start`가 실패해도 이를 무시하고, `select 1`이 성공하면 재시작 성공으로 기록한다. 실제 크래시 복구 경로는 실행되지 않았을 수 있다.

**보완 방향:** 대상 PID를 검증하고 kill 성공 및 기존 프로세스의 소멸을 확인한 뒤 조회 가능 여부를 검사한다. 자동 재시작을 허용하려면 서버 전체가 내려간 상태보다 **기존 PID가 사라졌는지**를 확인하는 방식이 적절하다.

## 시나리오별 검증 범위

엔진의 [복구 후 페이지 정리](https://github.com/CUBRID/cubrid/blob/369cf9ce3a63e057b234af2f36903fc16089310c/src/storage/page_buffer.c#L3952-L4017)는 섹터 해제 시점보다 오래된 페이지를 버리고, 그 섹터를 재사용한 파일의 더 새로운 페이지는 보존해야 한다.

| 시나리오 | 검증하려는 엔진 동작 | 현재 판정 기준 | 남은 검증 공백 |
| --- | --- | --- | --- |
| 새 테스트 Case 1 | redo가 다시 만든 파괴 파일의 페이지를 제거하고 크래시 이후 재할당 | 재시작, `t2` 8,000행, 마지막 `checkdb` | 실제 재사용된 섹터와 복구 중 페이지 제거의 증거가 없음 |
| 새 테스트 Case 2 | 크래시 전에 섹터를 재사용한 파일의 새로운 페이지 보존 | 재시작, `t4` 200행에 8,000행 추가 후 총 8,200행, 마지막 `checkdb` | 기존 200행의 `id`·`pad` 값과 섹터 동일성을 확인하지 않음 |
| TDE `file_enc_03` | 암호화 페이지 할당과 파일 파괴 요약 로그 | 숫자를 정규화한 로그 전체 비교 | 변경된 기대 문자열은 현재 엔진과 일치함 |
| TDE `file_enc_05` | 암호화 테이블 DROP 이후 크래시 복구와 새 테이블 적재 | 재시작, 새 테이블 5행, 파괴 로그 존재, `checkdb` | 실제 섹터 재사용과 저장 값의 무결성을 확인하지 않음 |

섹터 재사용은 현재 할당 방식에서 개연성이 있지만, 정적 검토만으로 실제 사용된 섹터를 확정할 수는 없다. 행 수 일치는 값의 무결성까지 보장하지 않는다. 체크포인트 시점을 제어하는 경우와 파일 파괴·섹터 해제 도중의 크래시도 이번 변경의 시나리오에는 포함되지 않았다. 이 항목들은 추가 검증 공백이며, 위 P2 두 건과는 구분한다.

TDE의 기존 페이지별 해제 로그를 제거한 변경은 타당하다. bulk destroy는 해당 로그를 남기지 않으며, 새 기대 문자열은 엔진의 [`file_destroy()` 요약 로그](https://github.com/CUBRID/cubrid/blob/369cf9ce3a63e057b234af2f36903fc16089310c/src/storage/file_manager.c#L4100-L4107)와 일치한다.

## 검증 결과와 한계

원본 `cbrd_27151.sh`를 수정하지 않고 셸 제어 흐름만 검사했다. `cubrid`·`csql`, 초기화·종료 처리, PID 조회, kill, sleep을 대체 함수로 구현했고, OK/NOK 기록에는 실제 CTP의 `write_ok`·`write_nok` 함수를 사용했다. DROP 실패 조건에서는 사전 SQL이 오류를 반환하도록 했고, kill 실패 조건에서는 원래 서버가 계속 실행 중인 상태와 추가 `server start` 실패를 모의했다.

| 셸 모의실험 입력 | 관측 결과 |
| --- | --- |
| 정상 제어 조건 | 5 OK / 0 NOK |
| 사전 SQL에서 DROP 실패 | **5 OK / 0 NOK** |
| kill 실패로 기존 서버가 계속 실행 | **5 OK / 0 NOK** |
| 행 수가 틀린 대조 조건 | 4 OK / 1 NOK |

위 결과는 실패를 놓치는 테스트 판정 로직을 확인한 것이다. **실제 CUBRID의 크래시 복구나 데이터 손상을 재현한 결과는 아니다.** 실제 DB 시험과 빌드는 수행하지 않았다. 코드와 GitHub 리뷰도 변경하지 않았다.

TC worktree에서 다음 정적 검사가 통과했다.

```bash
bash -n \
  shell/_06_issues/_26_2h/cbrd_27151/cases/cbrd_27151.sh \

  shell/_36_damson/cbrd_23608_tde/file_enc_05/cases/file_enc_05.sh
git diff --check ba7ba142f03c5b30471d5a11a6cecb8caa170fd8...HEAD
```

문서화된 코딩 규칙 위반은 0건, 테스트 요구사항 충족 여부에 관한 문제는 P2 두 건이다. 다음 단계는 두 판정 결함을 보완하고, 실제 섹터 재사용과 값 보존의 증거를 확보하면서 debug 엔진에서 native `cubrid-testkit`으로 해당 사례를 실행하는 것이다.
