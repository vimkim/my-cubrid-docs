Lock Manager를 다시 세우다

MVCC가 있어도 lock이 필요한 이유, 그리고 MVCCID self-lock이 미완료 삽입자를 안전하게 기다리게 하는 이유

독자·범위·학습 목표

이 책은 C/C++, 자료구조, 운영체제의 mutex, SQL transaction을 배운 컴퓨터공학 2학년을 대상으로 한다. Multi-granularity locking, wait-for graph(WFG), multi-version concurrency control(MVCC)은 처음 접한다고 가정한다.

공통 시나리오는 account(id PRIMARY KEY, balance)이다. T1이 기존 행을 갱신하고 새 key 7을 삽입한 채 미완료일 때, T2가 plain SELECT, SELECT FOR UPDATE, UPDATE, duplicate INSERT를 차례로 시도한다. 독자는 이 네 동작에서 visibility, class/instance lock, MVCCID self-lock의 책임과 wait 뒤 재검사를 설명하게 된다.

  1. mutex, page latch, transaction lock, MVCC visibility를 보호 상태와 수명으로 구분한다.
  2. typed resource key, mode table, holder/waiter, conversion, escalation, release를 추적한다.
  3. MVCC가 reader–writer 충돌을 줄여도 writer–writer와 미완료 unique/FK 판정에는 lock이 필요한 이유를 설명한다.
  4. self-lock의 X holder, S waiter, completion-before-unlock, wakeup/recheck를 재구현 가능한 순서로 설명한다.
  5. PostgreSQL과 MySQL/InnoDB의 책임 배치를 동등, 부분 유사, 대응 없음으로 구분한다.

Source-confirmed: CUBRID의 “MVCC lock”은 하나의 enum mode가 아니다. MVCC 경로가 기존 class/instance의 IS·IX·S·X와 MVCCID transaction resource의 사용 시점을 고르는 정책이다. CUBRID-C020 CUBRID-C030

MVCC visibility는 “내 snapshot에서 어느 version이 보이는가?”에 답한다. Lock Manager는 “누가 지금 논리적 객체를 바꿀 수 있는가?”와 “미완료 transaction의 unique/FK 결과를 지금 확정해도 되는가?”에 답한다. 둘은 경쟁 기술이 아니라 다른 race를 맡는다.

self-lock의 self는 자기 자신을 기다린다는 뜻이 아니다. Inserter T1이 자기 MVCCID M의 transaction resource에 X를 보유한다. Record에서 M을 발견한 observer T2가 같은 resource에 S를 요청해 T1의 완료를 기다린다. T1이 completed/inactive 상태를 먼저 공개하고 X를 풀면, T2가 깨어나 S를 완전히 풀고 index/record를 다시 검색한다. CUBRID-C030 CUBRID-C031 CUBRID-C032
