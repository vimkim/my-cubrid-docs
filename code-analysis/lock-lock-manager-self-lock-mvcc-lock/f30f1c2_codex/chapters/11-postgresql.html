학습 목표와 비교 질문

이 장을 마치면 relation, tuple, transaction XID, virtual transaction ID(VXID), speculative token을 구분하고, PostgreSQL의 owner/lifetime·wait/release·MVCC policy·recovery·observability를 CUBRID와 같은 축에서 설명할 수 있다. 질문은 “CUBRID self-lock과 이름이 같은 것이 무엇인가?”가 아니라 “같은 correctness 책임이 어디에 분산되어 있는가?”이다.

Source-confirmed: relation 안정성은 heavyweight relation tag, 정상 row ownership은 tuple header XMAX/MultiXact, completion wait은 XID tag, top transaction publication은 VXID tag, tentative ON CONFLICT decision은 speculative token이 나눠 맡는다. PG-C001 PG-C002 PG-C030 PG-C031

Ownership와 lifetime

shared LOCK: resource grant/wait mask와 queue
shared PROCLOCK: resource와 backend/lock group hold 연결
backend LOCALLOCK: mode별 reacquire count와 ResourceOwner count
prepared dummy PGPROC: 2PC recovery가 이어받는 qualifying lock owner

같은 backend의 재획득은 local count만 늘 수 있다. Top commit은 non-session standard locks를 풀고, abort는 session lock까지 포함하는 별도 정책을 갖는다. Subtransaction commit은 일반 lock ownership을 parent ResourceOwner로 넘기며 abort는 해당 owner의 locks를 개별 release한다. Prepared transaction은 qualifying transaction locks를 2PC record에 보존하고 dummy owner로 재획득하지만 VXID/session-only lock은 제외한다. PG-C104 PG-C110 PG-C119

Acquire → wait → grant → release

acquire(tag, mode):
  if same backend already holds: increment LOCALLOCK count
  else if eligible weak relation lock: try per-backend fast path
  else create/find shared LOCK + PROCLOCK
       if compatible with holders and preceding waiters: GrantLock
       else enqueue by priority-aware rule and ProcSleep

release:
  ungrant holder
  mark compatible waiter granted in shared state
  then signal waiter latch

Queue는 단순 strict FIFO가 아니며 기존 holder와 앞선 conflicting waiter를 고려한다. Shared state의 grant-before-wakeup은 깨어나는 waiter가 새 requester에게 추월당하는 race를 막는다. Access method caller는 별도로 tuple/index 조건을 다시 확인한다. PG-C105 PG-C106 PG-C109

Deadlock, timeout, interrupt

deadlock_timeout은 비싼 graph 검사를 늦출 뿐 wait 상한이 아니다. lock_timeout이 양수면 별도 lock-wait timer가 생기며 latch wait는 cancel/die interrupt도 처리한다. Deadlock detector는 soft edge의 queue reorder를 시도하고, hard/unresolvable cycle이면 error를 낸다. 실제 victim tie-break와 timing은 이 source-only 비교가 측정하지 않았다. PG-C107 PG-C108

MVCC operation policy

Plain reader는 old visible tuple을 반환할 수 있지만 FOR UPDATE는 row strength/wait policy를 heap_lock_tuple까지 전달한다. Conflicting XMAX를 만나면 buffer lock을 놓고 transaction/MultiXact completion을 기다린 뒤 XMAX를 다시 검사한다. UPDATE는 key 변경 여부에 따라 strength를 고르고, concurrent update 후 isolation policy에 따라 EvalPlanQual retry 또는 serialization failure로 갈린다. Unique/FK 역시 기다림 뒤 key/tuple condition을 재판정한다. “MVCC이므로 lock-free”가 아니라 operation별 책임 선택이다.

Startup·transaction end·shutdown 경계

Startup은 shared LOCK/PROCLOCK hashes와 fast-path strong-relation data를 요청·초기화하고 각 backend는 LOCALLOCK hash를 만든다. Top transaction은 VXID owner lock을 ProcArray advertise 전에 설치한다. Commit/abort는 outcome과 ProcArray 종료를 먼저 공개하고 ResourceOwner phase에서 locks를 정리한다. Server-wide worker shutdown choreography는 Unknown이며 이 transaction cleanup 순서와 같다고 가정하지 않는다. PG-C120 PG-C121 PG-C122

I/O·full-disk·page corruption은 ordinary volatile lock acquire의 직접 책임이 아니라 storage/WAL caller가 전파하는 인접 실패다. 이 장은 그 전체 오류 복구를 재구현한다고 주장하지 않는다.

Performance와 observability

Local reacquire와 weak relation/VXID fast path는 shared partition 경합을 줄이려는 설계다. Strong request가 오면 관련 fast-path relation locks를 main table로 옮긴다. pg_locks와 pg_blocking_pids, wait/failure logging GUC가 진단점을 제공하지만 tuple header의 모든 logical row lock이 독립 tuple row로 나타나지는 않는다. Memory/throughput 우열은 측정하지 않았다.

측정 절차는 workload·GUC·isolation을 고정하고, pg_locks/blocker snapshot과 SQL outcome을 함께 수집하며, observer query와 snapshot race를 기록하는 것이다. Source-only 이 장은 그 runtime 수치를 제공하지 않는다.

불변식과 Unknown

  • Grant-before-wakeup, outcome-before-release, buffer/leaf release-before-wait, recheck-after-wake를 지킨다.
  • Normal-lock 음성 검색을 Serializable predicate-lock promotion이나 extension protocol에 확장하지 않는다.
  • MultiXact recovery, prepared/hot-standby 모든 조합, server-wide shutdown, 실제 wait·memory·throughput은 미검증이다.

복습과 다음 장

PostgreSQL은 relation·tuple·XID·VXID·speculative token에 책임을 나눈다. 추상 wait/recheck lifecycle은 CUBRID와 비교할 수 있지만 self-lock 전체의 단일 equivalent는 없다. 다음 장에서는 MySQL server의 metadata lock과 InnoDB table/record lock이 책임을 다시 나누는 방식을 본다.
