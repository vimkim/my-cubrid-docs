MySQL/InnoDB — MDL과 data lock의 분리

11장목차13장

학습 목표와 owner 경계

이 장을 마치면 server metadata lock(MDL)과 InnoDB data lock의 owner, lifetime, wait graph, recovery를 분리하고, plain read·locked read·update·duplicate insert의 responsibility placement를 설명할 수 있다. 또한 InnoDB implicit record X가 CUBRID MVCCID self-lock과 목적 일부는 닮아도 resource identity가 왜 다른지 말할 수 있다.

THD / MDL_context                    trx_t / trx_lock_t
  MDL_ticket to MDL_lock               lock_t to table or page+record bitmap
  metadata namespace                   InnoDB data resource

MDL은 metadata object의 사용과 DDL을, InnoDB는 table intention·record/gap과 read view를 맡는다. MDL_SHARED_WRITE가 row X를 대신하지 않고 InnoDB LOCK_NONE이 metadata 무잠금을 뜻하지도 않는다. MYSQL-C001 MYSQL-C002 MYSQL-C020

Ticket owner는 connection별 MDL_context다. 이 표는 대표 enum 의미와 duration을 말하며 모든 SQL 문법별 request 전수를 주장하지 않는다.

InnoDB owner와 release

trx_t는 trx_locks, lock heap, record-lock count를 소유한다. lock_t payload는 table 또는 page+record bitmap이다. Commit/rollback release는 queue에서 transaction locks를 제거해 waiter에게 진행 기회를 주고 transaction lock heap을 비운다. 같은 page의 여러 record bits가 한 객체를 공유할 수 있어 “row마다 객체 하나” 모델은 정확하지 않다.

두 acquire/wait lifecycle

server MDL:
  acquire ticket, enqueue in MDL_lock, MDL cycle check,
  release ticket, reschedule compatible waiters

InnoDB data:
  row search/update/insert, table+record check,
  waiting lock_t with wait_lock and blocking_trx edge,
  suspend, deadlock/timeout handling,
  commit/rollback release and waiter wake

blocking_trx는 actual resource가 아니라 waiter에서 blocker transaction으로 가는 edge다. Actual resource는 waiting table/record lock_t다. 두 manager의 graph와 owner를 합치지 않는다.

통합 detector가 아니다

MDL 내부 cycle은 MDL detector가 처리하고 InnoDB table/record cycle은 InnoDB detector가 처리한다. MDL wait와 InnoDB row wait가 섞인 invisible edge cycle은 MDL graph만으로 완전하지 않을 수 있으며 source는 timeout 경계를 명시한다. 따라서 “MySQL의 모든 lock은 하나의 전역 WFG에 있다”는 모델은 틀리다.

XA prepare와 connection detach

XA prepare는 undo를 file-based PREPARED state로 만들고 durability 설정에 따라 LSN을 flush한 뒤 memory state도 PREPARED로 바꾼다. READ COMMITTED 이하에서 조기 해제하는 것은 전체 S/X가 아니라 gap 부분이다. Durable data를 바꾼 prepared transaction은 connection close 때 rollback/free되지 않고 session에서 detach되어 XA COMMIT/ROLLBACK을 기다린다. “prepare가 모든 lock을 푼다”는 설명은 금지된다.

Prepared XA의 server MDL backup

Disconnected prepared XA를 정리할 때 server는 transaction-duration MDL tickets를 XID별 backup context로 clone한다. Restart recovery는 원래 mode 정보가 없으므로 modified tables에 보수적인 MDL_SHARED_WRITE requests를 acquire한다. 다른 THD가 second phase를 수행할 때 backup tickets를 그 THD의 MDL_context로 복원한다. 이는 server MDL 책임이며 다음의 InnoDB IX resurrection과 다른 구조다.

Restart reconstruction

transaction recovery: undo에서 modified table_id 수집
dictionary recovery: recovered transaction locks 재구성
data lock boundary: modified tables의 IX resurrection
prepared transaction: PREPARED/XID 유지, recovery API에 보고,
                      background rollback에서 제외

정상 실행의 개별 lock_t queue나 waiter ordering을 디스크에서 그대로 replay한다고 말하지 않는다. Recovery가 재구성한다고 source-confirmed된 data-lock 범위는 undo-derived table IX다.

lock_sys startup/shutdown

Startup은 transaction system 다음에 lock_sys의 hashes, slots, mutex, event를 memory에 만든다. Shutdown은 변경 생산 중단·buffer flush·shutdown LSN·file close를 거친 resource cleanup에서 transaction system 다음 lock system을 닫는다. 이는 process-lifetime ordering이지 individual lock queue를 WAL로 지속한다는 근거가 아니다.

Resource pressure와 no-escalation 경계

Pinned search 범위에서는 record-count 기반 table escalation을 확인하지 못했다. Transaction lock structures가 10000개보다 많고 buffer pool이 running-out이면 DB_LOCK_TABLE_FULL로 실패하고 whole-transaction rollback 범주가 된다. 이 숫자는 일반 row-lock quota나 자동 escalation threshold로 해석하지 않는다.

Observability와 snapshot 한계

Monitor counters는 deadlock, graph rounds, waiting threads, timeout, record/table wait/request/create/remove/current count를 노출한다. Performance Schema의 data_locks/data_lock_waits iterator는 lock_sys shards를 restartable batch로 순회하고 transaction status는 lock count·heap bytes·row lock count를 출력한다. Mutex hold와 memory를 제한하는 대신 전체 결과는 원자적 snapshot이 아니며 chunk 단위 일관성만 가진다.

측정 시 isolation·timeout·buffer pool·workload를 고정하고 SQL outcome, data lock/wait rows, counters를 같은 시간창에 모으며 observer scan 자체와 batch race를 기록해야 한다. 이 source-only 장은 throughput 우열을 주장하지 않는다.

Durability boundary

Prepared 여부는 undo/LSN을 통해 durable state가 되지만 정상 runtime lock_sys slots/queues는 memory에서 생성·파기된다. Restart의 table IX와 MDL backup은 modified-table/transaction metadata에서 재구성된다. 따라서 “모든 lock이 durable”도 “prepare 뒤 lock 책임이 모두 사라짐”도 틀리다.

Not applicable과 Unknown

  • Not applicable: CUBRID식 transaction MVCCID S/X resource, record-count table escalation, MDL+InnoDB 통합 detector, runtime waiter queue의 durable replay는 pinned positive model에 direct equivalent가 없다.
  • Unknown: crash 전 record waiter fairness/ordering의 동일 재생, starvation 보장, 성능 수치, 모든 isolation의 gap/next-key 조합은 미검증이다.

복습과 다음 장

MySQL server MDL과 InnoDB data lock은 owner와 graph가 다르다. Implicit record X는 object 절감 목적은 닮았지만 transaction-ID resource가 아니므로 CUBRID self-lock의 direct equivalent가 아니다. 다음 장은 세 DBMS를 한 responsibility map으로 압축하되 semantic gap을 지운 등가 표시는 피한다.
