학습 목표와 질문

목표는 “X lock”만 말하지 않고 typed key, hierarchy, caller obligation까지 명시하는 것이다. INSTANCE(row 1)의 X와 TRANSACTION(M=1)의 X는 숫자와 mode가 같아도 왜 충돌하지 않는가?

typed key와 compatibility

LK_RES_KEY =
  (INSTANCE, oid, class_oid)
  (CLASS, class_oid, ROOT)
  (ROOT_CLASS, ROOT, NULL)
  (TRANSACTION, full MVCCID)

같은 global resource table을 쓰더라도 type tag와 payload가 identity를 나눈다. 같은 typed key로 모인 요청만 lock_Comp와 lock_Conv의 대상이다. Enum 숫자 순서나 “X”라는 이름만으로 충돌을 만들지 않는다. CUBRID-C001 CUBRID-C002

Conditional request는 기다리지 않는 conflict 결과이고 unconditional request는 timeout/WFG/suspend로 갈 수 있다. API가 grant를 반환해도 caller의 SQL predicate 성공을 보장하지 않는다.

Dependency seam과 call flow

query executor / scan policy
  locator / heap / B-tree: candidate와 latch 관리
  lock_object: class/instance 권리
  mvcc / heap history: snapshot-visible version
  log transaction table: MVCCID allocation/completion
  lock_transaction_mvccid: X self-lock 또는 S observer wait
commit/abort: outcome publication, 그 다음 release_all

Query layer는 어떤 lock이 필요한지 고르고, storage layer는 candidate와 latch를 관리한다. Lock Manager는 typed resource의 compatibility/wait를 소유하지만 SQL predicate와 version reconstruction은 소유하지 않는다.

Ordering·configuration·failure

  • 잘못된 class OID/mode는 hierarchy 의미를 깨므로 caller 입력 계약이다.
  • cond_flag와 transaction timeout은 queue 생성 여부와 대기 상한을 바꾼다.
  • Allocation 또는 self-lock ensure 실패 뒤 half-linked resource나 observable INSID를 남기지 않는다.
  • Lock escalation threshold는 concurrency와 entry 수의 trade-off이며 correctness mode table을 바꾸지 않는다.
