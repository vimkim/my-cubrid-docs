Acquire, conversion, escalation

4장목차6장

학습 목표와 upgrade 시나리오

이 장을 마치면 new request, re-request, conversion, no-wait miss, suspended wait, escalation을 서로 다른 branch로 구현할 수 있다. T1이 S를 가진 resource에서 더 강한 mode를 요청하고 T2가 incompatibility를 만들 때, T1은 old grant를 버리는가를 추적한다.

Interface에서 generic state machine까지

lock_object(thread, oid, class_oid, mode, cond)
  validate object/class; NULL_LOCK is no-op
  derive ROOT/CLASS/INSTANCE and required class intention
  acquire/check parent intention when required
  call lock_internal_perform_lock_object
    FIND_RESOURCE
    NEW_REQUESTER or EXISTING_HOLDER
    optional SUSPENDED
    POST_GRANT
    DONE

입력 오류, implicit class coverage, resource miss/allocation, re-request, conversion, conflict-without-enqueue, wait는 각각 다른 결과를 낸다. Standalone mode와 bulk loader의 precovered path는 ordinary server state machine의 branch가 아니라 front-door exception이다. MVCCID transaction resource도 generic acquire scheduler를 재사용한다. CUBRID-C052

Conversion은 fresh acquire가 아니다

if requested protection is already covered:
  reuse holder and increment count
else:
  target = lock_Conv[granted][requested]
  if target compatible with other holders:
    granted_mode = target
  else if zero_wait:
    keep old granted_mode; return NOT_GRANTED
  else:
    keep old granted_mode; blocked_mode = target
    place by Upgrader Positioning Rule; suspend

Blocked upgrader는 protection gap을 만들지 않는다. Old grant와 target blocked mode가 한 holder entry에 공존하고 WFG에도 들어간다. Enum 숫자 비교가 아니라 conversion table이 target을 정한다. CUBRID-C053

Escalation은 여러 resource를 상위로 치환한다

if BU_LOCK or missing class or already escalating: SKIP
choose superclass/class granule counter
if count less than lock_escalation: SKIP

if rollback_on_lock_escalation is true:
  set abort reason and return aborted before conversion

target = IS to S, or IX/SIX to X
drop transaction hold mutex before generic acquisition
try class conversion with FORCE_ZERO_WAIT
if granted:
  remove covered instance locks; preserve original class count
else:
  retain all pre-existing instance locks; return failure

Fast, miss, retry, failure

  • Fast: empty/compatible resource, equal re-request, compatible upgrade.
  • Miss: conditional conflict는 waiter 없이 not-granted.
  • Slow: incompatible new request 또는 blocked conversion은 published wait state로 suspend.
  • Retry: same-transaction lead waiter와 join하는 race에서 lead가 이미 깼으면 resource lookup부터 다시 시작.
  • Failure: entry allocation은 half-link 없이 error; escalation true-policy abort와 false-policy conversion miss를 구분.

Complexity와 trade-off

Hash bucket을 찾은 뒤 hot resource의 holder/waiter list work는 H holders와 W waiters에 대해 worst-case O(H+W)로 추론된다. 이는 source loop에서 유도한 구조적 bound이지 latency 측정이 아니다. Escalation은 entries를 줄이지만 class-level conflict domain을 넓힌다. Self-lock은 escalation과 달리 rows를 class로 합치지 않고 unfinished insert completion을 MVCCID key 하나에 모은다. CUBRID-C065
