학습 목표와 질문

T1이 key 7을 insert했지만 아직 commit하지 않았고 T2가 같은 key를 insert한다고 하자. 이 장을 마치면 “self”의 주체, X/S의 owner, wait 전 release, transaction-end ordering, wake 뒤 recheck를 한 sequence로 설명하고, 순서를 뒤집은 반례를 만들 수 있다.

한 줄 protocol과 직접 관측

T1: MVCCID M lazy allocation
    X ensure on TRANSACTION(M)
    publish INSID=M and INSERT_IN_PROGRESS in row/index

T2: find active other INSID M
    release page latch and transient object state
    request S on TRANSACTION(M), conflict with T1 X, wait

T1: publish commit/abort result and M inactive/completed
    unlock X(M), grant/wake waiter

T2: fully release S(M)
    verify M terminal, restart B-tree/record search
    decide unique/FK outcome from current state

Publication invariant: 다른 transaction이 관찰할 수 있는 INSID=M이 있고 inserter가 active라면 같은 M resource의 X self-lock이 이미 존재해야 한다. CUBRID-C030

Runtime-observed: Experiment 4의 한 contended dump에서 Transaction self-lock (inserter MVCCID = 5)에 T1 X_LOCK holder와 T2 S_LOCK waiter가 함께 있었다. T1 rollback 뒤 T2 key 7 insert가 성공했다. 이는 rendezvous identity와 좁은 결과만 관찰하며 latch release와 root restart는 source 근거다. raw dump · SQL output. CUBRID-C043

Unique/FK fast·wait·retry·failure

ensure_self_lock(T1):
  M = lazy_get_main_or_sub_mvccid()
  if local hint does not prove this M:
    acquire TRANSACTION(M), X
    on error: return error before INSID publication
  remember hint; return success

wait_for_inserter(T2, M):
  if M is own or already terminal: skip external wait, re-evaluate
  release leaf/overflow latch and transient row lock
  result = acquire TRANSACTION(M), S, normal wait policy
  if result is timeout/deadlock/interrupt/error: cleanup and propagate
  fully release S; require terminal state
  mark scan interrupted and restart search

finish_inserter(T1):
  publish main/sub MVCC completion or abort
  release X through self-lock/subtransaction/all-lock path
  grantable S waiter may wake

Unique checker는 root부터 key를 다시 찾는다. FK checker는 active inserting parent에서 leaf/overflow latch와 현재 row lock을 놓고 scan을 interrupted로 만든다. Delete-in-progress FK는 object-lock branch를 사용할 수 있어 “모든 FK wait가 self-lock”은 틀리다.

왜 row X가 아니라 MVCCID X인가

Successful MVCC insert fast path는 새 row마다 object X holder를 만들지 않는다. Transaction이 N개 row를 insert해도 한 main/sub MVCCID X가 여러 unique/FK observer의 completion target이 될 수 있다. Holder-side entry의 성장 방향을 inserted rows N에서 active MVCCID 수 A로 바꾸는 것이다.

비교 모델은 M_row ≈ N·E, M_self ≈ A·E + W·E다. E는 entry 크기, W는 실제 observer wait entries다. 이는 allocator/cache overhead를 뺀 symbolic formula이며 speedup 측정값이 아니다. Hot inserter에 W가 몰리는 fan-in, non-MVCC/tracking-failure row-X fallback, prepared 2PC OID tracking과 object-X materialization 때문에 “항상 O(1)”은 아니다. CUBRID-C033

PG/InnoDB와 왜 동일하지 않은가

PostgreSQL XID lock은 transaction XID의 Exclusive owner와 Share waiter라는 모양이 가깝고 speculative token은 decision-before-release 순서가 직접 닮았다. 그러나 tuple ownership은 XMAX/MultiXact에도 남고 VXID/speculative token의 caller와 scope가 다르다. InnoDB는 DB_TRX_ID로 per-record implicit X owner를 찾고 contention 때 그 record에 explicit X를 materialize한다. Transaction wait edge는 있지만 transaction-ID S/X resource는 없다. 모두 partial analogy이며 CUBRID식 단일 MVCCID rendezvous와 equivalent가 아니다.
