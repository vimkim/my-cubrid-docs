MVCC에도 왜 Lock Manager가 필요한가

version 선택과 상태 전이 조정은 서로 다른 문제다

목차2장

학습 목표와 질문

이 장을 마치면 snapshot visibility가 해결하는 read–write race와 row/self-lock이 해결하는 write–write·미완료 판정 race를 구분할 수 있다. 질문은 하나다. “T1이 아직 끝나지 않았는데 T2는 무엇을 지금 확정할 수 있는가?”

한 장면에서 네 SQL을 비교한다

T1: UPDATE account SET balance = 900 WHERE id = 1;
T1: INSERT INTO account VALUES (7, 700);  -- 아직 COMMIT/ROLLBACK 전

T2-A: SELECT balance FROM account WHERE id = 1;
T2-B: SELECT balance FROM account WHERE id = 1 FOR UPDATE;
T2-C: UPDATE account SET balance = balance + 1 WHERE id = 1;
T2-D: INSERT INTO account VALUES (7, 701);
동시 실행에서 SQL 동작별 판단과 추가 조정
T2 동작첫 판단추가 coordinationwait 뒤 재검사

FOR UPDATE보이는 후보class IX + latest row Xversion과 predicate

위에서 아래로 read-only visibility, locked read, writer serialization, unfinished-inserter completion wait로 책임이 늘어난다. CUBRID-C020 CUBRID-C022 CUBRID-C030 CUBRID-C031

직관: 사진과 출입권

Snapshot은 과거 시점의 사진처럼 어떤 version이 보이는지 정한다. X lock은 현재 상태를 바꿀 출입권이다. 과거 사진을 볼 수 있다고 두 사람이 동시에 다음 version을 확정할 권리가 생기지는 않는다. CUBRID는 plain reader에게 row S를 생략해 writer와의 불필요한 충돌을 줄이지만, locked read와 DML에는 class IX와 row X를 남긴다. CUBRID-C021 CUBRID-C022

잠금을 지웠을 때의 두 반례

  1. 두 writer: T2가 T1의 old version만 보고 곧바로 새 version을 확정하면 write–write serialization과 wait 뒤 predicate 재평가가 사라진다.
  2. 두 inserter: unique checker가 active inserter를 무시하면 둘 다 commit할 수 있다. 미완료 row를 즉시 duplicate로 확정하면 T1 rollback 뒤 합법적인 T2 insert를 거절한다.

Self-lock은 둘째 딜레마를 “지금 성공/실패를 고르지 말고 owner가 끝날 때까지 기다린 뒤 다시 검색하라”로 바꾼다. Owner는 inactive/completed 상태를 먼저 공개하고 X를 풀어야 한다. CUBRID-C030 CUBRID-C031 CUBRID-C032

불변식: visibility는 version을 선택하고, transaction lock은 상태 전이 권리와 미완료 결과의 대기 순서를 조정한다.

경계와 실패

Wakeup은 SQL 조건의 성공을 뜻하지 않는다. Holder가 rollback했는지 commit했는지, row가 삭제·갱신되었는지, unique key가 남았는지 다시 읽어야 한다. Timeout·interrupt·deadlock victim은 정상 grant와 다른 종료이며, caller는 이를 업무상 “없음”으로 바꾸지 말고 오류·retry 규칙으로 전파해야 한다.

복습과 다음 장

MVCC는 reader가 old version을 고르는 데 강하지만 변경 권리와 미완료 transaction outcome을 확정하지 않는다. 다음 장에서는 mutex, page latch, transaction lock, visibility를 보호 대상·owner·lifetime으로 분리한다.
