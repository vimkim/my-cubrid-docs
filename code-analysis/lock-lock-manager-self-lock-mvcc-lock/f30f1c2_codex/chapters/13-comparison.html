학습 목표와 비교 규칙

목표는 이름이 아니라 보호 상태, resource identity, owner/lifetime, wait/recheck 불변식으로 세 DBMS를 비교하는 것이다. Equivalent는 caller contract와 failure ordering까지 같을 때만 쓴다. 일부 책임만 같으면 Partial analogy, 대응 resource 자체가 없으면 No equivalent다.

Durability와 restart

Ordinary runtime holder/waiter tables는 세 제품 모두 memory coordination state다. CUBRID는 ordinary queue를 replay하지 않고 prepared 2PC object locks에 제한된 reacquisition이 있다. PostgreSQL은 qualifying heavyweight locks를 2PC record에 저장해 dummy owner로 복구한다. MySQL/InnoDB는 prepared/undo/modified-table metadata에서 table IX와 server MDL backup을 재구성한다. 이들은 “모든 lock durable”이라는 equivalent가 아니라 product별 prepared-transaction exception이다.

Not applicable: WAL/checkpoint/ARIES 전체 재구현과 crash 전 waiter ordering replay는 선언 범위 밖이다. 이 장은 lock responsibility가 durable transaction/storage state와 만나는 seam만 비교한다.

공정한 실험은 같은 workload/isolation/config에서 SQL outcome과 resource snapshot을 함께 수집하고 observer effect와 warm/cold state를 기록해야 한다. 서로 다른 source 구조만으로 처리량 순위를 만들지 않는다.

Self-lock 최종 판정

CUBRID: one MVCCID resource
  inserter X, unique/FK observer S, completion-before-unlock,
  appended-row holder entry aggregation

PostgreSQL: split responsibilities
  XID completion + VXID publication + speculative decision,
  normal row ownership remains in XMAX/MultiXact

MySQL/InnoDB: record-centered ownership
  DB_TRX_ID implicit owner, contention-time record X materialization,
  blocking_trx edge but no transaction-ID S/X resource

PostgreSQL 후보들은 각각 partial analogy이고 합쳐도 단일 Interface equivalent는 아니다. MySQL은 목적 일부가 유사하지만 resource identity에는 no equivalent다. 음성 결론은 고정 revision과 조사한 positive model/search 범위에 한정한다.

복습과 다음 장

비교의 단위는 이름이 아니라 보호 상태와 ordering이다. 다음 장은 CUBRID를 다시 구현할 수 있도록 typed model, total transitions, Interface obligation, recovery/error seam, conformance oracle을 하나의 blueprint로 묶는다.
