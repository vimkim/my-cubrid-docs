Branch-preserving workflow

execute(operation, snapshot, candidate):
  if operation == PLAIN_SELECT:
    evaluate mvcc_satisfies_snapshot
    if current is too new: follow previous-version chain
    return visible version; do not take qualifying row S

  if operation in {FOR_UPDATE, UPDATE, DELETE}:
    ensure class IX
    candidate = snapshot-visible candidate
    try conditional instance X
    if conflict:
      release transient page state
      wait unconditionally or propagate timeout/deadlock/interrupt
      refetch latest row and re-evaluate predicate
    mutate/reserve only if the latest condition still holds

  if operation == INSERT:
    ensure class IX and MVCCID self-lock before observable INSID
    use row-X fallback when lockless-insert preconditions fail
    publish new version; let unique/FK observer use completion wait

Plain scan의 old-version traversal은 storage/MVCC 책임이다. Locked path의 conditional-first 요청은 불필요한 wait를 피하지만, conflict 뒤 기존 candidate를 신뢰해서는 안 된다. CUBRID-C021 CUBRID-C022 CUBRID-C027 CUBRID-C030

Fast path는 visibility-only 또는 즉시 X grant다. Slow path는 transient state release, unconditional wait, refetch, predicate 재평가다. Failure path는 오류를 전파하며 stale candidate를 결과로 만들지 않는다.

정책, 비용, 병적 workload

Plain row-S 생략은 read/write conflict와 entry 수를 줄이지만 version history traversal 비용을 남긴다. Conditional-X-first는 uncontended path에서 queue work를 줄이지만 conflict 때 refetch/re-evaluation 비용을 낸다. Escalation은 많은 instance entries를 class lock으로 바꿔 memory를 줄이는 대신 충돌 범위를 넓힌다. Self-lock은 inserted row 수 대신 active MVCCID 방향으로 holder entries를 모으지만 hot inserter 하나에 많은 S waiter가 fan-in할 수 있다. 정량 임계값과 workload별 speedup은 이 책이 측정하지 않은 Unknown이다.

PG와 InnoDB의 책임 배치

PostgreSQL plain SELECT는 tuple visibility와 relation AccessShareLock을 조합하고, locked read/update는 tuple header XMAX/MultiXact와 transaction completion waits를 쓴다. InnoDB consistent read는 read view/old version을 사용하고 locking read/update는 table intention과 record S/X를 쓴다. “reader는 version, writer는 별도 coordination”이라는 책임 수준은 부분 유사하지만 resource와 retry 표현은 같지 않다.

복습과 다음 장

Visibility는 어느 version을 읽을지 정하고, class/row lock은 누가 latest logical state를 바꿀지 조정한다. 다음 장에서는 INSERT가 생략한 per-row X의 completion-wait 책임을 MVCCID self-lock이 어떻게 채우는지 본다.
