학습 목표와 검증 질문

이 장의 목표는 lock dump 문자열을 결론으로 착각하지 않고, precondition·resource identity·mode relation·SQL-visible outcome·cleanup을 하나의 oracle로 묶는 것이다. 질문은 네 가지다. 한 locked read가 class IX와 instance X를 같은 owner에게 두는가? X/X waiter가 release 뒤 진행하는가? MVCC plain read와 locked read가 갈라지는가? Unique observer가 정말 MVCCID self-lock에서 S로 기다리는가?

실험 계약

Mandatory observation은 wrapper의 요약이 아니라 hash가 봉인된 SQL을 absolute-path csql -C -u dba --no-auto-commit -i … -t DB로 실행한 receipt다. Supporting receipt는 setup, reset, holder, full-dump readiness, contended dump, post-release, owner-verified cleanup을 분리한다. Experiment 2–4의 accepted series는 observer를 시작하기 전에 full dump로 holder X를 확인했으며, contended lockdb -c에서 같은 resource block의 waiter를 확인했다.

owned DB provision → direct schema/config
  per repetition:
    direct reset → direct holder → FULL lockdb readiness
    → direct observer → CONTENDED lockdb relation
    → holder rollback + observer completion
  post-release dump → exact DB cleanup → registry/path absence

1 — hierarchy: 두 mode가 아니라 두 typed resource를 본다

Full dump에서 class와 instance block을 분리하고 holder의 transaction index가 같음을 확인했다. 이것이 class IX가 instance X를 “대신”한다는 해석을 막는다. Accepted direct output은 여기, lock dump는 여기다. 앞선 capture miss는 숨기지 않았고 한 번의 hierarchy 존재 증명만 Claim에 넣었다. CUBRID-C040

2 — release: elapsed가 아니라 same-resource X/X가 oracle

r10, r11, r12 모두 uncontended full dump로 holder X를 먼저 확인하고, observer 뒤 같은 instance block에서 granted X와 blocked X를 확인했다. Holder rollback과 observer exit는 모두 0이고 direct outputs는 모두 balance 101이다. One-way edge뿐이므로 장 제목의 deadlock 부분까지 실행했다고 말하지 않는다. r10 raw block, r10 SQL. CUBRID-C041

3 — visibility와 exclusion: 같은 row, 다른 책임

T1이 900을 아직 commit하지 않은 동안 T2의 plain SELECT는 100을 먼저 출력했다. 이어진 FOR UPDATE는 T1과 같은 instance에서 X waiter가 되었고 rollback 뒤 100을 얻어 101을 commit했다. 세 반복의 순서와 값이 같았다. 이는 “읽을 version 고르기”와 “변경 권리 얻기”가 다름을 행동으로 보이지만 runtime output만으로 exact source 함수를 명명하지 않는다. r8 X/X, r8 SQL. CUBRID-C042

4 — self-lock: literal transaction resource의 X/S

Observer 전 full dump는 unfinished inserter의 Transaction self-lock (inserter MVCCID=N) X holder를, contention dump는 같은 block의 S waiter를 보였다. MVCCID 값은 r8/r9/r10마다 달라 상수로 채점하지 않았다. 세 번 모두 T1 rollback 뒤 T2가 observer-after-wait row를 commit했다. 따라서 wait identity는 row/page가 아니라 transaction resource였지만 latch release와 root restart instruction은 source-confirmed 영역이다. r8 readiness, r8 X/S, r8 SQL. CUBRID-C043

Warm/cold, variability, observer effect

각 3회 series는 DB/server를 한 번 만들고 첫 반복 전에도 schema/readiness가 catalog·heap·index를 건드렸으므로 strict cold가 아니다. 뒤의 두 run은 reset만 한 warm run이다. Observer elapsed min/median/max는 Exp2 18.417/18.457/18.465s, Exp3 18.421/18.468/18.492s, Exp4 18.405/18.455/18.499s였다. 20초 SLEEP, debug build, polling, dump 때문에 생긴 capture-window 수치이며 성능 비교가 아니다.

SLEEP은 lock lifetime을 인위적으로 늘린다. lockdb는 administrative transaction을 만들고 lock table을 순회하며 scheduling을 교란한다. 그러므로 duration, polling attempt, transaction index, OID, MVCCID, dump order를 채점하지 않았다. Typed resource identity, same-block mode relation, SQL-visible final invariant, actor completion과 cleanup만 채점했다.

실패 receipt도 method evidence다

처음 readiness에 lockdb -c를 썼을 때 Exp2 r6, Exp3 r5, Exp4 r5가 holder를 보지 못했다. -c는 contention view라 아직 waiter가 없는 holder-only resource를 숨긴다. 실패 receipt를 덮어쓰지 않고, full dump readiness로 수정한 새 run ID만 accepted했다. Exp2 provisioning의 초기 gawk variable 충돌과 cleanup output-file 잔존도 실패 receipt로 보존했고, reserved/owned state cleanup과 exact path absence를 추가했다. “성공한 마지막 출력만 남기기”보다 실패가 어떤 alternative explanation을 제거했는지를 보여 주는 편이 재현성에 중요하다.
