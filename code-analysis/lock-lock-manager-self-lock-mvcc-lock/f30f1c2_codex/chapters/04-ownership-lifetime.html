학습 목표와 질문

목표는 resource 중심 lookup과 transaction 중심 cleanup이 왜 동시에 필요한지 설명하는 것이다. T1이 commit할 때, 전체 hash table을 검색하지 않고 자기 lock만 어떻게 찾을까?

세 구조와 두 탐색 방향

global hash: LK_RES_KEY to LK_RES
  LK_RES: key, aggregate holder/waiter mode,
          holder list, waiter list, non2pl list, res_mutex
               |
               +-- LK_ENTRY --+
                              |
transaction table: LK_TRAN_LOCK
  class hold list, instance/transaction hold list, waiting entries

LK_RES는 “이 key를 누가 잡고 기다리는가?”를 답한다. LK_ENTRY는 resource–transaction–thread를 잇는다. LK_TRAN_LOCK은 “이 transaction을 끝낼 때 무엇을 풀어야 하는가?”를 답한다. Acquire와 release의 출발점이 달라 양방향 link가 필요하다. CUBRID-C004

Allocation·partial failure·release

lookup key
  hit: existing LK_RES under res_mutex
  miss: allocate/init resource; publish atomically or unwind
allocate LK_ENTRY
  link resource side and transaction side only as one valid state
release/cancel
  unlink both directions; recompute aggregate mode
  publish grant before wake; reclaim empty resource

위 pseudocode는 구조적 구현 계약이다. 실제 failure branch의 세부 호출은 5~6장에서 source claim으로 좁힌다. 반쯤 한쪽 list에만 연결된 entry, aggregate mode와 list가 불일치한 state, empty resource가 lookup 가능한 state는 금지한다.

Memory와 scaling 모델

정확한 allocator overhead는 측정하지 않았다. 비교 가능한 symbolic formula는 M ≈ R·sizeof(LK_RES) + E·sizeof(LK_ENTRY) + T·sizeof(LK_TRAN_LOCK) + hash/pool overhead이다. R은 active typed keys, E는 holder/waiter entries, T는 transaction slots다. Row마다 X를 잡는 insert에서는 E가 inserted rows에 따라 늘 수 있지만, self-lock fast path는 holder-side entry를 active MVCCID 방향으로 모은다. Prepared 2PC와 fallback 때문에 항상 O(1)은 아니다. CUBRID-C033

Volatile/persistent 경계

Ordinary resource/entry/queue는 runtime coordination state이며 restart 때 그대로 replay하지 않는다. Durable row/version/log outcome이 먼저 복구되고 필요한 runtime table은 다시 초기화된다. Prepared 2PC object-lock reacquisition은 제한된 예외이며, 9장에서 정확한 비약속 범위를 다룬다.
