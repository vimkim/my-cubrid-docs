CUBRID flush/AIO에서 SX latch가 정말 필요한가

frame 안정성, strict READ, snapshot copy, 범용 SX, 전용 I/O freeze를 같은 책임 축으로 비교한 한국어 소스 분석서

먼저 답

Source-confirmed. 현행 synchronous snapshot-copy flush는 live frame이 아니라 분리된 image를 쓰므로 content freeze용 SX가 필요하지 않다. [CUBRID-C002]

Inferred. synchronous live-frame write에는 strict READ + retained fix가 정확성 후보이고, frame AIO에는 public SX 대신 전용 IO_WRITE_FREEZE + request-owned reference를 쓸 수 있다. copy AIO라면 live frame freeze가 필요 없다. 아직 성능 우위는 주장하지 않는다. [CUBRID-C007, CUBRID-C013, CMP-C002]

가장 중요한 정정: synchronous O_DIRECT는 direct이지만 asynchronous가 아니다. blocking call이면 buffer 안정 구간은 호출부터 반환까지다. submit 반환 뒤 terminal completion까지 buffer가 살아야 하는 계약은 AIO에서 생긴다. [CUBRID-C009, PG-C004, MYSQL-C003]

대상 독자는 C/C++, 운영체제의 memory와 I/O, B-tree 기초를 배운 대학 2학년 수준이다. DBMS buffer manager 내부를 몰라도 읽을 수 있도록 page와 frame부터 시작한다.

  • 10분 경로: 1장 → 2장 → 6장 → 10장으로 결론과 선택지를 본다.
  • 구현 경로: 3장 → 4장 → 5장 → 11장으로 owner, 전이, 순서, conformance test를 본다.
  • 검증 경로: 7장 → 12장 → Quiz로 command, raw receipt, Claim index를 확인한다.
  • B-tree SX 예시: ACTIVE 100만 건의 overflow OID AS-IS/TO-BE만 바로 읽는다.
