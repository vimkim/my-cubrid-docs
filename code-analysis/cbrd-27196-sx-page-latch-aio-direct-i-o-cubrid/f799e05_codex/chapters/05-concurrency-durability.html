5장 — 동시성과 durability

학습 목표. thread별 역할과 보호 state, 획득 순서, wait/wakeup의 happens-before를 설명하고 crash 지점별 durable 결과를 판정한다.

구체적 상황. flusher는 BCB mutex를 놓고 I/O하는데도 왜 두 번째 flusher와 victim은 막히고 writer는 진행할 수 있는가?

PGBUF_LATCH_READ와 WRITE는 content 접근을 조정하고, fix는 frame 교체를 막는다. 반면 FLUSHING_TO_DISK는 victim 후보 제외와 두 번째 flush 방지에 쓰이며 writer는 snapshot 이후 다시 page를 고칠 수 있다. [CUBRID-C001, CUBRID-C003, CUBRID-C007]

AIO에서는 submit thread와 completion thread가 다를 수 있다. current holder가 thread anchor에 귀속된다는 사실 때문에, READ holder 자체를 callback으로 넘기는 설계에는 별도 ownership protocol이 필요하다. [CUBRID-C008]

순서와 happens-before

  1. BCB mutex acquire 뒤 VPID·DIRTY·FLUSHING을 재검증한다.
  2. 같은 mutex 구간에서 image/LSA를 확정하고 FLUSHING을 publish한다.
  3. mutex release는 이후 writer가 FLUSHING과 cleared DIRTY를 보고 새 DIRTY 세대를 쓰기 전의 경계다.
  4. WAL durable 확인이 data submit보다 먼저다.
  5. completion은 BCB를 다시 잡아 terminal state를 publish하고, 그 뒤 waiter를 깨운다.

lock order: BCB mutex → 짧은 state/image 작업 → BCB mutex 해제 → WAL/DWB/file I/O → BCB mutex 재획득이다. 느린 I/O를 기다리며 BCB mutex나 unrelated page latch를 잡지 않는다. future frame AIO에서도 request claim은 BCB 안에서 하지만 completion wait는 BCB 밖에서 한다.

메모리 안정성과 WAL은 직교한다

content image 확정
    ├─ memory 계약: 누가 언제까지 이 bytes를 바꾸지 못하는가?
    └─ durability 계약: 이 image의 LSA보다 log가 먼저 durable한가?

CUBRID는 snapshot LSA까지 log를 먼저 flush한 다음 data/DWB write를 수행한다. memory가 안정해도 WAL 순서를 어기면 recovery가 깨지고, WAL이 먼저 나가도 I/O 중 input bytes가 바뀌면 잘못된 image가 기록된다. 둘 다 필요하다. [CUBRID-C004]

TDE는 plain frame과 다른 암호문 allocation을 만들고, DWB는 받은 image를 자기 slot으로 복사한다. 그래서 “live frame copy 제거”가 곧 전체 경로의 zero-copy를 뜻하지 않는다. InnoDB도 redo 선행과 output/completion lifetime을 별도 책임으로 유지한다. [CUBRID-C005, MYSQL-C005]

요약과 다음 질문

동시성의 핵심은 publish-before-wakeup과 frame non-reuse이고, durability의 핵심은 WAL-before-data와 DWB/recovery다. 다음 장에서는 이 invariant를 만족하는 정책 가운데 무엇을 선택할지 비교한다.
