1장 — 결론과 범위

학습 목표. SX가 필요하다는 말의 숨은 전제를 찾고, 이 책의 포함 범위·근거 수준·읽기 경로를 설명한다.

생각할 상황. flusher가 page 주소를 kernel에 넘긴 직후 다른 writer가 같은 주소를 바꾸면, 어떤 보호가 정확히 필요한가?

질문에 대한 정확한 답

“flush나 AIO에는 왜 SX가 필요한가?”라는 질문은 반쯤 잘못 놓였다. 필요한 것은 latch 이름이 아니라 I/O가 읽는 memory의 주소와 bytes가 소비 종료까지 유효하고 불변이라는 계약이다. 현행 CUBRID는 live frame을 쓰지 않고 snapshot을 쓰므로 이미 이 계약을 만족한다. [CUBRID-C002]

상황별 답
상황SX 필요성정확한 이유
현행 sync snapshot flush불필요I/O는 live frame과 분리된 image를 읽는다.
sync live-frame write유일한 답 아님strict READ가 writer를 막고 fix가 reuse를 막을 수 있다.

권고. flush/writeback만을 위한 기능이라면 public latch enum을 넓히기보다 BCB 내부 IO_WRITE_FREEZE + io_ref를 우선 검토한다. B-tree가 별도로 generic SX를 정당화하는지는 독립 결정이다. [CUBRID-C013, CMP-C002]

이전 설명에서 바로잡을 세 가지

  1. direct ≠ async. synchronous O_DIRECT의 input buffer는 blocking call 반환까지 안정하면 된다. AIO는 callback/terminal completion까지다. [CUBRID-C009, PG-C004, MYSQL-C003]
  2. AIO ≠ zero-copy. AIO가 request-owned snapshot을 읽으면 live frame writer를 막지 않는다.
  3. 이전 B-tree promotion summary를 성능 근거로 재사용하지 않는다. computed field를 누적·배율 처리하는 산식 때문에 상세 raw counter와 일치하지 않는 경로가 확인됐다. [CUBRID-C011]

포함과 제외

포함 범위는 CUBRID page-buffer flush funnel, latch/fix/BCB state, WAL·TDE·DWB seam, file write, runtime counter, PostgreSQL과 InnoDB의 같은 책임이다. 실제 SX/AIO 구현, read prefetch, device queue tuning, 성능 향상률은 제외한다. PostgreSQL/MySQL 서버는 실행하지 않았다.

이 책을 읽고 할 수 있어야 하는 일

  1. direct, async, copy/live-frame 세 축을 분리한다.
  2. content, frame lifetime, single flusher, WAL, re-dirty 책임을 각 state에 배정한다.
  3. 현행 copy, sync READ/fix, copy AIO, frame AIO를 같은 기준으로 평가한다.
  4. PG/MySQL의 SX를 CUBRID에 이름만 옮기면 안 되는 이유를 설명한다.

요약과 다음 질문

필요한 것은 SX라는 이름이 아니라 consumer 종료까지의 memory 계약이다. 다음 장에서는 page와 frame을 분리해 “어느 주소를 언제까지 지키는가”를 묻는다.
