4장 — 현행 CUBRID snapshot-copy flush

학습 목표. explicit/checkpoint/victim flush가 만나는 funnel을 찾고, skip·wait·snapshot·re-dirty·retry·failure branch를 상태 전이와 pseudocode로 재구성한다.

구체적 상황. flusher가 page image A를 복사한 직후 writer가 live frame B를 수정하면, A의 성공이 B의 DIRTY를 지워도 되는가?

정상 흐름: image를 먼저 분리한다

  1. BCB mutex 아래 dirty page를 확인하고 FLUSHING_TO_DISK를 세우며 기존 DIRTY를 지운다.
  2. plain page는 aligned stack buffer에 IO_PAGESIZE를 memcpy하고 TDE page는 cipher output을 만든다.
  3. DWB가 있으면 image를 DWB-owned slot에 다시 복사할 수 있다.
  4. page LSA와 oldest-unflush LSA를 snapshot한 뒤 BCB mutex를 놓는다.
  5. image LSA까지 WAL을 먼저 flush하고 DWB 또는 blocking fileio_write를 호출한다.
  6. BCB를 다시 보호해 success/error를 끝내고 waiter를 깨운다.

흐름 그림 설명: live frame에서 snapshot 화살표가 갈라진다. 왼쪽 live frame에는 writer가 새 변경을 넣고 DIRTY를 다시 세울 수 있다. 오른쪽 immutable output은 WAL 선행 뒤 DWB/datafile로 간다. 두 경로는 completion의 state 정리에서 다시 만난다. [CUBRID-C002, CUBRID-C003, CUBRID-C004, CUBRID-C005]

이번 pinned runtime의 SQL runner 세 번은 각각 20,000 rows와 양의 dirty counter를 만들었다. 세 workload와 background activity 및 online-backup trigger를 포함한 active observation window에서 global data-page I/O counter는 0에서 3으로 증가했다. exact caller나 unique page 수는 이 값으로 구별하지 않는다. [CUBRID-C006]

비교 DBMS는 live frame을 쓰는 대신 content SX와 별도 pin/io state를 묶는다. CUBRID의 snapshot+재더티와 목적은 같지만 writer overlap 정책은 다르다. [PG-C002, PG-C003, MYSQL-C004, MYSQL-C005, CMP-C001, CMP-C003]

caller에서 core funnel까지

explicit:    pgbuf_flush[_with_wal]
checkpoint:  pgbuf_flush_checkpoint → seq list
victim:      pgbuf_flush_victim_candidates → neighbor-safe
                          ↓
         pgbuf_bcb_safe_flush_internal
                          ↓
         pgbuf_bcb_flush_with_wal

sequence 그림 설명: caller는 BCB를 재검증한다. clean이면 바로 반환한다. 다른 flusher가 있으면 skip/wait한다. WRITE holder가 있으면 deferred request 또는 wait 경로로 간다. core에 진입한 한 flusher만 image를 확정하고 WAL 뒤 write한다.

branch를 보존한 pseudocode

flush(bcb, caller_policy):
  lock(bcb)
  if identity_changed or invalid: unlock; return MISS
  if not DIRTY: unlock; return FAST_CLEAN
  if FLUSHING: wait_or_skip(caller_policy); return RETRY_OR_DONE
  if WRITE_latched: request_deferred_flush(); wait_or_return(); return RETRY

  old_dirty_lsa = oldest_unflush_lsa
  set FLUSHING; clear old DIRTY
  output = encrypt_or_copy(live_frame)
  if output_failed: rollback_all_state(); wake_waiters(); return ERROR
  snapshot_lsa = output.lsa
  unlock(bcb)

  if wal_flush(snapshot_lsa) fails: goto common_error
  if DWB_enabled:
     if DWB_add(output) fails: goto common_error
  else if blocking_file_write(output) fails: goto common_error

  lock(bcb); clear FLUSHING; preserve any new DIRTY; wake; unlock
  if checkpoint_horizon still covers re-dirty: retry this BCB
  return OK

common_error:
  lock(bcb); clear FLUSHING; restore old DIRTY/oldest LSA; wake; unlock
  return ERROR

현재 TDE와 첫 DWB-slot 조기 실패가 pseudocode의 rollback_all_state로 합류하지 않을 수 있다는 점은 아래 결함 후보로 따로 표시한다. [CUBRID-C004, CUBRID-C010]

mark_is_flushing이 DIRTY를 먼저 지우므로 copy 이후 writer는 새 DIRTY 세대를 만든다. 성공 cleanup은 FLUSHING만 지워 그 새 변경을 보존한다. common write 실패는 dirty/oldest LSA와 waiter를 복구한다. [CUBRID-C003, CUBRID-C004]

소스 감사에서 발견한 결함 후보. TDE encryption 또는 초기 dwb_set_data_on_next_slot 실패는 mark_is_flushing 뒤 공통 rollback 전에 바로 return한다. 이 경우 FLUSHING/DIRTY/wakeup 정리가 빠질 수 있다. 소스상 분기는 확정했지만 fault-injection runtime 재현과 실제 발생률은 확인하지 않았다. [CUBRID-C010]
