7장 — 성능 관측과 runtime 실험

학습 목표. hot-path 비용과 memory/replacement trade-off를 계측 항목으로 바꾸고, exact command·raw receipt·observer effect를 이용해 runtime 주장 범위를 제한한다.

구체적 상황. Num_data_page_iowrites=3이면 정확히 page 세 장이 flush됐다고 말할 수 있는가?

성능 판정에 필요한 계측

  • snapshot copy bytes/time과 TDE/DWB copy bytes를 따로 잰다.
  • writer의 freeze wait 시간, reader 통과량, 최대 in-flight request/bytes/age를 잰다.
  • submit→completion latency, queue-full fallback, cancel/error cleanup 횟수를 잰다.
  • logical page flush와 DWB/home physical write를 구분한다.

현행 counter는 page write/skip/wait와 DWB 시간을 보여 주지만 위 AIO lifecycle이나 copy 비용을 직접 분해하지 않는다. TDE·DWB에 남는 copy를 빼먹으면 효과를 과대평가한다. [CUBRID-C005, CUBRID-C014]

카운터 해석 정정. B-tree promotion computed summary는 기존 computed slot에 raw complex counter를 다시 누적하고 배율을 적용하는 산식 경로를 가진다. 이 summary를 raw promotion count로 읽어 “insert당 횟수”를 계산한 결론은 폐기한다. [CUBRID-C011]

overflow OID 관측 경계. btree_find_free_overflow_oids_page에는 helper 전체 시간을 기록하는 bt_fix_ovf_oids counter/timer가 있다. 이는 경로가 관측 가능하다는 뜻이지, page별 fix 횟수·chain 길이·latch wait나 “알려진 병목”을 직접 증명하지 않는다. 이번 experiment-1 workload는 저카디널리티 index를 만들지 않았고 이 값을 검증 근거로 쓰지 않는다. [CUBRID-C017, CUBRID-C021]

copy AIO의 peak memory는 대략 max_inflight_requests × (IO_PAGESIZE + metadata)다. frame AIO는 그 copy 대신 같은 수의 frame을 replacement 불가로 만든다. buffer pool이 작거나 hot page가 몰리면 후자가 더 비쌀 수 있다. DWB의 PB_SYNC_ON_NFLUSH 같은 sync threshold와 TDE/DWB on/off도 반드시 실험 configuration에 기록한다.

overflow SX 후보는 (1) bulk-load 직후 같은 key DML, (2) runtime-only append, (3) old page에 hole을 만든 fragmentation을 나눠 측정한다. insert latency의 주기적 spike와 방문 page 수, leaf WRITE hold/wait, overflow READ/WRITE wait를 함께 기록해야 O(K) 탐색과 latch 충돌을 분리할 수 있다. [CUBRID-C018, CUBRID-C021]

고정 build에서 한 런타임 검증

Runtime-observed. 동일 SQL을 세 번 직접 실행했다. 매회 table을 다시 만들고 20,000 rows를 삽입했으며 Num_data_page_dirties는 각각 204,467 / 204,516 / 204,515였다. 세 workload·background activity·online-backup trigger를 포함한 active observation window에서 global Num_data_page_iowrites는 0 → 3으로 증가했다. [CUBRID-C006]

이 실험은 현행 활동을 보강할 뿐, memcpy, WAL-before-data, exact re-dirty/error branch, 미래 SX/freeze의 성능을 증명하지 않는다. 해당 내용은 pinned source와 향후 계측 실험으로 분리했다. 실험 문서와 안전한 runner는 experiment-1에 있다. [CUBRID-C006]

controls, observer effect, cleanup

positive control은 매 pass의 inserted_rows=20000과 dirty > 0이다. negative baseline은 workload 전 dirty/I/O counter 0이다. 그러나 watcher/statdump, background flush, backup과 DWB가 관찰 대상에 영향을 준다. 그래서 0→3을 backup caller나 unique page 수에 귀속하지 않는다.

cleanup 순서는 watcher 종료 → server stop → quiz/report-owned DB delete → backup file/directory delete → registry/process 확인이다. cleanup verification은 DB와 watcher가 남지 않았음을 기록한다. 첫 긴 DB 이름의 createdb 실패와 정리 receipt도 evidence에 남겼지만 Claim에는 성공 observation만 연결했다.
