6장 — copy·READ·SX·freeze·WRITE 선택

학습 목표. source-confirmed stable-buffer 계약과 설계 권고를 분리하고, workload·TDE/DWB·queue bound에 따라 정책을 고르는 알고리즘과 실패 fallback을 제시한다.

구체적 상황. 16 KiB copy 하나를 아끼려고 writer를 2 ms 멈추는 것이 항상 이득인가? 무엇을 측정해야 답할 수 있는가?

CUBRID strict READ는 WRITE를 배제하므로 synchronous live-frame write 구간에는 correctness 후보가 된다. 그러나 current holder의 thread ownership 때문에 true AIO로 그대로 연장하기 어렵다. [CUBRID-C007, CUBRID-C008, CUBRID-C009]

권고 아키텍처. flush/AIO만 필요하면 public SX보다 request-owned IO_WRITE_FREEZE + io_ref를 우선한다. B-tree도 독립적으로 SX semantics를 필요로 하고 동일한 공정성·승격 계약을 공유할 때만 generic SX의 비용을 정당화한다. [CUBRID-C013, CMP-C002]

아직 모르는 것. copy 제거가 writer stall, cache miss, TDE/DWB copy를 포함한 전체 비용을 이길지는 구현과 경쟁 workload 없이는 알 수 없다. [CUBRID-C014]

선택 pseudocode

choose_policy(config, page, queue):
  if not aio_enabled: return CURRENT_SNAPSHOT
  if page_needs_TDE_transform: return REQUEST_OWNED_OUTPUT
  if DWB_requires_copy and measured_copy_is_not_hot: return COPY_AIO
  if queue.inflight_bytes + IO_PAGESIZE > max_inflight_bytes:
     return configured_fallback(COPY_SYNC or CURRENT_SNAPSHOT)
  if writer_p99_budget is not measured: return COPY_AIO
  return FRAME_AIO_WITH_IO_WRITE_FREEZE

configuration/threshold: max_inflight_requests, max_inflight_bytes, queue-full fallback, freeze timeout, shutdown drain timeout은 명시적으로 둔다. 기본값을 임의로 정하지 않고 baseline 뒤 결정한다. copy memory는 최대 N × IO_PAGESIZE, frame mode의 replacement pressure는 최대 N pinned frames다.

복잡도: page당 state transition은 O(1)이고 copy는 O(page size)다. queue scan을 도입한다면 completion/timeout lookup은 request ID hash 또는 bounded ring으로 O(1)이어야 한다. hot-page 연속 flush, tiny buffer pool, TDE-heavy workload는 pathological case다.

B-tree 적용 예: ACTIVE OID가 한 키에 몰릴 때

쉬운 상황. CREATE INDEX idx ON t(status)를 만들었고, 100만 행의 status가 모두 ACTIVE라고 하자. 한 leaf record에 모든 OID를 넣을 수 없으므로 CUBRID는 다음처럼 한 key를 overflow OID page의 단일 연결 리스트에 연결한다.

leaf record for ACTIVE
[ key | leaf OIDs | flag 0x2000 | head VPID ]
                         |
                         v
                       H1 -> H2 -> H3 -> NULL

그림 설명: leaf record 끝에는 첫 overflow page의 VPID가 있고, 각 overflow page header에는 다음 page VPID 하나만 있다. 새 DML overflow page는 H1 앞, 즉 leaf 바로 뒤에 새 head로 들어간다.

(a) 어디에 저장하고, (b) 어떻게 표시하는가

Source-confirmed. overflow 여부는 별도 record header가 아니라 첫 OID의 slotid 상위 비트에 BTREE_LEAF_RECORD_OVERFLOW_OIDS (0x2000)로 pack된다. leaf record 꼬리에는 chain head VPID가 붙고, link가 없어지면 VPID와 flag를 함께 지운다. 런타임 증설은 기존 OID를 옮기는 것이 아니라 새 OID를 담은 page를 새 head로 만든다. unique index도 MVCC physical version이 공존하면 이 경로를 쓸 수 있으므로 “비유니크 전용”은 아니다. [CUBRID-C016, CUBRID-C019]

CREATE INDEX와 이후 INSERT는 다르다. 기존 100만 행으로 index를 처음 만드는 bulk loader는 현재 overflow tail을 들고 다음 page를 바로 연결한다. 아래 선형 탐색은 index 생성 자체가 아니라 그 뒤 같은 key에 DML로 OID를 추가할 때 나타난다. [CUBRID-C017]

(c) AS-IS — 한 장씩 WRITE로 확인

예시: bulk-load 뒤 H1과 H2는 가득 찼고, 마지막 H3에만 빈자리가 남았다고 하자.

leaf WRITE는 계속 보유
  H1 WRITE fix -> full 확인 -> H2 주소 복사 -> H1 unfix
  H2 WRITE fix -> full 확인 -> H3 주소 복사 -> H2 unfix
  H3 WRITE fix -> free 발견 -> WRITE를 잡은 채 caller에 반환
  caller        -> H3에 OID 삽입 -> H3 unfix

overflow page끼리는 latch crabbing을 하지 않는다. 탐색 helper가 동시에 잡는 overflow latch는 최대 한 장이지만, 호출자는 그동안 leaf WRITE latch를 계속 보유한다. 공간을 찾은 H3도 놓지 않고 그대로 삽입하므로 “사이에 다른 writer가 공간을 선점해 재검증한다”는 race는 없다. 비용은 방문 page마다 fix/unfix와 짧은 exclusive 구간을 반복하고, 긴 탐색일수록 leaf WRITE 보유 시간도 늘어난다는 점이다. [CUBRID-C017]

복잡도 정정. 한 번의 최악 탐색은 chain 길이 K에 대해 O(K)지만 매 INSERT가 O(K)는 아니다. DML이 새 page를 head에 만들면 그 page에 여유가 있는 동안 다음 INSERT는 보통 H1에서 끝난다. 긴 scan은 head가 찬 증설 시점, bulk-built chain 끝의 partial page를 찾을 때, 또는 delete로 빈칸이 깊이 생긴 경우에 주기적으로 나타난다. [CUBRID-C018]

TO-BE 후보 — 지나갈 page는 SX, 쓸 page에서 SX→WRITE

제안 SX가 READ와 호환되고 SX/SX·SX/WRITE는 충돌한다고 가정하면, H1·H2를 읽어 확인하는 동안 그 overflow page의 reader는 통과할 수 있다. H3에서 빈자리를 찾으면 SX를 놓지 않고 WRITE로 올린 뒤 OID를 넣는다. 한 modifier 후보만 존재하므로 경쟁 promoter가 먼저 끼어들어 재시작하는 경우를 없앨 수 있다. 다만 이는 현재 코드가 아니라 설계 가설이다. [CUBRID-C020]

“SX→WRITE는 항상 성공”의 정확한 뜻. 즉시·무조건 성공한다는 뜻은 아니다. page당 SX owner가 하나이고, 승격 대기 중 새 reader 유입을 닫고, 기존 reader가 유한 시간 안에 빠지며, 다른 page latch와 cycle이 없다는 조건에서만 경쟁 promoter 때문에 실패·재시작하지 않고 reader drain 뒤 획득한다고 말할 수 있다. timeout·cancel·shutdown은 여전히 별도 실패다. [CUBRID-C020]

중요한 한계. 표준 range scan은 leaf READ를 유지한 채 overflow page를 읽고, insert는 leaf WRITE를 먼저 보유한다. 따라서 overflow page만 SX로 바꿔도 upstream leaf 충돌이 이득을 가릴 수 있다. SX는 O(K), fix/unfix, 같은-leaf writer 직렬화를 없애지 않는다. 실제 이득은 leaf wait와 overflow wait를 분리한 prototype A/B 전까지 Unknown이다. [CUBRID-C020, CUBRID-C021]

주차장 비유. leaf WRITE는 건물 입구를 닫는 차단기이고, overflow latch는 각 층의 문이다. 층 문을 SX로 바꿔 보행자를 통과시켜도 입구가 이미 닫혔다면 체감 효과는 작다. 이 비유는 latch 호환성만 설명하며 O(K) 탐색, WAL, 공정성은 설명하지 않는다.

실무 판단. 저카디널리티 단독 index는 선택도가 낮고 이 overflow 구조도 만들기 쉽다. 무조건 생성하기보다 실제 predicate와 실행 계획을 확인하고, 필요하면 다른 선택 컬럼을 포함한 composite index와 비교한다. SX 최적화와 tail/free-page hint처럼 주소 탐색 자체를 줄이는 개선은 서로 다른 문제다.

현행 common write 실패는 dirty/oldest LSA와 waiter를 되돌리지만, TDE와 첫 DWB-slot 실패는 그 공통 cleanup 전에 return하는 결함 후보가 있다. shutdown도 현재의 동기 drain 순서에 AIO request quiescence가 추가되어야 한다. [CUBRID-C004, CUBRID-C010, CUBRID-C012]

queue 크기, fallback(copy 또는 sync), timeout 정책은 아직 구현·실험되지 않았다. “전용 freeze가 더 빠르다”가 아니라 “책임 경계가 더 좁다”까지만 이 보고서가 결론낸다. [CUBRID-C014]
