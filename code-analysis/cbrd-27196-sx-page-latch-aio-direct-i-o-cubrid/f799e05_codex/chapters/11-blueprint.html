11장 — 전용 I/O freeze 재구현 청사진

학습 목표. source를 다시 열지 않고도 request-owned frame AIO module의 Interface, data model, 모든 terminal transition, lock order, recovery, configuration과 conformance test를 구현할 수 있게 한다.

구체적 상황. submit은 성공했지만 callback이 error로 끝나고 동시에 shutdown이 시작되면, 누가 freeze와 ref를 정확히 한 번 해제하는가?

deep module: request가 lifecycle을 끝까지 소유한다

prepare(page)
  BCB mutex: dirty/identity 확인, FLUSHING + IO_WRITE_FREEZE + io_ref 설정
  output 선택: live frame | request-owned TDE/copy | DWB slot
  WAL dependency 만족
submit(request)
  성공: terminal completion만 cleanup 권한 보유
  실패: prepare를 정확히 한 번 rollback
complete(request, result)
  BCB identity/generation 재검증
  success/error/cancel별 dirty/LSA 처리
  IO_WRITE_FREEZE, FLUSHING, io_ref 해제; waiter wakeup

public caller는 latch mode를 조립하지 않고 prepare/submit/complete 계약만 사용한다. request 안에 VPID와 frame generation, input allocation, WAL dependency, result, cleanup state를 둔다. submit thread가 아니라 terminal state가 release 권한을 소유해야 current thread-holder 한계를 피할 수 있다. [CUBRID-C008, CUBRID-C013]

불변식

  1. I/O consumer가 끝날 때까지 input 주소와 bytes는 유효·불변이다.
  2. in-flight request가 있으면 해당 frame을 다른 VPID에 재사용하지 않는다.
  3. 같은 page generation에는 datafile flusher가 하나다.
  4. data submit 전에 image LSA까지 WAL이 durable하다. [CUBRID-C004]
  5. success/error/cancel/submit-failure 모두 cleanup을 정확히 한 번 실행한다.

정상·오류 shutdown은 새 submit을 닫고 모든 completion을 drain한 뒤 page pool과 DWB를 파기한다. [CUBRID-C012]

구현 순서와 ship gate

  1. copy 경로를 바꾸기 전에 lifecycle counter와 invariant assertion을 추가한다.
  2. 먼저 synchronous live-frame + READ/fix prototype으로 content/lifetime 계약을 검증한다.
  3. 그다음 request-owned freeze/ref와 fake async completion을 만들고 모든 실패 전이를 fault injection한다.
  4. TDE/DWB/queue-full fallback을 붙인 뒤 snapshot baseline과 다중 writer workload를 비교한다.
  5. writer p99, throughput, copy bytes, memory, correctness 중 하나라도 기준을 벗어나면 copy AIO 또는 현행으로 되돌린다.

이 청사진은 구현 전 설계 inference다. InnoDB의 SX+io_fix+completion 책임 묶음과 의미상 대응하지만, CUBRID writer admission 전체를 계측·시험하기 전 correctness나 성능을 확정할 수 없다. [CMP-C001, CUBRID-C014]

2. abstract data model과 layout

BCB additions (volatile, on-disk layout change 없음):
  uint64 frame_generation;
  uint32 io_ref_count;
  bool   io_write_freeze;
  request_id active_write_request;   // 0 or exactly one

write_request (queue-owned allocation):
  request_id id; VPID vpid; uint64 frame_generation;
  BCB *bcb; input_kind; void *input; size_t length;
  LOG_LSA image_lsa; LOG_LSA old_oldest_unflush_lsa;
  atomic terminal_owner; terminal_result result;
  bool restored_dirty; timestamps; error_code;
  • identity: (VPID, frame_generation)이 callback의 old-frame/new-page 혼동을 막는다.
  • allocation: bounded request pool에서 가져오며 queue limit 전에 frame을 freeze하지 않는다.
  • reclamation: terminal cleanup과 waiter publish가 끝난 뒤 request를 pool로 돌린다.
  • persistent compatibility: BCB/request는 volatile이고 page/DWB/WAL layout을 바꾸지 않는다. TDE output 형식과 DWB recovery는 현행을 유지한다. [CUBRID-C005, CUBRID-C015]

4. concurrency와 ordering

  1. request-pool slot을 먼저 확보한다. queue full이면 BCB를 건드리지 않고 fallback한다.
  2. BCB mutex 아래 identity/dirty를 재검증하고 active ID, FLUSHING, freeze, io_ref를 한 번에 publish한다.
  3. reader는 freeze와 무관하게 READ 가능하다. writer/두 번째 flusher/victim은 각각 writer gate/active ID/io_ref에서 대기 또는 retry한다.
  4. BCB mutex를 놓고 WAL을 기다린 뒤 submit한다. BCB나 다른 page latch를 잡은 채 completion을 기다리지 않는다.
  5. completion CAS 승자가 BCB mutex 아래 result와 state를 publish한 뒤 waiter를 깨운다.

fairness는 writer waiter가 생기면 신규 freeze admission을 제한하는 gate와 oldest-request metric으로 방어한다. bounded timeout은 request를 버리는 시간이 아니라 cancel을 요청하고 terminal 확인을 기다리는 상위 정책이다.

5. startup, shutdown, abort, recovery

startup: init request pool → queue/completion workers → submit gate OPEN
shutdown: gate CLOSED → stop new flush scheduling → drain/cancel terminal
          → log/data/DWB synchronize → workers stop → pool/page buffer destroy
abort: terminal CAS → dirty/LSA rollback → state/ref clear → wake → reclaim
restart: volatile request/freeze는 없음 → DWB home-page recovery → WAL redo
         → 새 BCB/frame state로 시작

current shutdown 순서를 유지하되 AIO drain을 page-pool free보다 앞에 삽입한다. crash 후 active request를 되살리지 않고 persistent WAL/DWB만 신뢰한다. [CUBRID-C012, CUBRID-C015]

7. 구현 순서와 conformance oracle

  1. 현행 snapshot path의 state assertion과 metrics를 먼저 추가한다.
  2. request pool과 fake completion executor를 만들고 disk I/O 없이 total transition을 fault-inject한다.
  3. synchronous live-frame READ/fix prototype으로 writer exclusion/non-reuse를 검증한다.
  4. FRAME_AIO_FREEZE를 plain, TDE, DWB 순으로 연결한다.
  5. shutdown/restart fault matrix를 통과한 뒤에만 performance A/B를 실행한다.
