2장 — page, frame, image와 네 I/O mode

학습 목표. page·frame·image를 구분하고 direct/buffered, sync/async, copy/live-frame을 직교 축으로 분류한다.

구체적 질문. 같은 O_DIRECT라도 blocking pwrite와 AIO request의 buffer 수명이 왜 다른가?

주소 하나로 생각하기

frame F의 주소 p  ──>  I/O 함수 또는 I/O request

Q1. I/O는 p를 언제까지 읽는가?
Q2. 그동안 누가 p[0..page_size)를 바꿀 수 있는가?
Q3. buffer pool이 F를 다른 page Q에 재사용할 수 있는가?

page는 디스크의 논리 block이고, frame은 page를 담는 재사용 가능한 memory slot이다. page image는 특정 순간의 bytes다. live frame, plain snapshot, TDE 암호문, DWB slot은 같은 page를 나타낼 수 있지만 서로 다른 allocation이다.

latch는 주로 Q2의 content 접근을, fix/pin/reference는 주로 Q3의 identity와 lifetime을 지킨다. 동기 file write가 반환될 때까지 input을 소비하는 CUBRID와, sync/callback lifetime을 명시적으로 나누는 InnoDB가 이 구분을 뒷받침한다. [CUBRID-C009, MYSQL-C003]

O_DIRECT는 첫 축, AIO는 둘째 축, frame zero-copy는 셋째 축이다. PostgreSQL의 current data write는 blocking pg_pwritev이고 InnoDB는 sync와 async buffer lifetime을 다른 Interface로 표현한다. [PG-C004, MYSQL-C003]

네 mode의 안정 구간

네 I/O mode의 input 안정 구간

frame AIOlive frameterminal completioncompletion 전 금지

그림 설명: sync 두 mode의 보호 막대는 call 시작에서 return까지다. copy AIO의 막대는 copy allocation에만 submit에서 completion까지 놓인다. frame AIO의 막대는 live frame에 submit 전 freeze부터 completion까지 놓인다. [CUBRID-C002, CUBRID-C009, MYSQL-C003]

이 책의 “zero-copy”는 page buffer가 snapshot copy를 만들지 않는다는 좁은 뜻이다. TDE, DWB, kernel, device까지 end-to-end copy 0을 약속하지 않는다.

전체 그림

transaction writer --WRITE--> live frame
reader --------READ/S------> live frame
flusher --snapshot 또는 freeze--> WAL gate --> DWB/datafile I/O
victim/replacer --fix/io_ref 확인--> frame reuse
completion --result--> dirty/FLUSHING/ref/waiter 정리

그림 설명: writer와 reader는 live frame에 접근한다. flusher는 사본을 만들거나 frame을 얼린 뒤 WAL gate를 거쳐 I/O한다. victim은 reference를 확인하고 completion은 모든 임시 state를 끝낸다.

요약과 다음 질문

direct는 cache 축, async는 완료 축, copy는 memory 축이다. 다음 장에서는 각 allocation의 owner와 caller pre/postcondition을 고정한다.
