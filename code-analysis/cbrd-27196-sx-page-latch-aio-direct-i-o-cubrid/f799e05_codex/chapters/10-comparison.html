10장 — 세 DBMS responsibility map

학습 목표. 세 엔진을 공통 scenario와 responsibility 축으로 비교하고 각 행을 Equivalent, Partial analogy, No equivalent로 판정한다.

구체적 상황. 동일한 dirty page P를 reader가 읽는 동안 disk로 내보낼 때, 세 엔진은 어떤 memory를 I/O에 넘기고 누가 completion을 끝내는가?

이름이 아니라 책임으로 대응시킨다

같은 scenario의 세 흐름

CUBRID:  claim FLUSHING → copy image → unlock → WAL → sync write → re-dirty aware cleanup
PG:      pin + content SX → claim IO bit → WAL → live frame sync write → terminate IO
InnoDB:  page SX + io_fix → redo → DWB → live frame AIO → callback/pass cleanup

그림 설명: 세 흐름 모두 WAL과 single-I/O state를 거친다. CUBRID만 snapshot 뒤 writer를 허용하고, InnoDB만 traced normal path에서 callback이 장기 SX/io_fix를 끝낸다.

CUBRID snapshot path와 두 비교 DB의 live-frame path는 목적은 같지만 mechanics가 다르다. 공통점은 content, lifetime, single-I/O, WAL을 분리한다는 것이고, 차이는 writer overlap과 re-dirty를 허용하느냐이다. [CMP-C001, CMP-C003]

CUBRID READ와 InnoDB S는 이름만 비슷하다. CUBRID READ는 WRITE를 배제하지만 InnoDB S는 SX와 호환된다. 그러므로 lock mode 이름을 일대일로 번역하면 틀린다. [CMP-C002]

안전한 비교 결론. PostgreSQL/InnoDB는 “live frame을 쓰려면 SX 하나면 된다”가 아니라, reader-compatible writer exclusion + non-reuse reference + single-I/O state + completion ownership이 필요하다는 설계 증거다. CUBRID는 이를 public SX가 아닌 internal state로 구현할 수 있다. [CMP-C001, CMP-C002]

PostgreSQL의 buffer SHARE_EXCLUSIVE와 InnoDB block SX는 “reader와 공존하고 modifier를 하나로 제한한다”는 호환성 한 축에서는 Partial analogy다. 그러나 PostgreSQL nbtree는 그 mode를 삽입에 쓰지 않고 SX→X promotion API도 없으며, InnoDB의 tree/block SX 경로도 CUBRID처럼 head부터 overflow page를 first-fit 탐색하지 않는다. 그러므로 두 DBMS는 SX 호환표의 참고 사례이지 이 성능 제안의 검증 사례가 아니다. [PG-C007, MYSQL-C007, CMP-C006]

비교 한계: 세 source revision, persistent layout, startup/shutdown, configuration, counter 명칭과 runtime은 같지 않다. PG/MySQL은 실행하지 않았고 성능 수치 비교도 하지 않았다. 따라서 timing·ABI·page-format equivalence는 No equivalent다.
