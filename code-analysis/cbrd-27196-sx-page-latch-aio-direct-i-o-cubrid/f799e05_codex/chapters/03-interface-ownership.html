3장 — Interface와 owner/lifetime

학습 목표. flush caller의 pre/postcondition과 error 의무를 말하고, BCB·frame·snapshot·request의 owner와 reclamation 시점을 구분한다.

구체적 상황. submitter가 return한 뒤 callback이 page를 정리한다면, thread-owned holder와 request-owned reference 중 누가 release 권한을 가져야 하는가?

Module seam과 caller 의무

flush caller
  -> page buffer: image/state 결정
  -> WAL: image LSA까지 먼저 durable
  -> TDE: plain -> encrypted output
  -> DWB: torn-write용 slot/image
  -> file I/O: input buffer를 call return까지 소비
  -> page buffer: success/re-dirty/error 정리

CUBRID public content latch는 READ/WRITE이고 FLUSH는 fix에 쓰지 못하는 block pseudo-mode다. 현행 flush는 public holder를 새로 만들지 않고 BCB mutex/flags에서 시작한다. image를 만든 뒤 WAL과 data write를 호출하고 다시 BCB state를 끝낸다. [CUBRID-C001, CUBRID-C002, CUBRID-C004]

ordering precondition: image와 LSA를 같은 BCB 세대에서 확정하고, BCB mutex를 놓은 뒤 WAL과 느린 I/O를 수행한다. postcondition: 성공·실패 어느 쪽도 FLUSHING/ref/waiter를 고아로 남기지 않는다.

CUBRID holder는 thread anchor에 연결되고 pgbuf_unfix는 current thread의 holder를 해제한다. 이것은 synchronous call에는 자연스럽지만 다른 completion thread가 끝낼 AIO request ownership과 같지 않다. PostgreSQL도 AIO subsystem pin과 I/O state를 별도로 두고, InnoDB도 callback/pass로 소유권을 넘긴다. [CUBRID-C008, PG-C003, MYSQL-C003]

TDE와 DWB는 snapshot copy와 목적이 다르다. plain snapshot을 없애도 암호화 output이나 DWB slot copy가 남을 수 있다. [CUBRID-C005, MYSQL-C004]

future request의 memory 하한은 대략 N × (request metadata + copy policy이면 IO_PAGESIZE)다. frame policy면 page-size copy는 줄지만 N개의 frame이 victim 불가 상태가 된다. 따라서 queue bound는 memory와 replacement pressure를 동시에 제한해야 한다.

요약과 다음 질문

latch는 content, fix/ref는 identity, request는 cross-thread completion을 소유한다. 다음 장에서는 이 객체들이 정상·재더티·실패에서 어떻게 전이하는지 끝까지 추적한다.
