11장 — 성능과 관측: 카운터, 함정, 측정법

학습 목표

9장의 결정 게이트가 요구하는 수치를 실제로 걷는 방법과, 그 과정에서 만나는 두 가지 함정(수집 게이트, 카운터 이름)을 익힌다.

함정 1 — 수집 게이트: 카운터는 기본적으로 꺼져 있다

Source-confirmed + Runtime-observed stats_on은 숨김(PRM_HIDDEN) 서버 파라미터로 기본 false이고, perfmon 카운터는 watcher가 붙어 있는 동안에만 누적된다(perf_monitor.c:3200-3206: PRM_ID_STATS_ON이 참일 때만 상시 watcher 등록). 실제로 watcher 없이 20,000건 insert를 실행한 기록에서는 모든 카운터가 0이었다. watcher가 되는 방법: (a) cubrid statdump -i <초>를 붙여 두기(전역), (b) csql에서 ;set communication_histogram=yes + ;.hist on(해당 트랜잭션만), (c) cubrid.conf에 stats_on=yes. [CUBRID-C014]

함정 2 — 이름이 그럴듯한 카운터: Num_data_page_flushed

Runtime-observed + Source-confirmed experiment-2에서 checkpoint가 dirty page를 실제로 디스크에 밀어냈는데도(Num_data_page_iowrites 229→1163) Num_data_page_flushed는 0에 머물렀다. 소스를 보면 이 카운터의 증가 지점은 pgbuf_flush_victim_candidates(page_buffer.c:4167) 한 곳뿐 — 즉 victim 후보 flush만 세고 checkpoint flush는 세지 않는다. 이름과 실체의 이 불일치는 본 보고서가 소스와 런타임으로 독립 확인했고, CUBRID JIRA의 page buffer EPIC에도 결함 D6으로 기록해 두었다(발췌 사본: research/jira/CBRD-27193.md). [CUBRID-C012]

교훈. SX 도입 전후 비교의 오라클을 정할 때 카운터 이름을 믿지 말고 증가 지점을 소스에서 확인하라. 특히 "flush 처리량" 비교에 Num_data_page_flushed를 쓰면 checkpoint 비중이 통째로 빠진 결론이 나온다.

비용의 위치 (hot path 지도)

  • memcpy 사본: flush당 IO_PAGESIZE — flush-pressure 워크로드에서 CPU 프로파일(perf)의 pgbuf_bcb_flush_with_wal 아래 memcpy 비중으로 측정.
  • 승격 실패 세금: promote_fail 1건 = 루트 재탐색 + WRITE 하강. B-tree 경합 워크로드에서 promote_fail 증가율과 tps 하락의 상관으로 측정.
  • lock-free READ 경로: SX 도입이 이 CAS 경로에 분기를 더하면 read-heavy가 물러날 수 있다 — 무회귀 확인 대상.
  • 관측 비용 주의: watcher 자체가 카운터 증가 비용을 켠다. 성능 비교는 양쪽 모두 watcher를 켠 상태로, 절대치가 아니라 delta로 비교한다.

요약

측정 전 두 함정을 기억하라: watcher 없으면 0만 나오고, 이름만 믿으면 틀린 오라클을 고른다. promote_fail과 iowrites가 9장 게이트의 두 기둥이다. 다음 장은 이 도구들로 실제 수행한 실험 기록이다.
