16장 — 재구현 청사진: CUBRID에 SX를 넣는 설계 스케치

학습 목표

지금까지의 사실들로부터, SX를 CUBRID에 도입할 때의 인터페이스 계약·상태 표현·경로별 변경·검증 순서를 독립 구현자가 따라갈 수 있는 수준으로 정리한다. 이는 구현 지시가 아니라 조사(JIRA CBRD-27196) 산출물의 설계 스케치다.

1. 인터페이스 계약 (제안)

  • 호환성: SX는 READ와 공존, 다른 SX·WRITE와 배타 (15장 용어 대응의 세 엔진과 동일 행렬).
  • 획득 규칙: SX는 (a) fix 시점 요청 또는 (b) READ 보유 중 nowait 승격으로만. blocking READ→SX는 API 차원에서 금지 — InnoDB는 이를 "S 보유 중 SX 획득 실패" 규칙으로, PostgreSQL은 nowait 전용 함수로 강제했다 [MYSQL-C006, PG-C005].
  • SX→WRITE 승격: 대기 등록 시 waiter_exists를 세워 신규 lock-free reader를 차단한 뒤 fcnt가 자기 fix 수로 줄 때까지 대기. 경쟁 promoter가 구조적으로 없으므로 실패 코드가 필요 없다(7장 논증).
  • downgrade: SX→READ 해제는 sx 표시 제거로 자연 처리. WRITE→SX는 1단계 범위 밖.
  • 재귀: 같은 스레드의 중복 SX는 owner 비교로 허용 여부 결정(미해결 — 17장).

2. 상태 표현 (제안 2안 비교)

3. 경로별 변경 목록

  1. lock-free READ: grant 조건에서 sx bit는 무시(공존이 목적). 단 sx bit 조작 자체는 반드시 같은 word의 CAS 재시도 루프 — reader가 mutex 없이 다니므로 mutex-보호 read-modify-write는 lost update를 만든다 [CUBRID-C003].
  2. 대기열/wakeup: pgbuf_block_bcb에 SX 대기 클래스 추가. wakeup 시 READ 묶음 + SX 1명까지 동시 기상 가능, WRITE는 단독. PGBUF_LATCH_FLUSH pseudo-mode 대기자와의 구분 유지 [CUBRID-C001].
  3. 승격 함수: SX→WRITE용 새 함수(실패 분기 없음). 기존 pgbuf_promote_read_latch는 이행기 동안 공존.
  4. flusher 소유권: flush 스레드는 fix 없이 동작하므로 holder 목록과 독립인 sx_owner가 소유를 표현(InnoDB의 io_fix 유사). 기존 FLUSHING_TO_DISK 플래그와 통합할지는 미해결.
  5. conditional 축: PGBUF_CONDITIONAL_LATCH와 조합한 nowait SX가 1급 시민이어야 한다 — InnoDB flush 완충 전략 전체가 nowait 위에 서 있다 [MYSQL-C002].
  6. ordered fix/watcher: 다중 page latch 순서를 다루는 pgbuf_ordered_fix의 재획득 규칙에 제3 mode가 주는 영향 조사 필요.
  7. SA_MODE: 단일 스레드 standalone에서는 승격이 무조건 제자리 전환이듯(page_buffer.c:3057) SX도 자명한 grant로 정의 — loaddb 등 SA 경로의 assert 통과 확인 [CUBRID-C013].
  8. 관측: SX 획득/대기/승격 카운터를 perfmon에 추가하되, 11장의 교훈대로 증가 지점과 이름을 일치시킨다.

4. 단계적 도입과 검증 순서

  1. 0단계 — baseline 측정: promote 실패율, flush memcpy CPU 비중 (9장 게이트 1).
  2. 1단계 — flush 내부 상태 한정: pgbuf_fix 공개 계약 불변. flusher만 sx bit를 쓰고 plain page 무사본 flush. 검증: 6장 불변식(WAL 선행, 재더티) 유지 + 9장 게이트 2 워크로드. TDE/DWB 경로는 사본 유지.
  3. 2단계 — public fix mode: B-tree 하강에 SX 노출. 검증: 5장 fallback 제거 후에도 delete/merge 3-page 시퀀스가 순서 교착 없이 동작(다중 page 승격 규칙 필요 — 미해결), promote_fail 소멸 확인.

5. 적합성 테스트 후보

  • 동일 page에 reader N + SX 1 공존, SX→WRITE 승격 완료가 유한 시간 내 보장되는가 (기아 없음).
  • READ 보유 스레드의 SX 요청이 즉시 실패하는가 (전제조건 강제).
  • flush 중(1단계) reader 통과 / writer 대기 / 재더티 소멸 확인.
  • latch timeout 빈도가 도입 전과 동일한가 (7장 — 교착 방어가 얇으므로 회귀 지표로 사용).
  • quiz-1/quiz-2 오라클이 도입 후 어떻게 변해야 하는지 명시 (promote_fail → 0, flush memcpy 소멸).

요약

sx bit + owner 필드, CAS 전용 조작, nowait 획득 규칙, flush-먼저 단계 도입, 그리고 게이트별 측정 — 이 순서면 독립 구현자가 소스를 다시 열지 않고 착수할 수 있다. 남은 미해결 항목은 17장에 모았다.
