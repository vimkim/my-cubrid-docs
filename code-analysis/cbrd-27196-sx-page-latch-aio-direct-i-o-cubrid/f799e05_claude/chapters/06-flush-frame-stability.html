6장 — flush 깔때기: 사본, WAL 선행, 재더티 추적

학습 목표

dirty page가 디스크로 가는 유일한 길(pgbuf_bcb_flush_with_wal)을 단계별로 추적하고, 사본이 왜 존재하는지, 무엇이 durability(내구성 — 커밋된 변경이 장애 후에도 남는 성질)를 지키는지 이해한다. 이것이 SX의 두 번째 적용 후보(사용자 질문 2)의 실체다.

시나리오

여러 세션이 어떤 table의 page들을 수정해 dirty로 만들었다. checkpoint(복구 시작점을 앞당기기 위해 dirty page들을 디스크에 반영하는 작업)가 시작되어 flusher가 이 page들을 디스크에 써야 한다. 그동안에도 세션들은 같은 page를 계속 읽고 쓰고 싶어 한다.

깔때기의 전체 흐름

Source-confirmed buffer pool의 모든 data page 쓰기는 pgbuf_bcb_flush_with_wal(page_buffer.c:10733) 한 함수로 합류한다. 호출원은 page flush 데몬, victim 경로(pgbuf_bcb_safe_flush_internal), checkpoint 순차 flusher, neighbor flush 등이다. [CUBRID-C007]

그림 설명: 깔때기는 BCB mutex 아래에서 플래그를 세우고 사본을 만든 뒤 mutex를 풀고, WAL을 먼저 디스크에 내린 다음 사본을 DWB를 거쳐 데이터 볼륨에 쓴다. mutex 해제 이후 원본 frame의 수정은 자유이며 DIRTY 재설정으로 추적된다.

사본은 왜 존재하나

디스크로 가는 이미지가 쓰는 도중에 바뀌면 안 되기 때문이다. 선택지는 셋이었다: (a) I/O 내내 WRITE latch로 막기 — reader까지 서고 I/O는 느리다. (b) I/O 내내 "수정만 금지" 상태 유지 — 그런 중간 mode(SX)가 없다. (c) 사본을 떠서 원본을 풀어 주기 — CUBRID의 선택. 사본 덕에 writer조차 I/O 동안 자유라는, 세 DBMS 중 가장 관대한 동시성을 얻은 대신, 모든 plain page flush가 16KiB memcpy를 지불한다. [CUBRID-C007]

durability는 무엇이 지키나

Source-confirmed 사본이 아니라 WAL 순서가 지킨다. 깔때기는 data page를 쓰기 전에 그 page의 LSA(log sequence address — 마지막 수정 로그의 위치)까지 로그를 먼저 디스크에 내린다(:10848). 그래서 "디스크의 page가 가리키는 시점까지의 로그는 반드시 디스크에 있다"가 성립하고, 장애 시 로그 재적용으로 복구된다. flush 도중 원본에 가해진 새 수정은 사본에 없지만, DIRTY 재설정 덕에 다음 flush가 반드시 다시 쓴다 — 잃는 것은 없고 "다시 쓸 일"이 남을 뿐이다. flush가 I/O 오류로 실패하면 DIRTY와 oldest_unflush_lsa(이 page가 처음 dirty가 된 시점)를 복원해 재시도를 보장한다. [CUBRID-C008]

불변식. (1) data page 디스크 기록 전, 그 page LSA까지의 로그가 디스크에 있다. (2) DIRTY가 꺼진 page는 "디스크 이미지 = 사본 시점의 메모리 이미지"이거나 FLUSHING_TO_DISK 진행 중이다. (3) 사본 시점 이후의 수정은 DIRTY 재설정으로 반드시 다시 flush된다.

런타임 검증

Runtime-observed 10,000건 insert가 per-transaction 통계로 Num_data_page_dirties ≈ 102,000을 만들고, checkpoint를 강제하자 전역 Num_data_page_iowrites(DWB 물리 쓰기)가 229 → 1163으로 늘었다. 흥미롭게도 Num_data_page_flushed는 0에 머물렀는데, 이 카운터는 victim flush 경로에서만 증가하기 때문이다 — 관측 지표의 함정은 11장에서 다룬다. 상세는 12장 experiment-2. [CUBRID-C012]

SX가 이 그림을 어떻게 바꾸나 (미리보기)

flusher가 SX를 쥐고 frame을 직접 쓰면: 사본 memcpy가 사라지고(plain page), reader는 그대로 통과하며, writer만 I/O 완료까지 대기한다. InnoDB가 정확히 이 방식이다(14장). 무엇을 얻고 무엇을 내주는지의 저울질은 9장에서.

요약

flush는 "사본 뜨고 원본 풀어주기 + WAL 선행 + 재더티 추적"의 조합이다. 사본은 동시성(writer 자유)을 사는 비용이고, durability는 WAL 순서가 책임진다. 다음 장에서 이 모든 것의 밑바닥 — 동시성 규칙 — 을 본다.
