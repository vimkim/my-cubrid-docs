같은 문제, 다른 경계

같은 이름을 찾지 않고 responsibility, Interface, identity, owner, wait, failure와 관찰 경계를 비교합니다.

이전 장목차다음 장
학습 목표CUBRID, PostgreSQL, MySQL/InnoDB를 고정된 8개 축으로 비교하고 Equivalent·Partial analogy·No equivalent를 구분합니다.
시작 상황큰 값과 unique key를 가진 행을 bulk load하며, 아직 끝나지 않은 inserter를 다른 transaction이 발견합니다.
확인할 불변식같은 책임을 수행해도 resource identity, owner와 lifetime이 다르면 같은 mechanism이라고 부르지 않습니다.
실패·한계PostgreSQL/MySQL runtime은 실행하지 않았습니다. CUBRID 세 실험은 한 번의 의도된 interleaving/input이며 exact timing이나 모든 schedule로 일반화하지 않습니다.

PostgreSQL을 읽기 위한 두 열쇠

COPY FROM은 target relation에 RowExclusiveLock을 잡습니다. 다른 RowExclusiveLock과 호환되므로 CUBRID BU_LOCK과는 coarse table coordination 책임만 닮은 Partial analogy입니다. PG-C001 · CMP-C001

permanent XID를 받은 transaction은 자기 XID resource에 ExclusiveLock을 잡습니다. observer는 같은 XID에 ShareLock을 요청해 종료를 기다린 뒤 tuple/index를 다시 검사합니다. regular completion rendezvous 축에서는 CUBRID MVCCID X/S와 Equivalent입니다. identifier, subtransaction, speculative token과 2PC lifetime은 다릅니다. PG-C010 · CMP-C010

traced native core COPY에서는 session lock owner와 별도 worker transaction의 분리를 찾지 못했습니다. 이 bounded negative는 core heap COPY에만 적용하며 FDW·trigger·extension을 배제하지 않습니다. No equivalent PG-C020 · CMP-C020

MySQL/InnoDB를 읽기 위한 세 층

MDL(Metadata Lock)은 table의 이름·정의·open 상태가 작업 중 바뀌지 않게 조정하는 MySQL SQL 계층 잠금입니다. 일반 LOAD DATA는 MDL_SHARED_WRITE, InnoDB table IX, record/gap lock을 조합합니다. CUBRID BU_LOCK 하나와 exact equivalent가 없습니다. Partial analogy MYSQL-C001 · CMP-C001

trx_t는 InnoDB transaction의 state와 lock ownership을 담는 내부 transaction 객체입니다. LOAD DATA ... ALGORITHM=BULK의 여러 execution thread는 별도 transaction을 만들지 않고 하나의 trx_t를 공유합니다. CUBRID session/worker owner split에는 No equivalent입니다. MYSQL-C020 · CMP-C020

record의 DB_TRX_ID는 active owner를 찾는 표식입니다. 실제 wait queue의 key는 transaction ID가 아니라 record의 page·heap number입니다. unfinished writer를 기다리고 다시 판단하는 책임은 닮았지만 transaction-ID keyed self-lock은 아니므로 Partial analogy입니다. MYSQL-C010 · CMP-C010

3. Resource identity object resource는 type+OID, self-lock은 type+full MVCCID입니다. OOS VFID는 file identity이지 lock key가 아닙니다.
CUBRID-C005, CUBRID-C012, CUBRID-C017; CMP-C003		 relation key는 relation locktag, completion key는 permanent XID locktag입니다. VirtualXID와 speculative token은 다른 identity입니다.

4. Owner / lifetime session transaction이 BU를 소유합니다. 각 worker batch transaction이 자기 MVCCID X를 소유하며 batch commit/abort까지 갑니다. session BU는 outer session transaction 종료에서 풀립니다.

No equivalent는 CUBRID의 worker별 transaction에 적용합니다. MYSQL-C001, MYSQL-C006, MYSQL-C011, MYSQL-C020; CMP-C004
5. Compatibility / wait BU는 BU·SCH_S와 호환되고 일반 data mode와 충돌합니다. MVCCID holder X와 waiter S가 충돌하며, waiter는 page latch를 놓고 wake 뒤 active/B-tree를 재검사합니다.
CUBRID-C002, CUBRID-C006; CMP-C005, CMP-C010		 RowExclusive는 다른 RowExclusive와 호환됩니다. XID Exclusive/Share는 completion wait를 만들고 unique search는 wait 뒤 처음부터 다시 합니다.
Partial analogy(relation), Equivalent(regular completion). PG-C002, PG-C004, PG-C005, PG-C011; CMP-C005, CMP-C010		 MDL SW끼리, IX끼리는 호환됩니다. MDL X는 강하게 충돌합니다. record/table conflict는 DB_LOCK_WAIT를 만들고 일반 insert graph를 재실행합니다.
Partial analogy MYSQL-C002, MYSQL-C003, MYSQL-C005; CMP-C005, CMP-C010
6. Commit / abort main/sub MVCCID를 inactive로 보이게 한 뒤 self-lock을 해제합니다. worker success는 commit, failure는 abort 뒤 transaction index를 free합니다. session BU는 session transaction 종료에서 정리됩니다.
CUBRID-C004, CUBRID-C007, CUBRID-C013; CMP-C006		 commit/abort 상태를 먼저 publish하고 ResourceOwner lock phase에서 relation/XID lock을 해제합니다. prepared transaction은 ordinary release의 예외입니다.
PG-C006, PG-C007; CMP-C006		 full commit/rollback은 transaction lock을 해제합니다. timeout·duplicate·FK는 statement/savepoint rollback일 수 있고 deadlock·lock-table-full은 whole transaction rollback입니다. AUTO_INC는 statement-lifetime 예외입니다.
MYSQL-C006, MYSQL-C009; CMP-C006
7. Failure behavior timeout·deadlock·interrupt는 generic lock error로 돌아갑니다. ordinary OOS/file error는 sysop/page/payload cleanup을 거칩니다. historical assert process abort 뒤 recovery는 Unknown입니다.
CUBRID-C013, CUBRID-C015, CUBRID-C016; CMP-C007		 cancel·process death·lock timeout·deadlock은 lock wait cleanup으로 이어집니다. duplicate/FK/serialization error는 transaction 또는 subtransaction error path로 전파됩니다.
PG-C012; CMP-C007; PG-PACKET §6		 duplicate·FK·timeout·deadlock이 handler error로 변환됩니다. bulk path는 interrupt·unsorted·duplicate·generic bulk failure를 main session에 보고합니다. bulk crash matrix는 Unknown입니다.
MYSQL-C009, MYSQL-C020; CMP-C007; MYSQL-PACKET “Unknowns”
8. Performance / observability transaction-keyed rendezvous는 many-row per-object lock을 줄이는 대신 active MVCCID entry와 hash lookup을 냅니다. xlock_dump는 allocated entry/resource 수와 일부 메모리를 표시하고 event log는 MVCCID를 표시하지만 전용 self-lock counter는 없습니다.
CUBRID-C014, CUBRID-C015, CUBRID-C019; CMP-C008		 pg_locks가 relation/XID owner·waiter를 구분하고 pg_stat_progress_copy와 wait event를 함께 볼 수 있습니다. lock memory pressure는 max_locks_per_transaction과 관계합니다. PostgreSQL runtime은 실행하지 않았습니다.
PG-C008; CMP-C008; PG-PACKET §§6–7		 performance_schema.metadata_locks, data_locks, data_lock_waits와 InnoDB status가 관찰점입니다. implicit record X는 per-row explicit object를 줄이고, bulk path는 MDL X로 동시 접근을 줄이는 대신 parallel direct build를 택합니다. MySQL runtime은 실행하지 않았습니다.
MYSQL-C008; CMP-C008; MYSQL-PACKET “공유 비교 축”

표의 말뜻: CUBRID와 PostgreSQL은 regular transaction-ID completion rendezvous에서 X/Share wait와 재검사 책임이 가깝습니다. 하지만 CUBRID의 session BU와 worker batch transaction 분리는 PostgreSQL core COPY와 MySQL bulk path에서 찾지 못했습니다. MySQL은 transaction ID가 아니라 record resource에서 기다립니다.

성능·observability를 별도로 읽는 법

CUBRID는 many-row per-object rendezvous를 transaction-keyed MVCCID resource 하나로 모아 lock entry 수를 줄이는 방향입니다. 그 대신 active MVCCID마다 entry와 hash lookup 비용이 있습니다. hash bucket은 startup에 num_trans와 lock_escalation으로 산정되고 최대 2²³으로 제한됩니다. xlock_dump의 allocated size는 entry와 resource 크기만 합산하므로 lock manager 전체 메모리가 아닙니다. event log는 MVCCID를 보여 주지만 전용 self-lock counter는 없습니다. fresh X가 wait counter를 전혀 올리지 않는다는 runtime 측정도 없습니다. CUBRID-C014 · CUBRID-C015 · CUBRID-C019 · CMP-C008

PostgreSQL은 pg_locks, pg_stat_activity, pg_stat_progress_copy로 relation/XID wait와 COPY progress를 나눠 봅니다. MySQL은 performance_schema.metadata_locks, data_locks, data_lock_waits로 MDL과 record wait를 나눠 봅니다. 두 DBMS의 관찰점은 pinned source로 확인했으며 이번 Report Run에서 서버를 실행한 결과는 아닙니다. PG-C008 · MYSQL-C008 · CMP-C008

비교와 실험에서 피해야 할 실패

  • PostgreSQL RowExclusiveLock의 이름만 보고 다른 writer를 배제한다고 판단하지 않습니다.
  • MySQL DB_TRX_ID가 출력된다는 이유로 transaction-ID keyed wait resource라고 판단하지 않습니다.
  • OOS placement는 value round-trip만이 아니라 no-file control과 VFID/live-record 출력으로 판정합니다. 비정상 logical-size 수치는 사용하지 않습니다.
  • source-only PostgreSQL/MySQL 관찰점을 runtime result처럼 쓰지 않습니다.

10장 복습

한 문장: 비교의 목적은 비슷한 이름을 찾는 것이 아니라 같은 책임이 어느 module, resource와 owner에 놓였는지 찾는 것입니다.

실험의 진전: 새 receipts는 BU holder/SCH_M waiter, MVCCID X/S, small/large OOS placement와 cleanup check를 직접 연결했습니다. 한 번의 schedule이라는 한계와 setup gate timestamp 주의는 남습니다.
