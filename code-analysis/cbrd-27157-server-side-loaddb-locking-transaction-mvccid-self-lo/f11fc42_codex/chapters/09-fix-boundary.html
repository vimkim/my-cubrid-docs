정책 전체를 작은 알고리즘으로 쓰기

decide_and_request(thread, typed_key, mode, wait_policy):
  if thread.type == TT_LOADDB and typed_key.type != TRANSACTION:
    return POLICY_ERROR

  if same_owner_already_holds(typed_key):
    return convert_now_or_wait_as_blocked_holder(mode, wait_policy)

  if compatible_with_holders_and_earlier_waiters(typed_key, mode):
    return GRANTED

  if wait_policy is CONDITIONAL or expired:
    return NO_GRANT_OR_TIMEOUT

  waiter = allocate_waiter_entry()
  if waiter == NONE:
    return ALLOCATION_ERROR       # ER_LK_ALLOC_RESOURCE, queue에 넣기 전 실패
  append_waiter_tail(waiter)
  return suspend_until_grant_timeout_deadlock_or_interrupt(waiter)

비용과 pathological case

hash lookup이 잘 분산된 평상시에는 resource 찾기가 빠르지만, compatibility와 unlock은 현재 holder/blocked holder/waiter list를 순회할 수 있습니다. 따라서 한 resource에 request가 몰리면 queue 길이에 비례한 scan과 wakeup 경쟁이 생길 수 있습니다. self-lock을 uniform하게 두는 선택은 “observable MVCCID에는 matching X가 있다”는 단순한 invariant를 얻는 대신 transaction resource와 entry를 더 만듭니다.

가장 나쁜 사고 실험은 많은 S holder 사이에서 X conversion이 막히고 새 S waiter가 계속 들어오는 경우입니다. UPR와 앞선 blocked mode를 고려해 grant하지만 이 책의 고정 source만으로 strict FIFO나 starvation 부재를 약속하지 않습니다. 또 entry allocator가 고갈되면 append 후 유령 waiter를 정리하는 것이 아니라 append 전에 ER_LK_ALLOC_RESOURCE를 설정하고 allocation error로 끝나야 합니다. debug assert와 runtime correctness

assert는 개발 build에서 예상하지 않은 경로를 즉시 드러내는 tripwire입니다. release build에서는 compile-out될 수 있으므로 “release도 같은 assert로 반드시 죽는다”고 말할 수 없습니다. 반대로 assert 한 줄을 없앴다는 사실만으로 acquire, release, cleanup, future waiter invariant가 모두 안전하다고 증명되지도 않습니다.

좋은 fix 설명은 네 가지를 함께 말합니다. 실제 request가 grant되는가, owner가 누구인가, transaction end에서 해제되는가, 기존 object-lock prohibition이 유지되는가.

왜 이 seam인가?

MVCCID allocation early-return은 caller context에 정책을 섞습니다. internal lock boundary의 resource-type check는 “누가 이 공통 lock manager에 어떤 key로 들어올 수 있는가”를 한곳에서 표현합니다. 다만 함수 이름에 object가 남아 있어 reviewer가 key type을 놓치기 쉬우므로, 테스트와 설명은 항상 resource를 명시해야 합니다.

Total policy pseudocode

request_internal_lock(thread, key, mode, wait_policy):
  is_tx_key = (key.type == LOCK_RESOURCE_TRANSACTION)

  if thread.type == TT_LOADDB and not is_tx_key:
    assert_fail_in_debug()
    return POLICY_ERROR

  result = generic_grant_convert_or_wait(key, mode, thread.tran_index, wait_policy)
  if result == ALLOCATION_ERROR:
    return result  # waiter allocation이 append 전에 실패했으므로 wait entry 없음
  if result in {TIMEOUT, DEADLOCK, INTERRUPTED}:
    generic_engine_removes_wait_or_blocked_state()
    return result
  return GRANTED

publish_observable_insid(record, transaction):
  result = ensure_mvccid_self_lock(transaction)
  if result != GRANTED:
    return result
  stamp_insid(record, transaction.mvccid)
  return SUCCESS

같은 owner가 이미 key를 보유하면 generic engine은 별도 waiter 생성 전에 conversion을 계산합니다. 이 pseudocode는 policy branch를 보여 주는 재구현 계약이며 실제 ABI나 내부 enum 값의 호환성을 약속하지 않습니다. CUBRID-C005 · CUBRID-C011 · CUBRID-C018
