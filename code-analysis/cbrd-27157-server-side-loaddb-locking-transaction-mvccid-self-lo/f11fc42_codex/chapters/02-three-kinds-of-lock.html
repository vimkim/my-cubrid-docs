화이트보드에 펜이 하나뿐인 상황은 mutex를 떠올리기 좋습니다. 서랍의 카드 배열을 바꾸는 동안 잠깐 고정하는 걸쇠는 latch와 비슷합니다. 대출 승인이나 취소가 끝날 때까지 자료에 붙이는 예약표는 transaction lock과 비슷합니다.

CUBRID의 실제 예로는 B-tree page latch를 놓은 뒤 MVCCID transaction lock을 기다리는 흐름이 있습니다. 짧은 물리 보호와 긴 논리 조정을 한 요청 안에서도 이어서 사용할 수 있지만, 두 도구의 owner와 수명은 합쳐지지 않습니다. CUBRID-C006 · CUBRID-C017

비유의 중단점: mutex는 실제 펜이 아니며 SQL commit의 의미를 모릅니다. latch는 row에 접근할 권리를 주지 않습니다. transaction lock도 모든 DBMS에서 언제나 commit까지 유지된다고 일반화할 수 없습니다.

“transaction lock”에는 두 질문이 섞이기 쉽다

owner와 resource를 분리한 두 가지 표현
표현대답하는 질문CBRD-27157의 예
transaction-owned lock누가 lock을 소유하고 나중에 해제하는가?session transaction이 class의 BU_LOCK을 소유합니다.
transaction-resource lock무엇을 lock resource의 주소로 삼는가?worker transaction이 자기 MVCCID를 key로 한 X_LOCK을 소유합니다.

둘은 배타적인 분류가 아닙니다. MVCCID self-lock은 transaction이 소유하는 동시에 transaction 식별자를 resource로 사용합니다. 반면 BU_LOCK도 transaction이 소유하지만 resource는 transaction이 아니라 class OID입니다.

따라서 “transaction lock이 있다”는 문장만으로는 부족합니다. owner가 transaction이라는 뜻인지, resource가 transaction이라는 뜻인지 먼저 확인해야 합니다. 이 책은 좁은 두 번째 의미를 말할 때 MVCCID transaction-resource lock 또는 MVCCID self-lock이라고 씁니다.

기다리기 전에 page latch를 놓는 이유

T2가 T1의 transaction 종료를 몇 초 기다리면서 B-tree page latch까지 들고 있다고 생각해 봅시다. 그 page가 필요한 다른 thread가 모두 멈추고, T1의 종료 작업도 같은 page를 필요로 하면 더 큰 교착을 만들 수 있습니다.

그래서 CUBRID의 unique/FK 경로는 transaction self-lock을 기다리기 전에 page latch와 임시 object lock을 놓습니다. 깨어난 뒤에는 page가 달라졌을 수 있으므로 B-tree를 다시 읽습니다. 짧은 물리 보호와 긴 논리 대기를 분리한 것입니다.

race condition은 “동시에 실행”보다 좁은 말

두 thread가 함께 달린다고 모두 버그는 아닙니다. 실행 순서에 따라 허용되지 않은 결과가 생길 때 race condition입니다. lock은 동시 실행 자체를 없애기보다, 충돌하는 순서만 기다리게 만드는 도구입니다.

이 구분을 놓치면 생기는 실패

page latch를 transaction 종료까지 유지하면 물리 page를 필요로 하는 작업이 함께 멈춥니다. 반대로 transaction lock 대신 짧은 latch만 사용하면 latch를 놓은 뒤 logical 충돌을 조정할 장치가 사라집니다. 두 primitive는 서로의 긴 수명과 짧은 수명을 대신하지 않습니다.

한 문장: 보호 대상이 물리 구조인지 logical transaction 상태인지, 필요한 수명이 얼마나 긴지가 도구를 결정합니다.

CBRD-27157에 쓰는 법: OOS page latch 문제와 MVCCID transaction lock 문제를 같은 것으로 부르지 않습니다. 또한 transaction이 owner인 것과 transaction ID가 resource인 것을 구분합니다.
