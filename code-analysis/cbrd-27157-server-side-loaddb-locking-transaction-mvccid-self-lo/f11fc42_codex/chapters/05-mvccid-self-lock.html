“같은 요청에 속한다”와 “같은 owner다”를 분리합니다.

학습 목표session transaction, worker batch transaction, MVCCID self-lock의 owner와 lifetime을 분리합니다.
시작 상황T1이 unique key를 insert하고 끝나기 전에 T2가 같은 key를 검사합니다.
확인할 불변식INSID(record에 적힌 inserter MVCCID)가 관찰 가능하고 inserter가 active이면 같은 MVCCID resource에 matching X self-lock이 있어야 합니다.

session transaction과 worker batch transaction

connection / load session
  session transaction S ──owns── class T의 BU_LOCK
              ·
              · object-lock lookup redirect
              ·
  worker W1 ──runs── batch transaction B1 ──owns── MVCCID M1의 X self-lock
  worker W2 ──runs── batch transaction B2 ──owns── MVCCID M2의 X self-lock

실선은 실제 ownership, 점선은 worker가 object lock 상태를 물을 때 session transaction을 보는 redirect입니다. B1과 B2는 S의 nested child transaction이 아닙니다.

각 accepted batch는 새 tran_index를 받고, 성공하면 정해진 batch 순서로 commit하며 실패하면 abort합니다. client identity 일부를 복사해도 transaction descriptor와 lock ownership이 복사되는 것은 아닙니다.

self-lock은 자기 자신을 막지 않는다

T1이 MVCCID 42를 처음 받으면 같은 MVCCID 42 transaction resource에 X lock을 잡습니다. record가 normal MVCC insert라면 INSID에 42가 보일 수 있습니다. T2의 unique 또는 FK 검사 경로가 active inserter 42를 발견하면 같은 resource에 S lock을 요청합니다.

T1: MVCCID 42 발급 → X(42) 보유 → INSID=42 공개
T2: INSID 42 발견 → page latch 해제 → S(42) 요청 → 기다림
T1: commit 또는 abort → active=false → X(42) 해제
T2: 깨어남 → S(42) 즉시 해제 → active와 B-tree를 다시 검사

일반 snapshot reader는 과거 version을 읽을 수 있으므로 이 S-lock 대기와 같다고 가정하지 않습니다. 여기의 observer는 source에서 확인한 unique/FK conflict checker입니다.

핵심 불변식: 다른 transaction이 관찰할 수 있는 INSID가 있다면, 그 inserter가 아직 active인 동안 같은 MVCCID의 X self-lock이 있어야 합니다.

Runtime-observed: f03-exp2-lockdb-v3는 inserter MVCCID 7 resource에 X holder와 S waiter가 동시에 있음을 보였습니다. direct csql observer f03-exp2-observer-v3는 약 10.7초 뒤 observer-after-wait 행의 insert와 조회에 성공했습니다. 이 한 번의 실행은 내부 page latch 해제나 전체 재검사 호출을 직접 관찰하지 않았으며, 그 순서는 Source-confirmed 근거입니다. CUBRID-C010

현재 bulk row는 INSID를 생략한다

session BU를 확인한 bulk insert는 is_bulk_op으로 전달되어 row INSID와 per-row object lock, class IX를 생략합니다. 그래서 현재 분석한 bulk row metadata만 보면 unique/FK checker가 worker MVCCID를 발견하는 길이 없습니다.

그러나 이것은 “어떤 loaddb worker도 MVCCID가 필요 없다”는 말이 아닙니다. file metadata 같은 다른 경로가 MVCCID를 요구할 수 있고, 미래에 새로운 INSID producer가 생길 수도 있습니다. current path에 대한 좁은 추론과 전체 invariant 정책을 구분해야 합니다.

self-lock acquire가 실패하면

MVCCID assignment 지점의 최초 X acquire는 API 제약 때문에 실패를 log로 남기는 best-effort 경계입니다. 실제 INSID를 외부에 보일 수 있는 heap producer는 logtb_ensure_mvccid_self_lock을 다시 호출해 실패를 statement error로 전달합니다. 이 ensure 없이 INSID를 먼저 공개하는 전이는 금지됩니다. timeout·deadlock·interrupt를 받은 S waiter도 성공처럼 진행하지 않고 caller 오류 또는 retry 규칙을 따라야 합니다. generic 대기 경로는 실패 wakeup에서 blocked/waiter 정보를 제거합니다. CUBRID-C005 · CUBRID-C006 · CUBRID-C018
