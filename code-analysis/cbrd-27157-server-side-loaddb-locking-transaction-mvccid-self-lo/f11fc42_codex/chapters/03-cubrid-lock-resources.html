둘 다 X_LOCK이어도 다른 잠금일 수 있다

처음 보는 세 용어: OID(Object Identifier)는 이 책에서 class나 row 같은 logical object를 가리키는 식별자이며 메모리 pointer가 아닙니다. tran_index는 현재 server process의 transaction table에서 owner를 찾는 칸 번호이지 영구 보존되는 업무 ID가 아닙니다. SCH_M_LOCK은 schema modification mode이며, 이 issue의 실험에서는 class 정의를 바꾸는 ALTER 요청이 가진 mode입니다. CUBRID-C001 · CUBRID-C002 · CUBRID-C003 · CUBRID-C004 · CUBRID-C017

CUBRID의 resource key에는 resource type도 들어갑니다. 같은 숫자 비트가 우연히 같아도 CLASS OID와 TRANSACTION MVCCID는 다른 주소입니다. holder와 waiter entry의 owner는 runtime transaction table의 tran_index로 연결됩니다.

Source-confirmed: LK_RES_KEY는 object OID와 MVCCID를 type으로 구분합니다. 실제 compare/hash identity는 object resource에서 type+oid, transaction resource에서 type+full MVCCID입니다. instance key를 복사할 때 class_oid도 보존하지만 object compare/hash에는 쓰지 않습니다. CUBRID-C017

Interface seam: generic internal 함수의 이름에 object가 있어도 typed key가 TRANSACTION일 수 있습니다. TT_LOADDB worker는 이 transaction-resource request만 허용되고 class/instance acquire는 session BU redirect 경계를 유지합니다. resource와 transaction 양쪽 list를 함께 바꿀 때 mutex 순서는 resource mutex → transaction hold_mutex입니다. CUBRID-C003 · CUBRID-C005 · CUBRID-C011 · CUBRID-C022

Interface 경계에서 묻기

함수 이름이 lock_internal_perform_lock_object라고 해서 입력이 모두 object resource인 것은 아닙니다. 현재 함수는 공통 search key를 받아 transaction resource도 처리합니다. 이름보다 parameter의 type과 caller obligation을 읽어야 합니다.

정책 seam은 “어떤 caller가 어떤 resource type을 요청할 수 있는가”를 판정하는 경계입니다. CBRD-27157의 한 줄 수정도 바로 이 경계에서 TT_LOADDB와 transaction resource의 조합을 좁게 허용합니다.

lock table 안에서는 resource mutex가 그 resource의 holder·waiter list를 보호합니다. transaction hold list에도 entry를 연결하거나 제거해야 할 때는 resource mutex를 가진 채 transaction의 hold_mutex를 잠급니다. 이 순서를 뒤집는 구현은 같은 두 mutex를 반대 방향으로 기다리는 deadlock을 만들 수 있습니다. 해제의 전체 순서는 7장에서 이어집니다. CUBRID-C003 · CUBRID-C005 · CUBRID-C011 · CUBRID-C017 · CUBRID-C022

같은 resource에서 mode가 충돌하면 요청자는 waiter가 됩니다. holder가 해제하면 waiter가 깨어나지만, wakeup은 업무 조건이 그대로라는 보장이 아닙니다. row나 index를 다시 읽어야 합니다.

“worker가 X lock을 잡았다”라는 문장을 보면 다섯 가지를 되물으세요. 어느 resource인가? 요청 mode는 무엇인가? 어느 transaction이 owner인가? 누가 기다리는가? 언제 풀리는가? 이 질문이 없으면 설명은 아직 절반입니다.

충돌·wait·오류의 최소 규칙

compatible이면 즉시 grant합니다. incompatible인데 conditional request라면 임시 entry를 정리하고 no-grant를 반환합니다. 기다리는 request라면 waiter queue의 뒤에 넣고 resource mutex를 놓은 뒤 suspend합니다. 같은 owner가 더 강한 mode를 요청하면 새 waiter가 아니라 conversion 중인 blocked holder가 될 수 있습니다. timeout·deadlock·interrupt로 깨어나면 대기 정보를 제거하고 오류를 caller에 돌려야 합니다. 정상 wakeup도 업무 조건의 재검사를 생략할 권한은 주지 않습니다.

대기 순서는 단순한 “무조건 선착순”이 아닙니다. CUBRID는 앞선 blocked mode와 현재 holder의 호환성, UPR(Upgrader Positioning Rule, 잠금 강화를 기다리는 holder의 queue 위치 규칙)을 함께 봅니다. 따라서 이 책은 strict FIFO나 starvation 부재를 약속하지 않습니다. CUBRID-C018
