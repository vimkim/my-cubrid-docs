큰 행 하나가 debug assert에 닿기까지

먼저 숲 전체를 봅니다. 모르는 용어는 뒤 장에서 하나씩 풉니다.

목차다음 장
학습 목표작은 값과 큰 값의 경로가 갈리는 지점을 찾고, session BU_LOCK과 worker self-lock을 처음부터 분리합니다.
시작 상황같은 server-side loaddb에서 작은 행은 성공하지만 큰 variable value가 debug assert 경로를 엽니다.
확인할 불변식서로 다른 resource key와 owner를 가진 잠금은 같은 이름이나 같은 manager를 지난다는 이유로 대체되지 않습니다.
실패·한계이 장은 전체 지도를 보여 줍니다. 각 lock mode와 OOS 물리 형식은 뒤 장의 source 근거로 좁힙니다.

작은 값과 큰 값의 갈림길

server-side loaddb worker가 작은 행을 넣을 때는 보통 heap 안쪽 경로로 곧장 갑니다. 하지만 큰 variable value는 heap record 안에 모두 담지 않고 OOS(Out-of-row Overflow Storage, 큰 값을 heap record 밖의 전용 저장소에 두는 기능)로 옮길 수 있습니다. 그 class에서 OOS를 처음 쓰면 전용 file도 처음 만들어야 합니다.

큰 값
  → OOS로 옮길 준비
  → 첫 FILE_OOS 생성
  → file_create가 current MVCCID 요구
  → worker가 자기 MVCCID에 X self-lock 요청
  → 오래된 TT_LOADDB assert에 도달

그림의 말뜻: 데이터 크기가 lock mode를 직접 바꾼 것이 아닙니다. 큰 값이 평소에는 가지 않던 file 생성 경로를 열었고, 그 경로가 MVCCID 발급과 self-lock을 불렀습니다.

Source-confirmed: 현재 고정 revision은 이 transaction resource 요청을 허용합니다. class나 instance object lock을 모두 허용한 것이 아닙니다. CUBRID-C011

처음부터 둘로 나누기

session transaction S
  └─ class T에 BU_LOCK

worker batch transaction B1
  └─ 자기 MVCCID M1에 X_LOCK

BU_LOCK은 class OID(Object Identifier, class를 가리키는 logical 식별자)가 resource입니다. MVCCID self-lock은 transaction형 resource이며 key가 MVCCID입니다. 같은 lock manager를 지나가도 주소와 owner가 다릅니다.

비유하면 현장 책임자가 건물 사용 허가를 들고, 작업팀은 자기 작업 번호표에 “작업 중” 표시를 거는 상황입니다. 다만 실제 transaction은 조직도 속 부모·자식이 아닙니다. 각자 별도로 commit하거나 abort하는 owner입니다.

이 책이 답할 것과 답하지 않을 것

  • 답함: lock resource, mode, owner, waiter, lifetime.
  • 답함: session과 worker batch transaction의 분리.
  • 답함: unique/FK checker가 MVCCID에서 기다리고 재검사하는 이유.
  • 답함: OOS lazy file creation에서 assert까지의 호출 사슬과 fix 경계.
  • 짧게만 다룸: latch, WAL·recovery, deadlock, OOS 물리 형식.
