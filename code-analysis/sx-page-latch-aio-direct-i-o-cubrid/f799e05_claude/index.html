SX page latch 도입 효과 — AIO/direct I/O 필수성과 현행 CUBRID에서의 성능 이득

CUBRID page buffer의 latch 체계(READ/WRITE)를 소스와 런타임 실험으로 재구성하고, SX(shared-exclusive) latch 도입이 무엇을 바꾸는지, AIO/direct I/O write가 왜 frame 안정성을 전제조건으로 만드는지를 대학교 2학년 눈높이로 설명하는 책이다. PostgreSQL·MySQL(InnoDB)과 같은 축으로 비교한다.

한 문단 결론

질문 1(현행 구조에서 B-tree 이득?) — 구조적 근거는 확실하다: 승격은 insert당 4회가 넘는 실존 hot path이고(런타임 관측 88,779회/20,000 insert), 실패 시 루트 재시작이라는 세금이 있다. 크기는 promote 실패율 baseline이 정하며, 그 측정은 SX 없이 지금 가능하다. 질문 2(AIO 없이 flush 이득?) — 사본 memcpy 제거 대 writer 대기의 교환이며 측정으로 판정할 사안이다. 질문 3(AIO 도입 시 SX 필수?) — 그렇다, 방향이 중요하다: AIO/direct I/O write ⇒ frame 안정성(SX 등가 또는 상시 사본) 필수. PostgreSQL이 정확히 이 이유로 SHARE_EXCLUSIVE를 도입했다(커밋 메시지에 btrfs 오류 사례 명시). 상세 근거는 9장.
