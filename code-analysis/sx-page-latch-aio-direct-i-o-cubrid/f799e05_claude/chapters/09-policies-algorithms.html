9장 — 정책의 저울질: 사본 vs SX, 그리고 AIO가 SX를 필수로 만드는 이유

학습 목표

사용자 질문 세 개에 정면으로 답한다: (1) AIO/direct I/O 없이 SX만으로 B-tree가 좋아지는가, (2) flush 쪽 이득이 있는가, (3) AIO/direct I/O를 도입하면 왜 SX(또는 그 등가물)가 필수가 되는가.

질문 1 — 지금 구조에서 B-tree 이득이 있는가

이득의 존재는 I/O 방식과 완전히 무관하다. 5장에서 본 대로 승격은 insert당 4회가 넘는 실존 hot path이고, 실패 시 루트 재시작 + WRITE 하강이라는 세금이 붙는다. SX는 이 세금 자체를 없앤다(7장). 문제는 세금이 실제로 얼마나 걷히고 있는가다:

  • 실패는 동시 경쟁에서만 발생한다. 단일 세션 관측(12장)에서 실패는 0이었다 — 즉 이득의 크기는 실운영 워크로드의 promote 실패율에 비례한다.
  • 실패율은 이미 측정 가능하다: Data_page_total_promote_fail(11장). 프로토타입 없이 지금 당장 걷을 수 있는 baseline이다.
  • 실패율이 높지 않아도 남는 이득이 있다: 실패가 두려워 처음부터 WRITE 하강을 택하는 보수적 코드 경로들(재시작 후 하강 전체)의 배타 창 축소, 그리고 delete/merge의 3-page 연속 승격 같은 복잡한 fallback 코드의 단순화. 다만 이 부분은 정량화가 어렵다.

답. "성능이 좋아질 수 있는 구조적 근거는 확실히 있고(승격 hot path + 실패-재시작 세금), 좋아지는 크기는 promote 실패율 baseline이 결정한다. 그 baseline은 SX 없이 지금 측정할 수 있으므로, 측정이 구현보다 먼저다." [CUBRID-C004, C005, C011]

질문 2 — AIO 없이 flush 이득이 있는가

있다 — 단, 공짜가 아니라 교환이다. 6장의 사본 flush를 SX 직접 flush로 바꾸면:

주의 깊게 볼 것은 셋째 줄이다. 현행 설계는 "writer조차 막지 않는" 가장 관대한 동시성을 사본으로 산 것이고, SX 직접 flush는 그 관대함을 일부 반납한다. 다만 buffered write에서는 write()가 kernel page cache로의 복사만 하고 곧 반환되므로 writer가 막히는 창이 짧다 — SX 직접 flush의 비용이 buffered 환경에서 오히려 싸다는, 직관과 반대인 사실이다. InnoDB는 이 교환을 받아들였고 nowait SX + 획득 실패 시 우회(flush-list는 DWB 강제 flush 후 blocking, LRU는 포기)로 비용을 완충한다 [MYSQL-C002].

답. "AIO 없이도 사본 memcpy 제거라는 이득 후보가 있으나, writer 대기라는 반대급부와의 저울질이며, 저울질의 답은 flush-pressure 워크로드 측정으로만 나온다. 측정 전 임계값 합의가 필요하다(아래 결정 게이트)." [CMP-C001]

질문 3 — 왜 AIO/direct I/O에는 frame 안정성이 "필수"인가

층을 나눠 설명한다.

1층: buffered write의 숨은 계약

일반 write(fd, buf, n)은 반환 시점에 데이터가 이미 kernel의 page cache로 복사되어 있다. 시스템콜이 끝나면 buf는 kernel과 무관해진다 — "반환 후 buf 수정 자유"가 buffered write의 계약이다. CUBRID의 사본 flush는 사실 이 계약 위에 서 있다: 사본을 뜨는 진짜 이유는 kernel이 아니라 "사본을 뜨는 시점과 write() 호출 사이"에 다른 스레드가 frame을 고칠 수 있어서다.

2층: direct I/O/AIO가 계약을 깨는 방식

direct I/O(O_DIRECT)는 page cache를 우회해 사용자 버퍼에서 장치로 직접 DMA한다. AIO는 제출과 완료가 분리되어 제출 반환 후에도 I/O가 진행 중이다. 두 경우 모두 "시스템콜이 돌아왔다 = kernel이 내 버퍼를 다 읽었다"가 성립하지 않는다. I/O가 진행되는 동안 버퍼(우리의 frame)가 바뀌면, 장치로 가는 데이터가 중간에 섞인다.

그림 설명: buffered write는 시스템콜 실행 구간만 버퍼가 안정하면 되고 반환 즉시 수정이 자유롭다. direct I/O와 AIO write는 제출부터 완료 통지까지 장치가 버퍼를 직접 읽으므로 그 전체 구간 동안 frame이 불변이어야 하며, 수단은 사본 유지 또는 SX 등가 latch 둘뿐이다.

3층: 실제 엔진의 증언

Documented (PostgreSQL commit 82467f627bd). PostgreSQL이 SHARE_EXCLUSIVE를 도입한 커밋 메시지가 이 논리를 그대로 담는다: 종전(share lock 아래 hint bit 허용) 구조에서는 flush마다 페이지를 복사해야 했는데, 이 사본이 (1) AIO write에서는 "in-flight page마다 사본 버퍼가 필요하고, worker 방식 AIO에서는 그 사본이 shared memory에 있어야 하는" 문제를, (2) AIO와 무관하게 direct I/O에서는 "일부 파일시스템/RAID가 쓰는 도중의 데이터 변경을 견디지 못한다 — btrfs에서 파일시스템 오류 사례" 문제를 만든다. 결론으로 share 아래 수정을 금지하고 SHARE_EXCLUSIVE(SX 등가)를 flush와 hint bit 양쪽에 요구했다. [PG-C003]

4층: 그래서 화살표의 방향

정리. SX ⇒ AIO가 아니라 AIO/direct I/O write ⇒ (사본 상시 유지 또는 SX 등가 latch)다. 사본 유지를 택하면 in-flight마다 버퍼가 늘고 zero-copy 이점이 반감되므로, 실무 엔진(InnoDB, PG 20devel)은 SX 쪽으로 수렴했다. CUBRID가 EPIC의 scan prefetch/AIO 후보를 write까지 확장하는 날, SX는 "성능 옵션"이 아니라 "선행 조건"이 된다.

결정 게이트 (측정 계획)

  1. 1단계 — baseline 분석 게이트 (프로토타입 불필요): 기준 소스에서 (a) flush 경로 memcpy CPU 비중(perf 프로파일), (b) 실운영형 동시 워크로드의 promote 실패율을 수집한다. 두 수치가 모두 무시 가능한 수준이면 구조 변경 없이 종료(no-go). 판정 임계값은 수치 확보 후 합의한다 — 이 보고서는 임계값을 지어내지 않는다.
  2. 2단계 — 프로토타입 비교 게이트: baseline이 이득을 시사하면 flush 내부 상태 한정 프로토타입으로 read-heavy/write-heavy/flush-pressure/B-tree 경합/TPC-H를 비교한다. read-heavy와 TPC-H 무회귀를 전제로, flush-pressure 또는 B-tree 경합의 유의미한 개선이 확인될 때만 구현으로 전환. write-heavy 악화 시 InnoDB식 nowait 완충을 평가한다.

같은 구성의 게이트를 JIRA 조사 이슈(CBRD-27196)로 제안해 두었다 — 발췌 사본은 research/jira/CBRD-27196.md.

요약

B-tree 이득은 I/O와 무관하게 구조적으로 성립하고 크기는 실패율이 정한다. flush 이득은 memcpy 절감 대 writer 대기의 교환이다. AIO/direct I/O는 frame 안정성을 계약으로 요구하므로 SX(또는 비싼 사본 유지)가 전제조건이 된다. 다음 장에서 이 모든 것을 어떤 카운터로 관측하는지 본다.
