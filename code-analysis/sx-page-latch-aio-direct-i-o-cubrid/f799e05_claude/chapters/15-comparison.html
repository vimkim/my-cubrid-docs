학습 목표

판정: InnoDB와 PG 20devel은 이 축에서 서로 equivalent하고, CUBRID 현행은 같은 문제를 사본으로 푸는 partial analogy다. 특기할 사실 — CUBRID 방식은 출시 PostgreSQL(18 이하)과 동형이며, 그 PostgreSQL이 방금 SX 쪽으로 이주했다. CUBRID만 "틀린" 것이 아니라, buffered write 세계에서는 셋 다 합리적이었고 AIO/direct I/O가 저울을 기울인 것이다.

판정: 세 엔진 모두 "교착 가능한 대기 대신 포기/재시작"이라는 원칙을 공유하므로 partial analogy다. 차이는 재시도의 가격표다 — CUBRID가 가장 비싸고(경로 직렬화), InnoDB는 index SX로 가격을 낮췄고, PostgreSQL은 문제 자체를 프로토콜로 제거했다. CUBRID의 SX 도입은 "InnoDB의 가격표로 이사"에 해당한다.

책임 소재 비교

세 엔진 모두 이 문제의 소유자는 buffer 관리자(CUBRID pgbuf, InnoDB buf0*, PG bufmgr)다. 다만 MySQL은 이 전부가 storage engine(InnoDB) 안의 일이고 SQL 서버 계층은 관여하지 않는다 — "MySQL의 SX"라고 말할 때 실제 주어는 InnoDB다.

증거의 비대칭 고지

CUBRID 주장은 소스 + 런타임 실험으로, InnoDB/PostgreSQL 주장은 소스로만 뒷받침된다(두 서버는 실행하지 않았다). PostgreSQL 쪽은 미출시 브랜치라 릴리스 전 변경 가능성이 남는다. 정량 성능 수치는 세 엔진 모두 이 보고서 범위에서 제시하지 않는다 — MySQL 5.7 발표문도 SX 개선을 정성적으로만 서술했다.

요약

flush 축에서는 InnoDB·PG가 SX 보유로 수렴했고 CUBRID만 사본에 남아 있다. 승격 축에서는 셋 다 blocking 승격을 금지하되 재시도 가격이 다르다. 두 축 모두에서 SX 도입은 CUBRID를 검증된 산업 패턴 쪽으로 옮기는 일이다. 다음 장은 그 이사의 설계도다.
