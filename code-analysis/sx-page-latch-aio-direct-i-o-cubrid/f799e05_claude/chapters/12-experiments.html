12장 — 실험 기록: 승격과 flush의 런타임 증거

학습 목표

두 central behavior의 런타임 증거가 어떤 절차로 수집되었고, 무엇을 증명하며 무엇을 증명하지 않는지 판별한다. 원시 기록은 evidence/runs/에, 실행물은 experiments/에 있다.

공통 환경

기준 소스 f799e05d의 debug 빌드(runtime-baseline-build-2로 캡처, evidence/runtime-tools-baseline.json에 바이너리 해시 봉인), 실험 전용 데이터베이스 sx_latch_lab(생성·서버 기동·삭제 전 과정 기록), 기본 설정. 첫 빌드 게이트 시도(runtime-baseline-build)는 대상 환경에 실행 중이던 서버 때문에 설치 단계가 거부되어 exit 75로 기록되어 있으며(컴파일 자체는 성공), 사용자 승인 후 서버를 중지하고 성공한 build-2가 이 보고서의 기준 빌드다. debug 빌드이므로 절대 시간은 release보다 느리다 — 이 실험들의 오라클은 시간이 아니라 카운터 불변식이다.

experiment-1 — B-tree insert는 승격을 대량 사용한다

experiment-1 요약 (전문: experiments/experiment-1/)
항목내용
질문소스에서 본 승격 호출(btree.c 11곳)이 런타임에서 실제로, 어느 규모로 발생하는가
가설단조 key 20,000건 insert → 승격 수만 회, 단일 세션이므로 실패 0
방법csql 세션 histogram(;.hist on)을 관측 장치로 내장한 runner를 3회 실행 (exp1-obs-1/2/3)
관측promote_success = 89,587 / 88,779 / 88,779 (obs-1/2/3 실행 순), promote_fail = 0, Num_btree_inserts = 20,024 / 20,012 / 20,012 (첫 실행은 카탈로그 초기화분 포함)
해석승격은 insert당 약 4.4회의 실존 hot path다. SX 논의는 가상의 경로가 아니라 이 경로를 다룬다
대조군양성: 3회 반복 재현. 음성: 단순 SELECT에서 promote 0. 관측장치: watcher 없는 초기 실행(exp1-run-1~3)에서 전 카운터 0 — 11장 함정 1의 증거
한계실패율(동시 경쟁)은 측정하지 않음 — 9장 1단계 게이트로 넘김

[CUBRID-C011] 대안 설명 배제: 전용 DB + 단일 세션 + per-tran histogram이므로 다른 작업의 승격이 섞일 수 없고, 카운터-이벤트 결합(promote 카운터의 증가 지점이 pgbuf_promote_read_latch 내부뿐임)은 소스로 확인했다.

experiment-2 — flush 깔때기의 실행과 카운터 함정

experiment-2 요약 (전문: experiments/experiment-2/)
항목내용
질문flush 깔때기 실행을 어떤 카운터로 관측할 수 있는가; Num_data_page_flushed는 신뢰 가능한가
가설dirty 생성은 per-tran에 잡히고, 물리 쓰기는 Num_data_page_iowrites로 잡히며, Num_data_page_flushed는 victim 전용이라 0에 머문다(소스 기반 예측)
방법interval statdump watcher를 붙이고, 10,000건 insert runner 2회(exp2-obs-1/2) → backupdb -C -r로 동기 checkpoint 강제 → statdump 전후 비교
관측Num_data_page_dirties = 102,218 / 102,158 (per-tran), Num_data_page_iowrites 229 → 1163 (+934), Num_data_page_flushed 0 → 0
해석깔때기는 실행되었고(+934 물리 쓰기), flushed 카운터는 이름과 달리 checkpoint flush를 세지 않는다(본 보고서가 독립 확인, JIRA EPIC 발췌 사본 research/jira/ 참조)
한계checkpoint flush와 flush 데몬 자발 flush를 구분하지 못함(둘 다 같은 깔때기라 결론에는 무영향)

[CUBRID-C012] 과정에서 배운 것: csql sysadm의 ;checkpoint는 비동기 요청이라 per-tran histogram에 잡히지 않고, checkpoint 데몬의 페이싱 때문에 수 분간 완료되지 않는 경우도 있었다 — 동기 강제 수단으로 backupdb를 채택한 이유다. 또 cubrid statdump는 wrapper가 실제 프로세스를 자식으로 띄우므로 pid 파일이 wrapper를 가리켜 정리가 누락될 수 있다 — 교정 정리(exp2-watcher-stop-2)까지 기록되어 있다.

관측자 효과

watcher는 perfmon 증가 비용을 켠다. 두 실험의 결론(횟수 불변식)은 이 비용과 무관하지만, 시간 측정을 겸하려면 비교군 모두 watcher를 켜야 한다(11장).

요약

승격은 실존 hot path(수만 회/2만 insert), flush 깔때기는 실행 확인, 그리고 카운터 이름의 함정까지 — 세 사실이 재현 가능한 기록으로 남았다. 다음 세 장은 같은 문제를 PostgreSQL과 InnoDB가 어떻게 풀었는지다.
