1장 — 오리엔테이션: 세 가지 질문과 답

학습 목표

이 보고서가 어떤 질문에 답하는지, 어떤 범위의 코드를 근거로 삼는지, 결론이 무엇인지를 먼저 파악한다. 세부 근거는 이후 장에서 층층이 쌓는다.

이 보고서가 답하는 세 질문

  1. CUBRID는 지금 AIO(asynchronous I/O — 요청 스레드가 완료를 동기적으로 기다리지 않는 입출력)도 direct I/O(운영체제 page cache를 우회하는 입출력)도 쓰지 않는다. 그런 현재 상태에서 SX latch만 도입해도 B-tree 같은 작업의 성능이 좋아질 수 있는가?
  2. AIO/direct I/O 없이도 flush 쪽 이득이 있는가?
  3. 나중에 AIO/direct I/O write를 도입한다면 그때 SX가 왜 "필수"가 되는가?

핵심 결론 (요약)

결론 1 — B-tree. SX의 첫 번째 이득은 I/O 방식과 무관하다. CUBRID B-tree insert는 지금도 page latch 승격(READ를 쥔 채 WRITE로 올리는 것)을 대량으로 사용하며 — 20,000건 insert에서 승격 약 88,000회를 직접 관측했다 — 이 승격은 교착을 피하려고 경쟁이 감지되면 실패하는 방식이라, 실패한 insert는 루트부터 WRITE 하강으로 재시작한다. SX는 이 실패-재시작 분기를 구조적으로 없앨 수 있다. 다만 "얼마나 빨라지는가"는 승격 실패가 실제로 얼마나 자주 나는지(동시 경쟁 워크로드의 baseline 측정)에 달려 있고, 이 보고서는 그 측정 방법까지만 제시한다. [CUBRID-C004, CUBRID-C005, CUBRID-C011]

결론 2 — flush. AIO 없이도 이득 후보가 있다: 현행 flush는 디스크에 쓸 때마다 페이지 사본(기본 16KiB memcpy)을 만든다. SX가 있으면 plain page는 사본 없이 frame에서 직접 쓸 수 있다(InnoDB 방식). 대신 I/O 동안 그 page의 writer가 대기하는 새 비용이 생기므로, 사본 CPU 절감과 writer 대기 증가의 트레이드오프를 측정해야 한다. buffered write에서는 write() 시스템콜이 빨리 끝나므로 writer 대기 창이 짧다는 점도 고려 대상이다. [CUBRID-C007, CMP-C001]

결론 3 — AIO/direct I/O. 화살표의 방향이 중요하다: "SX가 AIO 덕을 본다"가 아니라 "AIO/direct I/O write를 하려면 frame 안정성(SX 등가 latch 또는 사본) 확보가 전제조건"이다. buffered write는 시스템콜이 반환되는 순간 kernel이 데이터를 이미 복사했으므로 이후 frame을 고쳐도 안전하지만, direct I/O/AIO는 시스템콜 반환 후에도 kernel/장치가 사용자 버퍼를 계속 읽는다. PostgreSQL이 정확히 이 이유로 SHARE_EXCLUSIVE mode를 도입했고, 그 커밋 메시지는 btrfs에서 실제 파일시스템 오류가 난 사례까지 언급한다. 사본을 유지한 채 AIO를 하는 길도 있으나 in-flight page마다 사본 버퍼가 필요해져 이점이 반감된다. [PG-C003]

범위와 한계

  • 다루는 것: CUBRID page buffer의 latch 체계, 승격(promotion), flush 깔때기, 그 관측 지점. InnoDB/PostgreSQL의 같은 축 비교. SX 도입 설계 스케치.
  • 다루지 않는 것: SX의 실제 구현 코드, LRU/victim 정책 상세, DWB(Double Write Buffer — 원래 위치에 쓰기 전 사본을 별도 파일에 먼저 기록하는 torn-write 보호 장치) 내부, WAL(Write-Ahead Logging — data page보다 log를 먼저 기록하는 규칙) 포맷.
  • 성능 수치 약속 없음: "현행 구조에 이 비용이 존재한다"는 사실과 타 DBMS의 설계 선택까지만 증거로 말한다. 개선 폭 추정은 JIRA CBRD-27196의 측정 계획으로 넘긴다.

요약

SX의 B-tree 이득은 지금 구조에서도 성립하는 후보이고(승격은 실존하는 hot path), flush 이득은 사본 제거 대 writer 대기의 트레이드오프이며, AIO/direct I/O는 SX를 "선택"에서 "필수"로 바꾸는 미래 요인이다. 다음 장에서 latch가 무엇인지부터 쌓아 올린다.
