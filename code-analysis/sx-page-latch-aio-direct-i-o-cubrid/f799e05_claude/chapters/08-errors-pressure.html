8장 — 오류와 자원 압박: 실패 경로의 계약

학습 목표

승격 실패, latch timeout, flush I/O 실패가 각각 어떻게 전파되고 누가 뒷정리를 책임지는지 파악한다. SX 도입은 이 실패 경로들의 계약을 바꾸므로, 현행 계약의 정확한 모양이 기준선이다.

승격 실패는 "예상된 실패"다

ER_PAGE_LATCH_PROMOTE_FAIL은 notification 심각도로만 기록된다 — 시스템 오류가 아니라 정상 프로토콜의 한 분기라는 뜻이다. 그 대신 모든 호출자는 실패 처리 코드를 갖출 의무를 진다. 5장에서 본 12개 호출 지점 각각에 fallback이 붙어 있는 이유이며, SX가 승격을 확정적으로 만들면 이 12벌의 fallback 코드가 단순화 후보가 된다.

자원 압박 아래의 상호작용

  • buffer 부족(victim 압박): 빈 frame을 못 찾는 스레드는 dirty victim의 flush를 기다린다 — flush 깔때기가 밀리면 fix 자체가 밀린다. SX 직접 flush로 I/O 동안 writer를 막는 설계는 이 압박 아래에서 대기 사슬을 하나 더 만들 수 있어, 측정 계획(9장)의 flush-pressure 시나리오가 이 지점을 겨눈다.
  • 로그 압박: WAL 선행(6장) 때문에 로그 flush가 느리면 data flush도 느려진다 — 깔때기 안에 로그 대기가 내장되어 있다.
  • shutdown/restart: 서버 종료는 dirty 전체 flush를 강제하고, 복구는 WAL 재적용으로 재구성한다. latch 상태는 휘발성이라 복구 대상이 아니다 — durable한 것은 page 이미지와 로그뿐이다.

성능 저하 모드의 증상

7장의 방어(timeout) 때문에, latch 설계 결함의 현장 증상은 교착 보고가 아니라 "간헐적으로 수 초~수십 초 멈추는 쿼리"다. 승격 실패 폭증의 증상은 promote_fail 카운터 증가와 B-tree 처리량 하락이 함께 나타나는 것이다(11장의 관측법).

요약

승격 실패는 호출자 책임의 예상된 분기, latch 교착은 timeout으로만 방어, flush 실패는 깔때기가 상태 복원으로 재시도를 보장한다. 다음 장에서 정책 수준의 저울질 — 사본 대 SX, 그리고 AIO 필수성 — 을 다룬다.
