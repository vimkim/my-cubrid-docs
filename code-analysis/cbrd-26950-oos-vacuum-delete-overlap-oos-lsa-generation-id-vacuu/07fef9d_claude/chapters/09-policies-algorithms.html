ch09 — 정책과 알고리즘: 재사용은 설계가 유도한다, heap 은 자기 증언으로 산다

학습 목표

  • 슬롯 재사용 정책의 세 겹(ANCHORED / 최저 슬롯 / bestspace)을 코드 근거와 함께 말할 수 있다.
  • heap 의 mvcc_satisfies_vacuum 이 왜 재시도-안전한지, "자기 증언" 원리로 설명할 수 있다.
  • (설계) 스탬프 비교 알고리즘의 의사코드를 쓸 수 있다.

1. 슬롯 재사용 정책 — 세 겹의 촉진

  1. ANCHORED — OOS 페이지는 spage_initialize(..., ANCHORED, ...)(oos_file.cpp:2087). ANCHORED 페이지에서 spage_delete 는 슬롯을 REC_DELETED_WILL_REUSE 로 표시한다 (slotted_page.c:2091-2096). 대비: 바로 아래 ANCHORED_DONT_REUSE_SLOTS 분기는 REC_MARKDELETED(재사용 금지)를 쓴다 — CUBRID 에는 재사용 안 하는 앵커 모드가 이미 존재하며, OOS 는 그것을 선택하지 않았다.
  2. 최저 슬롯 우선 — spage_find_free_slot 은 슬롯 0 부터 훑어 첫 REC_DELETED_WILL_REUSE 를 취한다(slotted_page.c:1284-1290). 방금 비워진 낮은 슬롯이 선호 착지점.
  3. bestspace 즉시 재등록 — oos_delete_chain 이 청크를 지울 때마다 oos_stats_update(..., prev_freespace=0) 를 호출해(oos_file.cpp:2210) 그 페이지를 전역 캐시에 무조건 밀어 넣는다 — 삭제 sysop 커밋 전에.

Source-confirmed (CUBRID-C020) · Inferred — 세 겹의 곱: "vacuum 이 방금 비운 그 (volid,pageid,slotid) 는 다음 insert 의 선호 착지점이다" (CUBRID-C045). 반증 조건: 재등록을 커밋 후로 미루거나 최저-슬롯 정책이 바뀌면 약화된다.

"재사용은 드물고 재수 없는 우연"이라는 직관은 반대다 — 공간 회수가 목적인 시스템에서 재사용은 성능 목표이고, 정책 세 겹이 전부 재사용을 앞당기는 방향으로 조율되어 있다. 실측: 회수 중 6개 세션의 insert 가 비워지는 슬롯을 실시간으로 받아갔다(ch12).

2. 디스패치 게이팅 정책

is_cursor_entry_ready_to_vacuum(vacuum.c:3255-3283)의 게이트: newest_mvccid < oldest visible(:3260) — 블록 안 모든 트랜잭션이 닫히고 그 옛 버전들이 어떤 스냅샷에도 안 보일 때만 배포한다. 이 게이트의 피연산자는 죽은 버전들의 나이다. "슬롯 점유자의 신원"은 게이트가 만져 본 적 없는 개념이다 — MVCCID 게이팅이 이 결함을 못 막는 이유를 한 문장으로 줄이면 그렇다.

3. heap 의 해법 — 자기 증언(occupant-intrinsic) 판정

/* mvcc.c:320-374 — 시그니처가 곧 설계다 */
MVCC_SATISFIES_VACUUM_RESULT
mvcc_satisfies_vacuum (THREAD_ENTRY *, MVCC_REC_HEADER *rec_header, MVCCID oldest_mvccid)

Source-confirmed — 입력에 로그도 LSA 도 없다. heap vacuum 은 로그에서 주소만 얻고, 파괴 판정은 그 주소의 현재 점유자를 다시 읽어(vacuum_heap_prepare_record, spage_get_record :2188) 점유자 자신의 MVCC 헤더로 재계산한다. 슬롯이 재사용되었다면? — 새 점유자의 헤더가 "살아 있음"을 증언하고, 판정은 CANNOT_VACUUM 으로 나온다. 재시도가 안전한 이유는 코드가 아니라, 대상이 자기 신원·상태를 스스로 증언하는 데이터를 지녔기 때문이다 (CUBRID-C041).

vacuum 이 지연 삭제하는 세 대상의 신원 메타데이터
대상자기 증언 데이터재사용돼도 안전?
heap 슬롯MVCC 헤더 (insid/delid/flags)안전 — 판정 재유도
btree 엔트리키 + MVCC info (키 조회로 정확히 그 엔트리만 접근)안전
OOS 청크없음 (길이/인덱스/next 뿐)불안전 — 본 결함

제안되는 신원 필드는 새 발명이 아니라, vacuum 지연-삭제 대상이라면 갖춰야 할 이 기존 계약을 OOS 에 채워 넣는 것이다. (btree 행은 로컬 문서 근거이며 이 run 에서 btree.c 를 직접 추적하지는 않았다 — ch17 unknown 목록에 명시 CUBRID-C041 한계.)

4. 현재 probe 알고리즘 vs (설계) 스탬프 비교 알고리즘

# 현재 (source-confirmed)
probe(oid) = spage_get_record(oid.slot, PEEK) == S_SUCCESS      # 점유 여부만

# 설계 (미구현 — ch16 blueprint 의 의사코드)
delete_if_mine(vfid, oid, expected_gen):                 # expected_gen 은 undo image 의 확장 stub 에서
    page ← pgbuf_fix(oid.page, W_LATCH)                  # W-latch 안에서 판정+삭제 (TOCTOU 제거)
    recdes ← spage_get_record(oid.slot, PEEK)
    if recdes 없음: unfix; return SKIPPED                # 기존 의미 유지
    header ← parse(recdes)
    if header.generation != expected_gen:                # 등가 비교 — 부등호 아님
        unfix; return SKIPPED                            # 재사용된 슬롯 — no-op
    ... 기존 삭제 계속 (체인 링크도 같은 검증을 통과한 head 에서만 신뢰)

비교가 등가여야 하는 이유(부등호 불가)는 ch16 threshold 반례가 증명한다 (CUBRID-C033).

요약

재사용은 설계가 유도하는 성능 목표라 막을 대상이 아니고, 블록 재주행은 진행 모델의 합리적 귀결이라 없앨 대상이 아니다. heap 이 보여주듯 해법의 자리는 "삭제 판정을 대상의 자기 증언으로 재계산할 수 있게 하는 데이터"다. 다음 장에서 이 결함의 오류 모델 — 왜 아무 신호가 없는가 — 를 본다.
