ch02 — 멘탈 모델: UPDATE 한 번의 일생

학습 목표

  • slotted page, OID, MVCC, WAL/undo image, vacuum, OOS 를 결함 이해에 필요한 깊이로 정의할 수 있다.
  • "UPDATE 한 번이 어디에 무엇을 남기는가"를 그림 없이 말로 재구성할 수 있다.
  • 사고 시퀀스의 뼈대(1차 회수 → 재사용 → 2차 회수)를 개요 수준에서 말할 수 있다.

구체적 시나리오 하나

테이블 t (id INT PRIMARY KEY, gen INT, payload BIT VARYING) 에 5,000바이트 payload 를 가진 행이 있다. 누군가 UPDATE t SET payload = ... WHERE id = 7 을 실행하고 커밋한다. 몇 초 뒤 서버가 정상 종료되고 재기동한다. 이 평범한 시퀀스가 다른 행의 데이터를 지울 수 있다 — 왜 그런지가 이 책 전체의 질문이고, 이 장은 그 질문을 이해할 부품을 쌓는다.

1. 저장 구조: 페이지, 슬롯, 그리고 주소로서의 OID

page 는 디스크 I/O 의 단위다(이 환경에서 16KB). 테이블의 행들은 slotted page 에 담긴다: 페이지 앞쪽에 슬롯 배열(slot directory)이 있고, 각 슬롯이 페이지 안 어딘가의 레코드 위치를 가리킨다. 레코드가 페이지 안에서 이동해도 슬롯 번호는 불변이므로, 바깥 세계는 레코드를 (볼륨 id, 페이지 id, 슬롯 id) 세 쌍으로 부른다. 이 세 쌍이 OID 다.

뿌리 사실 ① — OID 는 이름이 아니라 물리 좌표다. 집 주소이지 주민번호가 아니다. 살던 사람이 이사 가고 새 사람이 들어와도 주소는 그대로다. 슬롯이 비워졌다 재할당되면, 같은 OID 가 완전히 다른 데이터를 가리킨다. 이 하나의 사실에서 결함의 절반이 따라 나온다.

2. 로그: WAL 과 undo image

WAL(Write-Ahead Logging)은 "페이지를 고치기 전에 로그부터 append 한다"는 규칙이다. 로그 레코드 하나는 보통 redo(다시 적용할 방법)와 undo(되돌릴 방법)를 한 봉투에 담는다. UPDATE 의 undo 는 옛 레코드 원본 바이트 통째 — 이것을 undo image 라 부른다. 로그 안의 위치는 LSA(Log Sequence Address, 로그 페이지 id + 오프셋)로 가리키며, LSA 는 곧 시간 순서이기도 하다.

뿌리 사실 ② — 로그는 append-only 불변이다. 한 번 쓰인 undo image 는 아무도 고치지 않는다. 그래서 로그 안의 물리 오프셋(LSA)을 영구 주소로 써도 안전하다 — 그리고 같은 이유로, undo image 속에 박힌 남의 주소(OID)는 세월이 지나 낡아도 갱신되지 않는다.

페이지에는 page LSA 라는 도장이 있다: "이 페이지에 마지막으로 반영된 로그의 LSA". crash recovery 의 redo 가 같은 로그를 같은 페이지에 두 번 적용하지 않게 하는 장치다. 이 도장이 무엇을 못 막는지는 ch08 의 핵심이다.

sysop(system operation)은 트랜잭션 내부의 원자적 미니 단위다. sysop 이 커밋되면 상위 트랜잭션이 나중에 롤백해도 그 부분은 확정된다. "한 번 호출의 원자성"과 "정확히 한 번 실행"은 다른 약속이다 — ch08 에서 대면한다.

3. MVCC: 덮어쓰지 않는 UPDATE

읽는 트랜잭션을 막지 않으려고, CUBRID 는 UPDATE 시 값을 제자리에서 덮어쓰지 않고 버전을 만든다(MVCC, Multi-Version Concurrency Control). 레코드 머리의 MVCC 헤더에 insert MVCCID(만든 트랜잭션), delete MVCCID(대체/삭제한 트랜잭션), prev_version_lsa(이전 버전이 있는 로그 위치)가 실린다.

MVCCID 는 트랜잭션의 첫 write 시점에 발급되는 단조증가 번호다 — 커밋 시점이 아니라는 것이 뒤에서(ch16) 결정적으로 중요해진다 (CUBRID-C031). 각 스냅샷은 "어느 MVCCID 까지 보이는가"를 판정하고, 시스템 전체에서 살아있는 스냅샷들의 하한선을 oldest visible MVCCID 라 한다.

뿌리 사실 ③ (CUBRID 특유) — CUBRID 는 in-place MVCC 다: 새 버전이 heap 슬롯을 차지하고, 옛 버전의 유일한 실체는 로그의 undo image 다. PostgreSQL 처럼 옛 버전이 heap 에 남지도, Oracle 처럼 별도 rollback segment 가 있지도 않다. "옛 버전을 참조하려면 로그를 읽는다" — 이 설계가 vacuum 의 모양을 결정한다.

4. vacuum: 로그를 작업 큐로 쓰는 청소부

MVCC 의 청구서는 지연 회수다: 아무 스냅샷도 더는 볼 수 없게 된 옛 버전들을 누군가 나중에 청소해야 한다. CUBRID 의 vacuum 은 테이블을 스캔하지 않는다 — 로그 자체를 작업 큐로 쓴다. 로그를 일정 크기(vacuum block)로 잘라, 블록 요약 {blockid, start_lsa, oldest/newest MVCCID} 을 영속 큐(vacuum data)에 등록하고, 블록 안의 모든 트랜잭션이 닫힌 뒤(newest < oldest visible) worker 에게 배포한다. worker 는 블록의 로그 레코드들을 걸으며 죽은 버전을 청소한다.

5. OOS: 큰 값을 밖으로

4바이트 id 하나를 읽으려고 9KB 레코드를 읽는 낭비를 없애려고, CUBRID 는 큰 가변 컬럼 값을 별도의 OOS 파일(heap 파일당 최대 1개)로 빼낸다. heap 레코드에는 16바이트 OOS inline stub 만 남는다: head OOS OID(8B — 값이 시작하는 OOS chunk record 의 물리 OID) + full length(8B). 값이 한 페이지에 안 들어가면 청크들이 next_chunk_oid 로 이어진 OOS value chain 이 된다.

OOS chunk record 의 헤더는 딱 세 필드다 — total_data_length / chunk_index / next_chunk_oid.

Source-confirmed — 뿌리 사실 ④: 청크 헤더에는 신원 필드가 없다. 누구의 것인지(owner), 몇 번째 세입자인지(generation), 언제 태어났는지(MVCCID/LSA) — 아무것도 없다 (CUBRID-C002). 구조체 네 줄을 읽으면 스스로 확인할 수 있다 (oos_file.hpp:26-31).

소유 규칙: 한 OOS value chain 은 정확히 하나의 논리 heap-record 버전이 소유하며, 버전 간에 공유되지 않는다(현행 M1 — UPDATE 는 항상 새 체인을 만든다). 그래서:

UPDATE 후 옛 체인을 가리키는 유일한 참조는, 로그 속 undo image 안의 옛 stub 하나뿐이다. 살아있는 어떤 heap 레코드도 옛 체인을 가리키지 않는다. 그럼 옛 체인은 누가 지우나? — vacuum 이 undo image 를 읽어서 지운다. 이것이 forward-walk 다(ch06).

6. 한 UPDATE 의 일생 (V-1)

텍스트 대안: UPDATE 는 heap 페이지의 새 버전과 WAL 의 UPDATE 로그(undo = 옛 레코드 통째)를 동시에 남긴다. 뒤이은 로그가 블록 경계를 넘으면 블록 요약이 발행되어 vacuum data 에 AVAILABLE 로 등록되고, 그 블록의 옛 버전을 볼 수 있는 트랜잭션이 모두 끝나면 worker 가 받아 로그를 걸으며 옛 OOS 체인을 즉시 삭제한다. 완주해야 VACUUMED 도장이 찍히고, 못 하면 블록 전체가 재실행된다 (CUBRID-C001, C010, C042).

7. 옷보관소 비유 — 그리고 이 비유가 깨지는 곳

옷보관소 직원(vacuum)이 "5번 고리의 코트를 치워라"는 오래된 표(undo image 속 옛 stub)를 들고 온다. 직원은 "5번 고리에 코트가 걸려 있나?" 만 확인하고(점유-probe) 치운다. 그 사이 5번 고리는 비었다가 다른 손님이 자기 코트를 걸었다(슬롯 재사용). 직원은 남의 코트를 치운다. 직원은 규정을 어기지 않았다 — 결함은 부주의가 아니라 계약의 공백이다.

비유의 정확한 한계 세 가지를 지금 박아 둔다:

  • 표는 고칠 수 없다 — 표는 관공서 대장(WAL)에 잉크로 인쇄되어 나오며 직원에게 수정 권한이 없다. "표에 완료 체크를 하면 되잖아"는 이 시스템에서 불가능하다(뿌리 사실 ②).
  • 옷에는 이름표를 달 칸 자체가 없다 — 청크 헤더 네 줄에 신원 필드가 없다(뿌리 사실 ④). 직원이 아무리 자세히 봐도 대조할 것이 없다.
  • 표에는 옷 사진이 없다 — 표(stub)에는 위치(head OOS OID)와 크기(full length)만 적혀 있다. undo image 는 값을 풀어서 저장하지 않는다.

"직원이 왜 이틀 연속 오는가"(블록 재처리)는 이 비유가 담지 못한다 — ch05 에서 별도 비유(재고 실사)로 다룬다.

8. 미리 차단하는 오개념 4가지

  • "page LSA 가 모든 이중 효과를 막는다" — page LSA 는 crash recovery 의 redo replay 중복만 막는다. ch08 에서 대면.
  • "undo 에는 값이 풀린 채 저장된다" — undo image 는 옛 레코드 원본(stub 포함) 그대로다. 값을 풀면 undo 로그가 OOS 의 존재 이유를 스스로 무너뜨린다.
  • "vacuum 은 레코드 단위로 진행을 기록한다" — 블록 단위뿐이다. ch05.
  • "MVCCID 순서 = 커밋 순서" — 발급은 첫 write 시점이다. 장기 트랜잭션이 끼면 순서가 어긋난다. ch16 의 반례가 여기서 나온다.

요약

네 개의 뿌리 사실 — ① OID 는 물리 좌표다, ② 로그는 불변이다, ③ 옛 버전은 로그 안에만 산다, ④ OOS 청크에는 신원이 없다 — 위에 "vacuum 은 로그를 작업 큐로 쓴다"를 얹으면, 남은 것은 시간 문제다: 불변의 낡은 주소를 들고 오는 재방문자와 그 주소에 새로 든 세입자가 만나는 순간. 다음 장에서 그 재방문자가 지나는 문(Interface)들을 정확히 살펴본다.
