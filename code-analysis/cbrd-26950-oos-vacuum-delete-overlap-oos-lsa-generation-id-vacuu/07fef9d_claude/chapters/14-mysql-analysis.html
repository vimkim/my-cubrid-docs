ch14 — MySQL/InnoDB: 같은 모양의 경로, 이미 구현된 스탬프

학습 목표

  • InnoDB off-page LOB 참조(20B)와 purge 의 undo-유도 forward 경로를 설명할 수 있다.
  • purge 가 exactly-once 가 아님에도 이중 해제가 없는 세 겹 방어를 나열할 수 있다.
  • UPDATE 경로와 DELETE 경로의 방어 비대칭 — CUBRID 와의 정확한 대응점 — 을 짚을 수 있다.

기준: MySQL trunk 06a5c1c99, 실소유자는 스토리지 엔진 InnoDB (storage/innobase/). SQL 서버 계층에는 회수 훅이 없다 — purge 는 전적으로 엔진 내부다.

1. 같은 모양: undo 레코드에서 물리 주소로

Source-confirmed — 클러스터드 레코드의 off-page 컬럼 참조는 20바이트: space id 4B + page no 4B + offset/version 4B + length 8B(상위 비트에 owner/inherited/being-modified 플래그) — 물리 주소다 (lob0lob.h:102-136). UPDATE 로 대체된 extern 값의 회수는 purge 스레드가 row_purge_upd_exist_or_extern_func(row0purge.cc:700-828)에서 roll_ptr 로 undo 페이지를 열고 그 안의 참조를 읽어 lob::purge 를 호출하는 — CUBRID forward-walk 와 동형의 "로그 유도 물리 주소 회수" 경로다 (MYSQL-C001).

2. purge 는 exactly-once 가 아니다 — 그런데도 안전한 이유

Source-confirmed — purge 진행(purge_sys 의 iter/limit)은 메모리 전용이다(trx0purge.cc:220-232). 재기동하면 on-disk rollback-segment history list 의 꼬리에서 위치를 재유도한다(trx0rseg.cc:270-301) — 처리했지만 아직 history 에서 unlink 되지 않은 undo 레코드는 다시 처리된다. CUBRID 의 블록 재처리와 정확히 같은 상황이다 (MYSQL-C002). 그런데 이중 해제가 없다. 세 겹:

  1. 드라이버의 파괴적 자기-표시 — LOB 를 해체한 같은 redo-logged mini-transaction 안에서, undo 페이지에 든 참조 자체에 FIL_NULL 을 써 넣는다 (lob0purge.cc:541-542). 재처리는 page_no == FIL_NULL 을 보고 즉시 return. "지시서를 소비하면서 지시서에 도장을 찍는" 방식 — CUBRID 의 WAL 은 불변이라 이 방식이 이식 불가능하다(undo image 를 고쳐 쓸 수 없음) (CMP-C002).
  2. 대상 객체의 신원 스탬프 — 다음 절.
  3. 페이지 타입 검사 — LOB 첫 페이지가 아니면 ut_a 로 즉사(조잡한 점유자-내재 검사 — "지금은 B-tree 페이지"는 잡지만 "지금은 다른 LOB"는 못 잡는다).

중요한 예외: 해제 조건의 실제 형태는 if (rec_type == TRX_UNDO_DEL_MARK_REC || ok_to_free)(lob0purge.cc:517)로, delete-mark 레코드는 스탬프 비교 없이 해제된다. 스탬프가 필요 없는 이유는 §4 에 있다 — 그 경로는 살아있는 클러스터드 레코드에서 점유자-내재 검사(roll_ptr 등가 + delete-mark)를 할 수 있기 때문이다. ch14 만 보고 재구현하는 사람이 모든 경로에 스탬프 검사를 걸지 않도록 명시해 둔다.

3. 신원 스탬프 — 제안된 수정의 동형 선례

Source-confirmed — LOB 첫 페이지 헤더에 OFFSET_LAST_TRX_ID(6B) + OFFSET_LAST_UNDO_NO(4B)가 있다 (lob0first.h). 컬럼을 통째로 대체하는 UPDATE 는 옛 LOB 의 첫 페이지에 (trx->id, trx->undo_no - 1) 을 기록한다(mark_cannot_be_partially_updated, lob0first.cc:403-413). 호출부 주석이 목적을 명시한다: "This is to inform the purge thread that the older version LOB in this update operation can be freed"(lob0lob.cc:570-576). purge 는 해제 전에 등가 비교한다(lob0purge.cc:505-517):

ok_to_free = (rec_type ∈ {UPD_EXIST, UPD_DEL})
          && !can_be_partially_updated(lob)
          && last_trx_id == trxid            /* undo 레코드의 트랜잭션 */
          && last_undo_no == undo_no;        /* undo 레코드의 번호 — 정확한 등가 */

물리 주소만으로는 절대 해제하지 않는다 — UPDATE(참조를 해제한 자)가 미리 써 둔 신원과, 지금 소비 중인 undo 레코드의 신원이 정확히 일치할 때만. CUBRID 제안(4B generation 등가 비교)과 목적·비교 형태가 같다 (MYSQL-C004).

버전 간 LOB 공유(= CUBRID 미래 dedup 과 동형)는 참조의 owner/inherited 플래그로 관리된다: PK 변경형 UPDATE 에서 무변경 extern 컬럼은 새 엔트리가 owner+inherited 를 받고 옛 레코드는 disown 된다(row0upd.cc:2530-2650) — "여러 버전이 하나의 값을 공유할 때 해제 권한을 누가 갖는가"를 데이터로 표현한 선례.

4. 정직한 관찰: UPDATE 경로의 방어는 스탬프뿐이다

Source-confirmed — DELETE 경로의 purge 는 살아있는 클러스터드 레코드에 커서를 대고 occupant-intrinsic 검사 (roll_ptr 등가 + delete-mark, 중간 mtr 커밋 후 재검증까지)를 한다. 그러나 UPDATE-of-extern 경로에서는 그 검사들이 구조적으로 비활성이다: 이 경로의 BtrContext 는 클러스터드 레코드 없이 만들어져(m_rec = nullptr) is_delete_marked() 가 무조건 true 를 반환한다(lob0lob.h:1470-1476). 남는 살아있는 방어 = 스탬프 등가 + FIL_NULL self-mark 뿐 (MYSQL-C003).

즉 InnoDB 는 "CUBRID 와 같은 모양의 경로에는 occupant 검사가 불가능하다"는 것을 이미 겪었고, 그 답으로 스탬프를 택했다. CUBRID 제안이 걷는 길의 선례 그 자체다.

불일치 시의 실패 방향도 참고할 만하다: ok_to_free 의 논리곱이 거짓이면 purge 는 아무것도 해제하지 않고 지나간다(lob0purge.cc:505-517) — 즉 이중 해제 대신 회수 보류 (최악의 경우 누수)를 택하는 구조다. 이것이 CUBRID 제안의 "불일치 = no-op" 정책과 같은 방향이다.

다만 정확히 구분해 둘 것: 같은 파일의 :531-538 주석 — "If a crash happens after the btr_mtr commit and before freeing the LOB first page, then the LOB first page will be leaked. We need to come up with a mechanism to avoid this leak." — 은 설계 선택이 아니라 인정된 미해결 결함(크래시 창 누수)이며, 저자가 제거하고 싶다고 적어 둔 것이다. InnoDB 를 "누수를 의도적으로 감수하는 설계"로 인용하면 소스를 오독하는 것이다.

해제된 페이지 자체에는 세대/에포크 표시가 없다(XDES free 비트뿐, fsp0fsp.cc:3600-3603) — 컨테이너 수준 재사용 감지는 InnoDB 에도 없으며, 그 공백을 대상-객체 스탬프가 메운다.

위치 차이의 이유: InnoDB 의 회수 단위는 페이지라 대상 객체(첫 페이지)에 스탬프를 둘 수 있다 — 회수가 끝날 때까지 그 페이지는 재활용되지 않으니까. CUBRID 의 회수 단위는 슬롯이라 "객체"가 삭제와 함께 소멸한다 — 그래서 스탬프는 살아남는 두 곳, 즉 점유물(청크 헤더)과 참조(stub, undo image 에 보존됨)에 나눠 실리고, 유일성의 원천은 컨테이너(페이지 카운터)가 되어야 한다(ch16).

요약

InnoDB 는 CUBRID 와 같은 모양의 undo-유도 물리 주소 회수를 갖고 있고, 같은 재처리 가능성을 안고 있으며, 그 답이 정확히 "UPDATE 가 미리 써 둔 신원 스탬프의 등가 비교"다. 차이는 스탬프의 위치와 폭, 그리고 CUBRID 가 쓸 수 없는 self-mark 보조 장치의 유무뿐이다. 다음 장에서 세 시스템을 한 표에 놓는다.
