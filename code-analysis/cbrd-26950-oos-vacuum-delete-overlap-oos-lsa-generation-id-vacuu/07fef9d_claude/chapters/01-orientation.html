ch01 — Orientation: 무엇을, 어디까지, 왜

학습 목표

  • 이 책이 답하는 8개 질문과, 각 질문이 어느 챕터에서 닫히는지 말할 수 있다.
  • 무엇이 구현된 사실이고 무엇이 설계 단계 제안인지 구분할 수 있다.
  • 선언된 범위(Declared Scope)의 경계 — 포함/제외 — 를 말할 수 있다.

주제 한 문장

CUBRID vacuum 이 UPDATE/DELETE 로 죽은 heap 레코드 버전의 OOS value chain 을 지연 회수(forward-walk)할 때, 블록 재처리와 OOS 슬롯 재사용이 겹치면 신원 확인 없는 probe 가 살아있는 행의 체인을 두 번째로 삭제하는 결함(CBRD-26950)의 전체 메커니즘 — 그리고 이를 막는 신원 스탬프 설계와 미래 dedup 의 OOS update log 방향.

용어가 아직 낯설어도 괜찮다. ch02 가 바닥부터 쌓는다. 여기서는 지도를 그린다.

구현된 것 vs 설계 단계인 것

  • Source-confirmed (구현 사실) — forward-walk 회수 경로, 점유-probe, 블록 상태 기계, 슬롯 재사용 정책, eager 경로. 그리고 결함 자체 (CUBRID-C023, 이 run 에서 캡처된 런타임 재현 2/2 — 그중 rep 2 가 정상 셧다운 회차다).
  • Inferred / Documented — 신원 스탬프 후보 판정(6a/6b/threshold/owner OID/generation), 2026-08-07 회의의 generation·OOS LSA 채택 방향, dedup 의 OOS update log 방향. 어느 것도 아직 코드에 없다. 판정의 전제들만 source-confirmed 다.
  • Unknown — "OOS LSA" 의 회의 정의(CUBRID-C035), experiment-2 채널 B 구성(CUBRID-C048), btree 안전성의 소스 직접 확인 등. 전체 목록은 ch17.

Declared Scope

포함

  • forward-walk 회수 경로 전체(undo image 파싱 → probe → 체인 삭제 → sysop → bestspace 재등록)와 그 두 호출부.
  • vacuum 블록 상태 기계: 생산·게이팅·중단·재장전·재주행, start_lsa 불변.
  • OOS 슬롯 재사용: ANCHORED, 최저 슬롯 우선, 삭제 즉시 bestspace 재등록.
  • 결함 성립 3조건의 결합, eager 경로·DELETE(REMOVE) 경로가 대상이 아닌 이유.
  • 기존 보호 장치(page LSA, sysop, 래치, MVCCID 게이팅)가 왜 못 막는가.
  • 신원 스탬프 설계 공간(R1~R5, 후보 6종 — OOS LSA 포함)과 dedup 보호 장치 4종(OOS update log 포함) — 설계 분석.
  • 런타임 재현 실험 2종.

제외 (이웃 책임 — 언급만)

  • OOS demotion 정책 상세(largest-first, 4,060B 타깃 유도 — CBRD-26776/27057).
  • bestspace 3-tier 내부 구조(CBRD-26658) — 슬롯 재사용 촉진 역할만.
  • TDE, replication 상세, CDC/flashback, unloaddb 성능.
  • btree vacuum 상세, 빈 OOS 페이지 회수(CBRD-26786 — 미구현).
  • 수정 구현 자체 — 이 책은 분석·blueprint 이며 소스를 바꾸지 않았다.

Provenance 와 재현성

모든 소스 인용은 고정 3 리비전 기준이며 파일 해시가 evidence/claims.jsonl 에 기록되어 있다. CUBRID worktree 는 dirty 상태로 기록되어 있고 (provenance.json 의 dirty: true), 추적 항목 중 변경된 것은 cubrid-cci 서브모듈 포인터 하나이며 나머지는 비추적 파일이다. 인용된 소스 파일은 전부 커밋과 바이트 일치한다(evidence_state=COMMIT, 감사에서 97/97 해시 확인). 런타임 증거는 evidence/runs/<id>/ 에 argv·exit·stdout/stderr 가 원자적으로 보존된다.

한계 선언

  • 설계 후보의 정확성 논증은 현재 구현의 불변식에 조건부다 — 어떤 불변식에 기대는지 ch16 이 명시한다.
  • 비교 대상(PG/MySQL)은 소스 근거만 사용했고 그들의 서버는 실행하지 않았다.
  • 본 결함의 재현은 debug 빌드에서 관측되었다 — 관측 채널(oos.log)만 debug 전용이고 발현 메커니즘은 release 와 동일 코드다(CUBRID-C023 한계 참조).

요약

이 책은 "vacuum 이 남의 데이터를 지운다"는 한 문장을, 고정 리비전 소스의 함수 단위 증거와 캡처된 2/2 런타임 재현으로 분해하고, 그 수리 설계 공간을 InnoDB 선례·PostgreSQL 대안 설계와 나란히 놓는다. 다음 장에서 UPDATE 한 번이 시스템에 남기는 것들을 그림으로 쌓는다.
