ch10 — 오류 모델: silent loss 는 어떻게 "무증상"이 되는가

학습 목표

  • forward-walk 의 오류 격리 정책(무전파·유계 누수)과 그 이유를 설명할 수 있다.
  • 발생 시점·검출 시점·불검출 가능성의 삼분법으로 silent loss 를 분석할 수 있다.
  • 중단·assert 경계(debug vs release)와 부수 발견들을 열거할 수 있다.

1. forward-walk 의 오류 격리

Source-confirmed — vacuum_forward_walk_reclaim_oos 는 어떤 실패도 블록으로 전파하지 않는다: 모든 오류 경로가 vacuum_er_log_error 로 기록하고 er_clear() 후 return 한다 (vacuum_oos.cpp:218-220, 275-303). in-source 근거: "블록을 실패시키면 vacuum_finished_block_vacuum 의 shutdown 전용 assert 를 건드리고 vacuum 전체를 멈출 수 있다". 실패의 결과는 유계·기록된 OOS 누수 — 데이터 손상보다 훨씬 나은 실패 방향이다 (CUBRID-C044).

아이러니: 오류 처리는 fail-safe 방향(누수)으로 잘 설계되어 있는데, 정작 오류가 아닌 경로(probe 통과 → 삭제 성공)가 데이터를 파괴한다. 결함의 어떤 단계도 오류 코드를 만들지 않기 때문에 오류 처리 체계 전체가 관여할 기회가 없다.

2. silent loss 의 삼분법

발생·검출·오검출 (CUBRID-C023)
시점일어나는 일신호
발생 (2차 삭제)정상 RVOOS_DELETE — 로그·통계 모두 정상 vacuum 작업으로 기록없음. 릴리스에서도 살아 있는 oos_error 계열은 실패 분기 전용이고 이 삭제는 성공하므로 걸리지 않는다; 성공 기록은 debug 전용 oos_debug 한 줄뿐이다 (CUBRID-C047)
검출 (이후 읽기)stub → head OID → 빈 슬롯: Internal error: slot N ... is not allocated읽기 시점의 internal error — 원인과 시간·주체가 분리됨
불검출 위험비워진 피해 슬롯이 또다시 재사용된 뒤 읽히면 — 오류 없이 남의 값이 반환될 수 있음없음 — 값 검증 애플리케이션만 감지 가능

재현 실험은 payload 앞 8 hex 에 자기 id 를 각인해 세 번째 행(값 오염)도 감지하도록 설계되었고, 이번 run 관측치는 0 이었다 — 그러나 0 관측은 "일어나지 않는다"의 증명이 아니라 이번 타이밍에서 안 일어났다는 뜻이다(ch12).

3. 중단과 assert 경계

  • 정상 셧다운 — worker 는 thread_p->shutdown 에서 goto end (vacuum.c:3493-3498). 오류가 아니라 협조적 중단이며, 블록은 INTERRUPTED 로 남는다.
  • debug 빌드의 경계 — vacuum_finished_block_vacuum 은 비-shutdown 중단을 assert(thread_p->shutdown) 으로 잡는다(:3918-3919). 따라서 "블록 중간 에러로 인한 재처리" 트리거는 release 빌드 전용 시나리오다 (CUBRID-C011 한계).
  • 머지 준비 항목(결함과 별개) — vacuum_oos.cpp 의 무조건 abort() 2곳 (:315, :372 — "remove before develop merge" 표시): undo image 에 OOS 플래그가 있는데 heap 에 OOS 파일이 없으면 release 에서도 프로세스를 죽인다. 진단용 임시 크래시 장치다 (CUBRID-C044).
  • 부수 발견 — 이 run 에서 실제로 발생했고 스택을 확보했다 (별도 티켓 후보, CBRD-26950 과 다른 결함): 셧다운이 클라이언트의 OOS INSERT 를 인터럽트하면 pgbuf_fix 가 ER_INTERRUPTED 를 정상 반환하는데 oos_file_alloc_new 가 이를 불가능 상황으로 보고 assert(false)(oos_file.cpp:1892) 를 걸어 debug 서버가 abort 한다. experiment-2 rep 1 이 이렇게 종료됐다 — 확보된 스택 (evidence/raw/rep1-abort-backtrace.txt, SIGABRT): qexec_execute_insert → locator_attribute_info_force → heap_attrinfo_transform_to_disk_internal(heap_file.c:13150) → heap_attrinfo_insert_to_oos → heap_oos_insert_serialized_values → oos_insert_many → oos_insert_single_page_batch → oos_find_best_page(rec_length=5024) → oos_file_alloc_new → assert. 즉 R3 writer 의 5,000B INSERT 가 정지 요청과 겹친 것이다. 인터럽트는 정상 경로이므로 에러를 전파해야 할 자리다. 이 abort 는 rep 1 의 해석에 영향을 준다 — ch12 의 rep 1 / rep 2 구분과 대안 설명 참조. (1.4 GB 코어 파일은 스택 추출 후 삭제했고 스택만 증거로 보존한다.)

4. 자원 압박 관점

  • 디스크 풀·I/O 오류 — forward-walk 안에서는 위 오류 격리로 누수化(fail-safe). 이 결함 자체는 자원 압박과 무관하게, 오히려 시스템이 건강할수록(회수·삽입이 빠를수록) 잘 발현된다.
  • OOS 누수의 축적 — 오류 격리·수정 후보의 skip 분기 모두 누수를 만든다. 빈 페이지 회수(CBRD-26786)가 미구현이므로 누수는 파일 성장으로 남는다 — 스탬프 설계에서 "불일치 = skip" 이 안전한 이유는 그 skip 이 이미 남의 것이 된 슬롯에 대한 것이라 누수조차 아니기 때문이다(정당한 대상은 항상 일치 — R3).

요약

이 결함의 오류 모델은 "오류가 없다"는 것이다: 발생은 정상 연산으로 기록되고, 검출은 시간·주체가 분리된 internal error 이며, 최악의 경우 오류 없이 남의 값이 반환된다. fail-safe 하게 설계된 오류 격리조차 관여할 틈이 없다. 다음 장에서 이 무증상성이 관측성 공백과 어떻게 결합하는지 본다.
