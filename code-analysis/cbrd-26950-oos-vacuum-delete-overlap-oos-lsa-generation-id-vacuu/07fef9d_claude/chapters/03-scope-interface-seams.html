ch03 — Interface 와 Seam: 세 삭제 경로와 probe 의 계약

학습 목표

  • OOS 체인을 지우는 세 경로(forward-walk / within-sysop / eager)의 호출자 의무를 구분할 수 있다.
  • oos_chunk_exists 가 약속하는 것과 약속하지 않는 것을 시그니처 수준에서 말할 수 있다.
  • 신원 확인이 들어가야 할 Seam(이음새)의 위치를 지목할 수 있다.

Module 경계

이 책의 Module 은 "vacuum 의 OOS value-chain 지연 회수 서브시스템"이다. 구현 파일은 src/query/vacuum_oos.cpp(vacuum 쪽 어댑터), src/storage/oos_file.cpp/.hpp(스토리지 연산), src/storage/heap_oos.cpp(heap-속성 계층)이고, 이 Module 이 의존하는 외부 Seam 이 둘 있다: vacuum 블록 상태 기계(vacuum.c — 진행 단위를 결정)와 슬롯 재사용 정책 (slotted_page.c + OOS bestspace — 재사용 속도를 결정).

forward-walk 만이 "죽은 지 오래된 버전의, 페이지에서 이미 사라진 참조"를 다룬다. 나머지 두 경로는 삭제 순간에 대상의 신원이 다른 수단으로 보장된다 — within-sysop 은 점유자 자신에게서 판정을 재유도하고, eager 는 동기 실행이라 재사용이 끼어들 창 자체가 없다 (CUBRID-C040, C041).

probe 의 계약 — 정직하지만 불충분한

forward-walk 의 삭제 직전 유일한 관문은 이것이다:

/* oos_file.hpp:112-114 */
/* Idempotency probe: *out_exists is true iff the chunk's slot is still present. ... */
extern int oos_chunk_exists (THREAD_ENTRY *thread_p, const OID &oid, bool *out_exists);

Source-confirmed — 시그니처를 읽자. 입력은 OID 하나다. 기대 신원을 받을 자리 자체가 없다. 구현은 spage_get_record(..., PEEK) 가 S_SUCCESS 면 가져온 레코드를 한 바이트도 읽지 않고 *out_exists = true 를 반환한다 (oos_file.cpp:2235-2275, 판정 :2262-2266). 헤더 주석도 정직하다 — "the chunk's slot is still present"(슬롯의 존재이지 청크의 신원이 아니다) (CUBRID-C002).

호출부(vacuum_oos.cpp:174-191)의 in-source 주석은 설계 의도를 그대로 보여준다: 블록 재시도가 이미 지운 OID 를 다시 제시할 수 있으니 "없으면 건너뛰라"는 것. 저자는 재시도를 정확히 인지했고, 존재 여부를 멱등성 장치로 택했다 — 그 선택은 슬롯이 재점유될 수 없을 때만 건전하다. 계약의 공백은 여기다.

두 번째 삭제 직전, 엔진이 아는 것: (volid, pageid, slotid) 에 레코드가 있다. 알 수 없는 것: 그 레코드가 여전히 undo image 가 소유하던 그 청크인가. 비교할 데이터가 청크에도(헤더 3필드), stub 에도(OID+길이), 시그니처에도 없다.

호출자 의무 (precondition) 정리

  • vacuum_forward_walk_reclaim_oos(thread_p, undo_data, undo_data_size, vfid, memo) — 호출자는 NOTIFY 계열 undo image 만 넘겨야 하며(레코드 타입 가드 :245 가 REC_BIGONE/RELOCATION 의 8바이트 OID 이미지를 걸러냄), 실패를 기대하면 안 된다(오류는 내부에서 소비되고 유계 누수로 남는다, CUBRID-C044).
  • oos_delete(thread_p, vfid, oid) — 문서화된(그러나 forward-walk 에서는 공허한) 전제: "호출자가 행 수준 잠금을 보유"(oos_file.cpp:2137-2138 미해결 주석). 죽은 행에는 잠글 실체가 없다.
  • oos_insert 계열 — 페이지 W-latch 아래에서 헤더 직렬화(:1503) → 슬롯 확정(:1516) → 전체 이미지 물리 로깅(:1530). 스탬프 설계가 개입할 지점이다(ch16).

신원 확인이 들어갈 Seam

바뀌어야 할 최소 계약은 한 곳이다: 삭제 직전 확인. 단, 구현 위치는 probe 가 아니라 oos_delete_chain 의 W-latch 구간이어야 한다 — probe 는 판정 전에 페이지를 unfix 하므로 (:2260) 내용 검사를 넣어도 확인-후-삭제 사이(TOCTOU)의 경쟁이 남는다 (CUBRID-C002 한계). Seam 의 형태: oos_delete(thread_p, vfid, oid, expected_identity) — 기대 신원은 undo image 의 확장된 stub 이 나른다(ch16 blueprint).

이웃 책임 (범위 밖, 경계만)

  • OOS demotion(어떤 값이 OOS 로 가는가): 쓰기 시점 정책. 이 책은 "5,000B 값은 간다"만 쓴다.
  • bestspace: 빈 공간 힌트 캐시. 이 책에는 "삭제 즉시 재등록되어 재사용을 촉진한다"는 역할로만 등장한다.
  • 빈 OOS 페이지 회수: 미구현(oos_remove_page 프로덕션 호출자 0 — CBRD-26786). 따라서 probe 의 "페이지 소멸" 분기는 사실상 도달 불가다 (CUBRID-C020 한계).

요약

세 삭제 경로 중 forward-walk 만이 "신원을 확인할 수단이 없는 대상"을 다루고, 그 유일한 관문(probe)은 시그니처부터 신원을 받을 수 없게 생겼다. 계약의 공백은 코드 실수가 아니라 설계 가정("빈 슬롯은 그대로 비어 있다")의 공백이다. 다음 장에서 그 가정이 왜 성립하지 않는지 — 데이터의 소유권과 수명을 따라가며 본다.
