ch11 — 성능과 관측성: 빠를수록 위험하고, 릴리스에선 보이지 않는다

학습 목표

  • 발현 빈도를 결정하는 성능 변수(회수율, 도장 지연, 재사용 속도)를 말할 수 있다.
  • oos.log 관측 채널의 비대칭(삭제만 기록)과 그 파급을 설명할 수 있다.
  • 스탬프 설계의 성능·공간 비용 회계를 제시할 수 있다.

2. 관측성 공백 — oos.log 는 절반만 말한다

Source-confirmed — debug 전용 oos.log 의 기록 지점은 4곳뿐이며, insert 기록은 단건 API oos_insert(oos_file.cpp:1219)에만 있다. 실제 프로덕션 INSERT 경로인 배치 API (oos_insert_many → oos_insert_single_page_batch, :1223-1274)는 아무것도 남기지 않는다. 삭제는 남는다(:2212-2213) (CUBRID-C043).

파급 세 가지:

  1. 슬롯 재사용을 로그로 직접 증명할 수 없다 — "삭제 후 같은 자리에 insert" 의 후반부가 안 보인다. 재현 실험이 두 pass 의 삭제 집합 교집합(재삭제 = 그 사이 누군가 점유했다는 간접 증거)으로 우회한 이유.
  2. 채널 B 의 구성 미해명(ch12)도 같은 공백의 결과 — 재삭제된 슬롯의 점유자를 사후 식별할 수단이 없다 (CUBRID-C048).
  3. release 빌드에는 이 채널조차 없다 — 운영 환경에서 이 결함은 사후 진단이 사실상 불가능한 부류다(CBRD-26871 이 요구하는 도구의 부재).

3. 스탬프 설계의 비용 회계 (V-10)

텍스트 대안: 제안 설계에서 OOS inline stub 은 head OOS OID 8B + full length 8B + generation 4B = 20B, 청크 헤더도 16B 에 generation 4B 가 더해져 20B 가 된다. stub 비용은 행마다· OOS 컬럼마다, 청크 헤더 비용은 청크마다 반복된다. 패딩으로 24B 를 만들지 않는 이유는 variable area 안 오프셋이 임의여서 정렬 이득이 없기 때문이다.

쓰기 경로 비용: 페이지 카운터 증가는 이미 보유한 W-latch 아래 정수 하나 — 추가 래치·추가 페이지 fix·추가 로그 레코드가 없다(전체 이미지 로깅에 4B 가 실려 갈 뿐) (CUBRID-C032). 읽기 경로 비용: probe/delete 시 헤더 4B 비교 1회. 연쇄 갱신 항목: OR_OOS_INLINE_SIZE 16→20, demotion 수익성 문턱, 경계 테스트류.

4. 계측 채널: 카운터·유틸리티·디버거 랜드마크

Source-confirmed — vacuum 에는 자체 perfmon 카운터가 있고 릴리스 빌드에서도 cubrid statdump 로 볼 수 있다 (CUBRID-C047):

이 Module 과 관련된 계측 채널
채널무엇을 세는가이 결함에 쓸 수 있는가
Num_vacuum_log_pages_vacuumed (PSTAT_VAC_NUM_VACUUMED_LOG_PAGES, vacuum.c:3755) 블록 완료 시 그 블록의 로그 페이지 수를 누적 — 즉 블록 처리량 부분적. 재주행이 일어나면 같은 페이지가 다시 더해지므로 총합이 로그 크기를 넘는 것이 재처리의 간접 신호가 된다. 그러나 어느 블록인지·어느 슬롯인지는 알 수 없다
vacuum_job / vacuum_worker_execute (PSTAT_VAC_JOB, PSTAT_VAC_WORKER_EXECUTE, vacuum.c:3778-3779) job·worker 실행 횟수와 누적 시간 부분적. job 수가 발행 블록 수보다 크면 재실행을 시사
oos.log (oos_debug) OOS 청크 단위 삭제 {vol,page,slot} — 이 결함을 직접 보이는 유일한 채널 debug 전용: 매크로가 NDEBUG 에서 no-op 로 컴파일된다(oos_log.hpp:162-177). 게다가 insert 는 배치 경로에서 기록되지 않는다(CUBRID-C043)
서버 에러 로그 (er_log_vacuum) Add block, 완료 통지, is interrupted! 부분적 — 경고 부재가 안전을 뜻하지 않는다(ch05)

디버거 랜드마크(포워드워크를 추적할 최소 중단점 4개): vacuum_forward_walk_reclaim_oos (undo image 진입) → heap_recdes_get_oos_oids(stub 에서 OID 추출) → oos_chunk_exists(관문 — 여기서 oid 와 반환 *out_exists 를 본다) → oos_delete_chain(W-latch 안의 실제 삭제, header.next_chunk_oid 확인). 블록 상태를 보려면 vacuum_finished_block_vacuum 과 vacuum_data_load_and_recover 에 걸고 blockid 의 상위 3비트를 읽는다.

결론: 릴리스 빌드에는 블록 수준 계측은 있지만 OOS 청크 수준 관측 채널이 없다. 그래서 이 결함은 운영에서 "vacuum 이 바쁘다"까지만 보이고 "남의 슬롯을 지웠다"는 보이지 않는다 — CBRD-26871 이 요구하는 도구의 공백이 정확히 이 지점이다.

5. 이 주제에 적용되지 않는 성능 항목 (근거 포함)

  • 메모리 사용 공식 — Not applicable: 이 Module 은 자체 메모리 구조를 소유하지 않는다. forward-walk 가 쓰는 것은 worker 의 기존 undo_data_buffer 와 함수-로컬 std::vector<OID>(undo 레코드 하나가 참조하는 head OID 개수 = OOS 컬럼 수만큼, 보통 1~2개)뿐이고, 페이지는 공용 버퍼 풀에서 fix/unfix 한다. 공식화할 상주 구조가 없다.
  • 확장 한계(scaling limit) — Not applicable (제안 설계에서는 존재): 현재 코드에는 이 경로가 소비하는 고정 크기 자원이 없다 — worker 수는 vacuum_worker_count 로, 블록 크기는 vacuum_log_block_pages 로 외부에서 정해진다. 반면 제안된 4B generation 은 페이지당 2³² 재할당이라는 명시적 한계를 도입하며, 그 한계가 왜 실무상 도달 불가인지는 ch16 에서 계산한다.
  • CPU/캐시 특성 — 이 경로의 비용은 페이지 fix I/O 가 지배하며(청크마다 fix/unfix), CPU·캐시 국소성은 측정 가치가 없다. 실측된 회수율의 요동(§1)이 버퍼 온도에 지배된다는 관측이 그 근거다.

6. 재현을 조율한 파라미터 (측정 주의사항 포함)

캡처된 실험 conf(raw/poc-work-r2/cubrid.conf)의 비기본 설정 전부: vacuum_worker_count=1(순서 단순화), vacuum_master_interval_in_msecs=10 (도장 처리 주기), vacuum_log_block_pages=128(블록 크기 = 재주행 단위), enable_string_compression=no(payload 크기 고정 — 압축되면 OOS 문턱 밑으로 내려간다), er_log_vacuum=4163(서버 로그의 vacuum 진단 줄을 켠다 — ch12·quiz-2 가 읽는 채널), data_buffer_size=256M·log_buffer_size=64M(회수율에 영향 — 관측된 요동의 일부), max_clients=20(6개 병렬 writer 수용), 그리고 createdb --db-page-size=16K (5,000B payload 가 단일 청크가 되게 하는 설정 — 멀티청크 피해를 이 실험이 다루지 못하는 이유). 전부 정식 파라미터이며, 안전장치를 끄는 종류가 아니라 발현 빈도를 높이거나 관측을 켜는 종류다. 측정 주의: 회수율은 버퍼 온도에 따라 한 자릿수 배로 요동하므로, 재현 스크립트는 고정 sleep 이 아니라 진행률 폴링으로 정지 시점을 잡는다.

요약

발현 빈도는 성능 변수들의 곱이고 전부 "좋은 성능" 쪽이 위험을 키운다. 관측 채널은 debug 전용인 데다 절반(insert)이 비어 있어, 운영에서는 발생도 진단도 보이지 않는다. 다음 장에서 이 모든 주장을 캡처된 실험으로 검증한다.
