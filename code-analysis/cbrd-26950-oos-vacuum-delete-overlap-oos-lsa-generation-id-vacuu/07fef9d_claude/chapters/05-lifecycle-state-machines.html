ch05 — vacuum 블록 상태 기계: 무엇이 영속되고, 왜 두 번 읽는가

학습 목표

  • 블록의 상태(AVAILABLE / IN_PROGRESS / VACUUMED + INTERRUPTED 플래그)와 전이 트리거를 말할 수 있다.
  • 정상 셧다운·크래시·완주-후-미표기 각각이 왜 같은 결과(재주행)로 수렴하는지 설명할 수 있다.
  • "레코드 단위 진행을 남기면 되잖아"가 왜 간단하지 않은지 답할 수 있다.

비유: 체크리스트 없는 재고 실사

창고 실사는 구역(zone) 단위로 배정된다. 실사원은 구역 안의 항목을 하나씩 처리하며 — 폐기 대상은 실제로 버린다 — 처리 결과는 그때그때 장부에 확정 기입한다(sysop 커밋). 그러나 "구역 완료" 도장은 구역을 끝까지 돌았을 때만 찍힌다. 도장 없는 구역은 다음 날 처음 항목부터 다시 돈다 — 어디까지 했는지 적는 칸이 배정표에 없기 때문이다. 이미 버린 것은 되돌아오지 않는다.

주의: 구역은 창고의 장소가 아니라 작업 일지(로그)의 페이지 범위다. 그리고 "칸을 추가하면 되잖아"는 아래 §왜 레코드 단위 진행이 없는가가 답한다.

블록 엔트리 — 4개 필드가 전부다

/* vacuum.c:106-131 — VACUUM_DATA_ENTRY 의 데이터 필드 */
VACUUM_LOG_BLOCKID blockid;        /* blockid + 상위 3비트의 상태 플래그 */
LOG_LSA start_lsa;                 /* 블록 내 마지막 MVCC op 로그 레코드의 LSA */
MVCCID oldest_visible_mvccid;
MVCCID newest_mvccid;

Source-confirmed — 상태는 blockid 상위 3비트에 인코딩된다: VACUUMED(0x8000…), IN_PROGRESS(0x4000…), AVAILABLE 은 리터럴 0, INTERRUPTED(0x2000…)는 상태가 아니라 직교 플래그다. 그래서 set_interrupted() 는 "AVAILABLE 로 되돌리고 + INTERRUPTED 플래그를 켠다" (vacuum.c:8358-8363) — INTERRUPTED 이면서 동시에 AVAILABLE(재배포 가능)인 것이 구조적으로 자연스럽다. 블록 내 위치(커서·오프셋·처리 수)를 담는 필드는 없다 (CUBRID-C010).

블록의 탄생 — 발행은 경계를 넘는 다음 로그가 한다

블록 요약은 로그 append 경로(prior_lsa_next_record_internal, log_append.cpp:1376-1386)가 "지금 append 하려는 레코드의 blockid ≠ 마지막 MVCC op 의 blockid" 일 때만 발행한다. 즉 다음 로그 레코드가 경계를 넘어야 직전 블록이 큐에 들어간다. 워크로드가 멈추면 마지막 블록은 영원히 대기한다 (CUBRID-C042) — 실험 setup 이 대형 필러 트래픽을 밀어 넣어야 했던 이유(ch12).

상태 기계 (V-5)

텍스트 대안: 블록은 AVAILABLE 로 등록되고, MVCCID 게이트(블록의 newest < 현재 oldest visible — vacuum.c:3260)를 통과하면 worker 에 디스패치되어 IN_PROGRESS 가 된다. 완주하면 finished-job 큐를 거쳐 master 가 VACUUMED 를 영속화한다. 완주 전에 중단되면 — worker 의 thread_p->shutdown 감지(:3493-3498), (release 빌드의) 블록 중간 에러, 또는 재기동 시 IN_PROGRESS 로 남은 엔트리의 재장전(:4400-4403) — 모두 AVAILABLE+INTERRUPTED 로 되돌아가고, 다음 디스패치 때 start_lsa 부터 통째로 재주행된다.

재주행의 세 관문 — 전부 소스로 확인

  1. 중단은 흔하다 — 정상 cubrid server stop 이 worker 루프의 thread_p->shutdown 검사(vacuum.c:3493-3498)에서 블록을 포기하게 만든다. 크래시가 필요 없다 (CUBRID-C011).
  2. 재주행은 전체 재주행이다 — start_lsa 는 블록 처리 중 결코 전진하지 않는다(쓰기 지점 전수 조사: 생성자·소비·복구 재구축뿐). 소스의 TODO 가 이를 자인한다: "Check that if start_lsa can be set to a different value when vacuum is not complete, to avoid processing the same log data again" (vacuum.c:3766-3767) (CUBRID-C010).
  3. 완주조차 안전하지 않다 — VACUUMED 도장은 worker 가 아니라 master 가 finished-job 큐를 비동기로 소비하며 찍는다 (vacuum_data_mark_finished, vacuum.c:4792-4869; RVVAC_DATA_FINISHED_BLOCKS :4946). 도장이 영속화되기 전에 셧다운되면 완료 블록도 IN_PROGRESS 로 남아 재기동 시 재주행된다. Runtime-observed — 이번 재현에서 pass 1 이 20,000 체인을 전부 회수하고 'is interrupted!' 경고 0건이었는데도 12,432건이 재삭제되었다 (CUBRID-C012).

따라서 "서버 로그에 interrupted 경고가 없으니 재처리도 없었다"는 추론은 틀린다. 그 경고는 master 가 종료 전에 큐를 소비한 경우에만 남고, 소비하지 못한 블록은 조용히 IN_PROGRESS → INTERRUPTED 재장전 경로를 탄다.

왜 레코드 단위 진행이 없는가

세 가지가 겹친다:

  1. 표현 문제 — worker 는 블록의 로그를 역방향으로 (prev_mvcc_op_log_lsa 링크를 따라) 걷는다(vacuum.c:3490). "여기까지 했다"를 단일 LSA 전진으로 표현할 수 없다.
  2. 원자성 문제 — 진행 기록이 삭제 sysop 과 한 원자 단위로 영속되지 않으면, 기록과 삭제 사이의 크래시에서 같은 창이 남는다. 그렇게 하려면 worker 의 레코드 단위 sysop 안에서 vacuum data 페이지까지 갱신해야 한다 — 진행 모델의 코어 수술이다.
  3. 설계 전제 — 이 상태 기계는 "재처리는 멱등하다"를 전제로 설계되었고, heap/btree 는 그 전제를 구조적으로 충족한다(ch09). OOS forward-walk 만 그 전제를 가정했다.

그래서 vacuum 쪽 수선(진행 영속화·블록 sysop·INTERRUPTED 스킵)은 전부 기각되었다 — 각각 코어 수술 / 창 축소일 뿐 / 영구 누수이기 때문(ch16 대안 검토).

요약

진행의 확정 단위(레코드별 sysop 커밋)와 진행의 기록 단위(블록)가 다르다. 그 간극에서 "이미 실행된 삭제 지시를 두 번째로 읽는 일"이 설계상 정상 동작으로 일어난다. 다음 장에서 그 두 번째 읽기가 실제 데이터 손실이 되는 정확한 워크플로를 의사코드로 따라간다.
