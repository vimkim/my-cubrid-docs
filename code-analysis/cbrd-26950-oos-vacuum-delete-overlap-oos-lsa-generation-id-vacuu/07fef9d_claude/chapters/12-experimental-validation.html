ch12 — 실험 검증: 정상 경로의 무해성과 결함의 재현

학습 목표

  • 두 실험의 가설·관찰·해석·대안 설명을 재구성할 수 있다.
  • 결정적 증거(채널 A)와 보강 증거(채널 B)의 강도 차이를 설명할 수 있다.
  • 재현 레시피의 각 레버가 어느 성립 조건을 만드는지 대응시킬 수 있다.

공통 조건: HEAD 07fef9d48, debug_gcc, 소스 무변경·fault injection 없음. 전 실행이 evidence/runs/<id>/ 에 argv·exit·stdout/stderr 로 캡처되어 있다. 필수 관측 실행은 캡처된 csql 바이너리가 해시된 SQL 러너를 직접 실행한다.

experiment-1 — 정상 forward-walk (negative control)

질문: 중단 없는 회수는 무해한가? 가설: 옛 체인만 회수되고 살아있는 값은 무손상. 절차: 전용 DB(oos26950exp1)에 5,000B 행 2,000개 INSERT(전부 OOS) → 단일 트랜잭션 전체 UPDATE → 대형 필러로 로그를 밀어 블록 발행(ch05 §발행) → oos.log 삭제 카운트 2,000 도달 대기 → csql 관측.

  • 관찰 (2회 반복 동일): 삭제 2,000건 기록, 문장 1 = 2000 (전 행 존재), 문장 2 = 0 (payload mismatch 없음), ERROR 문자열 없음.
  • 해석: 회수는 일어났고(negative result 아님) 손상은 없다 — 조건 ②(재사용)·③(재처리) 부재 시 forward-walk 는 건전하다 (CUBRID-C003).
  • 대안 설명 배제: "vacuum 미실행" — 삭제 2,000건이 반박. "비교식이 형식적" — payload 는 행마다 고유(id 각인)라 남의 값 반환도 잡힌다. "필러 오염" — 필러는 gen=0, 관측은 gen=1 만.
  • 기록: setup 실패 2회 보존 — PL 서버 일시 기동 실패(→ stored_procedure=no), 필러 과소로 블록 미발행(→ 5,000B 배치 필러). 둘 다 가설과 무관한 setup 결함.

experiment-2 — 결함 재현 (PoC)

질문: 세 조건이 겹치면 살아있는 커밋 데이터가 지워지는가? 가설: 커밋 후 무수정 행의 payload 가 판독 불가가 된다. 레시피와 조건의 대응 (V-15):

V-15. PoC 단계 ↔ 성립 조건 (CUBRID-C023)
단계내용성립시키는 조건
1R1 20,000행 INSERT (5,000B, 전부 OOS)회수 대상의 재료
2단일 트랜잭션 전체 UPDATE — 커밋 순간 옛 체인 20,000개가 일시에 회수 대상化백로그 (vacuum 이 커밋 전엔 못 건드림)
3동시에 6개 세션이 같은 크기 R3 INSERT — 비워지는 슬롯을 실시간 재사용② 슬롯 재사용 (재사용 창이 가장 넓은 곳은 삭제와 같은 서버 세션 안)
4회수 30% 시점 정상 cubrid server stop③ 블록 재처리 (도장 미영속 블록들)
5재기동 — vacuum 이 같은 블록들을 start_lsa 부터 재주행① 신원 없는 probe 가 재사용 슬롯을 통과시킴
  • 관찰 — setup 2회 (양쪽 캡처 exit 0 = 재현). 두 회차의 종료 형태가 다르고, 그 차이가 해석을 가른다:
    · rep 2 — 정상 셧다운 회차 (이 결함의 대표 시나리오): pass 1 이 20,000 중 7,969 체인만 회수해 백로그 12,031 이 남은 상태에서 중단(vacuum blocks abandoned mid-walk: 1), 서버 로그에 abort 없음. 커밋된 gen-3 1,815행 중 판독 불가 233, 재삭제 OID 233 — 두 채널이 정확히 1:1. 대조군 손상 0, 값 오염 0.
    · rep 1 — 비정상 종료(abort) 회차: pass 1 이 20,000 체인을 전부 회수 (abandoned mid-walk: 0)한 뒤, 종료가 클라이언트의 OOS INSERT 를 인터럽트해 oos_file_alloc_new 의 assert(false) 가 발화하며 서버가 abort 했다 (raw/poc-work/cubrid-start-initial.log 의 assertion 줄 + 같은 시간대의 core 파일; ch10 부수 발견 — CBRD-26950 과 별개 결함). 커밋된 gen-3 2,090행 중 판독 불가 528, 재삭제 OID 12,432, 대조군 손상 0, 값 오염 0. 이 회차의 '완주 후 전체 재주행'에는 abort 라는 경쟁 설명이 있으므로 도장 비동기 지연 단독의 실증으로 쓰지 않는다(아래 대안 설명).
  • 관찰 (필수 csql 관측 실행): 문장 1 = 1815(피해자 모집단), 문장 2 = 0·무오류(대조군 무손상), 문장 3 = 캡처된 stderr 의 ERROR: Internal error: slot 1 on page 8083 ... is not allocated. csql 기본 모드이므로 exit 는 0 이고 oracle 은 캡처된 출력 내용이다 — 결함이 수정되면 그 오류가 사라지는 것이 회귀 게이트다.
  • 해석: 피해 행들은 슬롯이 비워진 뒤 INSERT·COMMIT 되었고 이후 아무도 수정하지 않았다 — 커밋 후 이들을 만진 유일한 주체는 2차 vacuum pass 다. 대조군(재사용 슬롯에 있을 수 없는 체인들)의 무손상이 손상의 위치를 "재사용 슬롯"으로 정확히 국한시킨다 (CUBRID-C023). "크래시 불필요"의 런타임 근거는 rep 2 하나로 충분하다 — 정상 셧다운·백로그 잔존·abort 없음의 회차에서 233행이 손실됐다. rep 1 은 같은 결함의 abort 경유 발현이다.
  • 대안 설명 (rep 1 전용): rep 1 의 "블록 완주 후 전체 재주행"은 (a) VACUUMED 도장의 비동기 영속화 지연으로도, (b) abort 로 인해 master 가 finished-job 큐를 전혀 비우지 못한 것으로도 설명된다. 이 실행만으로는 둘을 분리할 수 없으므로, "완주한 블록도 재주행될 수 있다" (CUBRID-C012)의 정상 종료 판본은 소스 근거(master 의 비동기 표기 — vacuum.c:4854-4869, :4946, 재장전 :4400-4403)에 근거하고, 런타임으로는 미검증으로 남긴다.

Unknown (부분 해소) — 채널 A:B 관계는 실행 형태에 좌우된다. 정상 셧다운 회차인 rep 2 는 정확히 1:1(233:233) 이다 — 캡처된 이 한 회차로 1:1 관계가 성립한다(캡처 없는 2026-08-05 관측은 근거로 쓰지 않는다). rep 1 만 12,432:528 로 벌어졌는데, 그 실행은 pass 1 이 백로그를 완주한 뒤 debug assert 로 abort 하며 종료되어 블록 전체가 재주행된 경우다 — 초과분 다수가 살아있는 데이터가 아닌 대상이었다고 추정되지만, 원인이 도장 미영속인지 abort 로 인한 큐 미소비인지 분리되지 않고(위 대안 설명), oos.log 에 insert 기록이 없어(ch11) pass-2 시점 점유자를 사후 식별할 수도 없으므로 확정하지 못한다. 결론은 어느 쪽이든 같다: 채널 B 는 피해 규모의 척도가 아니고, 피해 판정은 채널 A 로만 한다 (CUBRID-C048). 해소 경로: 배치 insert 로그 추가(CBRD-26871) 후 재실행.

반복성과 통계

이 report 의 캡처된 재현: 2/2. experiment-1 은 2회(결과 동일), experiment-2 는 2회 모두 발현(정상 셧다운 회차 233행, abort 회차 528행) — 모두 evidence/runs/ 에 argv·exit·stdout/stderr 로 보존되어 있다.

캡처 없는 선행 관측(증거 기반에서 제외) — 같은 스크립트로 2026-08-05 에 3회(293/163/240행) 발현했다는 기록이 로컬 문서에 있으나, 그 실행들의 캡처(argv·exit·stdout)는 이 report 에 없다. 따라서 claim 의 증거 기반에서 제외하고 "참고 이력"으로만 적는다 — 재현율을 5/5 로 세지 않는다. 발현은 존재 명제(∃)이므로 2/2 로도 성립하며, 피해 규모가 실행마다 다른 것(이 run 233~528)은 타이밍 변수(ch11)의 함수다.

관찰자 효과와 한계

  • debug 빌드는 관측 채널(oos.log)에만 필요하다 — 발현 메커니즘(블록 상태 기계, probe, 슬롯 재사용)은 release 와 동일 코드다. 단, debug 의 assert 경계(ch10) 때문에 release 에는 있는 추가 트리거(블록 중간 에러)가 debug 에는 없다 — 즉 debug 재현은 오히려 보수적이다.
  • 비기본 설정은 conf 8종(vacuum 3종 + 압축 해제 + er_log_vacuum + 버퍼 2종 + max_clients) + createdb 의 16K 페이지 크기이며, 전부 발현 빈도를 높이거나 관측 채널을 켜는 것이고 안전장치를 끄지 않는다 — 전체 목록과 각각의 영향은 ch11 §6.
  • 실험이 증명하지 않는 것: 제2 호출부(REC_NEWHOME 경로)에서의 발현(CUBRID-C046 한계), 멀티청크 피해의 실측, 값-오염(무오류 오답)의 실제 발생.

요약

무중단이면 무해(2/2), 세 조건이 겹치면 발현(이 run 2/2 — 정상 셧다운 회차 233행, abort 회차 528행) — 인과의 양쪽이 캡처된 실행으로 고정되었다. 관측 스크립트는 회귀 게이트를 겸하는데, 판정 기준은 exit code 가 아니라 캡처된 stderr 에 slot … is not allocated 오류가 사라지는가다 (기본 모드 csql 은 결함이 있어도 exit 0 이다 — ch16 §9 참조). 이제 시선을 밖으로 돌린다: 같은 문제를 PostgreSQL 은 어떻게 원천 차단했는가.
