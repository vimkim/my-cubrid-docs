ch15 — 3-DB 교차 비교: 하나의 시나리오, 세 개의 답

학습 목표

  • 공유 시나리오를 세 시스템의 용어로 각각 서술할 수 있다.
  • 각 대응의 equivalent / partial analogy / no equivalent 판정과 그 이유를 말할 수 있다.
  • 이름이 비슷한 것(page LSA/LSN 게이트)과 책임이 같은 것을 구분할 수 있다.

2. 공유 시나리오의 세 흐름

시나리오: "행 UPDATE 로 대체된 큰 out-of-row 값의 지연 회수 — 회수자가 중단 후 재시도할 때, 그 사이 물리 위치가 재사용되었다면 무엇이 이중 회수를 막는가?"

  1. CUBRID: UPDATE 가 새 체인 생성 → 옛 체인 참조는 undo image 에만 → vacuum forward-walk 가 물리 OID 로 삭제 → 재시도 시 같은 OID 재제시, probe 는 점유 여부만 — 막는 것이 없다 (결함) (CUBRID-C023).
  2. PostgreSQL: UPDATE 트랜잭션이 old TOAST 행들을 그 자리에서 MVCC delete → 회수는 VACUUM 이 점유자 header 재평가 — 재시도가 재평가라서 질문이 소멸; 참조는 논리 이름이라 재사용 앨리어싱 자체가 불가 (PG-C001, PG-C002, PG-C003).
  3. InnoDB: UPDATE 가 옛 LOB 에 (trx_id, undo_no) 스탬프 기록 → purge 가 undo 레코드의 물리 참조로 forward, 스탬프 등가일 때만 해제 + 소비한 참조에 FIL_NULL self-mark (MYSQL-C002, MYSQL-C004).

비슷한 이름에 속지 말 것: 세 시스템 모두 가진 page LSA/LSN 게이트는 셋 다 replay 전용이며 이 시나리오의 방어가 아니다. 반대로 이름이 전혀 다른 InnoDB 의 (last_trx_id, last_undo_no) 와 CUBRID 제안의 generation 이 같은 책임을 진다 — 비교는 이름이 아니라 책임의 흐름으로 한다.

5. 종합: 설계 공간의 세 좌표

세 시스템은 "stale 물리 참조" 문제의 설계 공간에서 서로 다른 꼭짓점이다:

  • 참조를 논리화한다 (PG TOAST) — 근본적이지만 모든 읽기에 조회 비용, 이름 발급기 필요. CUBRID 가 지금 가기엔 온디스크·읽기 경로 전면 개편.
  • 재평가 가능하게 만든다 (PG/CUBRID heap) — 대상이 자기 증언 데이터를 지녀야 함. OOS 청크에 죽음 정보를 넣는 것은 지연 정리 설계와 충돌(DELETE 가 OOS 페이지를 만져야 하게 됨).
  • 참조에 신원을 태운다 (InnoDB, CUBRID 제안) — 최소 침습. 등가 비교 한 줄이 방어의 전부.

CUBRID 의 제약(WAL 불변 → self-mark 불가, 회수 단위 = 슬롯 → 객체 스탬프 불가)을 대입하면 세 번째 좌표의 컨테이너-카운터 변형만 남는다 — ch16 의 결론이 여기서 이미 그려진다.

요약

같은 시나리오에 PG 는 "질문을 없애는 설계", InnoDB 는 "질문에 답하는 데이터", CUBRID(현재)는 "질문을 하지 않는 코드"다. 다음 장에서 CUBRID 가 InnoDB 좌표로 이동하는 구체적 설계 — 스탬프 후보 판정과 dedup 확장 — 를 완성한다.
