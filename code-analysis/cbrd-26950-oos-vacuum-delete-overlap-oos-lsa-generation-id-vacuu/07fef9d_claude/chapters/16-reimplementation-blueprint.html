ch16 — 재구현 Blueprint: 신원 스탬프와 dedup 설계

지위 안내 — 이 장의 §1(요건)과 §2~§5(후보 판정)의 전제들은 source-confirmed 지만, 설계안 자체는 미구현이다. 채택 방향(generation)은 로컬 설계 문서와 2026-08-07 회의 결과의 Documented 사항이고 (CUBRID-C034), 판정 논증은 Inferred (전제·반증 조건 명시)다. 여기서부터는 비유를 내려놓는다 — 정확성 논증에 비유가 끼면 판정이 뭉개진다.

0. 문제의 재정식화

forward-walk 의 삭제 대상(옛 OOS value chain)은 live 레코드가 참조하지 않고 undo image 에만 남는다. "이 청크가 쓰레기인가"는 청크 자신의 속성이 아니라 소유 heap 버전의 죽음이라는 외재적 사실이고, 그 버전은 페이지에서 이미 사라졌다. 따라서 재처리 시 필요한 것은 쓰레기 여부의 재유도가 아니라 신원 확인 — "지금 슬롯 점유자가 undo image 가 가리키던 그 체인인가". heap 과의 비대칭(ch09): heap 헤더의 delid 는 죽음 정보라 점유자-내재 기준이 되지만, OOS 청크에는 출생 정보조차 없고, 죽음 정보를 넣으려면 DELETE/UPDATE 가 OOS 페이지를 만져야 해 지연 정리 설계와 충돌한다. 모든 후보는 이 비대칭의 우회이며, 판정은 "무엇을 스탬프로 삼아 등가 비교하느냐"로 수렴한다.

2. 탈락 후보들 — 각각 정확히 하나의 요건에서 죽는다

6a. 청크에 생성 MVCCID 저장, undo image 의 MVCC 헤더와 비교 — R1 위반

Source-confirmed 전제 — vacuum 의 정상 작업 중 하나가 오래 닫힌 레코드의 on-page 헤더에서 insert MVCCID 를 물리적으로 제거하는 것이다(insid 정리 — REC_HOME/REC_NEWHOME arm 에서 플래그와 값을 지우고 본문을 당겨 붙임, vacuum.c:2282-2291/2378-2387). 이후 그 행이 UPDATE 되면 undo image 는 정리된 헤더를 그대로 캡처한다 — 비교할 기대값 자체가 없다. 값을 남기는 MVCCID_ALL_VISIBLE 치환은 REC_BIGONE 전용이고 OOS+bigone 은 쓰기 시점 거부라 무관 (CUBRID-C030). 기대값 소실 시 skip 은 R3, 강행은 R2 위반 — 방어가 "UPDATE 전에 insid 정리가 먼저 왔는가"라는 vacuum 타이밍에 좌우되는 비결정적 방어가 된다.

(정정 이력: "같은 트랜잭션 다중 UPDATE 시 스탬프 충돌"이라는 초기 기각 사유는 철회되었다 — 닫힌-블록 게이팅과 MVCCID 단조성 때문에 현행 구현에서 성립하지 않는다. 6a 의 사인은 오직 R1 이다.)

A/B. 임계값(threshold) 비교 계열 — 등가가 아닌 부등호의 구조적 실패

Inferred (CUBRID-C033) — 점유자의 생성 MVCCID 를 임계값과 부등호 비교하는 두 변형:

  • A: 현재 oldest visible 과 비교 ("충분히 오래됐으면 삭제") — R2 위반. 재시작 후에는 pre-crash 트랜잭션이 전부 닫혀 임계값이 재시작 이전의 모든 MVCCID 보다 커진다 → 검사가 "항상 삭제"로 퇴화 → 대표 트리거(재시작 경유 재시도)에서 보호가 정확히 0. 근본 원인: 임계값은 점유자의 나이만 보지 정체를 모른다 — 수년 전 INSERT 되고 한 번도 안 바뀐 살아있는 체인도 "오래됨"을 만족한다.
  • B: 블록에 동결된 oldest_visible 과 비교 — 방향을 뒤집으면 오탐은 막힌다(재사용자는 항상 블록 동결값 이후). 대신 R3 위반: MVCCID 는 첫 write 시점 발급이라 발급 순서 ≠ 커밋 순서다(CUBRID-C031). 반례(V-9): 장기 배치 writer W 가 MVCCID 100 을 쥐고 실행 중 → T1(MVCCID 200)이 OOS 행 INSERT·커밋 → W 가 그 행을 UPDATE(READ COMMITTED 에서 정상). 이 undo 가 든 블록의 동결값 ≤ 100 인데 삭제 대상 체인의 생성자는 200 → 영구 skip. W 가 사는 동안 채워진 모든 블록이 걸리는 시스템적 누수.

텍스트 대안: 배치 트랜잭션 W 는 첫 쓰기에서 MVCCID 100 을 받고 오래 실행된다. 그동안 T1 이 MVCCID 200 으로 OOS 행을 INSERT·커밋하고, 이어 W 가 그 행을 UPDATE 한다. 커밋 순서는 T1 → W 이지만 MVCCID 순서는 W(100) → T1(200) 이므로, 블록 동결 임계값(≤100)과 삭제 대상 생성자 (200)의 부등호 비교는 정당한 대상을 영구히 건너뛴다. 반대 방향 변형(A)은 재시작 후 모든 것을 통과시킨다. 등가 비교만이 두 모집단을 정확히 가른다.

owner OID — 차선. 쓰는 순간 신원이 아직 없다

Source-confirmed 전제 — 청크는 heap_attrinfo_insert_to_oos(heap_file.c:13150)에서 쓰이는데, 이 시점은 heap 슬롯 확정(heap_insert_logical → :21626-21680) 이전이다. 이 체인들을 소유할 새 버전의 OID 는 아직 존재하지 않는다 (CUBRID-C032). 채우려면 heap insert 후 청크 헤더 backfill(핫패스에 페이지 fix+WAL 영구 추가) 또는 OID 할당 순서 재배치(침습) — 방향은 옳지만 비용 구조가 나쁘다.

3. 성립하는 차선 — 6b: stub 탑재 MVCCID

oos_insert 시 생성 트랜잭션의 MVCCID 를 청크 헤더와 stub 양쪽에 기록하고, forward-walk 가 undo image 속 stub 의 기대값과 청크의 저장값을 등가 비교한다.

  • R1 충족 — insid 정리는 MVCC 헤더만 다듬고 variable area(stub)는 건드리지 않으므로 기대값이 소실되지 않는다(6a 의 사인 해소).
  • R2 충족(현행 구현 기준) — vacuum 은 닫힌 블록만 처리하고(vacuum.c:3260), MVCCID 는 복구를 포함해 단조·비재사용이므로(CUBRID-C031) walk 가 비운 슬롯의 재사용자는 항상 생성자보다 큰 MVCCID 를 갖는다. 생성자 활동 중의 해제 경로(롤백 보상, eager)는 walk 대상 참조를 남기지 않는다.
  • R3 충족 — 같은 체인이면 같은 시점에 같은 값이 양쪽에 기록.
  • R4 열세 — 8B: stub 16→24B, 청크 헤더 16→24B (generation 은 20B/20B). 4B 로 절단하면 "의미가 붙은 4B 카운터"가 될 뿐 — 그럴 바엔 처음부터 카운터가 낫다.
  • R5 열세 — R2 논증이 vacuum 게이팅 + MVCCID 단조성 + 롤백 보상 의미론 + eager 가드 + M1 항상-새-체인이라는 4개 서브시스템 횡단 불변식 8줄에 의존한다. 미래에 "생성자 활동 중 해제 + walk 가능 참조"를 만드는 변경(예: 자기-트랜잭션 중간 버전 즉시 회수)이 들어오면 조용히 깨진다.

4. 권고 — 4B generation (페이지 카운터 발급, 등가 비교)

Documented (채택 방향) + Source-confirmed (기반 사실) — 설계: OOS 페이지 헤더에 uint32 카운터를 두고, 청크 insert(슬롯 재할당)마다 증가시켜 그 값을 청크 헤더(+4B)와 stub(+4B)에 기록한다. 삭제 전 등가 비교 — 불일치면 재사용된 슬롯이므로 no-op (CUBRID-C034).

구현 기반 사실 (source-confirmed)

  • 쓰기 지점 페이지는 이미 W-latch — 카운터 증가에 추가 래치 없음. 단, 청크 헤더는 슬롯 확정 전에 직렬화되므로(:1503→:1516) 카운터를 미리 읽거나 사후 패치해야 한다 — 설계서가 명시해야 할 순서 결정 (CUBRID-C032).
  • RVOOS 물리 로깅은 전체 이미지라 복구 핸들러 불변. replication 은 slave 가 자체 oos_insert 를 수행하므로 generation 도 slave 로컬 발급 — 규칙 명문화만 필요.
  • uint32 폭: 오탐에는 한 블록 재처리 창 안에 같은 페이지 2³² 회 재할당 사이클이 필요 — 물리적으로 불가. stub 은 패딩 없이 20B(정렬 이득 없음, PG 18B 선례). 미래 예약은 행마다 반복되는 stub 이 아니라 체인당 1회인 청크 헤더에.
  • 연쇄 갱신: OR_OOS_INLINE_SIZE 16→20, demotion 수익성 문턱(>20B), 경계 테스트, OOS-CONTEXT 문서. 온디스크 포맷 변경은 feat/oos 미출시인 지금이 마이그레이션 비용 0 인 유일한 시점.

5. "OOS LSA" — 회의 어휘의 정직한 분석

Unknown (정의) + Source-confirmed (기반 사실) — "OOS LSA" 는 2026-08-07 회의 어휘로 로컬 문서에 정의가 없다 (CUBRID-C035). 가장 그럴듯한 해석 — 체인 생성 연산의 로그 LSA 를 청크 헤더와 stub 에 신원 스탬프로 저장, 등가 비교 — 로 분석한다:

  • 물리적으로 가능하다 — insert 의 LSA 는 append 직후 tdes->tail_lsa 로 관측 가능하다(멀티청크 replication 경로가 이미 이 값을 읽는다, oos_file.cpp:1440, 1476-1479) (CUBRID-C032).
  • 그러나 순서 문제가 있다 — LSA 는 로그 append 후에야 존재하는데, 청크 바이트(헤더 포함)는 append 되는 redo 이미지 안에 있다. 자기 LSA 를 자기 이미지에 넣을 수 없으므로: 두 번째 페이지 쓰기+로그, 또는 로깅 순서 재설계가 필요 — generation 에는 없는 비용.
  • 폭 8B — stub 24B. 등가 비교에는 유일성만 필요하므로 전역 유일·순서성은 잉여다.
  • 페이지 LSA 해석은 소스로 반박된다 — 페이지 LSA 는 페이지의 모든 수정이 공유·덮어쓰므로 청크 신원이 될 수 없다. redo 게이트 해석은 범주 오류다(ch08/ch13 — replay 전용).
  • 정직한 결론: "LSA 를 등가 스탬프로 쓴다" = "LSN 이기도 한 세대 카운터" — 성립하되 generation 대비 이점(카운터 필드 불필요, 진단성) 이 비용(8B, 쓰기 순서 재설계)을 상쇄하지 못한다. 회의의 실제 의도 확인이 선행 과제다.

6. InnoDB 선례와의 정합

권고안은 InnoDB 의 (last_trx_id, last_undo_no) 등가 비교와 목적·형태가 같다 (MYSQL-C004, CMP-C004). 위치가 다른 이유는 회수 단위(페이지 vs 슬롯, ch14 §5) — InnoDB 는 대상 객체에, CUBRID 는 컨테이너 카운터에서 발급해 점유물·참조 양쪽에 싣는다. InnoDB 가 잔여 경쟁에서 누수를 선택했다는 사실은 "불일치 = skip(no-op)" 정책의 선례이기도 하다 — 단, generation 의 skip 은 누수조차 아니다: 불일치 슬롯은 이미 남의 것이고, 정당한 대상은 항상 일치한다(R3).

7. dedup 확장 — 수명 문제와 OOS update log

미래 dedup(무변경 OOS 값의 체인 재사용)은 M1 의 "버전당 새 체인"을 깨고 한 체인을 여러 버전이 공유하게 만든다. 이때 새 문제는 신원("점유자가 그 체인인가")이 아니라 수명("아직 누가 참조하는가")이다 — 신원 스탬프는 dedup 과 무관하게 계속 필요하고, dedup 은 별도 보호 장치를 추가로 요구한다.

dedup 보호 장치 4종 (CUBRID-C036)
장치방식성립성

OOS update log 의 정확한 위치 (V-13)

Inferred (CUBRID-C036) — 이 방식의 본질: 옛 체인 참조가 사는 곳을 "heap UPDATE 의 undo image"에서 "전용 OOS update log 레코드"로 옮기고, 소비 시점을 그 레코드의 vacuum 시점으로 정의한다. 장점 — 무변경 값의 회수 책임이 명시적 레코드로 분리되어, dedup 시 "공유 체인의 마지막 참조자" 판정을 로그 구조로 표현할 여지가 생기고, 핫패스(무변경 UPDATE)에 스탬프 bump 쓰기조차 없다. 그러나 성립 요건 네 가지가 남는다:

  1. 원자성 — 레코드는 heap 변경과 같은 원자 단위 안에서 로깅되어야 한다. 사이에서 크래시하면: 로그만 유실 → aaa 영구 누수 / 로그만 생존(heap 롤백) → 살아있는 aaa 회수.
  2. 게이팅 — 소비는 지금의 NOTIFY 경로와 동일한 MVCCID 게이팅을 받아야 한다 (스냅샷 독자가 aaa 를 아직 볼 수 있는 동안 회수 금지).
  3. replication — 물리 OID 는 slave 에서 무의미하므로(slave 는 자체 oos_insert) 레코드는 값-논리적이거나 slave 로컬 재생성이어야 한다.
  4. 신원은 그대로 필요하다 — 이것이 핵심이다. 블록 재처리는 update log 레코드도 똑같이 두 번 읽고 같은 물리 aaa 를 재유도한다. 레코드(또는 청크)가 신원을 나르지 않으면 같은 이중 삭제가 그대로 남는다. update log 는 참조의 거처를 바꾸는 수명 메커니즘이지, 소비의 검증을 바꾸는 신원 메커니즘이 아니다. dedup 완성형은 "update log (수명) + 스탬프(신원)"의 합이다.

반증 조건(명시): update log 소비를 블록 재처리와 무관한 별도의 exactly-once 큐로 설계하면 신원 요건은 그 큐의 정확성으로 이전된다 — 그 큐가 다시 "정확히 한 번 소비" 문제를 풀어야 하므로 문제가 이동할 뿐 소멸하지 않는다는 것이 현재 판단이다(InnoDB 의 self-mark 가 그 큐의 한 구현인데, CUBRID WAL 불변성이 막는다 — ch14).

스냅샷 안전성 보강: "마지막 참조자의 death 블록에서 삭제" 프로토콜은 커밋 순서 전이성으로 안전이 증명된다 — 공유 체인 C 의 마지막 참조 버전을 지운 블록이 디스패치되려면 그 이전 모든 버전의 독자 스냅샷도 이미 배제되어 있다(M1 게이팅 원리의 자연 확장).

8. 기각된 대안 경로 (요약)

  • 수정 불필요론 — OOS OID 는 물리 주소라 "재발급 지연"이 없다: 재점유가 곧 재등장이고, 정책 세 겹이 재점유를 촉진한다(ch09).
  • INTERRUPTED 블록의 forward-walk 스킵 — INTERRUPTED 는 "얼마나 했는지"를 모른다. 스킵 = 옛 체인 영구 누수(회수 유일 경로).
  • 레코드 단위 진행 영속화 — 역방향 링크 순회라 단일 LSA 로 표현 불가 + 진행 기록과 삭제의 원자성 문제 = vacuum 코어 수술(ch05).
  • 블록 전체 단일 sysop — VACUUMED 표기가 비동기라 창이 닫히지 않고, 커밋 전 빈 슬롯 노출(bestspace)과 abort 복원 충돌 창이 블록 길이로 확대(ch08).
  • forward-walk 폐지(tombstone/영속 큐/스캔 GC) — undo image 는 이미 영속적이고 MVCCID 게이팅되며 추가 쓰기 0 인 완벽한 삭제 대기 큐다. 대체물들은 그 큐를 재발명하며 "정확히 한 번 소비"를 그대로 계승한다. 고장난 것은 큐가 아니라 소비 단계의 신원 확인 하나다.
  • 슬롯 재사용 유예 — "블록 완료까지" 라는 조건 자체가 새 추적 문제 + 회수율 저하. 스탬프 대비 이점 없음.

구현 순서와 적합성 테스트

  1. 온디스크: 헤더·stub 확장 + 상수(OR_OOS_INLINE_SIZE 등) + reader/writer (경계 테스트: 20B 정확성).
  2. 발급: 페이지 카운터 + insert 경로 배선 (테스트: 재할당마다 증가 — R2 국소 불변식의 직접 검증).
  3. 검사: oos_delete 시그니처 확장 + forward-walk 배선 (테스트: 불일치 no-op).
  4. 적합성 오라클 — exit code 가 아니라 캡처된 출력 내용이 판정 기준이다 (csql 기본 모드는 문장 오류와 무관하게 exit 0 이므로 결함이 있는 빌드에서도 exit 0 이 나온다): ① experiment-2 관측의 stderr 에 Internal error: slot … is not allocated 가 없고 victim 문장이 mismatch 0 을 반환하는가(수정 확인) + ② experiment-1 이 여전히 통과하는가(누수 없음 — 정당한 대상은 스탬프가 일치해 정상 회수) + ③ REC_NEWHOME 경로 변형 테스트(C046). exit-code 게이트를 원하면 관측을 --no-single-line --error-continue 로 실행해야 한다 (그 조합에서는 결함 present = exit 1, 수정 후 = exit 0 — 이 run 의 experiment-2-observe-r1b 가 전자의 캡처다).
  5. dedup 은 별도 마일스톤: update log(수명) 설계 확정 후 (i) 또는 (ii)와 스탬프의 합성.

요약

등가 비교만이 두 모집단(재사용자/정당한 대상)을 가르고, 등가 스탬프 중 generation 이 비용·검증 반경에서 우위다 — InnoDB 가 같은 형태의 답을 이미 운영한다. "OOS LSA" 는 해석상 성립하되 이점이 비용을 못 넘고, OOS update log 는 dedup 의 수명 문제를 풀지만 신원 문제는 스탬프에 남긴다. 남은 것: 증거의 전체 색인과 unknown 목록(ch17).
