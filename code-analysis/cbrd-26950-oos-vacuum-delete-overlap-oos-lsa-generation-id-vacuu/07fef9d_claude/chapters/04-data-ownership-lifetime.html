ch04 — 데이터 소유권과 수명: 체인, stub, undo image

학습 목표

  • 세 저장소(heap 페이지 / 로그 / OOS 파일)에 흩어진 상태와 각각의 수명을 그릴 수 있다.
  • UPDATE 전후의 참조 그래프 변화 — "유일한 참조" 개념 — 를 설명할 수 있다.
  • 스탬프 후보가 물리적으로 놓일 수 있는 자리들을 열거할 수 있다.

핵심 구조와 바이트 배치 (V-3, V-4)

텍스트 대안: OOS inline stub 은 16바이트 — 앞 8바이트가 head OOS OID(volid 2B + pageid 4B + slotid 2B), 뒤 8바이트가 full length. OOS chunk record 는 16바이트 헤더(total_data_length 4B, chunk_index 4B, next_chunk_oid 8B)와 payload 로 구성되어 next_chunk_oid 로 체인을 이룬다. 헤더에는 이 청크가 누구의 것인지 나타내는 필드가 없다. 어느 가변 컬럼이 stub 인지는 VOT(Variable Offset Table) 엔트리의 IS_OOS 비트가, 레코드에 stub 이 하나라도 있는지는 MVCC 헤더의 HAS_OOS 플래그가 표시한다.

소유권 불변식: 한 OOS value chain 은 정확히 하나의 논리 heap-record 버전이 소유한다. UPDATE 는 항상 새 체인을 만들므로(M1) 옛 체인과 새 체인의 head OID 는 서로소다 — forward-walk 는 이 서로소성에 암묵적으로 기대고 있다. 미래 dedup 이 이 불변식을 깨는 순간 새 보호 장치가 필요해진다(ch16).

UPDATE 전후의 참조 그래프 (V-2)

텍스트 대안: UPDATE 후 살아있는 heap 레코드의 stub 은 새 체인을 가리키고, 옛 체인을 가리키는 유일한 참조는 로그 속 undo image 의 옛 stub 하나뿐이다. 스냅샷 독자는 prev_version_lsa 를 따라 undo image 에서 옛 버전을 재구성하며, 그때 옛 stub 의 head OOS OID 로 옛 체인을 읽는다. 이것이 옛 체인을 UPDATE 시점에 지울 수 없는 이유이자, vacuum 이 undo image 를 읽어 지워야 하는 이유다.

수명 불일치 — 결함의 시간 구조

참조(undo image 속 옛 stub)의 수명과 참조 대상(옛 체인이 살던 슬롯)의 의미 수명이 어긋난다:

  1. forward-walk 1차 pass 가 옛 체인을 지운다 — 슬롯의 의미는 "빈 칸"이 된다.
  2. 다른 행의 insert 가 슬롯을 재사용한다 — 슬롯의 의미는 "남의 체인"이 된다.
  3. 그러나 undo image 는 불변이라, 블록 재처리는 1 단계 이전의 세계관(그 슬롯 = 내 옛 체인)을 그대로 다시 들고 온다.

C 프로그래머의 언어로 정확히 use-after-free + 재할당 = ABA 문제다. free 된 포인터(옛 OID)를 dangling 상태로 보관하다가, 같은 주소가 재할당된 뒤 역참조-후-해제하는 것. CS 에서 이 문제의 표준 해법이 태그드 포인터/세대 카운터라는 사실이 ch16 의 예고편이다.

요약

상태는 세 저장소에 흩어져 있고, 그중 로그만 불변이다. 옛 체인의 유일한 참조가 불변 저장소에 살기 때문에, 슬롯의 의미가 바뀌어도 참조는 낡은 세계관을 유지한다 — ABA 문제의 데이터베이스판. 다음 장에서 "누가, 언제, 왜 같은 undo image 를 두 번 읽는가"(블록 상태 기계)를 본다.
