CBRD-26950 — vacuum 이 재사용된 OOS 슬롯의 살아있는 데이터를 지우는 이유

CUBRID vacuum 의 OOS(Out-of-row Overflow Storage) 지연 회수 경로에서 일어나는 이중 삭제 데이터 손실 결함과, 그것을 막는 신원 스탬프 설계(4B generation / OOS LSA / MVCCID), 그리고 미래 dedup 의 OOS update log 방향을 소스와 런타임 재현으로 재구성한 책.

핵심 결론 (TL;DR)

  1. 결함은 세 정상 동작의 곱이다 — 신원 없는 점유-probe(CUBRID-C002) × 설계가 유도하는 즉시 슬롯 재사용(CUBRID-C020, C045) × 블록 단위 재처리(CUBRID-C010, C011, C012). 크래시 없이 정상 cubrid server stop 만으로 재현된다 — 이번 run 에서 528개의 커밋된 행이 오류·경고 없이 데이터를 잃었다(CUBRID-C023).
  2. 기존 보호 장치는 전부 다른 질문에 답한다 — page LSA 는 replay 중복만, sysop 은 호출 원자성만, 래치는 현재 접근만, MVCCID 게이팅은 옛 버전의 죽음만 보증한다(CUBRID-C022).
  3. 수정의 최소 계약: probe 의 질문을 "슬롯이 점유돼 있는가"에서 "점유자가 여전히 undo image 가 소유하던 그 체인인가"로 바꾸는 것 — 즉 신원 스탬프. 설계 판정은 4B generation 권고(CUBRID-C034), stub 탑재 MVCCID(6b) 차선, threshold 계열 탈락(CUBRID-C033), "OOS LSA"는 회의 어휘로 정의 미문서화(CUBRID-C035).
  4. InnoDB 가 동형의 선례다 — UPDATE 가 옛 LOB 에 (trx_id, undo_no) 스탬프를 쓰고 purge 가 등가 비교한다(MYSQL-C004, CMP-C004). PostgreSQL 은 논리 신원(chunk_id)으로 질문 자체를 제거한다(PG-C003).
  5. 미래 dedup 의 OOS update log 는 수명 메커니즘이지 신원 메커니즘이 아니다 — 참조가 사는 곳을 옮길 뿐, 소비 시점의 신원 확인(스탬프)을 대체하지 못한다(CUBRID-C036).
