# quiz-5 답안 — 강한 답안이 도달해야 하는 다섯 지점

## 1. heap update 와의 원자성

레코드는 heap UPDATE 를 만드는 것과 **같은 원자 단위**(그 heap 연산의 로그 시퀀스 / 동일
sysop 계열) 안에서 로깅되어야 한다. 사이에서 크래시하면: (a) heap 변경만 영속 →
`aaa → bbb` 기록 유실 → aaa 를 지울 주체가 영원히 없음(영구 누수 — dedup 에서는 undo image
경로도 aaa 를 안 지우기로 했으므로 대체 회수자가 없다). (b) 레코드만 영속·heap 롤백 →
살아있는 aaa 회수(즉시 데이터 손실). 두 방향 모두 실패가 조용하므로 원자성은 협상 불가.

## 2. MVCCID 게이팅

소비는 "aaa 를 참조하던 마지막 버전을 볼 수 있는 스냅샷이 소멸한 뒤"로 게이트되어야 한다 —
기존 NOTIFY_VACUUM 블록 게이트와 동일한 형태(레코드가 속한 블록의 newest MVCCID <
oldest visible). 커밋 순서 전이성 논증(ch16 §7 말미)이 "마지막 참조자 블록 게이트가 앞선
모든 버전의 독자까지 배제함"을 보장한다.

## 3. 신원 문제는 그대로 남는다 — 이 퀴즈의 핵심

블록 재처리는 update log 레코드도 두 번 읽는다. 1차 소비가 aaa 를 지우고 슬롯이 재사용된 뒤
2차 소비가 오면 — 레코드가 나르는 것이 물리 OID 뿐이라면 **정확히 CBRD-26950 이 재현된다**.
update log 는 참조가 사는 곳(undo image → 전용 레코드)을 바꾸는 **수명** 메커니즘이지,
소비 시점의 **신원** 확인을 대체하지 않는다. 따라서 레코드는 (aaa 의 OID, aaa 의 기대
generation) 쌍을 날라야 하고, 소비는 등가 비교를 거쳐야 한다. dedup 완성형 =
update log(수명) + 스탬프(신원). InnoDB 식 "소비하면서 레코드에 FIL_NULL 도장"은 CUBRID
WAL 불변성 때문에 불가하다는 점까지 언급하면 만점(ch14, `CMP-C002`).

## 4. 다중 참조(공유 체인)의 마지막 참조자 판정

무변경 재사용이 이어지면 aaa 는 여러 버전이 공유한다. "이 레코드가 vacuum 될 때 aaa 회수"
규칙은 aaa 의 **마지막** 참조가 끊긴 UPDATE 의 레코드에만 성립한다. 판정 장치 택일:
(i) 재참조 시 generation bump — 중간 버전 레코드의 기대값이 불일치해 자연 skip (국소적,
ch16 권고와 합성 시 자연스러움), (ii) 레코드에 "post-image 도 aaa 참조" 플래그(old∩new
검사의 로그화 — 쓰는 쪽이 판정을 미리 함), (iii) refcount (선형 참조에는 과잉). 어느 것을
고르든 비용을 명시해야 한다.

## 5. replication

물리 OID 는 slave 에서 무의미하다(slave 는 자체 oos_insert, `CUBRID-C034` 연쇄 규칙과 동일).
레코드는 slave 로 건너갈 때 값-논리적이어야 하거나(예: "이 heap 레코드의 몇 번째 OOS 컬럼"),
slave 가 자기 물리 OID/generation 으로 재작성해야 한다. master 의 (OID, gen)을 그대로
실어 보내는 설계는 replication 에서 즉시 깨진다.

## 심화 답

- **D1.** head OID(+기대 gen)만으로 충분하되, **검증을 통과한 head 에서만** 체인 링크를
  신뢰한다는 규칙이 함께 가야 한다. 체인 전체를 레코드에 담으면 레코드가 비대해지고
  (멀티청크 체인 = OID 목록), head 검증 후 링크 추적과 안전성이 같다 — 단 "head 는 일치하는데
  중간 청크가 재사용된" 경우가 없음은 체인 단위 원자 해제(sysop)가 보장한다.
- **D2.** 위 5 참조.
- **D3.** undo image 는 M1 세계의 완벽한 삭제 대기 큐였다(영속·게이팅·추가 쓰기 0).
  dedup 은 그 큐의 **의미**("undo 의 stub = 죽은 참조")를 깨뜨리므로 update log 라는 새 큐가
  필요해진 것이다 — 그러나 어느 큐든 소비 단계의 신원 확인은 별도 문제로 남는다. 진단은
  그대로 유효하다: 큐를 바꾸는 것과 소비를 검증하는 것은 직교한다.

## 이 과제가 증명하지 않는 것

update log 설계는 회의 방향 수준의 **미구현·미상세** 안이다(`CUBRID-C036` — inference).
이 답안은 성립 요건의 열거이지 구현 검증이 아니며, 요건 중 하나(별도 exactly-once 큐로의
회피 가능성)는 반증 조건으로 열려 있다(ch16 §7).
