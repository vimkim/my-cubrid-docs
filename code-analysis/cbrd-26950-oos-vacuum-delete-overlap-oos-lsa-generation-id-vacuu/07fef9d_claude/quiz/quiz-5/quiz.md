# quiz-5 — 설계 과제: OOS update log 를 명세하라

- **학습 목표**: 2026-08-07 회의 방향인 **OOS update log** 를 스스로 명세하면서, 그 방식이
  풀어주는 문제(수명)와 풀어주지 못하는 문제(신원)를 구분하는 데 도달한다.
- **선수 지식**: quiz-4 완료, ch08(내구성), ch16(blueprint).
- **예상 시간**: 30–40분 (지필 설계).
- **연결**: 중심 행동 `identity-stamp-and-dedup-design` · claim `CUBRID-C036` · 챕터 ch16 §7.

## 배경

미래 dedup: heap record UPDATE 에서 OOS 값이 안 바뀌면 **OOS insert 를 생략**하고 기존 체인을
새 버전 stub 이 재사용한다(M1 의 "버전당 새 체인" 붕괴). 회의 방향: 변경되지 않으면 generation
조차 갱신하지 않고, **변경된 OOS 값에 한해** heap record update 로그를 남기듯
`OOS aaa → bbb` 이동 로그를 남긴다. 이 로그 레코드가 vacuum 될 때 aaa 를 정리한다.

## 과제 — 다음 네 가지를 명세하라

1. **레코드 정의**: `OOS aaa → bbb` 로그 레코드의 필드 목록과, 어떤 원자 단위(트랜잭션/sysop)
   안에서 어느 시점에 기록되는가. heap update 와 이 레코드 사이에서 크래시가 나면 각각 어떻게
   되는지 두 방향 모두 서술하라.
2. **소비 규칙**: 이 레코드는 언제 소비(= aaa 회수)되어도 안전한가? 어떤 게이트가 필요한가?
3. **불변식 목록**: 이 설계가 지켜야 할 불변식을 최소 4개 쓰라(원자성/게이팅/replication/재처리).
4. **generation bump 와의 비교**: 이 방식이 bump 를 **대체하는** 부분과 **대체하지 못하는**
   부분을 나눠라. "블록 재처리가 이 레코드를 두 번 읽으면 무슨 일이 일어나는가"를 반드시
   통과시켜라.
