## 과제 2

- **S1.** 기대값이 소실되면 남는 선택지는 skip(누수 — R3 위반) 아니면 강행(오탐 — R2 위반)
  둘뿐이다. R1 위반은 독립 실패가 아니라 R2/R3 중 하나를 강제로 위반하게 만드는 상위 실패다.
- **S2.** 스탬프의 역할은 "값의 버전"이 아니라 **"슬롯 재점유의 감지"** 다. 위험한 사건이
  슬롯 재할당이므로 그때마다 값이 바뀌어야 하고, 발급원을 페이지 카운터 하나로 유지해야
  "한 슬롯을 거쳐 간 모든 스탬프는 서로 다르다"가 지역 논증으로 닫힌다(청크값+1 방식은
  미래 insert 의 카운터 발급과 충돌 가능 — ch16 §7).
- **S3.** PG 는 참조가 논리 이름(chunk_id)이고 그 이름은 죽은 참조가 남아 있는 동안 재발급되지
  않으므로(발급기가 SnapshotAny 로 충돌 검사) 재사용 앨리어싱이 성립 불가 — 질문이 없으니
  매트릭스도 없다. 대가: ① 모든 TOAST 읽기가 인덱스 조회 경유, ② 이름 발급기 유지(테이블당
  2^32 미만 가정, 발급 루프 비용).
- **S4.** 위치 — InnoDB 는 대상 객체(LOB 첫 페이지): 회수 단위가 페이지라 회수 완료까지 객체가
  존속. CUBRID 는 회수 단위가 슬롯이라 객체가 삭제와 함께 소멸 → 컨테이너(페이지) 카운터 발급
  + 청크/stub 저장. 폭 — 10B(trx_id 6+undo_no 4) vs 4B: InnoDB 는 기존 트랜잭션 식별자를
  재사용했고 CUBRID 는 전용 카운터라 유일성에 필요한 최소 폭 선택. 기록 시점 — InnoDB 는
  UPDATE(참조 해제자)가, CUBRID 안은 insert(할당자)가 쓴다: InnoDB 의 스탬프는 "이 undo 가
  지울 권리"의 표식이고 CUBRID 의 것은 "이 슬롯 세입자의 신원"이라 의미가 다르다.
- **S5.** 얻는 것 — 전용 카운터 필드 불필요, 전역 유일·시간 순서(진단성). 잃는 것 — 8B(stub 24B),
  그리고 LSA 는 로그 append 후에야 존재하는데 청크 바이트는 append 되는 이미지 안에 있어
  쓰기 순서 재설계 또는 이중 쓰기가 필요. 등가 비교에는 유일성만 필요하므로 순서성은 잉여 —
  비용이 이점을 넘는다(ch16 §5, `CUBRID-C035` 는 회의 정의 자체를 unknown 으로 명시).

## teach-back 모범 답안

재사용 점유자와 정당한 대상은 어떤 단일 수치 축(나이/MVCCID)에서도 분리되지 않는다 —
아주 오래된 살아있는 체인도, 방금 태어난 재사용자도 존재한다. 신원은 순서가 아니라
정체성이므로, "그 값과 정확히 같은가"(등가)만이 두 모집단을 가른다.

## 이 퀴즈가 증명하지 않는 것

매트릭스의 판정은 **미구현 설계에 대한 추론**이다(전제만 source-confirmed —
premises.sh 로 확인 가능). 특히 threshold 반례는 현행 MVCCID 발급 시점(첫 write)에
조건부다 — 발급 규칙이 바뀌면 재평가 대상(ch16 반증 조건).
