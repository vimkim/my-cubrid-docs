# quiz-2 답안

## Q1 — 상태와 영속

상태는 블록 엔트리(VACUUM_DATA_ENTRY)의 `blockid` 상위 3비트에 인코딩되어 vacuum data
페이지(영속, WAL 보호)에 저장된다: `VACUUMED`(0x8000…), `IN_PROGRESS`(0x4000…),
`AVAILABLE`(리터럴 0). `INTERRUPTED`(0x2000…)는 셋과 직교하는 **플래그**다 —
`set_interrupted()` 는 상태를 AVAILABLE 로 되돌리면서 플래그를 켠다(vacuum.c:8358-8363).
"재배포 가능(AVAILABLE)"과 "이전에 중단됨(INTERRUPTED)"이 동시에 참일 수 있어야 하기
때문이다. 엔트리에는 blockid/start_lsa/두 MVCCID 외에 **블록 내 위치 필드가 없다**
(`CUBRID-C010`, ch05).

## Q2 — 정상 셧다운과 재처리

(1) worker 루프가 매 레코드마다 `thread_p->shutdown` 을 검사하고 참이면 블록을 버린다
(vacuum.c:3493-3498). (2) 미완 블록의 `start_lsa` 는 전진하지 않는다 — 소스의 미해결 주석
(vacuum.c:3766-3767)가 "같은 로그 데이터를 다시 처리하게 됨"을 자인한다. 결과: 블록은
AVAILABLE+INTERRUPTED 로 되돌아가 다음 디스패치 때 처음부터 재주행된다(`CUBRID-C011`).

## Q3 — 아니다 (경고 부재 ≠ 안전), 그리고 그 이유가 두 층이다

`is interrupted!` 경고는 master 가 종료 전에 finished-job 큐를 소비한 경우에만 남는다. 소비하지
못하면 블록은 vacuum data 에 IN_PROGRESS 로 남고, 다음 부팅의 `vacuum_data_load_and_recover` 가
조용히 INTERRUPTED 로 바꾼다(vacuum.c:4400-4403). 재주행은 어느 쪽이든 일어난다(`CUBRID-C012`).

보존된 로그가 이를 정확히 보여준다: **rep 2**(정상 셧다운, 백로그 잔존)는 경고 1건 — worker 가
블록을 포기한 것이 기록됐다. **rep 1**(백로그 완주 후 abort 종료)은 경고 **0건**인데도 재기동 후
12,432건이 재삭제됐다. 즉 경고 0 은 "재처리 없음"을 뜻하지 않는다.

단 rep 1 의 규모에는 교란 변수가 있다 — 그 회차는 정상 종료가 아니라 debug assert 로 **abort** 한
회차이므로, 완주 블록이 재주행된 원인이 (a) 도장 비동기 지연인지 (b) abort 로 master 가 큐를 전혀
비우지 못한 것인지 이 실행만으로는 분리되지 않는다(ch12 대안 설명). 정상 셧다운에서도 같은 창이
존재한다는 부분은 **소스 근거로만** 성립한다.

## Q4 — 블록 단일 sysop 이 안 되는 세 가지

1. VACUUMED 표기는 여전히 master 가 비동기로 기록한다 — sysop 커밋과 표기 영속화 사이의
   중단에서 같은 재주행이 남는다(창이 좁아질 뿐).
2. `oos_delete_chain` 은 커밋 전에 페이지를 unfix 하고 bestspace 에 재등록한다 — 커밋 전
   빈 슬롯 노출 창이 레코드 단위에선 마이크로초, 블록 단위에선 블록 처리 시간 전체가 되고,
   abort 시 undo 의 원-슬롯 복원이 남의 슬롯과 충돌할 창도 같이 커진다(ch08).
3. 로그 수십 페이지 분량의 무한계 sysop 은 vacuum 의 짧은-시스템-트랜잭션 설계와 충돌한다.

## teach-back 모범 답안 (요지)

heap 슬롯은 MVCC 헤더를, btree 엔트리는 키+MVCC info 를 **자기 몸에** 지닌다. 재시도가
같은 주소에 도착해도 판정을 점유자의 자기 증언에서 다시 유도하므로, 재사용된 슬롯의 새
점유자는 "살아 있음"을 스스로 증언해 보호된다. vacuum 이 지연 삭제하는 대상 중 OOS 청크만
그런 데이터가 없어서, 같은 재시도 조건이 손상이 된다(ch09, `CUBRID-C041`).

## 실행 확인 문항 답

1. **`Add block` 이 정지 전 부팅에 몰리는 이유** — 블록은 로그를 쓰는 쪽에서 발행된다
   (`prior_lsa_next_record_internal`, 다음 레코드가 경계를 넘을 때 — `CUBRID-C042`). 정지 전 부팅이
   20,000행 INSERT+UPDATE+동시 INSERT 로 로그를 만든 구간이므로 발행이 거기 몰린다. 재기동 부팅은
   이미 발행된 블록을 **소비**할 뿐이고, 그 부팅에서 새로 쓰는 로그(재삭제 자신의 RVOOS_DELETE 등)가
   경계를 한 번 넘어 1건이 추가된다.
2. **경고 수와 재주행 규모가 반대인 이유** — 경고는 "worker 가 블록을 중도 포기했다는 사실이 master 를
   통해 기록됐는가"를 세고, 재삭제 규모는 "재기동 후 몇 개의 블록이 다시 걸렸는가"를 반영한다. rep 2 는
   포기가 1건 기록됐지만 재주행 대상이 그 블록 근방이라 233건. rep 1 은 포기 기록이 0인데(완주했고,
   그 뒤 abort) 도장이 영속화되지 못한 완료 블록 다수가 재장전되어 12,432건. 두 지표는 다른 것을 센다.
3. **experiment-1 에 vacuum 로그가 없는 이유** — 그 DB 의 conf 에 `er_log_vacuum` 이 설정되지 않았다.
   기능이 없어서가 아니라 **채널을 켜지 않았기 때문**이다. ch11 §4 의 논점과 같다: 관측은 기본이 아니라
   설정이며, 릴리스 빌드에는 OOS 청크 수준 채널이 아예 존재하지 않는다(`CUBRID-C047`).

## 이 퀴즈가 증명하지 않는 것

로그 카운트는 재처리의 **간접** 증거다(직접 증거는 experiment-2 의 재삭제 집합).
보존된 발췌는 이 report run 의 두 회차에 한정되며, `--live` 모드는 회전된 최신 로그 하나만
보므로 정지 전 부팅의 블록 생산 기록을 놓친다 — 그래서 채점 기준은 `preserved/` 사본이다.
