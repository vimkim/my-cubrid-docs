# quiz-3 답안

## Q1 — 채널의 강도

채널 A(판독 불가가 된 커밋 행)는 대안 설명이 없다: 그 행들은 슬롯이 비워진 **뒤에**
INSERT·COMMIT 되었고 이후 아무도 수정하지 않았으므로, 커밋 후 그들을 만진 유일한 주체는
2차 vacuum pass 다. 채널 B(재삭제 OID)는 "두 삭제 사이에 슬롯이 재배부되었다"는 물증이지만,
피해가 아닌 재삭제가 섞인다 — 예: 셧다운 순간 abort 된 forward-walk sysop 의 undo 가
청크를 원 슬롯에 **복원**했고, 재기동 후 재주행이 그것을 **정당하게** 다시 지운 경우.
그래서 피해 판정은 채널 A 로만 한다(ch12, `CUBRID-C023`).

## Q2 — 대조군의 구조적 무손상

gen-1 행들의 UPDATE 후(BB) 체인은 **어떤 삭제보다도 먼저** 자리를 잡았다. 재사용된 슬롯은
정의상 pass 1 이 비운 슬롯인데, 그보다 먼저 할당된 체인은 그 안에 있을 수 없다. 따라서
"재사용 슬롯을 물려받은 행"이라는 피해 집합에 구조적으로 속하지 않는다 — 손상이 관측되면
분석이 놓친 더 넓은 메커니즘이 있다는 신호가 되도록 실험이 설계되어 있다.

## Q3 — 아는 것 / 모르는 것

안다: 그 (volid,pageid,slotid)에 **어떤** 레코드가 존재한다(`oos_chunk_exists` 는
spage_get_record 의 성공 여부만 본다). 모른다: 그 레코드가 여전히 undo image 가 소유하던
**그** 청크인지 — 청크 헤더(길이/인덱스/next)에도, stub(OID/길이)에도, probe 시그니처에도
대조할 신원이 없다(`CUBRID-C002`).

## Q4 — 멀티청크 확대

`oos_delete_chain` 은 **현재 점유자**의 헤더에서 `next_chunk_oid` 를 읽어 체인 끝까지
따라가며 지운다(oos_file.cpp:2152-2219, 헤더 memcpy :2192-2194). 재사용된 head 슬롯이
남의 멀티청크 체인의 것이면 그 체인 **전체**가 삭제된다(`CUBRID-C021`). 이번 재현의
payload(5,000B)는 단일 청크라 피해가 슬롯 1개 단위였다.

## Q5 — 더 나쁜 결과와 감지 설계

피해 슬롯이 **또다시** 재사용된 뒤 읽히면 오류 없이 **남의 값이 반환**될 수 있다
(무증상 오답). 실험은 payload 앞 8 hex 에 행의 id 를 각인해 값 비교(`payload <> 기대값`)가
이 경우를 mismatch 로 잡도록 설계했다 — 이번 run 관측 0건(부재 증명은 아님).

## Q6 — 실행 형태의 차이, 그리고 태도: 추정은 추정으로

**차이**: rep 1 은 pass 1 이 20,000 체인 백로그를 *완주* 한 뒤 VACUUMED 도장이 영속화되기
전에 종료됐다 — 재기동 후 *블록 전체 집합* 이 재주행되며 이미 정당하게 끝난 구간까지 다시
걸었다. rep 2 는 백로그가 *남은 채* 중단되어 재주행 범위가 실제 미완 구간에 가까웠고,
그래서 재삭제 = 피해가 233:233 으로 맞았다.

**태도**: 위 설명은 **추정**으로만 적혀 있고, 초과분의 pass-2 점유자 구성은 `CUBRID-C048`
에서 **unknown** 으로 남아 있다. 옳은 이유: oos.log 에 insert 기록이 없어(`CUBRID-C043`)
점유자를 사후 식별할 수단이 없다. 추정을 결론처럼 쓰면 채널 B 를 피해 척도로 오독하게
만든다. 결론(결함 성립)은 채널 A 만으로 서므로, 간극은 정직하게 미해결로 남기고 해소
경로(배치 insert 로그 추가 후 재실행)를 적는 것이 맞다.

## teach-back 모범 답안

forward-walk 의 확인을 "슬롯이 점유돼 있는가"에서 **"슬롯이 여전히 undo image 가 소유하던
그 청크를 담고 있는가"** 로 바꾼다 — 구현으로는 등가 비교 가능한 신원 스탬프(ch16).

전부 ch17 unknown/후속 실험 목록에 있다.
