# quiz-1 답안

## P1 — ② 로그의 undo image

UPDATE 는 항상 새 체인을 만들고(M1), 살아있는 새 버전의 stub 은 새 체인만 가리킨다.
옛 체인을 가리키는 유일한 참조는 UPDATE 로그 레코드의 undo image(옛 레코드 원본) 속
옛 stub 하나다. ①은 틀림 — 살아있는 레코드는 옛 체인과 무관하다. ③도 틀림 — 청크 헤더에는
next_chunk_oid(자기 체인 내부 링크)만 있지 소유자 역참조가 없다. ④ bestspace 는 빈 공간
힌트일 뿐 참조가 아니다. (ch04 V-2, `CUBRID-C001`, `C002`)

## P2 — 값은 처음부터 끝까지 온전하다

스냅샷 독자가 남아 있는 동안 vacuum 은 블록 게이트(newest MVCCID < oldest visible)에
막혀 아예 시작하지 않고, 회수가 시작된 뒤에는 옛 체인을 읽을 독자가 정의상 없다.
회수는 옛 체인만 제거하므로 새 값 읽기는 영향이 없다 — 관측: total=2000, mismatch=0
(`CUBRID-C003`, 캡처된 experiment-1 과 동일 결과).

## P3 — delete 는 2,000+, insert 는 0 (함정)

대부분 "insert 도 2,000+(새 체인)"라고 예측한다. 실제로는 **0** 이다: oos.log 의 insert
기록은 단건 API `oos_insert`(oos_file.cpp:1219)에만 있고, 실제 INSERT/UPDATE 가 쓰는
배치 API(`oos_insert_many`)에는 로그가 없다(`CUBRID-C043`, CBRD-26871). 관측 채널이
"삭제만 보이는 반쪽"이라는 사실이 P3 의 교훈이다.

## T1 — 재사용이 없었던 이유

UPDATE 이후 이 DB 에 들어온 OOS 값이 없도록 설계되어 있어서가 아니라 — 필러도 5,000B
OOS 행이다! — 필러가 들어가는 시점에 비워진 슬롯이 있으면 재사용될 수 있다. 그러나
재사용 자체는 무해하다: **블록 재처리가 없으므로** 옛 OID 를 두 번째로 들고 오는 주체가
없다. 손상의 필요조건은 재사용이 아니라 "재사용 + 재처리"의 결합이다(ch06). 이 실험은
그 결합의 negative control 이다.

## T2 — 필러를 빼면

마지막 vacuum 블록이 발행되지 않는다. 블록은 "다음 로그 레코드가 경계를 넘을 때"만
발행되므로(log_append.cpp:1376-1386, `CUBRID-C042`), UPDATE 후 로그가 조용하면 회수
카운트가 2,000 에 도달하지 못하고 스크립트는 타임아웃으로 실패한다(exit 2).

## T3 — 증거 설계에의 영향

슬롯 재사용을 "삭제 후 같은 자리 insert"로 직접 증명할 수 없으므로, PoC 는 두 pass 의
삭제 집합 **교집합**(같은 OID 가 두 번 삭제됨 = 그 사이 누군가 점유)을 보강 증거로 쓰고,
결정적 증거는 "커밋 후 무수정인데 판독 불가가 된 행"(채널 A)으로 세운다(ch12).

## 이 실험이 증명하지 않는 것

- 결함의 부재(그건 experiment-2 가 반대로 증명) — 이 실험은 정상 경로의 건전성만.
- 멀티청크 체인의 정상 회수(payload 가 단일 청크 크기).
- release 빌드 동작(관측 채널이 debug 전용일 뿐 메커니즘은 동일 — ch12).
