Identity: src HEAD = 1f9f09f362390e10ed06d80f9aae3ae2e361b2d2 (verified), base d52b1889. Source-only review (no builds, servers or ctest run). Coverage: complete for the assigned invariants. No evidence above level 3.

## Shared challenge: (a) heap record removed w/o OOS reclaim, (b) referenced OOS reclaimed, (c) block marked complete with a skipped object
Answer: no feasible schedule found through the paths this PR changes (level 3, source argument). Residual gaps listed in C1/C2.
- (a) In vacuum_heap_prepare_oos_vfid a failed lookup now returns an error before vacuum_heap_record can run. Order: nowait fails -> pages released (home+forward unfixed, bulk slots logged) -> waited lookup -> on error return -1393 (worker) or raw error (non-worker). The caller (vacuum_heap_page, error branch at ~L1815) unfixes forward, goto end; no spage_vacuum_slot occurs for that record. After the waited lookup succeeds, home is refixed and the record is re-read (goto retry_prepare), and oos_vfid stays non-NULL, so a slot change in the released window is re-examined with the right vfid. The remaining removal-without-reclaim path is "lookup succeeded with NULL VFID" (heap really has no OOS file): release logs and removes (bounded leak), debug asserts. That is pre-existing/by design (fix-decisions decision 1), not an interleaving.
- (b) The PR does not touch the reclaim side (vacuum_heap_oos_delete_within_sysop, forward walk). Deferral only removes work from a run. Not affected.
- (c) vacuum_heap: first deferral sets deferred, skips remaining pages of that vfid (scan from obj_ptr, correct since obj_ptr = first object of next page), continues other heaps; at the end error_code NO_ERROR -> er_stack_pop restores the saved -1393 and returns it; another error -> er_stack_pop_and_keep_error keeps the newer error. Either way vacuum_process_log_block goes to end with vacuum_complete=false -> vacuum_finished_block_vacuum produces the blockid without the VACUUMED flag -> vacuum_data_mark_finished set_interrupted. er stack semantics verified in error_context.cpp: push adds a new empty top, pop destroys the top and exposes the saved error, so -1393 is the live error at vacuum_finished_block_vacuum and the asserts (er_errid) see it. er_clear in the 2nd-deferral branch clears only the top. The released-window re-read plus was_interrupted rerun covers objects already vacuumed in the first run.

## Assigned invariants
1. Cursor gate: CLEARED (level 3).
 - force_data_update callers: xvacuum (SA, L1032/L1071, local cursor, single thread; SA never passes retry=true) and vacuum_master_task::execute (L3330 retry=true, L3363 retry=false); m_cursor is a member of the master task, run only by the single master daemon. Other vacuum_Data.update/mark_finished callers (vacuum_finalize L1489 with NULL, vacuum_sa_reflect_last_blockid L8142, xvacuum end L1133) are shutdown/SA contexts without the cursor and never touch m_retry_blockid/m_next_retry_time. Checkpoint/vacuumdb do not reach the cursor.
 - Rewind cannot skip: m_blockid only moves down to min(m_retry_blockid); readjust then clamps up to first block. Interrupted entries stay "available" in vacuum data, so the rescan sees them. If retry >= m_blockid it is just dropped (cursor reaches it anyway).
 - Rewind cannot double-dispatch: an entry stays IN_PROGRESS from start_job_on_current_entry until the master itself consumes the finished queue (vacuum_data_mark_finished asserts is_job_in_progress), and is_cursor_entry_available skips in-progress and vacuumed entries. So a block still running on a worker (or finished but not yet consumed) is skipped by the rewound scan.
 - Timer: had_interrupted is read before update; timer set only on first interrupted observation, retained across mid-iteration updates and when a smaller blockid is added (min kept by vacuum_data_mark_finished). Reset to NULL only on actual rewind, so a repeated failure restarts the 1 s window. Worst case a retry is delayed up to ~1 s + master period; no lost retry (m_retry_blockid persists until it fires).
2. Latch ordering on worker path: CLEARED (level 2-3). A vacuum worker holds only the helper's home/forward pages when it does the nowait conditional fix (cannot block). On failure it releases both (log_and_reset + unfix) before the unconditional waited lookup, then refixes home after the header (header -> home order, same as the base code). vacuum_heap/vacuum_heap_page hold no other latch across it. ALTER path: heap_vacuum_all_objects holds its ordered watchers (pg_watcher/old_pg_watcher) across the waited lookup; this is unchanged from base (not introduced).
3. ALTER path raw error: CLEARED (level 2). vacuum_is_thread_vacuum_worker is type == TT_VACUUM_WORKER. ALTER/heap_vacuum_all_objects runs on a client worker thread, so prepare returns the raw error (-72/-836), vacuum_heap_page goes to end, heap_vacuum_all_objects gets it. Behavior change vs base: ALTER now fails on a lookup failure instead of silently swallowing (intended). SA mode: vacuum_sa_run_job converts the thread to TT_VACUUM_WORKER, so SA/vacuumdb sees -1393 (not raw); xvacuum then goto end returns -1393 and persists the interrupted state via vacuum_Data.update (SA has no retry loop). The SA assert branch in vacuum_finished_block_vacuum was updated to accept -1393. Note only; acceptable.
4. Shutdown: asserts accept -1393 exactly (L8332 and both vacuum_finished_block_vacuum branches, SERVER and SA). See N1.

## Candidates
C1 (pre-existing, same defect class, NOT fixed by the PR; proposed priority P2-medium; evidence level 2, unproven by execution): forward-walk reclaim still swallows a failed OOS header lookup and lets the block complete. vacuum_oos.cpp vacuum_forward_walk_reclaim_oos (lines ~315-330 of the pinned file): lookup_result == VACUUM_OOS_VFID_ERROR -> "leaving OOS unreclaimed (bounded leak)", er_clear(), "DO NOT propagate; the block must complete". vacuum_oos_vfid_lookup uses the waited heap_oos_find_vfid (L116), so a header latch timeout/IO error there leaks the OOS values of a relocated record whose NEWHOME delete (RVHF_DELETE_NEWHOME_NOTIFY_VACUUM) is only in the undo image (slot already physically gone, so this is the only reclaim chance, forever leaked) and marks the block vacuumed. Actors: vacuum worker vs any transaction holding the heap header page past the latch timeout (same trigger as the reproduced bug). Violates the same invariant as (c). Fix direction: return a deferred error (worker-only -1393) here too and rerun the block; the block rerun is idempotent. Whether the user considers this in scope for CBRD-27933 is a coordinator/author decision; the PR title ("OOS vfid lookup error") reads as covering it. Also in that function: file_descriptor_get/HFID-null failures and OOM (db_private_alloc) and non-INTERRUPTED vacuum_forward_walk_oos_delete_atomic failures are swallowed the same way (L245/L315/L329/L356; design says bounded leak).

N1 (low, evidence 2): shutdown latency. A worker lookup failure that is ER_INTERRUPTED during shutdown is now converted to -1393 in prepare. vacuum_heap then does not stop: it only skips that heap and keeps vacuuming every remaining heap in the block (previously ER_INTERRUPTED broke out at once; the old check `thread_p->shutdown && ER_INTERRUPTED`). Correctness holds (block ends interrupted, retried after restart) but shutdown may wait for the rest of the block. Suggest: do not convert ER_INTERRUPTED (keep raw, which the assert already allows), or break the vacuum_heap loop when shutdown is requested.

N2 (info): debug builds: vacuum_oos_report_missing_oos_file asserts when lookup succeeds with NULL VFID and the record has the OOS flag. Legit only if invariant broken; design decision 1. Not a concurrency issue; stale-object cases (heap/OOS file dropped while old blocks remain) belong to the recovery reviewer.

## Rejected hypotheses
- Cursor state touched by another thread: rejected (callers above).
- Rewind re-dispatches a running block: rejected (IN_PROGRESS flag lifecycle).
- Stale -1393 on the worker thread masks a later unexpected error in the assert: only matters if a worker does not clear errors between jobs; assert-quality issue only, not pursued.
- er_stack_push/pop imbalance: all exits of vacuum_heap after the first deferral go through the post-loop pop (breaks replaced the early returns); no early return remains between push and pop (checked L1595-1660).
