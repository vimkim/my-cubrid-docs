# PR #8350 리뷰 스레드 회신 초안

이 글은 hornetmj 팀장님의 [PR #8350 리뷰 댓글](https://github.com/CUBRID/cubrid/pull/8350#discussion_r4452180248) 스레드에 답글로 올릴 초안이다. 아직 게시하지 않았다. 숫자와 관측의 근거는 [repro-analysis.md](repro-analysis.md)에 있다.

## 답글 본문

팀장님, CBRD-27933을 재현한 결과를 공유드립니다. 수리 방향을 제안해 주신 것과 조금 다르게 잡았기 때문에 그 이유도 함께 말씀드립니다.

**제안해 주신 방향**

조회 실패를 오류로 반환해서 vacuum이 같은 페이지를 다시 처리하게 하고, 셧다운 중이면 블록을 미완료로 남겨 재기동 후 다시 처리하게 하는 것이었습니다.

**재현 결과**

병합 전 PR #8350 head(`1ef6ed612`)의 release 빌드로 확인했습니다. 테스트 스레드가 heap 헤더 페이지를 WRITE latch로 잡고 있으면, vacuum의 헤더 대기가 latch timeout으로 실패합니다. timeout은 2초로 줄여서 실행했습니다.

- 현재 코드에서는 timeout 한 번으로 삭제 행의 슬롯만 제거되고 OOS 값이 남았습니다. 로그 블록은 complete로 끝났습니다. `REC_HOME`, `REC_RELOCATION`, 셧다운 중 실패에서 모두 같았습니다. 지적하신 그대로입니다.
- 제안하신 방향을 prototype으로 넣어 보니, 일시 오류에서는 헤더가 풀린 뒤 OOS 값이 회수되었습니다. 셧다운 중 실패에서는 블록이 interrupted로 남았습니다.
- 문제는 조회가 계속 실패할 때였습니다. release의 [`vacuum_heap`](https://github.com/CUBRID/cubrid/blob/1ef6ed6125eb6028c06b0e05282dc0041bde3f48/src/query/vacuum.c#L1593-L1621) 은 셧다운이 아닌 페이지 오류를 지우고 같은 페이지를 다시 처리합니다. 헤더를 60초 동안 잡아 두었더니 워커는 같은 페이지만 다시 시도했고, timeout이 2초 간격으로 23번 났습니다. vacuum 워커를 1개로 두고 같은 조건을 만들었을 때는, 그 60초 동안 다른 heap의 삭제 행을 하나도 vacuum하지 못했습니다.

**바꾼 방향**

헤더 조회가 실패하면 같은 페이지를 다시 처리하지 않고, 그 로그 블록을 interrupted로 넘기려 합니다. 워커는 다음 블록으로 가고, vacuum master가 그 블록을 나중에 다시 배정합니다. `ER_OUT_OF_VIRTUAL_MEMORY` 가 이미 이 경로를 씁니다. 다른 페이지 오류는 지금처럼 같은 페이지를 다시 처리합니다.

같은 조건(워커 1개, 60초)에서 이 방식의 prototype을 돌려 보니, 다른 heap의 행은 14.6초에 vacuum되었습니다. 실패한 블록은 interrupted로 23번 다시 실행되었고, 헤더가 풀린 뒤 complete가 되면서 OOS 값도 회수되었습니다. 일시 오류와 셧다운에서는 제안하신 방향과 결과가 같았습니다.

**이유**

같은 페이지를 다시 처리하면, 헤더 하나가 계속 실패하는 동안 그 워커가 무기한 묶입니다. 워커가 적으면 다른 heap의 vacuum까지 멈춥니다. 블록 단위로 넘기면 그 비용이 실패한 블록의 재실행으로 한정됩니다.

**함께 정리하는 것**

- "기다린 조회의 답을 최종으로 쓰는" 처리는 조회가 성공한 경우에만 적용됩니다. 실패하면 그 자리에서 오류를 반환하므로, 비어 있는 OOS 파일 ID로 레코드를 다시 준비하는 일이 없습니다.
- 지금 실행되지 않는 `vacuum_heap_prepare_oos_vfid` 의 오류 검사가 실행됩니다. 블록을 넘기는 표시도 그 자리에서 남깁니다.

**아직 확인하지 않은 것**

- 헤더 페이지 읽기 오류처럼 기다리지 않고 바로 실패하는 오류는 실행하지 않았습니다. 이때는 같은 블록이 vacuum master 주기마다 다시 실행될 수 있습니다(소스를 보고 추론). 수리하면서 측정하고, 필요하면 재실행 간격이나 진단 로그를 넣겠습니다.
- 재기동 뒤 interrupted 블록이 다시 실행되어 OOS 값을 회수하는 단계는 실행하지 못했습니다.
- debug 빌드에서는 latch timeout이 `pgbuf_timed_sleep` 의 FIXME assert(`page_buffer.c:7365`)에서 먼저 서버를 멈춥니다. 그래서 이 재현은 release에서만 판정됩니다.
- PR #8350이 병합된 뒤의 `feature/oos-merge` 에서는 아직 다시 돌리지 않았습니다.

재현 절차와 측정 기록은 [재현 분석 문서](https://github.com/vimkim/my-cubrid-docs/blob/main/cbrd-27933/repro-analysis.md)에 정리했습니다. 재현 테스트는 수리 PR에 함께 올리겠습니다. 이 방향으로 진행해도 괜찮을지 의견 부탁드립니다.
