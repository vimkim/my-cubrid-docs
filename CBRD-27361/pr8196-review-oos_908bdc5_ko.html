NULL인데 계수의 부호와 숫자를 읽습니다

eb_cell_num()은 NULL이면 0을 반환하며 출력 변수 nv를 채우지 않습니다. 호출자는 그 직후 nv.is_negative와 nv.coefficient를 먼저 읽습니다. 반환값이 0인지 확인하는 시점이 늦습니다.

입력에 따른 코드의 의미 · 설명용 전환
got = eb_cell_num(col, layout, &nv);an = nv.is_negative ? -nv.coefficient : nv.coefficient;
got = 0 · nv는 채워지지 않았는데 다음 줄에서 읽습니다.

비교 결과를 나중에 버리더라도 이미 초기화되지 않은 값에 접근했습니다. 개선 방향은 got > 0일 때만 계수를 만들고, NULL과 읽기 실패를 각각 먼저 처리하는 것입니다.

병렬 작업을 만들지 못했을 때의 경계가 없습니다

new callable_task(...) 결과를 바로 작업 관리자에 넘깁니다. 서버의 wrapped new는 NULL을 반환할 수 있고, 내부 std::function 구성은 할당 중 예외를 던질 수 있습니다.

이미 제출한 작업을 기다린 뒤 예약 worker와 merge 상태를 정리하고, 실패를 CUBRID 오류 코드로 전달해야 합니다. 이 리뷰에서 메모리 부족을 주입하지는 않았습니다.

오류를 정리하다가 다른 NULL 포인터를 읽습니다

out_rows 할당은 성공하고 out_partials 할당만 실패할 수 있습니다. 그런데 정리 루프는 out_rows != NULL만 확인한 후 두 배열을 모두 인덱싱합니다.

두 배열을 독립적으로 검사해야 합니다. 이는 기존 Greptile 지적을 소스로 재확인한 것으로, 새로운 실행 재현은 아닙니다.

소스 확인Standards · P2

입력 읽기 오류를 정상적인 끝으로 취급합니다

런타임 필터는 build 입력의 키를 전부 읽어야 안전하게 probe 행을 버릴 수 있습니다. 현재 루프는 S_SUCCESS 동안만 돌고, 끝난 이유가 S_END인지 S_ERROR인지 확인하지 않은 채 필터를 설치합니다.

설명용 예: 필요한 키가 {3, 7, 11}인데 {3, 7}을 읽은 뒤 오류가 났다면, 이 집합으로 11을 가진 행을 거절하면 안 됩니다. 실제 I/O 오류를 주입한 실험 결과는 아닙니다.

마지막 scan 코드를 보존하고 오류를 전파한 후에만 필터 설치 여부를 결정해야 합니다.

캐시 슬롯이 이동했는데 옛 위치로 다음 항목을 지웁니다

GROUP BY 캐시는 실제 aggregate 값의 포인터를 보관합니다. 같은 충돌 구간의 그룹 여러 개가 축출될 때, 첫 항목을 지우면서 뒤 항목을 앞으로 당깁니다. 다음 항목도 지우려면 이동한 위치를 반영해야 하지만 현재 코드는 미리 저장한 슬롯 번호를 계속 사용합니다.

무효화를 놓치면 나중에 이미 축출되었거나 slab에서 재사용된 aggregate 값에 접근할 수 있습니다. 여러 항목을 먼저 표시한 뒤 재배치하는 등, 슬롯 이동과 독립적인 무효화 방식이 필요합니다.

OOS와는 논리적으로 함께 동작할 수 있습니다

저장 표현과 실행 단위는 서로 다른 관심사입니다. 통합의 핵심은 raw 디코더가 OOS 표현을 식별하고 올바른 읽기 경로를 선택하게 만드는 것입니다.

OOS의 역할

큰 값은 밖에 두고 필요할 때 읽습니다

heap 레코드에는 OOS inline stub을 두고, 실제 값은 OOS value chain에 저장합니다. 작은 컬럼만 사용하는 질의는 큰 값을 읽지 않을 수 있습니다.

배치 실행의 역할

필요한 값들을 묶어 평가합니다

가시 행을 모으고 사용하는 컬럼만 처리해 필터·집계의 CPU 비용을 줄입니다. OOS 값을 쓰지 않는 경우에도 이 최적화가 의미를 가질 수 있습니다.

서로 보완할 수 있는 방향입니다. OOS는 불필요한 큰 값 읽기를 줄이고, 배치는 작은 컬럼에 대한 행별 평가 비용을 줄일 수 있습니다. 다만 통합 성능은 아직 측정하지 않았습니다.

지금의 호환성 공백: 값이 있는 자리에 stub이 있습니다

새 eb_cell_str()는 필드의 첫 바이트를 짧은 문자열 길이로 해석합니다. OOS의 IS_OOS를 확인하는 단계가 없으므로, 이 경로를 그대로 합치면 stub을 문자열로 해석할 수 있습니다. 예를 들어 stub 첫 바이트가 0이면 실제 긴 값 대신 길이 0인 문자열처럼 받아들일 수 있습니다.

소스로 확인한 통합 공백입니다. 실제 값이 긴 “A…” 문자열인 행에 WHERE v LIKE 'A%'를 적용하는 경우가 통합 재현 후보입니다. OOS와 합친 바이너리에서 오답을 재현한 결과로 표현해서는 안 됩니다.

PR: eb_cell_str():958–975 · OOS: IS_OOS 검사 후 Resolve

호환성을 확보하는 단계

  1. 먼저 기존 OOS 읽기 계약을 보존합니다

    현재 develop의 속성 디코드 API와 OOS-only 호출부를 맞춥니다. Resolve한 임시 버퍼를 COPY한 뒤 해제하는 소유권 처리를 유지해야 합니다.

  2. 안전한 초기 버전은 HAS_OOS 행을 fallback합니다

    배치 평가와 소비가 시작되기 전에 해당 행을 포함한 청크를 행 경로로 넘깁니다. 성능상 보수적이지만 stub 오해석을 차단할 수 있습니다.

  3. 이후 사용하는 컬럼의 IS_OOS만 검사합니다

    읽지 않는 큰 컬럼 때문에 숫자 컬럼 배치를 포기하지 않도록 범위를 좁힙니다. 사용하는 OOS-backed 속성은 행 경로 또는 명시적인 Resolve로 처리합니다.

  4. Resolve 결과의 소유권과 GROUP BY 키를 정의합니다

    heap 페이지 고정만으로 OOS 임시 버퍼 수명까지 보장되지는 않습니다. 물리 stub과 논리 값의 차이를 캐시 키·무효화 정책에 반영해야 합니다.

  5. 혼합 데이터와 동시성으로 검증한 뒤 성능을 측정합니다

    같은 컬럼의 inline/OOS 혼재, LIKE·IN·NULL·GROUP BY, 직렬/병렬, UPDATE·vacuum·이전 버전 읽기를 대조합니다.

질의가 사용하는 컬럼에 따른 통합 방향 · 제안이며 구현 완료 상태가 아닙니다

모든 행을 무조건 Expand하는 방법은 우선 권장하지 않습니다. 쓰지 않는 큰 값까지 가져오면 OOS의 I/O 절약을 없앨 수 있습니다. Resolve는 속성 단위의 지연 읽기, Expand는 레코드 전체의 eager 복원이라는 차이를 유지해야 합니다.

따라서 다섯 충돌을 모두 이 PR이 새로 만든 것으로 볼 수 없습니다. OOS는 PR base에 이미 있는 HEAP_REC_LAYOUT·디코드 API 변경과도 차이가 있습니다. 반면 새 raw 문자열 경로의 OOS 식별 누락은 이 PR을 통합할 때 추가로 해결해야 하는 문제입니다.

실제 브랜치 병합, 충돌 해결, 통합 빌드와 회귀 실행은 하지 않았습니다. 가상 merge tree에는 충돌 표시가 남아 있으며 빌드 가능한 결과물로 취급하지 않았습니다.

문제가 아닌 부분과 별도 점검할 부분
  • OOS의 VOT offset 매크로는 flag 비트를 제거합니다. OOS 매크로를 보존한다면 flag가 그대로 offset에 섞이는 문제가 핵심은 아닙니다.
  • MVCC header 크기는 하위 세 flag 비트로 계산되어 HAS_OOS 메타데이터 비트를 크기로 세지 않습니다.
  • 문제는 올바른 위치를 얻은 뒤 그 필드가 inline 값인지 stub인지 검사하지 않는다는 점입니다.
  • GROUP BY의 raw 바이트 캐시는 서로 다른 OOS chain에 있는 같은 값에 대해 miss가 늘 수 있습니다. miss가 행 경로로 가므로, 이것만으로 잘못된 그룹 결과가 재현되었다고 판정하지 않았습니다.
  • 검토한 지점에서 별도의 watcher 위반이나 OOS 임시 버퍼 수명 결함을 추가로 입증하지는 않았습니다.

다음 리뷰는 가시성·수명·OOS 경계부터 진행합니다

대규모 diff를 한 번에 승인하기보다 작성자가 제안한 여섯 단위를 따라 검증 범위를 나누는 편이 좋습니다.

  1. 코어: heap 가시성·청크·기본 집계

    heap_next_1page와 같은 가시 행을 반환하는지, 중간 fallback에서 행이 중복·누락되지 않는지 확인합니다. OOS 식별 gate를 이 단계에 포함합니다.

  2. 투영·해시 GROUP BY 소비 노드

    NULL·누산기·레코드 소유권과 캐시 축출을 확인합니다. inline/OOS가 섞인 같은 논리 키도 포함합니다.

  3. 숫자 리프와 조인 아래 필터

    타입·오버플로·scan reset과 페이지 해제를 확인합니다.

  4. 문자열·IN·OR·SUBSTRING

    collation·공백·3값 논리를 확인하고, OOS-backed 문자열의 안전한 fallback 또는 Resolve를 검증합니다.

  5. 잔여 GROUP BY 병합·병렬화·slab

    메모리 예산, spill, 순서 의존 집계와 작업 생성·정리 실패를 확인합니다.

  6. 해시 조인 런타임 필터

    허용되는 join 모양, 전체 키 집합의 완성, 오류 전파와 filter 수명을 확인합니다.

통합 목표는 “큰 값은 필요할 때만 읽고, 작은 값의 평가는 묶어서 처리하기”입니다. 안전한 행 경로를 유지하며 OOS-aware 배치 범위를 넓히는 방식으로 접근할 수 있습니다.
