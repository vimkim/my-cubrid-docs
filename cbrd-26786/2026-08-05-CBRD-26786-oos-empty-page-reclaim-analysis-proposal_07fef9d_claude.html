비어 있는 OOS 페이지, 어떻게 되찾을까?

vacuum 의 OOS 빈 페이지 회수 — 분석과 제안 (쉬운 설명 버전)

JIRA 상태: Analysis (미해결) 유형: Sub-task (부모: CBRD-26583 M2 epic) 우선순위: Minor 목표 버전: guava
📌 한눈에 보기 (TL;DR)

vacuum(청소부)이 OOS 페이지 안의 데이터를 전부 지워도, 지금은 그 페이지가 "비었다"는 사실을 bestspace cache 라는 메모장만 알고 있습니다. 그런데 이 메모장은 칸이 1000개뿐이고, 꽉 차면 새 메모를 못 쓰고, 서버를 재시작하면 전부 지워집니다. 메모장에서 빠진 빈 페이지는 INSERT 경로에서 투명 인간이 되어, 빈 페이지를 놔두고 파일을 새로 늘리게 됩니다.

제안: vacuum 이 페이지를 다 비운 순간, file_dealloc 를 호출해서 그 페이지를 파일 관리자(file manager)의 partial sector table 이라는 영구 장부에 "빈 페이지"로 되돌려 놓자는 것입니다. 이 장부는 칸 제한이 없고 재시작해도 남습니다. — 질문 주신 "vacuum 이 빈 페이지를 file partial table 로 되돌리면 되는가?"에 대한 답은 "네, 정확히 그 방식이 현재 제안"입니다.

단, 조건이 하나 있습니다. 이 제안은 "실제로 효과가 있는지"를 측정으로 먼저 증명해야 하는 ANALYSIS 게이트가 걸려 있습니다. 측정 결과 효과가 미미하면 이슈는 Won't Fix 로 닫고, 죽은 함수 정리만 소규모 패치로 처리하기로 되어 있습니다.

1. 배경 지식 3분 요약

이 문서를 읽는 데 필요한 개념은 네 개뿐입니다. 창고 비유로 기억하면 쉽습니다.

개념비유실제 의미
OOS 파일 창고 건물 테이블의 큰 컬럼 값(예: 4KB 넘는 문자열)을 heap 레코드에서 떼어내 따로 보관하는 파일. 테이블(heap 파일)당 최대 1개.
OOS 페이지 창고 안의 선반 파일을 구성하는 16KB 단위 저장 공간. 선반 하나에 상자(슬롯)가 여러 개 놓입니다.
vacuum 청소부 아무 트랜잭션도 더는 보지 않는 옛 데이터를 뒤늦게 치우는 백그라운드 프로세스. OOS 의 경우, 죽은 레코드 버전이 갖고 있던 OOS 값들을 oos_delete 로 지웁니다.
bestspace cache 사무실 화이트보드 "3번 선반에 빈자리 있어요"라고 적어두는 메모. INSERT 가 빈자리를 빨리 찾도록 돕는 힌트일 뿐, 진짜 장부가 아닙니다. 메모리에만 존재합니다.

그리고 이 문서의 주인공인 partial sector table 은 창고의 정식 장부입니다. 파일 관리자(file manager)가 파일 헤더 페이지에 디스크로 영구 저장하는 표로, "이 구역(sector)의 어느 페이지가 사용 중이고 어느 페이지가 비었는지"를 비트맵으로 기록합니다. 새 페이지가 필요할 때 file_alloc 이 가장 먼저 뒤져 보는 곳이 바로 이 장부입니다.

2. 문제: 빈 페이지가 '투명 인간'이 되는 과정

2-1. 지금까지 된 것 — 슬롯(상자) 단위 회수

선행 이슈(CBRD-26609, CBRD-26668)로 슬롯 단위 회수는 이미 완성되어 있습니다. vacuum 이 oos_delete 를 부르면 페이지 안의 상자(청크 레코드)가 지워지고, 그 직후 "이 선반에 빈자리 생겼어요"가 화이트보드(bestspace cache)에 메모됩니다.

2-2. 안 된 것 — 페이지(선반) 단위 회수

그런데 선반의 상자가 전부 비워져도, 그 선반을 창고 장부(partial sector table)에 "빈 선반"으로 되돌리는 코드는 아직 아무도 호출하지 않습니다. 코드에는 oos_remove_page 라는 함수가 준비만 되어 있고 (현재 oos_file.cpp:1104), 바로 위에 이런 주석이 붙어 있습니다: "TODO: will be called by vacuum when OOS vacuum is implemented". 즉, 페이지 회수는 설계 의도만 있고 연결이 안 된 상태입니다.

2-3. 화이트보드(bestspace cache)의 세 가지 약점

코드로 확인된 사실 세 가지입니다 (커밋 07fef9d48 기준):

약점 ① 칸이 1000개 OOS_BESTSPACE_CACHE_CAPACITY = 1000 (oos_file.cpp:109). 이 1000은 서버 전체의 모든 OOS 파일을 합산한 상한입니다. OOS 컬럼을 가진 테이블이 여러 개면 충분히 도달할 수 있습니다.
약점 ② 꽉 차면 새 메모 불가 캐시가 가득 차면 새 페이지 등록 함수가 그냥 NULL 을 반환하고 끝납니다 (oos_file.cpp:346). 기존 메모의 숫자만 고칠 수 있고, 한 번 못 들어간 페이지는 다시 등록될 기회가 없습니다.
약점 ③ 재시작하면 백지 캐시는 malloc 으로 만든 메모리 해시테이블입니다. 서버를 재시작하면 그동안 쌓인 빈 페이지 정보가 어디에도 남지 않습니다.

2-4. 그래서 생기는 두 가지 낭비 시나리오

  • 시나리오 1 — 캡 도달(cap-bound): OOS 테이블이 많아 화이트보드 1000칸이 가득 찬 뒤에 생긴 빈 페이지들은 영영 메모되지 못합니다.

⚠️ 정확히 무엇이 손해인가 (그리고 무엇은 손해가 아닌가)

사용자 눈에 보이는 SQL 동작에는 영향이 없습니다. 손해는 성능/공간 효율입니다: 빈 페이지를 재사용하지 못해 OOS 파일의 확장 빈도가 불필요하게 올라갑니다. 또한 oos_delete 의 주석에 적힌 설계 의도 ("Empty pages will be reclaimed by vacuum…", oos_file.cpp:2304)가 미완으로 남아 있는 것도 기술 부채입니다.

3. 해결 후보 비교 — 왜 "vacuum + file_dealloc" 인가

질문 주신 "bestspace 가 모든 빈 페이지를 추적하지 못하니, 되찾는 권장 방법은 무엇인가?"에 대해 세 가지 후보를 비교합니다.

후보 A — 화이트보드 자체를 고친다 (bestspace cache 개선)

캡을 늘리고, 오래된 메모를 지우는 eviction 을 넣고, 디스크에 저장(persistence)하게 만드는 방법입니다. 하지만 bestspace 는 태생이 "틀려도 되는 힌트"입니다 — heap 파일이 15년 넘게 검증해 온 설계 자체가 그렇습니다. 힌트 캐시를 "절대 잊으면 안 되는 진실의 원천"으로 승격시키면 캐시 정합성·복구·동시성 문제를 전부 새로 떠안게 됩니다. 배보다 배꼽이 커집니다.

후보 B — PostgreSQL 방식 (tail truncate / VACUUM FULL)

PG 의 일반 VACUUM 은 파일 꼬리(맨 끝)의 빈 페이지만 잘라서 OS 에 돌려줍니다. 중간에 흩어진 빈 공간까지 회수하려면 VACUUM FULL(테이블 통째 재작성)이나 pg_repack 확장이 필요합니다. CUBRID 는 sector 기반 파일 구조라 "꼬리 자르기" 개념이 그대로 이식되지 않고, VACUUM FULL 급 재작성은 이번 이슈와는 비교가 안 되는 큰 공사입니다. (이 비교는 이슈 코멘트에도 기록되어 있습니다.)

후보 C — vacuum 이 빈 페이지를 창고 장부에 되돌린다 제안

vacuum 이 페이지를 다 비운 시점에 file_dealloc 를 호출하면, 파일 관리자가 그 페이지를 partial sector table(영구 장부)에 "빈 페이지"로 기록합니다. 이 장부는 캡이 없고, 재시작해도 살아남고, 다음 file_alloc 이 즉시 재사용할 수 있습니다. 이미 존재하는 검증된 인프라(RVFL_DEALLOC postpone 복구 경로 포함)를 그대로 재사용하므로 변경량도 작습니다.

구현 크기 중간~큼 (캐시 수명주기 재설계) 매우 큼 (파일 재작성/이동) 작음 (helper 1개 + 호출 3곳)

✅ 결론

권장 방법은 후보 C — 질문에서 예상하신 대로, vacuum 이 빈 페이지를 file manager 의 partial sector table 로 되돌리는 방식입니다. 화이트보드(bestspace)는 지금처럼 빠른 힌트로 계속 쓰고, "비었다"는 사실의 보관은 영구 장부에 맡기는 역할 분담입니다.

⚠️ 정직한 한계 — 디스크 사용량 자체가 줄지는 않는다

file_perm_dealloc 는 sector 를 디스크 관리자(disk manager)에게 반환하지 않습니다 (반환은 file_destroy, 즉 DROP TABLE 경로에서만 일어남). 그래서 이 제안이 줄여 주는 것은 OOS 파일의 확장 빈도이지, 이미 점유한 디스크 총량이 아닙니다. 다른 파일이 그 공간을 가져갈 수 있게 되는 것도 아닙니다. (이 구분은 초안 리뷰에서 바로잡힌 부분으로, 이슈 본문에 경위가 기록되어 있습니다.)

4. 제안 설계 — 어떻게 동작하나

4-1. 새 함수 하나: oos_try_reclaim_empty_page

페이지 회수의 실제 동작(mechanic)은 storage 레이어의 helper 함수 한 곳에 모읍니다. 이름의 try 가 중요합니다 — 실패해도 괜찮고, 여러 번 불려도 안전(멱등, idempotent)해야 합니다.

그림 2 — helper 내부의 4단계 안전 체크
oos_try_reclaim_empty_page (oos_vfid, vpid) "이 페이지, 비었으면 장부에 되돌려 줘" 요청
↓
① 사용 중인 슬롯이 있나? 하나라도 있으면 → 아무것도 안 하고 정상 종료 (동시 INSERT 가 이미 재사용했을 수도 있음 — 정상 상황)
↓ 비어 있음
② 파일의 첫 페이지(sticky first page)인가? OOS 파일 헤더가 사는 페이지는 절대 회수하면 안 됨 → 맞으면 정상 종료

③ file_dealloc (FILE_OOS) 파일 관리자의 partial sector table 에 "빈 페이지"로 영구 등록. 실제 반영은 WAL 의 postpone(RVFL_DEALLOC) 메커니즘으로 커밋 시점에 안전하게 처리
↓
④ bestspace cache 에서 이 페이지 메모 삭제 회수된 페이지를 화이트보드가 계속 가리키면 안 되므로 oos_stats_del_bestspace_by_vpid 재사용. 단, 이 함수는 글로벌 해시 캐시만 지운다 — 헤더 페이지의 best[10] 배열은 남는다 (§5 의 "추가 발견 ①" 참고)

4-2. 누가, 언제 부르나 — 세 명의 호출자

"언제 검사할지"(trigger)는 호출자 책임입니다. OOS 값을 지우는 경로는 세 곳이고, 각 경로의 batch 경계(한 묶음 처리가 끝나는 지점)에서 한 번씩 부릅니다. 상자 하나 지울 때마다 부르면(핫루프 안) 비용이 O(지운 상자 수)가 되지만, 묶음 끝에서 부르면 O(건드린 선반 수)로 줄기 때문입니다.

호출자 (현재 코드 기준 이름)언제 동작하나helper 호출 시점

호출자 공통 패턴 (4단계):
  1. 기존 oos_delete 루프는 그대로 둔다.
  2. 루프를 도는 동안 "건드린 페이지(VPID)" 목록을 모아 둔다.
  3. 루프가 끝나면 목록의 페이지마다 oos_try_reclaim_empty_page 를 부른다.
  4. helper 가 실패해도 경고만 남기고 vacuum 은 계속 간다 — 회수 못 한 페이지는 다음 vacuum 사이클의 후보로 남으면 충분하다.
그림 3 — 전체 흐름: 슬롯 회수(기존) 위에 페이지 회수(신규)를 얹는다
vacuum: oos_delete 루프 죽은 OOS 값들의 상자(청크)를 슬롯 단위로 삭제 — 이미 구현됨 (CBRD-26609/26668). 건드린 페이지 목록을 옆에 적어 둠
↓ batch 끝
신규: 건드린 페이지마다 oos_try_reclaim_empty_page 완전히 빈 페이지만 골라 file_dealloc → 창고 장부(partial sector table)에 등록
↓ 나중에 새 OOS 값 INSERT
file_alloc 이 장부에서 빈 페이지를 발견 → 재사용 화이트보드(bestspace)가 어떤 상태이든 — 꽉 찼든, 재시작 직후든 — 상관없음. 파일 확장이 일어나지 않음

4-3. 곁들여 정리되는 것들

  • 죽은 함수 oos_remove_page (oos_file.cpp:1104, 선언 oos_file.hpp:102)는 새 helper 가 상위 호환(superset)이므로 삭제. TODO 주석도 함께 제거.
  • oos_delete 헤더 주석(oos_file.cpp:2304)의 "Empty pages will be reclaimed by vacuum…" 을 helper 이름을 명시하는 문장으로 갱신.

5. 아직 확정 안 된 것들 — Open Questions (Q1~Q5)

아래 다섯 가지는 ANALYSIS 단계에서 확정할 항목입니다. 각각에 이슈의 잠정 권고가 있지만, 모두 아직 최종 결정이 아닙니다.

질문쉬운 설명잠정 권고 (미확정)
Q1. 복구(recovery) 호환성 file_dealloc 는 "커밋되면 그때 실제로 지워라"라는 예약(postpone) 방식으로 동작합니다. vacuum worker 의 트랜잭션 모델에서 이 예약이 제때 실행되는지, 크래시 후 복구와 충돌하지 않는지, 비교적 신참 파일 타입인 FILE_OOS 의 복구 분기가 다른 타입과 똑같이 동작하는지 확인이 필요합니다. 코드 정독 + 크래시 주입 테스트로 세 항목 모두 검증
Q2. 호출 묶음 단위 helper 를 레코드마다 부를지(A), heap 페이지마다(B), vacuum 로그 블록마다(C) 부를지. 자주 부르면 페이지 fix 비용이, 늦게 부르면 빈 페이지 방치 시간이 늘어납니다. vacuum 은 A(per-record)로 시작해 측정 후 B 승격 검토, SA_MODE 는 A(per-UPDATE) 고정
Q3. "건드린 페이지" 목록 자료구조 목록 크기가 보통 한 자릿수~수십 개라, 정렬된 set 보다 단순 vector 가 빠를 수 있습니다. std::vector + 호출 직전 sort/unique
Q4. 멱등성(idempotency) vacuum worker 가 도중에 죽으면 같은 블록을 다시 처리합니다. 그래서 ① 이미 회수된 페이지 ② 그 사이 다른 INSERT 가 재점유한 페이지 ③ 첫 페이지 강제 호출 — 세 경우 모두 에러 없이 조용히 통과해야 합니다. helper 내부에서 세 경우 전부 NO_ERROR 로 흡수 (4-1 의 ①·② 체크가 그 장치)
Q5. 실측 게이트 진행 조건 "bestspace 한계가 실제 워크로드에서 정말 문제인가?"를 측정으로 증명해야 합니다. ① 캡 도달 시나리오 ② 재시작 직후 시나리오 ③ UPDATE 폭주 시나리오에서 helper 도입 전/후의 OOS 파일 페이지 수·확장 빈도를 비교합니다. 효과가 유의미하면 진행, 미미하면 Won't Fix + 죽은 함수 정리만 minor 패치

추가 발견 — 코드 분석에서 확인된 두 가지 갭 (2026-08-05, Q1/Q4 에 편입 권장)

이 문서 작성 중 커밋 07fef9d48 의 bestspace 코드를 직접 읽으면서, helper 의 캐시 퇴출(④)만으로는 닫히지 않는 구멍 두 개를 확인했습니다. 둘 다 JIRA 이슈 본문에는 아직 없는 내용이므로, ANALYSIS 단계에서 Q1/Q4 와 함께 다뤄야 합니다.

🔍 추가 발견 ① — 헤더 페이지의 best[10] 배열은 퇴출되지 않는다

oos_stats_del_bestspace_by_vpid (oos_file.cpp:396) 는 글로벌 해시 캐시(vpid_ht / vfid_ht)의 엔트리만 제거합니다. 그런데 힌트는 한 군데 더 있습니다 — OOS 헤더 페이지에 persist 되는 best[10] 배열(OOS_HDR_STATS)입니다. 이 배열은 그대로 남기 때문에, 페이지 탐색(oos_stats_find_page_in_bestspace)의 Phase B (best[] 스캔)가 이미 회수된 페이지의 VPID 를 후보로 반환할 수 있습니다.

문제는 후보 페이지를 잡는 Phase C 가 plain OLD_PAGE fix 를 쓴다는 점입니다 — dealloc 된 페이지에 대한 plain OLD_PAGE fix 는 debug 빌드에서 assert 에 걸립니다 (page_buffer.c:2358-2377, ADR-0001 이 명시한 dead-page tripwire). release 빌드는 에러 후 skip 으로 살아남지만 debug 는 죽습니다. 대응 후보: (a) helper 가 헤더 페이지의 best[] 항목도 함께 purge (헤더 페이지 fix 필요), (b) lookup 의 방어적 skip 에 맡기고 tripwire 정책을 조정 — 어느 쪽이든 ANALYSIS 에서 확정 필요.

🔍 추가 발견 ② — postpone 타이밍 레이스 (퇴출 후 재등록 창)

file_dealloc 는 RVFL_DEALLOC postpone 방식이라 실제 dealloc 은 커밋 시점(run-postpone)에 일어납니다. 즉 helper 가 캐시를 지운 뒤 ~ postpone 실행 사이의 구간에서 그 페이지는 "아직 유효하고 텅 빈" 상태입니다. 이 창에서 동시 실행 중인 Tier-3 sync (oos_stats_sync_bestspace)가 그 페이지를 발견하고 캐시에 다시 등록할 수 있습니다 — 그러면 dealloc 이 완료된 뒤 스테일 엔트리가 재발합니다.

조기 퇴출 자체는 항상 안전합니다 (힌트를 잃는 방향의 오류는 성능 손해뿐). 위험한 것은 재등록으로 힌트가 잘못 남는 방향이며, 이 창을 완전히 닫으려면 sync 측 고려(예: dealloc 예약된 페이지 스킵, 또는 발견 ①과 같은 방어 정책)가 함께 필요합니다. Q1 (postpone 호환성) · Q4 (멱등성) 검증 항목에 편입을 권장합니다.

📎 선행 조건 — ADR-0001 (non-numerable 전환)이 본 이슈보다 먼저

FILE_OOS 는 현재 numerable 로 생성됩니다 (oos_file.cpp:982). numerable 파일에서 페이지 dealloc 은 user page table 에 mark-delete 만 쌓고, 본 이슈가 dealloc churn 을 만들면 file_numerable_find_nth 가 per-call O(n) slow path 로 밀려납니다 (find_nth 캐시는 temp 파일 전용이라 OOS 는 사용 불가). 그래서 ADR-0001 은 vacuum caller 를 연결하기 전에 non-numerable + sector-bitmap walk 로 전환하기로 결정했습니다 — 보존할 live dealloc 경로가 없을 때 마이그레이션이 가장 쉽습니다. 전환으로 잃는 기능은 OOS 가 쓰지 않는 것뿐이고 (nth 순서 보장, truncate), 페이지 할당마다 붙던 user-page-table append + WAL 이 사라져 오히려 순이득입니다. 해당 구현은 oos-m2-all-plans-experimental 브랜치에 있으며 아직 feat/oos 에 merge 되지 않았습니다 (관측 counter 미추가).

🔭 참고 — 이 이슈가 완성하는 그림

이 이슈가 끝나면 OOS 페이지의 생애 주기가 완성됩니다: INSERT (페이지 할당) → DELETE/UPDATE (슬롯 회수, 완료) → 빈 페이지 회수 (본 이슈) → DROP TABLE (파일 통째 회수, 완료). 또한 먼 미래에 disk manager 가 sector 단위 반환을 지원하게 되면, 본 helper 의 효과는 "확장 빈도 감소"에서 "디스크 사용량 감소"로 확장될 수 있습니다 (별도 후속 이슈).
