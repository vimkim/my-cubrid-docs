## 원인 분석

### 1. `cbrd_25637_recovery`: DBLink 2PC coordinator 복구 TC가 엔진 수정보다 먼저 들어옴

- **관찰**
  - core 7개의 stack은 모두 종료 경로에 있다. `log_2pc_commit_first_phase ()` → `fi_handler_exit ()` → `exit ()` 다음, `boot_shutdown_server_at_exit ()` → `log_final ()` 에서 heap 해제가 깨진다(`malloc_printerr`, `logtb_tran_free_update_stats ()` 또는 `log_prior_inflight_finalize ()`). 같은 시각에 다른 thread(`concurrency_slot_daemon_task`)도 해제된 상태를 읽다가 core를 남긴다.
  - fault injection이 commit 도중 worker thread에서 `exit ()` 를 불러, 다른 thread가 살아 있는 채로 exit handler가 서버를 정리한다.
  - page buffer(`pgbuf_*`) 프레임은 stack에 없다.
- **Baseline**: merge base `0eec910fc1` 의 develop run [45848728067](https://github.com/CUBRID/cubrid/actions/runs/45848728067)에서 이 testcase 하나만 error로 실패한다. TC `ed2232670`(#5127)는 head TC와 baseline TC 모두에 들어 있다.
- **이력(`cubrid-tcr show`)**: 상태 FAILING. 2026-11-26 06:43Z 처음 실패한 뒤 실패 78번, 통과 1번(그중 develop 72번). 여러 PR(#8771, #8675, #8782, #8772, #8780, #8786 등)의 서로 다른 엔진 커밋에서 실패했다. 처음 실패한 시점은 TC #5127이 머지된 2026-11-26 05:56Z 직후다.
- **추론**: TC가 요구하는 엔진 동작(CBRD-28361, PR #8725 "Replay undelivered DBLink 2PC decisions on every server start")이 아직 develop에 없다. 그래서 develop을 base로 하는 모든 PR에서 실패한다.
- **모르는 것**: 이 core들이 PR #8725 머지 후에 사라지는지는 확인하지 않았다. FI `exit ()` 경로의 종료 경합이 별도 결함인지도 확인하지 않았다.
- **반증 조건**: PR #8725 머지 후의 develop에서도 같은 core가 계속 나면, 이 실패는 #8725로 해결되지 않는다. 별도 이슈로 다뤄야 한다.
- **다음 행동**: PR #8725 머지를 기다린다. 머지 후 develop run에서 이 testcase가 통과하는지 확인한다.
