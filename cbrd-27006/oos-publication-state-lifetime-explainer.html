CBRD-27006 · 쉬운 한국어 설명

OOS insert publication 상태는 왜 “시작할 때” 비워야 할까?

코드부터 보지 않고, 두 개의 임시 메모장이 어떻게 한 쌍으로 움직이는지부터 설명합니다. 그다음 현재 코드의 빈틈, 안전한 수정 위치, 그리고 LOG_TDES가 없을 때의 선택을 차례로 봅니다.

대상: PR #7391 리뷰 확인한 HEAD: 840e5e904 핵심: 임시 상태의 수명 OOS 데이터 형식 변경 없음
한 줄 결론 OOS부터 두 메모장 왜 따로 보관? 정상 흐름 문제 흐름 수정 원칙 LOG_TDES 테스트 용어
00

먼저, 한 줄로 결론부터

이 문서의 나머지 내용은 아래 한 문장을 자세히 풀어 설명한 것입니다.

🧹
새로운 논리 OOS insert 준비를 시작하면, 실패할 수 있는 일을 하기 전에 이전 작업의 임시 메모 두 개를 함께 비워야 합니다. 그래야 새 작업이 중간에 실패해도 “이전 작업의 정보가 새 작업의 정보처럼 남아 있는 상태”가 되지 않습니다.
비우는 대상

OOS 파일의 실제 데이터가 아니라, 나중에 replication log를 만들 때 쓸 임시 목록 두 개입니다.

비우는 시점

OOS 값 저장 직전이 아니라, vector 준비와 값 직렬화보다도 앞선 논리 작업의 시작점입니다.

성공했을 때

새로 쌓인 임시 정보는 바로 비우면 안 됩니다. 기존 replication consumer가 사용할 때까지 남겨야 합니다.

가장 흔한 오해: 여기서 clear()는 OOS 파일에 저장한 큰 값을 삭제하지 않습니다. 주소와 WAL 위치를 적어 둔 임시 메모만 비웁니다.
01

OOS는 큰 값을 heap record 밖에 두는 기능입니다

먼저 왜 OOS OID라는 주소가 필요한지 이해해 봅시다.

Heap record 안

자주 읽는 작은 정보와 16바이트짜리 OOS inline stub이 있습니다.

id = 10 name = Kim OOS inline stub 16B
→

OOS file 안

실제 큰 column 값은 별도의 OOS value chain에 저장됩니다.

큰 BIT VARYING / VARCHAR 등의 실제 값
Heap record의 OOS inline stub에는 head OOS OID와 전체 길이가 들어 있습니다. head OOS OID는 “OOS file의 어디에서 이 값이 시작하는가”를 나타내는 물리 주소입니다.
02

핵심 등장인물: 순서가 맞아야 하는 두 개의 임시 메모장

코드 이름은 어렵지만 역할은 단순합니다. 왼쪽과 오른쪽의 같은 번호끼리 한 쌍입니다.

메모장 A — “무엇을 저장했나?” worker thread 소유

thread_p->oos_oids

1column A의 head OOS OID
2multi-chunk 경계용 NULL marker
3column B의 head OOS OID
↔
메모장 B — “어느 WAL 기록인가?” transaction 소유

tdes->oos_insert_lsa_queue

1column A OOS insert의 WAL LSA
2multi-chunk dummy WAL LSA
3column B tail-chunk WAL LSA
왜 반드시 한 쌍인가? 나중에 replication record를 만들 때 메모장 A에서 OID 하나를 읽고, 메모장 B에서 그에 대응하는 LSA 하나를 꺼냅니다. 개수나 순서가 어긋나면 “어떤 OOS 값이 어느 WAL 기록과 연결되는가”를 신뢰할 수 없습니다.

누가 OID를 적는가?

oos_insert()와 oos_insert_many() 같은 public OOS insert API가 성공한 head OOS OID를 적습니다.

누가 LSA를 적는가?

OOS WAL 처리 코드가 대응하는 LSA를 transaction의 queue에 적습니다. 작성자는 나뉘지만 결과는 한 쌍입니다.

03

왜 하나는 thread_p에 있고, 하나는 LOG_TDES에 있을까?

두 정보가 만들어지고 사용되는 subsystem이 서로 다르기 때문입니다. 먼저 각 owner의 역할부터 분리해 봅시다.

thread_p = 지금 일을 하는 worker의 작업 가방

현재 request를 실행하면서 잠깐 필요한 page, lock, query, locator 관련 상태를 들고 다닙니다. 같은 worker thread는 request가 끝난 뒤 다른 client/transaction의 일을 맡도록 재사용될 수 있습니다.

실제로 css_set_thread_info()는 worker가 새 request 정보를 받을 때 thread_p->oos_oids.clear()를 실행합니다.
LOG_TDES = transaction의 로그 서류철

transaction index, 현재 WAL tail LSA, replication record, insert/update 대상 LSA처럼 transaction logging과 함께 움직여야 하는 상태를 보관합니다. worker 자체가 아니라 transaction에 붙어 있습니다.

실제로 oos_insert_lsa_queue는 repl_insert_lsa, repl_update_lsa, repl_records 옆에 있으며 TDES 초기화/정리 때 clear됩니다.

각 정보를 실제로 누가 만들고 누가 쓰는지 보면 더 명확합니다

정보만드는 쪽사용하는 쪽그래서 선택된 owner

중요한 구분 — “어디에 보관하는가”와 “언제까지 유효한가”는 같은 질문이 아닙니다.
OID는 worker 객체에, LSA는 transaction 객체에 보관하는 것이 각 subsystem에는 자연스럽습니다. 하지만 이번 OOS insert에서 두 값이 한 쌍으로 유효한 기간은 더 짧습니다. 즉, 한 번의 논리 OOS insert 준비가 시작해서 consumer가 사용할 때까지입니다. 더 오래 사는 owner 안에 들어 있다고 해서 이전 논리 작업의 값까지 계속 유효한 것은 아닙니다.
왜 둘 다 thread_p에 두지 않나?
LSA는 현재 transaction의 WAL 순서와 replication record에 결합됩니다. 재사용되는 worker에만 붙이면 transaction log 상태와 owner가 어긋나고, log manager가 worker scratch의 수명까지 알아야 합니다.
왜 둘 다 LOG_TDES에 두지 않나?
OOS OID 목록은 현재 record의 inline stub fixup과 locator 실행에 쓰는 짧은 scratch입니다. TDES에 넣으면 transaction log 계층이 record/locator 작업 상태까지 떠안고, request 사이에 실행-local OID가 남을 범위도 커집니다.
역사적 근거의 한계: 두 필드는 OOS replication POC commit 60312494d에서 함께 추가됐습니다. commit에는 위 선택을 장문으로 설명한 ADR은 없습니다. 위 설명은 현재 코드의 owner, 초기화 지점, producer, consumer를 대조해 확인한 설계 의도입니다. 이 분리 자체가 버그라는 뜻은 아닙니다. 분리된 두 상태의 논리 수명을 함께 관리하지 못한 것이 이번 문제입니다.
04

문제가 없는 정상 흐름을 먼저 봅시다

1
새 논리 작업을 시작합니다 이전 작업의 메모가 남아 있지 않도록 두 메모장을 비웁니다.
OID [] · LSA []
2
row A의 첫 번째 큰 값을 저장합니다 OOS insert와 WAL 기록이 성공하여 양쪽 메모장에 1번 항목이 생깁니다.

3

06

실제로 어떤 “찜찜한 상태”가 남는가?

row A가 끝난 뒤 row B를 시작하는 상황을 순서대로 따라가 봅시다.

A
직전 row A가 OOS 저장에 성공했습니다 아직 consumer가 사용할 수 있도록 A의 OID/LSA가 남아 있습니다.
OID [A] · LSA [LA]
B1
새로운 row B의 논리 OOS 준비를 시작합니다 하지만 현재 코드는 아직 두 메모장을 비우지 않았습니다.
여전히 OID [A] · LSA [LA]
B2
row B의 값 직렬화에서 오류가 납니다 함수는 현재 late reset에 도달하기 전에 실패를 반환합니다.
B 실패
B3
row B 작업은 끝났는데 메모에는 row A 정보가 남습니다 이것이 “publication 상태의 수명이 논리 작업 경계와 맞지 않는다”는 뜻입니다.
stale: OID [A] · LSA [LA]
리뷰가 증명한 것: early return 뒤에 이전 publication 상태가 남을 수 있습니다. 즉, 방어적으로 지켜야 할 clean-start invariant가 현재 코드 구조에서 깨집니다.
리뷰가 아직 증명하지 못한 것: 남은 A 상태가 실제 후속 consumer에게 소비되어 곧바로 잘못된 replication이나 데이터 손상을 만든다는 구체적 경로는 제시되지 않았습니다.
따라서 판단은 두 문장으로 나눠야 합니다. “상태 수명 버그가 있다”는 맞고, “현재 재현 가능한 P1 데이터 손상이다”는 근거가 부족합니다. 심각도를 과장할 필요는 없지만 invariant는 명확히 고치는 편이 안전합니다.
07

수정은 “clear 두 줄 이동”이 아니라 소유권 이동입니다

무엇을 언제 누가 비우는지 논리 작업 단위로 정해야 합니다.

현재: downstream helper가 늦게 reset

논리 작업 시작
reserve 실패 가능
직렬화 실패 가능
class/VFID lookup 실패 가능
그제야 두 목록 clear
OOS insert
→

수정: 논리 작업 시작점이 reset

LOG_TDES 확인
두 목록 함께 clear
reserve
직렬화
class/VFID lookup
OOS insert
확정한 방향: heap-record transform 경로에서는 heap_attrinfo_insert_to_oos() 시작부가 OOS-owned strict helper를 호출하여 start reset을 정확히 한 번 소유합니다. 이후의 heap_oos_insert_serialized_values()는 lookup과 insert만 담당하며 늦은 중복 reset은 제거합니다.

그렇다면 모든 종료 지점에서 clear하면 될까요? 아니요.

① 전체 성공

새 OID/LSA 짝이 정상적으로 만들어졌습니다.

비우지 않고 consumer까지 유지
② publication 전 실패

reserve, 직렬화, lookup 중 하나가 실패했습니다.

시작할 때 이미 비웠으므로 빈 상태
③ 일부 publication 후 실패

앞 request는 성공했고 뒤 request가 실패했습니다.

현재 작업의 두 목록 clear + transaction abort
start reset과 partial-failure cleanup은 서로 다른 책임입니다. 시작 reset을 새로 추가했다고 해서 oos_insert_many()의 부분 성공 후 실패 정리를 없애면 안 됩니다. 이미 저장된 OOS chunk는 기존 계약대로 transaction abort 때 WAL undo로 되돌립니다.

오류 정리는 scope_exit로 표현하면 더 깔끔합니다

scope_exit가 잘 맞는 위치

oos_insert_many()가 모든 request를 먼저 검증한 직후 guard를 만듭니다. 그 뒤 physical insert 도중 어느 error return으로 빠져도 guard가 현재 작업의 OID/LSA publication 상태를 함께 비웁니다.

scope_exit로 대체할 수 없는 것

새 논리 작업 시작 전 stale 상태를 버리는 start reset은 여전히 필요합니다. downstream 함수의 error-exit guard만으로는 vector reserve와 직렬화가 시작되는 순간에 이전 상태가 그대로 남습니다. 

// oos_insert_many(): request validation은 먼저 끝낸다.
validate_all_requests (requests);

// 이 지점부터 physical insert가 OID 또는 LSA를 일부 publication할 수 있다.
scope_exit clear_publication_on_error ([&] ()
{
  oos_clear_insert_publication_state (thread_p);
});

for (oos_insert_request &request : requests)
  {
    if (insert_request (request) != NO_ERROR)
      {
        return error;   // guard 실행: 현재 partial publication clear
      }
  }

clear_publication_on_error.release ();
return NO_ERROR;        // 성공 publication은 consumer에게 넘김
왜 request 검증 뒤에 guard를 설치할까? 사전 검증 단계는 아직 OID나 WAL LSA를 만들지 않습니다. 실제 publication 가능 구간에만 guard를 두면 기존 계약을 넓히지 않으면서, physical insert 이후의 모든 error return을 하나의 정리 규칙으로 묶을 수 있습니다.
08

LOG_TDES가 없으면 왜 선택이 필요할까?

여기가 현재 grill에서 확인이 필요한 다음 설계 결정입니다.

메모장 A는 worker 가방 안에 있습니다

thread_p->oos_oids는 현재 worker thread에서 바로 접근할 수 있습니다.

메모장 B는 transaction 서류철 안에 있습니다

tdes->oos_insert_lsa_queue에 접근하려면 현재 transaction의 LOG_TDES를 먼저 찾아야 합니다.

만약 LOG_FIND_TDES()가 NULL을 반환하면 transaction 서류철 자체를 찾지 못한 것입니다. 메모장 A에는 접근할 수 있지만 메모장 B는 확인하거나 비울 수 없습니다. 즉, “두 메모장을 함께 비웠다”고 말할 수 없습니다.
권장: 둘 다 비우거나, 둘 다 건드리지 않기

먼저 LOG_TDES를 검증합니다

  • LOG_TDES가 있으면 두 목록을 함께 clear합니다.
  • 없으면 기존 fatal ER_LOG_UNKNOWN_TRANINDEX를 설정합니다.
  • 실패를 반환하고 transaction 경로를 즉시 중단합니다.
  • 두 목록을 함께 reset했다는 거짓 인상을 만들지 않습니다.
VS
비권장: 접근 가능한 A만 비우기

oos_oids만 먼저 clear합니다

  • OID 목록은 비었지만 LSA queue 상태는 알 수 없습니다.
  • 하나의 paired state가 반쪽만 reset됩니다.
  • 호출자가 reset 성공으로 오해하기 쉬워집니다.
  • fatal 오류 뒤에도 계속 진행할 수 있다는 잘못된 신호가 됩니다.
// 개념을 보여 주기 위한 예시입니다. 실제 이름/return type은 local style에 맞춥니다.
SCAN_CODE heap_oos_begin_insert_publication (THREAD_ENTRY *thread_p)
{
  LOG_TDES *tdes = find_current_tdes (thread_p);

  if (tdes == NULL)
    {
      set_fatal_error (ER_LOG_UNKNOWN_TRANINDEX);
      return S_ERROR;   // 두 목록을 reset했다고 가장하지 않음
    }

  thread_p->oos_oids.clear ();
  tdes->oos_insert_lsa_queue.clear ();
  return S_SUCCESS;
}
“둘 다 건드리지 않는다”는 계속 진행한다는 뜻이 아닙니다. 오히려 정상적인 paired reset이 불가능한 fatal invariant 오류임을 분명히 하고 즉시 멈춘다는 뜻입니다. 이것이 현재 권장안입니다.
09

수정 후 각 함수의 책임은 이렇게 나뉩니다

책임을 섞지 않으면 중복 clear와 너무 이른 clear를 모두 피할 수 있습니다.

위치맡는 책임맡지 않는 책임
heap_attrinfo_insert_to_oos() 논리 heap OOS 준비의 시작 경계. strict reset helper를 첫 fallible step 전에 호출. transaction 내부 container를 직접 조작하지 않음.
새 OOS-owned strict helper 현재 LOG_TDES 조회/검증과 paired state의 start reset. class/VFID lookup이나 실제 OOS insert를 하지 않음.
heap_oos_insert_serialized_values() class heap 정보, OOS VFID 조회/생성, prepared request insert. 같은 논리 경로의 publication 상태를 늦게 다시 clear하지 않음.
oos_insert_many() request 순서대로 publication. 검증 뒤 설치한 scope_exit가 physical-insert 오류 시 현재 publication을 정리하고, 전체 성공 시 release(). heap-level 논리 작업의 시작 reset을 소유하지 않음.
기존 replication consumer 성공한 OID/LSA 짝을 순서대로 소비. 새로운 lifetime 규칙 때문에 format이나 소비 순서를 바꾸지 않음.
10

테스트는 무엇을 보여 줘야 할까?

그냥 helper를 직접 호출해 clear() 결과만 보는 것으로는 “올바른 위치에서 실행됐다”는 사실을 증명할 수 없습니다.

상황테스트 준비반드시 확인할 결과
start reset 기본 계약 알아보기 쉬운 가짜 OOS OID와 LSA를 두 목록에 미리 넣습니다. strict helper 성공 후 두 목록이 함께 비고, 이후 정상 insert는 새 결과를 다시 publication합니다.
class/OOS-file lookup 실패 stale 값을 넣은 뒤 잘못된 class 등으로 deterministic lookup 실패를 만듭니다. lookup이 실패했어도 그보다 앞선 start reset 덕분에 두 목록이 이미 비어 있습니다.
더 이른 request 준비 실패 전역 allocator failpoint 대신 좁은 test bridge 또는 유지 가능한 직렬화 실패 seam을 사용합니다. reserve/직렬화 경계보다 먼저 reset됐음을 실제 논리 entry를 통해 확인합니다.
일부 publication 후 실패 여러 request 중 하나 이상을 성공시킨 뒤 다음 physical insert를 실패시킵니다. OID와 LSA 목록이 모두 비고, 이미 기록한 OOS chunk는 transaction abort 계약을 유지합니다.
정상 성공 non-regression single-chunk와 multi-chunk 값을 섞어 batch insert합니다. attribute 순서, NULL dummy/head OID pairing, 성공 publication 유지, locality가 그대로입니다.
기존 unit_tests/oos/test_oos_server.cpp는 SERVER_MODE라 THREAD_ENTRY와 LOG_TDES를 모두 사용할 수 있습니다. 또한 이미 mixed single/multi-chunk publication 순서를 검사하므로 이번 paired-state regression을 붙이기 좋은 위치입니다.
11

마지막으로 용어를 짧게 정리합니다

같은 말을 서로 다른 뜻으로 쓰면 lifetime 논의가 다시 흐려집니다.

OOS insert publication 성공한 OOS insert 결과를 나중의 replication logging이 사용할 수 있도록 등록하는 행위입니다.
OOS insert publication 상태 논리 OOS insert 하나에 대해 순서대로 짝을 이루는 OOS OID entry와 WAL LSA의 임시 상태입니다.
논리 OOS insert 준비 한 heap record에서 OOS로 선택된 attribute들을 준비하고 저장해 하나의 coherent publication 상태를 만드는 작업입니다.
start reset 새 논리 작업의 첫 fallible step 전에 이전 작업의 publication 상태를 버리는 정리입니다.
partial-failure cleanup 현재 작업이 일부 결과를 publication한 뒤 실패했을 때 그 현재 결과를 버리는 정리입니다.
publication이 아닌 것 commit, 사용자 공개, 네트워크 전송, OOS file의 실제 데이터 삭제를 뜻하지 않습니다.
12

현재 grill 결정 상태

확정한 내용은 이미 glossary와 CBRD-27006 설계 문서에 반영했습니다.

확정됨

●publication 상태는 OOS OID entry와 WAL LSA의 ordered pair입니다.
●두 entry의 생산자는 나뉘어도 수명은 하나의 상태로 관리합니다.
●heap 경로의 논리 OOS 준비 시작점이 start reset을 소유합니다.
●oos_insert_many()의 partial-failure cleanup은 유지합니다.
●partial-failure cleanup은 request 검증 뒤의 scope_exit로 묶고, 전체 성공 시 release()합니다.
●성공 publication은 consumer가 사용할 때까지 유지합니다.

다음 확인 필요

●LOG_TDES가 없으면 fatal 실패로 중단하고 두 목록 모두 건드리지 않는 all-or-nothing reset을 채택할지.
●strict helper의 정확한 layer/name과 독립 scalar 경로의 재사용 범위.
●request 준비와 partial-publication 실패에 사용할 최소 deterministic test seam.
