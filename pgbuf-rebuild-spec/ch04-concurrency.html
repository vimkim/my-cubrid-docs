4장 — 동시성 프로토콜

3장이 "무엇이 있는가"라면 이 장은 "누가 언제 무엇을 만질 수 있는가"다. 5장 이후의 의사코드는 전부 이 장의 규칙을 전제로 쓰여 있으므로, 여기 규정된 락 순서와 부여 규칙을 어기면 알고리즘이 글자 그대로 맞아도 동작하지 않는다.

이 장의 큰 그림 CUBRID 페이지 버퍼의 동시성 설계는 세 층이다. ① 무잠금 층 — 읽기 전용 fix/unfix의 대부분은 어떤 뮤텍스도 잡지 않고 64비트 latch 워드 하나에 대한 CAS로 끝난다. ② 뮤텍스 층 — 그 조건을 못 맞추면 버킷/BCB/LRU 뮤텍스로 내려간다. 여기서 락 순서가 중요해진다. ③ 대기 층 — 그래도 안 되면 스레드가 잠들고, 데드락 감지기 없이 타임아웃만으로 깨어난다. 층을 내려갈수록 비용이 커지므로, 이 장의 규칙 대부분은 "어떻게 하면 위층에 머무를 수 있는가"에 관한 것이다.

4.2 락 획득 순서 규칙

MUST — 최상위 순서 규칙 MUST 버킷 hash_mutex를 보유한 채 어떤 BCB 뮤텍스에도 블로킹하지 않는다. BCB 뮤텍스가 필요하면 trylock만 시도하고, EBUSY면 먼저 버킷 뮤텍스를 놓고 무조건 획득으로 전환한다. 이 규칙 하나가 해시-BCB 사이의 사이클을 원천 차단한다.

  • 반환값 ≠ NULL ⇒ 호출자는 BCB 뮤텍스를 보유하고 버킷 뮤텍스는 보유하지 않는다.
  • 반환값 = NULL ⇒ 호출자는 버킷 뮤텍스를 보유한다.
이 비대칭이 의도적인 이유: 미스일 때 버킷 뮤텍스를 이미 쥐고 있으므로 재획득 없이 곧바로 buffer lock 프로토콜(§4.6)로 진입할 수 있다. 재작성 시 "항상 락을 놓고 반환"으로 정리하고 싶은 유혹이 크지만, 그러면 미스 경로에 창(window)이 생겨 두 스레드가 동시에 같은 페이지의 팻말을 세울 수 있다.

무잠금 체인 순회가 안전한 이유: 체인에서 BCB를 떼어내는 쪽 (pgbuf_delete_from_hash_chain)은 버킷 뮤텍스를 잡고 unlink한 뒤에야 VPID를 NULL로 만든다(page_buffer.c:7917-7919). 순회자가 볼 수 있는 최악은 이미 떨어져 나간 BCB를 계속 따라가는 것이고, 그 경우 VPID 재검증(④)에서 걸러진다. 반대로 놓칠 수는 있는데(삽입과 경합), 그건 미스로 처리되어 two_phase 혹은 buffer lock 경로에서 복구된다.

4.2.2 해시 삽입 — 분할된 임계 구역

MUST — 분할 임계 구역 MUST pgbuf_insert_into_hash_chain은 hash_mutex를 잡고 체인 head에 밀어 넣은 뒤 뮤텍스를 쥔 채로 반환한다. 해제는 곧바로 이어지는 pgbuf_unlock_page(..., need_hash_mutex = false)가 담당한다. page_buffer.c:7817-7823

왜 나눠야 하는가: 만약 삽입 함수가 뮤텍스를 놓으면, 그 틈에 buffer lock 대기자가 깨어나 재시도했을 때 페이지는 해시에 있는데 팻말도 아직 서 있는 중간 상태를 볼 수 있다. 하나의 임계 구역 안에서 "해시에 공개"와 "팻말 제거 + 전원 기상"을 함께 해야 그 중간 상태가 관측되지 않는다. 재작성 시 이 두 함수를 하나로 합치는 것은 MAY 허용되지만, 사이에서 뮤텍스를 놓는 것은 금지다.

삭제(pgbuf_delete_from_hash_chain) 규칙: MUST 호출자가 BCB 뮤텍스를 보유한 상태로 진입하고, BCB가 flush 중이면 삭제를 거부하며(page_buffer.c:7867-7876), unlink → hash_mutex 해제 → 그 다음에 VPID를 NULL로 만들고 count_fix_and_avoid_dealloc을 리셋한다(page_buffer.c:7917-7919). 순서를 뒤집어 VPID를 먼저 지우면 무잠금 순회자가 체인 중간에서 NULL VPID를 만나 페이지를 놓친다.

  3. condition == PGBUF_UNCONDITIONAL_LATCH

경로 자체는 page_buffer.c:7669-7732:

bcb = 무잠금 해시 체인 탐색 (버킷 뮤텍스 없음)
if (bcb == NULL) return NULL;               /* 슬로우 패스로 */

do {
    impl = get_impl (&bcb->atomic_latch);    /* 세 필드 일관 스냅샷 */
    if (impl.latch_mode != PGBUF_LATCH_READ  /* ① */
     || impl.waiter_exists                   /* ② */
     || impl.fcnt == 0                       /* ③ */
     || bcb->vpid != *vpid)                  /* ④ */
        return NULL;                         /* 슬로우 패스로 */
    new_impl = impl; new_impl.fcnt++;
} while (!CAS (bcb->atomic_latch, impl, new_impl));

holder 갱신 또는 신규 할당;
return page pointer;
안전 논증 주장: 이 경로는 BCB 뮤텍스도 버킷 뮤텍스도 잡지 않지만, 반환된 PAGE_PTR는 요청한 VPID의 유효한 READ-latched 페이지를 가리킨다.

① fcnt != 0이 안전의 닻이다. victim화의 필요조건은 fcnt == 0이다 (§3.2.1의 플래그 마스크와 별개로 pgbuf_is_bcb_fixed_by_any가 따로 검사한다, page_buffer.c:9210). CAS가 성공했다는 것은 그 순간까지 fcnt가 0이 된 적이 없다는 뜻이므로, 우리가 관측한 시점부터 증가시킨 시점 사이에 이 BCB가 회수되어 다른 페이지로 바뀌었을 수 없다. 즉 "살아 있는 READ latch는 BCB를 그 페이지에 고정시킨다".

② latch_mode == READ는 라이터 배제를 보장한다. 라이터가 들어오려면 fcnt가 0이 되어 idle이 되거나(①에 모순), 대기 큐에 서야 한다(그러면 waiter_exists가 켜져 ③에 걸린다).

③ !waiter_exists는 기아 정책을 유지한다. 이 검사가 없으면 무잠금 리더가 §4.3의 Case 1″(라이터 뒤에 서기)를 우회해 버려 라이터가 굶는다. 정확성이 아니라 공정성을 위한 조건이다.

④ VPID 재확인이 ABA를 막는다. 무잠금 체인 순회는 이미 체인에서 떨어진 BCB를 볼 수 있다. CAS 성공 전에 루프 안에서 VPID를 다시 보므로, 회수 후 다른 페이지로 재사용된 BCB를 잡는 일이 없다.

실패는 항상 안전하다. 어느 조건이든 어긋나면 NULL을 반환하고 §4.2의 정규 슬로우 패스로 내려간다 — 무잠금 경로는 순수한 최적화이며, 이를 아예 구현하지 않아도 정확성은 유지된다(성능만 크게 다르다).

4.4.2 unfix 쪽

page_buffer.c:7751-7774. 진입 조건은 latch_mode == READ ∧ !waiter_exists ∧ fcnt != 1이며, 통과하면 CAS로 fcnt--하고 BCB 뮤텍스와 LRU 장부 전체를 건너뛴다.

MUST — fcnt != 1 가드의 역할 MUST fcnt == 1(내가 마지막 unfixer)이면 반드시 슬로우 패스로 보낸다.

이유: fix count가 0이 되는 순간에만 해야 하는 일이 여럿이다 — LRU zone 전이/boost, MOVE_TO_LRU_BOTTOM 처리, 대기자 기상(§4.5), ASYNC_FLUSH_REQ 처리. 무잠금 경로가 fcnt를 1에서 0으로 떨어뜨려 버리면 이 작업들이 아무도 하지 않은 채 페이지가 idle이 된다. 대기 중이던 스레드는 영원히 깨어나지 못하고, BCB는 LRU 위치가 갱신되지 않아 교체 정책이 왜곡된다.

waiter_exists 검사만으로는 부족하다는 점에 주의: 대기자가 없어도 LRU 장부와 async flush 처리는 여전히 필요하다. 두 가드는 서로 다른 것을 지킨다.

MUST holder 쪽 정리(holder->fix_count--, 0이면 holder 반환)는 무잠금 시도 이전에 이미 끝나 있어야 한다. 즉 unfix의 순서는 holder 정리 → 무잠금 시도 → (실패 시) BCB 뮤텍스 + 슬로우 경로다. page_buffer.c:3116-3149

4.5.2 unfix 시 기상 정책

fix count가 0이 된 unfix에서만 호출되며, BCB 뮤텍스를 보유하고 {latch_mode == NO_LATCH, fcnt == 0}을 assert한 상태로 진입한다. page_buffer.c:7403-7535 큐를 head부터 훑으며 대기자 종류별로 처리한다.

큐 항목처리
NO_LATCH(포기자)큐에서 제거하고 계속 진행. 깨우지 않는다
LATCH_FLUSH건너뛴다(큐에 남긴다). SHOULD 이때 ASYNC_FLUSH_REQ가 켜져 있거나 실제 flush 중임을 assert한다 — 아니면 이 대기자는 영원히 안 깨어난다

MUST 부여 CAS 직전에 thread_lock_entry로 대기자 엔트리를 잠그고, 잠근 뒤 다시 한 번 request_latch_mode == NO_LATCH인지 확인한다 — 그 사이에 타임아웃으로 포기했을 수 있다. 포기했으면 부여를 취소하고 큐에서 제거한다. page_buffer.c:7467-7482

MUST — waiter_exists 화해 MUST 스윕이 끝나면 반드시 아래를 수행한다. page_buffer.c:7531-7534 
if (!pgbuf_is_exist_blocked_reader_writer (bufptr))
  {
    set_waiter_exists (&bufptr->atomic_latch, false);
  }
pgbuf_is_exist_blocked_reader_writer는 FLUSH 대기자를 무시한다 (page_buffer.c:10964-10984). 따라서 FLUSH 대기자만 남은 BCB는 waiter_exists = false가 되고, 이는 §4.4의 무잠금 읽기 경로를 다시 열어준다 — FLUSH 대기는 latch가 아니므로 리더를 막을 이유가 없다는 설계다.

이 화해를 빠뜨리면 §4.3의 idle 부여 CAS가 무한 스핀한다(CBRD-27084).

타임아웃/인터럽트 시의 부분 기상: 포기한 스레드가 큐 head였다면, 자기를 빼면서 뒤따르는 호환 리더들에게 latch를 넘겨준다(latch_mode == READ인 경우에 한해 fcnt += request_fix_count 후 기상). 라이터를 만나면 중단한다. page_buffer.c:7177-7221 MUST 이 함수는 세 경로 모두에서 BCB 뮤텍스를 보유한 채 반환하고, 해제는 호출자가 한다 — "빈 큐" 조기 반환 경로(page_buffer.c:7154-7158)도 예외가 아니다.

4.6 buffer lock — 미싱 페이지 팻말

미스가 났을 때 두 스레드가 같은 페이지를 두 번 읽어 두 BCB를 만드는 것을 막는 장치다. 디스크 IO 중에는 어떤 뮤텍스도 쥘 수 없으므로(규칙 R8), 뮤텍스 대신 팻말을 세운다.

pgbuf_lock_page는 hash_mutex를 보유한 채 진입하고 항상 보유하지 않은 채 종료한다. page_buffer.c:7935-8033

4.7 타임아웃과 데드락 정책

설계상 명시 — 페이지 latch 데드락 감지기는 없다 소스가 직접 밝힌다. page_buffer.c:7093-7100 
/* We do not guarantee that there is no deadlock between page latches.
 * So, we made a decision that when read/write buffer fix request is
 * not granted immediately, block the request with timed sleep method.
 * ...
 * When the request is waken up, the request is treated as a victim.  */
페이지 latch 데드락은 오직 타임아웃으로 해소되고, 타임아웃된 스레드가 지정 희생자다. (행/객체 락은 별개다 — 그쪽에는 src/transaction/wait_for_graph.c에 wait-for 그래프가 있다.) 이 사실이 pgbuf_ordered_fix(§4.8)의 존재 이유이기도 하다.

4.7.1 타임아웃 값 결정

충실 재현 대상 quirk MUST 다음 로직을 그대로 재현한다. page_buffer.c:7250-7262 
old_wait_msecs = wait_msecs = <트랜잭션의 wait_msecs>;
if (wait_msecs == LK_ZERO_WAIT || wait_msecs == LK_FORCE_ZERO_WAIT)
    wait_msecs = 0;
else
    wait_msecs = pgbuf_latch_timeout_msecs;   /* <-- 전역값으로 덮어씀 */
즉 zero-wait가 아닌 한 트랜잭션이 설정한 wait_msecs는 완전히 무시되고, 전역 pgbuf_latch_timeout_msecs(PRM_ID_PAGE_LATCH_TIMEOUT_IN_MSECS, 기본 300,000 ms = 5분)가 쓰인다. LK_INFINITE_WAIT를 요청해도 5분이다.
이는 사용자 관측 가능한 동작이므로 수정하지 말고 그대로 재현한다. 원래 값은 old_wait_msecs에 보관되어 오류 코드 선택에만 쓰인다.

관련해서 fix 프롤로그에도 quirk가 하나 더 있다: MUST 트랜잭션이 LK_ZERO_WAIT/LK_FORCE_ZERO_WAIT이면 무조건(unconditional) latch 요청이 조용히 조건부(conditional)로 강등된다. page_buffer.c:2273-2283

4.8 pgbuf_ordered_fix 순서 규약

데드락 감지기가 없으므로(§4.7), 여러 페이지를 동시에 latch해야 하는 코드는 전역 순서를 지켜야 한다. 적용 대상은 PGBUF_IS_ORDERED_PAGETYPE(ptype) = PAGE_HEAP || PAGE_OVERFLOW뿐이다(page_buffer.h:166-167) — 고전적인 heap home vs. heap overflow 순서 위험 때문이다.

MUST — 정렬 키는 VPID가 아니다 MUST 정렬 키는 (group_id, rank, vpid) 사전식이며, group_id가 NULL인 항목은 맨 뒤로 보낸다. page_buffer.c:12128-12183
  • group_id = 그 페이지가 속한 heap header의 VPID(PGBUF_WATCHER_SET_GROUP).
  • rank = PGBUF_ORDERED_HEAP_HDR < ..._HEAP_NORMAL < ..._HEAP_OVERFLOW.
  • vpid는 동점 처리용일 뿐이다.
즉 heap header가 항상 자기 normal/overflow 페이지보다 먼저 latch된다. 헤더 주소가 우연히 더 큰 VPID를 갖더라도 그렇다. 소스 주석의 근거: 순수 VPID 순서라면 "우선순위 높은 페이지를 굳이 unfix하고 재정렬해서 다시 fix"해야 하는 경우가 생기는데, rank를 우선하면 그 비용을 피할 수 있다. page_buffer.h:219-229

절차 요약(전체 의사코드는 5장):

  1. 이 스레드가 다른 페이지를 하나도 안 쥐고 있으면(또는 대상 페이지만 쥐었으면) UNCONDITIONAL, 아니면 CONDITIONAL로 먼저 시도한다. page_buffer.c:12277-12286
  2. 성공하면 끝 — 이것이 압도적으로 흔한 경로이고 추가 비용이 0이다.
  3. 실패 시: ER_PB_BAD_PAGEID/ER_INTERRUPTED는 그대로 전파, zero-wait 트랜잭션은 ER_LK_PAGE_TIMEOUT으로 포기, 무조건 시도가 실패한 경우는 재시도하지 않는다.
  4. 그 외에는 에러를 지우고 재정렬 시작: 현재 watch 중인 페이지들을 수집하고, 대상 페이지보다 뒤에 정렬되는 것들만 저장한다.
  5. 저장된 페이지들을 unfix한다. MUST unfix 전에 각각 pgbuf_bcb_register_avoid_deallocation을 걸고, holder의 fix_count 횟수만큼 루프 돌며 unfix하며, watcher마다 page_was_unfixed = true를 세운다.
  6. qsort로 (group_id, rank, vpid) 정렬.
  7. 정렬 순서대로 전부 PGBUF_UNCONDITIONAL_LATCH로 재fix한다. 재fix 실패는 ER_PB_ORDERED_REFIX_FAILED. 성공한 것마다 pgbuf_bcb_unregister_avoid_deallocation.
MUST — 호출자에게 전달되는 신호 MUST 재fix가 일어난 모든 watcher에 page_was_unfixed = true를 세운다. 이는 호출자에게 "네 PAGE_PTR가 가리키는 내용이 바뀌었을 수 있으니 상태를 다시 검증하라"는 계약상의 신호다. 오류 반환 시에도 일부 페이지만 재fix된 상태일 수 있으므로, 호출자는 watcher의 pgptr를 쓰기 전에 반드시 확인해야 한다.
승인된 위험 — avoid_dealloc은 victim을 막지 않는다 잠시 unfix된 페이지는 avoid_dealloc 카운터로 vacuum의 논리적 할당 해제로부터만 보호된다. victim화는 막지 못한다 — 소스가 그 불완전성을 명시적으로 수용한다. page_buffer.c:16218-16222
"victimizing a bcb marked to avoid deallocation is not perfectly safe. however, the likelihood of page really getting deallocated is ... almost zero. the alternative ... poses serious risks (what if we leak the counter and prevent bcb from being victimized indefinitely?). so, we prefer the existing risks."
그 귀결로 MUST unregister_avoid_deallocation은 카운터가 0인 경우를 허용하고 assert 대신 로그만 남긴다(페이지가 victim화된 뒤 다시 읽혀 카운터가 사라졌을 수 있으므로). page_buffer.c:16195-16231 이 관대함을 제거하면 정상 워크로드에서 assert가 터진다.

참고 비용(계산값): ordered_holders_info[64]가 스택에 잡히고 각 원소가 watcher 포인터 64개를 품으므로 pgbuf_ordered_fix 프레임은 약 35 KiB의 스택을 쓴다. 재작성 시 스레드 스택 크기 설정에 영향을 준다.
