2장 — Public API 계약

이 장은 page_buffer.h가 내보내는 모든 진입점을 기능군으로 나누어 계약으로 고정한다. 재작성물이 drop-in 교체가 되려면 이 표의 시그니처·의미론·에러 동작을 하나도 빠짐없이 재현해야 한다. 표가 길어지는 것은 정상이다 — 헤더에 있는 것은 전부 누군가가 부르고 있다는 뜻이다.

표 읽는 법
  • 시그니처는 헤더 원형 그대로다. THREAD_ENTRY * thread_p 첫 인자는 지면 절약을 위해 표에서 TE*로 축약했다(원형에서는 항상 THREAD_ENTRY * thread_p).
  • 매크로 간접: CUBRID의 pgbuf API 상당수는 이름이 매크로이고 실제 심볼은 debug/release가 다르다. 비고 칸에 매크로 → _debug / _release로 표기했다. 재작성물은 매크로 이름과 인자 개수를 그대로 유지해야 한다 — 호출부 수만 곳이 그 이름을 쓴다.
  • 스레드 문맥: "워커"는 클라이언트 요청 처리 스레드, "vacuum"은 vacuum 워커, "데몬"은 pgbuf 소유 데몬 4종, "부팅"은 초기화/복구/종료 단일 스레드 문맥을 뜻한다.
  • 모든 규범 문장의 근거는 page_buffer.c:NNNN 또는 page_buffer.h:NNNN 형태로 병기한다.

2.3 (c) ordered fix와 watcher

페이지 latch에 데드락 탐지기가 없으므로(1장 G3), 여러 heap 페이지를 동시에 잡아야 하는 코드는 전역 순서를 지켜야 한다. pgbuf_ordered_fix는 그 순서를 강제하는 장치이며, 필요하면 이미 잡고 있던 페이지를 풀었다가 순서대로 다시 잡는다.

순서 규약 — 정렬 키는 VPID가 아니다

정렬 키는 (group_id, rank, vpid) 3중 튜플이며, group이 NULL인 것은 맨 뒤로 간다. c:12128–12183, :12142–12150

  • group_id = 소속 heap의 헤더 페이지 VPID. PGBUF_WATCHER_SET_GROUP(w, hfid)가 hfid->vfid.volid와 hfid->hpgid로 채운다. HFID가 NULL이거나 불완전하면 group은 NULL VPID. page_buffer.h:97–109
  • rank = PGBUF_ORDERED_HEAP_HDR(0) < PGBUF_ORDERED_HEAP_NORMAL(1) < PGBUF_ORDERED_HEAP_OVERFLOW(2) < PGBUF_ORDERED_RANK_UNDEFINED(3). 즉 헤더가 항상 normal보다, normal이 overflow보다 먼저 latch된다. VPID는 마지막 tiebreak일 뿐이다. page_buffer.h:222–229
  • 적용 대상은 PGBUF_IS_ORDERED_PAGETYPE(ptype) = PAGE_HEAP || PAGE_OVERFLOW뿐이다. page_buffer.h:166–167

MUST 재작성물은 이 3중 키 순서를 정확히 재현해야 한다. 단순 VPID 순서로 바꾸면 헤더 페이지를 놓쳤다 다시 잡는 일이 잦아지고, 헤더 경합이 폭증한다 — 헤더 우선 규칙은 성능 최적화가 아니라 설계 의도다(헤더 주석: "this allows us to keep pages with more priority fixed even when VPID order would require to make unfix, reorder and fix in VPID order", page_buffer.h:219–221).

2.12 계약의 미묘한 지점

아래는 시그니처만 봐서는 절대 알 수 없지만, 틀리면 회귀 테스트가 조용히 실패하는 지점들이다. 재작성 시 각각을 별도 테스트로 고정할 것을 SHOULD 권장한다.

S1 — NEW_PAGE는 디스크를 읽지 않는다. 그런데 hit로 계수된다.

NEW_PAGE fix는 프레임을 확보한 뒤 읽기를 완전히 건너뛰고 메모리에서 LSA를 초기화한다 (영구 볼륨은 NULL LSA + prv.pageid/volid = -1, 임시 볼륨은 temp LSA). c:8543–8567

동시에 show_status->num_hit을 증가시킨다 c:8574–8575. 따라서 insert 위주 워크로드에서 SHOW PAGE BUFFER STATUS의 히트율이 부풀려진다. perfmon 쪽 비율(NUM_FETCHES − NUM_IOREADS)/NUM_FETCHES은 이 문제가 없다. 이것은 재현해야 할 동작이다 — 두 지표가 서로 다른 값을 내는 것 자체가 관측 가능한 현상이다.

S2 — unconditional 요청이 조용히 conditional로 바뀐다

트랜잭션의 wait_msecs가 LK_ZERO_WAIT 또는 LK_FORCE_ZERO_WAIT이면, pgbuf_fix는 호출자가 PGBUF_UNCONDITIONAL_LATCH를 넘겼더라도 프롤로그에서 이를 PGBUF_CONDITIONAL_LATCH로 말없이 바꾼다. c:2273–2283

결과적으로 zero-wait 트랜잭션은 unconditional fix에서도 실패할 수 있고, 그 실패는 ER_LK_PAGE_TIMEOUT으로 보고된다 c:6532. "unconditional인데 왜 실패하는가"는 이것으로 설명된다.

S3 — promote 실패 시 페이지가 unfix되고 포인터가 무효가 된다

pgbuf_promote_read_latch는 실패 시 페이지를 unfix한 상태로 돌아온다. 특히 PGBUF_PROMOTE_SHARED_READER 경로는 대기하러 가기 전에 이미 자신의 fix를 전부 반납하고 홀더 엔트리를 제거한다 — 코드 주석이 "at this point the page is unfixed"라고 못 박는다 c:2937.

MUST 따라서 호출자는 승격 성공 여부와 무관하게 실패 시 페이지 포인터를 다시 쓰면 안 되고, 승격 성공 시에도 대기가 있었다면 페이지 내용이 바뀌었을 수 있음을 가정해야 한다. 이 계약을 어기는 재작성물은 "가끔 다른 페이지를 수정한다"는 형태의 버그를 낳는다.

S4 — NULL 반환이 에러가 아닌 경우들
  • pgbuf_fix(..., OLD_PAGE_IF_IN_BUFFER, ...): 페이지가 버퍼에 없으면 NULL을 반환하지만 에러를 설정하지 않는다. 호출자는 er_errid()를 보지 말고 NULL 자체를 정상 결과로 다뤄야 한다. c:2357–2362
  • pgbuf_set_lsa(): 페이지가 이미 temp LSA를 갖고 있거나, 볼륨이 보조 볼륨 (volid < LOG_DBFIRST_VOLID, 예: copydb/backupdb)이거나, 임시 볼륨이면서 트랜잭션이 활성이면 아무것도 하지 않고 NULL을 반환한다. c:4969–4986
  • pgbuf_fix_if_not_deallocated(): 해제된 페이지에 대해 NO_ERROR와 *page == NULL을 동시에 반환한다. c:15311–15314
  • pgbuf_copy_buffer_alloc(): NULL은 OOM이지만 에러를 설정하지 않는다 — 호출자가 캐싱 없이 진행하도록 설계되어 있다. c:882–885
S5 — latch 타임아웃은 트랜잭션의 대기 시간을 무시한다

페이지 latch 대기 시간은 트랜잭션의 wait_msecs가 아니라 전역 pgbuf_latch_timeout_msecs(PRM_ID_PAGE_LATCH_TIMEOUT_IN_MSECS, 기본 300,000 ms)로 덮어써진다. zero-wait 트랜잭션만 예외다. c:7250–7262, :107, :1673

또한 디버그 빌드에서 무한 대기 트랜잭션의 latch 타임아웃은 살아 있는 /* FIXME: remove it. temporarily added for debugging */ assert (0);에 걸려 서버를 중단시킨다 c:7345–7346. 재작성 시 이 assert를 그대로 둘지는 판단이 필요하지만, 있다는 사실을 모르면 디버그 빌드 스트레스 테스트에서 원인 불명의 abort를 만난다.

S6 — avoid_dealloc은 victim화를 막지 않는다

OLD_PAGE_PREVENT_DEALLOC과 pgbuf_has_prevent_dealloc()이 다루는 표시는 vacuum의 논리적 해제만 막는다. 같은 페이지가 victim으로 뽑혀 다른 VPID로 재사용되는 것은 막지 않는다. 코드 주석이 이 불안전성을 의도적으로 수용한다고 명시한다 — 대안(카운터가 선 BCB의 victim화 금지)은 "카운터가 새면 BCB가 영원히 회수 불가"라는 더 나쁜 위험을 만들기 때문이다. c:16218–16222

이 수용의 직접적 귀결로, 해제 함수는 카운터가 0인 상태를 관용한다 — assert하지 않고 로그만 남긴다. c:16195–16231

S7 — pgbuf_flush는 저자 본인이 쓰지 말라고 한 API다

주석 원문: "caller flushes page but does not really care if page really makes it to disk. or doesn't know what to do in that case… I recommend against using it." c:3517–3518

결과를 알 수 없는 void 반환이므로, 새 코드는 pgbuf_flush_with_wal()을 쓰고 NULL을 검사해야 한다. 그럼에도 기존 호출자가 남아 있으므로 API 자체는 유지해야 한다.

S8 — 매크로 위생: pgbuf_set_dirty_and_free는 감싸여 있지 않다

#define pgbuf_set_dirty_and_free(thread_p, pgptr) pgbuf_set_dirty (thread_p, pgptr, FREE); pgptr = NULL page_buffer.h:388 — do{}while(0)가 없다. 중괄호 없는 if/while 본문에 쓰면 pgptr = NULL이 조건 밖으로 새어 나간다. 같은 헤더의 pgbuf_unfix_and_init, pgbuf_ordered_unfix_and_init, PGBUF_INIT_WATCHER 등은 모두 제대로 감싸여 있어 이 하나만 예외다.

SHOULD 재작성 시 do{}while(0)로 감싼다. 정상 호출부의 동작은 바뀌지 않으며, 잠재 버그만 제거된다.

S9 — pgbuf_simple_fix 계열은 별세계다

임시 파일 읽기 전용 뒷문으로, latch를 걸지 않고 LRU 뮤텍스도 잡지 않으며 fcnt만 조작한다. 헤더 주석의 경고: "Cannot be mixed with general FIX(LATCH)." c:2641–2646

또 하나의 차이: 일반 fix는 첫 unfix 시점에 BCB를 LRU에 넣지만, pgbuf_simple_fix는 fix 시점에 즉시 넣는다(private TOP, 없으면 shared MIDDLE). c:2689–2698

S10 — 릴리스 빌드는 pgbuf_set_lsa에서 dirty를 자동 설정한다

디버그 빌드는 하지 않는다. 코드 주석이 이유를 밝힌다: "누락된 pgbuf_set_dirty 케이스를 찾아 고치고 싶지만, 릴리스에서는 안전을 확보한다." c:5022–5028

따라서 같은 워크로드에서 디버그와 릴리스의 dirty 카운트가 다를 수 있다. 재작성물의 통계 비교 테스트는 반드시 같은 빌드 타입끼리 해야 한다.

S11 — 페이지 해제는 BCB를 무효화하지 않는다

pgbuf_dealloc_page()는 ptype과 pflag를 지우고 DIRTY | MOVE_TO_LRU_BOTTOM을 설정한 뒤 unfix할 뿐, BCB를 invalid 리스트로 보내지 않는다. 무효화하면 동기 flush가 강제되기 때문이다. 대신 페이지는 LRU 바닥으로 가라앉아 비동기 flush와 victim화를 기다린다. c:15127–15131

귀결: 해제된 페이지는 잠시 동안 여전히 해시에서 조회 가능하다. 그래서 OLD_PAGE_DEALLOCATED·OLD_PAGE_MAYBE_DEALLOCATED 같은 fetch mode가 필요하다.
