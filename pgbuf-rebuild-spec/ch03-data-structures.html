3장 — 자료구조 스펙

이 장은 페이지 버퍼가 메모리에 갖는 모든 상태를 규정한다. 필드 하나하나에 대해 타입·역할·누가 보호하는가·초기값을 고정하고, 비트로 압축된 두 워드(flags, atomic_latch)의 배치를 그림과 표로 못박는다. 4장 이후의 모든 알고리즘은 여기서 정의한 필드 이름을 그대로 사용한다.

이 장을 읽는 법 "보호 주체(protected by)" 열이 이 장의 핵심이다. CUBRID 페이지 버퍼에는 하나의 큰 락이 없다. 같은 구조체 안에서도 필드마다 보호 주체가 다르고, 어떤 필드는 의도적으로 보호되지 않는다 (hit_age, 해시 탐색 중의 vpid 읽기). 재작성 시 이 열을 그대로 지키지 않으면 컴파일은 되지만 4장의 동시성 논증이 전부 무효가 된다.

3.1 전역 객체

페이지 버퍼의 전체 상태는 단 두 개의 파일 스코프 정적 객체에 들어 있다. page_buffer.c:845-846

static PGBUF_BUFFER_POOL pgbuf_Pool;              /* 버퍼 풀 전체 */
static PGBUF_BATCH_FLUSH_HELPER pgbuf_Flush_helper; /* neighbor flush 스크래치 */

MUST pgbuf_Pool은 정적 저장 기간을 갖는 단일 인스턴스여야 한다. 동적 할당하거나 인스턴스를 복수로 두면 §3.12의 결함 D2가 실제 크래시로 바뀐다(정적 0-초기화가 버그를 가려주고 있기 때문).

MUST pgbuf_Flush_helper도 단일 전역이다. page_buffer.c:451-458 이는 설계상의 결과를 낳는다 — neighbor flush 배칭은 구조적으로 단일 스레드이며, 두 스레드가 동시에 이웃 배치를 만들 수 없다. 8장의 flush 알고리즘은 이 사실에 의존한다. 이 구조체는 npages, fwd_offset, back_offset, 그리고 2 × PGBUF_MAX_NEIGHBOR_PAGES − 1 = 63칸짜리 pages_bufptr[]/vpids[] 배열로 이뤄진다 (PGBUF_MAX_NEIGHBOR_PAGES = 32, page_buffer.c:310).

3.3 atomic latch word

이 브랜치의 가장 큰 설계 변경. latch 상태 셋이 하나의 64비트 원자 워드에 들어간다. page_buffer.c:365, :499-508

typedef std::atomic<uint64_t> PGBUF_ATOMIC_LATCH;

union pgbuf_atomic_latch_impl
{
  uint64_t raw;
  struct
  {
    PGBUF_LATCH_MODE latch_mode;   /* enum : uint16_t */
    uint16_t         waiter_exists;
    int32_t          fcnt;
  } impl;
};
MUST — enum 폭 고정 MUST PGBUF_LATCH_MODE를 typedef enum : uint16_t {...}로 선언한다. page_buffer.h:190-197 기본 int 폭이면 구조체가 16+32(패딩)+32이 되어 union이 8바이트를 넘고, std::atomic<uint64_t>와의 대응이 깨진다. SHOULD static_assert(sizeof(PGBUF_ATOMIC_LATCH_IMPL) == 8)를 넣어 컴파일 타임에 고정한다.

fcnt는 holder 수가 아니다. 모든 holder의 fix_count 총합이며, 개별 holder->fix_count는 스레드 로컬 메모리에 산다(§3.9). 한 스레드가 같은 페이지를 3번 fix하면 fcnt = 3, holder는 1개다.

do {

MUST — 버킷 수는 고정 MUST 버킷 수는 HASH_SIZE_BITS = 20, PGBUF_HASH_SIZE = 1 << 20 = 1,048,576으로 풀 크기와 무관하게 고정이다. page_buffer.c:295-296, :5631-5642 버퍼가 1,000개든 1,000만 개든 같다. 버킷마다 pthread_mutex_init을 하므로 뮤텍스도 1Mi개이며, 종료 시 1Mi번 pthread_mutex_destroy를 돈다(page_buffer.c:1894-1897).

x86-64 glibc 기준 버킷당 56 B(뮤텍스 40 + 포인터 2개) ⇒ 항상 약 56 MiB 상주. 작은 버퍼 풀을 설정해도 이 비용은 줄지 않는다. 이는 계산값이며, 재작성 시 풀 크기 비례로 바꾸면 동작은 같지만 메모리·시작 시간 특성이 달라져 drop-in 검증이 흔들린다.

해시 함수 — "mirror" 해시. volid의 하위 8비트를 뒤집어서 상위에 놓고 pageid와 XOR한 뒤 20비트로 자른다. page_buffer.c:1522-1553

hash (vpid):
    reversed = 0
    reverse_mask = 1 << (20 - 1)          /* 0x80000 부터 시작 */
    lsb_mask     = 1
    repeat 8 times:                        /* volid 하위 8비트만 */
        if (vpid.volid & lsb_mask) reversed |= reverse_mask
        reverse_mask >>= 1
        lsb_mask    <<= 1
    return (vpid.pageid ^ reversed) & ((1 << 20) - 1)

효과: 한 볼륨 안의 연속 pageid는 연속 버킷에 떨어지고(순차 스캔 시 캐시 지역성), 서로 다른 볼륨은 해시 공간에서 멀리 떨어진다(볼륨 간 충돌 억제). MUST 이 함수를 그대로 재현한다 — 버킷 뮤텍스 경합 패턴이 바뀌면 성능 특성이 달라진다. 유일한 진입점은 PGBUF_HASH_VALUE(vpid)다.

주의 — 별개의 해시 함수가 하나 더 있다 pgbuf_hash_vpid(key, htsize) = (pageid | (volid << 24)) % htsize page_buffer.c:1561-1567는 완전히 다른 함수로, 버퍼 해시가 아니라 AOUT의 MHT_TABLE에만 쓰인다(page_buffer.c:5823). 이름이 비슷해 혼동하기 쉽다 — 둘을 통합하지 말 것.

결함 D2 — direct_victims memset의 잘못된 sizeof

  memset (&pgbuf_Pool.direct_victims, 0, sizeof (PGBUF_VICTIM_CANDIDATE_LIST));
#endif

대상은 PGBUF_DIRECT_VICTIM(포인터 3개 = 24 B)인데 크기는 PGBUF_VICTIM_CANDIDATE_LIST(16 B)에서 온다. 결과적으로 마지막 8바이트 — waiter_threads_low_priority — 가 0화되지 않는다. 이 포인터는 page_buffer.c:1796에서야 대입되는데, 그 전에 goto error가 걸리면 pgbuf_finalize가 쓰레기 포인터를 delete한다 (page_buffer.c:2026-2030).

왜 지금은 터지지 않는가: pgbuf_Pool이 정적 저장 기간이라 최초 진입 시에는 이미 0이다. 따라서 한 프로세스에서 pgbuf_initialize가 두 번째로 호출될 때만 도달 가능하다.

권장 처리: SHOULD 재작성 시 sizeof (PGBUF_DIRECT_VICTIM)으로 바로잡는다. 관측 가능한 동작이 바뀌지 않으므로(0장 방침의 "동작이 바뀌지 않는 결함은 수정") drop-in 검증에 영향이 없다.

이 장에서 정의한 필드 이름과 보호 주체는 4장~8장에서 그대로 쓰인다. 특히 atomic_latch의 세 필드(§3.3)와 flags의 victim 무효 마스크(§3.2.1)는 다음 장의 모든 규칙이 참조하는 기본 어휘다.
