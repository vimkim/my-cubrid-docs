10장 — 구현 로드맵과 수용 검증

이 장의 목표 1~9장이 "무엇을 만들어야 하는가"라면, 이 장은 "어떤 순서로 만들고, 다 만들었는지 어떻게 아는가"다. 17,500줄짜리 모듈을 한 번에 켜서 디버깅하는 것은 불가능하므로, 각 단계마다 실제로 부팅되고 관측 가능한 시스템이 되도록 M0~M7로 쪼갠다. 각 단계는 "이전 단계의 임시 스텁을 무엇으로 두는가"까지 규정한다 — 스텁 설계가 잘못되면 단계 자체가 검증 불가능해진다.
수용 기준의 성격 이 장의 수용 테스트는 정확한 수치 일치가 아니라 관계식(패턴) 일치로 판정한다. 퀴즈 실측치는 CPU·디스크·타이밍·vacuum 진행도에 따라 흔들린다. "2차 스캔의 ioreads가 1차와 거의 같다"는 재현되어야 하고, "917과 914"라는 숫자는 재현될 필요가 없다. 각 퀴즈 행의 판정 기준 열이 그 경계다.

M0 — 자료구조와 생명주기

구현 범위3장 전부: pgbuf_Pool 전 멤버, PGBUF_BCB (flags/latch 워드 비트 배치 포함), 프레임 배열, 해시 테이블(고정 1 Mi 버킷), buffer lock 테이블, invalid list, 홀더 풀, 사이징 공식, pgbuf_initialize의 초기화 순서와 pgbuf_finalize의 역순 해제.
선행없음. 이 단계는 외부 모듈 계약을 거의 쓰지 않는다 (thread_num_total_threads(), 파라미터 읽기 정도).
완료 판정서버가 부팅해서 pgbuf_initialize를 통과하고 pgbuf_finalize까지 도달한 뒤 정상 종료한다. 이 시점에는 어떤 페이지도 fix되지 않으므로 부팅 후반(볼륨 마운트, 로그 읽기)에서 죽는 것이 정상이다 — 죽는 위치가 pgbuf 밖이면 M0 통과다.
스텁pgbuf_fix는 assert(false) + NULL 반환. victim/flush/perfmon 계열은 빈 함수. 단, 시그니처는 2장 계약대로 전부 존재해야 링크가 된다 — M0의 실질 산출물의 절반은 "page_buffer.h가 내보내는 모든 심볼의 정의"다.
함정(1) 해시 테이블은 풀 크기와 무관하게 고정 1 Mi 버킷 + 1 Mi 뮤텍스다 — 약 56 MiB가 항상 잡히고 종료 시 1 Mi번의 pthread_mutex_destroy가 돈다. "풀 크기에 비례"로 잘못 구현하면 소형 data_buffer_size에서 해시 충돌이 폭증해 M3 이후의 성능 관측치가 전부 어긋난다. (2) PGBUF_BCB에 std::atomic이 들어 있으므로 초기화는 memset이 아니라 placement_new다. (3) num_buffers의 하한은 PGBUF_MINIMUM_BUFFERS = MAX_NTRANS × 10이다.

M1 — 단일 스레드 fix/unfix

구현 범위5장의 hit 경로와 miss 경로: 해시 조회 → 히트면 fix count 증가, 미스면 프레임 확보 → buffer lock → fileio_read → 해시 삽입 → unlock. pgbuf_unfix의 fix count 감소. fetch 모드 4종(OLD_PAGE* / NEW_PAGE)의 분기. latch는 아직 없다 — 단일 스레드이므로 모든 요청을 즉시 승인한다.
선행M0. 외부 계약: fileio_read, TDE 복호화(9.4), dwb_read_page(9.2.4)를 이 단계에서 이미 붙인다 — 나중에 끼워 넣으면 miss 경로를 다시 쓰게 된다.
완료 판정SA 모드(cubrid createdb, csql --SA-mode)로 DB 생성과 기본 DDL/DML/SELECT가 통과한다. SA 모드는 스레드가 하나이고 private LRU가 강제로 0개이므로 page_buffer.c:13918, M3 이전 단계를 검증하기에 딱 맞는 환경이다.
스텁victim = invalid list만. 즉 "빈 BCB가 없으면 실패"로 두고, data_buffer_size를 워크로드보다 크게 잡아 회피한다. 이 스텁이 성립하는 이유는 M1의 목표가 "쫓아내지 않아도 되는 소형 워크로드에서 fix/unfix가 정확한가"이기 때문이다. LRU 리스트 삽입은 no-op으로 두고, unfix 시 BCB를 VOID zone에 그냥 남긴다. flush는 pgbuf_flush_all*만 얕게 구현(전수 스캔 + 동기 쓰기)해 종료 시 데이터가 남게 한다.
함정(1) buffer lock을 M1부터 넣어야 한다. 단일 스레드에서는 무의미해 보이지만, "같은 VPID를 두 스레드가 동시에 miss"라는 상황의 자료구조(팻말과 대기 큐)를 나중에 끼워 넣으면 miss 경로 전체가 재작성된다. (2) NEW_PAGE는 디스크를 읽지 않는다 — 그리고 hit로 집계된다(D6d, §10.6). (3) 임시 볼륨 페이지는 읽은 뒤 LSA가 temp sentinel이 아니면 다시 찍고 dirty로 표시한다.

M2 — latch·대기·무잠금 fast path

구현 범위4장 전부와 5장의 latch 부분: 64-bit atomic latch 워드, 승인 규칙 표, 대기 큐(next_wait_thrd), pgbuf_block_bcb / pgbuf_timed_sleep / pgbuf_wakeup_reader_writer, 타임아웃(page_latch_timeout_in_msecs, 기본 300초), read→write promote, 그리고 무잠금 read fast path.
선행M1. 외부 계약 9.6.3(suspend/resume 프로토콜)이 여기서 처음 필요해진다.
완료 판정다중 세션 read/write 혼합 워크로드에서 페이지 내용 손상 0, 데드락/영구 대기 0. quiz 02: 수백 회 fetch 후 Num_data_page_fixed 게이지가 0~2로 돌아온다.
스텁M1의 스텁 유지(victim = invalid list). LRU는 여전히 no-op. 즉 이 단계의 워크로드도 풀보다 작아야 한다.
함정(1) 무잠금 fast path의 안전 논증(4장)을 구현이 실제로 만족하는지 확인할 것 — "BCB를 읽고 → VPID 확인 → CAS로 fcnt 증가 → VPID 재확인"의 재확인 단계를 빼면 ABA로 엉뚱한 페이지를 준다. (2) 대기자가 있는 BCB를 기상시킬 때 waiter_exists 비트를 정리하지 않으면 CREATE INDEX 라이브락이 재현된다 — 원본이 주석으로 이 버그를 기록해 두었다 page_buffer.c:10944-10953. (3) 기상 후 resume_status 검사(계약 N9-11)를 빼면 인터럽트를 성공으로 오해한다.

M3 — LRU zone·private/shared·quota

구현 범위6장 전부: zone 1/2/3 경계 계산과 전이, 삽입 3종(top/middle/bottom), 제거, tick 회계, private/shared 배정, pgbuf_adjust_quotas, private→shared 이사, AOUT 구조(비활성 상태로).
선행M2. 외부 계약 9.6.1(세션이 private 인덱스를 소유)이 필수 — 이게 없으면 quiz 05/08의 격리가 재현되지 않는다.
완료 판정quiz 05·06·07·08의 패턴이 재현된다(§10.3). 특히 quiz 08("이웃 세션의 대량 스캔 후에도 내 재스캔 miss 0")은 private 리스트와 quota가 동시에 맞아야만 나오는 결과라 단일 지표로 강력하다.
스텁victim은 여전히 단순화 가능하다: "자기 private list의 bottom부터 non-dirty를 선형 탐색"만 있으면 quiz 05·06·08이 전부 돈다. lock-free 큐, direct victim, 3단계 탐색은 M4로 미룬다. flush는 M1 수준(flush_all) 유지 — dirty가 쌓이면 그냥 실패시키고 워크로드를 read 위주로 짠다.
함정(1) private list의 zone 비율은 파라미터와 무관하게 5%/5%/90% 고정이다 page_buffer.c:14390-14391. lru_hot_ratio/lru_buffer_ratio는 shared list에만 적용된다. 이걸 private에도 적용하면 quiz 05의 "자기가 자기를 쫓아냄"이 훨씬 늦게 일어난다. (2) zone 1 unfix는 아무 조작도 하지 않는다 — hit 등록만 하고 끝난다. "LRU니까 top으로"를 넣으면 quiz 06의 keep ≫ to_top이 무너진다. (3) AOUT은 구현하되 max_count == 0으로 전부 꺼진 채여야 한다(D7). 그 결과 모든 새 페이지가 private TOP으로 들어가고 middle 삽입 코드는 도달 불가가 된다 — 이것이 정상이다.

M4 — victim과 direct victim

구현 범위7장 전부: pgbuf_get_victim의 3단계 탐색 (자기 private → 남의 private → shared), restrict_other 규칙, 리스트 스캔(MAX_DEPTH = 1000), lock-free 순환 큐 3종, direct victim 배급/소비/무효화, 대기 큐 2종(high/low)과 기아 방지(매 4번째는 low 우선, low 포화 시 승격).
선행M3. 외부 계약 9.5(vacuum은 high priority)를 여기서 붙인다.
완료 판정quiz 09: 모든 후보가 dirty인 압박 상황에서도 시스템이 ER_PB_ALL_BUFFERS_DIRTY 없이 진행한다. Num_victim_assign_direct_flush > 0으로 "flush → 직접 배급" 경로가 실제로 탄 것을 확인한다.
스텁여기서 순서가 뒤집힌다: direct victim은 flush 데몬(M5)이 있어야 완결된다. M4 단계에서는 배급자(donor)를 unfix 경로와 clean 후보 발견 경로로만 두고, "모든 후보가 dirty"인 워크로드는 M5까지 미룬다. 즉 M4의 판정은 "3단계 탐색과 큐가 정확한가"까지이고, quiz 09의 완전 재현은 M5 이후다.
함정(1) big_private_lrus_with_victims 큐는 생산자가 없다(D4). 소비 후 되넣는 produce 하나뿐이라 이 큐는 영원히 비어 있고, over-quota 스레드의 2단계 탐색은 항상 NULL을 받아 shared로 직행한다. 충실 재현 대상 — "버그 같으니 채워 넣자"고 하면 victim 분포가 달라져 quiz 05/08의 수치가 바뀐다. (2) pgbuf_direct_victims_maintenance의 두 루프는 진입 즉시 종료한다(D3). index = prv_index로 초기화한 뒤 index != prv_index를 조건으로 걸었기 때문이다. pgbuf-maintain 데몬이 하는 두 일 중 하나가 통째로 no-op이라는 뜻이다. (3) victim 후보 정의는 zone3 ∧ non-dirty다. SHOW의 동명 컬럼은 정반대(D6c).

M5 — dirty·WAL·flush 데몬

구현 범위8장의 flush 부분: pgbuf_set_dirty/pgbuf_set_lsa와 oldest_unflush_lsa 회계, pgbuf_bcb_flush_with_wal(단일 쓰기 관문), pgbuf_bcb_safe_flush_internal의 즉시/지연 판정과 ASYNC_FLUSH_REQ, pgbuf_flush_victim_candidates, 데몬 4종, 토큰 버킷 연동, 이웃 flush.
선행M4. 외부 계약 9.1(WAL), 9.3(write mode), 9.6.4(데몬 인프라)가 전부 필요하다.
완료 판정quiz 03·04 재현. 그리고 WAL 순서 위반 0: 디버그 빌드에서 "쓰기 직전 logpb_need_wal(page_lsa)가 참인데 쓴다"를 assert로 잡고 장시간 워크로드를 돌린다(§10.2 R6).
스텁DWB는 아직 붙이지 않아도 된다 — double_write_buffer_size=0으로 꺼 두면 flush 경로가 fileio_write(FILEIO_WRITE_DEFAULT_WRITE) 한 갈래로 단순해진다. checkpoint는 pgbuf_flush_all로 대체해 두고 M6에서 교체한다.
함정(1) flush는 BCB의 프레임이 아니라 스택 사본에서 나간다. 사본을 뜬 뒤 BCB mutex를 놓고 쓰기 때문에, 쓰는 도중 재수정이 가능하고 그것이 의도다 (mark_is_flushing이 DIRTY를 미리 끄는 이유). (2) WRITE latch를 쥔 채로도 flush가 허용된다 — 단 그 latch 홀더가 자신일 때만. (3) flush 데몬의 "히트율 낮음" 술어는 99.9% 미만이면 참이다 (PGBUF_DESIRED_HIT_VS_MISS_RATE = 1000). 현실적인 미스율에서는 항상 참이라 page_flush_interval_in_msecs=0이어도 데몬이 계속 돈다. (4) 매 victim flush 패스마다 ER_NOTIFICATION_SEVERITY 레코드 2개가 서버 에러 로그에 찍힌다 — 파라미터와 무관하게. 로그 diff 시 이걸 노이즈로 오해하지 말 것.

M6 — checkpoint와 DWB 연동

구현 범위8장의 checkpoint 부분과 9.2: pgbuf_flush_checkpoint(BCB 테이블 전수 스캔 → 수집 → (volid,pageid) 정렬 → 배치 flush), PGBUF_SEQ_FLUSHER와 rate control(burst 16장, 최대 1.5초 양보), smallest_lsa 산출, flush_all 3변종, DWB 2단계 프로토콜, pgbuf_invalidate_all(DWB 복구가 부른다).
선행M5. 계약 N9-3(checkpoint 출력·fsync 소유권), N9-4~N9-7(DWB).
완료 판정quiz 10·11 재현. 그리고 crash-restart 정합: 워크로드 중 SIGKILL → 재기동 → DWB 복구 경로가 돌고(에러 로그 확인) 데이터 검증 쿼리가 통과한다(§10.4).
스텁없음 — 이 단계는 앞 단계 스텁을 제거하는 단계다. M1의 얕은 flush_all을 정식 구현으로, M5의 flush_all 대체 checkpoint를 정식 seq flusher로 교체한다.
함정(1) checkpoint는 Num_data_page_flushed를 올리지 않는다(D6b). 그 카운터는 victim flusher 전용이다. (2) checkpoint의 Num_log_wals는 정확히 +1이다 — 시작할 때 한 번만 logpb_flush_log_for_wal(flush_upto_lsa)를 부르기 때문. 페이지마다 부르면 +수백이 된다. (3) checkpoint는 이미 clean한 페이지도 일부러 다시 쓴다(순차 구간을 끊지 않으려고). "clean이면 건너뛰기"로 최적화하면 iowrites가 줄어 diff가 깨진다. (4) checkpoint와 victim flusher는 서로 양보한다: checkpoint는 victim flush 중 최대 1.5초 대기, victim flusher는 checkpoint 중 10× 부스트를 끈다. (5) DWB on이면 iowrites가 페이지당 2다(D6a) — 구현이 아니라 DWB 쪽 집계다.

M7 — 관측 가능성과 quirk

구현 범위9.7~9.10 전부: 모든 PSTAT_* 증가 지점, activation flag 게이트 위치, per-thread 통계 샤드, pgbuf_peek_stats, SHOW PAGE BUFFER STATUS의 두 스캔, 파라미터 30여 개 반영, 그리고 §10.6의 quirk 전부.
선행M6.
완료 판정동일 워크로드에서 원본 빌드와 재작성 빌드의 statdump 델타 및 SHOW 출력이 일치한다(§10.4의 허용 오차 내). quiz 12의 트레이서를 재이식해 이벤트 시퀀스가 같은 모양으로 나온다.
스텁없음.
함정카운터를 "고치고 싶은" 충동이 최대가 되는 단계다. D6의 네 건은 전부 충실 재현이 기본값이다 — 자세한 근거는 §10.5.

10.2 런타임 불변식 체크 목록

10.4 drop-in 등가성 체크

원본 page_buffer.c를 재작성본으로 바꿔 넣었을 때, 외부에서 구별할 수 없는가를 본다. 같은 하드웨어·같은 DB·같은 워크로드로 두 빌드를 각각 돌려 아래 5종을 비교한다.

(1) statdump 카운터 diff

# 두 빌드에서 동일 워크로드 실행 후
cubrid statdump quizdb > before.txt   # watcher 켠 상태에서 전/후 델타를 뜰 것
# ... 워크로드 ...
cubrid statdump quizdb > after.txt
diff <(delta before.txt after.txt) <(delta before_ref.txt after_ref.txt)
카운터군허용 오차이유
Num_data_page_fetches, Num_data_page_dirties0 (완전 일치) 워크로드가 결정적이면 fix/set_dirty 호출 횟수는 구현과 무관하다
Num_data_page_ioreads±수 % 교체 정책이 같으면 거의 같지만 타이밍·vacuum 개입으로 흔들린다
Num_data_page_iowrites, Num_file_iosynches±10~20% flush 시점은 데몬 타이밍에 좌우된다. 비율(DWB on/off 2배 관계)이 유지되는지가 핵심
Num_unfix_* 전수분포 형태 일치 절대값이 아니라 "어느 분기가 지배적인가"가 같아야 한다. lru1_keep이 최대이고 aout_found가 0인 형태(§10.3 quiz 06·07)
Num_victim_*분포 형태 일치 own_private_success 우세, Num_lfcq_big_private_lists는 항상 0(D4)
Num_log_walscheckpoint 구간은 정확히 +1 구현 차이가 즉시 드러나는 지표
게이지류(lru1/2/3, private_quota)같은 자릿수 스냅샷이라 순간값은 다르다. quota 산식이 같은지만 본다

(2) SHOW PAGE BUFFER STATUS diff

19개 컬럼을 같은 시점(예: 동일 워크로드 종료 직후 + 5초 안정화)에 떠서 비교한다. SHOULD 특히 다음 세 컬럼을 확인:

  • Victim_candidate_pages — zone3 ∧ dirty 정의여야 한다. statdump의 Num_data_page_victim_candidate(zone3 ∧ non-dirty)와 값이 다른 것이 정상(D6c). 두 값이 같아졌다면 정의를 "고쳐 버린" 것이다.
  • Num_pages_written — DWB on에서 Num_data_page_iowrites보다 훨씬 작아야 한다(D6a).
  • Hit_rate — insert-heavy 구간에서 statdump 기반 히트율 (1 − ioreads/fetches)보다 높게 나와야 한다(D6d, NEW_PAGE 집계).

(3) 에러 로그 비교

로그기대
ER_LOG_FLUSH_VICTIM_STARTED / _FINISHED victim flush 패스마다 2개가 ER_NOTIFICATION_SEVERITY로 찍힌다 — log_pgbuf_victim_flush 파라미터와 무관하게. 두 빌드에서 발생 빈도의 자릿수가 같아야 한다
ER_PB_ALL_BUFFERS_DIRTY정상 서버 워크로드에서 0회
ER_LOG_CHECKPOINT_SKIP_INVALID_PAGE0회 — 나오면 LSA 회계가 깨진 것
er_log_debug "flushing page %d|%d to disk without logging" 드물게 나오는 것이 정상. 폭증하면 oldest_unflush_lsa 갱신이 빠진 것

(4) crash-restart 정합

1. 대량 UPDATE 워크로드 실행 (dirty가 충분히 쌓이도록)
2. checkpoint 직후가 아닌 임의 시점에 서버 프로세스 SIGKILL
3. 재기동 — 부팅 로그에서 DWB 복구 경로가 돌았는지 확인
4. 데이터 검증 쿼리(체크섬성 집계) 결과가 crash 이전 커밋 상태와 일치
이 테스트가 실제로 무엇을 잡는가 DWB 복구 경로는 pgbuf에 단 하나의 요구를 한다: pgbuf_invalidate_all (thread_p, NULL_VOLID) (계약 N9-7). 이것이 빠지거나 dirty를 flush해 버리면, DWB가 디스크에 다시 쓴 수리된 페이지를 버퍼에 남아 있던 복구 이전 사본이 덮어써서 손상이 되살아난다. crash-restart 없이는 이 결함을 절대 발견할 수 없다 — MUST M6의 필수 관문.
double_write_buffer_size=0(DWB off)으로도 한 번 돌려 두 경로를 모두 확인할 것.

(5) 성능 스모크 — 무잠금 fast path 확인법

재작성에서 가장 조용히 사라지는 것이 무잠금 read fast path다. 기능 테스트는 전부 통과하는데 처리량만 떨어진다. 카운터로 직접 확인한다:

지표확인법기대
Num_data_page_hash_anchor_waits extended_statistics_activation에 PB_HASH_ANCHOR(0x08)를 켜고 (기본값 15에 이미 포함) 읽기 전용 hot 워크로드를 다중 세션으로 돌린다 fetch 수 대비 무시할 수준. 이 값이 fetch에 비례해 늘면 fast path가 없어 매 hit마다 해시 버킷 뮤텍스를 잡고 있다는 뜻
Data_page_fix_lock_acquire_time_msec같은 워크로드에서 비교 원본과 같은 자릿수. 급증하면 락 경합
perf record / perf top hot 워크로드 중 프로파일 pthread_mutex_lock이 상위에 없어야 한다. 상위에 있으면 fast path 미구현 또는 조건이 너무 좁다
세션 확장성1 → 2 → 4 → 8 세션으로 hot read 처리량 측정 원본과 같은 기울기. fast path가 없으면 4세션 이후 평평해진다

D1flush_with_wal early return 2곳이 FLUSHING_TO_DISK 누수 → BCB 영구 victim 불가 + flush 대기자 미기상 Medium수정 없음. 발생 조건이 "TDE 로드됨 + 암호화/DWB 슬롯 실패"로 희귀해서 정상 워크로드에서는 경로 자체를 타지 않는다. 카운터·로그 diff 무영향. 불변식 R7이 잡는 결함이므로, 충실 재현하면 assert가 자기 구현을 때린다 — 재현할 이유가 없다
D2direct_victims memset의 잘못된 sizeof (PGBUF_VICTIM_CANDIDATE_LIST 16B로 PGBUF_DIRECT_VICTIM 24B를 지움) Low (latent)수정 없음. 재작성 코드는 애초에 이 memset을 그대로 옮길 이유가 없다 (sizeof pgbuf_Pool.direct_victims 또는 멤버별 초기화). 동작이 관측 가능하게 바뀌지 않는다
D3pgbuf_direct_victims_maintenance의 두 루프가 index != prv_index 때문에 진입 즉시 종료 → 문서화된 backup plan이 무동작 Medium1차: 충실 재현 (별도 커밋으로 수정 검토) 있음. 루프를 살리면 pgbuf-maintain 데몬이 100ms마다 실제로 victim을 배급하게 되어 Num_victim_assign_direct_* 분포와 대기 시간이 달라진다. quiz 09의 assign_direct_flush 비중이 눈에 띄게 감소한다. 먼저 재현해 등가성을 확보한 뒤 별도로 고칠 것
D4big_private_lrus_with_victims 큐에 생산자 없음 → over-quota 스레드의 2단계 탐색 무효Low충실 재현 큼. 큐를 채우면 victim 출처 분포가 바뀌어 quiz 05·08의 격리 특성이 달라진다. Num_lfcq_big_private_lists가 0이 아니게 되는 것만으로 statdump diff가 깨진다. 큐와 카운터는 존재하되 항상 비어 있는 상태로 구현할 것
D5double_write_buffer_size=2M 같은 크기 접미사를 거부하고 서버 부팅 실패Low (usability)범위 밖 — 그대로 없음. system_parameter.c는 재작성 대상이 아니다. 재작성자는 "바이트 정수로 쓴다"만 알면 된다. 고치려면 PRM_SIZE_UNIT과 PRM_DIFFER_UNIT을 함께 달고 변환 함수 쌍을 추가해야 한다 (9.8 참조) — 별도 티켓
D6관측 카운터 의미 불일치 4건: (a) DWB 이중 집계 (b) flushed 편향 (c) SHOW victim 정의 상충 (d) NEW_PAGE 히트 집계Low (observability) 전부 충실 재현 결정적. 네 건 모두 관측값 그 자체다. 하나라도 고치면 statdump/SHOW diff가 반드시 틀어지고, 운영 중인 모니터링 대시보드의 기준선이 깨진다. (c)는 "이름이 같은데 정의가 정반대"라 재작성자가 통일하고 싶어지는 대표적 함정 — §10.6 참조. 개선하려면 새 컬럼/새 카운터를 추가하는 방향이어야지 기존 의미를 바꾸면 안 된다
D7"LRU + Aout of 2Q" 주석 vs AOUT 강제 비활성 — 사용자 설정이 경고 없이 무시됨Info (doc gap)그대로 + 문서화 없음(pgbuf 쪽은). 강제 0은 system_parameter.c가 한다. pgbuf는 max_count == 0에서 전 기능이 꺼지도록만 구현하면 된다. 개선안(설정 무시 시 경고 로그)은 근본 원인 CBRD-20741과 함께 다룰 일
D8pgbuf_peek_stats 헤더 선언의 파라미터 이름 stale Cosmetic수정 없음. 헤더 주석 수준. 재작성 시 정의와 같은 이름을 쓰면 자동 해결
기본 규칙 — 한 문장 동작이 관측되지 않는 결함(D1, D2, D8)은 고치고, 관측되는 결함(D3, D4, D6)은 먼저 재현한다. D5·D7은 pgbuf 밖이라 선택의 여지가 없다.
D3·D4·D6를 고치고 싶다면 등가성 검증을 통과한 뒤 별도 커밋으로 — 그래야 "성능/동작 변화가 재작성 때문인가 결함 수정 때문인가"를 나눌 수 있다.

10.6 재작성자가 놓치기 쉬운 quirk 체크리스트

전부 충실 재현 필수 항목이다. 각 항목은 "직관적으로 고치고 싶어지지만 고치면 관측값이 바뀌는" 것들이다. 구현 후 이 목록을 하나씩 짚어 볼 것.

□quirk왜 틀리기 쉬운가확인법
1NEW_PAGE fix가 hit로 집계된다 page_buffer.c:8574-8575 디스크를 읽지 않았으니 hit가 맞아 보이지만, "캐시에 있어서 안 읽었다"와 "애초에 존재하지 않아서 안 읽었다"는 다르다. insert-heavy에서 Hit_rate가 과대해진다 대량 INSERT 후 SHOW의 Hit_rate > statdump 기반 히트율
2unconditional → conditional 강등이 존재한다 어떤 조건에서 무조건 요청이 조건부로 낮춰진다(5장 결정 트리). "무조건인데 왜 실패하지?"로 보여 제거하기 쉽다5장의 강등 조건 표를 코드와 1:1 대조
3대기자가 있으면 LRU 훅을 생략한다 page_buffer.c:6662, 6674 unfix의 boost/zone 조정은 is_zero_fcnt이고 블록된 reader/writer가 없을 때만 돈다. "어차피 unfix니까 항상"으로 짜면 zone 분포가 달라진다 경합 워크로드에서 Num_unfix_lru*_to_top 비중 비교
4AOUT 강제 비활성 — 모든 새 페이지가 private TOP으로 middle 삽입 코드가 도달 불가라는 사실을 모르면 "scan resistance가 왜 middle 삽입으로 안 되지?"를 며칠 뒤진다 Num_unfix_void_to_private_mid = 0, aout_found = 0
5pgbuf_direct_victims_maintenance는 no-op(D3) 주석이 "backup plan"이라고 설명해서 동작한다고 믿게 된다 데몬 주기(100ms)에 맞춘 victim 배급 증가가 없어야 한다
6big private 큐는 항상 비어 있다(D4) 큐와 카운터가 멀쩡히 존재해서 "왜 안 차지?"로 오해 Num_lfcq_big_private_lists 항상 0, PSTAT_PB_LFCQ_LRU_PRV_GET_BIG 항상 0
7DWB on이면 iowrites가 페이지당 2(D6a) "쓰기 카운터가 2배로 이상하다"며 한쪽을 빼고 싶어진다. DWB 파일 쓰기와 원위치 쓰기를 각각 세는 것이 현재 의미다 quiz 11의 on/off 비교 — 약 2배 관계
8Num_data_page_flushed는 victim flusher 전용(D6b) "flush량"으로 읽으면 checkpoint가 통째로 빠진다. checkpoint 경로에 카운터를 추가하고 싶어진다 quiz 10 — checkpoint +206 iowrites에 flushed +0
9checkpoint의 Num_log_wals는 정확히 +1 WAL을 페이지마다 강제하도록 짜면 수백이 된다. checkpoint는 시작할 때 한 번 민다 quiz 10
10flush 데몬의 "히트율 낮음"은 99.9% 미만 (PGBUF_DESIRED_HIT_VS_MISS_RATE = 1000) "저 히트율"이라는 이름과 달리 사실상 항상 참이다. page_flush_interval_in_msecs=0이어도 데몬이 쉬지 않는다 0으로 설정하고 CPU 사용/flush 발생을 관찰
11zone 1 unfix는 아무 조작도 하지 않는다 LRU라면 top으로 옮겨야 할 것 같지만, 가장 뜨거운 페이지는 어차피 victim이 안 되므로 리스트 뮤텍스 비용을 없앤 것이다 quiz 06 — lru1_keep ≫ to_top
12private list의 zone 비율은 5%/5%/90% 고정 page_buffer.c:14390-14391 lru_hot_ratio/lru_buffer_ratio가 shared에만 적용된다는 것을 놓치면 private가 거대한 victim zone이라는 성질이 사라진다 quiz 05·12 — 새 페이지가 TOP에 꽂혀도 금방 zone 3으로 떨어진다
13victim 후보 정의가 두 개: 내부 = zone3 ∧ non-dirty, SHOW = zone3 ∧ dirty(D6c) 이름이 같아 통일하고 싶어진다. 실제로는 "지금 가져갈 수 있는 것"과 "flusher가 노릴 것"이라는 서로 다른 질문의 답이다 두 값이 달라야 정상
14flush는 스택 사본에서 나가고, 쓰는 동안 BCB mutex는 풀려 있다 "쓰는 동안 잠가야 안전"으로 짜면 flush가 fix 경로를 막아 처리량이 급락한다 flush 중 같은 페이지 fix가 블록되지 않는지 확인
15일반 읽기 경로에 torn 검사가 없다(9.2.6) "안전하니까"로 추가하기 쉽다. 검사는 수리 가능한 곳(DWB 복구)에만 있다 fileio_is_page_sane 호출 지점이 5곳을 넘지 않는다
16이웃 flush는 clean 페이지도 일부러 쓴다 (/* flush even if it is not dirty. todo: is this necessary? */) 원저자도 의문을 남겼지만 현재 동작이다. 제거하면 iowrites가 줄어 diff가 깨진다 data_buffer_neighbor_flush_nondirty=true에서 비교
17checkpoint는 clean 페이지도 재flush하고, 한 패스에서 같은 페이지를 두 번 쓸 수 있다순차 구간을 끊지 않으려는 의도적 낭비다 quiz 10의 iowrites가 dirty 페이지 수보다 많다
18victim flush 패스마다 에러 로그 2줄 "로그 노이즈"로 보여 파라미터 게이트를 걸고 싶어지지만, 현재는 무조건 찍힌다 에러 로그 라인 수 비교
19통계 샤드는 비원자적이고 캐시라인 정렬이다(계약 N9-13) "경쟁 조건"으로 보여 atomic으로 바꾸고 싶어진다. 의도적 설계다(CBRD-26898) 다중 세션 hot read 처리량 비교
20release/debug의 dirty 마킹 의미가 다르다 — pgbuf_set_lsa의 자동 dirty 표시는 #if defined(NDEBUG)에서만 디버그 빌드에서만 assert가 터지는 현상의 원인. 의도적으로 "debug는 누락된 set_dirty를 버그로 드러내고 release는 안전하게" 두 빌드 모두에서 회귀 테스트를 돌린다

10.7 완료 선언 기준

이 책의 재작성이 "끝났다"는 것
  1. M0~M7 전부 통과 — 각 단계의 완료 판정이 재현 가능하게 문서화되어 있다.
  2. quizzes 12종의 판정 기준(§10.3.2 오른쪽 열) 전부 충족 — 절대 수치가 아니라 관계식으로.
  3. drop-in 등가성 5종(§10.4) 통과 — 특히 crash-restart와 무잠금 fast path 확인.
  4. 디버그 빌드에서 R1~R18 assert를 켠 채 전체 회귀 스위트가 통과한다.
  5. quirk 체크리스트 20항목을 한 번씩 확인했다 — 각 항목의 "확인법"을 실제로 실행해서.
  6. D1·D2·D8은 수정, D3·D4·D6는 재현된 상태다(§10.5). 수정한 것이 있다면 별도 커밋으로 분리되어 있다.
여섯 번째가 특히 중요하다. "고쳐 놓고 재작성 탓으로 오해되는" 변경이 하나라도 섞이면 등가성 검증의 신뢰가 통째로 무너진다.
