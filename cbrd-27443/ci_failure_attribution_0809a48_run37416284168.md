## 관련이 의심되는 두 TC의 확인 방법

### bug_xdbms_sus1416: master 프로세스 선택

관찰된 직접 실패 원인은 메모리 증가가 아니라 **복수 RSS 값을 단일 숫자로 계산한 것**이다. 기존 TC는 `ps ux` → `grep master` → RSS 추출을 사용한다. [Engine master relay 설정](https://github.com/CUBRID/cubrid/blob/0809a480df55ac6767a905d03fa3d31edd40a93c/src/executables/master.c#L1813)의 console log 이름이 이 검색에 걸릴 수 있다.

다음 확인: 매칭된 PID와 전체 command line을 기록하여 relay 포함 여부를 확인하고, 실제 master PID만 선택해 기존 메모리 증가 기준으로 평가한다. 추가 PID가 relay가 아니거나 정확한 master PID에서도 증가가 발생하면 현재 가설을 수정해야 한다. 현재 로그만으로 메모리 누수라고 판단할 수 없다.

### bug_bts_5244: 세션 종료 dump 출력 위치

기존 TC는 서버 시작·종료를 포함한 subshell 출력을 `test.log`에 모은 뒤 `SESSION COUNT = 0`이 정확히 한 번 있는지 검사한다. [변경된 서버 console 출력 경로](https://github.com/CUBRID/cubrid/blob/0809a480df55ac6767a905d03fa3d31edd40a93c/src/executables/util_service.c#L1846)와 [종료 시 session dump 호출](https://github.com/CUBRID/cubrid/blob/0809a480df55ac6767a905d03fa3d31edd40a93c/src/session/session.c#L631), [stdout 출력](https://github.com/CUBRID/cubrid/blob/0809a480df55ac6767a905d03fa3d31edd40a93c/src/session/session.c#L2286)을 함께 보면, dump가 console log로 옮겨졌을 가능성이 있다.

다음 확인: 정상 종료 여부와 caller log / server console log 양쪽을 확인하고 JDBC 테이블 생성·연결 오류도 조사한다. 정상 종료 후 양쪽 모두 dump가 없거나 별도 초기화 실패로 검사 전제가 성립하지 않았다면 출력 위치 변경만으로 설명할 수 없다. 현재 로그만으로 세션 누수라고 판단할 수 없다.

## 판단의 한계와 후속 조치

- 실패 shell 4개의 testcase 디렉터리는 base/private revision `9e9f773d128833aa9e808776ec124ba056bb7bc1`과 PR/private revision `c1a50b94f72e4e16bea866c60378a5a5a6b4bd16` 사이에서 동일하다. 전체 CI 환경까지 동일하다는 뜻은 아니다.

- 같은 testcase revision·설정으로 비교했을 때 head에서만 추가 문제가 드러나거나 core의 실제 원인이 달라지면 비관련 판단을 재검토해야 한다. 특히 기존 hash join assertion crash는 실제 Engine 문제이므로 별도 조사 대상이다.
- Base에서만 실패한 TDE `file_enc_05`는 현재 실패 목록에 없다. 따라서 전체 실패 수는 12 → 13이지만 추가된 실패는 위 2개다.
- 수정한 CBRD-27443 신규 TC는 정확한 `c1a50b94f`에서 4/4 통과했다. 축소된 shell/CCI 검증 범위의 통과이며 과거 Python suite 전체 coverage를 다시 입증한 것은 아니다.
