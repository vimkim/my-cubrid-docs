\[CBRD-27443 검토 결과\] develop c63a3b993, debug 빌드 실측

1\. 이슈 분석 중 타당한 부분 (develop에서 재현)

-   cub_server와 cub_pl이 호출자의 잠금 FD를 유지합니다. 서버를 띄우는 proc_execute_internal()과 PL을 띄우는 create_child_process()에 FD 정리가 없는 것이 원인입니다.

-   server stop 자체는 FD를 유출하지 않습니다. cubrid server stop \| cat 은 바로 끝나며, stop이 멈추는 것은 앞선 start가 남긴 잠금이나 파이프를 기다리기 때문입니다.

2\. 다시 살펴봐 주셨으면 하는 부분

-   \"master에는 이미 정리 코드가 있다\"는 전제를 다시 확인해 주시면 좋겠습니다. util_service는 master를 띄우기 전에 NO_DAEMON=true를 설정하므로, 정리 코드가 있는 css_daemon_start()가 실행되지 않습니다. master가 없는 상태에서 server start를 하면 cub_master도 잠금 FD를 쥐고, 서버를 멈춘 뒤에도 service stop 전까지 잠금이 풀리지 않습니다. 재현 스크립트는 master가 이미 떠 있는 상태를 전제로 해서 이 부분이 드러나지 않았으므로, master가 없는 조건도 재현에 넣어 주시면 좋겠습니다.

-   파이프 대기를 이번 이슈의 핵심 원인으로 다뤄 주시면 좋겠습니다. cubrid server start fdtest \| cat 은 명령이 1\~3초 만에 끝나도 reader가 끝나지 않습니다. 파이프의 쓰기 쪽은 cub_server와 cub_pl이 쥐고 있고, 그 명령이 master를 새로 띄웠다면 cub_master도 쥡니다. 데몬 모드 master(cub_master \| cat)도 같은 이유로 끝나지 않는데, css_daemon_start()가 FD 3 이상만 닫고 0/1/2는 남기기 때문입니다. 따라서 master 방식(FD 3 이상 정리)만으로는 파이프 대기가 해결되지 않습니다. 표준 입출력 처리 정책을 TBD로 두지 말고 이번 수정 범위에 넣어 검토해 주시면 좋겠습니다.

-   \"master가 부모인 재기동은 조건이 다르다\"는 판단을 다시 살펴봐 주시면 좋겠습니다. master가 호출자의 FD를 이미 물려받은 상태이므로, master가 다시 띄우는 서버와 PL에도 같은 FD가 전달됩니다(4번 HA 실측 참고).

3\. 함께 확인해 주셨으면 하는 부분

-   NO_DAEMON으로 뜬 master는 setsid()를 하지 않아 호출자의 프로세스 그룹에 남습니다. 그래서 호출자의 timeout이 만료되면 master도 함께 종료되고 서버만 남습니다. HA에서는 이것이 master 종료로 이어지므로 별도 이슈로 검토해 주시면 좋겠습니다.

-   cub_pl은 cub_server 내부의 FD(서버 에러 로그, 액티브 로그 볼륨 \_lgat 등)도 물려받습니다. 내부 FD에 close-on-exec를 적용하는 보완책도 함께 검토해 주시면 좋겠습니다.

-   이슈의 분석과 테스트는 feat/oos 기준입니다. develop에서도 같은 현상이 재현된다는 점을 이슈에 적어 주시면 좋겠습니다.

4\. HA 관점 (single-node HA, cubrid heartbeat start 실측)

-   cub_master, cub_server, cub_pl이 모두 잠금 FD를 쥡니다.

-   cub_server를 kill -9로 종료하면 heartbeat가 재기동하는데, 새로 뜬 cub_server와 cub_pl도 같은 잠금을 쥡니다. master를 통해 FD가 다시 전달되기 때문입니다.

-   cubrid heartbeat stop 이후에도 master가 잠금을 유지합니다. HA에서는 master를 거의 내리지 않으므로 잠금이 사실상 계속 붙잡힙니다.

-   2-node 구성의 copylogdb와 applylogdb는 실측하지 않았으며, 같은 함수를 거치므로 결과도 같을 것으로 예상합니다. 수정본 검증 항목에 넣어 주시면 좋겠습니다.
